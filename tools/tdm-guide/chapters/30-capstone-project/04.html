30.7 Deliverables

The BU SME evaluates deliverables, so decide early what you will hand over. A reasonable set, kept in one folder with the activity number in each file name:

  • Progress log: the daily entries from the plan.
  • Per activity: inventory export, algorithm or entity configuration, query and shell output, job summaries or reports, and a decision note per column or table.
  • Algorithm sheet: one line per column: algorithm, parameters, reason, and "docs" or "design".
  • Final report (two to four pages): scope, approach, results against each acceptance criterion, warnings and how they were explained, limits, and what you would do next, following the assessment report outline.
  • Presentation for Day 57, following the slide outline in the same chapter.

30.8 What evaluators look for

The syllabus describes the evaluation only as the BU SME judging the deliverables; I have no marking scheme, so this section is my general reading of what a reviewer of masking work needs to see, not a published rubric. Four things recur.

  1. Proof, not claims. Each acceptance criterion has a query result or report next to it. A statement such as "SSN is masked" without a before/after comparison counts for little.
  2. Understanding of why. You can say why you chose an algorithm, what it guarantees (deterministic, unique, format-keeping) and what it does not (for example, that the FirstName algorithm can return the input, or that nothing I read says CM Digits yields valid SSNs).
  3. Integrity and safety. Keys and joins survive, the same value masks the same way in the database and the file, nothing real is left behind, and the work was done on a restorable copy.
  4. Honesty about limits. Warnings are explained, assumptions and design choices are labelled, and open items are listed. Separating documented fact from your own choice is a strength, not a weakness.

30.11 Common mistakes and gotchas

Where capstones lose marks
  • Masking a key to "be safe". It breaks joins. Leave keys alone unless the same deterministic algorithm is applied on both sides.
  • Different algorithms for the same value. An SSN masked differently in the database and the file ruins consistency; reuse one instance.
  • Numeric columns and leading zeros. Digit masking on a numeric zip or tax id can collide; keep such values as text or use the numeric algorithm.
  • Trusting profiling for six-digit postal codes. The documented ZIP data patterns target US formats; the column name does the work.
  • A subset left unmasked. It is real data; say how it will be masked.
  • Presenting design choices as product facts. "CM Digits is the SSN algorithm" is false; "I chose CM Digits for SSN because..." is right.

30.12 Recap

Recap
  • The project has three activities: names, subset, and SSN, alphanumeric values, TaxID and ZipCode. Plan them over daily steps and log progress every day.
  • Use Delphix for the masking activities and Informatica for the subset, with the other tool as a cross-check and GenRocket for fake source rows; follow your trainer if the assignment differs.
  • Every activity has acceptance criteria that a query or report can prove.
  • Format-preserving, deterministic algorithms (CM Digits, CM Alpha-Numeric, a Character Mapping instance with a preserve range, or Informatica key masking with a mask format and seed) keep shape and consistency. Segment Mapping and Informatica SSN masking are documented alternatives with their own limits.
  • Integrity means both intact foreign keys and the same value masked the same way in every system.
  • A subset is real data until it is masked.
  • Label every decision as documented or designed, and explain every warning.
