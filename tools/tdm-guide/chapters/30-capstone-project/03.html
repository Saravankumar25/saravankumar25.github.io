30.6 Activity 3: profile and mask SSN, alphanumeric values, TaxID and ZipCode

Brief

Goal. Mask four kinds of identifying value so the data stays useful: formats are kept, the same real value always becomes the same masked value, and keys and joins still work. Inputs. CUSTOMERS with ssn, membership_code, tax_id and zip_code; the customer extract customers.dat (which carries the SSN); the "before" copy; and the edge row 1004 with SSN N/A. Tool. Delphix primary; Informatica as a cross-check. Output. Four verified columns, an algorithm sheet where every line says "docs" or "design", and the evidence.

The word "integrity" has two meanings here, and you must show both. Referential integrity: foreign keys still match. None of these four columns is a key, so the safest decision is not to mask any key at all. Consistency: the same SSN or TaxID appears in several places (the database and the extract file) and must mask to the same value everywhere, or joins between systems fail. Deterministic algorithms, with the same algorithm instance and key used everywhere, give consistency.

Algorithm design, column by column

The table separates what the sources say from what I chose. The default algorithm for the SSN, ZIP and TAX_ID domains is not stated in the Delphix pages I read; look at Settings, Domains on your engine and decide whether to keep or replace each default.

To create the custom instances in the UI (Settings, Algorithms, + Algorithm): enter a unique name, choose the Character Mapping framework, add the character group, tick Case Sensitive if relevant, set Minimum Masked Positions, and add the preserve range. Through the API the shape is as below. The framework ids differ between engines, so look them up first with GET /algorithm/frameworks; the field names are from the documentation examples.

{ "algorithmName": "SS_ZipKeepRegion", "algorithmType": "COMPONENT",
  "frameworkId": <Character Mapping id>,
  "algorithmExtension": { "caseSensitive": true, "characterGroups": ["0123456789"],
    "minMaskedPositions": 1, "preserveLeadingZeros": false,
    "preserveRanges": [ { "start": 0, "length": 3, "direction": "FORWARD" } ] } }

{ "algorithmName": "SS_SSN_Seg", "algorithmType": "COMPONENT",
  "frameworkId": <Segment Mapping id>,
  "algorithmExtension": { "autoIgnoreCharacters": true, "allowShortSegments": false,
    "segments": [ { "length": 3, "segmentType": "MASK_NUMERIC" },
                  { "length": 2, "segmentType": "MASK_NUMERIC" },
                  { "length": 4, "segmentType": "MASK_NUMERIC" } ] } }

The Segment Mapping sketch masks the three groups of digits separately and ignores the dashes. Left at its default ranges it may produce area numbers such as 000, which real SSNs never use. Restricting ranges is possible (the docs describe input and mask value ranges), but if input and mask ranges differ, values outside the input range are left unmasked and the mapping is no longer reversible for tokenization, so test it before relying on it.

Steps

  1. Profile and review.

    Run a profiling job over the rule set (Lab 5). By the published ASDD patterns, ssn and tax_id are found by column name and type, zip_code by name (its data rule targets US 5-digit and ZIP+4 values, so six-digit codes will not match by value), and membership_code, with no matching name, probably not at all. Assign it by hand.

    An inventory listing four columns with a domain or a manual note, and a log of what the profiler missed.

  2. Create the custom algorithm instances (zip, tax_id, and optionally membership_code with prefix kept), and record the exact configuration in the algorithm sheet.
  3. Assign the algorithms in a rule set that holds only these four columns, with Enable Automatic Updates off.
  4. Mask the extract file with the same SSN algorithm.

    Use the file route of Lab 6 (format file, flat-file rule set, inventory) and assign the same algorithm instance to the ssn field. Using the identical instance is what makes the database and the file agree.

  5. Snapshot, run the job, then run the file job. Read the execution summary: the planted N/A SSN should produce a non-conformant warning (CM Digits needs at least one digit; see the algorithms and masking jobs chapter).
  6. Verify with the queries below and save the output.

SELECT COUNT(*) FROM customers WHERE customer_id <= 1003 AND membership_code !~ '^[A-Z]{2}-[A-Z0-9]{6}$';

Expect criteria A3-2 to A3-5 to count 0 for the "bad" queries. Query 2 shares the earlier caution: an equal value is not strictly impossible for every algorithm. For Character Mapping the docs say the masked value never matches the input when at least one maskable character is present, so any match there is a finding. Evidence: the inventory CSV, algorithm sheet, query and shell output, the warning log rows (patterns only), a screenshot of each custom algorithm's configuration, and the leak-search output.
