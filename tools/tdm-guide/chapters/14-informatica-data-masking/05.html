Choosing a technique: questions to ask

  • Does the test environment need this column at all? If not, nullification is the simplest and safest.
  • Does the application check a format (SSN pattern, card checksum, phone layout, URL)? Use the matching built-in technique (SSN, SIN, credit card, phone, email, IP, URL) so the checks pass.
  • Does it need real-looking text such as names and places? Substitution (new values from a dictionary) or shuffle (existing values moved between rows).
  • Is the value an identifier that appears in several tables and must stay joinable? Use key masking with the same seed, or rely on auto cascade for keys with constraints, or repeatable substitution with the same seed (14.4, 14.5).
  • Is it a number or date where only "near the original" matters? Random masking with blurring.
  • Do you need to undo the masking later? Format preserving encryption, knowing the privacy trade-off.
  • Does a masked value depend on more than one column? An advanced rule, or a mapplet if PowerCenter logic already exists.

14.8 Advanced masking rules in depth

An advanced rule is a small program built from columns of three types (User Guide 10.5.10, p.137 to 138, p.156 to 158) From docs: input (receives the source value), variable (a scratch column that holds an intermediate result from an expression or a masking technique, so you can combine several techniques) and output (the target column that receives the final value). Column names inside the rule are your own; at assignment time you map them to real columns.

Worked example: first names by gender and nationality (guide)

The guide's name example (p.177 to 182) keeps gender and nationality: a dictionary with SNO, COUNTRY, GENDER, FIRSTNAME; a string substitution rule with Lookup column GENDER; then an advanced rule with inputs in_Country, in_FirstName, in_Gender, variable columns var_FirstName_us (condition in_Country='us') and var_FirstName_jp (condition in_Country='jp') that each apply the substitution rule, and output o_FirstName. A condition on a variable column lets one rule choose a different substitution per row.

Worked example: shuffle addresses, keep ZIP (guide)

The shuffle address example (p.183 to 189) shuffles address lines together and leaves ZIP unmasked: a Random, Constrained shuffle rule, then an advanced rule where v_AddressLine3 applies the shuffle with lookup column i_ZIP, and v_AddressLine1 and v_AddressLine2 use dependent masking on it so they follow the same row.

14.9 Custom rules: mapplets and the Data Masking transformation

Three parts: what a mapplet is, a worked build in PowerCenter, and how Test Data Manager uses a mapplet once it exists. The build follows the LearningMart video "How to create mapplet in informatica"; the TDM side follows the User Guide.

The general idea From video

A transformation in PowerCenter is one processing step on rows of data (calculate, look up, mask). In the LearningMart video "How to create mapplet in informatica", the presenter defines a mapplet as a reusable object that you create in the Mapplet Designer. His motivating case: many mappings must join first name and last name into a full name, so you build that logic once and reuse it everywhere, like a function you write once and call from many programs. A mapplet therefore has input ports, some transformations inside, and output ports. A Data Masking transformation applies masking techniques to a port; a mapplet that contains one is how you bring a PowerCenter masking technique into TDM.

Mistakes this video's steps guard against
  • Forgetting the Mapplet Output: the mapplet has nothing to return.
  • Using a mapplet without validating it first.
  • Making the full_name port too small for a joined value.
  • Choosing the wrong load type when the target has a primary key (the video says Normal).
  • Leaving out the space, which gives "AshaMenon".

From PowerCenter mapplet to TDM rule From docs

Steps 8 to 11 above build a mapping and workflow by hand. TDM does not need those, because the PowerCenter Integration Service creates the mappings, transformations, mapplets, sessions and workflows itself when a plan runs, and the guide warns that editing generated components in the PowerCenter Client may give unexpected results (User Guide 10.5.10, p.141, p.150). What TDM needs is the mapplet. So the sequence is: build and validate the mapplet in PowerCenter (steps 1 to 7), export it to an XML file from the PowerCenter repository, then import it in Test Data Manager as a rule (p.137, p.140).

In the wizard you mark at least one input and one output column as mandatory, so for the video's mapplet you might mark first_name and full_name (p.141). When you assign the rule you link source columns to the input ports and the output port to a column (p.142 to 143).

The video's mapplet contains only an Expression, so it combines values and masks nothing. For masking, the guide says to include one or more Data Masking transformations in the mapplet and that all transformations must be passive (p.150); it does not show how to configure one. The guide's own full-name example is on the generation side: a custom generation rule from a mapplet that combines first and last name from an EMPLOYEES table (User Guide 10.5.10, p.196, p.211; see the Informatica data generation chapter). That is the closest fit for this mapplet.

What the guide says From docs

  • Purpose. Mapplet rules let you use PowerCenter masking techniques that are "not available in Test Data Manager" (p.150). The mapplet holds the logic to mask the input columns and return data to the target columns (p.137, p.152).
  • How it gets in. You export the mapplet to an XML file from the PowerCenter repository or the Model repository, then import it as a rule (p.137, p.140). To mask Hadoop data you import mapplets built in the Developer tool (p.137). The TDM repository stores the mapplet logic, and you cannot change the mapplet inside Test Data Manager (p.137).
  • What it must contain. One or more Data Masking transformations, and all transformations must be passive (they must not add or remove rows) (p.137, p.150). It can have multiple input and output columns (p.137).
  • Required ports. Mark at least one input and one output column as mandatory; mandatory columns need source and target assignments (p.137, p.141, p.155).
  • Custom masking parameters (p.156): Column Name, Column Type (input or output), Data Type, Precision, Mandatory, Group Name (input, output or another name you gave in the mapplet).
  • Exporting the other way. You can also export rules as PowerCenter mapplets (p.150).
  • Assignment. Select the rule in the Masking Rule column, then link source columns to rule input ports and rule output ports to source columns (p.142 to 143). Sybase to Hadoop limit: 20 columns.
  • Hadoop engine limits. A Blaze engine allows Expression, Data Masking, Case Converter, Comparison, Decision, Labeler, Merge, Parser, Weighted Average, Standardizer and Java Passive transformations in a mapplet rule; Spark allows Expression, Data Masking and Java Passive; Hadoop mapplets cannot use sequence generator, lookup or classifier (p.62, p.137).
  • Changes. If you change the name or type of a field of a custom rule, existing assignments do not see it; import the mapplet again (p.144).
  • Data Masking transformation session properties (chapter 3, p.52 to 53): SSN High Group File path, DMO Cache Directory, Cache Size (default 8 MB), Shared Storage Table (default disabled) and Storage Commit Interval (default 100,000).

The architecture behind it, with PowerCenter running the workflows that TDM generates, is in the Informatica overview and architecture chapter. Video: "How to create mapplet in informatica" by LearningMart.
