Choosing a technique: questions to ask

  1. Does the test environment need this column at all?

    If not, nullification is the simplest and safest.

  2. Does the application check a format (SSN pattern, card checksum, phone layout, URL)?

    Use the matching built-in technique (SSN, SIN, credit card, phone, email, IP, URL) so the checks pass.

  3. Does it need real-looking text such as names and places?

    Substitution (new values from a dictionary) or shuffle (existing values moved between rows).

  4. Is the value an identifier that appears in several tables and must stay joinable?

    Use key masking with the same seed, or rely on auto cascade for keys with constraints, or repeatable substitution with the same seed (14.4, 14.5).

  5. Is it a number or date where only "near the original" matters?

    Random masking with blurring.

  6. Do you need to undo the masking later?

    Format preserving encryption, knowing the privacy trade-off.

  7. Does a masked value depend on more than one column?

    An advanced rule, or a mapplet if PowerCenter logic already exists.

The tool-neutral reasoning behind these choices is in the masking concepts chapter. If you meet the same ideas in Delphix, the equivalent algorithms are in the Delphix algorithms and masking jobs chapter.

14.8 Advanced masking rules in depth

An advanced rule is a small program built from columns of three types (User Guide 10.5.10, p.137 to 138, p.156 to 158) From docs: input (receives the source value), variable (a scratch column that holds an intermediate result from an expression or a masking technique, so you can combine several techniques) and output (the target column that receives the final value). Column names inside the rule are your own; at assignment time you map them to real columns.

PropertyForMeaning
Column Name, Column Type, Datatype, Precision, Scale, Mandatoryinput, variable, outputGeneral properties. Mandatory means the column must be assigned to a source column in every project (input and output only)
Expressionvariable, outputAn expression built in the Expression Builder

Worked example: a masked full name

The guide's example (p.158) builds a masked full name from first and last name, and it fits ShopSphere. Say the target has a full_name column derived from first_name and last_name:

Result for customer 1001, illustrative: input Asha and Menon; variables Divya and Iyer; output "Divya Iyer". The guide's advice: build expressions by point-and-click to minimise errors, and check that the expression returns the output column's datatype.

Worked example: first names by gender and nationality (guide)

The guide's longer example (p.177 to 182) preserves gender and nationality when masking first names. In outline: (1) add a dictionary in Administrator | Dictionaries with columns SNO, COUNTRY, GENDER, FIRSTNAME (sample rows: 1, US, M, Adam; 2, US, F, Sarah; 3, JP, M, Mahito; 4, JP, F, Kyoko); (2) create a standard string substitution rule with Override Allowed, Masked Value FIRSTNAME, Lookup column GENDER and a serial number column; (3) create an advanced rule with inputs in_Country, in_FirstName, in_Gender; variable columns var_FirstName_us (condition in_Country='us') and var_FirstName_jp (condition in_Country='jp'), each applying the substitution rule with Repeatable Output and Unique Substitution Data overridden on, lookup column in_Gender and input column in_FirstName; and an output column o_FirstName using in_FirstName as conditional input. The lesson: a condition on a variable column lets one advanced rule choose a different substitution for different rows.

Worked example: shuffle addresses, keep ZIP (guide)

The other long example (p.183 to 189): you want to shuffle address lines but leave ZIP unmasked and keep each address's lines together. Create a string shuffle rule with Shuffle Type Random and Constrained, then an advanced rule with inputs i_AddressLine1, i_AddressLine2, i_AddressLine3, i_ZIP. A variable v_AddressLine3 applies the shuffle rule with lookup column i_ZIP. Variables v_AddressLine2 and v_AddressLine1 use dependent masking on v_AddressLine3, with dictionary columns i_AddressLine2 and i_AddressLine1, so they follow the same row. Output columns repeat the dependent settings. The ShopSphere parallel would be shuffling a street, city and state together while keeping zip_code as is.

14.9 Custom rules: mapplets and the Data Masking transformation

This is the Day 54 topic "masking rules, algorithms, mapplet creation, using transformations". I will separate three things: what the guide says, what it does not say, and the general idea.

What the guide says From docs

  • Purpose. Mapplet rules let you use PowerCenter masking techniques that are "not available in Test Data Manager" (User Guide 10.5.10, p.150). The mapplet holds the logic to mask the input columns and return data to the target columns (p.137, p.152).
  • How it gets in. You export the mapplet to an XML file from the PowerCenter repository or the Model repository, then import it in Test Data Manager as a rule (p.137, p.140). To mask Hadoop data you import mapplets built in the Developer tool (p.137). The TDM repository then stores the mapplet logic, and you cannot change the mapplet inside Test Data Manager (p.137).
  • What it must contain. One or more Data Masking transformations, and all transformations must be passive (they must not add or remove rows) (p.137, p.150). It can have multiple input and multiple output columns (p.137).
  • Required ports. Mark at least one input and one output column as mandatory; mandatory columns need source and target assignments when you assign the rule (p.137, p.141, p.155).
  • Custom masking parameters (p.156): Column Name, Column Type (input or output), Data Type, Precision, Mandatory, Group Name (input, output or another name you gave in the mapplet).
  • Single port mapplets. For one input and one output port you may use the same source port for both; you can do this for several ports at once when assigning (p.150).
  • Exporting the other way. You can also export rules as PowerCenter mapplets (p.150).
  • Assignment. Select the rule in the Masking Rule column, then link source input columns to rule input ports and rule output ports to source columns (p.142 to 143). Sybase to Hadoop limit: 20 columns.
  • Hadoop engine limits. With a Blaze engine a mapplet rule may use Expression, Data Masking, Case Converter, Comparison, Decision, Labeler, Merge, Parser, Weighted Average, Standardizer and Java Passive transformations. With Spark: Expression, Data Masking and Java Passive. Importing mapplets to mask Hadoop data cannot use sequence generator, lookup or classifier transformations (p.62, p.137).
  • Lookups in plans. If a mapplet rule contains multiple Lookup transformations, the plan shows a Mapplet Settings section where you choose a connection type and value for each (p.281). A lookup connection also appears in source settings (p.295).
  • Update strategy. If an imported mapplet contains a transformation set to define the update strategy, the default Treat source rows as option is Insert (p.286 to 287). The plan Advanced Options include a Mapplet setting to reuse or replace mapplets in PowerCenter (p.287).
  • Changes. If you change the name or type of a field of a custom rule, existing assignments do not see it; import the mapplet again (p.144).
  • The Data Masking transformation's session properties (User Guide chapter 3, p.52 to 53): SSN High Group File path, DMO Cache Directory (dictionary cache, default $PMCacheDir), Cache Size (default 8 MB; recommended minimum 32 MB for 100,000 records), Shared Storage Table (default disabled; enable it when two transformations or ports use the same dictionary column, connection, seed and locale) and Storage Commit Interval (default 100,000 rows).
  • What TDM generates itself. When you run a masking plan, the PowerCenter Integration Service creates mappings, transformations, mapplets, sessions and workflows in the PowerCenter repository. The guide warns that if you edit these generated components in the PowerCenter Client, the session might give unexpected results (p.150).

What the guide does not say

The guide tells you to export a mapplet that contains Data Masking transformations; it does not teach how to build one in PowerCenter Designer or the Developer tool. There are no steps for creating the mapplet, no list of the Data Masking transformation's port properties or its masking types, and no example of a finished mapplet in the chapters I read. It points to PowerCenter documentation for that. So "mapplet creation" in the syllabus, as a click-by-click task, is outside this guide; ask your trainer which PowerCenter material your course uses.

The general idea General concept

This paragraph is explanatory background and is not from the guide. A transformation in PowerCenter is one processing step on rows of data (calculate, look up, filter, mask). A mapplet is a reusable bundle of such steps with defined input and output ports, which you can drop into many mappings, like a function you write once and call from many programs. A Data Masking transformation is the PowerCenter step that applies masking techniques to a port, and TDM's built-in techniques are the same family of logic exposed through a form. So a mapplet rule means "run my own bundle of steps instead of one built-in technique": for example check a country code first, then mask the phone number differently per country, then write two output columns.
