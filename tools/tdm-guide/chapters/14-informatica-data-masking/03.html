14.6 The masking techniques, one by one

The guide lists these techniques (User Guide 10.5.10, p.152 to 153): Advanced, Credit card, Email address, Encryption, Expression, IP address, Key, Mapplet, Nullification, Phone, Random, Shuffle, SIN, SSN, Substitution and URL. Advanced and Mapplet are about combining or importing logic and get their own section (14.8 and 14.9). The other fourteen follow here. For each I give: what it does, when to use it, parameters, a ShopSphere before and after, gotchas and repeatability.

How to read the before and after tables

The "before" values are the fake ShopSphere sample data. The "after" values are illustrations I made up to show the kind of result; the tool generates its own values, and its output will differ on your machine. Where the guide gives its own example I use it and say so. Techniques that need a column ShopSphere does not have (credit card, IP address, URL) use the guide's example.

Substitution masking

What it does. Replaces a value with a "similar but unrelated" value looked up in a dictionary, a flat file or database table of replacement values (User Guide 10.5.10, p.176 to 177) From docs. Works on date, numeric and string columns. The guide calls it an effective way to replace production data with realistic test data; its examples are a dictionary of addresses, or the InvalidSSN dictionary of Social Security numbers that are not valid.

Use it for names, cities, product names, anything where realism matters: testers see "Divya Iyer", not "XQWZ KLPT". The Day 55 lab uses it.

Gotchas.

  • Choose Unique Substitution Data only if the dictionary is bigger than the number of distinct values in the column. A dictionary of 4 names cannot uniquely replace 20 customers; the operation fails.
  • Two customers with the same first name get the same replacement only if Repeatable Output is on (the storage table remembers pairs). Without repeatability, each row can get a different value.
  • You cannot use flat-file dictionaries and unique substitution to mask Hadoop data, and a Spark engine cannot do shuffle or substitution at all (p.176, p.62).
  • Dictionaries are added in Administrator | Dictionaries, as relational (pick connection, datasource, table) or flat file (choose file, optionally overwrite an existing file in the LkpFiles directory, pick the encoding) (p.178).

Repeatability. Tick Repeatable Output and set a seed. Name the storage connection in the plan.

Shuffle masking

What it does. Swaps values of one column between rows of the same table. The guide's example (p.173) uses four rows: Tom Bender, Sue Slade, Bob Bold, Eli Jones. After a shuffle of the first-name column they read Bob Bender, Eli Slade, Tom Bold, Sue Jones. You can restrict which values may be swapped by a lookup condition or a constraint. Works on date, numeric and string columns From docs.

Use it for columns where realistic, real-looking values are wanted and the connection between the value and its person is what you must break, for example last names, cities, salary amounts (the distribution stays the same).

Gotchas.

  • Shuffle does not invent new values. Every masked value is a real value from production. For a column with mostly unique values (SSN, phone) that may not satisfy a privacy reviewer; for names it is usually acceptable. This is my judgement, General concept, not a statement from the guide.
  • It cannot be used for XSD sources, and not when both source and target are Hadoop HDFS connections (p.135, p.173). A Spark engine cannot do it (p.62).
  • Empty strings: set Null and Empty Spaces to Treat as Value, or the empty columns are skipped (p.173).
  • With JDBC connections the Content Management Service cannot create reference tables when a Varchar or Varchar2 column has precision above 2000, or a Char column above 1000. The workflow then resets precision to 2000 and 1000 and data can be truncated (p.174).
  • Shuffling several related columns independently breaks their relationship, for example an address line moving away from its city. The guide's shuffle address example (14.8) uses an advanced rule so address lines move together and the ZIP code stays unmasked.

Repeatability. Random shuffle can be random; Representative with a seed gives repeatable output; the guide says you can configure shuffle to be random or repeatable.

Key masking

What it does. Produces deterministic results: the same source value, rule and seed always give the same masked value. Works on date, numeric and string columns (User Guide 10.5.10, p.164 to 168) From docs.

Use it for identifiers: tax IDs, account numbers, primary and foreign keys, and for text where you want the shape kept (letters stay letters, digits stay digits) but the content changed. The Day 56 lab (alphanumeric text) uses this.

The mask format characters (shared with random masking; p.165):

CharMeans
AAlphabetical, ASCII a to z and A to Z

If no mask format is given, each source character is replaced with any character. A mask format longer than the input is truncated; shorter than the input means the characters at the end are not masked. Lowercase letters you type are converted to uppercase (p.164).

Other forms the guide describes.

  • Result characters: to limit output to uppercase A to F enter ABCDEF. With Use only A, B, c the word "horse" might become "BAcBA"; with Use all except the output never contains A, B or c (p.166). To avoid two inputs giving the same output, use a wide set of replacement characters or mask only a few characters (p.165).
  • Delimited strings: the guide's example masks "John Donne" consistently when it appears as the strings John and Donne in two columns and as "Donne, John" or "John Donne, General Manager" in two more. Assign delimited string masking with comma and space as delimiters to the last two (p.166 to 167).
  • Dates: output dates fall between 1753 and 2400 and are always valid. A leap year maps to a leap year; a 31-day month to a 31-day month; February stays February (p.167). Give the same seed as another column to get matching dates.
  • Numbers: to keep a primary-key to foreign-key relationship intact between two tables, give the key column in each table the same seed. Deterministic output means 1001 in CUSTOMERS and 1001 in ORDERS both become the same new number (p.167).

Gotchas. Output uniqueness is not guaranteed when the set of source characters is smaller than the set of result characters (p.165). The Case Insensitive option is easy to misread: by default a masked character may differ from the original only in case ("x" becomes "X"), and with the option on, the rule treats both cases as the same character so it cannot do that. If the same name appears in different cases in different tables ("John Brown", "JOHN BROWN") and you want identical masked output, convert the source to one case first with a preprocessing expression (p.166).

Repeatability. This is the technique whose whole purpose is determinism. Same seed, same rule, same input gives the same output.

Random masking

What it does. Produces random, non-repeatable output: the same source value and rule can give a different result each run. No seed. Works on date, numeric and string columns (User Guide 10.5.10, p.169 to 173) From docs.

Use it for columns where consistency across tables is not needed, or where you want a controlled range: dates of birth shifted a little, amounts that stay near the original, partial zip codes.

Gotchas. Because there is no seed, a rerun produces different values, and values for the same customer in two tables will not match. Numeric output depends on column precision (p.172). The mask format rule that a short format leaves trailing characters unmasked applies here too: a 6 digit zip with format +++DD would leave the last digit as it was.

Repeatability. None by design ("non-repeatable"). If you need repeatable output choose key masking, or substitution or expression masking with repeatable output.
