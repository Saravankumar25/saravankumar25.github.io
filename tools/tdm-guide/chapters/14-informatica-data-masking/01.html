14.1 Words to know first

Masking technique
The logic that replaces a value, such as "pick a name from a list" (substitution) or "swap values between rows" (shuffle).
Masking parameters
The options of a technique, such as the dictionary to use, the seed, or the range of dates allowed.
Masking rule
A technique plus its parameters, saved under a name. "FirstName_Substitution" is a rule. The same technique with different parameters is a different rule.
Data domain
A named group of columns that mean the same thing (for example "Social Security Number"), found by patterns in the data or in column names. You can attach preferred masking rules to it.
Policy
A bundle of data domains (and so their rules) that you reuse across projects. It holds no data source itself.
Deterministic / repeatable
The same input always gives the same masked output, so "Asha" becomes the same fake name in every table and in every run.
Seed
A starting number that makes repeatable output reproducible. Same seed, same rule, same input, same result.
Dictionary
A flat file or database table of replacement values used by substitution, for example a list of first names.
Mapplet
A reusable group of PowerCenter transformations with input and output ports. TDM can import one as a custom masking rule.
Value cascade / auto cascade
Ways to make related columns receive the same masked value: a value cascade for similar columns you group by hand, an auto cascade for primary and foreign keys.

14.2 The big picture: rules, domains, policies and assignments

Six objects and how they connect

Start with the ShopSphere problem. Your CUSTOMERS table has first name, last name, email, phone, SSN, date of birth, zip code and tax ID, all sensitive. You do not want to configure "how to mask an SSN" nine times in nine projects. TDM lets you define it once and reuse it. The guide's building blocks (User Guide 10.5.10, p.71 to 73, p.135 to 138, p.149 to 150) From docs:

You can create rules, domains and policies in any order. The guide's high-level policy task flow (p.72): create masking rules, define data domains, assign the rules to the domains, create a policy, assign the domains to the policy. You can apply the rules to source columns, data domains, policies and plans (p.136).

Data domains and preferred rules

A data domain (User Guide 10.5.10, p.73 to 76) From docs "represents the functional meaning of a column based on the column data or the column name". The guide's SSN example: social security numbers may sit in a column called SSN, in another table's SOCIAL_SECURITY and even in a COMMENTS column. You define a data expression for the format (regular expression [0-9]{3}-[0-9]{2}-[0-9]{4}) and metadata expressions for column names such as .*SSN* and .*SOCIAL*. Data discovery profiles (see the Informatica discovery and profiling chapter) use these patterns to assign domains to columns; without Data Discovery you assign columns by hand (p.73). Link back to discovery: profiling finds the sensitive columns, domains carry the rule to them.

When you attach masking rules to a domain they are called preferred rules. If you attach several, one is the default rule, applied to all columns of the domain, and you can change an individual column to another preferred rule (p.73). The guide's example: a Last_Name domain with shuffle as the default and substitution as another preferred rule for a different table.

TDM ships three policy packs, PII, PHI and PCI, each listing domains with a default rule (p.77 to 80). The PII pack, for example, pairs First Name Domain with First Name Rule, Phone Domain with Phone Number Rule and Social Security Number Domain with Social Security Number Rule. The guide does not say which technique each default rule uses, so open a rule in your install to see.

The task flow

A masking plan must contain at least one rule or one policy (User Guide 10.5.10, p.135). The PowerCenter Integration Service does the masking when the workflow runs. If a plan has both subset and masking components, subsetting happens first (p.275), as in the Informatica data subset chapter. Plans are explained in the Informatica plans, workflows and warehouse chapter, and the screens in the Informatica TDM tour.
