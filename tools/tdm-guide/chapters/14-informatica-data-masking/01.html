The previous chapters showed how to find sensitive columns (the Informatica discovery and profiling chapter) and how to cut production down to a small consistent slice (the Informatica data subset chapter). This chapter is about the step that makes the slice safe to hand to testers: data masking, which means replacing real sensitive values with realistic fake ones, so a tester sees "Divya Iyer" where production has "Asha Menon" and nothing in the test environment can identify a real person. The general idea, and why regulations care, are in the masking concepts chapter. Here we look at exactly how Informatica TDM does it.

Why you care: masking is the part of Informatica TDM that most job tasks and interviews ask about. In the syllabus it is Day 44 (masking techniques: substitution, shuffle, key masking, encryption), Day 54 (masking rules, algorithms, mapplet creation, transformations), Day 55 and Day 56 (mask first name; mask alphanumeric text, SSN and telephone number) and the masking half of the hands-on TDM_Handson2 (profiling and masking).

14.1 Words to know first

Masking technique
The logic that replaces a value, such as "pick a name from a list" (substitution) or "swap values between rows" (shuffle).
Masking parameters
The options of a technique, such as the dictionary to use, the seed, or the range of dates allowed.
Masking rule
A technique plus its parameters, saved under a name. "FirstName_Substitution" is a rule. The same technique with different parameters is a different rule.
Data domain
A named group of columns that mean the same thing (for example "Social Security Number"), found by patterns in the data or in column names. You can attach preferred masking rules to it.
Policy
A bundle of data domains (and so their rules) that you reuse across projects. It holds no data source itself.
Assignment
The link between a rule and a column in a project, so TDM knows which rule masks which column.
Deterministic / repeatable
The same input always gives the same masked output, so "Asha" becomes the same fake name in every table and in every run.
Seed
A starting number that makes repeatable output reproducible. Same seed, same rule, same input, same result.
Dictionary
A flat file or database table of replacement values used by substitution, for example a list of first names.
Mapplet
A reusable group of PowerCenter transformations with input and output ports. TDM can import one as a custom masking rule.
Value cascade / auto cascade
Ways to make related columns receive the same masked value: a value cascade for similar columns you group by hand, an auto cascade for primary and foreign keys.
Rule Simulator
A preview screen that shows original and masked values for a standard rule before you assign it.

14.2 The big picture: rules, domains, policies and assignments

Four objects and how they connect

Start with the ShopSphere problem. Your CUSTOMERS table has first name, last name, email, phone, SSN, date of birth, zip code and tax ID, all sensitive. You do not want to configure "how to mask an SSN" nine times in nine projects. TDM lets you define it once and reuse it. You can create rules, domains and policies in any order. The guide's high-level policy task flow (p.72): create masking rules, define data domains, assign the rules to the domains, create a policy, assign the domains to the policy. You can apply the rules to source columns, data domains, policies and plans (p.136).

Data domains and preferred rules

A data domain (User Guide 10.5.10, p.73 to 76) From docs "represents the functional meaning of a column based on the column data or the column name". Create one domain for each meaning you need to mask the same way. The guide's SSN example: a database may hold social security numbers in a column called SSN, in a different table's SOCIAL_SECURITY and even inside a COMMENTS column. Define a data expression for the format 999-99-9999 (regular expression [0-9]{3}-[0-9]{2}-[0-9]{4}) and metadata expressions for names such as .*SSN*, .*SOCIAL*, .*SECURITY*. A regular expression is a text pattern for matching strings. Data discovery profiles (see the Informatica discovery and profiling chapter) use these patterns to assign domains to columns. Without Data Discovery you can still use domains, but you assign columns by hand (p.73).

When you attach masking rules to a domain they are called preferred rules. If you attach several, one is the default rule, applied to all columns of the domain, and you can change an individual column to another preferred rule (p.73). The guide's example: a Last_Name domain with shuffle as the default and substitution as another preferred rule for a different table.

Policy packs: TDM ships three, PII, PHI and PCI, visible in the Policies view after installation, each listing domains with a default rule (p.77 to 80). For example the PII pack lists First Name Domain with First Name Rule, Phone Domain with Phone Number Rule, Social Security Number Domain with Social Security Number Rule, ZIP Domain with ZIP Rule, Credit Card Domain, Email Address Domain, and more. The PCI pack focuses on payment data (Account Number, Credit Card, Expiration Date, names, birth date). You must have the View Policies and Manage Policies privileges to work with policies (p.77). The guide's tables name the domains and default rules; the excerpt does not say which technique each default rule uses, so look at a rule's properties in your install rather than guess.

Why domains and policies matter

If the SSN rule lives in a domain, then every column anywhere that the profile recognises as an SSN gets masked the same way without anyone remembering to configure it. The risk of an unmasked SSN hiding in a column called COMMENTS drops. This is the link back to discovery: profiling finds the sensitive columns, domains carry the rule to them.
