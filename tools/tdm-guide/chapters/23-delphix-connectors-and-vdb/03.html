23.7 Which data sources are supported, and extended connectors

The supported-connectors page splits what the engine can profile, mask and tokenize into two kinds. Delphix connectors are built in and come in three licensing flavours: Standard (built and supported by Delphix, included with the licence), Select (built and supported by Delphix but needing a separate licence) and Premium (built by a third party, often with a separate licence). FEML (File Extract, Mask and Load) is a technique for sources with no dedicated connector: extract data to files through the source's APIs, mask the files, load the masked data back. From docs

Two rules from that page matter for ShopSphere. Database masking applies only to physical tables: views, materialized views, federated systems and proxy objects are not supported. And JSON or XML stored inside database columns can be masked with a separate "Document Store Type" feature. Pricing is usage-based, per terabyte managed. The per-database pages give versions and feature tables (for example Oracle: TLS, password vault, Kerberos, in-place and on-the-fly options and "identity column support" all available), but the version matrix page was missing from my copy, so check your version there.

23.7.1 Extended connectors: bring your own JDBC driver

If your database is not natively supported, an extended connector lets you upload a JDBC driver and use it. The rules, from the extended-connectors page: the driver must be a type 4 (pure Java) .jar, packaged inside a .zip even if it is a single file; anything needing compilation or an install script on the engine is not supported; drivers needing a Java version above 8 are listed as unsupported (a line that looks out of date, since release 2026.5 runs on Java 17); and extended connectors lack some native features, though driver support plugins can add Disable Constraints, Disable Triggers and Drop Indexes. Delphix supports them under its support policy.

  1. Get the driver from the database vendor's official site and, where a checksum is published, verify it.

    The page warns that uploaded drivers run inside the engine's JVM, so a tampered driver could run arbitrary code on the engine host.

  2. Zip the driver files together and open Settings > JDBC Drivers, then click + JDBC Driver.

    The Add JDBC Driver dialog: Name, optional Description, Class Name (the class that implements java.sql.Driver) and a file chooser.

  3. Create a connector with Source Type Database - Extended.

    The Credentials step asks for the JDBC driver, a Schema Name, a JDBC URL (avoid putting the username and password in it, because URLs may be logged), an Enable Logger checkbox (slows things down; for debugging only), Username and Password.

23.8 Database permissions and preparing the database

23.8.1 A dedicated masking user

The permissions page recommends creating a separate database user for the engine, in non-production, rather than reusing a person's account. Reasons given: it is easy to replicate with its privileges, it can be a central directory user used in many places, and access audits on the database host become simpler. For masking jobs that user needs to read, write and update table data; create, drop, disable and enable indexes, triggers and constraints; and add or delete columns (the engine may add a temporary column, as you will see in the keys chapter). For profiling jobs it needs only to see object definitions (the schema) and read table data. From docs

23.8.2 Preparing each database

The "Preparing data" pages say, first of all, that using a VDB is recommended: it is also the best security practice because the database runs in a sandbox, and the page adds that Selective Data Distribution is advised for further security. The per-database pages share one logic. In-place masking changes every row of every masked table, which creates huge amounts of log and undo data, so the database should be tuned for a heavy write load, and log files can hold unmasked copies of the data and must be cleared afterwards.

DatabaseWhat the page asks for (overview)
OracleSwitch off archive logging for the copy (NOARCHIVELOG), enough memory (automatic SGA management), larger undo space and retention for big in-place updates (about 2 to 3 times the largest table) to avoid "snapshot too old" (ORA-01555), well-sized redo logs, PCTFREE 40 to 50, and use ROWID as the logical key. Grant SELECT on several V$ views, and SELECT_CATALOG_ROLE if jobs drop or disable indexes, constraints or triggers.
SQL ServerUse the SIMPLE recovery model (transaction logs may contain unmasked data), tune memory, prefer a clustered primary key, and turn on the drop indexes, constraints and triggers options. Add the masking user to db_datareader, db_datawriter and db_ddladmin. Identity columns cannot be masked without special steps. When provisioning a masked VDB, this user must exist on the source the VDB is made from.
Db2For z/OS, DESCSTAT must be YES or rule set creation fails. Size the journal (about 3 times table size for in-place, 1.5 times for on-the-fly) and purge it after masking, because it holds unmasked data.
Sybase (SAP ASE)Size memory and the transaction log (larger than all masked tables combined; a full log makes the job appear to hang). Create a masking user with grants such as SELECT, INSERT, UPDATE, DELETE and ALTER on the tables.

All four pages also explain how the engine finds a row to update: with a primary key, logical key or identity column. That topic is the heart of the next chapter.

Never prepare production like this

Switching off archive logging, dropping constraints or giving a user schema-altering rights are fine on a disposable copy and unacceptable on production. That is one more reason the docs steer you to a VDB or another non-production copy.
