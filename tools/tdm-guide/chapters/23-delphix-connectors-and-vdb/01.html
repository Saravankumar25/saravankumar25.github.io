A masking engine that cannot reach your data cannot mask it. This chapter covers the connection layer of Delphix Continuous Compliance (documentation version 2026.5): the application and environment that hold your work, the connector that tells the engine how to log in to a database or a file store, and the database-side preparation needed before the first job. It also answers what it means to "create a connector to a VDB from the Delphix masking engine".

The overview chapter introduces the vocabulary. The next object built on a connector is the rule set (rule sets and keys), and profiling and the hands-on labs use it.

Documentation gaps

The connector pages link to a "Data Source Support" page that was not available in the documentation copy used here, so the version-by-version support matrix for each database is not given; check it for your engine version. The VDB section builds the procedure from the documented connector steps and the masked-provisioning pages, and marks every step the documents do not spell out.

23.1 Words to know first

Application
A tag, assigned to one or more environments, naming the system whose data you manage. You must create one before you can create an environment.
Environment
The folder-like container that holds the connectors, rule sets and jobs for one group of data sources.
Connector
A saved definition of how the engine reaches one data source: type, host, port, credentials and options.
Meta Data Source
The grouping label on the connector screen: Database, File or Mainframe.
JDBC
Java Database Connectivity: the standard way a Java program talks to a database. The engine uses a JDBC driver (a library) for each kind of database and a JDBC URL (a connection string such as jdbc:vendor://host:port/name) to say where to connect.
Extended connector
A connector built on a JDBC driver that you upload, for databases the engine does not support natively.
Masking user
A dedicated database account that the connector logs in as, with just the permissions masking needs.
dSource
In Delphix virtualization, the engine's compressed copy of a source database's data, from which VDBs are made.
VDB (virtual database)
A full read-and-write copy of source data, provisioned from a dSource or from another VDB and managed by the Continuous Data engine.
Masked VDB
A VDB whose data was masked by a masking job during provisioning.
SDD (Selective Data Distribution)
A way to replicate a masked VDB to another Delphix Engine in non-production without sending the original unmasked data.

23.2 Applications and environments

23.2.1 What they are and why they exist

Think of a shared drive at work. You do not dump every project's files in one folder; you create a folder per project and put sub-folders inside. An environment is that project folder. The environments page describes it as a place where "a specified user can create and manage connectors, rule sets, and jobs". The application is a label above it that groups related environments: for ShopSphere, one application "SHOPSPHERE_APP" and environments such as SHOPSPHERE_DEV and SHOPSPHERE_QA. Analogy limit: unlike a shared-drive folder, an environment also carries rules (its Purpose and whether approvals are required).

The main Environment screen is the first page every user sees after signing in. It lists only the environments that user may access. Its columns are ID (the number used to refer to it from the Masking API), Application, Environment, Purpose, and Actions (Edit, Export, Duplicate, Delete). The screenshots below show it. Sorting a column also sorts the Environment column ascending.

23.2.2 Adding an application

An environment cannot be created without an application, so start here. From docs

  1. Click + Application near the top right of the Environments page.

    The engine wants a label first so that every environment is tagged with the system it belongs to.

    A small "Add Application" dialog with one box, Application Name, and Cancel and Save buttons.

  2. Type a name and Save.

    Use only characters the naming rules allow (see the overview chapter). Example for ShopSphere: SHOPSPHERE_APP.

    You return to the Environments list.

23.2.3 Creating an environment

  1. Click + Environment.

    It opens the Add Environment dialog.

    A dialog with Select Application, Environment Name, Purpose and an approval checkbox.

  2. Choose the application.

    The dropdown shows existing applications. It is "for informative purposes", the page says: it labels the environment and does not change behaviour.

  3. Type an Environment Name.

    For example SHOPSPHERE_DEV.

  4. Choose the Purpose.

    Mask or Tokenize/Re-Identify. This decides which job types the environment offers. The screenshot shows the default as "Masking". Purpose becomes read-only after creation, so choose carefully.

  5. Decide on "Enable Approval Workflow (Database rulesets only)".

    If ticked, inventories must be approved before masking jobs can run in this environment. It applies only to database rule sets. For a first lab leave it clear.

  6. Click Save, or Save And View.

    Save returns to the list; Save And View opens the environment's Jobs screen.

    The new environment is in the grid. Opening it shows tabs Jobs, Rule Sets and Connectors.

23.2.4 Editing, copying, exporting and deleting

All of these are in the Actions (...) menu beside each environment.

  • Edit. You may change the application and the name and the approval workflow setting. Purpose is read-only.
  • Duplicate. Makes an exact copy (the page calls this "a very powerful feature" when you want several similar environments). You give a new name; the copy has the same purpose. Choose Duplicate or Duplicate And View.
  • Export. Writes everything in the environment (connectors, rule sets, inventory, jobs and so on) to a file, with an optional passphrase. The engine returns an Async Task ID; follow it under Monitor, and when it succeeds, use Download File in that task's Actions menu. The main reason to export is moving environments between masking engines.
  • Delete. After a confirmation, deletes everything for that environment: connections, inventory, rule sets and so on. It does not delete universal settings such as algorithms and domains.

Two more actions live in the page-level Actions menu: Export Settings / Import Settings (Domain, Algorithm, File Format and similar; the import has a Force Overwrite checkbox and must use the same passphrase as the export) and Import Environment (with options to import settings too, to overwrite, to choose the target application and environment, and an OTF Environment checkbox for importing on-the-fly connectors). Details are in the overview chapter's section on moving work between engines.

Delete is bigger than it looks

Deleting a connector also deletes its rule sets and inventory data (the connector page says so). Deleting an environment deletes all its connectors, rule sets, inventories and jobs. Neither can be undone from the screen. Export the environment first if you might want it back.
