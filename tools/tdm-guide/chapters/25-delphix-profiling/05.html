25.12 Common mistakes and gotchas

Watch out for these
  • Treating profiling as the finish line. The output is a draft. Review every flagged and every unflagged column, especially free-text and oddly named ones.
  • Forgetting that only the rule set is scanned. A table added to the database after the rule set was built is invisible to profiling.
  • Editing assignments and leaving automatic updates ticked. The next profiling run can replace your edits. Untick it on columns you decided by hand.
  • Changing a domain's default algorithm and expecting old inventories to change. They do not; only future profiling runs are affected.
  • Max Memory below 1024 MB per stream with an ASDD profile set. The docs say the job needs at least that. Four streams need 4096 MB or more.
  • Trusting name matching alone. A column called ssn_present is a flag, not an SSN; TYPE classifiers exist to reject these, but they only help when the data type is right.
  • Using legacy profile sets for new work. They are deprecated and give less coverage.
  • Expecting value-level detection in languages other than English. The built-in lists are English only.
  • Sharing the PDF report or CSV without thinking. They list table and column names with their domains, which tells a reader exactly where your sensitive data lives, so store them with care.

25.13 Recap

Key points
  • Profiling scans a rule set with a profile set and writes domain and algorithm assignments into the inventory.
  • Classifiers come in four frameworks: PATH and TYPE look at columns; REGEX and LIST look at values. Scores combine into a confidence compared with the assignment threshold (default 1).
  • A domain is a kind of sensitive data with one default algorithm. Changing it affects only future runs.
  • Create the job in an environment: rule set, profile set (ASDD Standard by default), streams, memory (at least 1024 MB per stream for ASDD).
  • Read results on the job page, in the PDF, in the rule set inventory or in an exported CSV.
  • Correct findings in the Edit dialog and untick Enable Automatic Updates so that the profiler does not overwrite you.
  • For ShopSphere, expect the customer columns to be flagged and price or amount columns to be false alarms.

25.14 Check yourself

What is the difference between a profile set and a domain?

A profile set is a bundle of classifiers (recognition rules) used by a profiling job. A domain is a kind of sensitive data (such as SSN) with a default masking algorithm. Each classifier points to one domain, so the profile set decides what can be detected, and the domain decides which algorithm gets assigned.

A column called passport_no holds 9 digits. Why might the profiler pick PASSPORT_NO rather than SSN?

In the docs' example both REGEX classifiers match the digits with equal strength (0.5), but only the PASSPORT_NO PATH classifier matches the column name (0.67). The combined confidence is 0.84 for PASSPORT_NO and 0.5 for SSN, so PASSPORT_NO wins.

You fixed three columns by hand, and after the next profiling run two of them changed back. What did you forget?

Untick Enable Automatic Updates on those columns. While it is ticked, a profiling job may update the assignment; unticking makes your decision override the profiler.

You change the default algorithm of the FIRST_NAME domain. Do existing inventories change?

No. The change only influences assignments made by future profiling job executions. Existing assignments stay until you edit them or re-profile.

Why might ORDER_ITEMS.unit_price be flagged, and what should you do?

The Payment Amount PATH rule matches names that end in "price" (also amount, amnt, amt, balance). That is a name coincidence; a catalogue price is not personal data. Clear the assignment and untick automatic updates, after confirming with the business that prices are not sensitive.
