You cannot protect data you have not found. A real application database has hundreds of tables and thousands of columns, and nobody remembers which of them hold a customer's phone number, a tax id, or a note typed in by a support agent. Profiling is Delphix's answer: a job that scans your data source, decides which columns look sensitive, and writes its decisions into a list that you review before any masking happens.

This chapter explains that scan from zero. It covers what a profile set, a classifier, a domain and an inventory are, how they fit together, how to create and run a profiling job, how to read the results, and how to correct them by hand. It ends with the Day 52 lab (TDM_Handson5) on the ShopSphere sample database. The connections and rule sets the lab needs are set up in the Delphix connectors chapter and the rule sets and keys chapter; the algorithms that profiling assigns are explained in the algorithms and masking jobs chapter. If you want the Informatica view of the same idea, see the Informatica discovery and profiling chapter.

25.1 Words to know first

Sensitive data discovery / profiling
The process of scanning a data source to find columns or file fields that hold sensitive information. The docs use both names for the same thing.
Profiling job
A saved set of instructions that says "scan this rule set using this profile set". You create it once and can run it many times.
Rule set
The list of tables (or files) that a job is allowed to look at. A profiling job covers only what is in the rule set; new tables are not discovered until you add them.
Profile set
A bundle of recognition rules (classifiers). Choosing a profile set decides which kinds of sensitive data the job can detect.
Classifier
One recognition rule, tied to one domain. Example: "a column whose name looks like ssn" or "a value that looks like an email address".
Domain
A named kind of sensitive data, such as FIRST_NAME, SSN or EMAIL, together with the default masking algorithm for it.
Algorithm
The recipe that actually replaces a real value with a safe one. Profiling only chooses an algorithm; the masking job runs it.
Inventory
The table of every column or field in a rule set with its domain and algorithm. It is the profiler's output and the masking job's input.
Confidence
The number (shown 0 to 100 in the UI) that says how sure the profiler is about a match.
Assignment threshold
The minimum confidence needed before the profiler writes a domain and algorithm into the inventory.
ASDD profiler
Automated Sensitive Data Discovery, the current profiler. It uses classifiers. The older "legacy" profiler uses search and type expressions.

25.2 Why profile at all?

Picture the ShopSphere developers asking for a copy of SHOPSPHERE_PROD to test the Customer Orders app. A TDM engineer must hide every real name, phone number and tax id before handing it over. With four tables and nine customer columns you could do that by reading the table definitions. With a real database of 3,000 columns you cannot, and one forgotten column is a privacy incident.

A profiling job automates the first pass. The documentation describes it as examining metadata (column names and types) and potentially the data itself, then assigning the matching domain and its algorithm to each column it judges sensitive From docs. A person then reviews the result. That last step matters: the profiler is a fast assistant, not an auditor.

Why it matters

Profiling is where masking projects are won or lost. Masking jobs only protect what is in the inventory. A column the profiler missed, and nobody caught, goes to the test environment untouched.

Analogy: an airport scanner flags bags using a rulebook (the profile set). A security officer (you) opens the flagged bags, waves through the harmless ones, and sometimes stops a bag the scanner missed. The analogy stops being accurate in one place: the scanner has no memory of the officer's decisions unless you tell it, which is what the "automatic updates" checkbox, described in the inventory review part of this chapter, is for.

25.3 Profile, domain, algorithm assignment and inventory: how they differ

Beginners often use these four words as if they meant one thing. They are four different layers, and each answers one question.

LayerQuestion it answersWhere you manage itShopSphere example
Profile set (made of classifiers)How do we recognise sensitive data?Settings, Profile Sets and Classifiers"ASDD Standard"
DomainWhat kind of sensitive data is this, and what is its default algorithm?Settings, DomainsFIRST_NAME, SSN, TELEPHONE_NO
Algorithm assignmentWhich recipe masks this particular column?Inventory screen of a rule setCUSTOMERS.first_name gets dlpx-core:FirstName
InventoryFor this rule set, what is every column's domain and algorithm?Click a rule set nameThe whole list for SHOPSPHERE_PROD

Two consequences follow, both stated in the docs From docs:

  • Because the profiler assigns an algorithm through the domain, the same kind of data is masked the same way everywhere. Every FIRST_NAME column in every rule set gets the same default algorithm, which keeps results consistent.
  • Each domain has exactly one default algorithm, so if you want the profiler to pick a different algorithm for some data, a separate domain (with its own recognition logic) has to exist for it.
Changing a domain later

Editing a domain's default algorithm affects only future profiling runs. It does not change assignments already sitting in existing inventories From docs. If you change a default and expect old inventories to follow, they will not.
