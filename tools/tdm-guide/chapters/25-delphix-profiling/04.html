25.8 Running a profiling job and reading the results

Run it

Click the ... button on the job row and choose Run. Before it starts, the engine checks two resources: total memory allowed for all running jobs, and the number of jobs allowed to run at once (the application setting NumSimulJobsAllowed, default 7). If either limit would be exceeded, the job waits in a queue From docs. You cannot edit or delete a job while it is running. To stop it, use Cancel and confirm. The docs' warning about semi-masked data is about cancelling a running masking job (see the algorithms and masking jobs chapter); a profiling job does not mask anything.

Monitor it

Go to Monitor > Job Executions, or click the job name from anywhere. The list can be sorted and filtered by Environment, Job Name, Status, Submit Time, Start Time and Type. A job moves through these states From docs:

StatusMeaning
QueuedWaiting for resources; events have not started
RunningIn progress
SucceededFinished successfully
Warning (Non-Conformant)Finished, but with a warning
FailedAn event in the execution had an error
CancelledA user cancelled it
SkippedAn event was skipped and the process moved on

Click the job name for details. The Execution Summary shows environment, job name, job type (Mask, Profile, Tokenize or Re-Identify), rule set, connection type, number of streams and, for profiling, files or tables profiled and remaining. The Events box lists stages such as Initializing, Collecting Configurations, Preparing, Starting and Profiling Completed. Execution Components shows each table or file with progress, duration and a View Logs action.

The Profile Results panel (only for profiling jobs) is the quickest read of the findings, one row per table-column or file-field. Its grid supports sorting and filtering on every column.

Four ways to share the findings

  1. Job page, Profile Results panel.

    Fast, but it lives in the UI.

  2. PDF report.

    On the job page click Report and Logs and choose Job Report. Good for sending to a compliance officer. Execution Log is in the same menu.

  3. Rule set inventory.

    Open the rule set. For databases, the assigned Algorithm shows the result; for file rule sets, the Domain and Algorithm per field.

  4. CSV round trip.

    On the rule set page click Actions > Export Rule Set for a CSV. Edit Is Masked, Algorithm or Domain in the spreadsheet, then use Actions > Import Rule Set to load it back. A reviewer without engine access can therefore correct findings in Excel.

For database rule sets only, the API endpoint /profileResultDatabase/{executionId} returns the same results as JSON (column, table, domain, algorithm, data type, confidence). It does not work for other connection types From docs. When profiling several mainframe data sets that share one format, ASDD averages results across the files.

Reading the confidence number

In the PDF screenshot the confidence is 80, from classifiers that carry strengths like 0.67 and 0.7. The API example in the docs shows 100 for some columns, without explaining how that arises. Do not treat these as probabilities you could audit; the docs say the combining formula may change. Use them to sort your review: look first at low-confidence findings.

25.9 From findings to a reviewed inventory

The profiler writes its decisions into the rule set's inventory. Reaching it takes one click: Environment > Rule Sets tab > click the rule set's name. The "Inventory" tab that older versions had was removed, and the banner in the screenshots says so From docs.

A database inventory lists every column of every table. The number beside a table name is its column count. Primary key, foreign key and index flags appear under the column name, and data type and length are shown read-only. By default the visible columns are Table Name, Column Name, Data Type, Domain, Algorithm and File Format. For fixed-width and delimited files, fields are grouped under record types; see the file masking chapter.

Correcting one column: the Edit dialog

  1. Click the pencil (Edit) icon in the Actions column of the column's row.

    The Edit Column (or Edit Field) dialog opens. From the inventory screen only the Masking section is editable.

  2. Decide about Enable Automatic Updates.

    When ticked (the default), a profiling job may change this column's masking decision. When unticked, your choice wins over the profiler. If you are about to override the profiler, untick it first, otherwise the next profiling run may undo your work.

  3. Pick the Domain and the Algorithm.

    The Domain drop-down fills in that domain's default algorithm; you may replace it with any other algorithm.

  4. If you chose a DATESHIFT algorithm on a column that is not a native date or datetime, fill in the Date Format.

    The default is yyyy-MM-dd. The letters are case sensitive: D means day of the year, d day of the month, MM month, yyyy four-digit year.

  5. Add a note if useful, then click Save.

    Nothing takes effect until you save.

Three more inventory tools worth knowing From docs:

  • Clear Masking Assignment (the circular-arrow icon in a row's Actions column, enabled only when that column or field has an assignment) removes the applied masking assignment and, in the same click, switches automatic updates off for it. A confirmation bar appears for a few seconds; if you do nothing, the clearing goes ahead, and Cancel keeps your assignment.
  • Nulling algorithms. If you pick an algorithm that can return null (such as Null SL) for a column that has a NOT NULL constraint, the UI shows an error.
  • Inventory Approval Workflow (database rule sets only, enabled per environment). Every edit sets the status to NEW; the editor clicks Submit; an Admin or a user with the Inventory Approval privilege clicks Approve or Reject. A masking job for that rule set will not run unless the status is Approved. This gives a data steward a formal sign-off point.

Reading a report like a reviewer

Take the PDF screenshot earlier: it has TELEPHONE_NO and EMAIL rows with confidence 80 and "Auto ID true". Ask four questions of every row, in this order:

  1. Is the domain right for what the column holds?

    A phone number column marked TELEPHONE_NO is right. A column of order codes marked TELEPHONE_NO would be a false alarm.

  2. Is the algorithm right for the application?

    The domain's default is only a default. A unique-email algorithm keeps each person distinct; a lookup-based one can map two people to the same address. Which one the tests need is a design decision, see the algorithms chapter.

  3. Is confidence low?

    Low means "worth a second look", not "wrong".

  4. What is missing?

    The rows with no domain, such as UNMASKED_00 in the database screenshot, are as important as the flagged ones. Ask for each: could this hold personal data?

A review checklist for the data steward

  1. List every table and column in the rule set.

    Export the rule set to CSV so that nothing is missed by scrolling.

  2. Mark every column that holds or could hold personal data.

    Use the data dictionary, the application team and a quick look at sample values.

  3. Compare your marks with the profiler's.

    Differences are your to-do list: extra flags to clear, missing flags to add.

  4. Record the reason for every manual change in the Notes field.

    The Edit dialog has a Notes box for exactly this. It makes audits easier.

  5. Untick Enable Automatic Updates on every manual change.

    Otherwise the next profiling run may undo it.

  6. If the environment uses the approval workflow, Submit, then have an approver sign off.

    Status shows Approved and masking jobs can run.

Doing the same from a script

Everything above is also available through the Masking API. The documentation's createInventory example logs in, finds a connector, rule set and table, creates table metadata for that table, then updates one column's inventory entry (it assigns an algorithm and a domain). The payload that does the assigning is just two fields From docs:

PUT /column-metadata/{columnMetadataId}
{
  "algorithmName": "AddrLine2Lookup",
  "domainName": "ADDRESS_LINE2"
}

That is the same act as picking a domain and algorithm in the Edit dialog. Teams use scripts like this to apply the same corrections to many rule sets. The script relies on helper files (apiHostInfo, loginCredentials, helpers) that are not shown, so you cannot run it as printed. To fetch the profiling results of a database job you would call /profileResultDatabase/{executionId}, mentioned earlier.

Why the checkbox matters in teams

A TDM engineer who fixes ten columns by hand, and a colleague who re-runs profiling the next day, are a common cause of "my changes disappeared". Untick automatic updates on every column you corrected deliberately, and let the profiler keep updating the rest.
