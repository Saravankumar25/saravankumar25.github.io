25.5 Profile sets: choosing and configuring the rulebook

Open Settings > Profile Sets to see the available sets. The table can be sorted by Name, Description and Created, and filtered by Name, Description, Owner and Created From docs.

The table follows the Out of the box profiling settings page, which says the product ships logic for "over 30 types" of sensitive data. The Domains screenshot later in this chapter shows 69 domains on one test engine, so treat "over 30" as a floor, not a count.

Create your own profile set (ASDD)

You would build a custom set when, for example, a project wants only a handful of domains scanned, or a different threshold. The steps below are for the ASDD profiler From docs.

  1. Click + Profile Set above the grid.

    This opens the Add Profile Set dialog.

  2. Type a unique Set Name; add a Description if you like.

    Names must be unique across all profile sets.

  3. Leave ASDD Support ticked (the default).

    This tells the engine the set will hold classifiers rather than legacy expressions. You cannot flip this later on an existing set; you would have to create a new one.

  4. Optionally enter an Assignment Threshold, 1 to 100.

    If you leave it empty, the application setting DefaultAssignmentThreshold applies.

  5. Tick the classifiers you want.

    Each classifier is tied to a domain, so the ticked list decides which domains this set can ever detect.

  6. Click Save.

    The new set appears in the grid and in the profile set drop-down of the profiling job wizard.

Other actions in the row menu are View (everything read-only), Edit (tick or untick classifiers), Duplicate (copy with a new name) and Delete. You cannot delete a profile set that is assigned to any job From docs. Profile sets can also be created through the API with two calls (see the ASDD profile set import and export page, which I did not read in full).

25.6 Domains and classifiers on the Settings screens

Domains

Settings > Domains lists each domain with its default Masking Method (algorithm) and, if defined, a Tokenization Method. The list can be sorted by Name, Masking Method and Tokenization Method From docs.

To add a domain, click + Domain, give it a unique name (this name will appear in the Domain drop-down on the inventory screen), pick a default masking algorithm, optionally a default tokenization algorithm, and save. If the environment's purpose is Tokenization/Re-Identify, the profiler assigns the domain's tokenization algorithm instead of its masking algorithm, so every domain used in such an environment should have one defined.

When you would add a domain

Suppose ShopSphere's compliance officer says "loyalty card numbers must be masked with a different algorithm than bank account numbers". The profiler can only assign one algorithm per domain, so you would create a LOYALTY_CARD domain with its own default algorithm and add a classifier that recognises such columns. This is an illustrative scenario, not something in the docs.

Classifiers

Settings > Classifiers lists every classifier instance with its Domain, Owner (System or a user), Type and Description. Sortable fields are Name, Domain and Description From docs.

To add a classifier you choose a Domain, enter a name and description, choose a framework (the docs list Data Type, Regex, Path or List), then fill the one mandatory field for that framework and click Add: a Profiling Regex for Regex, a Data Type for the type framework, an uploaded File for List, a Field Value for Path. Other fields take defaults. Name and framework cannot be changed after creation. Use the row menu to View, Edit or Delete.

Two technical notes from the docs: PATH and REGEX use Java 8 regular expressions, with separate options for whole-input matching and case sensitivity, so you should not wrap patterns in ^(...)$. List classifiers can "tokenize" input so that a full name is matched word by word against first-name and last-name lists, with the confidence being the sum of matching token strengths divided by the number of tokens.

Worked example: teach the profiler about a ShopSphere loyalty number

Suppose ShopSphere adds a column loyalty_no to CUSTOMERS (values like LY-123456) and the compliance officer wants it masked with its own algorithm. The built-in sets know nothing about it. This scenario is my illustration; the screens and rules it uses are the documented ones.

  1. Create a domain, for instance LOYALTY_NO, with the algorithm you want as default.

    One domain per distinct algorithm, because each domain has a single default algorithm. Algorithm choices are explained in the algorithms and masking jobs chapter.

  2. Add a PATH classifier for that domain.

    Framework Path, mandatory Field Value such as a pattern that matches names containing "loyalty". PATH is cheap and needs no data access. Use a match strength near the 0.67 used by the built-in ones.

  3. Optionally add a REGEX classifier for the value shape.

    A dashed pattern with two letters, a dash and six digits is distinctive, so it deserves a fairly high match strength. A bare six-digit pattern would match many other things and should get a low one.

  4. Create a profile set that contains your new classifiers plus the ones you still need.

    Or duplicate ASDD Standard, then tick your new classifiers. Duplicating keeps the original untouched.

  5. Pick the new set in the profiling job and run it.

    The loyalty_no column should show domain LOYALTY_NO in Profile Results.

25.7 Creating and managing a profiling job

Profiling jobs live inside an environment, next to masking jobs. Click an environment and you land on its Jobs tab. The documentation says profiling jobs can be created for relational databases (examples: Oracle, PostgreSQL) and for XML, JSON, mainframe, delimited and fixed-width rule sets. It is not supported for XML or JSON documents stored inside database columns, or for NoSQL databases From docs.

A documentation disagreement to be aware of

The profiling jobs page lists JSON rule sets as supported, while the inventory page says "Profiling is not supported on the JSON file rule sets". I could not settle this from the text. For delimited, fixed-width and database rule sets, which this course uses, there is no conflict. If you must profile JSON, test it on your engine version.

Create a profiling job, step by step

  1. In the environment, open the Jobs tab and click + Profiling Job.

    The Create Profile Job wizard opens with three steps: Details, Configuration, Summary.

  2. Details: enter a unique Job Name and pick the Rule Set.

    The rule set is the scope of the scan. Tables not in it are never examined.

  3. Details: choose the Profile Set.

    The UI pre-selects the profile set named in DefaultProfileSetName, which is ASDD Standard in the screenshot below.

  4. Details: decide on the two checkboxes.

    Multiple Profiler Expression Check assigns a fallback algorithm when classifiers in different domains tie at the same confidence; the report will mention the multiple matches. Clear previous auto domain assignments wipes domains assigned by earlier runs for columns whose automatic updates are on, so the run starts fresh. A third box, Multi Tenant, lets one rule set be reused for identical schemas through different connectors, with the connector picked at run time.

  5. Click Next. Configuration: set streams, memory and notes.

    See the table after the screenshots.

  6. Click Next to reach Summary, check it, and click Save.

    The job appears in the Jobs list with no status until you run it.

Edit, view and delete

Each job row has a ... button in the Actions column. Edit opens the same wizard; the job name is locked after creation, and Edit is disabled if you lack permission. View opens the wizard on the Summary step. Delete asks for confirmation (click Confirm) and is also permission controlled From docs.
