9.6 How the three tools sit on this picture

Each tool packages the same stages differently. The goal here is not to learn the screens (the tool chapters do that) but to see the ETL skeleton inside each one.

9.6.1 Informatica TDM: a plan that becomes a PowerCenter workflow

Core idea. You do not draw an ETL mapping. You describe what you want in a plan, and TDM generates the ETL objects for you. A plan defines a data subset, masking or data generation operation and holds the components it needs (User Guide 10.5.10, p.274). When you generate a workflow, "the PowerCenter Repository Service generates mappings for the workflow"; when you start it, the PowerCenter Integration Service does the subset, masking and generation tasks (p.308). The guide lists what the Integration Service creates for masking: mappings, transformations, mapplets, sessions and workflows (p.150). From docs

Where each pipeline stage lives, from the pages I read:

  • Extract subset. An entity has a driving table, and TDM adds the tables related to it through constraints; you attach filter parameters to columns. The workflow loads the matching subset into a target database (pp.112 to 114). Three data integrity options decide how whole the subset is: Transactional Integrity for Major Relation Type (a selected child pulls in its parents, the parents pull in all their children, and this repeats until no more related rows are found), Referential Integrity Only (the least rows needed to keep keys valid, so some children of a parent may be missing) and Two-way (criteria propagate down and then up until every table has some data). Recursive evaluation and Two-way need a staging connection (pp.121 to 122). From docs
  • Staging. A plan lets you choose source, target, staging, lookup, storage and dictionary connections (p.276). A staging connection is a database used for staging data, and cyclic tables in an entity require one (p.114). From docs
  • Mask. Masking rules (standard, advanced, or imported from a mapplet) are assigned to columns, data domains and policies. Subset and masking can share a plan: "the subset component gets priority", so TDM subsets first and then masks the subset, and does not mask data outside the subset (p.275). That is the extract-then-transform order of the reference architecture. From docs
  • Load. The target is a database, flat file, or the test data warehouse, which keeps versioned data sets that can be reset to a test system (pp.236 to 238, 275). Plan settings add update strategy (insert, update, or update else insert), commit type and interval, and error and recovery options (pp.284 to 285). A pre workflow and post workflow, and SQL before and after writing to the target, are available (pp.277 to 278). From docs
  • Operate. The Monitor view shows progress, and the Session Details tab shows affected, rejected and written rows (p.275). Up to eight workflows run at once (p.276). From docs

Architecture reminder (pp.25 to 27): Test Data Manager is the web front end; the TDM repository stores rules, projects and entities; the PowerCenter Repository Service and Integration Service hold and run the generated workflows. The Informatica architecture chapter covers this in full, and the plans and workflows chapter covers the plan screens.

9.6.2 Delphix Continuous Compliance: connectors, rule sets and masking jobs

Core idea. Delphix's masking engine models the pipeline as four objects you configure once and reuse: a connector (how to reach a source or target), a rule set (which tables or files), an inventory (which columns get which algorithm) and a job (the thing that runs). The terminology page defines masking as iterating through a dataset to find sensitive fields and replace them with desensitised values, and a rule set as a group of tables or flat files on which profile, masking or tokenization jobs run.   • Load: the two job methods. This is the clearest ETL parallel in any of the tools. In-place jobs update the source environment with the masked values. On-the-fly jobs read unmasked data from the source and write masked data to the target, and require a source environment and source connector as well as the target. Supported pairs are same-type databases or files, and database to delimited file (Create, view, edit, delete, verify jobs). From docs Create, view, edit, delete, verify jobs ↗

Commit Size, Update Threads, Batch Update, Truncate (on-the-fly only), Drop Indexes, Disable Triggers, Disable Constraints, a Pre SQL and Post SQL script, Number of Streams for parallel tables, Row Limit, Feedback Size, memory settings and email notification. A submitted job is run or queued depending on memory and a limit on simultaneously running jobs (default 7); a stopped running job leaves semi-masked data, and indexes, constraints or triggers that the job dropped are not recreated (Running and Stopping Jobs). 9.6.3 GenRocket: generators feed receivers; G-Subset is an ETL job

Core idea. GenRocket's main product creates data, so in the pipeline it replaces the "source". Its five key components give each ETL stage a name: a domain (like a table) with attributes (like columns), a generator that creates values, a receiver that "receives the data from an Attribute's Generator and morphs it into a usable format", and a scenario with the instructions for what to generate and how much. From docs GenRocket Five Key Components ↗

  • Load = receiver. The Receivers overview describes 120+ receiver types that format and deliver generated data: SQL and NoSQL databases, web services, fixed and delimited files, big data formats such as Parquet and Avro, message formats such as Kafka and MQ, packaged applications, EDI, documents and images, and cloud environments. More than one receiver can be attached to a domain, and data is generated for each in order. From docs Receivers Overview ↗ The FAQ adds that a receiver does not know whether it delivers to a mainframe or a PC; it only knows its format and destination. For large volumes, native bulk load receivers are preferred over JDBC. Pre and post SQL runs through the SQLUpdateReceiver. From docs
  • Where it runs. The Runtime executes scenarios on premises, behind your firewall (General FAQ). General FAQ ↗ This is the ETL engine; the cloud part is where you model and design (Architecture page). From docs
  • Synthetic replacement as a masking transform. "Synthetic Data Replacement" replaces sensitive values with generated ones and is used in G-Subset and file masking. From docs What is SDR? ↗

G-Subset as an ETL job. G-Subset is GenRocket's subsetting and masking feature for databases. Its description reads like our reference architecture. G-Subset Overview ↗ From docs

  1. Import the schema.

    You upload only the source database's metadata, not customer data. This is the "model" step and the source profile.

  2. Define subset conditions.

    A "Where" clause, a percentage of rows or a number of rows, and the sensitive columns to replace.

  3. Download the configuration.

    The files are the instruction set. The actual work runs in your environment.

  4. Extract into temporary dump files.

    Rows to be subset are read from the source tables into temporary files on the machine doing the migration. This is the staging area. In default mode, sensitive columns are never read: the dump file marks them "to be masked" and fills them with synthetic data from an automatically created domain and scenario.

  5. Load.

    The data is inserted into the destination tables, directly via JDBC with bulk files or using SQL insert files, and the temporary files are removed afterwards.

    Result: a smaller, masked copy in a destination database of the same type as the source.

Here the ETL parts are named: extract into staging, transform (replace), load, clean up. Note one design difference from most masking tools: by default the sensitive values are not read at all, which is a privacy advantage over reading and then hiding them. The overview also describes an optional conditional masking feature, disabled by default, that does read the actual values.
