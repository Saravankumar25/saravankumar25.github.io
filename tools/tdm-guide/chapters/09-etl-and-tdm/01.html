ETL is covered in ETL from scratch, and what TDM has to achieve in the chapters on subsetting, masking and generation. The two join up: a TDM job is an ETL job whose output is a safe, small, consistent copy of production for testing. Seeing the shared skeleton makes each tool easier to understand, because you can ask of every screen: which ETL stage is this?

The two are not the same. Treating a TDM job as an ordinary ETL job loads unmasked data, breaks foreign keys or leaves no record of what was done.

9.1 Words to know first

TDM pipeline
The chain of stages that turns production (or a generator) into a usable test data set: find sensitive data, cut it down, mask it, load it, check it.
Provisioning
Delivering a prepared data set to a test environment so testers can use it.
In-place masking
Masking that changes the values inside the database you point it at. Delphix describes in-place jobs as updating the source environment with the masked values.
On-the-fly masking
Masking while copying: unmasked data is read from the source and only masked data is written to the target. This is the ETL order.
Deterministic (consistent) masking
Masking that turns the same input into the same output every time, so the same customer is masked identically in every table and every run.
Driving table
The table whose rows decide which rows are copied. Informatica uses the term for the starting point of a subset.
Audit trail
A record of who ran what, when, and with which settings, kept so that compliance questions can be answered later.
Refresh
Re-running the pipeline to replace old test data with a new copy.
Receiver
GenRocket's component that receives generated data and writes it into a usable format at a destination. It plays the role of the load stage.
Workflow (Informatica)
The runnable job that Test Data Manager generates from a plan.

9.2 The same underlying idea

Concept. Both ETL and TDM move data and change it on the way. Both read from a source, apply rules, and write to a target. Both are driven by definitions that tell the engine what to do, both run as repeatable jobs, and both need logs, error handling and connections to databases.

Evidence from the products. The strongest proof is in the Informatica guide itself. The PowerCenter repository, it says, stores the workflows and mappings generated from Test Data Manager and "information required to extract, transform, and load data" (User Guide 10.5.10, p.26). From docs The workflows that perform data subset, data masking and data generation are run by the PowerCenter Integration Service (p.27). In other words, Informatica TDM is an ETL engine with a test-data front end.

The analogy is useful but incomplete: a photocopier that blacks out names is a good picture of masking, and a photocopier is not an ETL engine. TDM adds purpose-built rules (find the sensitive columns, hide them consistently, keep keys valid) on top of the same moving parts.

9.3 How they differ

The seven differences below explain why you cannot take an everyday ETL job and call it a TDM job.

DimensionTypical ETLTDM
PurposeMake data usable for reporting, integration or migrationMake data safe and suitable for testing
Direction and shapeMany sources converge into a reshaped target (warehouse tables)One source copied to one or many test environments, usually with the same shape
Output consistencyConsistent with business meaning (totals are right)Relationally intact: every foreign key still matches, even after values are hidden
PrivacyProtect access to the target; data stays realSensitive values must not reach the target at all
SizeAs much data as the business needs, often all of itAs little as the tests need (a subset), or newly generated
RepeatabilityScheduled, usually nightly; results are the latest factsOn demand or per release; results should be reproducible and resettable
Who uses itData engineers, BI developersTDM engineers, QA engineers, developers, with data stewards and compliance officers as approvers

9.3.1 The differences in more detail

Shape. ETL changes shape because the target has a different purpose (a star schema, as in the previous chapter). TDM keeps shape because the application under test expects its own tables. The documents show this: GenRocket's G-Subset can only migrate between databases of the same type, for example MySQL to MySQL (G-Subset overview); Delphix on-the-fly masking supports Oracle to Oracle or delimited file to delimited file, and database to delimited file (jobs page). From docs

Consistency. A warehouse can lose the original keys and use surrogate ones. A test database cannot, because the application joins on the real keys. Masking must keep joins working: if customer_id in CUSTOMERS is masked differently from customer_id in ORDERS, the join returns no rows. Delphix's terminology page shows how its algorithms deal with this: a secure lookup algorithm picks replacements by a cryptographic hash of the original value, "so masking output is consistent for each input"; mapping algorithms guarantee no collisions; segment mapping permutes short values with no collisions and is suggested for unique columns such as Social Security Numbers and keys. From docs Delphix masking terminology ↗

Size. Informatica describes a data subset as a "small, targeted, and referentially intact copy" of production for nonproduction use (User Guide 10.5.10, p.112). From docs Small matters because test environments are cheap and many; but small must still be whole, meaning parents and children come together. Section 9.6 shows the integrity options.

Repeatability. Informatica lets you use criteria parameters so the same workflow produces different subsets by changing values at run time (p.113). Delphix jobs can be multi-tenant, so the same rule set masks identical schemas through different connectors chosen when the job runs. GenRocket can regenerate the same data with a seed (General FAQ). From docs

Success measure. A broken ETL job is noticed when a report is wrong. A broken TDM job may produce a data set that looks fine and leaks a real phone number. Its success has to be proven by checks for leakage as well as for counts, which is why section 9.7 ends with a test step.
