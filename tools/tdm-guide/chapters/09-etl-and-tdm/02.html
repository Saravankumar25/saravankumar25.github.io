9.4.1 Masking really is a transformation

The cleaning transformation in ETL from scratch, LOWER(TRIM(email)) changes a value row by row, according to a rule. A masking rule such as 'user' || customer_id || '@example.test' does exactly the same. The only difference is the reason: cleaning makes a value better; masking makes it safe. In the Informatica guide, masking rules that come from mapplets are literally PowerCenter transformation logic imported into TDM (User Guide 10.5.10, p.137). From docs The same is true of generation: a custom generation rule is built from mapplet logic (p.192). From docs

9.4.2 Subsetting really is a filtered extract

The Informatica guide defines an entity as a driving table plus the tables related to it through constraints. Define a filter, such as EmpID equal to 10, and the workflow loads the Employee row, its history rows and its orders into the target (pp.114 and 121). From docs In SQL that is WHERE on the parent plus joins down to the children. Delphix rule sets offer the same at table level: each table can carry a Filter, "a WHERE clause to filter or subset the data", or a custom SQL SELECT (Managing rule sets). From docs Managing rule sets ↗ GenRocket's G-Subset offers a "Where" clause, a percentage of rows, or a number of rows (G-Subset overview).

9.4.3 Provisioning really is a load

Loading rules from ETL apply directly: load parents before children, decide truncate versus append, use commit sizes, handle constraints. Delphix on-the-fly jobs expose a Truncate checkbox, Commit Size, Batch Update and Disable Constraints. Informatica's plan has an update strategy and a commit interval (p.284 to 285). Provisioning adds one thing ETL rarely has: a path back. Informatica's test data warehouse stores versions of data sets and lets you reset a target to any version (pp.236 to 237). From docs

9.5 A reference architecture for a TDM pipeline

Every stage below is a stage of ETL; the two extra boxes at the ends (profile and test) are TDM additions. General concept

9.5.1 Stage by stage

  1. Profile.

    Reason: you cannot mask what you have not found. Profiling scans columns for patterns (SSN-like, phone-like) and learns which tables relate.

    Output: a list of sensitive columns and a relationship map, approved by a data steward. Covered in the Informatica profiling chapter and the Delphix profiling chapter.

  2. Extract the subset.

    Reason: copying everything is slow and expands the exposure. Choose driver rows, then pull in all related rows so the subset is whole.

    Output: a consistent slice in staging or in a stream, still containing real values.

  3. Mask (transform).

    Reason: this is the stage that removes risk, so it must happen before data lands anywhere testers can read.

    Output: the same rows with sensitive values replaced consistently.

  4. Load.

    Reason: put the result where tests run, in the right order and within the target's constraints.

    Output: a populated test database or set of files.

  5. Verify, then test.

    Reason: nobody should trust a TDM job on its exit code. Check keys, counts and, crucially, that no original sensitive value survived.

    Output: pass or fail evidence, stored with the run.

The supporting services mirror ETL architecture: a rules repository (metadata), an orchestrator (scheduler), logs (monitoring), plus a place to keep versions of data sets. Informatica provides the last as the test data warehouse, which stores multiple versions of test data in a central location, shareable across teams (User Guide 10.5.10, p.236). From docs

Why the order extract, mask, load matters

If you load first and mask afterwards (an ELT-style order), there is a time window in which real personal data sits in the test database, copies may be taken, and a failed masking job leaves the original data behind. Delphix says it plainly for in-place jobs: when a masking job fails, the target "may be in a partially masked or unmasked state" (Job monitoring), and stopping a running job results in semi-masked data (Running and Stopping Jobs). From docs On-the-fly masking avoids the window by never writing unmasked data to the target.
