9.7 An end-to-end ShopSphere story: profile, subset, mask, load, test

The request. The ShopSphere QA team needs a test copy of "Customer Orders" for a release. They need customers who ordered on 20 October 2026, with all of their orders and items. The compliance officer adds one rule: no real SSN, phone, email, tax id, name, date of birth or exact zip code may reach the test database. You are the TDM engineer. Here is the plan, with every step labelled as ETL-style or TDM-specific.

StepWhat happensETL-style?TDM-specific part
1. ProfileScan CUSTOMERS columns for SSN-like and phone-like patternsPartly (source profiling)Classifying columns as sensitive; steward approval
2. SubsetChoose the customers with an order on 2026-10-20Yes (filtered extract)Children and parents must travel together
3. MaskReplace names, email, phone, SSN, tax id, birth date and zipYes (transformation)Deterministic, format-preserving, nothing real left
4. LoadInsert customers, then orders, then items into the test tablesYes (load, parents first)Target must be a non-production system
5. TestNo orphans, no leaked values, counts match, rerun gives same outputReconciliation is ETL-styleThe leak check is TDM-specific

Run steps 2 to 7 as one script:

-- STEP 1 (profile): which columns look sensitive?
SELECT COUNT(*) AS ssn_like_values FROM customers
WHERE ssn GLOB '[0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9][0-9][0-9]';
SELECT COUNT(*) AS phone_like_values FROM customers
WHERE phone GLOB '[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]';
-- STEP 2 (extract a subset): choose the driver rows
INSERT INTO subset_keys SELECT DISTINCT customer_id FROM orders WHERE order_date = '2026-10-20';
SELECT * FROM subset_keys;
-- STEP 3 (transform = mask, and load customers)
INSERT INTO t_customers
SELECT c.customer_id,
       m.first_name,
       'Tester' || c.customer_id,
       'user' || c.customer_id || '@example.test',
       '90000' || SUBSTR('00000' || c.customer_id, -5),
       '900-00-' || SUBSTR('0000' || c.customer_id, -4),
       SUBSTR(c.date_of_birth, 1, 4) || '-01-01',
       SUBSTR(c.zip_code, 1, 3) || '000',
       'MASK' || SUBSTR('000000' || c.customer_id, -6)
FROM customers c
JOIN subset_keys k ON k.customer_id = c.customer_id
JOIN mask_names m ON m.slot = c.customer_id % 4;
SELECT * FROM t_customers;
-- STEP 4 (extract and load the children that belong to the subset)
INSERT INTO t_orders SELECT o.* FROM orders o JOIN subset_keys k ON k.customer_id = o.customer_id;
INSERT INTO t_order_items SELECT i.* FROM order_items i JOIN t_orders o ON o.order_id = i.order_id;
SELECT * FROM t_orders;
-- STEP 5 (test the result): no orphans, no leaked values, no lost rows
SELECT COUNT(*) AS orphan_orders FROM t_orders o
LEFT JOIN t_customers c ON c.customer_id = o.customer_id WHERE c.customer_id IS NULL;
SELECT COUNT(*) AS leaked_ssn FROM t_customers t JOIN customers c ON c.ssn = t.ssn;
SELECT COUNT(*) AS leaked_email FROM t_customers t JOIN customers c ON c.email = t.email;
SELECT (SELECT COUNT(*) FROM t_customers) AS customers,
       (SELECT COUNT(*) FROM t_orders) AS orders,
       (SELECT COUNT(*) FROM t_order_items) AS items;
-- STEP 6 (repeatability): the same input gives the same masked output
SELECT 'Tester' || 1001 = last_name AS same_as_first_run FROM t_customers WHERE customer_id = 1001;

9.8 Pitfalls: where ETL habits hurt TDM

9.8.1 Masking after load instead of before

The ETL reflex "land the raw data, then clean it" is wrong for sensitive data. Between the load and the end of masking, real values sit in an environment with wide access, and a failure leaves them there. Prefer on-the-fly or pre-load masking, or in-place masking inside a protected staging environment that testers cannot reach, and copy onward only after verification. Informatica's plan masks data inside the same workflow that loads the target, with subset first (p.275); Delphix on-the-fly jobs never write unmasked rows to the target; GenRocket G-Subset replaces sensitive values in the dump file before insertion. From docs

9.8.2 Consistency across ETL and masking

When keys are masked, they must be masked identically wherever they appear. I tested this with the three ShopSphere customers and four orders by adding 70000 to the key.

-- Customer keys masked, order keys left alone: the join breaks
SELECT COUNT(*) FROM ord o JOIN (SELECT customer_id + 70000 AS customer_id FROM cust) c
  ON c.customer_id = o.customer_id;                        -- returns 0

-- The same rule applied to both tables: the join works
SELECT COUNT(*) FROM (SELECT order_id, customer_id + 70000 AS customer_id FROM ord) o
  JOIN (SELECT customer_id + 70000 AS customer_id FROM cust) c
  ON c.customer_id = o.customer_id;                        -- returns 4

Two further consistency risks come from ETL-style staging. First, if the same person appears in two systems (CRM and billing) and each is masked by a separate job with a random rule, the person gets two different fake identities and cross-system tests fail. Use deterministic rules and share the algorithm and its key across jobs. Delphix algorithms differ in this respect: some are non-deterministic and "cannot guarantee the same output for the same input across masking jobs", while others are fixed (Delphix algorithm documentation excerpt); the terminology page also notes that a secure lookup can collide, which matters when a column must stay unique. From docs Second, a reversible method such as tokenization (the only algorithm type that allows reversing, per the terminology page) is a deliberate exception, not a default.

9.8.3 Performance

Masking adds work to every row, and subsetting adds joins. Plan for it as you would for ETL: choose commit sizes, parallelism and index handling, and expect trade-offs. Delphix's guidance includes number of streams, update threads (reduce them if you see database deadlocks), and the option to drop indexes during a job; Informatica allows up to eight workflows at once. A subset reduces volume, which is usually the biggest performance win, so extract less before you optimise anything else. From docs

9.8.4 Audit trails

An ordinary ETL log says whether the job ran. A TDM log must also help answer: who masked this, with which rules, and when? What the tools provide, from the pages I read: From docs

  • Informatica: an Audit Trail Report listing recent activities in Test Data Manager (type of activity, object, user, date and time, with filters and CSV download), a Data Masking Report listing columns with their assigned rules and policies, a Plan Audit Report, and a Row Count Report (User Guide 10.5.10, pp.321 to 322, 324). The Monitor view shows job types such as Generate Workflow, Execute Workflow and Reset Data Set from Test Data Warehouse (p.316).
  • Delphix: audit logs record user actions in the UI or REST API: the action, user and time, with action categories such as Create, Edit, Run, Login; the UI page is for admin users and can export a PDF. Audit logs ↗
  • GenRocket: the pages I read do not describe an audit log for the G-Subset feature, so check your version.
Other gotchas
  • Treating the exit code as proof. A job can finish and still have left a column unmasked. Always run the leak check.
  • Masking only some copies of a value. The same SSN in a notes column or a file export remains. Profile every column and every file.
  • Letting a rerun double-load. Use truncate, upsert or a reset path so a rerun does not duplicate rows.
  • Overwriting masked data with a refresh by accident. Name and version data sets, as the test data warehouse does.

9.9 Recap

Recap
  • A TDM job is an ETL job with a different purpose: safe, small, consistent test data. Informatica TDM is built on a PowerCenter ETL engine.
  • The seven differences: purpose, direction and shape, output consistency, privacy, size, repeatability, and who uses it.
  • Overlaps: masking is a transformation, subsetting is a filtered extract, provisioning is a load, generation is a source.
  • Reference pipeline: profile, extract subset, mask, load, verify, supported by a rules repository, an orchestrator, logs and a test data store. Mask before data lands where testers can read it.
  • Informatica: plan to generated PowerCenter workflow. Delphix: connector, rule set, inventory, then an in-place or on-the-fly job. GenRocket: generators feed receivers; G-Subset extracts into dump files, replaces sensitive values and loads.
  • Keys must be masked identically everywhere; use deterministic algorithms.
  • Verify leaks as well as counts, and keep audit evidence.
