21.3 What we are building, and the design decisions

The syllabus deliverable is four columns and 50 rows. Here is the target, with each column's source.

Target file layout and how each column is produced
Column headerAttributeGeneratorNotes
(not in output)idautomaticEvery domain gets an id attribute. We exclude it from the file with the receiver's include setting.
FirstNamefirstNameNameGen, nameType firstNameGenRocket assigns NameGen automatically to attributes with "name" in the name.
(not in output)middleNameNameGenHelper only. Visible is switched off.

Full NamefullNameConcatGenFirst name, a space, middle name, a space, last name.
Phone NumberphoneNumberPhoneNumberGenSequential numbers, one per row.

Four choices deserve a reason.

  1. Why a separate middleName attribute? The syllabus defines Full Name as "FirstName MiddleName LastName". For the Full Name to contain the same first and last name as the other columns, it must refer to those columns, not generate new names. So the middle name needs its own attribute too.
  2. Which generator for the middle name? From docs NameGen's documented nameType choices are firstName, lastName, maleName and femaleName. There is no "middleName" type, so I use firstName, because middle names are usually given names. That is my choice, not a documented rule. The help centre also has a FullNameGen, which generates "a full name consisting of a first, middle, and last name with an optional title and suffix" (FullNameGen). It is a valid alternative, but it creates its own first and last names inside one value, so they would not match the FirstName and LastName columns. Its title and suffix percentages also default to 100, so you would have to set them to 0.
  3. Why reference attributes instead of linked generators? The documentation shows both. The linked way builds the full name inside one attribute with three generators and no helper attributes (Linked Generators Overview, "Generate a Person's Full Name"). Our task needs separate FirstName and LastName columns as well, so we build the pieces as real attributes and reference them. The overview notes the cost of this approach: the helper attributes "would then need to have the visibility Parameter set to false"; otherwise they appear in the output.
  4. Why PhoneNumberGen and not a random phone generator? PhoneNumberGen is documented, with parameters. A random alternative, RandomPhoneNumberGen, is named on its page and appears in an API example with the parameters useAreaCode and uniqueNumbers, but I had no page of its own for it, so I do not use it in the main lab.
What the docs do not say about phone format

The PhoneNumberGen page describes a sequence "100-1000, 100-1001, ..., 999-9999" and its preview screenshot shows numbers like (800) 600-1000. It does not list a format option. If your project needs 10 plain digits like ShopSphere's sample phone 9876543210, the documented route is a second linked generator such as StringRemoveGen (parameters reference, valueToRemove, removalType) or StringReplacementGen (value, fromText, toText) to strip punctuation. See the extension ideas in 21.9.

21.4 Before you start: the checklist

The lab has two halves. The design half happens in the GenRocket web platform in your browser. The run half happens on a computer with the GenRocket Runtime installed (see the overview chapter for what the Runtime is). You need both.

  • A GenRocket login with permission to create projects. If the New Project button is missing, the project page says you lack that permission and must ask the organization admin.
  • The Runtime installed and working: the command genrocket must be recognised in a terminal. The setup page for your operating system covers it, along with a supported Java version.
  • Your resource values set. From docs Each user sets the path for resource.output.directory (where output files are written) and resource.home.directory in the upper right of the Project Dashboard. The help centre recommends using different folders for output and home, and not the same path for all (resource values and your user profile).
  • Your user profile downloaded and placed in the .genrocket folder. Every time you change a resource value, download it again (Download menu, Download My Profile).
  • A text editor or spreadsheet to open the result.

If any of this is missing, ask your trainer. I did not have an account, so I could not test the install part.

21.5 Lab: generate 50 customer records

Lab: 50 customers with FirstName, LastName, Full Name and Phone Number

Goal: a comma-delimited file with a header row and exactly 50 data rows. Every step says what to do, why, and what you should see. Screenshots are the vendor's, from the help page named in each caption.

  1. Create a project.

    In the Projects pane of the Project Dashboard click New Project. Enter a name such as ShopSphereCustomers, add a description, and click Save. Name is the only required field; Project Type appears only if your organization has enabled it (then pick the one your trainer names). A project holds the data model for one application, and a new project automatically gets a default Project Version.

    The project appears in the Projects list, and the dashboard shows its Domains, Scenarios and other panes.

  2. Create the domain Customer.

    Select the project, then in the Domains pane click New Domain and choose New Domain from the menu (not Import). Enter Customer and Save. Domain names allow letters and numbers only. A domain is the "thing" you generate data for (see the chapter on domains).

    The Domain Dashboard opens. The domain has one attribute, id, and a variable global.Customer.loopCount equal to 1.

  3. Set the loop count to 50.

    In the Domain Variables table, click the pencil beside global.Customer.loopCount, enter 50 in Value, and click Save. The loop count is how many rows the domain generates; it defaults to 1, so skipping this gives a one-row file. Setting it on the domain (template) level cascades to scenarios.

    The Value column shows 50.

  4. Add the firstName attribute.

    In the Domain Dashboard click New Attribute, type firstName (camel case, as the platform expects), click Save. GenRocket assigns a generator by name, and for names containing "name" it chooses NameGen. Check the generator form: nameType firstName, caseType capitalize, sortOrder random, waitAmount 1. Change the fields if needed and click Save Generator. Capitalize gives "Asha" rather than "ASHA" or "asha"; random gives variety.

    The Preview pane lists first names such as Venice, Lonna, Ileana.

    Optional: type a number such as 1 into seed if you want the same 50 names every run. Leave it empty for fresh names each run. This is the seeding idea from the patterns chapter.

  5. Add the middleName attribute and hide it.

    New Attribute, name middleName, Save. NameGen is assigned again. Keep nameType firstName, caseType capitalize and sortOrder random. Now, in the upper part of the Attribute Dashboard, untick Visible and click Save (the attribute Save, not Save Generator). Visible controls whether receivers see the attribute. Our file must not contain a Middle Name column, but the Full Name still needs the value.

    The attribute exists and its Visible box is unticked. The Preview still shows names.

  6. Add the lastName attribute.

    New Attribute, name lastName, Save. In the NameGen form set nameType to lastName, keep capitalize and random, and Save Generator. Order matters: add lastName after middleName so it sits below both, because the Full Name attribute will sit below all three and can only reference attributes above it.

    The Preview lists surnames such as Brough, Carnevale, Hollifield.
