21.1 Words to know first

TDG (test data generation)
Creating test data from scratch with a tool instead of copying production. The syllabus uses the abbreviation. In this chapter it means doing it with GenRocket.
POC (proof of concept)
A small, quick trial that shows an approach can work before you commit to the full effort.
Loop count
How many rows a domain generates. The documentation variable is global.<DomainName>.loopCount and it starts at 1.
Reference
A parameter value that points at another attribute or generator, written like #{self.gen1} or #{Domain.attribute}, so one value is built from others.
Visible
An attribute setting. Visible means it is written to the output; not visible means it is used only as a helper.
Delimited file
A text file where each row is one record and columns are separated by a character such as a comma or tab. CSV is the comma version.
Output directory
The folder where files are written. GenRocket stores it as an organization resource named resource.output.directory, set per user.
User profile
A small file downloaded from GenRocket Cloud that links your computer to your licence. It goes in a .genrocket folder and is needed to run a scenario.

From docs GenRocket's CI/CD page lists four facts you need before you can generate anything: the object (for example User or Customer), the properties of it (name, phone number), what data each property should hold, and the format to deliver it in (CSV, JSON, XML) (Automating Data Generation using CI/CD Pipeline). Those map straight onto GenRocket's domain, attributes, generators and receiver. Collect those four answers for every use case. Our lab: object Customer, properties FirstName, LastName, FullName and PhoneNumber, generators NameGen, ConcatGen and PhoneNumberGen, format CSV.

21.2.2 Stage 2: the proof of concept

A POC picks one narrow use case and builds it end to end, so you learn the tool and find surprises early. A good POC:

  • Uses one domain, a few attributes and a small row count (the 50-record lab fits).
  • Covers the whole path: model, design, deliver, run, check the file. A half-built POC proves nothing.
  • States success criteria in advance, for example "50 rows, no empty values, phone numbers all the same length, runs in a command line without manual edits".
  • Records what was hard: licence, runtime install, access to the output folder.

From docs The documentation frames GenRocket's own method as Model, Design, Deploy, Manage (The GenRocket Methodology, whose text is a title and a video that I could not watch, and the CI/CD page above that spells the four steps out). The POC exercises the first three: you model a Customer domain, design its attributes and scenario, and deploy by running the scenario. "Manage" is stage 4.

21.2.4 Stage 4: the deployment plan

The deployment plan says how generation becomes routine.

  • Roles. The documentation names the "Power User, a Test Data Engineer (or TDE)" as the start of the workflow (Test Data Workflow, again a title and a video). That is your target role. Decide who models, who approves, who runs.
  • Where scenarios live. Manual download from the web platform, or G-Repository, which the G-Cases page calls "Best Practice" because users do not download files.
  • How it is triggered. The CI/CD page says the Runtime can be triggered "from within CI/CD pipeline script using shell or batch command", or through a REST request to GMUS (GenRocket Multi-User Server).
  • Versions and changes. Project versions hold each release's model. When the application's tables change, someone updates the domains.
  • Data variety on demand. Test Data Cases (G-Cases) change volume and variety without editing scenarios.
  • Exit criteria. Define what "done" is: all use cases served, runbook written, owners named.
Why plan before you click

Teams that start with the tool often generate data nobody asked for, in a format nobody can load. A one-page plan with the four stages prevents that. For the final presentation, a clear plan plus a working POC is a much stronger story than the POC alone.
