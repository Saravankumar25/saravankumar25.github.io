Every earlier Informatica chapter ended the same way: "then you put it in a plan and run it". The discovery, subsetting, masking and generation chapters described what to do to data. This chapter covers the machinery that actually does it, and what happens afterwards: the plan that packages the work, the workflow TDM generates from it, the Monitor where you watch it, the reports that prove what happened, and the Test Data Warehouse where the result can be stored, versioned and restored.

If you already know ETL from the ETL from scratch chapter and the ETL and TDM chapter, here is the key idea in one line: a TDM workflow is an ETL job that TDM writes for you. You describe the data and the rules; TDM builds the mappings and runs them. The Day 45 syllabus asks you to understand generation in Informatica; the plan and workflow side is what turns your rules into rows.

16.1 Words to know first

Plan
The saved definition of one operation: which components, which source and target connections, which settings. It does nothing until you generate and run a workflow from it.
Workflow
The runnable job generated from a plan. It contains PowerCenter mappings and sessions and is run by the PowerCenter Integration Service.
Mapping
PowerCenter's design of how data flows from a source through transformations to a target. TDM writes these for you.
Session
One run of a mapping inside a workflow. A workflow may have several sessions.
Job
Anything you start in Test Data Manager that appears in the Monitor: an import, a profile, a workflow generation, a workflow run, a reset.
Connection
Saved details for reaching a database or file location. A plan names its source, target and helper connections.
Parameter
A named placeholder (for a connection, an owner or a filter value) whose value you supply at run time, so one plan serves many runs.
Test Data Warehouse (TDW)
A central store for versions of test data, so teams can save a known-good state and restore it later.
Data set
A named collection of one or more tables stored in the warehouse. Each time you store it again, a new version is created.
Reset
Copying a data set version from the warehouse back to a target so a test environment returns to a known state.
Data pack
A data set published to the self-service portal for testers who do not use Test Data Manager.
Data coverage
A check of whether a data set has enough rows for each combination of values your test cases need.

16.2 Plans and workflows: the big picture

The analogy stops at one point. A hand-written ETL job is a thing you maintain. A TDM workflow is disposable: change the plan, generate again. The guide says so directly: when you update or delete a plan component you must generate and run the plan again to apply the change (p.275).

16.2.1 Plan types and what each can contain

Plan components by operation (User Guide 10.5.10, pp.274-277, 306)
ComponentWhat it isUsed in
RuleA masking rule, assigned to a policy or standaloneMasking plan
PolicyA set of data domains, each with rulesMasking plan
EntityRelated tables with a parent-child hierarchy and filter parametersSubset or generation plan
GroupA set of tables to copy to a target subset databaseSubset plan
TemplateA reusable bundle of subset componentsSubset plan
TableTarget table columns that have generation rule assignmentsGeneration plan
XSD fileAn imported XML source definitionSubset, masking or generation plan

The practical plan types are:

  • Masking, subset, or masking plus subset in one plan. If both kinds of component are present, subset has priority: TDM subsets first, then masks columns in the subset data that have assignments. It does not apply masking to source rows outside the subset, even if they are part of a cascade (p.275).
  • Generation plan. Only entities, tables or XSD files. You cannot add masking or subset components to the same plan, and the reverse (pp.274, 276). See the Informatica generation chapter for the reasoning.
  • Hadoop plan. Groups and masking components for Hadoop sources and targets. No subset or generation (p.306).
  • Data set (related data set) plan. Created from a data set in the warehouse to cut a smaller data set from it (p.251).
  • Reset and restore plans appear in the guide's notes about pre and post workflows (p.277); resets are covered in the warehouse section below.

16.2.2 The guide's task list, with reasons

  1. Create a plan with a name and description.

    The name becomes part of the workflow and job names you will search for in the Monitor.

  2. Add masking rules and policies, subset entities, groups and templates, or generation entities and tables.

    This is the "what". Remember that generation cannot share a plan with the other two (p.275).

  3. Switch individual masking rules off or on, and optionally change subset criteria.

    Lets you test a plan with only some rules, without deleting anything.

  4. Configure plan settings: properties, error and recovery strategy, advanced settings.

    This is the "how" and "where".

  5. To store the result, select the Test Data Warehouse as the target connection.

    That is what creates a data set.

  6. Optionally configure test tool integration, and override settings per data source or table.

    For flat-file output to HP ALM, or exceptions to the plan-wide rule.

  7. If the plan has parameters, download the parameter file to review values.

    Parameters let one plan serve many runs.

  8. Generate the workflow (or generate and run in one step), pick parameter values, run, and monitor.

    Generating builds the mappings; running executes them.

Condensed from User Guide 10.5.10, p.275.

16.3 The ShopSphere story we will follow

ShopSphere's QA team needs a safe, small, realistic copy of SHOPSPHERE_PROD for the next release of Customer Orders. They want to refresh it quickly after every destructive test run. The path through this chapter:

  1. Discovery.

    A profile has already tagged ssn, tax_id, phone, email, first_name and last_name as sensitive data domains (the discovery chapter).

  2. Masking plus subset plan.

    An entity with CUSTOMERS as driving table pulls in its orders and items. A limit keeps about 5 percent of customers. Masking rules disguise the sensitive columns in that small slice.

  3. Workflow.

    Generate and run it. The target is the Test Data Warehouse.

  4. Monitor and reports.

    Watch the job turn to Success, read the session counts, run the Row Count report for the audit file.

  5. Store.

    The warehouse now holds data set SHOPSPHERE_MASKED, version 1.

  6. Reuse.

    After a test run damages the data, testers reset version 1 back into the test database, cut a smaller related data set for a hotfix, and check coverage.
