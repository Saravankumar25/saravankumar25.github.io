16.10 Generating and running a workflow

You generate a workflow from a plan to perform subset, masking and generation. When you generate, the PowerCenter Repository Service creates the mappings. When you start, the PowerCenter Integration Service performs the work. You can generate and start in a single step (User Guide 10.5.10, p.308).

  1. Generate: in the project click Execute, select a plan, Actions > Generate Workflow.

    This builds mappings and stores them. Do it again whenever the plan changes.

  2. Choose whether to run now or later.

    You may generate now and execute on a schedule.

  3. Execute: Actions > Execute Workflow from the Plan properties or Workflow view.

    If the plan has several workflows, open the Workflow view, select one and execute it. A workflow name contains the project, plan, connection and table names (p.309).

  4. Pick the Integration Service and run now or schedule.

    You must select the service configured in the Test Data Manager Service.

  5. Choose parameter values if the plan has parameters.

    See the parameters section.

  6. If the target is the warehouse, optionally publish to the self-service portal, then click Generate and Execute.

    Publishing creates a data pack for testers who cannot use Test Data Manager.

    The workflow appears in the Workflow Executions view and in Monitor.

Steps from User Guide 10.5.10, pp.308-311. To do both in one go use Actions > Generate and Execute on the Plan | Properties page.

Constraints that will not turn back on

If you ran the workflow with Disable Constraints and TDM then fails to re-enable them after loading, the workflow fails. Enable the constraints in the database by hand and run the workflow again (p.311).

16.10.1 The Workflow Executions view

This view shows the current workflow for the plan and all earlier ones, even for workflows that no longer exist in the plan. Click the Job ID to see the workflow log. Fields: Job ID, Name, Description (profiling, import or workflow), Status (In Queue, Running, Success, Error), Start and End Date/Time, User (pp.311-312). The Sessions tab lists each session, with Source Rows Succeeded and Failed and Target Rows Succeeded and Failed. Click the session name for Session Details, with the tables processed, affected rows, rejected rows, throughput and last error message (pp.313-314).

16.11.3 Reading the logs

Select a job and open the Logs tab. The TDM server writes TDM logs; the PowerCenter Integration Service writes session and workflow logs (a Data Integration Service does for Hadoop). TDM always writes console logs when a job is triggered, so if job logs are missing, read the console log (User Guide 10.5.10, p.318). Each message has a Date/Time, a Severity and a Description that explains the error, its cause and the solution.

Severity levels (p.319)
SeverityMeaningHow to react

InfoNormal operation, no problemSkim for the timeline

TraceMore specific than Debug, code pathsRare, for support
  1. Click Monitor, then the job ID, then the Logs tab.

    The log belongs to that job only.

  2. Filter by severity Error, and by date range or a keyword.

    Real logs are long; the first Error line is usually the cause and the rest are knock-on effects.

  3. Select a message and click Download to keep the log file.

    Attach it to a ticket. To see console logs, select the job ID and use Actions > View Console Logs.

  4. For a workflow, click its job ID to open the workflow details, then the Sessions tab.

    Look for a session whose Target Rows Failed is not zero.

  5. Click the Session ID to see tables processed, affected and rejected rows, error messages and the session log.

    This is where "which table broke" is answered.

    You can name the failing session, table and message.

Steps from User Guide 10.5.10, pp.319-320.

Two numbers that should agree

For a straight copy, Source Rows Succeeded and Target Rows Succeeded should match. If targets are lower and Failed is zero, check for an update strategy or a filter in the plan. If Failed is not zero, rows were rejected; look at the session's last error message.

16.13 Data coverage analysis, at overview level

Having a data set is not the same as having enough of the right data. Data coverage analysis checks whether a data set holds a minimum amount of data for specific test cases. It does pairwise analysis: you choose two columns and see how many rows exist for every combination of their values, drawn as a grid (User Guide 10.5.10, p.259). The guide's example: a card application needs enough customers for every card type in every location.

Visual referenceInformatica TDM 10.5.10 User Guide, p.266, figure "data coverage analysis page". I rendered this page. It shows a grid with one column's values (DEPARTMENT) along the bottom axis and another's (JOB) up the side, with most cells white, some light blue and a few darker blue, a green-bordered selected cell, and a side panel listing the task columns, with numbered callouts for axes, filters, Analyze, Fill Cell and Mark as invalid. What to look for: white cells are gaps.

Cell colour tells density: white means no data, light blue means below the minimum threshold you set, dark blue means more than the threshold (p.261). Steps in outline (pp.260-261):

  1. Open the data set, click Data Coverage, Actions > New, give a name and a minimum threshold.

    The threshold is the least number of rows you accept as "dense enough".

  2. Select a master table and optionally related tables.

    Related tables let the axes come from joined tables.

  3. Create task columns as Use as is (individual values, good for low-cardinality columns), Range (numeric or date ranges) or Mapping (group values, for example states into regions) (pp.261-262).

    Binary columns cannot be used, and some types are excluded for each column type (p.263).

  4. Put one column on the X axis and one on the Y axis, optionally add up to two filter columns, click Analyze.

    The grid shows data density.

  5. Fix gaps: mark meaningless cells as invalid, or select a gap and use Fill to move rows from dense cells.

    Fill runs a separate job per source cell. If a needed parent row is missing, a dialog asks you to type values, matching the column data types (pp.267-269).

16.14 Command-line tools: ilmcmd, tdwcmd and tdwquery

TDM ships three small command-line programs. All are batch files on Windows and shell scripts on UNIX. Command, option and object names are case sensitive, and you can show syntax with the -h option. Why bother with a command line? Scripts and schedulers can call it, so a nightly refresh needs no human clicking.

The three tools at a glance (User Guide 10.5.10, pp.326-350)
ToolPurposeDefault install folder
ilmcmdA subset of Test Data Manager tasks: import and export XML objects, search, validate, delete, generate and run workflows, show workflow status, reset data sets, list plans of a data set version, generate and run data set subset plans<installation directory>\utilities\ilmcli\bin
tdwcmdList test data warehouse details: the repository, the warehouse, connections, data sets, data set versions and version tables<TDM installation directory>\utilities\tdwcli\bin
tdwqueryRun SELECT queries (joins, aggregates, WHERE) on tables of one data set in the warehouse<Informatica installation directory>/TDM/utilities/tdwquery

16.14.1 ilmcmd

Limits: you need the required privileges and, for project tasks, project permission. You cannot use it to search data generation objects (pp.327, 333). If Test Data Manager runs on HTTPS you must first import the browser certificate, create a keystore with keytool and set the trust store location and password in userConfig.ilm (p.327).

Examples printed in the guide (pp.329-336):

ilmcmd -wf -g -Project Infa_Project -pn Plan_NameMasking
ilmcmd -wf -gs -JobId 360
ilmcmd -wf -ex -Project TDM -pn Plan_NameMasking -is PCInteg
ilmcmd -e -ot Policy -n Policy_Customer -f C:\Informatica\ILMServer\CLI\Policy_Customer.xml
ilmcmd -r -dvn "RESET Version1" -rf "C:\Documents\ResetObject.json" -ris PIS

They generate a workflow, get a workflow's status, run a workflow, export a policy, and reset a data set version using a reset file. The guide also lists commands to import and delete objects, ListPlans (plans in a data set version), TDWPlanGenerate, TDWPlanExecute and TDWPlanGenExe for related data set plans, Update Host for moving plans to another host, and a way to update stored passwords (pp.334-342). Exportable object types include rules, policies, data domains, entities, groups, templates, profiles, projects, data sources, source definitions, connections and plans (p.330).

16.14.2 tdwcmd and tdwquery

tdwcmd --list with one of Repository, TestDataWarehouse, Connection, Dataset, DatasetVersion or DatasetVersionTable, plus the host, port, user, password, security domain, domain name and Test Data Warehouse Service name, prints details (pp.345-347). It lists; it does not change anything. For tdwquery you first edit userConfig.ilm with the service URL, user, password, domain, namespace, service and warehouse names and the data set version name. Then you run, for example, tdwquery "SELECT * FROM td_empdetails" (pp.348-349). The user needs the View Data in Data Set privilege and at least read permission on the data set.

Passwords on the command line

The guide's tdwcmd examples place the password right in the command (-pd Administrator). Anyone who can read your shell history or the process list can read it too. In real scripts, follow your organisation's secret-handling rules, and never commit such a script. That advice is mine, not the guide's.
