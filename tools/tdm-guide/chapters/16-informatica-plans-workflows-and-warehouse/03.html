16.10 Generating and running a workflow

You generate a workflow from a plan to perform subset, masking and generation. When you generate, the PowerCenter Repository Service creates the mappings. When you start, the PowerCenter Integration Service performs the work. You can generate and start in a single step (User Guide 10.5.10, p.308).

  1. Generate: in the project click Execute, select a plan, Actions > Generate Workflow.

    This builds mappings and stores them. Do it again whenever the plan changes.

  2. Choose whether to run now or later.

    You may generate now and execute on a schedule.

  3. Execute: Actions > Execute Workflow from the Plan properties or Workflow view.

    If the plan has several workflows, open the Workflow view, select one and execute it. A workflow name contains the project, plan, connection and table names (p.309).

  4. Pick the Integration Service and run now or schedule.

    You must select the service configured in the Test Data Manager Service.

  5. Choose parameter values if the plan has parameters.

    See the parameters section.

  6. If the target is the warehouse, optionally publish to the self-service portal, then click Generate and Execute.

    Publishing creates a data pack for testers who cannot use Test Data Manager.

    The workflow appears in the Workflow Executions view and in Monitor.

Steps from User Guide 10.5.10, pp.308-311. To do both in one go use Actions > Generate and Execute on the Plan | Properties page.

Constraints that will not turn back on

If you ran the workflow with Disable Constraints and TDM then fails to re-enable them after loading, the workflow fails. Enable the constraints in the database by hand and run the workflow again (p.311).

16.11.3 Reading the logs

Select a job and open the Logs tab. The TDM server writes TDM logs; the PowerCenter Integration Service writes session and workflow logs (a Data Integration Service does for Hadoop). TDM always writes console logs when a job is triggered, so if job logs are missing, read the console log (User Guide 10.5.10, p.318). Each message has a Date/Time, a Severity and a Description that explains the error, its cause and the solution.

Severity levels (p.319): Error (the TDM server failed an operation; start here), Warning (an operation that might cause an error), Info (normal), Debug and Trace (increasingly detailed server operations, mostly for support).

  1. Click Monitor, then the job ID, then the Logs tab.

    The log belongs to that job only.

  2. Filter by severity Error, and by date range or a keyword.

    Real logs are long; the first Error line is usually the cause and the rest are knock-on effects.

  3. Select a message and click Download to keep the log file.

    Attach it to a ticket. To see console logs, select the job ID and use Actions > View Console Logs.

  4. For a workflow, click its job ID to open the workflow details, then the Sessions tab.

    Look for a session whose Target Rows Failed is not zero.

  5. Click the Session ID to see tables processed, affected and rejected rows, error messages and the session log.

    This is where "which table broke" is answered.

    You can name the failing session, table and message.

Steps from User Guide 10.5.10, pp.319-320.

For Hadoop plans you see mapping logs only: no workflow logs and no row counts (p.320). On a clean copy run the Source and Target Rows Succeeded counts match and both Failed counts are zero; a non-zero Failed count means rejected rows, so read the session's last error message.

16.13 Data coverage analysis, at overview level

Having a data set is not the same as having enough of the right data. Data coverage analysis checks whether a data set holds a minimum amount of data for specific test cases. It is pairwise: you choose two columns and see how many rows exist for every combination of their values, drawn as a grid (User Guide 10.5.10, p.259). Cell colour shows density: white means no data, light blue is below the minimum threshold you set, dark blue is above it (p.261).

Visual referenceInformatica TDM 10.5.10 User Guide, p.266, figure "data coverage analysis page". A grid with one column's values along the bottom and another's up the side, mostly white cells with some light and dark blue, a green-bordered selected cell and a side panel of task columns. What to look for: white cells are the gaps.
  1. Open the data set, click Data Coverage, Actions > New, name the task and set a minimum threshold.

    The threshold is the least number of rows you accept as "dense enough".

  2. Select a master table (and optionally related tables), then create task columns.

    Columns can be Use as is (individual values), Range (numeric or date ranges) or Mapping (group values, such as states into regions); binary columns are not allowed (pp.260-263).

  3. Put one column on each axis, optionally add up to two filter columns, and click Analyze.

    The grid shows density.

  4. Fix gaps: mark meaningless cells invalid, or select a gap and use Fill to move rows from dense cells.

    Fill runs a separate job per source cell. If a needed parent row is missing, a dialog asks you to type values (pp.267-269).

Coverage grid (schematic, ShopSphere)
threshold = 5 customers      total_amount band
zip band        under 500    500-2000    over 2000
56xxxx              9           7           0   <- gap
60xxxx              6           2           1   <- below threshold

Here "large order from a Bengaluru customer" has no data. Fill moves rows in, or you generate more. Fill changes the data set itself (p.268), so keep a version first. Coverage jobs show in Monitor as Data Coverage Analysis and Fill Cell, run by the Data Integration Service (pp.26, 316-317).

16.14 Command-line tools: ilmcmd, tdwcmd and tdwquery

TDM ships three small command-line programs (User Guide 10.5.10, pp.326-350). Scripts and schedulers can call them, so a nightly refresh needs no human clicking. Names of commands, options and objects are case sensitive, and -h shows the syntax.

The three tools at a glance
ToolPurpose
ilmcmdA subset of Test Data Manager tasks: import and export XML objects, search, validate, delete, generate and run workflows, show workflow status, reset data set versions, and run data set subset plans
tdwcmdList test data warehouse details: repository, warehouse, connections, data sets, versions and version tables (it lists and changes nothing)
tdwqueryRun SELECT queries (joins, aggregates, WHERE) on the tables of one data set in the warehouse

Examples printed in the guide for ilmcmd (pp.329-338): generate a workflow, get its status, run it, export a policy, and reset a data set version from a reset file. It cannot search data generation objects (p.333), and over HTTPS you must first set up a keystore (p.327).

ilmcmd -wf -g -Project Infa_Project -pn Plan_NameMasking
ilmcmd -wf -gs -JobId 360
ilmcmd -wf -ex -Project TDM -pn Plan_NameMasking -is PCInteg
ilmcmd -r -dvn "RESET Version1" -rf "C:\Documents\ResetObject.json" -ris PIS

For tdwquery you first fill in userConfig.ilm (service URL, user, domain, warehouse and data set version), then run for example tdwquery "SELECT * FROM td_empdetails" (pp.348-349).

Passwords on the command line

The guide's tdwcmd examples put the password in the command (-pd Administrator), where shell history can expose it. Follow your organisation's secret-handling rules.
