16.4 Creating plans

16.4.1 A data masking and data subset plan

You may combine subset and masking in one plan or keep separate plans; generation needs its own (User Guide 10.5.10, p.304). The wizard, with reasons:

  1. Open the project, click Execute, then Actions > New. Enter a plan name and optional description.

    Plans belong to a project so they can use its rules, entities and parameters.

  2. Click Add Masking Components and select policies and rules. Click Next.

    Pick only what this run needs. You may add rules assigned to a policy and rules that are not.

  3. Click Add Subset Components and select entities, groups, templates or XSD files. Click Next.

    This is where you say which tables to copy. If an entity is already inside a chosen template, you cannot add the same entity again (p.277).

  4. Skip the generation step with Next.

    Generation cannot be combined here.

  5. Switch off any masking rule you want to skip, using the check box and Off.

    A cheap way to test one rule at a time.

  6. Filter subset components: choose a basic or advanced expression, or click Limit and choose percentage, absolute value or an interval of rows. Click Next.

    An XSD subset component cannot have its criteria overridden. Details in the Informatica subsetting chapter.

  7. Configure connections and other properties.

    For a flat-file target you can set test tool integration. If you choose the test data warehouse as the target you enter the data set properties. With an XSD source you cannot add other source types. Click Next.

  8. Optionally override plan settings for one data source, or data source settings for one table. Click Finish.

    Overrides handle the one table that needs special treatment.

    The plan appears in the project's Execute list. Nothing has run.

Steps from User Guide 10.5.10, pp.304-305.

16.4.2 A data generation plan

The wizard is the same, but you skip the masking and subset pages, add generation components (entities and tables), enter the number of records and set connections (p.305). The full walk-through, with ShopSphere examples, is in the Informatica generation chapter. There is also a one-column ad hoc generation plan reached from Define | Data Generation with Actions > Generate and Execute (p.306).

16.4.3 Hadoop plans in one paragraph

Choose the Hadoop plan type when you create a plan. You can add masking components and groups only; sources can be Oracle, DB2, Sybase, Microsoft SQL Server, Hive, flat file or HDFS, and targets relational (including Hive) or HDFS in None, Avro or Parquet format. The engine can be Blaze or Spark, and a Data Integration Service runs it instead of PowerCenter (pp.291-292, 306). We do not use Hadoop in ShopSphere.

16.5 Plan components in practice

16.5.1 Masking and subset components

Masking components are policies and rules. You may restrict a run to some of them, and you can turn masking on or off for a specific column when you set plan criteria. A catch: if a plan contains a Format Preserving Encryption rule set to decrypt, no other masking rules may be in that plan, so disable the others (p.292). Subset components are entities, groups, templates or XSD files (p.293).

Component criteria. For each column of a subset component, choose a filter method in the Plan Components panel: Custom (a Basic expression with an operator and operand, or an Advanced expression with several columns, functions and parameters) or Limit (percentage, absolute value or interval of rows). Global parameters carry an asterisk in lists but not inside an advanced expression (p.294). To disable masking for a column click the masking component, select the column in the Criteria panel and click OFF (or ON) (p.294).

ShopSphere: shrink to about 5 percent

The plan holds one entity (driving table CUSTOMERS, children ORDERS and ORDER_ITEMS) and one policy PII_Policy. For the entity's customer criteria choose Limit by percentage and enter 5. Subset runs first, so only the customers in the slice, and their orders and items, are masked (p.275). Whether 5 percent applies to the driving table or the whole entity follows the subset rules explained in the subsetting chapter, so check the Row Count report after the first run.

What subset-then-mask does to three rows

This is my illustration of the rule on p.275. Suppose the entity keeps customers 1001 and 1003 and leaves out 1002. Subset happens first, so 1002 never reaches the target. Masking then changes columns only in the rows that arrived.

Rows that are not in the subset are not masked and not copied, even when they are part of a cascade (p.275). That is exactly what you want: the less sensitive data you move, the less you must protect.

16.5.2 Connections

A workflow connects to the Integration Service, the TDM repository and one or more connection objects. You choose them in the plan (p.276):

Connections you can set in a plan (User Guide 10.5.10, p.276)
ConnectionPurpose
SourceWhere data is read from
TargetWhere data is written: relational, test data warehouse, flat file or Hadoop HDFS, or a variable
StagingA database for temporary staging tables; a default comes from Preferences. Recommended to be the source connection for cyclic subsets and similar cases (p.286).
LookupA database that holds lookup tables
StorageA database for storage tables used for repeatable masking (substitution and expression); default from Preferences
TeradataAn ODBC connection to Teradata
DictionaryA database with a dictionary table for substitution, email masking and data generation

Plans also need connections to repositories, and this has a hard limit. An offline job needs three connections to the TDM repository, each workflow in a multi-workflow plan needs one more, and you can run at most eight workflows at a time (eight workflows need 11 connections). Extra workflows wait in the queued state (p.276).

The guide also states that Use Source Connection as Target Connection is for in-place masking, where data is changed in the same database it came from (p.279). That is risky; we never do it on ShopSphere's production copy.

16.5.3 Pre and post workflows, and target SQL

You can run another existing workflow in the project's PowerCenter folder before the TDM workflow (it must finish successfully first) or after all TDM workflows complete successfully. Example from the guide: copy files from production area to test area, mask them, then run database statistics. You can disable triggers before and enable them after. Not available for Hadoop, reset and restore plans (p.277).

You can also run target pre SQL and post SQL in the plan's Advanced Options, using the variables $OWNERNAME, $SCHEMA and $TABLENAME. Example from the guide: TRUNCATE TABLE $OWNERNAME.$TABLENAME; deletes all rows before the load (pp.277-278). Use these variables so one statement works across environments.

16.6.2 Update strategy

Treat source rows as Insert or Update, and Update as Update, Insert or Update else Insert (update rows that exist, insert the rest). Choosing the same connection for source and target switches "treat as" to Update (p.284). Update else Insert is also what the guide uses when restoring from a backup after a failed reset (p.247).

16.6.4 Advanced options (selection)

  • Tables Per Workflow: number of tables per workflow, default 10 (p.287). More tables than that means several workflows from one plan.
  • Max Parallel Sessions: sessions that may run at once, relevant when indexes and constraints are disabled (p.287).
  • Data Integrity for Subset: Referential only; Transactional Integrity for Major Relation Type (default); One-way; Two-way (p.287). See the subsetting chapter.
  • Email: notification address, subject and text for when the plan finishes (p.287).
  • Target Load Type: Normal (default) or Bulk. Bulk is faster but limits recovery because no database logging happens (p.288).
  • Source and Target Schema Name: use when the tables sit in a different schema; may be a parameter (p.288).
  • Batch Update and Batch Size: for in-place masking (p.288).
  • Shared Storage Table, Cache Size, Storage Commit Interval: tuning for repeatable masking (pp.289-290).
  • Enable special characters in metadata: default No (p.289).
  • Reset Recovery prefix: used only to restore after a failed reset (p.289).
  • Locale, Datetime Format String, Enable High Precision, DTM Buffer Size, SSN High Group File, Use SoftHSM: specialised settings (pp.287-290).

16.6.5 Log settings

You can keep workflow and session logs by run (a set number of historical logs plus the latest) or by time stamp (a log for every run, with a time stamp). Session logs can roll over by maximum size in megabytes or by time period, and you can also write a text version in addition to the binary log (pp.290-291). The default for rollover size and time is zero, meaning no limit.

16.6.6 Data set properties (when the target is the warehouse)

Choosing the test data warehouse as the target connection makes a Data Set Properties section appear: Name (required), Description, Data Set Version (not editable), Application, Application Version and Tags separated by commas (p.281). More in the warehouse section.

16.7 Source, table and file overrides

Many plan settings can be overridden for one data source or one table. If a property is not offered at the data source level, the plan level value applies (p.295). Overridable examples: connections, flat-file name, directory and delimiter (Delimited by default, comma), row separator, optional quotes, headers (default Yes), file encoding, source and target schema names, pre and post SQL, batch size, table name overrides and partitioning (Pass Through, Key Range or Database Partitioning) (pp.295-301).

For flat-file sources you can supply a file list: a text file naming one source file per line (with a path if it is not in the same directory). All files in the list must share the same properties (p.303). XML (XSD) sources have their own directory, file name and null-representation settings (pp.302-303).

Start at the plan level

Set everything at the plan level first and override only the one table that needs it. Every override is one more thing to forget when you copy the plan to another environment.

16.8 Parameters and parameter files

Parameters let one plan serve many runs. You may use project parameters and global parameters (created by an administrator, shown with an asterisk) in connections, owner names and filter criteria (pp.275, 279). In an entity or plan you can use a parameter instead of a fixed value in a criterion.

A parameter file lists every parameter used in a plan with its default value. Criteria parameters carry an ignore flag that defaults to "N" (include); set it to "Y" and save to ignore that criterion in a run. Parameters you cannot override do not change, and the workflow logs an error (pp.309-311). Create one with Actions > Create Parameter File on the plan. If you use parameters for connections, the parameter file must be on the node that runs the Test Data Manager Service, in the same path on every node (p.279).

When you execute the workflow you choose how values are supplied (pp.310-311):
