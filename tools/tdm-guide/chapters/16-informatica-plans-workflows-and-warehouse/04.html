16.15 The Test Data Warehouse

Test data goes stale and gets damaged. A tester deletes orders to check a refund flow; a batch job rewrites prices; another team starts testing on the same tables. Re-running the whole subset and masking plan each time is slow. The Test Data Warehouse solves this: it is a central location that stores multiple versions of test data, and multiple Test Data Manager services can use the same warehouse, so teams share one store (User Guide 10.5.10, p.236).

The guide's scenario: before any tests, store the original data as a data set. After each team finishes, store the modified data as another version. To return the environment to its original state, restore the version holding the original data. You can restore any version (p.237).

16.15.1 What is behind it

You create a Test Data Warehouse Service in the Informatica Administrator tool. That application service manages two relational databases (pp.26-28, 236):

  • the test data warehouse repository, which holds project metadata (plan information, version, tags) and source table metadata of each data set;
  • the test data warehouse itself, which holds the actual source data you put in data sets.

The service copies the metadata created when you make a data set and creates the data set tables in the warehouse (p.27). Workflows that store data in the warehouse need connections to the external source databases, the repository and the warehouse (p.28). Data coverage tasks run on the Data Integration Service (p.26).

A plain database backup

Restores a whole database, usually needs a DBA, and carries no test metadata. Hard for a tester to find "the data from the refund tests".

A warehouse data set (concept view)

Holds chosen tables, with application name, version and tags you can search. Testers with Execute permission can reset it, or pick it up from the portal. The analogy to a backup stops here: a data set can also be edited and sliced into related data sets.

16.16 Data sets, versions and tags

A data set is a collection of one or more tables from one or more data sources, and generally matches one or more test cases (User Guide 10.5.10, p.238). You create one when you subset production, make a masked copy, or generate data, by selecting the test data warehouse as the target when the plan runs. It stores source table metadata and plan metadata, and you can search by those properties.

16.16.1 Creating a data set

  1. Check the tables first.

    You cannot create a data set from tables with user-defined data types; mark such columns Restricted under Discover > Columns. Tables without primary keys need logical keys, or a reset might fail. Character columns with precision 4000 should be edited to 3,999 or less (p.239).

  2. Build a plan (masking, subset or generation) and in the plan settings select Test Data Warehouse from the target connections.

    The Data Set Properties section appears.

  3. Enter a data set name (default: the plan name), application name, application version and tags.

    A new name creates version 1. TDM fills in the version number (p.240).

  4. Finish the plan and click Actions > Generate and Execute.

    Optionally publish to the self-service portal in the same step.

    Monitor shows the job. On success the data set appears in the Data Sets view.

Condensed from User Guide 10.5.10, pp.239-240.

16.16.2 Versions and tags

Test data changes during testing. You make a new version in two ways (p.238):

  • rerun the same plan without changing the data set name; or
  • create and run a different plan and enter the same data set name.

Tags are comma-separated words (test case name, ticket number) used to filter and search data sets. Row-level tags mark individual rows, to track edits or to select rows for a related data set (p.239). Tag text may include spaces and special characters but not a comma (pp.247, 255).

ShopSphere: naming

Data set SHOPSPHERE_MASKED, application CustomerOrders, application version 2.4, tags baseline, masked, 5pct. After the regression run, rerun the plan or run a different plan with the same data set name to get version 2 tagged after-regression.

16.17 Restoring: the reset

Reset moves data from a data set version in the warehouse to a target, so a test environment goes back to a known state (User Guide 10.5.10, p.240). You can make the reset delete everything in the target and replace it, which suits tables you do not share. Or you can keep other testers' data in the target and replace only the part that overlaps the data set. In selective resets TDM runs an SQL script that backs up the deleted data in the target (p.241).

16.17.1 Master and transactional tables

Reset behaves differently per table, according to how you classify it (p.241):

Table classification and reset behaviour (pp.241-242)
ClassMeant forReset action by defaultShopSphere
MasterRecords shared by all testersNo deletes. Upsert: update rows that exist in both, insert rows that exist only in the data set.CUSTOMERS, PRODUCTS
TransactionalDescendants of master tables; rarely sharedInsert. If a record already exists the insert fails. Deletes cascade from top-level transactional tables (direct children of master tables).ORDERS, ORDER_ITEMS

Unclassified tables are treated as transactional. To classify: open the data set, Plan Components tab, Tables tab, Edit Table Type. When you mark a table as master you must choose to mark all descendants as transactional, or all other tables (pp.241-242). Verify the classification before every reset.

16.17.2 Reset options

  1. Open the data set version you want and click Actions > Reset.

    The source is fixed: the warehouse.

  2. Select the target connection.

    Usually your test database.

  3. Choose reset settings.

    Truncate Tables deletes all target data and loads the data set, disabling constraints and indexes; no backup is made. Disable Constraints and Indexes speeds things up. Upsert in Transactional Tables avoids insert failures when parents changed. Insert in Master Tables skips the existence check but needs all tables to be master and no overlapping records.

  4. Enter reset recovery properties if you are not truncating: a Backup Recovery Prefix and the Backup Recovery User Name (schema) for backup tables named <prefix>_<tablename>.

    This is your undo.

  5. Review Error and Recovery and Advanced Settings; optionally override at data source or table level; choose the PowerCenter Integration Service; run now or schedule.

    Then follow the job in Monitor.

    A "Reset Data Set from Test Data Warehouse" job reaches Success and the target matches the version.

Steps from User Guide 10.5.10, pp.243-244.

Visual referenceInformatica TDM 10.5.10 User Guide, p.245, figure "reset process". I rendered this page. It is a flowchart: Reset leads either to "Full restore" (truncate tables, insert tables from the data set, success message) or to "Reset with default settings", which validates table classification (not valid: exit with error), creates staging tables to find candidates for cascade delete, then asks whether to disable constraints and indexes. Yes goes to a parallel transactional cascade delete and insert; No goes to a sequential one. Both then upsert master tables in parallel, re-enable constraints, and show the success message. What to look for: a note says the backup tasks are not drawn.

16.17.3 Speed versus downtime

Disabling constraints lets TDM load several tables in parallel, so resets finish sooner. But constraints are disabled for the entire table, and while they are off, other testers' tests that use those tables might fail. If tables are shared, a slower reset may be better than downtime; if no one else is using them, disable constraints (pp.242-243). As good practice, create an index on foreign keys in the target so child-record deletes are quick (p.243).

16.17.4 Failure and special cases

  • Failed reset: if recovery was enabled, backups are kept. Restore with a separate plan: put the backed-up tables in a group, add it as a subset component, use the backup schema as source and the real database as target, disable constraints and indexes, set Treat Source Row As Update and Update As "Update else Insert", and put the backup prefix in the Reset Recovery Prefix advanced field (p.247). On success TDM deletes the backup tables (p.246).
  • Empty strings in non-null columns: a reset fails if it must copy empty strings into a non-null column, for example from an Oracle warehouse to SQL Server. The project can supply default values, but a reset fails if the non-null target columns are unique (p.243).
  • PWX NRDB Batch target: you must delete the target files yourself first; the reset only copies (p.243).

16.18 Managing data sets

  • Permissions. Whoever runs the plan owns the data set. Owner and domain administrator can grant Read (view, monitor, create coverage tasks, run related data set plans), Write (create, edit metadata and data, classify, delete, create related plans) and Execute (reset). Users also need matching privileges such as View Data Set or Reset Data Set (pp.252-253).
  • Lock and unlock. Owner and administrator can lock a data set so nobody edits or resets it, for example while you check it first. The owner and administrator can still reset it (p.254).
  • View and edit data. From the Tables tab you can browse, or run SQL in the SQL Query field and edit the grid, add or delete rows and add row-level tags. DML only, no DDL. Restrictions: no aggregates, GROUP BY or joins in SELECT; no table aliases or owner names; dates in WHERE need TO_DATE; Oracle BLOB and RAW data cannot be viewed or edited (pp.255-258).
  • Related data sets. A related data set is a subset of a data set, cut by an entity or group built inside the data set and run in a plan. A lineage window shows parent and child data sets (pp.248-252). ShopSphere use: a hotfix needs only the Kochi customers.
  • Self-service portal. Publish a data set as a data pack. Testers without Test Data Manager can then view and restore the data. You cannot delete a published data set until you delete the data pack (pp.239, 247-248).
  • Delete. From the Data Sets view, delete whole data sets or single versions, Actions > Delete. Data and metadata are removed (p.248).

16.20 Common mistakes and gotchas

Things that go wrong
  • Changing a plan and expecting the old workflow to follow. Generate and run again (p.275).
  • Mixing generation with masking or subset in one plan. Not allowed (p.274).
  • Forgetting the eight-workflow limit. Extra workflows queue (p.276).
  • Criteria parameters silently missing. They are not in the run list by default; add them with Select Parameter or the workflow ignores them (p.311).
  • Leaving tables unclassified before a reset. They are treated as transactional (p.241).
  • Truncating a shared schema on reset. You delete other testers' data (p.244).
  • Disabling constraints on shared tables. Other tests may fail during the window (p.243).

16.21 Recap

Recap
  • A plan defines a masking, subset or generation operation; TDM generates a workflow (an ETL job) from it and the PowerCenter Integration Service runs it.
  • Subset plus masking can share a plan (subset first); generation cannot share a plan with either.
  • Connections, target options, update strategy, error and recovery and parameter files control where and how the run happens, with overrides per source or table.
  • Monitor shows each job's status (In Queue, Running, Success, Error, Terminated), its logs by severity, and sessions with row counts. Start at the first Error.
  • Reports: Audit Trail, Data Masking, Plan Audit, Plan Detail and Row Count.
  • The Test Data Warehouse stores versioned data sets. Reset restores a version, with master and transactional classification deciding what is deleted or upserted.
  • Data coverage analysis finds gaps in a data set; ilmcmd, tdwcmd and tdwquery script and inspect the same objects.
