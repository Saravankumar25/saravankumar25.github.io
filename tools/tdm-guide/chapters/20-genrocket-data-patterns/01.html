So far in this part you have met the building blocks of GenRocket (the overview, domains, attributes and generators, receivers and scenarios). You know that every attribute gets a generator and that a generator decides each value. This chapter asks a sharper question: which values should a generator produce so that your tests find bugs?

Test data is not just "some rows". A shopping app that has only ever seen order totals like 49.99 and 120.00 has not really been tested. The bugs live at the edges: a total of exactly 0.00, a total of 999999.99 (the biggest the column can hold), a customer who is exactly 18 years old, an email box left empty, a phone number with one digit too few. Testers call these data patterns: deliberate shapes that the data takes. This chapter covers the shapes in the syllabus for Day 47: sequential, random, boundary and edge cases, and null.

For each pattern the chapter works the same way. First comes a plain-words explanation with a ShopSphere example. Then comes how GenRocket produces it, using only generator names and parameters that the official help centre documents. At the end there is a pattern coverage table and a lab that builds a small boundary-value suite. The next chapter then uses several of these patterns in a full hands-on lab.

20.1 Words to know first

Data pattern
A deliberate shape you give generated data, such as "counts up by one", "random between 1 and 120", "10 percent empty" or "exactly the largest allowed value".
Positive test
A test that feeds the app data it should accept, to check it works. Example: a valid order of 49.99.
Negative test
A test that feeds the app data it should reject or handle gracefully, to check it fails safely. Example: an order total of -5.00.
Sequential data
Values that follow a fixed order, such as 1, 2, 3, 4. The usual choice for ids and numbered records.
Random data
Values picked unpredictably from a set or range. Good for realistic variety.
Seed
A starting number for the random picker. Same seed in, same "random" values out, every run. This is how random data becomes repeatable.
Boundary value
A value at, just below or just above the limit of what is allowed. The limit is the "boundary".
Edge case
A rare or unusual situation outside the typical pattern, such as a name longer than the column allows. GenRocket's own definition is "a rare or unexpected scenario outside the typical usage pattern".
Null
"No value at all" in a database column. Different from an empty string, which is a value that happens to contain zero characters.
Blank / empty
A text value with nothing in it (or only spaces). The column holds something, but it is nothing visible.
Weight
The share of rows that should get a value. A weight of 70 on "Pass" means about 70 of every 100 rows are "Pass".
Linked generators
Several generators attached to one attribute that pass results left to right. The last one gives the final value of the attribute.

20.2 Why test data needs patterns

General concept Picture a vending machine. If you test it only by inserting the exact price, it will pass every time. The bugs appear when you insert one coin too few, one coin too many, a foreign coin, or no coin at all. Software behaves the same way. Most defects hide where the rules change: at a limit, at an empty field, or in a rare combination.

That is why real testing needs both kinds of data:

Typical data (positive tests)

  • Looks like real customers and real orders.
  • Proves the main flows work: place an order, view an invoice.
  • Needs variety and volume more than precision.
  • Tools: random generators, name and phone generators, lists.

Tricky data (negative and edge tests)

  • Sits on the rules: the minimum, the maximum, empty, null, too long, wrong type.
  • Proves the app rejects bad input safely.
  • Needs precision: the exact value matters.
  • Tools: lists, ranges, weights, edge-case and null generators.

A real production copy is poor at both. It has plenty of typical rows but may contain no order of exactly 0.00 and no 17-year-old customer, so the edge tests never run. Synthetic data fixes that, because you decide what exists. From docs GenRocket's CI/CD page describes its web platform as able to design "any form of test data (positive, negative, patterns, permutations, boundary values, dynamic, load, etc.)" for a given data model (Automating Data Generation using CI/CD Pipeline). The rest of this chapter shows which generators do each job.

Why this matters for a TDM engineer

When a developer says "the checkout broke on a zero total", the fix is a test row with a zero total, every time the suite runs. With a generator you write that row once as a rule ("one of the values is 0.00") and every future data refresh contains it. With a production copy you would have to hope such a row exists.

20.2.2 How GenRocket thinks about a pattern

From docs In GenRocket, every pattern in the table above is a generator choice plus its parameters on an attribute. There is no separate "pattern" feature to switch on. You pick a generator for the attribute (see the chapter on domains, attributes and generators), set its parameters, and look at the Preview pane, which shows sample values immediately. The help centre says a generator "generates synthetic data or queries for enumerated data for a Domain Attribute", and that generators only create the raw values while receivers format them into files.

Three mechanisms cover almost everything in this chapter:

  1. One generator with parameters. RangeGen with a start value counts up. RandomGen with a range picks randomly. ListGen walks a list.
  2. Several generators linked in one attribute. One produces a value, another decides whether to use it, a last one combines them. The page "Linked Generators Overview" explains the left-to-right rule.
  3. Attribute settings. The Attribute Dashboard has its own fields for nulls and for hiding values from the output, independent of the generator.

The generator list is long. The generators overview page says GenRocket has "over 765+" generators, so no chapter can list them all. We stick to the ones that map to the syllabus patterns.
