So far in this part you have met the building blocks of GenRocket (the overview, domains, attributes and generators, receivers and scenarios). This chapter asks a sharper question: which values should a generator produce so that your tests find bugs?

The bugs live at the edges: an order total of exactly 0.00 or 999999.99, a customer exactly 18 years old, an empty email, a phone number with a digit too few. Testers call these deliberate shapes data patterns. This chapter covers the Day 47 patterns: sequential, random, boundary and edge cases, and null. For each one you get a plain-words explanation with a ShopSphere example, then how GenRocket does it using only documented generators and parameters, then a pattern coverage table and a boundary-value lab. The next chapter uses several of these patterns in a full hands-on lab.

20.1 Words to know first

Positive test
A test that feeds the app data it should accept, to check it works. Example: a valid order of 49.99.
Negative test
A test that feeds the app data it should reject or handle gracefully, to check it fails safely. Example: an order total of -5.00.
Sequential data
Values that follow a fixed order, such as 1, 2, 3, 4. The usual choice for ids and numbered records.
Random data
Values picked unpredictably from a set or range. Good for realistic variety.
Seed
A starting number for the random picker. Same seed in, same "random" values out, every run. This is how random data becomes repeatable.
Boundary value
A value at, just below or just above the limit of what is allowed. The limit is the "boundary".
Edge case
A rare or unusual situation outside the typical pattern, such as a name longer than the column allows. GenRocket's own definition is "a rare or unexpected scenario outside the typical usage pattern".
Null
"No value at all" in a database column. Different from an empty string, which is a value that happens to contain zero characters.

20.2 Why test data needs patterns

General concept A vending machine tested only with the exact price always passes. Bugs appear with one coin too few, one too many, or none. Software is the same: defects hide where rules change, at a limit, an empty field or a rare combination. So testing needs typical data (positive tests: looks real, proves the main flows) and tricky data (negative and edge tests: sits on the rules, proves the app rejects bad input safely). A production copy is poor at the second kind: it may contain no order of exactly 0.00 and no 17-year-old customer. Synthetic data fixes that, because you decide what exists.

From docs GenRocket's CI/CD page says its web platform can design "any form of test data (positive, negative, patterns, permutations, boundary values, dynamic, load, etc.)" for a data model (Automating Data Generation using CI/CD Pipeline).

20.2.2 How GenRocket thinks about a pattern

From docs In GenRocket a pattern is a generator choice plus its parameters on an attribute; there is no separate "pattern" switch. You pick a generator (see the chapter on domains, attributes and generators), set its parameters and read the Preview pane. Generators only create raw values; receivers format them. Three mechanisms cover this chapter: one generator with parameters (RangeGen, RandomGen, ListGen), several generators linked in one attribute, and attribute settings such as % Null that sit outside the generator. The help centre says GenRocket has over 765 generators, so we stay with the ones that map to the syllabus.
