20.7 Null and blank values

20.7.1 In plain words

General concept Imagine a paper form with a "middle name" box. There are three different situations. The person wrote a name (a value). The person wrote nothing and left the box empty (blank). Or the box was crossed out because the question did not apply (not applicable). Databases make the same distinction.

Four things an email column can hold (illustrative)
What is storedNameTypical bug it exposes

(nothing, the cell is "unknown")NULLCode that calls a method on the email crashes with a null error.
(zero characters)Empty stringValidation lets "" through because it is not null.

Applications often treat these four differently, so test data needs all of them. A customer table with no NULL emails will never trigger the "email missing" branch of your code. GenRocket gives you three places to produce null and blank data.

20.7.4 Mixing normal, null and empty by percentage

The JSON walk-through combines both ideas in one attribute. A tester wants an address2 (apartment or suite) that is sometimes filled, sometimes null and sometimes empty. Four linked generators do it:

  1. gen1 ListGen: Apt A, Apt B, Suite A, Suite B.
  2. gen2 NullGen: a NULL value.
  3. gen3 ConstantGen with #{EMPTY}: an empty value.
  4. gen4 MultiWeightGen with valueList #{self.gen1}, #{self.gen2}, #{self.gen3} and percentList 60, 15, 25.

The result: about 60 percent of rows have an apartment or suite, 15 percent NULL, 25 percent empty. Only the rightmost generator, gen4, becomes the attribute's value, as the linked-generators rule says.

This pattern also shows how the page "hides" such values from the output. By selecting an Output Condition on the attribute, a null or blank address2 is left out of the JSON for that record entirely; the page's sample output omits the address2 key on rows where it is null or empty. That matters for APIs that treat "missing key" and "null value" differently, because you can generate both forms.

20.7.5 Place 3: how the receiver writes a null

A null is only a null inside GenRocket. The receiver decides how it is written to the file. The DelimitedFileReceiver documents a required parameter nullValue ("Represents a Null value") and a booleanValue format (DelimitedFileReceiver). The screenshot of its form shows nullValue pre-filled with (null). If a downstream loader expects the literal text NULL or an empty cell, change this parameter before you generate. A mismatch here is a classic source of "the data looks right in GenRocket but my load fails".

@@SHOT common_receivers_how_do_i_use_the_delimited_file_receiver 1 | DelimitedFileReceiver parameters including nullValue (null) and includeHeader True | The DelimitedFileReceiver form. Common null-testing mistakes
  • Only testing NULL. NULL, empty string and spaces are three different inputs. Cover all three.
  • Nulls in a primary key. Never use % Null on an id or a foreign key unless you are deliberately testing that the database rejects it.
  • Forgetting the receiver. A null written as (null) may load as the five-character text "(null)". Check nullValue.
  • Referencing a generator to the right. In a linked set, the percentage generator must be rightmost, or it will see null values from generators that have not run yet.

20.8 Boundary values and edge cases

20.8.1 Boundary value analysis, explained from zero

General concept Suppose a form accepts an age from 18 to 65. You cannot test every possible number. Boundary value analysis (BVA) is a way to pick a handful of values that find most bugs. The idea comes from experience: programmers make "off by one" mistakes. They write age > 18 when they meant age >= 18. Such a bug is invisible when you test age 40 and obvious when you test age 18.

Here is the method in four steps.

  1. Find the rule.

    Write down the allowed range. ShopSphere example: an order total is valid from 0.00 up to 999999.99.

  2. Split the world into groups ("partitions").

    Everything below the range is invalid, everything inside is valid, everything above is invalid. Testing one value from inside each group covers "the typical case" of each.

  3. Pick the values at each edge.

    For each boundary test the value just below it, on it and just above it.

  4. Write the expected result for each value.

    Decide accept or reject for every value before generating anything, so the data file doubles as a test oracle.

For an inclusive range from a minimum to a maximum, the classic set is seven values: just below the minimum, the minimum, just above the minimum, one typical value, just below the maximum, the maximum, and just above the maximum.

As noted at the start, the pages I had do not name a boundary generator. The documented building blocks combine into a few reliable recipes.

Why exact lists beat random for boundaries

A random generator might hit 999999.99 once in a million rows, or never. A boundary test must hit it every time. That is why exact lists and fixed ranges, not random generators, are the tools for boundary values, and why random generators are the tools for the "typical" partition.

20.8.3 Lab: a boundary-value suite for ShopSphere orders

Lab: generate the seven order-total boundary rows

Goal: a small domain that produces exactly one row per boundary case, with the expected result next to each value, and a delimited file you can hand to a tester. This lab reuses the project setup steps from the 50-record lab, so if the click paths are new to you, read that lab's steps first. The generator choices here come from the pages cited above; the lockstep behaviour of three ListGens in one domain is my design inference and you must confirm it in the Preview pane.

  1. Create a domain named OrderBoundary.

    In the Domains pane choose New Domain, then New Domain, enter the name and Save. Domain names take letters and numbers only. The new domain starts with only an id attribute.

    A Domain Dashboard with id and the variable global.OrderBoundary.loopCount equal to 1.

  2. Add attribute caseName and give it a ListGen.

    New Attribute, name it, Save. Replace the default generator with ListGen (Quick Generator Replacement menu, type ListGen, Replace). In list enter one item per line: below min, min, min plus 1, typical, max minus 1, max, above max. Set setLoop to True.

    The Preview shows seven labels. In a scenario the loop count will be locked to "N", as the ListGen page describes.

  3. Add attribute totalAmount with a ListGen.

    Enter -0.01, 0.00, 0.01, 500.00, 999999.98, 999999.99, 1000000.00, one per line, in the same order. Leave random False and setLoop False.

    The Preview lists the seven amounts in order. If a trailing zero such as 0.00 is shown as 0, see the formatting note below.

  4. Add attribute expected with a ListGen.

    Enter REJECT, ACCEPT, ACCEPT, ACCEPT, ACCEPT, ACCEPT, REJECT in the same order.

    Rows line up: row 1 is "below min", -0.01, REJECT; row 7 is "above max", 1000000.00, REJECT.

  5. Add a DelimitedFileReceiver, create a scenario and run it.

    Follow steps 11 to 13 of the 50-record lab: add the receiver with a comma delimiter and a file name such as OrderBoundary.csv, create a scenario with this domain as the primary domain, download it and run genrocket -r OrderBoundary.grs (use your scenario's name).

    A file with a header and exactly seven rows. A row count other than seven means setLoop was not applied to the first generator of caseName.
