20.5 Lists, weights and percentages

20.5.1 In plain words

General concept Real data is lumpy. In a real shop, most orders are Delivered, a few are Pending and a handful are Cancelled. If your generator gives each status the same share, your test data is unrealistic, and reports built on it (percentage cancelled, say) look wrong. A weighted pattern says "give value A to 70 percent of the rows and value B to 30 percent".

There are two related ideas. A list is the set of allowed values (Pending, Shipped, Delivered). A weight says how often each list value should appear. Lists come first, weights shape them.

A ShopSphere order-status mix we might want (illustrative)
StatusShare of ordersWhy that share
Delivered70 percentMost historical orders are finished.
Shipped15 percentIn transit.
Pending10 percentJust placed.
Cancelled5 percentRare, but the app must handle it.

20.5.2 ListGen: the allowed values

From docs ListGen "generates items in a provided list in sequential or random order" and is "a great choice when generating data from a fixed set of values (e.g., lookup table or categorical data)". Its documented parameters are list (one item per line), random (False by default), unique, waitAmount, iterate, seed, resetIndex and setLoop. It supports up to 15 items.

One parameter deserves attention because the boundary lab at the end of this chapter uses it. setLoop "gives users the ability to OVERRIDE the loop count at the Scenario Level and ONLY produce the number of rows defined in this list". If the first generator of an attribute is a ListGen with setLoop True, the scenario's loop count is locked to the list length and shows as "N" with no edit pencil. The help page "Why can't I update the Loop Count Value from the Scenario?" explains that this lock is the reason (link).

ListGen alone gives equal shares. To make some values more common, use WeightGen or MultiWeightGen.

20.5.3 WeightGen: a two-way split

From docs WeightGen "defines a percentage between 1 and 100 to determine how often values generated from variable1 will be selected over values generated from variable2". The parameters are percentage*, variable1*, variable2* and an optional seed. Variables can be constants or references to other generators or attributes (WeightGen).

The page's first example: percentage 70, variable1 Pass, variable2 Fail. In ten sample rows the output was 7 Pass and 3 Fail. For ShopSphere, percentage 95 with variable1 Valid and variable2 Invalid would give a file where roughly one row in twenty is invalid.

WeightGen splits between exactly two things. For more, use MultiWeightGen.

20.5.4 MultiWeightGen: any number of weighted values

From docs MultiWeightGen "allows multiple values to be weighted to determine how often each value is generated". The page's own example is rental vehicle types: economy 50 percent, midsize 35 percent, luxury 15 percent (MultiWeightGen).

MultiWeightGen parameters as documented
ParameterMeaning
valueListThe values. Press Enter after each. Each value is paired with the percentage in the same position.
percentListThe percentages (whole numbers) or references to values holding them. The page says to make them add up to 100 and notes the generator tolerates more than 100 in rare cases.
seedSame random data every run.
exactPercentage*When True, the distribution matches the percentages exactly. When False it is decided as rows are generated and may be off, with larger row counts converging on the percentages.
totalLoopCountTotal rows across a scenario, used when the loop count is dynamic.

With 100 records and exactPercentage True, the page says you get exactly 50 economy, 35 midsize and 15 luxury. That exactness is what you want when a test asserts "30 percent of loans are Mortgage".

Related generators named in the conditional-logic overview: MultiWeightCSVGen (values and weights loaded from a delimited file, so non-programmers can edit the mix), MultiWeightChildGen (spreads values across the children of each parent, for example 10 percent of a parent's children get a blue bag) and MultiWeightRegexGen (weights regular-expression patterns). The overview also notes that MultiWeightGen "works in the totality of all rows and does not consider parent/child relations".

Worked example: the ShopSphere status mix

Goal: the status table above for 1,000 orders.

  1. Assign MultiWeightGen to the status attribute.

    Use the Quick Generator Replacement menu on the Attribute Dashboard, type MultiWeightGen and click Replace (the same steps the help centre uses for its children-by-weight example).

  2. Fill the lists.

    valueList: Delivered, Shipped, Pending, Cancelled. percentList: 70, 15, 10, 5.

  3. Set exactPercentage True and a seed.

    Exact shares mean your report checks have a fixed expected answer. The seed means the order of values is repeatable.

    With a loop count of 1,000, expect 700 Delivered, 150 Shipped, 100 Pending and 50 Cancelled. Count them in the output file to confirm.

How to give each parent a different number of children by weight is covered by the help page "How to generate Children based on Weights (Percentages)", and you will build it in the parent and child lab.

20.6 Linked and conditional generators

20.6.1 In plain words

General concept Sometimes a value depends on another value. A voting-age check depends on age. A "refund reason" only makes sense if the order is cancelled. In a spreadsheet you would write an IF formula. GenRocket has the same idea in two parts: linked generators (several generators chained in one attribute) and conditional logic generators (generators that choose one result by testing a condition).

20.6.2 Linked generators: the left-to-right rule

From docs The "Linked Generators Overview" page gives the rules that every conditional recipe relies on (Linked Generators Overview):

  • Linked generators run left to right (top to bottom in the table): the first generates first, the second next, and so on.
  • A linked generator may only reference sibling generators to its left. Referencing one to the right "will yield null values" because it has not generated yet.
  • The rightmost generator holds the value returned for the attribute. The earlier ones are workings that do not appear in the output.
  • Each one gets a default name (gen1, gen2 and so on) and you can add an alias. In a parameter, a reference to a sibling looks like #{self.gen1}, as in the ConcatGen design-pattern page.

The same ordering applies between attributes: "Attributes can only reference other Attributes that are above them in the Attribute pane of a Domain." An attribute that references one below it "will return an empty value". The page "When can an Attribute not reference another Attribute?" shows the fix: click Rearrange Attributes and drag the attribute (link).

20.6.4 EvalCaseGen: if age is 18 or more

From docs EvalCaseGen takes an equation that uses var1 to var5, plus caseTrue and caseFalse. Allowed operators include &&, ||, !, >=, <=, ==, !=, <, >, % and /. Two cautions from the page: put string comparisons in double quotes (for example var1 == "Male"), and for numbers of type long append a lower-case L (var1l) (EvalCaseGen).

Its voting example is a perfect small boundary test. A domain Voting has an age attribute (RandomGen from 10 to 65) and an allowedToVote attribute using EvalCaseGen with equation var1 >= 18, var1 referencing the age attribute, caseTrue Yes and caseFalse No. Notice that the attribute order matters: age sits above allowedToVote.

20.6.5 EdgeCaseGen: sneak in the tricky value

From docs EdgeCaseGen mixes a normal value with an edge-case value. It "generates edge case data useful for negative testing and testing edge cases". The page lists example edge cases: rounding issues in currency conversion, mismatched time zones, special characters in passwords, names longer than the character limit, names with invalid characters, uncommon file formats and validating a user's age (EdgeCaseGen).

EdgeCaseGen parameters as documented
ParameterMeaning
source*The value (or reference) returned normally, when the edge-case condition is false.
edgeCase*The value (or reference) returned when the edge case applies.
conditionA reference to a generator that returns true or false. True returns the edge case, false returns the source.
cycleHow many cycles the source value is returned before the edge-case value is returned.
percentageThe percentage of time the edge-case value is returned.
seedSeed for the internal random picker used with percentage.

So there are three ways to decide when the edge case appears: a true/false condition, a fixed cycle, or a percentage.

Example 1 from the page: a negative age every few rows. Three linked generators: RandomGen age (1 to 120), RangeGen negative (-120 up to -1) and EdgeCaseGen case with source the age, edgeCase the negative value and cycle 5.

The documentation disagrees with itself here

The parameter list says the edgeCase value is returned when condition is True. The page's own screenshot shows the opposite for this example, and its prose goal matches the screenshot. I cannot tell from the pages which is right for your version. Do not guess: set up the generators, look at the Preview pane, and flip the condition if the result is reversed.

G-Cases are the other route to negative data

The EdgeCaseGen page points out that G-Cases (Test Data Cases) can also set up negative test cases. A G-Case "modifies the components within a Scenario", so one scenario can produce typical data in one case and edge-heavy data in another, with different loop counts, rules and generator settings per case. The overview names test categories such as Beta, Unit, Load and Negative (G-Cases Overview). Their "Negative Test Data" and "Permutations and Combinations" example videos are linked from the use case page, but I could not transcribe videos so I do not describe them.

Permutations: every combination, not just the edges

From docs PermutationGen "can generate all possible combinations of data for a given set of values", so you do not "worry about missing a permutation". It takes a list parameter and works with other permutation-type generators in the same domain. If a form has three drop-downs with 3, 4 and 2 choices, all combinations means 24 rows. Use boundary values for single fields and permutations for combinations of fields.
