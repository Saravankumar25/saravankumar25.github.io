17.8 Projects, project versions and categories

17.8.1 What a project is, and how many you need

From docs A Test Data Project contains the data model for one application or database you want data for. It contains aspects of your model (domains, attributes, generators, receivers, scenarios) but no customer data. This is also the unit of licensing: the Test Data Projects page says GenRocket is licensed based on the number of projects a customer needs.

The page gives a way to count. Start with what you are testing, find the applications and their databases, and count them. It then lists factors that may split one thing into several projects: database size, complexity of related tables, whether functions are related, and special message formats.

SituationMinimum projects (docs)
One application, one database1
Several unrelated modules, each with its own database1 each
Multi-schema database whose tables are related1 for all schemas (depending on complexity); unrelated schemas need a project each
Next release of the same applicationThe same project, with a new project version
A workflow across applications (for example customer, agent, quote, payment, policy)At least 1 per application, database or complex file type, so that referential integrity holds between applications
Closed or packaged systems such as SAP or Salesforce1 per module or group of related functions
SWIFT or EDI messages1 per message type
Subsetting or masking a SQL database1 per related group of tables

For ShopSphere's "Customer Orders" app with its single SHOPSPHERE_PROD schema, the docs' rule suggests one project, because the four tables are related.

The Project Types page lists three, and warns that GenRocket must enable the feature before you see the choice. If it is not enabled, every project is a Standard project.

17.8.3 Creating a project

  1. Open the Projects pane in the Project Dashboard and click New Project.

    If you cannot see this button, the docs say you lack permission; ask your organisation's administrator to assign the right role.

  2. Enter a name, a type if offered, and a description.

    The docs recommend a description. Choose the industry type if you can: they say it helps GenRocket assign the right generator to attributes.

  3. Optionally pick a team or tick Master Project, then click Save.

    A master project is a way to share master domains with other projects; teams are explained in the user section below.

    What you should see: the project appears in the list and extra panes appear for configuring it. A default project version is created automatically.

The next step after creating a project is to import or create the domains, which is the subject of the domains, attributes and generators chapter.

17.8.4 Project versions

From docs A project is born with a version numbered 1.0. A new version is normally created when the release your domains and scenarios test goes to production, and the next release needs testing. Each version has its own domains, receivers, scenarios and configuration.

There are two ways to make one, both from the Manage menu in the Project Versions pane.

New Version

A blank slate. No domains or scenarios from before. Use it when the data model changes so much that starting fresh is easier.

The dialog asks for a version number and description, an optional default date format (for the whole version; a more specific format at attribute or generator level wins), and an optional Enforce Type/Limit checkbox.

Copy Version

Replicates the whole version, or a subset of domains, so the new version matches the next release of your software.

The docs state a limit: permitted users can copy a version five times in 24 hours, counted from the first copy.

The Project Dashboard page lists some of those icons: generator search, the Domain Referencing Wizard, a project-version status report (which flags attributes with no generator, id attributes without a range generator, and foreign keys without the proxy reference generator), a global seed assigner and a generator tuning wizard. Terms like proxy reference generator are explained in the generators chapter.

17.8.5 Project categorization

A company with hundreds of projects needs a way to find them. From docs Project categorization lets an organisation administrator build a three-level list, then lets users filter projects by it:

  • Business Unit: the top level, such as a department or team (the docs' example is "Bank").
  • Category: a group of similar projects within a unit (Credit Card, Checking, Savings). No limit on how many.
  • Tag: the lowest level, a keyword for a category (New Accounts, Payments Received). A category can have up to five tags.

Only an Org Admin creates the units, categories and tags; an Org Admin or the project's creator assigns them to projects; any user can then filter projects by them. The docs recommend using this only when you have many projects, and say a small organisation can find projects by name. A user can find a matching project, copy it, and adapt the copy: reuse, not rebuilding.

17.9 Users, roles and licensing basics

From docs The licensing facts I found stated are these, and nothing more (prices and contract terms are not in the help centre):

  • Licence is counted in test data projects (see above).
  • Users are named users: a real, registered person whose email address is their unique ID. The number of users per organisation is unlimited.
  • A named user may have a desktop and a laptop, but should run scenarios on only one at a time.
  • When a scenario runs, the runtime checks that the user has a valid, enabled profile. An administrator can disable users.
RoleWhat the docs say it can do
Organization AdminCreates users, resets passwords, sets password expiry, accesses all projects, domains and scenarios, and can add or delete resources and organisation variables
Team ManagerCreates teams, adds projects and members to them and sets each member's permissions per project
General UserThe default role; changes only their own account and works with projects, domains, attributes, receivers and scenarios not placed in a team. Inside a team, permissions depend on what the team manager granted
Enable Web Service APILets the user call GenRocket's web API

A team is how an organisation restricts who sees which projects: if a project is placed in a team, members get exactly the permissions they were given, and a user without permission to manage, for example, receivers sees them read-only. Further administration topics exist (multi-factor login, restricting log-in by IP address, SCIM user provisioning); the help centre's User Management section covers them and I have not summarised them.

17.11 Common mistakes and gotchas

Things that trip up beginners
  • Expecting data to appear in the web platform. The cloud holds designs, not data. Rows are created only when a downloaded scenario runs under the runtime on your machine. The "Preview" you see in the web platform is a sample for checking configuration.
  • Forgetting the profile. Without a valid .grp profile (or offline certificate) in .genrocket, the runtime refuses to run. Download a fresh profile whenever a resource value changes.
  • Environment variables set but not picked up. A terminal opened before you changed variables keeps the old values. Close it and open a new one.
  • Port 443 blocked. The runtime cannot validate the licence. Use the browser or curl test, then ask the network team or use the offline certificate.
  • Treating the number of generators or receivers as fixed. The docs give changing counts ("765+", "120+", "more than 100"). Look the name up in your version rather than relying on a number.
  • Creating a new project for every release. A new version is the documented tool for that, and project count is a licensing unit.
  • Confusing the five components with the four phases. See the warning in the four-steps section.

17.12 Recap

Key points
  • GenRocket makes synthetic data from a model: no production rows are copied, and projects contain no customer data.
  • Five components do the work: domain (table or file), attribute (column), generator (value recipe), receiver (output format), scenario (instruction sheet).
  • "Model, Design, Deploy, Manage" is GenRocket's own methodology and the Test Data Automation four-step process.
  • Design happens in the cloud web platform; generation happens on your machine with the GenRocket Runtime, which needs Java, a profile, and usually port 443.
  • Docker and Jenkins are two ways to run the same runtime in automated environments.
  • A project is one data model and a licensing unit; a version is one release of it; categories help find projects.
  • Roles and teams control who may change what; named users run scenarios on one machine at a time.
