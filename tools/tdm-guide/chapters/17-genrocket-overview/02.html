17.4 Test Data Automation and "Model, Design, Deploy, Manage"

From docs GenRocket calls its platform a Test Data Automation platform. The CI/CD page explains the idea with a short list of things any generator of data must know, and then shows how GenRocket captures each one:

What the generator must be toldWhere GenRocket records it
The object to create (a User, a Customer)Domain
The properties of the object (name, id number, phone)Attributes
What each property should look like (Swedish names, a national id)Generators
The format of the result (CSV, JSON, XML)Receivers

Notice that the runtime has now joined the list as a sixth piece. The five components are the design; the runtime is the engine that executes it. The docs describe the runtime as a secure Java program that executes encrypted scenarios inside the customer's firewalled environment.

17.4.1 The four steps

The course syllabus for Day 46 says "Data generation: model, design, deploy, manage". GenRocket's Methodology page says the product uses exactly this "Model, Design, Deploy, Manage" methodology, and the CI/CD page gives each step a plain meaning.

The same page also lists the self-service vocabulary used in the Design step, in a table from the vendor's screenshot below. These names matter later (data patterns chapter), so recognise them now.

Do not confuse the stages with the five components

Model, Design, Deploy and Manage are phases of work. Domain, attribute, generator, receiver and scenario are things in the product. Several components appear in more than one phase: generators are chosen while designing, but a generator's output is only produced while deploying.

17.5 Architecture: a cloud for design, your machine for generation

From docs The Architecture page says GenRocket is built on a hybrid architecture. The cloud component is where synthetic data is modelled and designed. The on-premise component is where synthetic data is generated locally. The cloud itself is offered as a Virtual Private Cloud (VPC) or a Dedicated Private Cloud (DPC).

Read the diagram from top to bottom. A designer logs in to the web platform and builds the design. The design is then sent to the customer side as an encrypted scenario file. On the customer side, the runtime runs it and writes data into databases and files that never leave your network.

Why it matters

For a bank or hospital, the question "does our data leave the building?" decides whether a tool may be used at all. In this design, the cloud holds only the design (a data model and rules, not data). The only place rows are created is on a machine you control. Compare this with a masking tool (Informatica masking chapter), where real data is read and transformed.

The Architecture page links onward to security, team permissions, the runtime overview and "G-Repository", the component that keeps scenarios and configuration files synchronised across a company's machines. There is also a downloadable PDF, "Components and Ports Configuration Guide", which the docs call a vital resource for core components, diagrams, port configurations and deployment advice. I did not open that PDF; if your organisation deploys GenRocket, that is the document to ask for.

17.6 The GenRocket Runtime

17.6.1 What it is

From docs The runtime is a set of Java jar files, downloaded from GenRocket Cloud and installed wherever data generation is needed: a laptop, a shared machine, a server, a virtual machine or a container. The pages list these jars.

JarJob (docs wording, shortened)
genrocket.jarReads the command line, checks the user's licence, launches the engine
gr-engine.jarThe core engine that runs scenarios (and supports components such as the multi-user server)
gr-generators.jarThe generator classes
gr-receivers.jarThe receiver classes
gr-grepository-servers.jarCreates and runs a G-Repository server
gr-grepository-clients.jarCreates a G-Repository client

The page advises installing the runtime as close as possible to where the data is needed. Three setup styles are listed: a local user machine, a shared central machine where many people log in, and a local or remote server, including one used for automated testing in CI/CD.

A small warning from my own reading: the overview table writes the first one as GENROCKET_HOME, while the Windows setup and troubleshooting pages use GEN_ROCKET_HOME. I cannot tell which is correct for your version. Follow the setup article for your operating system and copy the spelling it uses.

17.6.3 Profiles: how the runtime knows who you are

A scenario file is encrypted and tied to your organisation. To run it, the runtime must find a profile file (extension .grp) in a hidden folder named .genrocket in your home directory. The profile ties the machine to a GenRocket licence.

ProfileUsed for
User ProfileEvery person who runs the runtime. It matches the scenario to your organisation and checks that you have an enabled account
Server ProfileA server with no particular person, typically a CI/CD machine. An organisation administrator must first add the server in the web platform

Both are downloaded from the web platform. Whenever a resource value changes, the docs say you must download your profile again and replace the old one.

17.6.4 Port 443, online mode and the offline certificate

From docs The runtime runs in online mode by default: when you run a scenario, it contacts GenRocket Cloud over port 443 to confirm the licence. The "Verify Port 443" page gives a quick test: open https://app.genrocket.com/license/check in a browser, or run curl on the same address. If the port is open you see a short JSON message saying a valid user or server was not found. That odd-looking "failure" is the proof that the connection works.

If your company blocks that port, the docs offer an offline certificate: download a file from the web platform, put it in the .genrocket folder, and run scenarios without internet. The certificate is specific to one organisation and lasts 24 hours, so you download a fresh one each day.

Offline certificate pitfall from the docs

If the home directory stored in your resource.home.directory resource does not match the machine's real home directory, you get "Unable to validate license". The fix on the page is: correct the resource value, download the certificate again and retry.
