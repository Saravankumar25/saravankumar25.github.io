GenRocket is built around the third way of making test data: generation. It does not copy production data at all. You describe the shape of the data you want, and it manufactures as many rows as you ask for, already consistent with each other.

The product is made of five building blocks. Some pieces run in a cloud web site and some on your own machine, and GenRocket's own method is Model, Design, Deploy, Manage. The building blocks are covered in detail in domains, attributes and generators, then receivers and scenarios.

17.1 Words to know first

Synthetic test data
Data manufactured by an algorithm instead of captured from real events. GenRocket's page defines it in nearly those words. Nobody's real name or card number is in it.
Domain
One "thing" you want data for, such as a customer. For a database it is a table. For output it can also be a file, message, JSON or XML document.
Attribute
One characteristic of a domain, such as firstName or email. For a database it is a column.
Generator
The small engine attached to an attribute that decides what value to produce, for example "a first name from a list" or "count up from 1".
Receiver
The component that takes the raw generated values and puts them into a usable form: a CSV file, a JSON file, SQL insert statements, a database table and many more.
Scenario
A saved instruction sheet: which domains to generate, how many rows of each, in what order. Running it is what actually produces data.
Test Data Automation (TDA)
The phrase GenRocket's pages use for its approach: test data defined once as components and then generated automatically, in real time, whenever a test needs it.
Web platform
GenRocket's web application in the cloud, where you model and design. Also called GenRocket Cloud.
GenRocket Runtime
A set of Java programs installed on your own computer or server. It reads a downloaded scenario and generates the data there, inside your firewall.
Project and project version
A project holds the data model for one application or database. A version is one release's copy of that model, with its own domains, receivers and scenarios.
Referential integrity
The promise that every foreign key points to a row that exists. See the data basics chapter.

17.2 What GenRocket is and why synthetic data

From docs GenRocket's welcome pages are short and to the point. They define synthetic test data as data "manufactured or generated by an algorithm rather than real-world events", and argue that companies can maximise test coverage by using it to test all permutations and combinations. The CI/CD page describes the product as a component-based platform for defining and provisioning test data for high-volume, automated testing.

Think of a bakery supplying cupcakes for a hundred tasting events. One approach is to buy finished cakes from a rival shop and scrape off the logos (masked production data). The GenRocket approach is to own the recipe and the oven: "chocolate, 12 per tray, one tray with a deliberately burnt top", made on demand. The analogy breaks in one place: a recipe makes cakes that taste alike, while a GenRocket recipe can vary values, include edge cases and keep related trays consistent.

Why it matters

A tester for ShopSphere's "Customer Orders" app needs a customer with 0 orders, one with 1, one with 200, one whose email is missing and one whose surname is 60 letters long. Production rarely contains all of these, and copying production brings real names along (see why TDM exists). Because GenRocket's data is manufactured to a rule, you can ask for the odd cases directly and rebuild the same set tomorrow.

From docs The documentation is also frank about the work involved. The FAQ says the harder data-design tasks are assigned to a small group of trained "Test Data Engineers", while testers and developers mainly search for the data they need, deploy it into their test environment and tweak it. The Test Data Workflow page starts from the same person: it says the workflow begins with a Power User, a Test Data Engineer.

From docs One more design choice matters for privacy. The Test Data Projects page says a project contains no customer data. It holds your data model and the five components that describe how to generate data. The architecture diagram (below) labels the cloud part "No Customer Data Stored".

17.2.1 The problem the vendor says it solves

From video GenRocket's 2020 webinar (the CEO and CTO, with a partner company) opens with the market problem: test automation is spreading fast, but test data is not keeping up. Citing an industry quality report that he names as the World Quality Report, the CEO gives two figures: 69% of organisations use spreadsheets to generate test data, and 59% still create it manually. He adds stories from unnamed customers: a large financial firm with a TDM tool finds the data it needs in production only about a third of the time, and a healthcare insurer's fastest delivery of test data is 34 days. The complaints he hears each week are that data is too slow, does not match the test cases, and is too manual.

These are the vendor's claims: the report, the two percentages (which the talk does not reconcile) and the customer stories are unverified. The 2022 overview video promises the matching fix, cutting days to minutes by replacing spreadsheets and manual methods. Its examples (25 hours of data preparation down to five to ten minutes per cycle, 16 days down to two hours, over 1,200 hours saved in nine months) are also vendor claims, with no method shown.

17.2.2 Traditional TDM versus synthetic test data automation

From video Both videos describe the contrast; the 2022 video draws it most clearly. The CEO does not call traditional test data management (TDM) wrong. He says it helps with privacy law and faster provisioning, and that GenRocket adds to it. The differences are in the starting point and in what each can produce.

Traditional TDM: copy, mask, subset, refresh

Start from a production database or application. Copy the data, run a masking algorithm to make a secure copy in a lower (non-production) environment, and refresh it from time to time. Testers then search the copy for data that fits their test case. The data is realistic and keeps referential integrity.

The gaps the vendor says its enterprise customers report: no unique data, no negative data (deliberately invalid values), not every permutation and combination, not enough volume, nothing in a required condition, and no dynamic data spanning many applications.

Synthetic test data automation

Start from the metadata (table and column definitions), not the data. The metadata becomes a test data project that acts as the template. It is versioned (version 1, version 2) and lifecycle-managed so it follows the application. Against the project you build test data cases for unit, integration, load and performance tests, and negative cases. Each gives realistic data with referential integrity plus the variety that copies lack.

The 2020 webinar adds that "query generators" can still blend a few real production values, such as an account number, into generated rows.

"Stateful" data, one of the gaps, is data in a particular condition that a workflow needs; for ShopSphere, an order already shipped whose payment has settled. On masking, the CTO said in the 2020 Q&A that when GenRocket moves production data to staging it replaces sensitive columns with synthetic values instead of obfuscating them. The help centre also lists masking receivers and an in-place masking project type (sections 17.8.2 and 19.3.9), so check the current product. The concepts are in the chapters on subsetting, masking and generation.

From docs One rule to remember from the Generators Overview: generators only generate values; receivers format them. The split is deliberate. You can change CSV to JSON by swapping the receiver, without touching any generator.

The five-component page adds a small note: the components can also be managed through the Runtime Application Interface (API). The CI/CD page, quoted later, uses that to change a scenario while a pipeline runs.

Worked example: one customer row

Take the ShopSphere row 1001 | Asha | Menon | asha.menon@example.com | 9876543210 | 123-45-6789 | 1990-04-12 | 560001 from the earlier chapters. In GenRocket terms: the domain is CUSTOMERS. The attributes are customer_id, first_name, last_name, email and so on. A generator on first_name produces "Asha" (then a different name for the next row), a generator on customer_id counts 1001, 1002, 1003. A receiver writes the lines into a file. A scenario says "make 3 of these". Every value is fake, so the row can go to any test environment.

17.3.1 The five components in plain words

From video The 2020 webinar explains the same five pieces before any demo, and its wording is a good way to remember them. A domain is a noun: a person, place or thing, such as organisation, department, user or address, with no limit on how many or how they are arranged. Its attributes are its characteristics (name, password, phone number, date of birth, card number). Each attribute gets a generator, and a generator has parameters that control exactly what comes out; a name generator, for example, can be told to give first, last, male or female names, and the CTO says its lists allow around 40 million combinations. A generator's output is raw, unformatted data, and the receiver formats it. The scenario is the instruction set that runs and produces the data. His rule of thumb is one scenario per domain, linked into a chain with a loop count each; section 19.4.7 works through his example with the arithmetic.
