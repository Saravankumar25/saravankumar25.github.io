17.6.5 Setting it up: the shape of the steps

You will not install the runtime in this guide's labs (the hands-on chapter assumes a trainer or lab machine has done it), but you should know what the steps look like. The three operating-system articles are long and similar. Here is the Windows article's skeleton, in my words. Details such as folder paths and the exact variable names belong to the vendor page for your system.

  1. Check the prerequisites.

    An active GenRocket user account and access to the cloud address from your network, port 443 open, admin rights on the machine, and Java installed.

    What you should see: java -version prints one of the supported versions.

  2. Download the runtime zip from the web platform.

    Log in, open the Options menu, and choose the download for the current runtime version. The docs also show a curl or wget way to fetch it.

    What you should see: a zip file named with the runtime version number.

  3. Extract it into your home directory and name the folder genrocket.

    The page warns that you must not end up with a nested folder such as genrocket\genrocket-3.5.x, and that the user name in the path must not itself be "genrocket".

    What you should see: a genrocket folder with bin and lib inside.

  4. Set the environment variables.

    Point the home variable at the folder, add its bin directory to PATH, check JAVA_HOME, and for Java 11 or later add the documented JAVA_OPTS value.

    What you should see: after opening a new terminal window, the word genrocket is recognised.

  5. Run genrocket once.

    This downloads the other jars into lib and creates the hidden .genrocket folder.

    What you should see: no error. If you see "genrocket is not a recognized command", the troubleshooting page says to check the folder name, the home variable and PATH.

  6. Download the helper libraries and your user profile.

    The page uses genrocket -lib for libraries. The profile comes from the Download menu in the Resources pane and goes into .genrocket.

    What you should see: a .grp profile file inside .genrocket.

  7. Fill in your organisation resources.

    Three default resources hold folder paths for you (home directory, JDBC config directory and output directory; the screenshots in the next section show them). Set them to real folders, and enter N/A for the JDBC one if you do not connect to a database.

    What you should see: your own paths in the Resources pane of the web platform.

From docs Typing genrocket alone, or genrocket -h, prints the list of runtime command-line options. That is the quickest way to see what your installed version supports.

17.6.6 Updates, Docker and Jenkins at overview level

Updates. The docs distinguish a full runtime update (replace the whole genrocket folder) from a jar-only update (done from the command line, and sometimes without re-downloading the runtime). Release notes say which is needed, and users see a pop-up after login when a new release arrives.

Docker. For teams that run containers, GenRocket provides a Docker image you download from the web platform (or with curl) and load with docker load. The page's basic idea is that a container forgets everything when it stops, so you mount folders from the host for the runtime, the scenarios, the configuration files, the .genrocket profile folder and the output. The page also notes that the runtime must be set up when using a container, and describes a custom-image option.

Jenkins (continuous integration). Jenkins is a popular tool that runs build and test jobs automatically. The Windows and Mac/Linux Jenkins pages walk through running a scenario as a Jenkins build step. The outline is the same as a normal setup, applied to the Jenkins server:

  1. Install the runtime on the Jenkins server and set the variables in Jenkins's own configuration screen.

    Jenkins builds do not see your personal environment, so the home variable and PATH must be set where Jenkins reads them.

  2. Register the Jenkins server in the web platform and download its Server Profile into the server's .genrocket folder.

    No person is logged in on a build server, so it uses a server profile, not a user profile.

  3. Create a Freestyle job and add a build step that runs the scenario.

    First the page has you run the bare genrocket command to prove Jenkins can find it, then replace it with genrocket -d -r SCENARIO_NAME.grs.

    What you should see: a SUCCESS message in the console output, and your generated files in the output folder.

The CI/CD page adds two ways to trigger generation from a pipeline: a shell or batch command running the runtime, or a REST request to a GenRocket server component. It also describes Java and REST APIs that let a pipeline create or modify a scenario in real time, for example to change a loop count (how many rows) per test.

Not covered here

Linux and Mac setup, the multi-user server, G-Repository administration and API method details are separate topics in the help centre. I read only the overview-level material for them, so I do not describe them further.

17.7 The web platform and the Project Dashboard

From docs You reach the web platform with a link, a user name and a temporary password from a welcome email. The first-login page lists password rules (8 characters, at least one number, one capital letter and one special character from a stated set, and not one of your previous six passwords). After accepting the licence agreement you may be asked to change the temporary password. Organisations that use single sign-on or multi-factor authentication may log in differently; ask your administrator.

The docs describe those three panes this way: Projects lists and manages the organisation's test data projects; Queue Status shows tasks waiting to run, such as a project deletion or a data import (a Refresh button updates it); Resources holds organisation resources, which are named variables whose value differs per user (typically a folder path), so one scenario works on everyone's computer.

Select a project and more panes appear. This one screen is where you will spend most of your time, so the Project Dashboard page is worth studying. Here is the complete screen with a small demo project loaded.

The page also lists common icons: an open padlock locks an item (locked items cannot be deleted, and a lock stops changes made higher up from flowing down); a pencil edits; a trash can removes; an "i" shows more information. You will meet locks again in the receivers and scenarios chapter.

The main menu bar offers Options (downloads such as the runtime), Management, Presets and Help; the Organization menu (visible to administrators) includes "My Organization" for managing users.

Reading order for the Project Dashboard

Work left to right, top to bottom: pick a project, pick a version, look at its domains, look at its scenarios. That is also the order in which you build things. If you can say which pane you are in, you will rarely feel lost in the product.
