The application services

The guide says TDM uses Informatica services that you create in the Administrator tool (User Guide 10.5.10, p.27). Here is the list with the plain-English job of each.

Service Its job (from the guide) When you notice it
Test Data Manager Service Creates and manages the TDM repository; runs Test Data Manager and manages connections between service components and users (pp.26, 28). Every login and every click.
Data Integration Service Performs data discovery; stores profile metadata through the Model Repository Service; loads results to the profiling warehouse you chose when creating it; also runs data coverage tasks for the test data warehouse (p.27). When a profile runs.
Model Repository Service Manages the Model repository for data discovery (p.27). Behind profiles; also when you import metadata or data domains from the Model repository.
monitoring Model Repository Service A Model Repository service that monitors statistics for Data Integration Service jobs (p.27). Rarely, as an administrator.
PowerCenter Repository Service Manages the PowerCenter repository and accepts requests from the PowerCenter Integration Service when a workflow runs (p.27). Generating a workflow; importing metadata from PowerCenter.
PowerCenter Integration Service Runs the data subset, generation and masking workflows. You choose which one when you create the Test Data Manager Service, and again when you generate a workflow from a plan (pp.27, 29). Every plan run.
Test Data Warehouse Service Manages the test data warehouse repository and the warehouse; copies the metadata created with a data set and creates the data set tables (p.27). Creating or resetting data sets.
Analyst Service Manages the Analyst tool TDM uses to link TDM objects to Business Glossary objects; needs a licence that supports Business Glossary (pp.27, 29). Linking glossary terms to policies and domains.
Content Management Service Manages reference data (p.26). The guide does not tie it to a particular TDM screen in this chapter.
Service Manager Manages all domain operations and the domain configuration repository (p.26). Login and domain-level problems.

The TDM databases (repositories)

These are the "recipe books and pantries". The guide lists seven relational databases that TDM connects to for metadata, profiling, TDM configuration, domain configuration and the test data warehouse (User Guide 10.5.10, p.28). Notice that only one of them holds a copy of test data; the rest hold Informatica's own working information.

Database What it stores ShopSphere reading
TDM repository The components you define in Test Data Manager (policies, projects, entities, rules) plus source or target metadata you imported (pp.26, 28). The masking policy, the "Customer Orders" project, the imported structure of CUSTOMERS and ORDERS.
Model repository Table metadata for data discovery profiles; connection information for connections made in TDM; optionally mappings saved for Hadoop operations (p.28). The profile's view of the tables.
PowerCenter repository Metadata for PowerCenter sources and targets and for the workflows generated from plans; also permissions and privileges for its users (pp.26, 28). The generated masking workflow.
Profiling warehouse Profile results for data discovery (p.28). "ssn looks like an SSN domain" lives here until you approve it.
Domain configuration repository Connections and metadata for the Informatica domain, including users (pp.26, 28). Who can log in.
Test data warehouse repository Project and source table metadata for stored data sets (p.28). The description of the stored "masked set v1".
Test data warehouse The source data of stored data sets (p.28). The masked customer rows themselves.
Do not confuse these with SHOPSPHERE_PROD

Your business database (the source SHOPSPHERE_PROD and any test target) is not on the list above. TDM needs a connection to it, but it is not one of TDM's own repositories. Beginners often mix this up and look for "their data" inside the TDM repository. The guide says that importing copies source metadata into the TDM repository (p.31), and that constraints you add in a project are stored in the TDM repository while the TDM server does not update the data sources (p.32).

TDM connections

TDM needs connections to databases, repositories and services, and what it needs depends on what you run (User Guide 10.5.10, p.28):

  • Discovery needs a database source connection and a Data Integration Service.
  • Subset and masking workflows need connections to services, the TDM repository, external database sources, and Informatica sources and targets.
  • Workflows that store data in the test data warehouse need external database sources, the test data warehouse repository and the test data warehouse itself.
  • To copy flat file results to a test tool, you first integrate the test tool server with TDM.

The guide splits them into service, repository and database connections. The table below keeps its meaning and shortens the words.

Connection kind Examples and purpose (pp.29-30)
Service connections Data Integration Service (discovery); Model Repository Service; PowerCenter Integration Service (running generated workflows; you pick its name when you generate the workflow); PowerCenter Repository Service (extracts source metadata from the PowerCenter repository on import); Analyst Service; Test Data Warehouse Service; Test Data Manager Service.
Repository connections TDM repository (a masking, generation or subset workflow needs it); Model repository; profiling warehouse (the Data Integration Service loads profile results there); PowerCenter repository; test data warehouse repository and test data warehouse.
Database connections A database source for discovery, a database target for generation, relational sources and targets for subset and masking, and a source plus the test data warehouse for storing data sets. You configure them in the Administrator view of Test Data Manager and do not need a separate driver. You pick them when creating a plan; TDM tests them when it generates the workflow, and the Integration Service uses them when it runs it.

A readiness checklist before your first job

Putting the connection rules together gives a practical checklist. Most items belong to an administrator, but as a TDM engineer you should know to ask for them. Each item is drawn from the guide pages cited; the order is mine.

  1. A user in the Informatica domain with the right roles and privileges.

    Users and groups are created in the Informatica Administrator, and roles and privileges decide which views you can open (pp.23, 27).

  2. A connection to the source database.

    Needed for discovery, and for subset and masking sources. Created in the Administrator view of Test Data Manager, with no extra driver to install (pp.28-30).

  3. Connections to the Data Integration Service and Model Repository Service.

    Needed before any profile can run (p.92).

  4. A PowerCenter Integration Service chosen for workflows.

    Selected when the Test Data Manager Service is created, and again each time you generate a workflow from a plan (pp.27, 29).

  5. A target connection to a test schema.

    For masking, subset and generation plans. Never the production database (p.31).

  6. The test data warehouse and its repository, if you will store data sets.

    Needed for plans that target the warehouse (p.28).

  7. Folder and connection permissions in the PowerCenter repository.

    Configured with the PowerCenter Client (p.27).

What you should be able to say afterwards: for each job I plan to run, which service runs it and which connections it needs.

General concept The practical lesson (my reasoning from the three journeys, not a quote): a failed profile points at the Data Integration Service, its connection, or the profiling warehouse. A failed workflow points at the PowerCenter Integration Service or the connections you picked in the plan. A missing table in a project usually means the metadata import did not finish or was rejected.
