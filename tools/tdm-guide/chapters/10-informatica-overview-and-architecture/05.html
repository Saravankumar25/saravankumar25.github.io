10.7 Advanced parameterization at a glance

Here is a problem you will meet within a week of working on a real project. ShopSphere's QA team needs test data for sprint 14 regression (orders from this month, in schema QA1), then for performance tests (orders from last year, in schema PERF, on a different server). Making a new plan for each request is slow. Editing one plan every time is error-prone.

The guide's answer is parameters: placeholders in the plan that point to a value, and the value is read when the workflow runs (User Guide 10.5.10, pp.35, 51). You change the value and run the same plan again to get different test data.

Three kinds of parameter

Type Placeholder for ShopSphere use
Connection Source or target connections "QA database" today, "PERF database" tomorrow.
Owner Source or target schema owner names QA1 versus PERF.
Criteria Values in filter criteria of an entity The order_date cut-off used to choose which orders to copy.

You can create parameters inside a project, or an administrator can create global parameters usable across Test Data Manager. Global parameters are marked with an asterisk (*) in parameter lists. If you import a global parameter into a project, you get a copy: changes you make to the copy do not touch the global parameter (p.35).

One rule to remember now

You must import source metadata from every source connection you might need into the project. A workflow whose parameter value points at metadata the project does not contain cannot run (p.35).

The sequence in the guide

The guide lists 16 tasks. Grouped into five phases they read like this (pp.35-36):

  1. Prepare the project.

    Create a project and import the required source metadata. Create connection, owner and criteria parameters in it with default values, and choose whether the default may be overridden. Optionally import global parameters.

  2. Use parameters in the entity.

    Create an entity with the required tables and add filter criteria that use parameters. You can add several criteria; they can be project or global parameters.

  3. Use parameters in the plan.

    Create a plan using parameters. On the Plan Settings page, add the source and target connection types as variables and choose the connection parameters. You must enter a parameter file name and the path to that file on the machine that hosts the PowerCenter Integration Service. In Advanced Settings, add schema owners as variables and select the owner parameters. Save the plan.

  4. Optional: use a parameter file.

    From the plan's Properties tab, Actions > Create Parameter File downloads a file listing every parameter in the plan. You may edit values, and set the "ignore" flags of criteria parameters to "Y" to leave them out of a run.

  5. Run.

    From the plan Properties page, Actions > Generate and Execute, then pick how values are supplied. Choose Default (the file entered in Plan Settings), Use Parameter File (a different file), or Add Parameter Values (edit values in Test Data Manager, and use the Select Parameter button to include criteria parameters). Click Generate and Execute and monitor the workflow.

What you should see: the same plan, different data each time you change values. The guide's two examples: change owner and criteria values to get data in the same connection but a different schema, or change connection parameters and include different criteria to get data between different connections (p.36).

ShopSphere example

Plan "Customer Orders masked subset" uses an owner parameter for the target schema and a criteria parameter for the order date. Sprint run: owner value QA1, criteria "this month". Performance run: owner value PERF, criteria "last year". One plan, two results. The names and values are ours; the mechanism is the guide's.

Details such as parameter naming prefixes, rules, and editing steps are in the guided tour of Test Data Manager. Using parameters inside plans is covered again in the Informatica plans, workflows and warehouse chapter.

Lab: trace three ShopSphere problems to the right piece

Goal: practise using the architecture map. This is a paper exercise, no software needed. The failures are invented by us; the pieces and their jobs come from the guide (User Guide 10.5.10, pp.25-30).

  1. Problem A.

    A data domain profile on CUSTOMERS finishes, but no results appear in Test Data Manager. Which service ran it, and where should the results be stored?

  2. Problem B.

    A masking plan generates a workflow successfully, but the run fails to start. Which service runs workflows, and which connections did you choose in the plan?

  3. Problem C.

    A tester cannot see the "Customer Orders" project in the list. Which kind of setting decides this, and where does an administrator manage users and roles?

Show a worked answer

A. The Data Integration Service performs discovery and loads profile results to the profiling warehouse. Check that service and the profiling warehouse connection. The guide also says to close and reopen a profile to see its results (p.103), so try that first.

B. The PowerCenter Integration Service runs the generated workflows (p.27). In the plan you selected source and target connections, and TDM tests them at generation (p.30). Check that service and those connections.

C. Project permissions. If a user has no permission on a project it does not appear in the list (p.68). Roles and privileges are managed in the Informatica Administrator (p.23). The guided tour of Test Data Manager explains the Read, Write and Execute levels.

10.8 Common mistakes and gotchas

Watch out
  • Looking for business data in the TDM repository. The repositories hold definitions, metadata, results and stored data sets. Your source and target databases are separate and need their own connections.
  • Treating "the TDM Server", "Test Data Manager" and "TDM" as three products. They are the web client, the go-between, and the product name respectively. When a document is ambiguous, ask which piece is meant.
  • Planning generation and masking in one plan. The guide says a generation operation needs its own plan (p.33).
  • Forgetting the overwrite. TDM overwrites existing data in the target schema (p.31). Use a dedicated test schema.
  • Skipping discovery on a database with no declared keys. The guide's example had none, so profiles created the logical keys the subset needed (p.34).
  • Importing only one connection's metadata, then parameterizing the connection. The workflow cannot run (p.35).
  • Assuming every feature in the guide exists in your installation. Licences, privileges and version differ. Confirm in your version.

10.9 Recap

Key points
  • Informatica TDM finds sensitive data, makes smaller copies, masks, generates data, and stores versions of test data (User Guide 10.5.10, pp.21-22).
  • Use cases fall into performance, security and compliance, and verified data with DVO.
  • Four tools (Test Data Manager, Developer, Administrator, PowerCenter Client), a TDM Server, about ten application services, and seven databases make up the architecture.
  • Your business databases need connections; they are not TDM's repositories.
  • The process is: policy, project and import, optional discovery, define, plan, generate and run, monitor.
  • Generation needs its own plan; masking and subset can share one.
  • Parameters (connection, owner, criteria) let one plan produce different test data.

10.10 Check yourself

Which database holds the profile results, and which service writes them there?

The profiling warehouse holds them, and the Data Integration Service loads them (User Guide 10.5.10, pp.27-30). Knowing this tells you where to look when a profile ran but nothing shows up.

Why does a policy not include a data source?

Because it describes what to protect and how, not where the data lives. That lets one policy apply to many projects (p.31).

Which two tools can create or run profiles, and which of them is web-based?

Test Data Manager (web-based) and Informatica Developer (a client application). The guide lists Developer as the tool to create and export profiles (pp.25-27) and Test Data Manager as the place to configure profiles for discovery.

A tester asks for a masked subset and 5,000 generated customers in one plan. What do you say?

Two plans. A data generation operation cannot be combined with masking or subset in the same plan (p.33).

You need the same plan to write to schema QA1 on Monday and PERF on Tuesday. Which feature, and which parameter type?

Parameters, with an owner parameter for the schema name (and a connection parameter if the server also changes). Change the value and rerun, without editing the plan (pp.35-36).
