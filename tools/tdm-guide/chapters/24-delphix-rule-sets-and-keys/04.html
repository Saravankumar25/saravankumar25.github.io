24.10 Hands-on lab: a rule set for the SHOPSPHERE tables

Lab: create a rule set, run the checklist, add a logical key

Goal: a rule set SHOPSPHERE_RS over the ShopSphere tables, a passing Identity Column Check, and a logical key on a table that has no primary key. Prerequisite: the environment and tested connector from the connectors and VDB chapter. The steps and screens are From docs. The table CUSTOMER_STAGING is my illustrative addition, because the four core tables all have primary keys and you need a keyless table to practise the logical key. Ask your DBA to create it in the lab database, or read steps 6 and 7 without running them:

CREATE TABLE CUSTOMER_STAGING (
  staging_row_id INTEGER NOT NULL,
  email          VARCHAR(100),
  first_name     VARCHAR(50),
  last_name      VARCHAR(50),
  ssn            VARCHAR(11)
);  -- no PRIMARY KEY declared (illustrative)
  1. Start the wizard. Open SHOPSPHERE_DEV, click the Rule Sets tab, then + Rule Set, choose Database and click Continue.

    The "Add a Rule Set for a Database" wizard opens on the Details step.

  2. Details. Name it SHOPSPHERE_RS and select the connector SHOPSPHERE_VDB_CONN. Check the connector details shown below the dropdown, then Next.

    Confirming the database name and host now saves a confusing failure later.

  3. Add the tables. Click Add Tables and tick CUSTOMERS, ORDERS, ORDER_ITEMS, PRODUCTS (and CUSTOMER_STAGING if it exists). Save the dialog.

    All related tables go in together so parent and child keys can be masked consistently.

    Five (or four) rows in the grid with empty Logical Key, Filter and Custom SQL.

  4. Save the rule set. Next, check the Summary, click Save, and note the Async Task ID. Watch Monitor > Async Tasks.

    The task completes and SHOPSPHERE_RS appears in the Rule Sets grid with a green Refresh/Save tick.

  5. Run the Checklist. In the rule set's Actions menu choose Checklist.

    It tests every table for a primary key, indexed identity column or logical key before any job exists.

    With the staging table present: a dialog titled Identity Column Check listing CUSTOMER_STAGING as missing a key. Without it: a passing result.

  6. Add the logical key. Actions > Edit, Next to Data Tables, tick CUSTOMER_STAGING, click Edit Logical Key, type staging_row_id, Save the dialog.

    staging_row_id is unique and never empty, which is what a logical key requires. It changes nothing in the database.

    The Logical Key column of that row shows staging_row_id.

  7. Save the wizard. Click Next, then Save in the wizard, and wait for the Async Task.

    The dialog Save only staged the change.

  8. Check again. Run Checklist again.

    The check passes (the job version of the dialog reads "Identity Column Check PASSED").

  9. Read the keys in the inventory. Click the rule set name to open the inventory and look under the key columns.

    Key columns carry the words "Primary Key" (and "Index" if indexed); a foreign key column such as ORDERS.customer_id is marked "Foreign Key" if the database declares it; the staging table is labelled "Logical Key".

Show a worked answer: the integrity plan for the next chapters

24.11 Common mistakes and gotchas

Key and rule set pitfalls
  • Believing a passing Checklist means integrity is safe. It only proves each table has a key.
  • Masking the primary key with a non-unique algorithm. Duplicates break the key. Use a unique, deterministic algorithm, and the same one on the foreign key side.
  • Masking a key without Disable Constraints and Drop Indexes. The job fails on the key constraint.
  • Using a random algorithm on a key. RANDOMIZE and the Gender SL type never preserve integrity.
  • Forgetting the wizard's Save. The logical key, filter or table list is lost.
  • Typing a logical key column that does not exist. The job fails, or the table is listed under Exception Detail in Async Tasks.
  • Leaving out a child table. A foreign key table linked to a masked key must be in the rule set.
  • Assuming refresh wipes your masking choices. It keeps existing algorithm assignments and updates the table list and columns.

24.12 Recap

Recap
  • A rule set is the list of tables or files of one connector that jobs run on. There are four types: Database, Semi-Structured Files, Flat Files and Copybook.
  • Creating one takes three steps (Details, Data Tables, Summary); the wizard's Save stores everything and starts an Async Task. Edit, Refresh, Duplicate, Delete and Checklist are in the Actions menu.
  • In-place masking finds each row by a key: a logical key if you set one, otherwise the primary key, otherwise an identity column, otherwise a temporary one the engine creates.
  • A logical key is a unique, non-null column (or comma-separated columns) given to Delphix only; it changes nothing in the database. On Oracle, ROWID is the recommended one.
  • The Checklist's Identity Column Check reports tables that have no usable key; it does not test integrity.
  • If you mask a primary key, mask the foreign key with the same deterministic, unique algorithm, and enable Disable Constraints and Drop Indexes on the job.
  • Algorithm syncability concerns producing the same output on several engines; non-deterministic algorithms cannot be synced.
