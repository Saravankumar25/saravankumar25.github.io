You now have an environment and a connector (the connectors and VDB chapter). The next object in the chain is the rule set: the list of tables, or files, that the engine will profile and mask. Building one is mostly point and click. The part that needs real understanding is keys. Delphix, like most masking engines, wants to know for every table which column or columns identify one row, and it expects masked values in related tables to stay matched. This chapter covers both, and it covers the syllabus's Day 51 topics: primary key basics and discovery, and data integrity in primary and foreign key columns.

You will build a rule set for the ShopSphere tables, run the engine's checklist on it, and add a logical key. If you skipped the basics of keys, the data basics chapter is a good first stop; here they are explained again briefly, with the masking twist.

24.1 Words to know first

Rule set
A group of tables or flat files, within one data source, on which you may run profile, masking or tokenization jobs.
Inventory
The detailed list of every column or field in a rule set with its domain and algorithm. You open it by clicking the rule set's name.
Primary key (PK)
A column (or columns) that uniquely identifies each row of a table and is never empty.
Foreign key (FK)
A column in one table that holds the primary key value of a row in another table, linking them.
Referential integrity
The promise that every foreign key value matches a real row in the table it points to.
Logical key
A unique, non-null column (or comma-separated columns) you tell Delphix to treat as the key. It changes nothing in the database; it is only information for Delphix.
Identity column
A database column that numbers rows automatically. Delphix can use an existing one as the key, or create a temporary one when a table has no key.
ROWID
In Oracle, a built-in pseudocolumn holding each row's address. The Oracle preparation page recommends it as the logical key for speed.
Deterministic (consistent) algorithm
One that always turns the same input into the same output (for a given algorithm key). This is what keeps matching values matching.
Checklist
An action on a rule set (and on a job) that checks every table has a primary key, an indexed identity column or a logical key.

24.2 Primary and foreign keys from zero, with ShopSphere

A database table is like a spreadsheet, but databases promise things a spreadsheet does not. One promise is that each row can be found unambiguously. Two customers may share a name, so the name cannot find a row. A primary key is the column designed to do it. In ShopSphere, CUSTOMERS.customer_id is the primary key: 1001 is Asha Menon, 1002 is Ravi Kumar, 1003 is Meera Nair, and there will never be two 1001s or an empty one.

Tables connect through foreign keys. ORDERS has a column customer_id that stores which customer placed the order. Each value there must exist in CUSTOMERS.customer_id.

24.3 Why a masking engine needs a key on every table

In-place masking works in three moves: read a row, compute the masked values, write them back to that same row. To write to the right row, the engine must be able to name it. The preparation pages for SQL Server, Db2 and Sybase say so plainly: a key is a unique, non-null value that identifies a row, and for in-place masking "this key looks up the row to update the masked record". For speed the key should be indexed (a clustered index is best, the pages say).

Analogy: a librarian who must correct the address on 100,000 library cards. If each card has a printed number, she can pull card 48213 directly. If cards have no numbers she must compare every card to find the right one, and with duplicate names she might correct the wrong person. The key is the card number. The analogy stops at speed: the engine updates in batches, not card by card.

The pages then list what the engine does with a table, in this order of preference. From docs

SituationWhat the engine uses
You defined a logical keyThat key. It "can override the key used". One or several columns, but always unique and never null.
The table has a primary keyThe primary key.
No primary key, but an identity columnThe identity column. If it is not indexed, the engine adds an index (named with i_MASKING_GENERATED_IDENTITY_TMP on SQL Server).
No key at allThe engine adds a temporary identity column called MASKING_GENERATED_IDENTITY_TMP and removes it when the job ends. This needs a database user allowed to alter the table, and slows the job. If identity support is unavailable the job may fail.

A detail the pages disagree on: the SQL Server page lists the order as logical key, primary key, identity column, none. The Db2 and Sybase pages list primary key, identity, logical key, none, but still describe the logical key as the override. The practical rule is the same: define a logical key when you want to control the choice. The documentation recommends on-the-fly masking as the alternative when a table has no key, since that method writes new rows rather than updating old ones.

Why the temporary column is not a free pass

The 2025.5 and 2025.6 release notes list known issues: failed jobs on heap tables (tables without a clustered index) may leave the generated temporary identity column and index behind. So "the engine will add one for me" is a fallback with a cost. Give the table a real key.

24.3.1 Oracle and ROWID

Oracle tables have the built-in ROWID. The Oracle preparation page says that adding ROWID as the logical key on each table through the GUI is generally the fastest approach, because Oracle manages the updates by the row address. A fixed issue in the 2025.2 release notes confirms that ROWID could not be added as a logical key from the Edit Ruleset screen before that, which is one reason to check your version.
