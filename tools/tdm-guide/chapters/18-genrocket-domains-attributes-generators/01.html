18.1 Words to know first

Template domain
A domain as defined in a project version. Think of it as the master copy. When you build a scenario, GenRocket makes a copy of it called a scenario domain.
Scenario domain
The per-scenario copy of a template domain. Changes to the template flow down to it unless it is locked.
Domain variable
A named setting that belongs to a domain, written global.DomainName.variableName, which generator parameters can refer to. Every domain gets three: id, loopCount and seed.
loopCount
How many rows (records) a domain generates.
Seed
A starting number for random generators. The same seed gives the same "random" data on every run.
Parent, child, sibling
GenRocket's way to express relationships between domains. A child has exactly one parent; "describing" tables are marked as siblings.
Primary attribute
The attribute marked as the key (shown with a key icon). Children refer to it.
Generator parameter
A setting on a generator, such as startRange. Required ones carry an asterisk in the web platform.
Linked generators
Several generators placed in one attribute so that later ones can use the values of earlier ones.
Preview
A sample of generated values shown in the web platform so you can check a configuration before downloading anything.
DDL
Data Definition Language: the SQL text that creates tables (CREATE TABLE ...). See the data basics chapter.

18.2 Domains: the tables of your design

18.2.1 What a domain is

From docs A domain "defines real-world objects", a noun such as a person, place or thing. When you model a database, a domain is a table and its attributes are the columns. The docs' own example has four tables, Company, Department, User and Address, each becoming a domain with its columns as attributes. At least one domain must exist in a project to generate any data.

A domain inside a project version is a template: it holds the attributes, generators and relationships. When you create a scenario, GenRocket copies the template into a scenario domain. Changes you make to the template cascade down to every scenario unless the scenario (or the scenario domain) is locked. This is similar to a document template and the letters printed from it, with one difference: you can pin a printed letter so that later edits to the template leave it alone.

The docs also state a rule that surprises beginners: a template domain works independently and cannot really reference another domain's attributes. Relationships at the domain level are "just probable". The real references are made at the scenario level, where related domains are put together. You will see this again with ProxyReferenceGen below.

Each time a domain is created or imported, it gets three default variables, all initially 1 (details below): id, loopCount and seed.

Names have a small rule. The "New Domain" page notes that a domain name should contain only letters and numbers (spaces are now also allowed), so for the ShopSphere table ORDER_ITEMS I would name the domain OrderItems and put the real table name ORDER_ITEMS in the Table Name field you can see on the dashboard. The page does not say what happens with an underscore, so I avoid it.

18.2.4 Lab-style walk: a new domain by hand

  1. Select your project in the Projects pane.

    The Domains pane only appears once a project is selected.

  2. Click New Domain, then choose New Domain.

    This is the single-domain method.

  3. Type a name, for example Customers, and click Save.

    Use letters and numbers.

    What you should see: the Domain Dashboard for the new domain, with just one attribute called id and three domain variables (global.Customers.id, .loopCount and .seed, each 1).

You would then add attributes. That is fine for two or three columns; for a whole database use an import.

18.2.5 Importing from DDL

From docs You can paste one table's DDL, or upload a file with many. The vendor's sample single-table DDL creates a user table with an id primary key and columns such as first_name varchar(25) not null. Choosing the database vendor from a list tells GenRocket how to read the SQL dialect.

Multi-table import:

  1. Open New Domain and choose Import from DDL, then Import Multiple Domains from DDL.

    The other choice in that first dialog is single-table import.

  2. Pick the vendor (for example mysql) and choose the DDL file.

    Optionally tick Enforce Type/Limit, which makes every assigned generator respect each column's declared type and size (explained below).

  1. Click Save and wait.

    The file goes into a queue (you can watch the Queue Status pane). The user who started the import gets an email when it starts and when it ends.

    What you should see: new domains with their attributes, a primary key marked, and generators assigned automatically.

  2. Optionally open the DDL audit from the Project Versions pane.

    The "GenRocket Table Schema (GTS) Audit Details" option shows what was imported and any errors.

What the DDL import does not do

The page is explicit: relationships between domains are not created automatically, receivers are not assigned and scenarios are not created. You must do these yourself (relationships with the Domain Referencing Wizard, below). It also lists SQL keywords the importer does not support, such as DEFAULT 'N'::bpchar, WITHOUT TIME ZONE and ON UPDATE CURRENT_TIMESTAMP(N). Remove them from the DDL before importing.

18.2.6 Importing a live database schema (XTS)

From docs "XTS" stands for Extract Table Schema. This is the documented way to pull a database's structure straight from the database. Two steps:

  1. Extract the schema with the runtime.

    Run the runtime's -xts option with the path to a JDBC properties file and, optionally, the table names (genrocket -xts /path/config.properties company,department,user). With no names, every table is extracted. Options exist to exclude tables (-xt, -xf), and tables in a specific schema are written schema1:tablename. The properties file holds four required entries: driver, user, password and url.

    What you should see: an encrypted schema file, tied to your organisation. The page calls it a schema extract; it does not say more about what is read.

  2. Import the file with the XTS Import Wizard.

    Open Self Serve Options then XTS Wizard (or choose Import from XTS in the New Domain menu), choose the file, optionally enable Enforce Type/Limit, click Save and wait. The project is frozen until the import finishes.

    What you should see: domains, attributes and generators created for every extracted table, and the wizard's step 1 ready to be marked completed.

Why use a wizard hub? Because after importing hundreds of tables, the remaining setup is also repetitive. Each step has its own wizard that works on a filtered set of domains at once, and you tick each step as complete so that the next unlocks.

ShopSphere: which method?

ShopSphere has three tables to generate. If the team gives you CREATE TABLE scripts, a DDL import takes minutes and keeps the primary key and sizes. If the QA lead can reach a dev copy of the database with a read-only account, an XTS extract avoids typing anything. For this chapter's walk-through, either works. The docs describe DDL and XTS imports as importing a schema, not rows.
