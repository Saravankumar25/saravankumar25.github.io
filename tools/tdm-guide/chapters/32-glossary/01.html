Plain-English definitions of the terms used in the guide, each with a pointer to the section that explains it. Terms are alphabetical within each group: general ideas first, then privacy, ETL, and one group per tool. Tool-specific terms carry the tool name in brackets, for example "(Delphix)".

Same word, different tool

A domain is a named kind of data found by patterns in Informatica, a kind of sensitive data with one default algorithm in Delphix, and a table-like thing you generate rows for in GenRocket. A rule changes data in Informatica, but a Delphix rule set only lists tables or files. Check the bracketed tool name before you trust a definition.

32.1 General TDM and data terms

Acceptance criterion
A measurable statement that decides whether a piece of work is done, such as "0 orphan orders". Section 30.1
Assessment
A structured review of an application and its data environment, ending in a written report of findings and recommendations. Section 29.9
Audit trail
A record of who ran what, when and with which settings, kept so compliance questions can be answered later. Section 9.1
Boundary value
A value at, just below or just above a limit the application enforces, such as ages 17, 18 and 19 for an 18-plus rule. Section 7.3
Collision
Two different inputs masked to the same output. Fine for names, harmful in a column that must be unique. Section 6.6
Column / field / attribute
One fact held for every row of a table, such as first name or order date. Section 3.3
Composite key
A primary key made from more than one column. Section 3.4
COTS
Commercial off-the-shelf software: bought ready-made from a vendor rather than built in house. Section 2.1
Coverage matrix
A grid of test conditions against the data that covers each one, so gaps show at a glance. Section 7.1
Data
Raw facts such as "1001" or "Asha", before anyone says what they mean. Section 3.2
Data pattern
One of five shapes for values: boundary conditions, sequential, random, edge cases and null. They serve test purposes rather than form a separate classification. Section 7.4
Data profiling
Scanning a data source with software and reporting facts about it, such as nulls, uniqueness and patterns. Section 5.2
Data subset
A smaller copy of a database that still hangs together: fewer rows, same structure, referential integrity intact. Section 5.6
Data type
The kind of value a column holds (number, text, date), which controls what is allowed. Section 3.3
Database
An organised store of data that a program can search and change reliably. Section 3.3
Database administrator (DBA)
The person who grants the TDM tool access to source and target databases and helps with performance and storage. Section 2.9
Deterministic masking
Masking that turns the same input into the same output every time, so a customer is masked identically in every table and run. Section 6.5
Dictionary / lookup file (masking)
A list of replacement values, such as thousands of first names, that substitution picks from. Section 6.4
Discovery (data discovery)
Finding out what a data source holds: which tables and columns exist, which are sensitive and how tables relate. Section 5.2
Driving table
The table you start from when choosing a subset; related rows are pulled in from it. Section 5.8
Dynamic masking
Masking at the moment of reading, depending on who asks. It protects production views, not test copies, and the guide's sources do not cover it. Section 6.7
Edge case
A rare but possible input outside normal use, such as a surname with an apostrophe or a date on 29 February. Section 7.3
Encryption
Scrambling data with a key so key holders can unscramble it. Reversible, so it is not masking. Section 6.2
Engagement
One piece of TDM work for one client or business unit, from first conversation to hand-over. Section 29.1
Environment
A complete running copy of the application with its own servers and database: dev, QA, UAT, staging or production. Section 2.3
Evidence pack
The queries, screenshots and reports that prove each success criterion is met. Section 29.1
False positive / false negative
Discovery mistakes: flagging a column that is not sensitive, or missing one that is. The second is more dangerous. Section 5.5
Flat file
A plain file holding records as lines of text, with no database engine, keys or data types behind it. Section 3.5
Foreign key (FK)
A column whose values must match the primary key of another table; it is the link between tables. Section 3.4
Format-preserving
A masked value that keeps the original's shape: a 10-digit phone stays 10 digits, a card number keeps its checksum. Section 6.4
Hand-crafted data
Test rows typed or edited by a person: slow, hard to repeat and tiny in volume. Section 7.3
Hash (MD5)
A one-way scramble: the same input always gives the same output, but the output cannot be turned back into the input. MD5 is one hash function, with a 128-bit result. Section 18.6.11
Hybrid test data
Masked or queried production data with generated rows added on top. Section 7.3
Information
Data with meaning: "customer 1001 is Asha, living in postal area 560001". Section 3.2
In-place masking
Masking that changes the values inside the database you point the job at. Never aim it at production. Section 6.7
Irreversible
You cannot recover the original value from the masked one. Section 6.6
KPI
Key performance indicator: a number tracked to show whether TDM is helping. Section 29.15
LOB
Line of business: one business area with its own applications and data. Section 29.1
Logical key (general)
A column the tool is told to treat as a key, with no change to the real database. Section 3.4
Luhn check
The checksum formula that real payment card numbers follow, used by payment forms to catch mistyped numbers. A Luhn-valid number is not necessarily a real card. Section 18.6.11
Masking
Replacing real sensitive values with realistic but fictitious ones so test data cannot identify real people. Section 6.2
Metadata
Data about data: table and column names, types, lengths and key definitions, not the values. Section 3.3
Metadata profiling / data profiling
Metadata profiling reads names and types; data profiling reads the values. They find different things. Section 5.3
Negative test / negative data
A test, or data, the application should reject or handle safely, such as an order total of -5.00. Section 7.3
Non-deterministic (random)
Giving a different output each time for the same input. Section 6.1
Non-production environment
Any copy of the application that is not live: development, QA, UAT or staging. Section 2.1
Null
"No value at all" in a column, different from an empty string, which is a value of zero characters. Section 20.7
Obfuscation
Umbrella word for making data hard to read by any method; masking is one kind. Section 6.2
On-the-fly masking
Reading unmasked data from a source and writing only masked data to a different target. Section 6.7
Orphan
A child row whose foreign key points at no existing parent; it means the data is broken. Section 3.4
Parent table and child table
The table pointed at is the parent; the table holding the foreign key is the child. Section 3.4
Pilot (services-partner sense)
In one services partner's approach, a real medium-sized project chosen to cover the key scenarios and show the client measurable improvement before a roadmap and rollout. It is larger than a lab POC. Section 29.8
POC (proof of concept)
A small, time-boxed trial of an approach on a slice of real systems, run before full rollout. Section 29.8
Positive test / positive data
A test, or data, the application should accept and process normally. Section 7.3
Primary key (PK)
A column, or columns, whose value is unique in every row and never empty. Section 3.4
Production (prod)
The live system real customers use; it holds real data. Section 2.3
Production support period
A set period after go-live in which the client can bring problems and questions back to the project team; the last phase of the partner's approach. Section 29.8
Provisioning
Delivering a prepared data set to a test environment so testers can use it. Section 9.1
RACI
A table marking who is Responsible, Accountable, Consulted or Informed for each task. Section 29.14
Random data
Values picked unpredictably from a set or range, giving realistic variety. Section 20.4
Record
One row of a table, or one line of a flat file: one customer, one order. Section 3.5
Referential integrity
The rule that every foreign key value matches an existing primary key value. Section 3.4
Refresh
Replacing the data in a test environment with a newer copy. Section 2.1
Regression testing
Re-checking that old features still work after a change; it wants the same data every run. Section 2.3
Repeatable
Giving the same results when re-run. Informatica uses the word for deterministic masking switched on by a seed. Section 6.3
Risk register
A living table of things that could go wrong, with likelihood, impact, owner and mitigation. Section 29.10
Sampling
Reading or picking only some rows; efficient, but a rare value may be missed. Section 5.3
Schema
The description of the data (tables, columns, types, keys) as opposed to the data itself. Section 3.3
Seed
A starting number for a random picker. The same seed gives the same "random" values every run. Section 7.7
Sequential data
Values that follow a fixed order such as 1, 2, 3, 4; the usual choice for ids. Section 20.3
Shuffle
Moving a column's existing values between rows. The values stay real, so check it is safe enough. Section 6.4
Sign-off
Formal written approval by named people that agreed criteria have been met. Section 29.12
SQL
Structured Query Language, used to ask a relational database questions and change its data. Section 3.6
Stateful data
Rows in a particular condition that a workflow needs, such as an order already shipped whose payment has settled. Section 7.3.3
Static masking
Creating a masked copy once; anyone using the copy sees masked data. The normal TDM approach. Section 6.7
Subsetting
Taking a small, consistent slice of a big database instead of all of it. Section 5.6
Substitution
Replacing a value with a believable, unrelated one picked from a list. Section 6.4
Success criteria
Measurable pass-or-fail statements agreed before a POC starts. Section 29.8
Synthetic data
Data created by a program from rules, not copied from real people. Section 7.5
TDG (test data generation)
Creating synthetic test data with a tool rather than copying production. Section 29.1
TDM engineer
The person who discovers sensitive data, designs subsets, configures masking and generation and fixes failures. The learner's target role. Section 2.9
TDM pipeline
The chain from production (or a generator) to usable test data: find sensitive data, cut down, mask, load, check. Section 9.5
TDM (Test Data Management)
The planning, tools and habits that give testers safe, realistic, right-sized data when they need it. Section 2.5
Technique (Informatica) / algorithm (Delphix)
The method that changes a value, such as substitution or date shift. Section 6.1
Technology landscape
The list of systems, databases, files and interfaces that hold or move the data in scope. Section 29.5
Test case
One specific check: "do this, with this data, expect that result". Section 2.1
Test condition
A specific situation a test wants to check, such as a customer with no phone number. Each needs data that creates it. Section 7.1
Test data
The data a test case needs: rows that exist before it starts and values typed during it. Section 2.1
Test data as a service
Test data that teams request and receive like a service-desk ticket, owned by a small group with the rules. Section 7.11
Tokenization (general)
Replacing a value with a token while keeping a protected way to reverse it. Section 6.2
UAT (user acceptance testing)
Testing where the business confirms the application does what it asked; it needs believable data. Section 2.3
Unique permutations
Every combination of values worth testing; one of the kinds of data GenRocket's CEO says masked production copies lack. Section 7.3.3
Unique / uniqueness
A column where no value repeats; masking must not create duplicates there. Section 6.6
Validation of masked data
Checking a finished job: re-run discovery, test joins, formats, uniqueness, repeatability and job warnings. Section 6.10
World Quality Report (vendor-cited)
An industry quality report that GenRocket's CEO cites for two figures: 69% of organisations use spreadsheets to generate test data and 59% still create it manually. Section 17.2.1

32.2 Privacy and regulation

Anonymisation
A goal: data that identifies no one, even in combination. Legal tests are strict, so masking alone does not guarantee it. Section 6.2
Business associate
Under HIPAA, a vendor that handles PHI for a covered entity, such as a firm testing a hospital's billing system. Section 4.5
CCPA
California Consumer Privacy Act: gives California residents rights over personal information businesses hold. Section 4.5
Compliance officer
The person responsible for making sure the organisation follows laws and internal data rules. Section 4.9
Consent / lawful purpose
Ideas shared by privacy laws: data needs a lawful reason, and testing is a different purpose from running the shop. Section 4.5
Covered entity
Under HIPAA, a health plan, healthcare provider or healthcare clearinghouse. Section 4.5
Data classification
Labelling data by how much damage a leak could do (for example public, internal, confidential, restricted) so protection fits. Section 4.6
Data minimisation
Collecting and keeping no more data than needed. It is the legal argument for subsetting. Section 4.5
Data steward
The person who knows a data set's meaning and quality and says what a column holds and who may see it. Section 4.9
De-identification
Making data no longer point to a person. HIPAA names two ways: remove 18 listed identifier kinds, or get an expert to certify tiny risk. Section 4.5
Detection signals
The clues tools use to find sensitive columns: column name, data pattern, list of values, plus type and length. Section 4.7
Direct identifier
Data that points to one person on its own, such as an SSN. Section 4.4
DPDP Act
India's 2023 consent-centred law on digital personal data. Rules are phased in, so check current status. Section 4.5
Especially sensitive data
Data many laws treat as extra delicate, such as ethnic origin, religion, health or biometrics. Blanking it can beat faking it. Section 4.6
GDPR
General Data Protection Regulation: EU law, applying since May 2018, covering personal data of people in the EU wherever the company sits. Section 4.5
HIPAA
US law from 1996 whose Privacy and Security Rules protect health information that identifies a person. Section 4.5
Identifier
A piece of data that points to one person, alone (direct) or in combination (indirect). Section 4.1
Indirect identifier (quasi-identifier)
Data that identifies only in combination, such as zip code plus birth date plus gender. Section 4.4
Minimum necessary
HIPAA idea: people and systems get only the least PHI their job needs. Testers rarely need the real thing. Section 4.5
PCI data
Payment card details such as card number and expiry date. Section 4.3
PCI DSS
Data Security Standard from the card brands for anyone handling card data. A contractual standard, not a law. Section 4.3
PHI (Protected Health Information)
Health data that can be tied to a person. The link to an individual, not the diagnosis alone, makes it PHI. Section 4.3
PII (Personally Identifiable Information)
Data that identifies a person alone or combined with other data, such as name, email, phone or government ID. Section 4.3
Pseudonymisation
Replacing identifiers with pseudonyms while a way back exists elsewhere; still personal data under GDPR. Section 6.2
Regular expression (regex)
A compact text recipe for a pattern, for example three digits, a hyphen, two digits, a hyphen, four digits. Section 4.7
Re-identification
Working out who a "nameless" record belongs to by combining it with other information. Section 4.4
Sensitive data
Data that could hurt a person or company if leaked or misused. "Sensitive" is a business and legal judgement. Section 4.2

32.3 ETL

All-or-nothing load
Loading inside a transaction so a failure undoes everything. Section 8.13
Batch processing
Collecting data for a period and processing it as one group; easy to re-run. Nearly all test data provisioning is batch. Section 8.9
Bulk load
Loading rows in the database's native bulk-load format instead of row by row, used for very large volumes. GenRocket's bulk load receivers write that format. Section 8.8.1
Change data capture (CDC)
Any technique that detects which source rows were inserted, updated or deleted, so only those are processed. Section 8.5
Cleaning
Making values consistent so equal things look equal, such as "MENON" and "Menon ". Section 8.7
Data quality dimensions
Completeness, validity, uniqueness, consistency and timeliness: five questions to check a load. Section 8.14
Data warehouse
A separate database built for reporting across lots of history, with a few big reads. Section 8.3
Deduplication
Keeping one row for each real-world thing. Section 8.7
ELT
Extract, Load, Transform: load raw data first, then transform in the target. Raw sensitive data lands unmasked. Section 8.9
ETL
Extract, Transform, Load: copy data out of sources, reshape and clean it, write it to a target. Section 8.2
Extract
Reading data out of a source system without changing it. Section 8.5
Full extract / incremental extract
Reading everything every time, versus only what is new or changed since last time. Section 8.5
Integration (ETL) engine
The program that actually reads, transforms and writes rows. Section 8.10
Load
Writing transformed rows into the target correctly, repeatably and fast enough. Section 8.8
Lookup (ETL)
Enriching a row by finding a related value in a reference table. Section 8.7
Mapping (ETL)
The definition of how source columns become target columns; also, narrowly, translating codes like S to Shipped. Section 8.7
Mapplet (ETL)
Informatica's reusable group of transformations, built once and used in many mappings. Section 8.12
Metadata repository (ETL)
A database storing mapping and connection definitions and run history. Section 8.10
Operational database (OLTP)
The database an application uses to run the business, built for many small fast reads and writes. Section 8.3
Reconciliation
Comparing counts and totals between two stages to show nothing was lost or invented. Section 8.14
Reject (error) row
A row the job could not process, written aside with a reason instead of stopping the run. Section 8.13
Scheduler
Starts jobs at the right time or after another job finishes. Section 8.10
Session (ETL)
A runnable instance of one mapping with its run settings. Section 8.11
Slowly changing dimension (SCD)
A way to keep history in a warehouse table when descriptive data, like an address, changes. Section 8.8
Staging area
A temporary landing zone where extracted data sits unchanged before transformation. Section 8.6
Streaming
Processing each event within seconds of arrival. Section 8.9
Transform
Turning staged raw data into the clean, correctly typed shape the target needs. Section 8.7
Transformation
One operation on rows, such as filter, lookup or aggregate. Section 8.11
Truncate and load
A full refresh: empty the target table, then insert everything. Section 8.8
Type conversion
Turning text into real dates and numbers so sorting and arithmetic work. Section 8.7
Upsert
"Update if the row exists, insert if it does not." Section 8.8
Watermark
A saved marker, such as the last order id loaded, telling the next run where to start. Section 8.5
Workflow / job (ETL)
A set of sessions and steps with an order and conditions, started by a schedule or trigger. Section 8.11
