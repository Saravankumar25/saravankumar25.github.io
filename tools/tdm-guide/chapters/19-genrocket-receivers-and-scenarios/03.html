19.4 Scenarios

19.4.1 What a scenario is

From docs A scenario contains instructions that tell the GenRocket engine what synthetic data to generate and how much. You select the domains, say how many rows each produces, decide their order, download the scenario to a computer, and run it with the runtime. Domains, attributes, generators and receivers are its building blocks, so all four must exist first.

A scenario is for one primary domain. If the primary domain has parents, the scenario pulls them in as helper domains so that foreign keys are valid: a scenario for Address with parents User and Department also creates departments and users. To output data for several related domains, create a scenario per domain and link them in a chain (below). The docs recommend a scenario for every domain, except pure helper domains.

19.4.2 Creating a scenario

There are three ways: New Scenario (with or without a primary domain), Quick Scenario (named after the domain and built from its relationships) and Batch New Scenarios (a quick scenario for each of several domains).

  1. Open the domain's dashboard and click Quick Scenario.

    Quick is the fastest way when the domain's parent relationships are already right, because it builds the parent domains in for you.

  1. Accept the name (it matches the domain), add an optional description and click Save.

    What you should see: the Scenario Dashboard for the new scenario.

For New Scenario, you enter a name and then choose to create it with or without a primary domain; with one, a wizard asks which domain and whether to add referential integrity automatically. Choose "without" when you want a different parent for this scenario only (see "Scenario domains and relationships" below).

19.4.3 The Scenario Dashboard

Open a scenario from the Scenarios pane of the Project Dashboard (or from the domain's Domain Scenarios pane).

The loop count of a child domain is counted per parent row. So to get 100 orders for 50 customers, you set the Orders loop count to 2. Section 19.4.7 works through a three-level example with larger numbers.

A reminder about where to change the number of rows

The domain page recommends test data cases for varying row counts. Here the loop count is edited in the Scenario Domains table or on the domain. One quirk from the docs: if the first generator of an attribute is ListGen with setLoop true, the list length decides the count and the pencil icon is absent.

19.4.4 Scenario domains, relationships and locks

A scenario holds copies of template domains (scenario domains). Template changes flow into scenarios unless the scenario, a scenario domain or an attribute is locked. A lock stops changes made higher up from cascading down; while a scenario is locked the Sync button is hidden, and a locked item cannot be deleted. Use Sync to pull in template changes deliberately.

You can also change a relationship for one scenario only, leaving the template alone. The vendor's story: for the Student scenario, make Teacher the parent of Student instead of Subject. The steps are to add the Teacher domain to the scenario, remove the Student domain's current parent, and add Teacher as its parent. Changes at scenario level do not flow back up. Relationships cannot be changed at the test data case level, so this is the place to do it.

19.4.5 Scenario variables and scenario state

Variables. Scenario variables are name-and-value pairs usable only inside the scenario that created them. In the Scenario Variables pane click New Variable, give a name and value and save, then reference it from a parameter (double-click the parameter field and pick it).

State. Normally every run of a scenario produces the same data, for example a RangeGen starting at 10000 starts there every time. Sometimes you want the next run to continue (ids 10000 to 10099 first, then 10100 and on). Clicking Make Stateful saves each generator's position at the end of every successful run; Make Stateless turns it off. By default scenarios are stateless. The state is kept in a small H2 database in the .genrocket folder of the machine, and two runtime options list or clear it: --state-list and --state-clear (with an id or all).

19.4.6 Scenario chains and chain sets

A scenario chain links two or more scenarios so that one downloaded file runs them in order. The vendor example has Department, User and Address scenarios that produce three files from one command. A chain set links chains. A chain holds up to 25 scenarios and a chain set up to 25 chains. Optionally set a delay in seconds after a scenario.

  1. In the Scenario Chains pane click New Scenario Chain, enter a name and description and click Save.

    Naming makes the chain findable among many.

  1. Click the plus beside each scenario to add it, in the order they should run.

    Parents must come first so that their output exists before children use it.

  2. Set delays with the pencil icon if you want one, then Save and Download.

    What you should see: a chain file you run just like a scenario.

19.4.7 Worked example: how loop counts multiply along a chain

From video In its 2020 webinar, GenRocket's CEO explains chains with a three-level example: Organization, Department and User, with one scenario per domain, linked so that every user belongs to a real department and every department to a real organization (referential integrity). Each scenario has a loop count, and a child's count applies to every parent row, so the numbers multiply down the chain.

The webinar's chain, with an arithmetic check in the last column
Scenario (one per domain)Loop countCountedRows madeCheck
Organization3once33
Department3per organization93 x 3 = 9
User3,000per department27,0009 x 3,000 = 27,000

A second route gives the same answer: each organization has 3 departments of 3,000 users, so 9,000 users per organization, and 3 organizations make 27,000. That matches the total the CEO states.

The ShopSphere lab in section 19.5 is the same idea one level shorter: 50 customers x 2 orders = 100 orders. One difference to remember: the webinar describes each scenario as producing its own domain, while the help centre says a child's scenario also pulls in its parents as helper domains (section 19.4.1), which is why non-primary receivers are disabled (section 19.7). Follow the help centre, and compare each file's row count with your calculation.

19.4.8 Running a scenario with the runtime

The scenario file is run from a command window on a machine that has the runtime and your profile.

  1. Download the scenario (or chain).

    The Download button on the dashboard, or the cloud icon in the Scenarios pane. Several scenarios can be downloaded together as a ZIP with Batch Download (up to 15).

  2. Open a command window or terminal in the folder where the file was saved.

    The command needs to find the file.

  1. Run genrocket -r <ScenarioName>.grs.

    The -r option means "run". Chains use the same command.

    What you should see: lines saying the licence was validated, the runtime versions, "Running Scenario ..." for each scenario, and finally "All done!" with the elapsed time.

When data is inserted into a database and loading fails, the runtime throws an exception to the command line (or to the testing framework when it runs in an automated pipeline), so no error means success. The vendor's note on stopping a run: press Ctrl+C, and on Windows answer the "Terminate batch job (Y/N)?" prompt with Y to abort.

From video The 2020 webinar's live demo shows a simple way to check a run. The CTO builds a user domain with an XML receiver, downloads the scenario (about 22 KB, and he points out it would stay that size whether it generates one row or a billion, because it holds instructions, not data), and runs it from a command line with the Java-based runtime. He then opens the XML output and checks that the ids start at 1,000 and rise by one, as the id generator was set to do, that the other values follow their generators' patterns, and that scrolling to the end shows 10,000 rows, the loop count he had set.

Scenarios can also be run through a repository server or an API, which are not covered here. Section 19.4.10 shows the command inside a pipeline.

19.4.9 The Scenario Thread Engine (overview)

The thread engine speeds up chains and chain sets by running several of their scenarios at the same time: genrocket -r Chain.grs -threaded 10. The docs caution that threads may run in any order, so use it only where order does not matter, for example many segment files that a merge receiver combines later (the engine waits for every segment before merging). Do not use it where SQL inserts depend on parent rows already being present, because the order matters for referential integrity.

19.4.10 Scenarios inside an automated test pipeline

From video Later in the 2020 webinar, the CEO plays a short vendor video about combining GenRocket with Jenkins (a tool that runs jobs automatically) and Selenium (a tool that drives a web browser to run functional tests). The point is that data is created at the moment a test needs it, not prepared days earlier. In plain steps:

  1. A Jenkins job starts.

    A trigger such as a build normally starts it; the video starts it by hand.

  2. The job opens a shell and runs GenRocket against a test plan.

    A test plan here is a set of scenarios to work through, so one command covers the whole run.

    What you should see: the Jenkins console showing the test plan loading and executing.

  3. When a test needs data, GenRocket generates it.

    Each test gets fresh data shaped for it, not a shared set that earlier tests may have changed.

  4. GenRocket then calls a Selenium step that performs the functional test.

    The test consumes the data it was just given.

  5. The data can be cleared, and the next test gets fresh data.

    The CEO says it need not sit around; in the 2022 overview video he adds that the transaction can be rolled back before the next test case runs.

The Jenkins page in the help centre (see the overview chapter) runs one named scenario per build step; the test-plan runner in the video is not documented on those pages, so check the current documentation before copying this layout.

Where should the runtime run when the test servers are in the cloud?

From video A viewer asked about cloud-hosted applications in the 2020 webinar's Q&A. The CTO's answer: for a quick data set on your own computer, download the scenario and run it with the local runtime (two or three minutes, he said, against an hour of hand-written Python or Groovy). For a full regression suite on a cloud test server, such as one on Amazon or Azure, install Java and the GenRocket jars on that server and generate the data there. Do not generate it elsewhere and carry it up, because that is slow and moves a lot of data into the cloud. The rule of thumb is: run the runtime where the tests run.

19.5 ShopSphere end to end: CUSTOMERS to CSV and ORDERS to SQL inserts

The build below uses the design from the domains, attributes and generators chapter. SQLFileInsertReceiver is used for orders because it needs no database connection.

Lab: one chain, two outputs

Goal: produce Customers.csv with 50 customers and Orders.sql with 100 insert statements whose customer_id values all exist in the CSV.

  1. Check your resources.

    In the Resources pane the home and output directories must point to real folders on the machine that will run the scenario, and your profile must be in .genrocket. If you change one, download the profile again.

    Expected: three resource rows with paths (JDBC may be N/A).

  2. Add a DelimitedFileReceiver to the Customers domain.

    Set fileName to Customers.csv, delimiter to a comma, includeHeader True, quoteTextData None, appendToFile false. Leave path as the output resource.

    Expected: the receiver appears in Domain Receivers.

  3. In its Attributes Property Keys tab, set columnName to the table's column names.

    Set the id, names and other columns to customer_id, first_name and so on, so the CSV header matches the source database. Set include false for anything the consumer does not want.

  4. Add a SQLFileInsertReceiver to the Orders domain.

    Set tableName to ORDERS, fileName to Orders.sql, batchCount 100, statementSeparator a semicolon, quoteTextData Single, nullValue NULL, appendToFile false. Set the column names to order_id, customer_id, order_date and total_amount.

    Setting useQuotes false on the numeric columns is a reasonable choice, but the vendor page only says "sometimes a numeric value should be quoted".

    Expected: the property-key tab shows the real column names.

  5. Create the scenarios.

    Use Quick Scenario on Customers and on Orders. The Orders scenario brings Customers in as its parent. Both will normally have their receivers, so in the Orders scenario open the Scenario Domain Receivers pane and disable the Customers receiver (or use Disable Non-Primary Receivers), so the CSV is written once, by the Customers scenario.

    Expected: the Orders Scenario Dashboard lists Customers and Orders, with Orders as primary and Customers as root.

  6. Set the row counts in the Scenario Domains table.

    Customers: 50. Orders: 2, meaning two orders for each customer, so 100 in total.

    Expected: the summary for Orders reads like "2 Orders For Each Customer" (the product's wording).

  7. Create a chain called ShopSphereChain with CustomersScenario first and OrdersScenario second, then download it.

    Order matters: parents first.

  8. Run genrocket -r ShopSphereChain.grs from the download folder.

    Expected: "Running Scenario CustomersScenario", then "Running Scenario OrdersScenario", then "All done". Output folder holds Customers.csv and Orders.sql.

Show how to check the result

Open the CSV: it should have a header and 50 rows with customer ids from 1001 to 1050 (if the id variable was set to 1001). Open the SQL file: it should contain 100 insert into ORDERS(order_id,customer_id,order_date,total_amount) values (...) lines whose customer_id values lie between 1001 and 1050, and every customer should appear twice. If you load both into a test database, load customers first so the foreign key is satisfied. (Load order is general database practice, not a documented GenRocket feature.) A header row in the CSV needs includeHeader true; if the Excel viewer shows a single column, the delimiter is wrong.

Variation: insert straight into a database

Replace the SQLFileInsertReceiver with GenericSQLInsertV2Receiver. Create a config.properties file with the connection settings (driver, user, password, url, batchCount) in the JDBC resource folder, set the receiver's table settings, leave truncate on "notApplicable", and put the JDBC driver jar in the runtime's lib folder. Test with --test-jdbc, then run the chain. This needs a database and credentials from the DBA.

19.7 Common mistakes and gotchas

Watch for these
  • Changing a receiver or loop count and re-running the old file. The scenario file is a snapshot. Download it again after every change.
  • Wrong chain order. Children before parents means keys do not exist when you load the data.
  • Column names that do not match the database. In SQL receivers, columnName must be the real column.
  • Parent data written twice. A child scenario brings its parents in; disable the non-primary receivers if you only want the child's file.
  • Truncating a table by accident. Leave truncate on "notApplicable".

19.8 Recap

Key points
  • A receiver turns generator output into a format. Sixteen categories, 120+ receivers; more than one can sit on a domain.
  • Receivers use organisation resources for folders. Download your profile again whenever a resource changes.
  • Delimited, fixed, JSON, XML, Excel and SQL-file receivers cover most needs; segment-and-merge receivers make nested output; masking receivers replace values in existing files.
  • JDBC receivers insert directly and need a JDBC config file; V2 adds resource path settings; bulk-load receivers are for very large volumes.
  • A scenario is built for a primary domain and pulls in its parents. A child's loop count is per parent row.
  • Download, then run with genrocket -r. Chains run several scenarios in order. Locks, state and variables control behaviour between runs.
  • Loop counts multiply down a chain (3 organizations x 3 departments x 3,000 users = 27,000 in the 2020 webinar), so work out the expected row count before you run, then compare it with the output.
  • In a pipeline, run the runtime where the tests run, generate data when a test needs it, and clear it afterwards.
  • When something fails, the commonest causes are a missing profile, wrong paths or variables, relationship or ordering mistakes, and Java memory settings.
