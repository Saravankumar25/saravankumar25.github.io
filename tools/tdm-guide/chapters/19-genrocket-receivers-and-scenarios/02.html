19.3 The common receivers in detail

These are the ones a beginner meets first. Parameters below are those the vendor pages list; a star means the page marks it required. Defaults and exact spellings can differ between product versions, so check the Parameters tab in your own project.

19.3.1 DelimitedFileReceiver (CSV and other delimited files)

Writes attribute values, separated by a delimiter, to a file. This is your CSV maker.

ParameterMeaning
path*, subDirFolder (and optional sub-folder) for the file
fileName*Name of the file
delimiter*The separator character. The screenshots show a tab (\t) as the default; type a comma for CSV
includeHeader*Whether to write a header row of column names. Set to False for no header
quoteTextDataNone, Single or Double quotes around text
nullValue*, booleanValue*How null and true/false appear
appendToFile*True adds to an existing file; false overwrites it
uniqueAttributeAn attribute used to stop a value being written twice
headerFilePath, headerFileNameOptional XML file that defines a multi-row header

Property keys per attribute: columnName (the header text) and include. With no header file, each attribute's Original Name becomes the header.

Header still showing after setting includeHeader to False?

Two vendor reminders: re-download the scenario after any change, because the old file contains the old settings; and if it still shows, your receiver jar may be out of date (the jar-update page explains how to update).

19.3.2 FixedFileReceiver

Writes fixed-width columns (every value padded to a set length), the shape of many mainframe and legacy files. Parameters: outputPath*, outputFileName*, subDir, lineSeparator (for example \n), delimiter, quoteTextData* and includeHeader*. Property keys: columnName, include and length, the width of each attribute. Entering #{BLANK} or #{EMPTY} as a column name blanks a header cell.

19.3.3 JSONFileReceiver

Writes a flat JSON file (not nested). Parameters: path*, subDir, fileName*, rootElementName and alwaysArray (true forces a JSON array even for a single record). Property keys: columnName, include, useQuotes (numbers such as SSNs are often quoted on purpose). One discrepancy worth flagging: the parameter list says path, while the page's use case mentions resourcePath. They are probably the same setting in different versions; trust the Parameters tab you see.

19.3.4 XMLFileReceiver

Writes flat XML. Parameters include path*, fileName*, rootElementName*, rowElementName* and exportStyle*, which chooses how values appear: ATTRIBUTES_ONLY (each value as an XML attribute of the row element), ELEMENTS_ONLY (child elements with text) or ELEMENT_VALUE (child elements with a value attribute). Property keys: name and include.

19.3.5 ExcelFileReceiver

Writes an Excel file. The type parameter selects xlsx or xls; path* and fileName* are required, with formatting settings for quotes, booleans and nulls. The page warns that Excel generation is generally slower than delimited files, and that on Linux a "Permission denied" error can mean the temporary profiles folder under /tmp is not writable.

19.3.6 SQLFileInsertReceiver (SQL statements in a file)

Creates a file of standard SQL insert statements, ready to run in any SQL client. Nothing touches a database while generating, which makes it a safe first choice for learning.

ParameterMeaning
path*, subDir, fileName*Where the .sql file goes and what it is called
tableName*The real table name in the database
batchCount*How many insert statements per batch written
statementSeparator*, rowDelimiter*End-of-statement text (for example a semicolon) and line endings (UNIX/Linux/Mac-LF or Windows-CR/LF)
quoteTextData*, nullValue*, booleanValue*, escapeCharacterQuoting and special-value formatting
appendToFile*, uniqueAttributeAppend or overwrite; avoid duplicates

Property keys: columnName (must match the real column name, such as first_name), include and useQuotes. This is where the attribute name versus original name distinction from the generators chapter pays off.

Example output from the vendor page: insert into user(id,first_name,last_name,middle_initial,emailAddress) values ('1','Penelope','Spaeth','F','user@email.com');. If a nullable column should show a real NULL rather than a quoted string, set nullValue to NULL and quoteTextData to Double (or the style your database wants).

19.3.7 Writing straight into a database: the JDBC receivers

From docs GenericSQLInsertReceiver inserts generated rows directly into a table through JDBC. Its parameters include resourceName* (the resource that points to the connection information), databaseName*, tableName*, truncate*, statementSeparator*, nullValue* and quoteTextData*. Property keys are columnName, columnType and include. The newer GenericSQLInsertV2Receiver adds resourcePath, resourceSubDir, continueOnError and logErrorDetails. The V2 page says it suits "up to 10,000 rows into a table with 25 columns or fewer", and recommends the GenericSQLInsertThreadReceiver for larger loads.

truncate empties the table

The V2 page warns that its truncate parameter can truncate or delete all existing rows before inserting, and that this cannot be undone. The default is "notApplicable" (nothing deleted). Never point a truncating receiver at a database you have not backed up.

Direct database receivers need a JDBC configuration file (config.properties) on the machine running the scenario. It holds driver, user, password, url and, for receivers, batchCount. Its folder comes from resource.jdbc.directory. You can check a connection with the runtime's --test-jdbc option before running a scenario.

Update receivers. SQLUpdateReceiver runs batched UPDATE statements whose values come from attributes (up to 20 attributes mapped to variables var1 to var20), which is the basis of replacing real values with synthetic ones in a table. SQLBatchUpdateReceiver reads one or more update statements from an XML configuration file that can address several databases, using placeholders such as #{firstName}. The FAQ also names StoredProcedureCallReceiver for calling procedures, while the FAQ says SQLUpdateReceiver can run DDL and DML scripts before or after a load, and another page uses SQLUpdateV2Receiver to create a database table.

19.3.8 Nested data: segment-and-merge receivers (overview)

JSONFileReceiver and XMLFileReceiver are flat. For nested output (customers containing orders containing items) GenRocket uses two receiver types together:

  1. Add SegmentDataCreatorReceiver to each domain except the merge domain.

    Each domain writes its rows as a small XML "segment" file, tagged with its parent's id so relationships survive.

  2. Create a merge domain and add a merge receiver, such as JSONSegmentMergeReceiver or XMLSegmentMergeReceiver.

    The merge receiver reads the segments and the configuration file, and writes nested files. Others exist for Avro, Parquet, delimited, fixed, EDI, HL7, SWIFT and SOAP.

  3. Put the merge scenario last in a scenario chain, create the configuration file, and download both.

    Merging only works once every segment exists. Imports of JSON, XSD and some other models set most of this up for you.

The JSON merge page lists parameters such as outputPath, configName, segmentPath and recordsPerFile. If the root domain's loop count is 50 and recordsPerFile is 8, seven files are made (six with 8 records, one with 2). I do not walk through a full nested build here; the vendor pages do it with many screenshots.

19.3.9 Masking receivers (overview)

GenRocket also masks: it replaces sensitive values with synthetic ones, a method it calls Synthetic Data Replacement. The file-masking receivers take an existing file and write a new one with the targeted values replaced: DelimitedFileMaskReceiver, ExcelFileMaskReceiver, JSONFileMaskReceiver, XMLFileMaskReceiver, ParquetFileMaskReceiver, ORCFileMaskReceiver, EDIFileMaskReceiver and FileMaskMultiBlockReceiver (fixed files such as VSAM). The same documents describe database masking in place (IPM). The vendor states that production data is never sent to GenRocket, since only metadata is used. How this compares with masking in other tools is in the Informatica masking chapter and the masking concepts chapter.
