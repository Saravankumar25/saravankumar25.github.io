15.12 From rules to a running job: the generation plan

Rules and assignments are only a description. A plan turns them into something that runs. The plan lists which entities and tables to generate, how many records, and which connections to use; then TDM generates a workflow from it and the workflow does the work (User Guide 10.5.10, p.207). The plan screens are shared with masking and subsetting, so the full tour is in the plans, workflows and warehouse chapter. Here is the generation-specific part.

15.12.1 Creating a generation plan

From the guide's wizard (User Guide 10.5.10, p.305), with the reason for each step:

  1. In the project, click Execute, then New Plan, and name it.

    Plans live in Execute, the project's "run things" tab.

  2. Click Next twice to skip the masking and subset pages.

    The wizard offers all three operation types on one path. You are skipping the two you must not use.

  3. Click Add Generation Components and choose entities and tables (or the XSD file for XML output).

    Only components with generation rule assignments make sense here.

    The chosen entities and tables appear in a list.

  4. Review table names, set generation criteria for an entity if you want, click Next.

    Criteria are where you can restrict which rules apply for a test.

  5. Enter the number of records to generate and set connections and target properties.

    The count is required (p.280).

  6. Optionally edit data generation, error and recovery, and advanced settings. Click Next and Finish.

    Defaults are usually fine for a first run.

    The plan appears in the project's Execute tab. It has not run yet.

You can also make a quick ad hoc generation plan for a single column: in Define | Data Generation select the column, choose Actions > Generate and Execute, name the plan, pick the Integration Service, enter the number of records and answer Yes at the prompt (p.306). It is the fast way to try one rule before you commit to a full plan.

15.12.2 Connections and settings that matter for generation

The settings that matter for generation (pp.280-285): the target connection (a relational database, a flat file or the test data warehouse); Number of Records to Generate (required); a Reference Lookup Connection if any reference lookup rule is assigned; a Dictionary Lookup Connection if the plan has a dictionary rule or a mapplet rule with a transformation; the default Numeric, String, Date and Binary rules with Apply Default Rule to; Minimum and Maximum child records (default 1); and the percentages of parents without children and children without a parent. Target options such as Truncate Table (off by default) and Disable Constraints are covered in the plans, workflows and warehouse chapter.

If the target is a flat file you can use the test tool integration properties to copy the output to an integrated HP ALM server. If the target is the test data warehouse, you fill in data set properties (name, application, version, tags) and the generated data is stored as a versioned data set (pp.190, 281). That is how generated data gets reused, see the plans, workflows and warehouse chapter.

Heap space and special characters

If a "Java heap space" exception occurs while setting an ad hoc rule, ask the administrator to increase the heap size (p.198). Remember also that special characters in table or column names make the generation workflow fail (p.190); the plan setting "Enable special characters in metadata" defaults to No (p.289).

15.13 Why a generation plan stands alone

The guide is firm: when you add data generation components to a plan, you cannot add data masking or data subset components, and the reverse holds too (User Guide 10.5.10, pp.274-276, 305). It repeats the rule in the plan overview, the task list, the component table and the creation steps. A Hadoop plan likewise cannot do subset or generation (p.306).

The guide states the restriction but does not explain it. Masking and subsetting both read existing rows from a source, then change or filter them. Generation has no source rows; it builds new rows from rules. A plan that tried to do both would have to decide what the masking rule should act on. Keeping them apart avoids that.

One plan: subset and masking

Source connection to target connection. The guide says you can combine them in one plan, or keep separate plans (p.304). If both are present, subset runs first and masking applies only to the subset rows (p.275).

Another plan: generation

Only entities, tables or XSD files with generation rule assignments. Number of records to generate. No source data is masked or subsetted in this plan.

What to do when you need both. Use two plans:

  • Masked copy of old customers plus brand-new ones: run a masking plan into the test database, then a generation plan into the same schema. Make the generation sequences start above the existing ids, or continue with "Start Sequence from Last Value", so keys do not collide.
  • Generate once, then make small slices: send the generation plan to the test data warehouse, then create a related data set, a subset of that data set built from an entity or group (pp.248-251). That is subsetting generated data without breaking the rule.
Why it matters

This restriction shapes how a data pipeline is designed: generation is its own track, not a masking option.

Lab A: generate 50 ShopSphere customers with valid orders

Goal: end with 50 rows in CUSTOMERS plus linked ORDERS and ORDER_ITEMS in an empty test schema, then prove the keys are valid. The steps follow the guide's task flow (pp.192, 195-205, 305). You need an installed TDM, an empty test schema SHOPSPHERE_TEST with the four tables, and a PRODUCTS table already holding a few products (P-100, P-200, P-300).

  2. In Policies, create standard rules with Actions > New > Generation Rule.

    The rules appear in the Policies list.

  3. Create a project and import metadata for the four tables.

    Click Projects, Actions > New, name it, open it, then Actions > Import Metadata and choose Datasource Connection to the test schema (pp.53, 66). Metadata tells TDM what columns exist; it copies no rows.

    The four tables appear under the project's data sources.

  4. Create an entity for the parent-child tables.

    In Define, create an entity with CUSTOMERS as driving table so TDM pulls in ORDERS and ORDER_ITEMS (pp.116, 277). If the foreign keys are not declared in the schema, add logical foreign keys first on Discover | Tables | Constraints (p.110).

    Set the relationship minimum and maximum to 1 and 3 for CUSTOMERS to ORDERS, and 1 and 4 for ORDERS to ORDER_ITEMS (p.117).

    A diagram shows the three tables joined.

    Every row has a rule name, and nothing is left to the default rule except columns you chose to ignore.

    The email cell shows the advanced rule's name.

15.14 Common mistakes and gotchas

Things that go wrong
  • Forgetting to Save each assignment. The earlier assignment is discarded (p.203).
  • Editing a rule and expecting a finished plan to change. Regenerate and rerun the plan (pp.195-196).
  • Combining masking or subset components with generation components in one plan. Not allowed (pp.274-275). Use two plans.
  • Using a pattern and "Generate Unique Values" together. The guide says uniqueness is unavailable with a regular expression (pp.222-223). Use sequences for keys.
  • Re-running into a table that already has ids from 1001. Key collisions. Truncate the target, or continue the sequence from its last value (p.231).
  • Believing pattern-made SSNs or card numbers are valid. They might not be (p.224). Use the Credit Card technique when validity matters.
  • Ignoring warnings. A rule that conflicts with a conditional constraint wins quietly and only logs a warning (p.202).

15.15 Recap

Recap
  • Generation builds new rows from rules and never reads production data. It is set up in a project, run from a plan, and executed as a generated workflow.
  • Rules come as standard, custom, advanced (global) and ad hoc (per project). Unassigned columns get the default rule for their data type.
  • The eleven techniques are Sequence, Random, Set of Values, Dictionary, Credit Card, Reference Lookup, Expression, Conditional, Effective Dates, Advanced and Custom. Reference Lookup, Expression, Effective Dates and Conditional are ad hoc.
  • Null and invalid values are mixed in by percentage through the Exception Test Data settings.
  • Entities with minimum and maximum child counts, and reference lookups, keep parent-child keys consistent. Always verify keys with a join.
  • The number of records is a plan setting. A generation plan cannot contain masking or subset components.
  • Conditional constraints restrict one column using another, but a conflicting rule wins and only produces a warning.
