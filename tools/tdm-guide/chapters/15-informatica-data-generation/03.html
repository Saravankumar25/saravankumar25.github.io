15.9 The generation techniques, one by one

A technique is the method a rule uses to produce values. The guide lists eleven (User Guide 10.5.10, p.209). Which ones you may choose depends on the column's data type, and some are ad hoc only, meaning you can use them only when you create a rule directly on a column inside a project (pp.208-209).

15.9.1 Sequence

From docs A global or ad hoc rule that makes numeric or date values in a sequence. You pick a beginning value and an increment (User Guide 10.5.10, p.230).

When: ids and anything that must be ascending: customer ids, ticket numbers, consecutive dates. The guide's example is a TICKET_NUMBER column with start 1000 and increment 1 (p.231).

Sequence parameters (pp.231-232)
ParameterApplies toMeaning

Start Sequence from Last ValueNumericOn the next run of the plan, continue from the previous output value. On a string column the sequence restarts from the beginning.
Start DateDateFirst date
Increment byDateA number plus a unit: year, month, day, hour, minutes or seconds
Null Values / Invalid ValuesBothException data. Invalid means below the start value for a positive increment, or above it for a negative one.

ShopSphere: customer_id with start 1001, increment 1 gives 1001, 1002, 1003 and so on. A date sequence for order_date with start 2026-01-01 and increment 1 day gives one order per consecutive day.

Limits: you cannot add a conditional constraint to a sequence column (p.201) or put conditions on a sequence rule (p.234).

15.9.2 Random

From docs A global or ad hoc rule that creates random strings, numbers and dates, for things like salary and birth dates (p.220). For strings you give a minimum and maximum length; for numbers a minimum and maximum value; for dates a range. You can instead supply a regular expression (a compact pattern language for text shapes) and say what percentage of rows follow it. If you use several patterns the percentages must total 100.

Writing patterns

For strings the usable operators are ., \d, \w, alternation (a|b|c), {n} repeat counts and [ ] sets. To make numbers that contain special characters, use the string technique. To make plain numbers use the numeric technique, which allows \d, alternates like (1|2|3) and [0-9], and alternates cannot be nested (p.223).

A five-minute pattern primer for beginners

If you have never written a regular expression, read a pattern left to right as a list of "slots". This primer is general knowledge, not from the guide, but every symbol in it is one the guide lists (p.223).

Pattern pieces, as used in the ShopSphere rules
PieceMeansExampleMatches
\done digit, 0 to 9\d7
{n}repeat the previous piece n times\d{3}482
[ ]one character from a set or range[A-Z]K
( | )one of the listed choices(6|7|8|9)8
\.a literal dotexample\.orgexample.org
plain charactersthemselves--

Now read the SSN-like pattern \d{3}-\d{2}-\d{4} aloud: three digits, a hyphen, two digits, a hyphen, four digits. Read the tax id [A-Z]{3}\d{6}: three capital letters, then six digits. Read the mobile pattern (6|7|8|9)\d{9}: a first digit of 6, 7, 8 or 9, then nine more digits, ten in all.

To test a pattern before you save the rule, write two or three values by hand and check each slot matches. Then generate 50 rows into a scratch table and look for rows that surprise you.

Patterns cannot make valid checksummed numbers

For credit card, Social Security and Social Insurance numbers the guide warns that pattern-made values might not be valid, because real numbers follow algorithms that a pattern cannot reproduce (p.224). That is fine for "SSN-like" test data, and it is why the Credit Card technique exists.

Date example: a random date rule from 1950-01-01 to 2005-12-31 for date_of_birth gives values such as 1990-04-12 and 1999-07-23. Set Exclude to Saturday and Sunday and no value falls on a weekend; "invalid" for dates means outside the range or on an excluded day (p.221).

15.9.3 Set of Values

From docs You type the values you want and the percentage of rows for each; the percentages must total 100 (decimals allowed). Works for string, numeric and date, and can be global or ad hoc (pp.232-233). Best for columns with a handful of values, such as membership status.

Parameters: Value (one row per value, add rows as needed), Distribution%, and the usual Null Values and Invalid Values. For this technique "invalid" means anything not in the list (p.233).

The guide's example is a PAYMENT_TYPE column with Visa 60, MasterCard 30, Paypal 10. ShopSphere: zip_code with 560001 at 40, 600017 at 35 and 682001 at 25. Of 50 customers, about 20, 17 or 18, and 12 or 13 will get each zip code. Percentages are targets, so expect small rounding differences.

15.9.4 Dictionary

From docs Loads values from a dictionary (a flat file or relational table of values) into a column. Good for columns with realistic but finite values: names, states, countries. Before you create the rule, someone with permission must add the dictionary under Administrator | Dictionaries. Works for string, numeric, date and binary data; flat file or relational source; binary only from relational (p.215).

If both lookup and table columns are of double data type the process generates nulls (p.216). The guide's example makes two string rules from one names dictionary: one picks the first-name column, one the last-name column (p.215).

ShopSphere: first_name uses dictionary NAMES column FIRST, last_name uses column LAST. Sample output: Meera, Nair; Ravi, Kumar; Asha, Menon. The dictionary's name and column names here are placeholders I made up. Because the two rules pick independently, "Ravi Menon" is as likely as "Ravi Kumar", which is fine for testing and wrong for anything that needs a believable family name.

15.9.6 Reference Lookup

From docs An ad hoc rule that takes column values from an existing table, for string, numeric and date columns. You name the parent table and map parent columns to child columns. The same rule can fill several child columns from the same parent table (p.229). The guide's example: use the same customer ids that exist in another table.

ShopSphere: ORDERS.customer_id reads CUSTOMERS.customer_id with minimum 1 and maximum 3, so each existing customer gets one to three orders. Set "Parent records without children" to 10 and about one customer in ten has no orders, a useful edge case. Remember the plan needs a Reference Lookup Connection (p.280), and see the note on reference lookup about where the parent rows must already live.

Reference lookup is not for XML targets

You cannot use reference lookup or effective dates rules for an XSD (XML) source (p.206).

15.9.7 Expression

From docs An ad hoc rule that computes a value from an expression you build in the Expression Builder, choosing columns and functions from lists. Works for string, numeric and date (p.219). Parameters: Expression, Null Values, Invalid Values (invalid = does not follow the expression) (p.220). If you tick "Override Data Type to Numeric" on a string column, you cannot enter a numeric expression (p.219).

The guide's example builds a Name column from FirstName and LastName with CONCAT (FirstName+'/'+LastName). ShopSphere: imagine a display_name column built as CONCAT(CONCAT(first_name,' '),last_name), giving "Asha Menon". I mirrored the nested CONCAT style the guide uses in its advanced example; check the exact function list in your Expression Builder.

When: any column that is a function of other columns in the same row. The dependent column must still be assignable after its inputs, so assign rules to the inputs too.

15.9.8 Conditional

From docs An ad hoc rule with one or more rows of "if this condition, then use this generation rule". Conditions are applied in the order listed (reorder with the up and down arrows). Works for string, numeric and date, but you cannot apply conditions to effective dates or sequence rules (p.234).

Conditional parameters (p.235)
ParameterMeaning
ConditionAn expression built in the Expression Builder. Add several for one column.
Generation RuleThe rule to apply when the condition is true. Use an existing project rule, create one, or edit an ad hoc rule.

The guide's example: DEPT_ID 11 gets a 5 percent hike, 22 gets 10, 33 gets 15. The column that the condition reads (DEPT_ID) must itself have a rule, and TDM generates it first, then the dependent column (p.234).

ShopSphere (hypothetical city column): if zip_code = '560001' then city is "Bengaluru", if '600017' then "Chennai", if '682001' then "Kochi". Each "then" is a one-value Set of Values rule. The guide does not describe a catch-all "else" row, so make sure every possible input value has a condition. Check how unmatched rows behave

15.9.9 Effective Dates

From docs An ad hoc date rule that fills two related columns, an effective start date and an effective end date, so that periods follow one another without overlap. It makes a random start in a range, an end after it, and the next start right after that end. A grouping column decides how many dates are in each sequence: the number of rows sharing the same grouping value (pp.217-218).

You create the rule on either the start or the end column and name the other. Parameters: Start Date/Time, End Date/Time, Exclude (up to two different weekdays), Effective Start Date column, Effective End Date column, Grouping Column, Invalid Values (percent of rows breaking the sequence; the rule is fixed to Default) (pp.218-219).

15.9.10 Advanced

From docs A combination of techniques that fills one or several target columns from one or more input, variable and output ports (pp.199, 212). Use it when one column needs two techniques, or the value depends on other columns. You can generate string, numeric and date data.

  • Input port: optional; takes a target column or a parameter file value. If you tick Parameterize Input Port and give a name, you need not map it to a column.
  • Variable port: a work field for intermediate values. Its technique is either Conditional or Generation Rule Set (rules with distribution percentages, optionally grouping records by foreign key). A variable can depend on another variable.
  • Output port: the column that receives data; needs an Expression built from inputs and variables.

Port names need not match column names; you map them at assignment time (p.199). Port properties: Column Name, Column Type, Datatype (string, numeric or date), Precision, Scale (pp.214-215).

It shows "New Generation Rule: Step 2 of 2" with a Columns pane listing one input column (Ip_1, string, 10), a variable column (Var_1) with Configure Rule and two default numeric sequence rules, and one output column (Out_1), plus a Properties pane showing the output expression CONCAT(Ip_1,Var_1). What to look for: the three port groups stacked in one list.

The guide gives two examples. One makes 50 invoice ids and 50 order ids ("Invoice-1" to "Invoice-50", "Order-1" to "Order-50") by concatenating an input prefix with a conditional numeric sequence (pp.199-200). The other builds email ids: input in_FirstName, variable var_Domain from a rule set of two domains, output CONCAT(CONCAT(in_FirstName,'@'),var_Domain) (p.213).

ShopSphere: realistic emails (my adaptation of the guide's example)

Input in_FirstName mapped to first_name. Variable var_Domain with a Generation Rule Set: example.com 50 percent, example.org 50 percent. Output out_Email with the expression above. Result: Asha@example.com, Ravi@example.org.

The limit, shared with the guide's own example: two customers called Asha get the same email. If email must be unique, add a second input (for example the customer id) to the expression, then test it. The guide does not say whether an input port reads the value generated for another column in the same run, so check that first_name is generated before the email. Verify in your version

15.9.11 Custom

From docs A global rule built from a PowerCenter mapplet. You import it, and mark at least one input and one output column as required. Works for string, numeric and date (pp.196, 211). Use it when you need PowerCenter transformations (SQL, Stored Procedure) or logic that the built-in techniques cannot express.

Imported columns have these properties: Column Name, Column Type (input or output), Data Type, Precision, Mandatory, Group Name (p.212). Assignment maps your table columns to the mapplet's input ports and its output ports to your target columns (p.204). The guide's example: standard rules make first and last names, and a custom rule combines them into a full name.

ShopSphere: a mapplet that takes first and last name and returns "Asha Menon" for a display_name column. A custom rule is heavier than an expression rule, so use it only when an expression cannot do the job. Building mapplets is covered in the Informatica masking chapter.

15.10 Conditional constraints: rules between columns

Techniques fill one column at a time. A conditional constraint is a table-level rule that restricts what may appear in a column based on another column. It becomes part of the target table's metadata (User Guide 10.5.10, p.201).

The guide's example: a flight table with From_City and To_City both filled by the same dictionary rule, plus the constraint To_City != From_City so no ticket flies from a city to itself (p.202). A ShopSphere analogue with hypothetical columns: delivery_date > order_date.

  1. In the project, open Discover > Tables and click the table.

    Constraints belong to a table, not a rule.

  2. Open the Constraints tab and click Create New Constraint.

    This is the same dialog used for foreign keys.

  3. Name it, set the constraint type to Conditional, click Next.

    Conditional is the type reserved for data generation.

  4. Build the expression in the Expression Builder and click Finish.

    The Expression Builder offers columns, functions, variables and operators.

    The constraint is listed on the table, and generation plans that include that table honour it.

Steps from User Guide 10.5.10, pp.110-111.

Where the constraint cannot be used: numeric sequence, date sequence and random data patterns (p.201). On XSD sources you cannot constrain an element that allows more than one child per parent (p.201).

When the rule and the constraint disagree, the rule wins

The guide's example: both Created_Date and Modified_Date use a random date rule ending 31 July 2014, with the constraint Modified_Date > Created_Date. When Created_Date is 31 July 2014 no later date is allowed, so TDM writes a date within the rule's range anyway and generates warning messages (p.202). The constraint was broken, quietly. Read the warnings in the Monitor logs (the plans, workflows and warehouse chapter) and loosen the rule's range, not just the constraint.
