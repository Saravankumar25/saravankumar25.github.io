15.4 Rule types: standard, custom, advanced and ad hoc

A rule can be created in four ways. The difference is mostly how many columns it touches and where it lives (User Guide 10.5.10, pp.192-193).

The four generation rule types

Global rules appear in every project and carry a name. Ad hoc rules have no name, cannot be moved, and are defined by the target columns you pick when you create them (p.193). The three techniques that exist only as ad hoc are reference lookup, effective dates and expression; conditional is also listed as ad hoc in the technique table (p.209).

15.4.1 Editing and deleting rules: the "impacted objects" check

If you edit or delete a global rule that is already assigned somewhere, TDM shows an Impacted Objects dialog listing affected columns, plans and data domains. You can export that list as a .csv file, then click Continue to save. The change does not reach a plan until you generate and run that plan again (User Guide 10.5.10, pp.195-196). The same dialog appears when you edit an ad hoc rule, assign a rule, or clear an assignment (pp.199, 204-206).

15.4.2 Creating a standard rule

  1. Open Policies and choose Actions > New > Generation Rule.

    Creating it in Policies, not inside a project, makes the rule global and reusable.

  2. Enter a name, pick the column's data type, select the standard type and optionally tick Override Allowed.

    The data type decides which techniques the wizard offers, so choose it first.

  3. Click Next, fill in the parameters, set the exception test data options and click Finish.

    The options choose whether to allow nulls or empty spaces and whether to produce invalid data (see exception test data).

    The rule appears in the Policies list and can be assigned in any project (p.195).

15.4.3 Override: one rule, small variations

If a rule has Override Allowed set, whoever assigns it can change its parameters for that one column without touching the global rule. The guide's example: a rule that makes random dates from 2011 to 2012 with override on; a user assigns it and adds Saturday and Sunday as excluded days, so that column gets weekday dates only (p.193). To do it, select the column in Define | Data Generation, choose Actions > Override, edit the values and Save. The Override column then reads Yes-Overridden (p.196).

15.4.4 Custom and advanced rules, in brief

A custom rule imports a PowerCenter mapplet. You must mark at least one input and one output column as required. The guide's use: combine first and last name into a full name, or use PowerCenter transformations such as an SQL or Stored Procedure transformation (User Guide 10.5.10, p.196). An advanced rule has input, variable and output ports and can mix techniques. Both get their own sections in the technique tour.

15.5 Default rules: what happens to columns you ignore

Columns without an assigned rule receive the default rule for their data type (User Guide 10.5.10, p.193). The defaults (Numeric, String, Date and Binary, plus separate primary key and unique key defaults for each type) are visible on a project's Overview | Properties tab (pp.193-194).

Keys get their own defaults because a primary key must never repeat or be empty. The administrator configures the initial defaults (p.193), and in the plan's Data Generation Properties you can adjust them again and tick Apply Default Rule to columns without rules (p.285).

Two more shortcuts the guide mentions (pp.194, 205):

  • Default data domain rule. You set this when you create and run a data domain profile (the Informatica discovery and profiling chapter), so discovery can feed generation.
  • Auto rule. After a column profile you review and finalise results. Columns whose Inferred Rule shows Yes can take the Auto Rule, which fills the column from the approved profile results. Do not apply an auto rule to a primary key column, because a primary key cannot contain nulls.
Default rules are not a plan

The guide notes that default rules are not filled in if the rules are not part of the project. If the default boxes in the plan are blank, you must choose the default rules yourself (p.284). Random defaults are fine for a column nobody tests, not for one with business meaning such as email.

Save after every assignment

In this view you must click the Save icon each time you assign a rule. If you pick a rule for the next column without saving, Test Data Manager discards the earlier assignment (User Guide 10.5.10, p.203). It is the most common way to lose twenty minutes of work.

15.6.1 How each kind of rule is assigned

  • Standard rule: click inside Generation Rule for the column, choose the rule, click Save (p.204).
  • Custom (mapplet) rule: choose it, and a Custom Rule Assignment dialog shows your table's columns on one side and the mapplet's input ports on the other. Select a column, select a port of the same data type, click the Link icon. Click Next, then link each rule output port to a target column and Save (p.204).
  • Advanced rule: the same linking dialog, with a second step for outputs. If the variable column groups child records by a foreign key, you must also select that foreign key column (pp.204-205). You need not map an input port that you parameterised, nor a rule with no input ports.
  • Auto rule: select the column, choose Auto Rule, Save. To apply it to many columns, select several rows and use Generation Rule Assignment, then Apply (p.205).
  • Remove an assignment: select the column and choose Actions > Clear Assignment (p.205).

15.7 Tables, entities, relationships and keys

Real data is not a pile of independent tables. Every ShopSphere order must point to a customer that exists, and every order item to an order that exists. If you generate each table separately with random numbers, the foreign keys will point nowhere and the app will fail for reasons unrelated to what you wanted to test. TDM gives you two tools for this.

15.7.1 Entities: generate a parent with its children

An entity defines tables related by physical or logical constraints, and keeps the hierarchy (User Guide 10.5.10, p.277). You can add entities (and plain tables) to a generation plan. You create the entity in the project's Define area, pick a driving table, and TDM finds related tables from the constraints. If your database has no declared foreign keys, add a logical foreign key on the Discover | Tables | Constraints tab, mapping the child column to the parent column (the Informatica subsetting chapter; User Guide 10.5.10, pp.110, 116).

For each relationship in an entity map there are Minimum and Maximum properties: the fewest and most child records to generate for each parent record (p.117). The plan-level Data Generation Properties repeat this as Minimum and Maximum (guide default 1 for each), plus Parent Records Without Children and Child Records Without Parent percentages for self-cyclic tables or reference lookups (p.285). A link between XML elements works the same way. A range set on an individual relationship takes priority over the plan-level ratio (p.207).

15.7.2 Reference lookup: borrow values from a table that already exists

The second tool is the reference lookup technique (see Reference Lookup). Instead of making values, it reads them from an existing parent table, so a child column can only receive keys that exist there. The plan then needs a Reference Lookup Connection, a connection to the database that holds the parent tables (User Guide 10.5.10, p.280). Use it for static reference data: ShopSphere's PRODUCTS table is the natural example for ORDER_ITEMS.product_code.

What I could and could not confirm

The guide says entities keep parent-child hierarchy and lets you set child counts per parent. It does not spell out, in the pages I read, exactly how TDM copies the parent key into the child's foreign key column, or whether a reference lookup may read a parent table generated in the same plan rather than one already loaded in the database. After a first run, always check keys with a quick join query (the lab does). Verify in your version

15.7.3 Primary keys and unique values

  • A computed column as primary key blocks generation for an entity: you cannot run generation that includes an entity whose primary key column is a computed column (p.191).
  • For multirecord IMS sources imported from PowerCenter, the table sequence is not imported, so you must supply it with the Manage Sequence button on the entity's Entity Map tab (pp.191-192). This is a mainframe case you can skip for ShopSphere.
  • Many techniques have a Generate Unique Values checkbox. It cannot be combined with regular-expression patterns, and cannot be used for binary or flat-file dictionary rules (pp.216, 222-223).
  • For ids, the cleanest choice is the Sequence technique. A sequence never repeats within a run, and "Start Sequence from Last Value" lets a second run continue where the first stopped (p.231).

15.8 How many records? And exception data

The number of rows is not part of a rule. It is set in the plan: the field Number of Records to Generate is marked Required for generation plans (User Guide 10.5.10, p.280). In the plan wizard it is step 14: "enter the number of records that you want to generate" (p.305). You can also give criteria per entity on the generation criteria step (p.305).

For a parent-child set, the Minimum and Maximum child settings decide how many children each parent gets, so total rows in the child tables are not a round number. My reading, flagged because the guide gives no worked example of totals: with 50 customers and 1 to 3 orders each, expect between 50 and 150 orders. Confirm with the Row Count report (the plans, workflows and warehouse chapter).

15.8.1 Exception test data: nulls and invalid values

Almost every technique ends with the same two settings, Null Values and Invalid Values (User Guide 10.5.10, pp.210-211). Each takes a rule (an existing global rule, or "Default") and a percentage, which may have up to two decimal places.

  • Null Values: the percentage of rows that will contain a null in this column. Cannot be generated for MongoDB sources (p.210).
  • Invalid Values: the percentage of rows that deliberately break the rule, where "invalid" means whatever does not conform to the rule: outside the numeric range, wrong length, not in the dictionary and so on.

The guide's trick: make a rule "Recent_Dates" for 2012 to 2013 and, in its Invalid Values setting, choose a second saved rule "Dates_2005" (2005 to 2010) at 15 percent. Now 85 percent of dates are recent and 15 percent are old (p.210). So "invalid values" is really a way to mix in a second population.

Why would I want bad data?

Good testing needs negative cases. If ShopSphere's checkout rejects a customer with no phone number, you need rows with no phone number. Ten percent nulls in phone and two percent invalid zip_code values give your tests something to reject, without hand-crafting rows.
