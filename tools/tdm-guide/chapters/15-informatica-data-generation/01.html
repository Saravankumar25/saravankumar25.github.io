So far in Part II every operation started with real production data: discovery looked at it, subsetting shrank it and masking disguised it. This chapter does something different. Data generation builds test data from nothing but rules, so no production row is read, copied or at risk. If you have read the generation concepts chapter, you know why teams want this. Here you learn how Informatica TDM does it.

The chapter has one running goal, taken from the Day 45 syllabus item "generate test data using the Informatica ILM tool": by the end you should be able to describe how a generation job is defined, choose a technique for every ShopSphere column, and generate 50 customers with valid orders. The plan, workflow and monitoring side is shared with masking and subsetting, so it is covered in the plans, workflows and warehouse chapter.

15.1 Words to know first

Data generation
Creating new, realistic but fictional rows by following rules, instead of copying real rows. Also called synthetic data creation.
Generation rule
A saved recipe for one kind of value, for example "ten random digits starting with 6 to 9". It names a technique and sets its parameters.
Assignment
The link between a rule and a target column: "column phone uses rule Phone_10_digits".
Global rule
A named rule created once in the Policies area and reusable in every project. Standard, custom and advanced rules are global.
Ad hoc rule
An unnamed rule created inside one project directly on a column. It cannot be moved to another project.
Default rule
The rule TDM applies to a column you did not assign anything to, chosen per data type.
Entity
A set of tables linked by keys (a parent with its children) that TDM treats as one unit. You met entities in the Informatica subsetting chapter.
Dictionary
A file or table of ready-made values, such as first names, that a rule can pick from. It must be added to TDM by a user with the right permission before a rule can use it.
Exception test data
Deliberate nulls and deliberately invalid values mixed into the output, so that tests also see bad data.

15.2 What data generation is for

Picture ShopSphere's performance team. They want to test the "Customer Orders" app with 500,000 customers, ten times more than production holds. Subsetting can only shrink what exists. Masking keeps the same number of rows. Neither can invent rows. Generation can, and since it never touches production, there is nothing to leak.

The guide defines it plainly: use data generation to create realistic test data for test environments, using rules that define the logic From docs (User Guide 10.5.10, p.190). You import the target table definitions (the metadata) into a project to say what shape of data you want, assign rules to columns, then run a plan.

Why it matters

Generated data is the safest test data there is, and it is the only kind that can reach any volume you like, or hit awkward cases (nulls, invalid values, boundary dates) on purpose. Its weakness is realism: it only looks as real as your rules. A rule that makes every email "name@example.com" will not exercise your duplicate-email checks. Most of this chapter is about writing rules that are realistic enough.

Steps 1 to 5 are design time: you are only describing data, and no row exists yet. Step 6 packages the description, and step 7 is the first time anything is written. This mirrors the ETL and TDM chapter: the plan is the specification, and the workflow that TDM generates from it is the ETL job.

One detail from the overview is easy to miss: if a table name or column name contains special characters, the data generation workflow fails (User Guide 10.5.10, p.190). Check your target names before you import metadata.
