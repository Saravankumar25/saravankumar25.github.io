4.7 How sensitive data is found

A real production database can have hundreds of tables and tens of thousands of columns. Nobody can read them all, and column names are often cryptic (COL_17, FLD_X2). So tools look for sensitive data automatically. At concept level they all rely on a small set of signals. The full hands-on process is the subject of the discovery and subsetting concepts chapter, the Informatica discovery and profiling chapter and the Delphix profiling chapter. Here we only need the ideas.

Three signals

The three detection signals (general concept, with where each tool uses it)
SignalWhat it checksStrengthWeakness
Column name (metadata)Does the name look like ssn, email, phone?Fast, needs no data accessMisses cryptic names. Flags harmless columns with unlucky names.
Data patternDo the values look like an SSN, a phone number, an email?Works even when the name is uselessSlower, reads real data. Nine digits may be an SSN or an order code.
Dictionary or list of valuesAre the values found in a list, such as common first names or country names?Finds things with no fixed shape, such as namesLists are language-specific and never complete.

A fourth signal, data type and length, is used to rule things out: an SSN cannot live in a column that holds one-character flags.

What Informatica does: data patterns and metadata patterns

From docs Informatica describes a data domain using regular expressions. A regular expression (regex) is a compact text recipe for a pattern, for example "three digits, a hyphen, two digits, a hyphen, four digits". The guide separates two kinds (User Guide 10.5.10, pp.74 to 75):

  • A data pattern matches the values. Its example for Social Security numbers is [0-9]{3}-[0-9]{2}-[0-9]{4}.
  • A metadata pattern matches column names. Its examples for Social Security numbers are .*SSN*, .*SOCIAL* and .*SECURITY*.

A column joins the data domain if it matches any expression in the domain. When you run a data domain profile you choose to search the data only, the column name only, or both, how many rows to read (default 1,000) and a minimum conformance percent, since not every row has to match the pattern (pp.95 and 100). From docs

Data pattern     [0-9]{3}-[0-9]{2}-[0-9]{4}     matches   123-45-6789
Metadata pattern .*SSN*                          matches   SSN, CUST_SSN, SSN_NO

What Delphix does: profile sets, classifiers and domains

From docs Delphix calls the detection step profiling. A profiling job examines metadata (column names and types) and possibly the data itself, and when it decides a column is sensitive it assigns the matching domain and that domain's default masking algorithm. It only covers the tables and files in the chosen rule set (Delphix "Discovering your sensitive data", source page ↗).

The logic is packaged in classifiers, grouped into profile sets. Four classifier frameworks exist, and they map neatly to our signals:

Delphix classifier frameworks (Delphix "Discovering your sensitive data")
FrameworkWhat it examinesLevel
PATHThe path to the data; for a database that means table and column name. Uses regex or exact match.Column
TYPEData type and length. Used to reject domain matches. Types: String, Number, Date, Binary.Column
REGEXThe data itself, using regular expressions to match or reject a domain.Data
LISTWhether data values appear in a list of values, to match or reject a domain.Data

The recommended built-in profile set, the "ASDD Standard" set, includes list classifiers that can detect domains such as FIRST_NAME and LAST_NAME even when column names are meaningless, though data-level detection is limited to English values (Delphix "Out of the box profiling settings"). From docs

One real example: how Delphix recognises an SSN

The ASDD Standard listing (Delphix "ASDD standard profile set", source page ↗) shows the SSN domain is defined by three classifiers. In our words:

  1. A PATH classifier.

    A regex on the column path catches names like ssn or social security number with variants such as social_security_no. Its match strength is listed as 0.67.

  2. A REGEX classifier on the data.

    Patterns for the nine-digit format. The dashed or spaced form (123-45-6789) is listed with match strength 0.7, while nine bare digits are listed with only 0.1.

    The lower number for bare digits fits the idea in the weaknesses table above: nine digits in a row are far more likely to be something other than an SSN.

  3. A TYPE classifier.

    The column must be a Number or String of at least 9 characters. This rejects tiny columns.

The excerpt I had does not explain how the strengths are combined into a final decision, so read the product page for your version before relying on the numbers. What matters for a beginner is the design: several weak clues, each with a weight, are combined to decide.

What GenRocket does: column names only

From docs GenRocket's "Data Column Profiling" scans column headers, not the data. It checks whether each column name contains a keyword from a list: 102 built-in names plus any your organisation adds (for example user_email matches email, client_ssn matches ssn). It then shows you the matches to choose from (GenRocket "PII Discovery with Data Column Profiling", source page ↗). It is the "column name" signal on its own. The upside is that the tool never needs to read real values.

Show a worked answer

Step 1: 9876543210 and 0987654321 match. 98765 43210 does not, because a space breaks the run of digits. 98765432101 is eleven digits but contains a ten-digit run, so it matches only if partial matches are allowed, which is a trap. +91 9876543210 also matches only as a partial match.

4.8 Policies, rules and data domains

Now the vocabulary promised at the start. A TDM tool needs one place that records the answer to "what is sensitive here, and how do we protect each kind?". Informatica calls that place a policy. The structure is worth learning exactly, because it explains many menus you will see later. From docs (User Guide 10.5.10, p.71)

What each piece is

Policy (Informatica)
"A data masking component that describes the methods to maintain the privacy of specific types of source data". It contains data domains. You assign a policy to a data source in a project, and one policy can serve several projects (p.71).
Data domain (Informatica)
Describes the functional meaning of a column based on its data or its name. It carries data patterns, metadata patterns, a sensitivity level, a status (enabled or disabled) and, optionally, preferred masking and generation rules (pp.73 to 75).
Rule (Informatica)
"A logic to mask sensitive data or to generate test data": a technique plus its parameters. Rules exist for string, numeric and date data (p.72).
Preferred rule and default rule
When you attach several rules to a domain they are "preferred rules", and one is the default, applied to all columns in the domain unless you pick another. The guide's example: a Last_Name domain with a shuffle rule as default and a substitution rule as another preferred rule (p.73).
Policy pack
A ready-made policy shipped with TDM. There are three: PII, PHI and PCI, visible after installation (p.77).

The order of work does not matter. The guide says you can create policies, rules and domains in any order, then connect them: create masking rules, define domains, assign rules to domains, create a policy, assign domains to it (p.72). From docs

The word "rule" means different things

In Informatica a rule changes data. In Delphix a rule set is only a list of tables or files that a profiling or masking job runs against (Delphix "Delphix masking terminology"). Mixing these up is the most common vocabulary mistake when someone switches tools.

Two behaviours from the Delphix "Managing domains" page are worth knowing: each domain has a single default masking algorithm, so you need a separate domain for each distinct algorithm you want the profiler to assign, and changing a domain's default algorithm only affects future profiling runs, not assignments that already exist in rule sets. From docs

Both tools use the domain idea for a consistency reason as well. Delphix says the domain mechanism helps ensure the same masking algorithm is applied consistently across rule sets whenever a particular type of sensitive data is discovered. Informatica says all columns in a domain are masked with the same rule, so "SSN" and "SOCIAL_SECURITY" in different tables end up masked the same way (p.73). Consistency across tables is a major theme of the masking concepts chapter.

Here is the whole chain in one story, so the pieces above fit together. This is the shape of a real engagement, simplified. It is an illustrative process General concept that uses the tool facts from earlier sections where marked.

  1. Start with the requirement, in business words.

    ShopSphere's compliance officer says: "No real customer identity may leave production, in India or Germany. Card data never leaves the payment zone." The reason to write it in plain words is that everything later is traced back to this sentence.

    A one-page statement of scope: which systems, which data subjects, which laws.

  2. Find candidate sensitive columns.

    Run discovery (the discovery and subsetting concepts chapter, then the tool chapters). The tool proposes columns and domains from names, patterns and lists.

    A candidate list of columns with a proposed domain and a match score or conformance percent.

  3. Review with the data steward.

    Remove false alarms, add misses, resolve doubtful ones such as zip_code and tax_id. Informatica's flow lets you approve each suggested domain (User Guide 10.5.10, p.105). From docs

    An approved list, with a short reason for each yes and no.

  4. Classify.

    Give each approved column a level (section 4.6) and decide the action for each level: mask, null out, or exclude.

    A table like the lab answer below, signed off by the compliance officer.

  5. Choose a protection for each domain.

    Pick techniques that keep data usable for tests (see the masking concepts chapter). In Informatica, attach them as preferred rules and mark one default per domain; in Delphix, choose the default algorithm for each domain.

    Each domain has one default protection and a written reason.

  6. Bundle into a policy and store it.

    In Informatica you add the domains to a named policy and assign the policy to a project's data source (p.71). You can export policies, domains and rules to XML files and import them into another TDM repository, so a tested policy can travel from a test setup to the real one (p.80).     Run on a small sample, look at the results, and have a second person check. The masking concepts chapter lists what to check.

    A short report: columns covered, rule used, sample before and after.

  8. Repeat on change.

    New columns appear whenever the application changes. Delphix notes that a profiling job only covers tables and files already in the rule set, and that newly reachable objects must be added by hand (Delphix "Discovering your sensitive data"). From docs Re-run discovery on every release.

4.12 Judgement calls: four short cases

Policies cover the common situations. The interesting work is in the edges. Each case below is fictional and shows the questions a TDM engineer asks before saying yes or no. General concept

Case 1: "Give me last week's production orders to reproduce a bug"

A QA lead wants a copy of production. The reflex answer is no. The useful answer starts with questions. Which orders trigger the bug? Probably a handful, so a subset around those customers is enough (see the discovery and subsetting concepts chapter). Does the bug depend on real names or only on the shape of the data, such as an order with 40 items? Usually only on the shape, so a masked subset reproduces it. The minimum-necessary idea turns a risky request into a small, safe one.

Case 2: "Our load-testing vendor needs production data"

The vendor needs volume (millions of orders), not real people. Masking millions of rows works, but so does generating fictional rows from scratch, which carries no personal data at all (the test data classification and generation chapter covers this). The data steward helps by describing the realistic shape: how many items per order, how skewed the customers are.

Case 3: "Analytics wants real birth dates for age-band reports"

Exact birth date is Restricted, but the report only needs age bands such as 25 to 34. Options: replace dates with ones shifted by a few days (age band stays the same for most people), or store only the year. The compliance officer decides whether the remaining year plus zip is acceptable, remembering the uniqueness lab earlier in this chapter. The takeaway is that "mask or not" is often really "how much detail does the purpose need?".

Case 4: "Support agents paste customer details into notes"

An ORDER_NOTES column (not in the shared schema, added here to illustrate) contains lines like "Customer 123-45-6789 asked for a refund, call 9876543210". No column name flags it, and a column-level data pattern may miss it because the value is a whole sentence. Options: exclude the column from test copies, null it out, or use a free-text redaction algorithm that looks for patterns inside the text. Delphix provides a Free Text Redaction framework for this and says it needs expertise to configure (Delphix "Free Text Redaction (Algorithm frameworks)"). From docs Always check the output with a search for digit patterns afterwards.

Common mistakes and gotchas

Mistakes beginners make
  • "We removed the names, so it is anonymous." Birth date plus zip plus gender can identify people (section 4.4).
  • Trusting automatic discovery. It gives candidates. Review them, and add what it misses.
  • Forgetting free-text columns. Notes, comments and descriptions can hold names and ID numbers that no column name reveals.
  • Ticking "sensitive" and stopping. In Informatica the flag is only a label. A masking rule must still be assigned (p.89).
  • Assuming a law's definition fits every country. Ask your compliance officer which regimes apply to your data subjects.
  • Mixing up Delphix "rule set" with Informatica "rule".
  • Treating PCI as a law. It is an industry standard, enforced through payment contracts.
  • Copying documentation sample values into tests. Samples like card numbers can be real by accident.

Recap

Remember
  • Sensitive data is whatever could harm a person or the company if leaked. PII identifies people, PHI ties health facts to a person, PCI covers payment card data.
  • Direct identifiers point to one person. Indirect identifiers (zip, birth date, gender) identify when combined, so deleting names is not enough.
  • GDPR and HIPAA, in plain words, say: have a lawful purpose, use the minimum necessary, secure it, and de-identify where you can. This is the legal case for subsetting and masking. This guide is not legal advice.
  • Classification gives each column a sensitivity level, and each level maps to an action.
  • Tools find sensitive columns by column names, data patterns and value lists, plus type checks. The output is candidates for human review.
  • An Informatica policy contains data domains. A domain holds patterns, a sensitivity level and preferred rules. A rule is a technique plus parameters. Delphix uses domains, classifiers, profile sets and algorithm instances for the same ideas.
  • People decide: the compliance officer sets what is sensitive, the data steward explains the data, the TDM engineer builds and runs the policy.

Check yourself

1. ShopSphere deletes names, emails, phones and SSNs from an extract but keeps date of birth, zip code and gender. Is the extract safely anonymous?

Not necessarily. Birth date, zip and gender are indirect identifiers. Combined with an outside list that holds the same facts plus a name, they can single out individuals. Anonymity has to be judged on combinations, not only on direct identifiers.

2. What is the difference between a data pattern and a metadata pattern in an Informatica data domain?

A data pattern is a regular expression that matches the values in a column (for example [0-9]{3}-[0-9]{2}-[0-9]{4} for an SSN). A metadata pattern matches column names (for example .*SSN*). A column belongs to the domain if it matches any expression.

3. A colleague says "I marked the SSN column Sensitive in TDM, so it will be masked." What is wrong?

In Informatica the Sensitive flag is reference only and does not affect processing. Masking needs a rule assigned to the column (directly or through a data domain) and a plan that runs it.

4. Which legal idea justifies subsetting, and which justifies masking?

Minimum necessary or data minimisation justifies subsetting: copy only the data the test needs. De-identification or anonymisation justifies masking: make the copy no longer identify anyone.

5. In Delphix, what is a rule set?

A group of tables or flat files in a data source on which profiling, masking or tokenization jobs run. It is not a masking rule. Delphix's masking logic lives in algorithm instances attached to domains.
