26.11 Labs on ShopSphere (Day 55 and Day 56)

Both labs mask a test copy of ShopSphere, never SHOPSPHERE_PROD. They assume the environment, connector and rule set from the connectors chapter and the rule sets chapter, and an inventory from the profiling chapter. The SQL is generic; adjust it for your database (Oracle, PostgreSQL and SQL Server differ in small ways, noted where it matters). The Delphix hands-on chapter repeats these labs in a wider flow: the Delphix hands-on labs chapter.

Take a "before" snapshot first

An in-place job overwrites the data, so create a copy of the original rows to compare against. In PostgreSQL or Oracle: CREATE TABLE customers_before AS SELECT * FROM customers; (SQL Server: SELECT * INTO customers_before FROM customers;). This snapshot table is my lab convention, not a Delphix feature. Drop it when you finish: it holds the real-looking data.

Lab A (Day 55, TDM_Handson7): mask FirstName

Goal: mask CUSTOMERS.first_name with dlpx-core:FirstName, run an in-place job and prove the result with SQL.

  1. Take the snapshot (above) and note the row counts of CUSTOMERS and ORDERS.

    You need the "before" numbers to judge "after".

  2. Open the rule set inventory and make sure only first_name carries an assignment: domain FIRST_NAME, algorithm dlpx-core:FirstName.

    One column keeps the lab clear. Use the Clear Masking Assignment icon on other columns, as described in the profiling chapter.

    The inventory shows one assigned column in CUSTOMERS.

  3. Create the job: + Masking Job, name ShopSphere_Mask_FirstName, Masking Method In-Place, your rule set.

    In-place is right here because the target is already a disposable copy.

  4. Database Options: leave Commit Size at the default, Update Threads 1, Batch Update ticked. Configuration: 1 stream, Min and Max Memory 1024.

    Tiny tables need no tuning; one update thread avoids deadlock risk.

  5. Save, run the job from its "..." menu and watch Monitor > Job Executions.

    Status Queued or Running, then Succeeded. Open the job: Tables Masked 1, Rows Masked equals your CUSTOMERS row count, Tables with Nonconforming Data 0.

  6. Verify with SQL.

    Run the queries below and compare to the expected results.

-- 1. row count unchanged
SELECT (SELECT COUNT(*) FROM customers_before) AS before_rows,
       (SELECT COUNT(*) FROM customers)        AS after_rows;

-- 2. side by side
SELECT b.customer_id, b.first_name AS before_name, a.first_name AS after_name
FROM customers_before b JOIN customers a ON a.customer_id = b.customer_id
ORDER BY b.customer_id;

-- 3. how many names were left unchanged
SELECT COUNT(*) FROM customers_before b JOIN customers a
  ON a.customer_id = b.customer_id WHERE a.first_name = b.first_name;

-- 4. distinct counts before and after
SELECT (SELECT COUNT(DISTINCT first_name) FROM customers_before) AS d_before,
       (SELECT COUNT(DISTINCT first_name) FROM customers)        AS d_after;

-- 5. determinism: any original name mapped to more than one output?
SELECT b.first_name, COUNT(DISTINCT a.first_name) AS outputs
FROM customers_before b JOIN customers a ON a.customer_id = b.customer_id
GROUP BY b.first_name HAVING COUNT(DISTINCT a.first_name) > 1;

-- 6. other columns untouched, joins intact
SELECT COUNT(*) FROM customers_before b JOIN customers a
  ON a.customer_id = b.customer_id WHERE a.last_name <> b.last_name;
SELECT COUNT(*) FROM orders o JOIN customers c ON c.customer_id = o.customer_id;
Show a worked answer

Expected results.

  • Query 1: both counts equal. Query 2: every row shows a new name; compare with the illustrative table in the first name section.
  • Query 3: a small number. The documentation says dlpx-core:FirstName can mask a name to itself, so do not demand zero. With three rows, zero or one is normal.
  • Query 4: d_after is at most d_before, because Name algorithms are not unique.
  • Query 5: no rows. The same input must give the same output (deterministic). Rows here would mean the algorithm was re-keyed during the run or case settings differ.
  • Query 6: zero mismatches, and the orders-to-customers join count equals the total number of orders, because customer_id was not touched.

If it fails: status Warning means open the Error Report (see the non-conformant data part above); status Failed means read the Execution Log. An unchanged column means the algorithm was never saved in the inventory.

Lab B (Day 56, TDM_Handson8): mask alphanumeric text, SSN and telephone number

Goal: mask tax_id (alphanumeric), ssn and phone with format-preserving algorithms and prove uniqueness, format and consistency. Start from a fresh test copy (restore the original rows and take a new customers_before snapshot).

  1. Create the SSN algorithm: Settings > Algorithms > + Algorithm, name SHOPSPHERE_SSN, framework Segment Mapping.

    Built-in instances exist, but building one shows how Segment Mapping works and guarantees uniqueness.

  2. Add three segments: length 3 Mask numeric, length 2 Mask numeric, length 4 Mask numeric. Set Ignore Characters to specific characters and enter -. Leave Short Numeric Segment Handling on "Report nonconforming data". Save.

    The dashes are removed before masking and restored after, so "123-45-6789" keeps its shape.

    The algorithm shows in the grid with owner admin and framework Segment Mapping.

  3. In the rule set inventory, edit each column: untick Enable Automatic Updates, then set tax_id to domain TAX_ID with dlpx-core:CM Alpha-Numeric, ssn to domain SSN with SHOPSPHERE_SSN, and phone to domain TELEPHONE_NO with dlpx-core:Phone Unique. Save each.

    Overriding the domain default needs automatic updates off, otherwise a later profiling run may undo your choice.

  4. Create and run job ShopSphere_Mask_Sensitive (In-Place, Update Threads 1, Batch Update on, 1 stream, memory 1024) as in Lab A.

    Succeeded, with no tables or columns reported under nonconforming data. A Warning here usually means a value did not fit: open the Error Report.

  5. Verify with SQL.
-- Format: SSN keeps dashes (expect 0 rows violating)
SELECT COUNT(*) FROM customers WHERE ssn NOT LIKE '___-__-____';

-- Uniqueness: rows minus distinct values (expect 0 for tax_id and ssn)
SELECT COUNT(*) - COUNT(DISTINCT tax_id) AS tax_dupes,
       COUNT(*) - COUNT(DISTINCT ssn)    AS ssn_dupes
FROM customers;

-- Changed? (SSN and tax_id: expect 0 or very close to 0)
SELECT COUNT(*) FROM customers_before b JOIN customers a
  ON a.customer_id = b.customer_id
WHERE a.ssn = b.ssn OR a.tax_id = b.tax_id;

-- Tax id shape, Oracle syntax (PostgreSQL: tax_id !~ '^[A-Z]{5}[0-9]{4}[A-Z]$')
SELECT COUNT(*) FROM customers
WHERE NOT REGEXP_LIKE(tax_id, '^[A-Z]{5}[0-9]{4}[A-Z]$');

-- Phone: ten digits, first three unchanged (expect 0 and 0)
SELECT COUNT(*) FROM customers WHERE LENGTH(phone) <> 10;
SELECT COUNT(*) FROM customers_before b JOIN customers a
  ON a.customer_id = b.customer_id
WHERE SUBSTR(a.phone,1,3) <> SUBSTR(b.phone,1,3);

-- Phone distinct counts, then side by side
SELECT (SELECT COUNT(DISTINCT phone) FROM customers_before) AS d_before,
       (SELECT COUNT(DISTINCT phone) FROM customers)        AS d_after;
SELECT b.customer_id, b.ssn, a.ssn, b.tax_id, a.tax_id, b.phone, a.phone
FROM customers_before b JOIN customers a ON a.customer_id = b.customer_id;

-- Joins still work (orders to customers)
SELECT COUNT(*) FROM orders o JOIN customers c ON c.customer_id = o.customer_id;
Show a worked answer

Why each expectation is justified.

  • tax_id: Character Mapping keeps letters as letters and digits as digits, and gives no two inputs the same output, so the shape and uniqueness checks should pass. The docs promise a masked value never equals the input if at least one character is masked.
  • ssn: Segment Mapping produces "no overlaps or repetitions", so duplicates should be 0. The page does not say a value can never map to itself, which is why that check is "0 or very close". If your application validates SSN rules (no 000 or 666 area, for instance), inspect the output; these frameworks do not promise valid issuing patterns.
  • phone: Phone Unique masks only the last seven digits and keeps all other characters, so the first three digits must be unchanged. The documentation excerpt I had does not guarantee distinct inputs always give distinct outputs, so a lower d_after than d_before is a finding to report, not necessarily a failure.
  • Joins: none of these columns is a key, so the join count equals the number of orders.

Consistency across tables. If an SSN or tax id also appears in another table or file, that column must use the same algorithm, or the same person gets two different masked values and tests break.

Extra challenge. Repeat the SSN step with dlpx-core:CM Digits instead of the custom algorithm and compare the output. Which one gave better-looking SSNs?
