26.9 Creating, choosing and managing algorithms

Create your own instance

  1. Settings > Algorithms > + Algorithm.

    Your instances are called user-defined algorithms; once saved they are available to all users.

  2. Enter a unique Algorithm Name, a Description and choose the Framework, then Next.

    Name and framework are locked after creation, so choose carefully. The wizard shows the framework's Mask Type (for Date Shift it showed LOCAL_DATE_TIME).

  3. Fill in the framework's configuration, then Next.

    The panel on the right explains each field. The frameworks in the catalogue each have their own options.

  4. Check the Summary and Save.

    The algorithm appears in the grid. Creating and editing are asynchronous tasks; a "Run in background" option may appear if it takes time.

To use a new algorithm in a profiling job you must first attach it to a domain as that domain's default (see the profiling chapter). If you build the inventory by hand, no domain is needed From docs.

Choosing between Character Mapping and Segment Mapping

The docs say Character Mapping is intended to replace Segment Mapping in many cases, but not all From docs.

Prefer Character Mapping when

  • Data is dirty or inconsistently formatted: it keeps non-masked characters automatically
  • You need Unicode (first plane) rather than just a-z and 0-9
  • Inputs differ in length and you want to preserve the last characters (reverse preserve ranges)
  • You want every position to influence every other

Prefer Segment Mapping when

  • Parts of the value must be masked differently by position
  • You need to map input ranges to different output ranges (A-D to W-Z)
  • You need numeric segments limited to a value range (up to 6 digits)

Multi-column algorithms

A multi-column algorithm (for example Dependent Date Shift or Multi Column Address) is assigned once but spans several columns, each filling a logical field. It is meant for coordinated masking, such as two dates that must keep their interval. Each non-optional logical field must be assigned for every Algorithm Group number, and incomplete assignments may only be noticed when the job runs. They only work where whole rows are processed together, and cannot be called by other algorithms through chaining From docs.

Usage and syncability (engine administration)

  • Usage. GET algorithm/{algorithmName}/usage lists every column, file field, domain and other algorithm that uses it. PUT on the same path with replacementAlgorithmName swaps it everywhere, with optional environment and rule set filters. The docs warn that this can change many inventories and is hard to undo, so first GET usage for both algorithms and export global settings and affected environments From docs.
  • Syncability. Algorithms are fully syncable between engines (GET /syncable-objects?object_type=USER_ALGORITHM). Non-deterministic ones (all Secure Lookup Random algorithms, DateShiftVariable, Gender SL, SexualOrientation SL, SecureShuffle) cannot give the same output twice, so they cannot be used for syncable masking. DateShiftFixed and RepeatFirstDigit are listed as fixed. Syncing an out-of-the-box instance updates its key but does not replace its files From docs.

Why this matters to a TDM engineer: if two engines mask the same source, identical output on both needs the same keys, which is what syncing delivers. The consistency argument is my reasoning, not a quote.
