26.10 Masking jobs: in-place or on-the-fly

A masking job lives in an environment next to the profiling jobs of the profiling chapter. A masking environment supports Profiling and Masking jobs; a tokenize environment supports Profiling, Tokenization and Re-Identification jobs, created with the same flow From docs. Start with the one choice that shapes everything else, the masking method.

In-Place

Updates the source environment with masked values. Typical use: you already copied production into a test database (for example a virtual database) and mask that copy where it sits. Risk: if the job fails midway, that database may be partly masked.

On-The-Fly

Reads unmasked data from a source environment and connector, and writes masked data to the target. Typical use: production stays untouched and the masked copy goes elsewhere. Supported pairs: same connector type (Oracle to Oracle, delimited file to delimited file) and database source to delimited-file target.

For a database-to-file job, tick Database to File Job so that the source connector list shows database connectors. Target files need not exist in advance if the file name pattern matches the source, but in a database-to-delimited-file job the target files must be created first, with names matching the source tables. You need the View Connector role to create or run on-the-fly jobs From docs.

Create a masking job, step by step

  1. In the environment's Jobs tab click + Masking Job.

    The Create Masking Job wizard opens: Details, then Database Options (database rule sets only), Configuration, Summary.

  2. Details: unique Job Name, Masking Method, Rule Set.

    The name must be unique across the entire application. For On-The-Fly you also choose Source Environment and Source Connector.

  3. Details: decide the optional boxes.

    Multi-Tenant reuses a rule set for identical schemas through different connectors, chosen at run time. Selective Data Distribution must be on if the job will be used in masked VDB provisioning. Stop job on first occurrence aborts on the first non-conformant value, but only where the algorithm or global setting says non-conformant data is a failure.

  4. Database Options: commit size, update threads and friends.

    See the table below. This step only appears for database rule sets.

  5. Configuration: streams, row limit, feedback size, memory, comments, email.

    These control speed and memory, not what is masked.

  6. Summary, then Save.

    The job appears in the Jobs list with status CREATED until you run it.

FieldWhat it does (from the docs)
Commit SizeRows processed before a commit. The related application setting DatabaseCommitSize has default 10000; the docs excerpt does not spell out how it interacts with an empty field.
Update ThreadsParallel threads writing to the target database; default from DefaultUpdateThreads (1). Do not use several threads if any table lacks an index, and reduce them if a deadlock appears, especially on T-SQL databases.
Batch UpdateLoads masked rows in batches of Commit Size. Recommended because it usually speeds the job.
TruncateOn-The-Fly only: empty the target tables before loading.
Drop Indexes / Disable Triggers / Disable ConstraintsSwitch off and automatically restore indexes, triggers or constraints so that keys and foreign keys can be updated. Not supported for every database. With driver-support plugins they appear under Enable Tasks.
Pre SQL / Post SQL ScriptA file of plain SQL statements separated by semicolons (maximum 10 MB) run before or after the job. No PL/SQL or T-SQL extensions, no dynamic SQL, and schema-changing SQL cannot run as a pre-script. The engine always opens a connection, even if no script is loaded.
Number of StreamsHow many tables are masked in parallel; default from DefaultStreams (1). Even one stream has separate input, masking and output threads. Expect some streams to finish before others.
Row LimitRows in flight per stream (lines, records or XML elements for files). 0 means unlimited; -1 or blank picks a default by rule set type. Defaults assume rows of about 2000 bytes with 100 masked columns; for bigger rows, add memory or lower the limit.
Feedback SizeRows between log messages.
Min / Max Memory (MB)Memory for the job; the docs recommend at least 1024.

Edit, view, delete. Use the ... menu on the job row; the name cannot be edited, and delete asks for confirmation. A job cannot be edited or deleted while running. The row menu also offers a Checklist for database jobs that runs an Identity Column Check: the rule set's tables must have a primary key, an indexed identity column or a logical key. The check looks only at the rule set, so it still passes if a primary key constraint is disabled by the job From docs.

Run, stop and monitor

Run. Click ... then Run. The engine checks the memory allowed for all running jobs (by default 75% of system memory minus 6 GB reserved for the web application, overridable with MaximumMemoryForJobs) and the number of simultaneous jobs (NumSimulJobsAllowed, default 7). If either limit would be exceeded the job queues From docs.

Stop. Cancel a running masking job and the data can be left semi-masked; indexes, constraints or triggers that were dropped are not recreated. Cancelling a queued job has no effect on your data From docs. Plan to restore from a copy rather than trust a half-masked database.

Monitor. Open Monitor > Job Executions or click the job name. The execution page shows a summary (tables masked, rows masked and remaining, tables and columns with non-conformant data, streams), the sequence of events (Initializing, Collecting Configurations, Preparing, Running Pre-execution Custom Driver Tasks, Starting, Creating Identity Column, Running PreSQL and PostSQL Scripts, Dropping Created Identity Column, Collecting Information, Job Completed) and a grid of Execution Components, one row per table or file.

Report and Logs offers the Execution Log plus PDF reports: the Job Report and the Inventory Report (the profiling job showed only Job Report).

Non-conformant data: when a value does not fit the algorithm

If a value does not match what an algorithm expects (letters going into a numeric-only algorithm, an 11-digit string into a 10-digit segment pattern), the job, depending on settings, fails, skips the value, or nulls it. The global default is the application setting DefaultNonConformantDataHandling; an algorithm's own setting overrides it, and a job can override both with Job-level Non-Conforming Data Handling: Use global setting, Fail on encounter (FAIL), Don't mask value (DONT_MASK) or Set value to null (NULLIFY). The job-level override applies only to Hop-based jobs. By default non-conformant data is not masked and the job ends with a warning From docs.

Unmasked data in a test database is a leak, so never ignore a yellow warning. Open the execution component's logs. The Error Report lists the event type (UNMASKED_DATA, or JOB_ABORTED if the job stopped), the cause (PATTERN_MATCH_FAILURE), the row count and the column, plus a sample of the pattern of the bad value, never the value itself. Each character is shown as a class: N digit, L letter, M mark, P punctuation, S symbol, Z separator, O other, U unknown.

To find the offending rows, translate the pattern into a database query. For the pattern LLLLL on an Oracle column, the docs use SELECT EXCEPTION_00 FROM testdata_EXCEPTION WHERE regexp_like(EXCEPTION_00, '[[:alpha:]]{5}');. For a multi-column algorithm the pattern is shown for every masked column of that algorithm, so you must read the message to find the real culprit.

Speed: PerfLogger and best practices

From version 2026.3 the throughput log is called PerfLogger. It logs at job start (every 10,000 rows), then every 30 seconds after 100,000 rows, and once at the end with totals. The main number is RPM, rows per minute; MB/sec is only informational, and BPR is the average bytes per row. Rows of about 1 KB or more lower RPM. A sharp RPM drop to zero with an unchanged BPR points at the target side (transaction log pressure, auto-growth, many indexes). If RPM falls below earlier runs, check for concurrent jobs, new indexes, constraints or triggers, and bigger rows From docs.

The best practices page recommends, for a dedicated compliance engine, 8 vCPUs and 64 GB RAM minimum (128 GB or more preferred), about one vCPU per concurrent job, at least 1 GB of memory per job and per stream (more for rows with 1,000 or more columns or big lookup files such as 500,000 values), the engine near the database server on a slow network, and tuning the masked VDB first (for Oracle, no-archivelog mode; for SQL Server, SIMPLE recovery) From docs. Mapping algorithms are the other big memory user: all mappings load into memory, so a 2 GB mapping needs much more job memory than a 2 MB one.
