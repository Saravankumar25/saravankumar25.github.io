Profiling tells you which columns are sensitive. Masking is the step that actually changes them. In Delphix the work is split in two: an algorithm decides how one value becomes another, and a masking job applies the assigned algorithms to every row of a rule set. This chapter covers both halves. First the idea of algorithms (frameworks, instances, keys, lookup files, uniqueness), then a catalogue of every algorithm framework the documentation lists, then a close look at the algorithms for first name, SSN, alphanumeric text and telephone number. The second half explains how to build, run, monitor and tune a masking job.

It ends with two labs on the ShopSphere tables: masking FirstName, and masking alphanumeric text, SSN and telephone number. Rule sets and inventories are covered in the rule sets and keys chapter and the profiling chapter. For the generic ideas behind masking see the masking concepts chapter, and for the Informatica equivalent see the Informatica data masking chapter. Masking files is the topic of the file masking chapter, and the full lab set is in the Delphix hands-on labs chapter.

26.1 Words to know first

Algorithm (instance)
A named, ready-to-use masking recipe with its configuration, such as dlpx-core:FirstName. You assign instances to columns.
Algorithm framework
A kind of algorithm that you can configure to create new instances, such as Secure Lookup or Segment Mapping. "FIRST NAME SL" is an instance of the Secure Lookup framework.
Out-of-the-box instance
An instance that ships with the engine. These cannot be edited or deleted; you create your own from a framework instead.
Algorithm key
A secret value inside most algorithms. Changing it changes the output, so the same input masks to something different.
Deterministic
Same input, same algorithm, same key, same configuration gives the same output every time. This keeps joins working across tables and across runs.
Lookup file
A plain text file with one replacement value per line (no header). The algorithm picks a line based on the input, so the output is always something from your file.
Collision
Two different inputs masked to the same output. Fine for names, harmful in a unique column.
Non-conformant data
A value that does not fit the format an algorithm expects, such as letters in a numeric-only algorithm. By default it is left unmasked and a warning is recorded.
Masking job
A saved set of options saying "apply the inventory of this rule set", with a method (in-place or on-the-fly), threads, memory and scripts.
In-place / on-the-fly
In-place changes the data where it sits. On-the-fly reads from a source and writes masked data to a different target.
Stream
One parallel lane of work. More streams let the engine mask several tables at once.

Where do the algorithms live? Open Settings > Algorithms. The grid shows Algorithm Name, Framework Name, Mask Type and Owner; sortable by name, framework and mask type, filterable by name, framework, mask type and owner From docs. The "+ Algorithm" button creates new instances.

The Owner column tells you which instances are yours: System rows ship with the engine. The docs say system-defined instances and those from algorithm plugins can only be viewed, never edited or deleted. Administrators and users with the EDIT Algorithm permission can edit any user-defined one, but the name and framework cannot change after creation From docs.

26.3 What an algorithm is, in five ideas

Idea 1: framework versus instance

Think of a framework as a recipe template ("replace each value with one chosen from a list") and an instance as a filled-in recipe ("...using this list of first names, ignoring case"). The documentation's own example: "FIRST NAME SL" is an instance of the Secure Lookup framework From docs. The analogy stops being accurate in one place: a framework is not something you assign to a column. Only instances are assigned.

Idea 2: the key makes output repeatable but secret

Most algorithms include a key. If FirstNameLookup masks "Michelle" to "Rachael", changing the key might make it "Ben" instead From docs. The key can be randomised through an API call (PUT /algorithms/{algorithmName}/randomize-key). Two consequences:

  • Within one key, repeatable output means the same customer name masks the same way in every table and every run, so test data stays internally consistent.
  • Whoever knows the key and the algorithm might be able to rebuild mappings, so treat the key like a password and do not casually re-key production algorithms, because every later run would produce different test data.

Idea 3: unique versus non-unique

Some algorithms may give two inputs the same output (collisions). Others guarantee that different inputs give different outputs. The docs are consistent about which is which:

PropertyFrameworksUse it for
Collisions possible (non-unique)Secure Lookup, Name, Full Name, Date Shift Discrete or Variable, Free Text Redaction, Min MaxNames, cities, comments: values that repeat naturally in real data
No collisions (unique)Character Mapping, Segment Mapping, Mapping, TokenizationKeys and identifiers: primary keys, foreign keys, SSN, account numbers

Caveat from the docs: even Character Mapping can collide for numeric data types, because "001" and "1" are the same number once stored in a numeric column From docs.

Idea 4: a lookup file is just a list

Lookup-based algorithms (Secure Lookup, Name and their out-of-the-box instances such as FirstNameLookup, LastNameLookup and FullNMLookup) hold a list of fake values. The engine hashes the input, uses the hash to choose a line, and returns that line. The file has one value per line, no header, in ASCII or UTF-8 From docs. For example, a tiny file for cities could be:

Smallville
Clarkville
Farmville
Townville

With a hash method of SHA256 (the default) the same input always chooses the same line. The framework also offers LEGACY (to mimic old behaviour) and RANDOMIZE, which picks a random line each time and therefore does not keep referential integrity. RANDOMIZE suits things like gender, where you want a statistical spread rather than consistency From docs.

Idea 5: masking versus tokenization

Almost all masking is one-way. Tokenization is the one family that can be reversed, which is why it exists: mask data, send it to an outside vendor, and later re-identify the vendor's findings From docs. It is covered in the framework catalogue below.

Generic technique names and their Delphix counterparts

The generic technique names map onto Delphix frameworks as follows:

  • Substitution: Secure Lookup, Name, Mapping (replace a value with another real-looking value).
  • Shuffle: SecureShuffle (moves existing values between rows).
  • Key masking: Character Mapping and Segment Mapping (keyed permutation that keeps uniqueness).
  • Encryption: Tokenization (AES-128 in the framework description, reversible).
