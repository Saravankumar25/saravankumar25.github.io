8.7 Transform: cleaning and reshaping

Concept. Transformation turns staged raw data into the clean, consistent, correctly typed shape the target needs.

Why it matters. This is where business rules live. If the transform is wrong, the data is wrong everywhere downstream, and nobody can tell from the target alone. Transformations are therefore the part of ETL most worth documenting and testing.

There are nine everyday kinds of transformation: cleaning, type conversion, mapping, deduplication, lookups, filtering, joining, derived columns and aggregation. We cover each in turn using the ShopSphere staging rows from the previous section. Each subsection shows the idea, the SQL, and the before and after.

8.7.1 Cleaning

Idea. Make values consistent so that equal things look equal. "MENON", "Menon" and "menon " are the same surname to a person, but three different strings to a database.

SELECT
  UPPER(SUBSTR(TRIM(first_name),1,1)) || LOWER(SUBSTR(TRIM(first_name),2)) AS first_name,
  UPPER(SUBSTR(TRIM(last_name),1,1))  || LOWER(SUBSTR(TRIM(last_name),2))  AS last_name,
  COALESCE(LOWER(TRIM(email)), 'not provided')                              AS email
FROM stg_customers;

Notes on dialects: TRIM, UPPER, LOWER and COALESCE exist in all the major databases. SUBSTR is SUBSTRING in SQL Server, and many databases have an INITCAP function that capitalises each word for you. Replacing a missing email with the text "not provided" is a business choice: some teams prefer to keep NULL. Decide once and write it down.

8.7.2 Type conversion

Idea. Staging holds everything as text. The target needs real dates and numbers so that sorting, comparing and adding work properly. As text, "9" sorts after "10", and "20/10/2026" sorts before "21/09/2026" only by accident.

SELECT
  CAST(order_id AS INTEGER) AS order_id,
  SUBSTR(order_date,7,4) || '-' || SUBSTR(order_date,4,2) || '-' || SUBSTR(order_date,1,2) AS order_date,
  CAST(total_amount AS REAL) AS total_amount
FROM stg_orders
WHERE total_amount NOT GLOB '*[^0-9.]*';   -- only rows whose amount is numeric

In Oracle or PostgreSQL you would write TO_DATE(order_date, 'DD/MM/YYYY') instead of slicing the string. SQL Server uses CONVERT or TRY_CONVERT. I sliced the string because SQLite has no date-parsing function with a format string, and the approach also works anywhere. The GLOB pattern is SQLite's way of testing "contains a character that is not a digit or a dot"; other databases use LIKE tricks, REGEXP or TRY_CAST.

Dates written day-first and month-first

"03/04/2026" is 3 April in India and Europe but 4 March in the USA. Always confirm the source's format with its owner, and then reject dates that do not parse instead of guessing. A job that silently swaps day and month corrupts every row it touches.

8.7.3 Mapping and standardising

The word mapping has two meanings in ETL, and both matter. In the broad sense a mapping is the whole definition of how source columns become target columns (we meet this in 8.11). In the narrow sense, value mapping means translating codes: the order system stores S, P and C, and reports want the words.

CREATE TABLE status_map (status_code TEXT PRIMARY KEY, status_name TEXT);
INSERT INTO status_map VALUES ('S','Shipped'),('P','Pending'),('C','Cancelled');

SELECT o.order_id, COALESCE(m.status_name, 'Unknown') AS order_status
FROM   stg_orders o
LEFT JOIN status_map m ON m.status_code = o.status_code;

The unmatched code Z becomes "Unknown" because of the LEFT JOIN plus COALESCE. An inner join here would silently drop order 5007 altogether, which is one of the most common ETL bugs: a lookup that loses rows when it fails to match.

8.7.4 Deduplication

Idea. Keep one row for each real-world thing. Customer 1002 arrived twice in the staging data.

SELECT customer_id, first_name, last_name, email, zip_code
FROM (
  SELECT s.*,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY customer_id) AS rn
  FROM stg_customers s
) t
WHERE rn = 1;

ROW_NUMBER() numbers the rows inside each customer id (1, 2, ...); keeping only number 1 removes the extras. The ORDER BY inside the window decides which duplicate survives. Here the two copies were identical so it did not matter. In real data the copies often differ, and you must choose a rule such as "keep the latest by modified date" or "keep the one with the most filled-in columns".

Exact versus fuzzy duplicates

Matching on a key (the same customer_id) is easy. Matching "Asha Menon, 12 Park Road" with "A. Menon, 12 Park Rd" is fuzzy matching, and tools use scoring rules for it. Start with exact keys; add fuzzy matching only when a real business need appears.

8.7.5 Lookups

Idea. A lookup enriches a row by finding a related value in a reference table. Order items carry only product_code. A lookup in PRODUCTS adds the product name.

SELECT i.item_id, i.product_code,
       COALESCE(p.product_name, 'UNKNOWN PRODUCT') AS product_name
FROM   stg_order_items i
LEFT JOIN products p ON p.product_code = i.product_code;

8.7.6 Filtering, validating and rejecting

Idea. Some rows should not reach the target. Filtering removes rows that are valid but unwanted (for example, test orders). Validating checks rows against rules and rejects those that fail, keeping them aside with a reason so someone can fix them.

CREATE TABLE reject_orders (batch_id INTEGER, order_id TEXT, reason TEXT);

INSERT INTO reject_orders
SELECT 1, o.order_id,
       CASE WHEN o.total_amount = '' OR o.total_amount GLOB '*[^0-9.]*'
            THEN 'total_amount is not a number'
            ELSE 'customer ' || o.customer_id || ' not found' END
FROM   stg_orders o
WHERE  o.total_amount = '' OR o.total_amount GLOB '*[^0-9.]*'
   OR  NOT EXISTS (SELECT 1 FROM dim_customer d
                   WHERE d.customer_id = CAST(o.customer_id AS INTEGER));

The valid orders carry on. This is the key design choice: one bad row must not stop the whole run, and must not vanish. It goes to a reject table with a batch id and a human-readable reason.

8.7.7 Joining

Idea. Combine rows from different inputs that describe the same thing. To build the sales fact table we join order items to their orders (to get date, customer and status). Each order item is a row; the order is its parent.

SELECT i.item_id, o.order_id, o.order_date, o.customer_id, i.product_code, i.quantity, i.unit_price
FROM   stg_order_items i
JOIN   stg_orders o ON o.order_id = i.order_id;

Here an inner join is right, because an item with no order is meaningless (and any such item should already have been caught by a check). The important skill is to ask of every join: "what should happen to a row with no match?" The inner join drops it, a left join keeps it with empty columns. The answer is a business decision, not a technical one.

8.7.8 Derived columns

Idea. Calculate a value that does not exist in the source. The line amount of an order item is quantity times unit price.

SELECT item_id,
       CAST(quantity AS INTEGER) * CAST(unit_price AS REAL) AS line_amount
FROM   stg_order_items;

8.7.9 Aggregating

Idea. Summarise many rows into fewer, such as a daily sales table for dashboards.

SELECT order_date,
       COUNT(DISTINCT order_id) AS orders_count,
       SUM(quantity)            AS units,
       SUM(line_amount)         AS revenue
FROM   fact_order_line
GROUP BY order_date;

Check the arithmetic: on 20 October, order 5001 has 1 unit at 1499.00 and order 5002 has 2 units at 100.00 plus 1 unit at 50.50, so units = 1 + 2 + 1 = 4 and revenue = 1499 + 200 + 50.5 = 1749.5. Always do this kind of hand check on a few rows of any new aggregate.

Order of transformations matters

Clean before you compare, convert before you calculate, deduplicate before you join, and filter early to cut work. For example, if you deduplicate after joining items to orders, one duplicated order doubles its items and doubles the revenue.
