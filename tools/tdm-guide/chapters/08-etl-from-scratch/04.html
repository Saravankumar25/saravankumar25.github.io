8.8 Load: writing into the target

Concept. Loading writes the transformed rows into the target tables, in a way that is correct, repeatable and fast enough.

Why it matters. A load that half-finishes leaves the target in a state nobody understands: some rows from tonight, some from yesterday. Loads must either complete or leave things as they were, and they must be safe to run again.

8.8.1 Load strategies

StrategyWhat it doesGood forDanger
Truncate and load (full refresh)Empty the target table, then insert everythingSmall tables, reference data, test databasesTarget is empty or partial during the load; slow for big tables
Append (insert only)Add new rows, never touch old onesEvent or fact data that never changesRunning twice duplicates rows
IncrementalLoad only the rows extracted incrementallyLarge tablesDepends on a correct watermark
Upsert (merge)Update rows that exist, insert those that do notDimensions and master dataNeeds a reliable key to match on
History-keeping load (SCD)Close the old version of a row and insert a new oneDimensions where history mattersMore complex; the table grows

What the tools say about these ideas, all in their own terms:

  • Informatica's plan has update strategy options: treat source rows as Insert or Update, and an "Update as" choice of Update, Insert or Update else Insert, which updates a row if it exists in the target and inserts the rest (User Guide 10.5.10, p.284). That is the upsert strategy, named. From docs
  • Informatica lets you run SQL before and after writing to a target. Its example is TRUNCATE TABLE $OWNERNAME.$TABLENAME;, which deletes all rows from the target table first (pp.277 to 278). That is truncate and load. From docs
  • Delphix on-the-fly masking jobs have a Truncate option that sets whether target database tables are emptied before the masked data is loaded, and a Batch Update option for loading in batches sized by the commit size. From docs Create, view, edit, delete, verify jobs ↗
  • GenRocket's FAQ says that for very large volumes you do not want to connect through JDBC; you generate data in the database's native bulk load format using bulk load receivers. From docs GenRocket General FAQ ↗

8.8.2 Upsert in SQL

Suppose Asha Menon's zip code changes in the next feed. A plain insert would collide with the existing row. An upsert updates it:

-- SQLite and PostgreSQL syntax
INSERT INTO dim_customer_simple (customer_id, full_name, email, zip_code)
VALUES (1001, 'Asha Menon', 'asha.menon@example.com', '560002')
ON CONFLICT (customer_id)
DO UPDATE SET full_name = excluded.full_name,
              email     = excluded.email,
              zip_code  = excluded.zip_code;

-- Oracle and SQL Server use MERGE instead

8.8.3 Keeping history: a slowly changing dimension


An upsert overwrites. After it, the warehouse says Asha always lived in 560002, so a report on October 20 sales would attribute them to the wrong zip. If history matters, keep both versions with validity dates. This pattern is commonly called a Type 2 slowly changing dimension. General concept


The pattern needs two statements, which you will run in Lab 2: first close the current row of any customer whose data changed (set valid_to and is_current = 0), then insert a new current row for every customer who has none. The table gets a surrogate key (customer_key), an artificial id, because the business key customer_id now appears more than once.

8.9 Batch, streaming, and ETL versus ELT


8.9.1 Batch versus streaming at a glance


Batch collects data for a period (an hour, a night) and processes it as one group. It is easy to reason about and to re-run, and results are always "as of the last run". Most ETL, and nearly all test data provisioning, is batch. Streaming processes each event within seconds of arrival. Results are fresh, but you must handle duplicates and out-of-order events, so it is used where the answer must be current, such as fraud alerts. A middle path, micro-batching, runs a small batch every minute or so.


8.9.2 ETL versus ELT


In ETL, transformations run in the ETL engine, on its own servers, before data reaches the target. In ELT, raw data is loaded into the target first (often a powerful cloud warehouse) and transformed there using its SQL engine.




ETLELT



Where transforms runSeparate ETL engineInside the target database


StrengthSensitive data can be cleaned or masked before it lands in the targetUses the target's power; raw data can be re-transformed later


WeaknessThe engine can become a bottleneckRaw (maybe sensitive) data sits in the target




Look at the last row, because it matters for test data. If raw data holds real personal details, ELT would place them in the target before masking. That is why test data work usually follows the ETL order: mask first, then load. The ShopSphere example in this chapter is really a hybrid: staging is a lightweight "EL" step and the transformation is done by SQL. Many practical systems mix both styles. General concept

8.12 Reusable components and the mapplet


Concept. A reusable component is a piece of ETL logic you build once and use in many places, like a function in programming.


Why it matters. Without reuse, the same rule (clean a phone number, standardise a country name) is copied into twenty mappings. When the rule changes, someone must find and fix twenty copies, and will miss one.


In Informatica's world, the reusable group of transformations is called a mapplet. A mapplet has input and output ports (named connection points), contains one or more transformations, and can be placed into many mappings. Think of it as a small mapping with sockets at each end.
