8.8 Load: writing into the target

Concept. Loading writes the transformed rows into the target tables, in a way that is correct, repeatable and fast enough.

Why it matters. A load that half-finishes leaves the target in a state nobody understands: some rows from tonight, some from yesterday. Loads must either complete or leave things as they were, and they must be safe to run again.

8.8.1 Load strategies

StrategyWhat it doesGood forDanger
Truncate and load (full refresh)Empty the target table, then insert everythingSmall tables, reference data, test databasesTarget is empty or partial during the load; slow for big tables
Append (insert only)Add new rows, never touch old onesEvent or fact data that never changesRunning twice duplicates rows
IncrementalLoad only the rows extracted incrementallyLarge tablesDepends on a correct watermark
Upsert (merge)Update rows that exist, insert those that do notDimensions and master dataNeeds a reliable key to match on
Bulk loadUse the database's fast loading path, bypassing row-by-row insertsMillions of rowsMay skip triggers and constraint checks, so check afterwards

What the tools say about these ideas, all in their own terms:

  • Informatica's plan has update strategy options: treat source rows as Insert or Update, and an "Update as" choice of Update, Insert or Update else Insert, which updates a row if it exists in the target and inserts the rest (User Guide 10.5.10, p.284). That is the upsert strategy, named. From docs
  • Informatica lets you run SQL before and after writing to a target. Its example is TRUNCATE TABLE $OWNERNAME.$TABLENAME;, which deletes all rows from the target table first (pp.277 to 278). That is truncate and load. From docs
  • Delphix on-the-fly masking jobs have a Truncate option that sets whether target database tables are emptied before the masked data is loaded, and a Batch Update option for loading in batches sized by the commit size. From docs Create, view, edit, delete, verify jobs ↗
  • GenRocket's FAQ says that for very large volumes you do not want to connect through JDBC; you generate data in the database's native bulk load format using bulk load receivers. From docs GenRocket General FAQ ↗

8.8.2 Upsert in SQL

Suppose Asha Menon's zip code changes in the next feed. A plain insert would collide with the existing row. An upsert updates it:

-- SQLite and PostgreSQL syntax
INSERT INTO dim_customer_simple (customer_id, full_name, email, zip_code)
VALUES (1001, 'Asha Menon', 'asha.menon@example.com', '560002')
ON CONFLICT (customer_id)
DO UPDATE SET full_name = excluded.full_name,
              email     = excluded.email,
              zip_code  = excluded.zip_code;

-- Oracle and SQL Server use MERGE instead:
-- MERGE INTO dim_customer_simple t USING (...) s ON (t.customer_id = s.customer_id)
-- WHEN MATCHED THEN UPDATE SET ... WHEN NOT MATCHED THEN INSERT ...
Upsert effect on one row
customer_idfull_namezip_code
Before1001Asha Menon560001
After1001Asha Menon560002

Notice the property that makes upserts valuable: running the same load twice gives the same result. A property like this is called idempotence, and it is what lets you safely re-run a failed job.

8.8.3 Keeping history: a slowly changing dimension

An upsert overwrites. After it, the warehouse says Asha always lived in 560002, so a report on October 20 sales would attribute them to the wrong zip. If history matters, keep both versions with validity dates. This pattern is commonly called a Type 2 slowly changing dimension. General concept

CREATE TABLE dim_customer (
  customer_key INTEGER PRIMARY KEY AUTOINCREMENT,   -- surrogate key
  customer_id  INTEGER,                             -- business key
  full_name    TEXT, email TEXT, zip_code TEXT,
  valid_from   TEXT, valid_to TEXT, is_current INTEGER
);

-- Step 1: close the current row of any customer whose data changed
UPDATE dim_customer
SET    valid_to = '2026-10-24', is_current = 0
WHERE  is_current = 1
  AND  EXISTS (SELECT 1 FROM clean_customers n
               WHERE n.customer_id = dim_customer.customer_id
                 AND (n.full_name <> dim_customer.full_name
                   OR n.email     <> dim_customer.email
                   OR n.zip_code  <> dim_customer.zip_code));

-- Step 2: insert a current row for anyone who has none (new or just closed)
INSERT INTO dim_customer (customer_id, full_name, email, zip_code, valid_from, valid_to, is_current)
SELECT n.customer_id, n.full_name, n.email, n.zip_code, '2026-10-24', '9999-12-31', 1
FROM   clean_customers n
WHERE  NOT EXISTS (SELECT 1 FROM dim_customer d
                   WHERE d.customer_id = n.customer_id AND d.is_current = 1);

Here clean_customers is the cleaned and de-duplicated customer query from 8.7. The table gets a surrogate key (customer_key), an artificial id, because the business key customer_id now appears more than once.

A fact row loaded on 20 October can now be joined to the version of the customer that was valid that day (order_date between valid_from and valid_to). The far-future date 9999-12-31 is a common convention for "still current".

8.8.4 Making a load safe

  • Transactions and commit size. Rows are written in groups; each group is committed. Informatica's plan lets you set a source-based or target-based commit (target-based is the default) and a commit interval whose default is 10,000 rows (User Guide 10.5.10, p.285). Delphix masking jobs have a Commit Size field with the same meaning. From docs
  • Constraints. Load parents before children, or disable and re-enable constraints carefully. Delphix jobs have optional Disable Constraints, Disable Triggers and Drop Indexes checkboxes, all off by default, for exactly this reason. From docs
  • Recovery. Decide in advance what a failed load does: roll back and stop, skip the bad row, or resume from a checkpoint (see 8.14).

8.9 Batch, streaming, and ETL versus ELT

8.9.1 Batch versus streaming at a glance

Batch

Collect data for a period (an hour, a night), then process it as one group.

Easy to reason about and re-run. Results are always "as of last run".

Most ETL, and nearly all test data provisioning, is batch.

Streaming

Process each event, or tiny groups of events, within seconds of arrival.

Fresh results, harder to build. You must handle duplicates, late and out-of-order events.

Needed when the answer must be current: fraud alerts, live dashboards.

A middle path, micro-batching, runs a small batch every minute or so. For this guide you can treat all jobs as batch. General concept

8.9.2 ETL versus ELT

In ETL, transformations run in the ETL engine, on its own servers, before data reaches the target. In ELT, raw data is loaded into the target first (often a powerful cloud warehouse) and transformed there using its SQL engine.

ETLELT
Where transforms runSeparate ETL engineInside the target database
Raw data reaches target?Usually no, only cleaned dataYes, kept as a raw layer
StrengthSensitive data can be cleaned or masked before it lands in the targetUses the target's power; raw data can be re-transformed later
WeaknessThe engine can become a bottleneckRaw (maybe sensitive) data sits in the target

Look at the last row, because it matters for test data. If raw data holds real personal details, ELT would place them in the target before masking. That is why test data work usually follows the ETL order: mask first, then load. The ShopSphere example in this chapter is really a hybrid: staging is a lightweight "EL" step and the transformation is done by SQL. Many practical systems mix both styles. General concept

8.11 Mappings, sessions, workflows and jobs

Every ETL tool has a few layers of "thing you can define and run". Names vary, so learn the layers and then the names. General concept

  1. Transformation.

    One operation on rows: filter, lookup, aggregate. The smallest piece.

  2. Mapping.

    A diagram or definition that connects a source to a target through a chain of transformations. It describes what happens to the data, but does not run by itself.

  3. Session (or task).

    A runnable instance of one mapping, with the run settings: which connections, commit size, error rules.

  4. Workflow (or job, or pipeline).

    A set of sessions and other steps with an order and conditions: "run session A; if it works, run B and C; if it fails, send an email".

  5. Schedule or trigger.

    When the workflow starts: a time, a file arriving, another workflow ending.

These layers in the Informatica TDM guide
  • When you generate a workflow from a plan, "the PowerCenter Repository Service generates mappings for the workflow"; when you start it, the PowerCenter Integration Service does the subset, masking and generation tasks defined in the plan (p.308). From docs
  • You can view the sessions that run from each workflow, with statistics for affected rows, rejected rows and rows written to the target (p.275, "Session Details" tab). From docs
  • A plan can run a chosen workflow before ("pre workflow") and after ("post workflow") the main one: its example copies files from production to test area first, then masks, then runs statistics on the tables (p.277). From docs
  • Up to eight workflows run at one time; others queue (p.276). From docs
  • The guide also warns that if you edit components generated from Test Data Manager in the PowerCenter Client, "the session might generate unexpected results" (p.150). From docs

8.12 Reusable components and the mapplet

Concept. A reusable component is a piece of ETL logic you build once and use in many places, like a function in programming.

Why it matters. Without reuse, the same rule (clean a phone number, standardise a country name) is copied into twenty mappings. When the rule changes, someone must find and fix twenty copies, and will miss one.

In Informatica's world, the reusable group of transformations is called a mapplet. A mapplet has input and output ports (named connection points), contains one or more transformations, and can be placed into many mappings. Think of it as a small mapping with sockets at each end.

Input portFIRST_NAME
→
Transformations insidetrim, fix case, reject blanks
→
Output portFIRST_NAME_CLEAN

What the TDM guide says about mapplets (the rest of the product is not needed to follow this):

  • Test Data Manager can create a masking rule from a mapplet. The mapplet holds the logic that masks the input columns and returns data to the target columns (User Guide 10.5.10, p.137). From docs
  • You import the mapplet from an XML file exported from the PowerCenter repository or the Model repository, and the mapplet can contain "any passive transformations" (p.137). A passive transformation is one that does not change the number of rows. From docs
  • A mapplet can have multiple input and multiple output columns; at least one input and one output must be marked required. When you assign the rule to a column you map the mapplet's column names to the real table columns (p.137). From docs
  • The TDM repository stores the mapplet logic when imported, and you cannot change the mapplet inside Test Data Manager. The guide also says that if you change the name or type of a field of a custom masking rule, you must import the mapplet again (p.144). From docs
  • Data generation uses the same idea: a custom generation rule is based on PowerCenter mapplet logic, for example one that joins first and last name into a full name (pp.192 and 211). From docs

ShopSphere mapplet idea

Define one mapplet, m_clean_name: input NAME_IN, output NAME_OUT, doing trim, first-letter upper case and the rest lower case. Use it for first_name and for last_name in the customer mapping.
