Every tool in this guide moves data. Informatica TDM copies a slice of a database, changes some values and writes it somewhere else. Delphix reads a source, masks it and delivers it to a target. GenRocket creates rows and writes them to a database or a file. Underneath, all three do the same three things: get data from somewhere, change it, put it somewhere else. The industry has had a name for that pattern for decades: ETL, which stands for Extract, Transform, Load.

This chapter teaches ETL on its own, with no test data management in it, so that you can recognise the pattern wherever it appears. We will build a small but complete ETL job for ShopSphere using plain SQL, with real input and real output tables, then look at the machinery that real ETL tools wrap around those SQL steps: schedulers, logs, error handling and reusable components. The next chapter on ETL and TDM lays the TDM tools on top of what you learn here.

You do not need any earlier ETL knowledge. You do need to know what a table, a primary key and a foreign key are; if not, read the data basics chapter first.

8.1 Words to know first

ETL
Extract, Transform, Load: copy data out of one or more sources, reshape and clean it, and write it into a target.
Source and target
Where the data comes from, and where it goes.
Extract
The step that reads data from the source.
Transform
The step that changes the data: cleaning, converting, combining, calculating.
Load
The step that writes the result into the target.
Staging area
A temporary landing zone, usually a set of tables or files, where extracted data sits unchanged before it is transformed.
Operational database (OLTP)
The database an application uses to run the business: place an order, update an address. Built for many small, fast reads and writes.
Data warehouse
A separate database built for reporting and analysis across lots of history. Built for a few big reads.
Full extract / incremental extract
Reading everything every time, versus reading only what is new or changed since last time.
Watermark
A saved marker, such as "last order id loaded was 5005", that tells the next run where to start.
Change data capture (CDC)
Any technique that detects which rows were inserted, updated or deleted in the source so only those are processed.
Upsert
"Update if the row exists, insert if it does not." Short for update plus insert.
Slowly changing dimension (SCD)
A way of keeping history in a warehouse table when descriptive data (an address) changes over time.
Mapping
The definition of how source columns become target columns, including every transformation in between.
Workflow, session, job
The runnable wrappers around mappings. A job or workflow runs one or more sessions or steps on a schedule.
Mapplet
Informatica's word for a reusable group of transformations that you build once and drop into many mappings.
Metadata
Data about data: table definitions, column types, mapping definitions, run history.
Reject (error) row
A row the job could not process, written aside with a reason instead of stopping the whole run.
ELT
Extract, Load, Transform: load raw data into the target first and transform it there using the target database's own power.

8.2 What ETL is and why it exists

Concept. ETL is a repeatable process that moves data from where it is created to where it is needed, fixing it on the way.

Simple explanation. Think of a school canteen that serves lunch to 1,000 students. Raw vegetables arrive from several farms in different crates, some muddy and some damaged (extract brings them to the back door). In the prep room, staff wash, peel, cut, discard the bad ones and combine them into recipes (transform). Finally trays go to the serving counter in a fixed layout (load). Nobody serves a muddy carrot straight from the farm crate, and nobody cooks in the dining hall. Each stage has its own place and its own rules.

The analogy stops being accurate in one important way: a canteen runs once a day and food is eaten. An ETL job usually runs many times, and the same job must give the same kind of result each time, even if it is interrupted and restarted. Cooks can improvise; ETL jobs must not.

Why it matters

Data in real companies lives in many places and many shapes. ShopSphere's orders sit in one database, product prices in a spreadsheet maintained by buyers, and a partner sends a daily file where dates are written day first. A manager who asks "how much did we sell last week, per product?" needs one clean answer. Someone has to collect, clean and combine. ETL is the name for doing that on purpose, automatically, and with a record of what happened.

ETL appears in data warehouses and reports (the classic case), system migrations, keeping two systems in step, feeding analytics, and test data provisioning, the topic of the next chapter.

8.3 Operational database versus data warehouse

ETL usually connects those two kinds of database, so the difference is worth knowing. General concept

QuestionOperational database (OLTP)Data warehouse
Main purposeRun the business, one transaction at a timeAnswer questions across lots of history
Typical work"Insert this order", "update this address""Total sales per product per month for three years"
Table shapeMany small tables, tightly normalised to avoid duplication (CUSTOMERS, ORDERS, ORDER_ITEMS)Fewer, wider tables arranged around facts and dimensions
HistoryMostly current values; old values are overwrittenHistory kept, often with dated versions of each row
Who writesThe application, all dayThe ETL job, on a schedule
Who readsThe application and its usersAnalysts, report tools, dashboards
Speed priorityFast small reads and writesFast big scans and summaries

A common warehouse shape is the star schema: a central fact table that records events or measurements (one row per order line, with quantity and amount), surrounded by dimension tables that describe the who, what and when (customer, product, date). A fact table is mostly numbers and keys; a dimension table is mostly descriptive text. We will build a tiny star for ShopSphere later in this chapter.

Why not report straight from the operational database?

Big summary queries compete with customers placing orders and slow the shop down. The operational tables are also shaped for writing, so reporting queries need many joins. A separate warehouse removes both problems, at the price of building and running ETL.
