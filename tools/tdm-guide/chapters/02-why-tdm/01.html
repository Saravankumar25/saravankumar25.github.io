2.1 Words to know first

Software testing
Checking, before real users rely on it, that a program does what it should and does not break when something unexpected happens.
Test case
One specific check: "do this, with this data, and expect that result". Example: place an order for a customer with no previous orders and expect a confirmation.
Test data
The data a test case needs: the customers, products and orders that exist before the test starts, and the values typed in during it.
Environment
A complete running copy of the application with its own servers and its own database. Different environments serve different purposes.
Production (prod)
The live environment used by real customers. It holds real data.
Non-production
Every environment that is not production: dev, QA, UAT, staging and so on.
Sensitive data
Information that would harm a person or the company if leaked: names with ID numbers, health records, card numbers. The sensitive data and regulations chapter covers it fully.
Refresh
Replacing the data in a test environment with a newer copy.
Edge case
An unusual but possible input, such as an empty name, a very long address or a date on 29 February.
COTS
Commercial off-the-shelf: software you buy ready-made from a vendor and configure, instead of building it yourself.
TDM
Test Data Management, the subject of this guide.

2.2 What software testing is, and why it needs data

Testing in brief

Imagine ShopSphere's developers have just changed how discounts are calculated. Before the change reaches real shoppers, someone has to check it. They log into a copy of the app, place an order, and look at the total. If the discount is wrong, they report a bug. That checking is software testing.

Testing is not a single activity. Teams run many kinds: a developer checks one function, a QA engineer clicks through a whole purchase, a performance tester sends thousands of orders at once, a business user confirms the app does what the business asked. They all share one need.

An application without data does nothing

An online shop with an empty database has no customers to log in, no products to buy, no orders to total. A test that says "check the discount for a returning customer" needs a returning customer to exist. So before the test starts, the environment must already contain:

  • customers with the right attributes (a returning customer, a new one, one with an expired card);
  • products with prices;
  • earlier orders for those customers, linked correctly to them.

That pre-loaded information is test data. It is as essential to a test as the code under test.

General concept
Why this matters

Bad test data produces two kinds of waste. Tests that should pass fail because the data is wrong (a false alarm that costs a developer an afternoon). Or tests pass when they should fail because the data never contained the tricky case (a bug reaches customers). Good data is not a luxury; it decides whether the test result can be trusted.

What makes test data "good"?

Testers usually want data that is:

QualityMeaningShopSphere example
RealisticLooks and behaves like real data, so the app reacts as it would in production.Phone numbers have 10 digits; emails contain "@"; order totals match their line items.
ConsistentRelated records agree with each other.Every order points to a customer that exists.
Complete enoughCovers the cases the tests need, including odd ones.A customer with zero orders; an order with 100 items; a customer born on 29 February.
Right-sizedBig enough to be meaningful, small enough to load and refresh quickly.Thousands of customers for functional tests, millions only for performance tests.
SafeCannot hurt anyone if it leaks.No real names with real ID numbers.
AvailableThere when the tester needs it, not three weeks later.A fresh dataset the morning a release starts testing.
RepeatableCan be put back to a known state so a test gives the same result twice.Re-running yesterday's test on yesterday's data.

Notice that these seven qualities pull against each other. "Realistic" and "safe" fight: the most realistic data is real data, which is the least safe. "Complete" and "right-sized" fight too. TDM is the work of balancing them deliberately instead of by accident.

Security is usually weaker outside production

The Informatica User Guide points out that organisations typically keep strict controls on production systems, while data security in non-production systems is often not as strong (User Guide 10.5.10, p.21). Who needs data, and when?

In ShopSphere, a single sprint can ask for data in several ways at once:

  • A developer fixing a rounding bug needs one customer with a specific order total.
  • A QA engineer testing refunds needs hundreds of orders in different states (paid, shipped, returned).
  • A performance tester needs millions of orders to see whether the site slows down.
  • A business analyst in UAT needs data that "looks like our real customers" so they can judge whether a screen makes sense.
  • An automation engineer needs the same data every night so the automated tests are repeatable.

Five people, five different requirements. If nobody manages this, each one solves it alone, usually in the least safe way. That is the next section.

Types of testing and the data each one wants

The word "testing" covers several activities. They need different data, which is why one dataset rarely suits everyone.
