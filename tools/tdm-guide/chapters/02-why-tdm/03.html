2.5 So what is Test Data Management?

Test Data Management (TDM) is the set of processes, roles and tools that plan, create, protect, deliver and retire the data used in non-production environments. In simpler words: it is how you make sure the right testers get the right safe data at the right time, without copying production carelessly.

General concept

Some people use "TDM" for the software and some for the practice. In this guide "TDM" is the practice, and "a TDM tool" is software that supports it.

Goals of TDM

  1. Protect people. No real sensitive data in non-production.
  2. Fit the test. Data that is realistic, consistent and covers the cases the tests need.
  3. Right size. Smaller than production where possible, large only where tests need it.
  4. Be fast. Data on request, refreshed in minutes or hours, not weeks.
  5. Be repeatable and traceable. Known data versions, known owners, known copies.
  6. Lower cost. Less storage, less waiting, less rework, lower breach risk.

2.6 The six capabilities of TDM

TDM splits into six capabilities. A project may use all six or only a few. The first four change the data; the last two deliver and control it.

1. Discover

You cannot protect what you cannot find. Discovery means scanning a database or a set of files to locate sensitive data: which columns hold names, ID numbers, phone numbers. Large databases can have thousands of columns, and sensitive values hide in odd places such as a "notes" column. Discovery also finds the relationships between tables, which later steps need.

Why it matters: if discovery misses a column, that column goes into test unmasked.

ShopSphere: discovery flags ssn, phone, email, date_of_birth and tax_id in CUSTOMERS. The discovery and subsetting concepts chapter teaches this in depth.

2. Subset

Subsetting builds a smaller database from a big one: for example "only customers from the last two years, and everything linked to them". Done properly, every order in the subset still has its customer and its items. Smaller means cheaper, faster to load and easier to refresh.

ShopSphere: pick 5,000 customers and bring their orders and items along, leaving the other millions of rows behind. The discovery and subsetting concepts chapter covers it; the Informatica data subset chapter shows it in Informatica.

3. Mask

Masking replaces sensitive values with realistic but fake ones. The application still works because the fake values look right (a fake phone has ten digits), but nobody can learn about a real person from them. Good masking is consistent: the same real value always becomes the same fake value, so relationships between tables survive.

The Delphix documentation describes masking as replacing confidential information such as social security numbers, patient records and card numbers with fictitious yet realistic data, and contrasts it with encryption: masking is irreversible, while encryption can be bypassed through schemes to obtain user credentials (Introduction to Delphix Masking). From docs

ShopSphere: Asha Menon, 9876543210, 123-45-6789 becomes, say, a made-up name, a made-up ten-digit number and a made-up SSN pattern. The masking concepts chapter teaches the techniques.

General concept

4. Generate

Generation creates data from rules instead of copying real data. You describe what you need ("fifty customers, each with a first name, a last name, a phone number") and a tool produces it. Use it when real data does not exist yet (a new feature), when you need edge cases, when you need very large volumes, or when real data cannot be used at all.

Informatica's documentation gives the second reason almost word for word: use data generation when you need test data but do not want to use production data, for example when test teams handle sensitive data and have no access to production (User Guide 10.5.10, p.23). From docs

ShopSphere: generate a customer whose name is 300 characters long. The classification and generation concepts chapter covers the idea; Part III is GenRocket, a tool built around it.

5. Provision and refresh

Provisioning means delivering a ready dataset into an environment: loading it into the QA database, or placing a file where a test tool expects it. Refreshing means doing it again later to get new or reset data. Speed and repeatability matter most here.

Both Informatica and Delphix address this in their own way. Informatica describes a test data warehouse that stores multiple versions of test data and can restore a version to put an environment back into a particular state (User Guide 10.5.10, p.23). Delphix describes virtual copies that are readable and writable, can be created or removed in minutes, and take a fraction of the storage of physical copies; in its example ten virtual copies fit in the space of one physical copy (Introduction to Delphix Masking). From docs

6. Govern

Governance is the rules and records around the other five: who may request what, which data is approved for which environment, which masking rules are in force, an audit trail of who received which dataset. It is the least glamorous capability and the first one auditors ask about.

Delphix says the platform lets operators audit, monitor and report against access and usage, and generates reports and email notifications confirming sensitive data has been masked. Informatica's administrator manages roles and privileges that decide what each TDM user can do (User Guide 10.5.10, p.23). From docs

Why the six are separate ideas

Beginners often use "masking" to mean everything. It is only one of six. A team that masks but never subsets still has a huge, slow copy. A team that subsets but never discovers may mask the wrong columns. Learn the six as separate tools in a toolbox, then pick the ones a project needs.

Goal: see in numbers why unmanaged test data is expensive. All figures below are invented for practice; replace them with your own project's.

  1. Storage.

    Production is 4 TB and ShopSphere has five non-production environments, each holding a full copy. Compute the total storage for the copies.

    An answer in TB.

  2. Waiting.

    A restore takes 2 days. QA needs one restore per fortnight and the team of 6 testers is idle half of the restore time. Compute idle tester-days per year.

    An answer in tester-days.

  3. Subset effect.

    A subset keeps 5 percent of the data. Recompute step 1.

    A much smaller number.

Show a worked answer

1. 5 environments x 4 TB = 20 TB.

2. About 26 fortnights a year. Each restore idles 6 testers for half of 2 days = 1 day each, so 6 tester-days per restore, 26 x 6 = 156 tester-days per year.

3. 5 percent of 4 TB is 0.2 TB, so 5 x 0.2 = 1 TB, one twentieth of the 20 TB. A smaller copy also restores faster, which shrinks the idle time in step 2 as well.

The numbers are made up, but the shape is real: costs multiply by the number of copies and the frequency of refreshes. Do not quote them as ShopSphere facts.
