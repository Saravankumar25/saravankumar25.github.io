2.4 The naive approach: copy production

The quickest way to get realistic, consistent data is to take a backup of the production database and restore it into the test environment. It is what many teams do first, because it works on day one and needs no special tool. This is the production copy approach.

It feels right: the data is as real as data can be, and every relationship between tables is already correct. The problems appear later, and they are serious. Here are eight, each shown with ShopSphere.

Problem 1: privacy and security leaks

Production holds real names, phone numbers, ID numbers and dates of birth. A full copy puts all of that where far more people have access: developers, testers, contractors, sometimes outside vendors, usually with weaker access controls and monitoring.

ShopSphere example. The row for customer 1001 (Asha Menon, her email, phone and SSN) is now in the dev, QA and UAT databases, in a test engineer's laptop dump and in a bug-report screenshot. Any one of those is a breach waiting to happen.

It is also often a legal problem. Laws and standards such as GDPR, HIPAA and PCI restrict how personal data can be used. The Delphix introduction names exactly these three (HIPAA, PCI and GDPR) as mandates organisations must stay compliant with, and notes that growing pressure from regulators and consumers makes protecting sensitive data across the enterprise essential (Introduction to Delphix Masking). From docs the sensitive data and regulations chapter explains the regulations.

Problem 2: huge size

Production databases grow for years. A full copy needs the same disk space as production, multiplied by the number of environments, plus time to move and back up each copy.

ShopSphere example. If production is 4 TB (example figure), five test environments need 20 TB, and most of the content is orders from five years ago that no current test will ever read.

Problem 3: slow refreshes

Copying terabytes takes hours or days, so teams refresh rarely, queue for the operations team, and sometimes freeze the data for weeks.

ShopSphere example. QA breaks the data while testing refunds. Restoring it takes two days. Everyone waits, or carries on with broken data and gets false test results.

Problem 4: stale data

A copy is a snapshot of one moment. The day after, production has moved on, so tests of the newest code may run against data that does not contain it.

ShopSphere example. A "gift card" payment type launched last week. The copy taken last month has no orders that use it, so the gift-card tests find nothing to test.

Problem 5: missing edge cases

Real data contains only the cases that happened. Tests need values at the boundary: the largest allowed order, an empty field, a name with an apostrophe, a negative quantity that the app must reject.

ShopSphere example. Nobody in production has a 300-character last name, so no test checks that the screen handles one. The first customer who does crashes the checkout page.

This is where synthetic data comes in. GenRocket's help site defines synthetic test data as data manufactured by an algorithm rather than collected from real-world events, and says companies can maximise test coverage by using it to test all permutations and combinations (Why Synthetic Test Data?). From docs

Problem 6: broken relationships when people shrink or edit it

Finding the copy too big, someone cuts it down by hand: "delete orders older than 2023". But orders are linked to customers and order items to orders. Delete the wrong rows and you leave order items pointing to orders that no longer exist, or orders for removed customers. The application then crashes or gives nonsense, for reasons unrelated to the code being tested.

ShopSphere example. A script deletes customers who have not logged in since 2022. It forgets their rows in ORDERS. Now there are orders with a customer_id that matches nobody. The "my orders" page fails for the wrong reason.

The same breakage happens if hand-made replacements differ between tables: the customer is "Asha" in one and "Priya" in another. The data basics chapter explains the keys that tie tables together. The Informatica documentation describes the goal directly: a data subset keeps primary and foreign key relationships so that the data stays referentially intact (User Guide 10.5.10, p.23). From docs

Problem 7: cost

The costs are not only disk space. Add the time of people who run restores, the delay while testers wait, and the risk cost of a breach or regulator fine. None of it appears as a "test data" line on a budget, which is partly why the problem lingers.

Problem 8: no repeatability and no control

If every team makes its own copy at its own time, nobody knows which data version a bug was found on. Tests that passed Monday fail Tuesday because the data under them changed. Nobody can say who has a copy of what.

The same problems, as a vendor described them in 2020

From video In a 2020 webinar, GenRocket's CEO used an industry quality report to argue that test data lags behind test automation. He said roughly two thirds of organisations still use spreadsheets to build test data and over half still create it by hand. He added two customer stories: a large financial firm with a TDM tool could get the data a test case needed from its production copies only about a third of the time, and a large health insurer waited many days for data. These are a vendor's claims from 2020, not measured facts.

In the same webinar a testing-services partner listed the challenges its clients keep raising. Most match problems above, and one adds something new:

  • Business-process coverage. Tests need negative cases and many permutations, not only the happy path (problem 5).
  • Speed. Data must arrive as fast as the team deploys (problems 3 and 4).
  • Quality and security. Good testing needs good data, and the data must be protected (problem 1).
  • Many formats and sources. Data arrives in files, databases and other forms, and a tool must deliver to all of them. This is the one the eight problems do not cover.
  • Sharing and reuse. Projects and environments want to share the same data (problem 8).

GenRocket's 2022 overview video presents customer results in the same spirit, for example a cycle time cut from 16 days to 2 hours. Those are again vendor-reported figures for specific customers.

"But we only use it internally" is not a defence

A breach through a test environment is still a breach of the people whose data it is. Internal staff, contractors and vendors can all misuse or lose data, and many regulations make no exception for non-production systems. The sensitive data and regulations chapter goes through this carefully.

Worked example: one bug report, three failures

A ShopSphere tester finds that the "order history" screen shows an empty page for customer 1002 in the QA environment. She files a bug. The developer cannot reproduce it on his machine because his data is different. After a day of investigation they discover that the QA database was a partial manual copy in which customer 1002's orders were not copied. The bug is not in the code at all.

That one incident shows three problems from the list: broken relationships (6), no control (8) and slow refresh (3). It also cost two people a day. Multiply by a team and a year and the cost becomes visible.
