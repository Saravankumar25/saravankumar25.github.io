2.4 The naive approach: copy production

The quickest way to get realistic, consistent data is to take a backup of the production database and restore it into the test environment. It is what many teams do first, because it works on day one and needs no special tool. This is the production copy approach.

It feels right: the data is as real as data can be, and every relationship between tables is already correct. The problems appear later, and they are serious. Here are eight, each shown with ShopSphere.

Problem 1: privacy and security leaks

Production holds real names, phone numbers, ID numbers and dates of birth. A full copy puts all of that into environments where far more people have access: every developer, every tester, contractors, sometimes outside vendors. Non-production systems usually have weaker access controls, weaker monitoring and more people logged in.

ShopSphere example. The row for customer 1001 (Asha Menon, her email, her phone, her SSN) is now in the dev database, in the QA database, in the UAT database, in a test engineer's laptop dump, and in a screenshot attached to a bug report. Any one of those is a breach waiting to happen.

It is also often a legal problem. Laws and standards such as GDPR, HIPAA and PCI restrict how personal data can be used. The Delphix introduction names exactly these three (HIPAA, PCI and GDPR) as mandates organisations must stay compliant with, and notes that growing pressure from regulators and consumers makes protecting sensitive data across the enterprise essential (Introduction to Delphix Masking). From docs the sensitive data and regulations chapter explains the regulations.

Problem 2: huge size

Production databases grow for years. A full copy needs the same disk space as production, multiplied by the number of environments. Storage costs add up, and so does the time to move and back up the copies.

ShopSphere example. If production is 4 TB (invented for illustration), five test environments need 20 TB, and most of the content is orders from five years ago that no current test will ever read.

Problem 3: slow refreshes

Copying terabytes takes hours or days. Teams therefore refresh rarely, queue for the operations team, and sometimes freeze the data for weeks to avoid doing it again.

ShopSphere example. QA breaks the data while testing refunds. Restoring it takes two days. Everyone waits, or carries on with broken data and gets false test results.

Problem 4: stale data

A copy is a snapshot of one moment. The day after, production has moved on. New products, new account types and new features may be missing from the copy, so tests of the newest code run against data that does not contain it.

ShopSphere example. A "gift card" payment type launched last week. The copy taken last month has no orders that use it, so the gift-card tests find nothing to test.

Problem 5: missing edge cases

Real data contains the cases that happened. It does not contain the cases that have not happened yet, or have happened too rarely to be in your copy. Tests need values at the boundary: the largest allowed order, an empty field, a name with an apostrophe, a negative quantity that the app must reject.

ShopSphere example. Nobody in production has a 300-character last name, so no test checks that the screen handles one. The first customer who does crashes the checkout page.

This is where synthetic data comes in. GenRocket's help site defines synthetic test data as data manufactured by an algorithm rather than collected from real-world events, and says companies can maximise test coverage by using it to test all permutations and combinations (Why Synthetic Test Data?). From docs

Problem 6: broken relationships when people shrink or edit it

Realising the copy is too big, someone tries to cut it down by hand: "delete orders older than 2023". But orders are linked to customers and order items are linked to orders. Delete in the wrong order or the wrong rows and you leave order items pointing to orders that no longer exist, or orders for customers who have been removed. The application then crashes or gives nonsense, for reasons unrelated to the code being tested.

ShopSphere example. A script deletes customers who have not logged in since 2022. It forgets their rows in ORDERS. Now there are orders with a customer_id that matches nobody. The "my orders" page fails for the wrong reason.

The same breakage happens if someone replaces names with random text by hand and uses different replacements in different tables: the customer is "Asha" in one table and "Priya" in another. The data basics chapter explains the keys that tie tables together and why every TDM operation must respect them. The Informatica documentation describes the goal directly: a data subset keeps primary and foreign key relationships so that the data stays referentially intact (User Guide 10.5.10, p.23). From docs

Problem 7: cost

The costs are not only disk space. Add the time of people who run restores, the delay while testers wait, the licence and infrastructure cost of big environments, and the risk cost of a breach or regulator fine. None of it appears as a line "test data" on a budget, which is partly why the problem lingers.

Problem 8: no repeatability and no control

If every team makes its own copy at its own time, nobody knows which data version a bug was found on. Tests that passed Monday fail Tuesday because the data under them changed. Nobody can say who has a copy of what.

A breach through a test environment is still a breach of the people whose data it is. Internal staff, contractors and vendors can all misuse or lose data, and many regulations make no exception for non-production systems. The sensitive data and regulations chapter goes through this carefully.

Worked example: one bug report, three failures

A ShopSphere tester finds that the "order history" screen shows an empty page for customer 1002 in the QA environment. She files a bug. The developer cannot reproduce it on his machine because his data is different. After a day of investigation they discover that the QA database was a partial manual copy in which customer 1002's orders were not copied. The bug is not in the code at all.

That one incident shows three problems from the list: broken relationships (problem 6), no control (8) and slow refresh (3: fixing it means a new copy). It also cost a day of two people's time. Multiply by a team and a year and the cost of unmanaged test data becomes visible.
