11.11 Data sources

A project cannot do anything until it knows what tables it is working on. To do subset, masking or discovery, you import source metadata into the TDM repository. To generate data, you import target metadata instead (User Guide 10.5.10, p.60). A project can hold more than one type of source, for example a flat file and a relational database, and you can create constraints that relate them and add filter criteria for subset and masking.

A numeric precision limit

If a numeric column has a precision above 28, you cannot apply a masking or subset condition to it. The Integration Service passes that row and column to the target without applying the condition (p.60). Check unusual numeric columns before you trust a run.

TDM source definitions

You can import source metadata from PowerCenter, from the Model repository, or directly from the source database (p.60). The guide's points:

  • The TDM project and the repository folders share the same name, so workflow information goes to the correct folder.
  • If the source is relational and has many tables, importing straight from the database is faster than going through PowerCenter or the Model repository.
  • Importing from the PowerCenter or Model repository brings in the definitions Informatica services support, by importing the repository folder that holds them; TDM makes a copy of that folder in the TDM repository.
  • MongoDB sources imported into PowerCenter need unique column names of at most 80 characters.
  • Flat files must come from the PowerCenter or Model repository; you cannot create flat file connections in Test Data Manager.
  • rowid is a reserved keyword. You cannot import Oracle sources that use it as a column or table name.

Importing data sources

Task: import the ShopSphere tables into the project

Goal: have the four tables visible in the project's Data Sources view. The steps are the guide's (pp.66-67). The choice of "Datasource Connection" and of the schema is our illustration; it assumes an administrator already created a connection to the ShopSphere database.

  1. Click Projects, then click your project to open it.

    Imports belong to a project, so the tables arrive in the right workspace.

  2. Click Actions > Import Metadata.

    The Import Metadata window appears.

  3. Choose the source type.

    Options: PowerCenter Repository, Model Repository, or Datasource Connection. For a plain relational database, Datasource Connection is the direct route. To import metadata from a flat file or a JDBC connection, you must use the Model repository.

  4. Decide whether to review metadata changes before the import.

    If you choose to review, TDM shows the metadata and its impact on rules and domain assignments, or entities and groups. You can skip this option. Reviewing is wise when re-importing into a project that already has assignments.

  5. Click Next and choose where to import from.

    For PowerCenter or the Model repository, pick the folder (filter by name or description). For Datasource Connection, pick the schema (filter by name). Click Next.

  6. Select the tables or files to import and click Next.

    You can filter by data source, table name or description. For a Hive database, do not select temporary "junk" tables created when mappings run.

  7. Choose when to import and click Finish.

    Import Now (tick Run import in the background if you want to keep working) or Schedule Later (pick a date and time).

    The Import Progress dialog box shows a progress bar. If you chose to review, the Impact Review dialog box appears with metadata, assignments and project objects; click Approve to import or Reject to cancel. Afterwards the tables are in the Data Sources details view.

Show what ShopSphere should look like afterwards

Illustrative, not from the guide: four tables in the project's data source, CUSTOMERS, ORDERS, ORDER_ITEMS and PRODUCTS, all under the schema you picked. A job for the import is listed in the project's Monitor view while it runs. If a table is missing, check the table selection step and the Monitor view for a failed import job.

Special source types in the guide

The guide spends several pages on source types that a ShopSphere beginner will not meet on day one. Know that they exist and what the headline rules are.

Source typeHeadline facts (pp.60-66)
Hive and HDFSYou can do data movement, data domain discovery and masking. A cluster configuration must exist in the Administrator tool. Use a Hadoop plan. You cannot do subset or generation on Hive and HDFS. Do not select temporary junk tables. Data domain discovery works, but primary key and entity profiles do not run on Hive. Before in-place masking on Hive, back up the source tables, because a failed move from staging can truncate them.
Avro and ParquetSemi-structured formats for single-level hierarchy files, usable when you choose an HDFS target. With Parquet you cannot use null or repeated constraints. You cannot run profiles on Avro and Parquet.
XSD (XML) sourcesSubset, masking and generation work on XML. Import the XSD source definition from the PowerCenter repository; importing the XML itself makes the workflow fail. View files under Discover > Files. On a file page, the Properties, View and Details tabs let you assign data domains, mark elements Restricted or Sensitive, and assign masking rules, generation rules or subset criteria. You cannot delete XML files after import.
PowerExchange nonrelationalAdabas, IMS unload, Sequential, and hierarchical and nonhierarchical VSAM. Define datamaps in PowerExchange, import into PowerCenter, then import into the project. You cannot import a PowerExchange source directly into the TDM repository.

Identity columns

An identity column is one the database fills in automatically with a counter. Three rules from the guide (p.67):

  • On Sybase, you cannot move data from a source DBO schema to a target non-DBO schema if the data has an identity column and indexes.
  • If auto identity is enabled in Sybase and a table has no primary or unique keys, Sybase adds a SYB_IDENTITY_COL column. Mark it Restricted (restricted means the Integration Service does not write the value to the target), or the workflow fails.
  • To disable an identity column on Microsoft SQL Server, the database user needs execute permission on sp_help.

Deleting a table

You can remove a table from a project if you added too many or no longer need some (pp.67-68). Rules: an orphan table (related to no other table and with no assignments) deletes directly. If the table is part of profile results, a warning appears and it is removed from them too. If it is part of an entity, group, masking plan or generation plan, the Impacted Objects dialog lists what will be affected; a table in a template that is part of a plan does not list the template and plan. You delete one table at a time.

  1. Open the project and click Discover > Tables.
  2. Select the table and click Actions > Delete Table.

    A confirmation message appears if the table has no assignments; otherwise the Impacted Objects dialog appears.

  3. Click Continue to confirm.

    Delete only tables not used in a TDM operation. Regenerate and run affected plans afterwards.

11.12 Project permissions and security

When you create a project you become its owner and can add users and user groups with permission levels. The domain administrator can also add and edit project permissions (User Guide 10.5.10, p.68). A project you have no permission on does not appear in your list, and you cannot open it even from search results. There are three levels, and they sit on top of privileges: you need the permission on this project and the minimum privilege for the task (p.50).

Permission levels and tasks (p.69)
PermissionWhat you can doMinimum privileges (as listed)
ReadOpen and view the project; monitor logs for project workflows.View project, Monitor project, Audit project
WriteEverything in Read, plus import metadata, delete tables, create entities, groups and templates, assign rules, generate workflows, run profiles, copy the project, delete the project.View, Monitor, Audit, Import metadata, Generate project, Manage project, Discover project
ExecuteOpen and view the project; monitor logs; run workflows.View, Monitor, Audit, Execute project

Notice that "run workflows" is separate from "generate workflows". That lets a team give a QA engineer Execute to re-run a prepared plan without letting them change it. Write does not list Execute in the guide's table; if a developer must both build and run, grant both.

  1. Open the project and click Permissions.

    Lists of users and user groups with their permissions appear (Users and User Groups tabs).

  2. Click Edit on the Users or User Groups tab.

    The Edit Project Permissions dialog opens.

  3. Change, delete or add.

    To change, select the user or group and edit the permission; save for each user or group. To delete, select and click Delete. To add, click Add Users or Add User Groups, select one or more, optionally pick the permission to give all selected, then OK; if you did not pick, select each one and set permissions, saving each.

  4. Click OK.

    Changes take effect from the user's next login.
