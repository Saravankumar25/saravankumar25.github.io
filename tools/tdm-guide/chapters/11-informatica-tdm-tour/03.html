11.9 Projects

A project is the top-level container for everything you do to one set of data: discovery, masking, subset and generation (User Guide 10.5.10, p.49). Think of a project as a folder on your desk for one job, "Customer Orders for QA". Inside it you keep the table descriptions, your profile results, which rule goes on which column, the subset recipe, and the plans. The analogy has one flaw: in TDM the project folder is also a real folder in the PowerCenter repository with the same name as the project, which is how workflow information lands in the right place (p.60).

The six views inside a project

Open a project and you see a second row of tabs (pp.49-50). The first screenshot in the guide shows the Overview tab with general properties such as project name, creation and modification information, counts for data sources, tables, domain and rule assignments, and entities, groups, templates and plans, and status fields for discover, masking and generation setup and execution.

Parameters in a project

The Informatica overview and architecture chapter explained why parameters exist. Here are the details (pp.51-52, 57-58). Parameters are placeholders pointing to a value; the workflow reads the value at run time. You can create three kinds inside a project, and the tool generates the name prefix for you.

TypePlaceholder forName begins with
Connection parameterSource or target connections$DBConnection
Owner parameterSource or target schema owner names$Param
Criteria parameterValues in an entity's filter criteria$$

Rules and guidelines

  • With a connection parameter for an Oracle source connection, you cannot enable the Oracle Rowid property.
  • You cannot do batch updates for in-place masking with connection parameters, because a batch update needs a staging connection and a staging connection cannot be a parameter.
  • If a plan uses the same connection parameter as source and target, the Update Strategy property does not change to Update. Workaround: choose the Use Source Connection as Target Connection option, or change Update Strategy to Update by hand (p.52).

Creating, editing and importing a parameter

  1. Click Projects, open the project, click Parameters, then click Add.

    The Add Parameter window opens. A project parameter is only usable in this project.

  2. Enter a name, an optional description, and choose the type (criteria, connection or owner).

    The correct prefix is added to the name for you.

  3. Choose the data type: String, Numeric or Date.

    For Date, enter an expression that tells a function how to use it, for example TO_DATE($$CRIT1,'MM-DD-YYYY') where $$CRIT1 is the parameter name (p.57).

  4. Enter a default value and choose whether to allow override.

    A default is required if you do not allow override. If you do not allow override, nobody can change the value when running the workflow.

  5. Click OK.

    The parameter appears in the project's parameter list.

To edit, click the row (not the checkbox), change values and Save; you cannot change the parameter type or data type. To delete, tick the box, click Delete, confirm. A list of entities and plans that use the parameter appears; you can Export it to CSV, and you must generate and run those plans again to apply the change (pp.57-58). To import a global parameter, click Add Global Parameter on the Parameters tab, select, OK. Changes you make to the project copy do not affect the global one (p.58). To export global parameters, go to the Parameters view, Actions > Export (a CSV file you can import into another TDM repository).

Project logs

PowerCenter writes workflow and session logs when you run a plan or workflow from a project (User Guide 10.5.10, p.52). If you set no location, it uses defaults from the PowerCenter Integration Service properties, and the Data Integration Service stores reject files in its default location. The default directory variables are $PMWorkflowLogDir\ (workflow logs), $PMSessionLogDir\ (session logs) and $PMBadFileDir\ (reject files, meaning rows that could not be written).

  • You can set the locations in the Edit Project dialog for an existing project, but not when you create it.
  • When you create a plan you can set workflow and session log properties, such as keeping logs by time stamp, number of runs or maximum size, and the error log type and location for that plan.
  1. Open the project and click Actions > Edit; open the Default Log File tab.

    This is where the three directory fields live (p.59).

  2. Fill in the Workflow Log Directory, Session Log Directory and Reject File Directory.

    You can use parameters or a full path, ending with a slash or backslash, for example $PMWorkflowLogDir\projectlogs\. The directory must already exist; TDM does not create it. A wrong workflow log location makes the workflow fail to run without an error log.

  3. Click Save.

    Later runs write logs to your location.

Data masking transformation session properties

You can tune run-time properties of the data masking session (one execution of a mapping) to improve performance (pp.52-53). The guide lists these. A "dictionary" is a list of replacement values used by substitution masking. The "storage table" is a table used with dictionary-based masking; this chapter of the guide does not explain it further, so ask your trainer before changing the related settings.

PropertyMeaningDefault or advice
SSN High Group FilePath to the High Group List directory with Social Security numbers issued by the Social Security Administration.No default stated.
DMO Cache DirectoryLocation of the dictionary cache. You need write permission.Default $PMCacheDir.
Cache SizeSize of the dictionary cache in memory. Larger improves performance.Default 8 MB. Minimum recommended 32 MB for 100,000 records.
Shared Storage TableLets two Data Masking transformation instances, or two ports in one, share the storage table when they use the same dictionary column, database connection, seed value and locale.Default disabled; disable when they do not share the column.
Storage Commit IntervalNumber of rows committed at a time to the storage table. Raise it for speed. Set it when you do not use the shared storage table.Default 100,000.

The Informatica masking chapter explains masking techniques. For now, note that the guide ties performance gains specifically to a larger cache size and a larger storage commit interval.
