11.9 Projects

A project is the top-level container for everything you do to one set of data: discovery, masking, subset and generation (User Guide 10.5.10, p.49). Think of a project as a folder on your desk for one job, "Customer Orders for QA". Inside it you keep the table descriptions, your profile results, which rule goes on which column, the subset recipe, and the plans. The analogy has one flaw: in TDM the project folder is also a real folder in the PowerCenter repository with the same name as the project, which is how workflow information lands in the right place (p.60).

The six views inside a project

Open a project and you see a second row of tabs (User Guide 10.5.10, pp.49-50).

Project components

A project has at least one data source. The other components depend on the work (pp.50-51):

  • Entity: a set of related tables (subset, generation). Group: a set of unrelated tables copied to the subset (subset). Both are made in Define.
  • Parameters: values for connections, criteria and schema owners.
  • Plan: defines the operations; a PowerCenter workflow is generated from it. Made in Execute.
  • Policy assignments: assigning a policy gives the project its data domains and masking rules. Rule assignments: which rule applies to which column.
  • Profile: suggests keys, relationships and data domains. Made in Discover.

Parameters in a project

The Informatica overview chapter explained why parameters exist. Details (pp.51-52, 57-58): the tool adds the name prefix for you: connection parameters begin $DBConnection, owner parameters $Param, criteria parameters $$.

  • With a connection parameter on an Oracle source, you cannot enable the Oracle Rowid property.
  • Connection parameters rule out batch updates for in-place masking, because that needs a staging connection and a staging connection cannot be a parameter.
  • If a plan uses one connection parameter as both source and target, Update Strategy does not change to Update. Tick Use Source Connection as Target Connection, or set it by hand.
  1. Open the project, click Parameters, then Add.

    A project parameter is usable only in this project.

  2. Enter a name and choose the type (criteria, connection or owner) and a data type (String, Numeric or Date).

    For Date, enter an expression such as TO_DATE($$CRIT1,'MM-DD-YYYY') so a function knows how to use it.

  3. Enter a default value and choose whether to allow override, then click OK.

    If you do not allow override, nobody can change the value when running the workflow, so a default is then required.

    The parameter appears in the project's list.

To edit, click the row (not the checkbox), change values and Save; the parameter and data types cannot change. To delete, tick the box and click Delete; you see the entities and plans that use it and must regenerate and run them again. To import a global parameter, click Add Global Parameter; changes to the copy do not affect the global one (pp.57-58). Global parameters export to CSV from the Parameters view (Actions > Export).

Project logs

PowerCenter writes workflow and session logs when you run a plan from a project. Unless you set locations, it uses defaults from the PowerCenter Integration Service: $PMWorkflowLogDir\, $PMSessionLogDir\ and $PMBadFileDir\ (reject files hold rows that could not be written) (p.52). You can set them in the Edit Project dialog but not when creating the project: open the project, Actions > Edit, Default Log File tab, fill in the three directories with a trailing slash, Save (p.59). The directory must already exist. A wrong workflow log directory makes the workflow fail without an error log.

Data masking transformation session properties

You can tune run-time properties of the masking session (pp.52-53). The guide ties better performance to a bigger Cache Size (the dictionary cache in memory; default 8 MB, at least 32 MB recommended for 100,000 records) and a bigger Storage Commit Interval (rows committed per batch to the storage table; default 100,000). Other properties: DMO Cache Directory (default $PMCacheDir, needs write permission), SSN High Group File (path to the Social Security Administration high-group list) and Shared Storage Table (default disabled; share it only when two masking instances or ports use the same dictionary column, connection, seed and locale). The Informatica masking chapter explains the techniques.
