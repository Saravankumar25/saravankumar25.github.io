Policy packs: PII, PHI and PCI

You do not have to start from an empty Policies view. TDM includes three ready-made policy packs: PII, PHI and PCI. After installation they are visible in the Policies view, with the data and metadata patterns of their domains, so you can read the actual regular expressions (User Guide 10.5.10, p.77). To view and work with policies you need the Test Data Manager Service View Policies and Manage Policies privileges, and without View Policies you cannot see policies at all.

The three names are explained in the sensitive data and regulations chapter: PII is personally identifiable information, PHI is protected health information, PCI is payment card information.

Look at how this fits ShopSphere. The PII pack already has First Name, Last Name, Email Address, Phone, Social Security Number, Birth Date and ZIP, which cover almost every personal column in CUSTOMERS (first_name, last_name, email, phone, ssn, date_of_birth, zip_code). Nothing in the packs obviously covers tax_id: that is a case where you would add your own domain or assign one manually. The guide's pack tables do not list a "tax ID" domain.

A small oddity in the guide's tables

The PHI and PCI tables label their columns "Policy Pack" and "Description" instead of "Data Domain Name" and "Default Rule", but the content is clearly domain and default rule, matching the PII table (pp.79-80). I read them as the same layout.

Importing and exporting policy components

You can export policies, domains and rules to XML files and import them into another TDM repository (pp.80-81). The details matter:

  • Exporting a policy exports references to its domains. Exporting domains exports references to rules. Neither exports the referenced objects unless you choose to export them as well.
  • Policies, domains and rules go into separate XML files, each with a default name and a date number such as Policy_121112141309.xml or Domain_121112141309.xml. You can rename them.
  • If a rule or policy in the target TDM already has assignments, you cannot import the file. Clear the assignment or change the name in the file first.
  • If the object already exists, import overwrites it.
  1. Export: in the Policies view tick the objects, click Actions > Export, then Open or Save. Test Data Manager prompts once for each type of file.
  2. Import: in the Policies view click Actions > Import, browse for the XML file, click Finish.

Importing data domains from the Model repository

Data domains created in the Informatica Developer tool live in the Model repository. Import them before you import a data domain profile (pp.81-82).

  1. Click Policies, then Actions > Import Data Domains.

    A window lists data domains in the Model repository.

  2. Select the domains, set a sensitivity level for each in the Sensitivity Level column, click Save, then Import.

    If a same-name domain exists, you can overwrite or cancel.

What comes across: name, description and links to business terms. What does not: data patterns, metadata patterns and preferred rules. So an imported domain is a shell that you finish in Test Data Manager. If you overwrite, TDM updates the description and linked terms but keeps the patterns and rules you set in TDM. Linked business terms are merged, and a term deleted in Developer is kept in TDM until you delete it by hand (p.81).

Linking Business Glossary terms

You can link Informatica Business Glossary terms to global objects: policies, domains, masking rules and generation rules (p.82). A business term has a business definition and examples of use, stored centrally so people can look things up. Link a term to a TDM object and you can see the object from the term in the Analyst tool. You need an Analyst Service configured in the Test Data Manager Service properties, as the Informatica architecture chapter listed.

  1. In Policies, select the object (policy, domain, masking rule or generation rule) and open the Linked Business Terms tab.

    The tab lists the term, its glossary and a description.

  2. Click Add, choose the glossary on the Link Asset to Business Term page, select terms and click OK.

    You need Manage privileges on the object.

  3. To remove a link: select the term on the tab, click Delete, then Yes. You can also delete it from the Business Glossary UI (p.83).

Side effects: deleting the TDM object deletes the link; renaming a linked object shows the new name in the glossary; deleting a term from a glossary deletes the link.

ShopSphere use

The data steward owns a glossary term "Customer Government ID". Linking it to the Customer_SSN domain lets anyone reading the glossary jump to how that data is masked in test. This is our illustration of a use the guide describes in general terms.

Policy management: create, copy, edit, delete

You can create a policy before or after you define rules and domains, and add domains later. A copy contains the rules and domains of the original, and a policy can be exported to XML and imported elsewhere (p.83).

Task: create the ShopSphere customer-data policy

Goal: one policy holding the domains your project will mask. Steps are from the guide (p.83); the policy and domain choices are ours.

  1. In the Policies view, click Actions > New > Policy.

    The New Policy dialog box appears.

  2. Enter a name and optional description, click Next.

    For example ShopSphere_Customer_PII, "Personal data in customer tables". A clear name matters because projects choose policies by name.

  3. Click Add Data Domains and select domains from the list.

    Choose First Name, Last Name, Email Address, Phone, Social Security Number, Birth Date and ZIP from the PII pack, plus your own Customer_SSN domain if you made one.

  4. Click Finish.

    The policy appears in the Policies view. Select it and look at its Data Domains tab to confirm the list.

Show a worked answer

You should see one policy with about eight domains. If you add the same pack domain and your own custom SSN domain, both will compete for ssn; decide which one you want and remove the other, or mark clear default rules. That judgement call is yours (not covered by the guide).

  • Copy a policy: in Policies, click the policy description (do not open it), Actions > Duplicate, change name and description, Save (p.84).
  • Edit a policy: click the name, Actions > Edit; change name, description or status; on the Data Domains tab click Add, select, OK, then Save. Deleting a domain that has rule assignments shows Impacted Objects, with Export for a CSV and Continue to proceed. Regenerate and run affected plans afterwards (p.84).
  • Delete a policy: open it, Actions > Delete, confirm. The domains and rules inside are not deleted, but all assignments made through the policy are. If assignments exist you see Impacted Objects; Export, then Continue (pp.84-85).

11.14 Common mistakes and gotchas

Watch out
  • Opening a project when you meant to select it. For Copy and Delete, select the row by clicking its Description or Created On column and do not open it (pp.56-57).
  • Expecting a project copy to contain the tables. Copy does not import metadata or objects (p.56).
  • Setting log directories that do not exist. TDM will not create them, and a wrong workflow log directory makes the workflow fail without an error log (p.59).
  • Changing a policy, domain or rule and forgetting to regenerate the plan. The guide repeats "generate and run the plan again" after every such change.
  • Importing a project before its policies. Import global components first (p.59).
  • Importing a Model repository data domain and expecting patterns. Patterns and preferred rules do not come across (p.81).
  • Using a connection parameter for a staging connection. Not allowed, so batch updates for in-place masking are unavailable with connection parameters (p.52).
  • Assuming Search finds connections. It does not (p.39).
  • Treating a policy pack as complete. Check that columns like tax_id are covered.

11.15 Recap

Key points
  • Test Data Manager has seven views: Overview, Policies, Data Sets, Projects, Monitor, Parameters and Administrator, with search, quick links, preferences, an Actions menu, a data filter and an Expression Builder on top.
  • You log in with an Informatica domain user at http(s)://host:port/tdm/; the guide's defaults are ports 6643 (TLS) and 6605.
  • A project holds data sources, entities, groups, parameters, plans, policy and rule assignments and profiles, and has six views including Permissions.
  • Create a project with Actions > New; copy it without its metadata; export and import it as XML after importing global components.
  • Import metadata with Actions > Import Metadata from PowerCenter, the Model repository or a database; importing does not copy rows.
  • Permissions are Read, Write and Execute, and each task also needs a minimum privilege.
  • A policy is a set of data domains; a domain finds columns by data patterns and metadata patterns (regular expressions) and carries preferred masking and generation rules, one marked default.
  • PII, PHI and PCI policy packs come ready-made.
