11.10 Managing projects

When you create a project you become its owner and have access to its folder by default. You can edit its name, description, folder location and associated sources, and the place where its logs are stored (User Guide 10.5.10, p.53). You can also export a project, with its components, to an XML file and import it elsewhere. People do this to back a project up or to move it from a development system to a production system.

Creating a project

Task: create the "Customer Orders" project

Goal: make an empty workspace for the ShopSphere work. The steps and field list are from the guide (pp.53-54). The project name and values we choose are illustrative.

  1. Click Projects.

    The Projects view lists existing projects. Always check here first that a project for this job does not already exist.

    A list of projects appears.

  2. Click Actions > New.

    This opens the Create Project dialog.

  3. Fill in the properties.

    Use the table below. For ShopSphere: Name CustomerOrders (no spaces, which the guide requires if you will use Hadoop sources), a short description, keep the default Folder (the project name), and keep the default Target Conflict Resolution Strategy (Rename) unless your team says otherwise.

  4. Click OK.

    The project opens in a new page.

Editing a project

  1. Click Projects and click the project name.

    It opens in its own tab, with properties and data sources.

  2. Click Edit, change options, click Save.

    You can change name, description, folder, owner, target conflict resolution strategy and target empty value (the PowerCenter Repository field is not in the edit list). You cannot remove a source that entities or groups in the project use. (pp.54-55)

Project default property configuration

An administrator with the Manage Preferences privilege can add extra default fields to every project of the same Test Data Manager Service. They appear on the project creation page. You find this on the Project Configuration tab of Administrator > Preferences (p.55). The guide gives two examples.

Default fieldWhat it does
Enable Old Dictionary Optimization (True or False)Version 10.5 uses a newer algorithm for optimising dictionary use in substitution masking. Set True in a project where you used the optimisation before and want the same masked output as the old algorithm gave. Set False, or leave unset, to use the new one (pp.55-56).
Target Empty ValueAdds the field for a replacement value used where source empty strings would break a non-null target column. The guide's scenarios: resetting a data set made on an Oracle test data warehouse to a Microsoft SQL Server database, or source characters the PowerCenter Integration Service cannot process (they become nulls). The workflow still fails if the target column is also unique (p.56).

Copying and deleting a project

  1. To copy: in Projects, click a project description to select it without opening it, then Actions > Duplicate. Edit the name and description in the Copy dialog and click Save.

    Test Data Manager copies the project but does not import the metadata or objects of the project (p.56). So a copy starts as an empty shell with the same settings.

  2. To delete: in Projects, select the project by clicking its Description or Created On column (do not open it), then Actions > Delete, then Yes in Confirm Delete.

    All sources associated with the project are deleted (p.57). The guide says nothing about an undo.

Exporting and importing a project

An exported project is an XML file containing source information, connections, constraints, data domains and assignments (p.59).

  1. Export: Projects, click a project, Actions > Export, choose the XML file name and path, OK.
  2. Import: Projects, Actions > Import, browse for the XML file, click Finish.

    Before importing, import all the global components that the project assigns (policies, domains and rules; see the policies section). Otherwise the project refers to objects the target repository does not have (p.59).

    Test Data Manager imports the project.

Real-world use

ShopSphere has a development TDM and a production-like TDM. The engineer builds and checks the project in development, exports it to XML, imports the global policy first in the other system, then imports the project. This is the "move from development to production" case the guide names (p.53). The two-system setup is our illustration.
