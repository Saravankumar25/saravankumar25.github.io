7.4 The data patterns on the map

There are five data patterns: boundary conditions, sequential, random, edge cases and null. They are not a separate classification. They are ways of shaping values, and each one serves one or more of the purposes in 7.3.3. the GenRocket data patterns chapter shows them in GenRocket; here we place them on the map.

Worked example: one rule, five patterns

Rule: "a customer must be at least 18 years old on the day of registration". Today, in the test, is 2026-10-23. Here is the same date_of_birth column shaped five ways.

Example date_of_birth values for the 18+ rule (example data)
PatternValuesExpected application result
Boundary2008-10-24 (17 years, 364 days), 2008-10-23 (exactly 18), 2008-10-22 (18 years, 1 day)Reject, accept, accept

Notice the boundary row. A boundary test needs three values per limit: just inside, on, and just outside. Many bugs are off-by-one mistakes (using "greater than" where "greater than or equal" was meant), and only the exact boundary value catches them. Random data hits the exact boundary almost never. That is the main reason boundary data must be designed, not left to chance.

7.5 What synthetic data is

Concept. Synthetic data is data created by a program following rules you set. No row in it was ever a real person's record.

Simple explanation. A film set looks like a street, but nobody lives in the houses. Synthetic data looks like customers, but no customer exists. It is built to be good enough to exercise the application, not to copy reality.

The analogy stops at one point: synthetic data must look right from every angle the application views it, with foreign keys that join, dates in order and totals that add up.

What the tools say.

  • GenRocket: "Synthetic Test Data" is data manufactured or generated by an algorithm rather than real-world events. Its stated benefit is that companies can maximise test coverage by testing all permutations and combinations. From docs Why Synthetic Test Data? ↗
  • Informatica: data generation creates realistic test data for test environments, using generation rules that hold the logic. You import the metadata (table and column definitions) so the tool knows which columns to fill, assign rules to columns, then create a plan and run it (User Guide 10.5.10, p.190). From docs

Both tools need only the shape of the target (the metadata) and a rule for each column, never a real customer.

A real-world example from the Informatica guide

The guide's own example is an airline that sells plane tickets. Rules load dictionary values such as names into the customer tables, create random number strings for ticket numbers, create a numeric sequence for identification numbers, and use a reference lookup for values such as airport codes (User Guide 10.5.10, p.191). From docs For ShopSphere: a name dictionary for first_name, a sequence for customer_id, and a lookup of valid product_code values.

7.6 Synthetic data versus masked production data

Neither is "better". They solve different problems, and mature teams use both. The table compares them on the dimensions that matter. The ratings are general experience, so each column heading carries the "General concept" badge rather than a product claim. General concept

QuestionMasked production dataSynthetic data
RealismHigh. Real shapes, real mess, real correlations between columnsAs good as your rules. Looks real only for the properties you modelled
Coverage of rare or future casesOnly cases that already happened in productionAny case you can describe, including ones that never happened, and boundary or invalid values on demand
PrivacyDepends on masking quality. Weak masking, or unmasked columns, can still identify peopleNo real person behind any row, so there is nothing to re-identify
Setup effortDiscovery, masking rules, consistency checksModelling the tables, writing rules for each column and relationship
Cost to refreshRe-run extract and mask, which grows with production sizeRe-run the generator; speed depends on the rows asked for, not on production size

DistributionsReal distributions come freeYou must state them (for example 20% of customers with no orders)
RepeatabilitySame snapshot until refreshedSame output every run if you use a seed

Main riskA leaked or unmasked columnA model that is too tidy and misses real-world mess

GenRocket's SDR page makes one claim worth noticing, which is the vendor's view: synthetic data "can produce edge cases that do not currently exist in production" and "can yield more accurate data patterns than exist in production". From docs That is a statement about coverage, and it is true for any generator that supports designed edge cases. It does not mean synthetic data is automatically more realistic than production, which it is not.

7.6.1 Which one should you choose?

  1. Is a realistic mix of messy data essential, such as for a new analytics report or a migration rehearsal?

    Lean towards masked production, because the real mess is the thing being tested.

    Result: use the subsetting and masking techniques from the subsetting and masking concept chapters.

  2. Is the system new, so there is no production data yet, or are you testing a feature with no history?

    Generate. There is nothing to copy.

    Result: use rules from this chapter.

  3. Do you need exact boundary, negative or very large data sets?

    Generate. Production rarely holds the 51st item in an order or a customer aged exactly 18 today.

  4. Do you need both realism and designed edge cases?

    Use a hybrid: masked subset as the base, generated rows added on top, with generated keys chosen so they never clash with the real ones.

Generated is not the same as safe by default

If a generator copies a real value (for example, picks names from an unmasked production table as its dictionary) the result is no longer purely synthetic. Always check where a generator's source list came from. Dictionaries should be made-up or public lists, never an export of real customers.
