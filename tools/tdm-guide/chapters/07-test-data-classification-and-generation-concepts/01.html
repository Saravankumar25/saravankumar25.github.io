So far you have met two ways to get test data. You can copy and cut down real data (the discovery and subsetting concepts chapter) and then hide the sensitive parts (the masking concepts chapter). This chapter introduces the third way: make the data up, on purpose, from rules. Before we do that we need a better question than "where do I get data?". The better question is: what is this data for?

A tester checking the login screen does not need "a lot of customers". She needs one normal customer, one customer whose account is locked, one with a very long surname, one with no phone number, and one whose date of birth makes them exactly 18 today. Each of those rows has a different job. Naming the jobs is called classifying test data, and it is the starting point for designing any data set, whether you copy it, mask it or generate it.

This chapter is also where the course syllabus phrase "Model, Design, Deploy, Manage" first appears, and where the five "data patterns" of the syllabus (boundary conditions, sequential, random, edge cases, null) are placed on a map. The tool chapters later (the Informatica data generation chapter and the GenRocket chapters) assume you have read this one.

7.1 Words to know first

Test data
Any data the application is fed or finds waiting in its database during a test. It includes both the rows in the database and the values typed into screens or sent in files.
Test condition
One specific situation a test wants to check, such as "customer with no phone number" or "order with the maximum number of items". Each condition needs data that creates it.
Positive (valid) data
Data the application should accept and process normally.
Negative (invalid) data
Data the application should reject or handle gracefully, such as letters in a phone number.
Boundary value
A value sitting exactly on the edge of what is allowed. If customers must be 18 or older, the boundary values are 17, 18 and 19 years.
Edge case
A rare or unusual situation outside normal use, such as a surname containing an apostrophe. GenRocket describes it as a rare or unexpected scenario outside the typical usage pattern.
Synthetic data
Data made by a program following rules, instead of being taken from real events. GenRocket's help centre puts it as data manufactured by an algorithm rather than real-world events.
Generator
The small piece of logic that produces the values for one column, for example "count up from 1" or "pick a name from a list".
Seed
A starting number given to a random generator. The same seed gives the same "random" values every time, so a test data set can be rebuilt exactly.
Distribution
How values are spread: for example, 20% of customers have no orders, 40% have one. Real data is lumpy, and good test data copies the lumps that matter.
Referential integrity
The promise that every foreign key points at a row that exists. An order whose customer_id has no matching customer breaks it. See the data basics chapter.
Parent table / child table
The table being pointed at (CUSTOMERS) is the parent; the table holding the foreign key (ORDERS) is the child.
Coverage matrix
A grid that lists test conditions against the data that covers them, so you can see gaps at a glance.

7.2 Why classify test data at all?

General concept Imagine a kitchen preparing for a cooking class. The chef does not just buy "food". She buys the exact ingredients each recipe needs, in the amounts each recipe needs, and she keeps the allergy-sensitive items (nuts) in a separate, labelled place. Test data works the same way. You prepare the exact rows each test needs, and you keep the dangerous ones (real personal data) away from places they must not be.

The analogy stops being accurate in one place: a chef can taste the soup, but nobody can "see" whether a table of 5 million rows has the right mix. That is why we write the classification down, as a plan, before building anything.

Why it matters

Without classification, teams fall into two traps. Either they copy everything from production (huge, risky, and still missing the odd cases that have never happened yet), or they hand-type five "happy path" rows and discover the bugs in production. Classification gives you a short list of questions to ask for any data request: where does it come from, how sensitive is it, and what must it prove?

7.3 Three ways to classify test data

You can sort the same piece of data along three independent lines. A single customer row can be "masked production" by source, "restricted until masked" by sensitivity, and "boundary" by purpose. Keep the three lines separate in your head and in your documents.

7.3.1 By source

The source is how the data came to exist. The syllabus groups tool capabilities exactly along this line: subsetting and masking work on production-derived data, while generation makes new data.

Source classHow it is madeTypical riskWhere this guide covers it
Production copy (raw) Straight copy of the real database Exposes real personal data; not allowed in test for regulated data Why TDM exists
Production subset A cut-down, consistent slice of production Still real data until masked the discovery and subsetting concepts chapter
Masked production Production (or a subset) with sensitive values replaced Weak masking can leak; masking must stay consistent across tables the masking concepts chapter
Synthetic (generated) Created from rules, no real person behind any row May not look like the messy real world unless the rules are good This chapter
Hand-crafted A person types or edits specific rows Slow, hard to repeat, tiny volume This chapter
Hybrid Masked or queried production plus generated rows added Needs a clear plan for which part comes from where Section 7.6

Hybrid is more than a theory. GenRocket's FAQ says it can query existing production data and merge it with synthetically generated data, and its G-Subset overview lists "test data augmentation" (adding a richer set of data to the destination) as one of its usage options. 7.3.2 By sensitivity

Sensitivity is how much harm follows if the data leaks. the sensitive data and regulations chapter covers PII, PHI and the regulations in depth. For classification purposes you only need a simple ladder. The labels differ between companies; the ladder below is a common shape, not a standard.

LevelMeaningShopSphere exampleAllowed in test?
Public Harmless if seen by anyone PRODUCTS.product_name Yes
Internal Business data, not personal ORDERS.total_amount with no customer link Yes
Personal Identifies or relates to a person first_name, email, phone, zip_code Only masked or synthetic
Highly restricted Identifiers regulators care most about ssn, tax_id, date_of_birth Only masked or synthetic, and strongly protected

Informatica's own introduction frames the same idea: you identify sensitive information in large volumes of production data, and its profiles can compare data against compliance standards, naming PII, PCI and PHI as examples (User Guide 10.5.10, p.24). From docs The key point for classification is simple: sensitivity decides what you are allowed to do to the data; source and purpose decide what you do with it. Synthetic data has no real person behind it, which is why it needs no masking step.

7.3.3 By purpose

This is the line testers care about most. Each purpose answers "what must this row prove?". There are seven that cover almost every request.

PurposeWhat it provesShopSphere example
Positive / valid The normal path works Asha Menon, 560001, valid email, two orders
Negative / invalid Bad input is rejected with a clear message Phone 98765abcde; email with no @
Boundary The edges of each rule behave exactly right Customer aged 17, 18 and 19; surname of 1 and of the maximum length
Edge case Rare or odd but legal situations Surname O'Brien, hyphenated name, name with leading spaces, order with 50 items
Null / empty Missing values do not crash anything No phone; empty zip_code; customer with zero orders
Volume / performance The system copes with realistic size 2 million customers, 10 million orders
Security Hostile input is blocked Name field containing '; DROP TABLE ORDERS;--
Negative data usually does not live in the table

A database column with a 10-digit phone constraint will refuse 98765abcde when you try to load it. Negative and security data are normally sent in through the screen, the API or an input file, not inserted straight into the table. Only load invalid values into a table if the table has no constraint and the test is about how the application reads bad stored data (for example a legacy table).
