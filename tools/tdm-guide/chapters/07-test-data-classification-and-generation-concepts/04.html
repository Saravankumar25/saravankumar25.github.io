7.9 The lifecycle: Model, Design, Deploy, Manage

The syllabus for Day 46 says "Data generation: model, design, deploy, manage". That is GenRocket's own phrase: its help centre states that GenRocket uses a "Model, Design, Deploy, Manage" methodology and explains it in a video that I could not watch, so the page text is all I can report. Evidence for the pieces. GenRocket's General FAQ says it assigns the more complex test data tasks to a small group of trained "Test Data Engineers" who model test data projects and design the data (the FAQ's examples are integration, load and negative data), while testers and developers only need to learn how to search for the data they need, integrate or deploy it into their test environment, and modify it with a questionnaire tool. GenRocket also names five building blocks that the phases work on. The reference table on its "Five Key Components" page reads like this in my words: a domain is a noun such as a table or file; an attribute is a characteristic of a domain, such as a column; a generator produces the values for an attribute; a receiver turns generated data into a usable format such as SQL, CSV or JSON; and a scenario holds the instructions for what to generate and how much. Where Informatica fits on the same cycle

Informatica's task flow has the same shape: import metadata into a project (model), create generation rules and assign them to columns (design), create a plan, generate a workflow and run it (deploy), then watch it in the Monitor view (User Guide 10.5.10, p.192). 7.10 Worked example: 50 ShopSphere customers and their orders

The request. The QA team testing ShopSphere's Customer Orders app asks the TDM engineer for a new data set in a QA database: 50 customers, with orders and items, covering the registration rules, the order history page and a customer-search feature. No production data may be used. We follow Model, Design and Deploy; Manage is covered by the lab at the end.

7.10.1 Model

The tables are the ShopSphere tables from the data basics chapter. The relationships are the only thing the generator needs to respect: ORDERS.customer_id points at CUSTOMERS, ORDER_ITEMS.order_id points at ORDERS, and ORDER_ITEMS.product_code points at PRODUCTS. PRODUCTS is a small reference table of four rows that we load by hand (P-100 Laptop Stand, P-200 USB Cable, P-300 Phone Case, P-400 Desk Lamp), because it is better to control the catalogue than to invent products.

These business rules are invented for this example. They are what the test conditions will aim at: customers must be 18 or older; first and last names are at most 30 characters; phone is 10 digits when present; zip code is 6 digits when present; email is optional; each order has between 1 and 4 items.

7.10.4 Deploy and verify

After the run, check three things before you hand the data over. These SQL checks are what I ran against my generated rows in SQLite; the syntax works on most databases.

-- 1. No orphan orders (expected: 0)
SELECT COUNT(*) FROM orders o
LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL;

-- 2. The orders-per-customer distribution matches the design
SELECT n AS orders_per_customer, COUNT(*) AS customers
FROM (SELECT c.customer_id, COUNT(o.order_id) AS n
      FROM customers c
      LEFT JOIN orders o ON o.customer_id = c.customer_id
      GROUP BY c.customer_id) t
GROUP BY n ORDER BY n;

-- 3. The null and empty rows really exist (expected: 2, 1, 1, 1)
SELECT SUM(CASE WHEN phone IS NULL THEN 1 ELSE 0 END)    AS null_phone,
       SUM(CASE WHEN email IS NULL THEN 1 ELSE 0 END)    AS null_email,
       SUM(CASE WHEN zip_code = '' THEN 1 ELSE 0 END)    AS empty_zip,
       SUM(CASE WHEN tax_id IS NULL THEN 1 ELSE 0 END)   AS null_tax_id
FROM customers;

Expected result: check 1 returns 0. Check 2 returns four rows: (0, 10), (1, 20), (2, 15), (5, 5); I got exactly this from the snippet in 7.7.2. Check 3 returns 2, 1, 1, 1 once the null and empty overrides from the design table are applied. The snippet in 7.7.2 generates only the typical shape, so I did not run check 3 against it; it is a template for you to run on a real design.

7.11 Test data as a service

Concept. "Test data as a service" means test data is something teams can ask for and receive, like a ticket to a service desk, instead of something each team builds in secret. A small group owns the know-how and the rules; many teams consume the results. General concept The phrase itself does not appear in the documentation pages I read, so I use it as a label for what the three tools describe in their own words.

Why it matters. Without it, every team writes its own scripts, nobody can reproduce another team's data and the same sensitive columns get masked ten different ways. With it, a request is a small form ("50 customers with orders, boundary included"), and the answer is a catalogued, repeatable data set.

7.13 Common mistakes and gotchas

Mistakes beginners make
  • Generating children before parents. The foreign keys then point at nothing. Always parents first, or have the child rule read from the finished parent table.
  • All-random data and no designed edges. Random values almost never hit an exact boundary, a null, or a name with an apostrophe. Put those rows in on purpose.
  • Not recording the seed. A failed test cannot be reproduced if the data cannot be rebuilt.
  • Requesting "about 10% null". In a 50-row data set that can come out as zero. Ask for an exact count.
  • Totals that do not add up. Derive total_amount from the items instead of generating it separately.
  • Loading invalid values into constrained columns. The load fails or the constraint is silently dropped. Keep negative data in the input channel.
  • Treating synthetic as automatically realistic. It only mirrors what you modelled. Compare a few generated distributions against real, masked, aggregated figures.
  • Reusing real values as the "dictionary". A name list exported from production defeats the purpose.

7.14 Recap

Recap
  • Classify test data along three lines: source (production-derived or synthetic), sensitivity (what harm a leak causes) and purpose (what the row must prove).
  • The seven purposes are valid, invalid, boundary, edge case, null or empty, volume and security. The syllabus data patterns (boundary, sequential, random, edge cases, null) are ways of shaping values to serve them.
  • Synthetic data is created from rules. It gives privacy and designed coverage; masked production gives real-world mess. Hybrids use both.
  • Generation needs a target shape, a rule or generator per column, and run settings. A seed makes it repeatable and a distribution makes it realistic.
  • Generate parents first and make every foreign key copy an existing parent id; control how many children each parent gets.
  • GenRocket's cycle is Model, Design, Deploy, Manage. Test data as a service means requestable, catalogued, repeatable data owned by a small expert group.
  • A coverage matrix shows gaps before the testers find them.
