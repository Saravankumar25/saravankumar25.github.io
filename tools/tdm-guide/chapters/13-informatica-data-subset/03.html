The four data integrity options

The entity says how tables are connected. The data integrity option in the plan says how aggressively TDM follows those connections at run time. This lets you reuse one entity to produce different subsets. You choose it in the Advanced Settings area of the Plan Settings page when you create the plan; the field is called Data Integrity for Subset and its default is Transactional Integrity for Major Relation Type (User Guide 10.5.10, p.121, p.287) From docs.

Two terms first. Referential integrity means no child row points at a missing parent. Transactional integrity goes further: if a parent is in the subset, all of its children are too, so a business transaction (a customer with all their orders) is complete.

A wording puzzle in the guide

The One-way description (p.123, repeated in the plan settings table on p.287) says One-way returns more data than Two-way, and in the same breath recommends it for "the smallest required subset that does not break referential integrity". Those two statements only fit together if "smallest" means "smallest among the ways that keep every row of the tables above the filtered table". When size matters, run a trial plan and count rows rather than trust the labels.

Which option for ShopSphere?

  • One criterion on CUSTOMERS, want complete customer histories: keep the default Transactional option. Every order and line of a selected customer comes along.
  • Same criterion, want the smallest consistent database for a quick smoke test: Referential Integrity Only. You may get a customer with only some of their orders. For a test that checks "order total equals sum of lines" that is fine; for one that counts "all orders for this customer" it is not.
  • Criteria on both CUSTOMERS and ORDERS (for example zip code and order value): consider Two-way so that both tables end up with data, or edit the criteria to OR (see the table).

These are my suggestions built on the guide's descriptions, General concept. Always verify on a trial run.

Optimizing relations

Because every relationship starts as major (p.119), a subset can pick up more rows than you need. Optimize Relations asks TDM to analyse the entity and propose which relationships can be minor while still reaching every table. The guide's procedure (User Guide 10.5.10, p.119 to 120) From docs:

  1. Make sure the entity already has a criterion.

    TDM raises an error if you optimize an entity with no criteria at entity level (p.119).

  2. Open the entity and click Actions > Optimize Relations.

    TDM analyses the constraints. The Optimize Relationships page lists each parent and child with the current and the proposed type.

  3. Optional: Download Optimizations.

    Saves the proposal as a CSV so you can review it with a colleague.

  4. Click Optimize to accept all proposals.

    You cannot accept some and reject others (the guide says results cannot be applied selectively). A list of plans that include the entity appears; regenerate and rerun them.

  5. Click Continue.

    The entity is updated. You can still edit single constraints by hand afterwards.

You can also optimize at run time in the plan (the "Optimize Relationship Type for Entities" setting, p.283). That changes the run, not the saved entity, and it also requires criteria at the plan level (p.283). When you choose Two-way or One-way integrity, optimization is ignored (p.122 to 123).

Disabling and enabling relationships

Sometimes you do not want TDM to follow a link at all, for example a link to a huge audit table. In the Entity Map or the Relationships view you can disable a relationship (p.120) From docs. In the map, choose to view all relationships and show excluded tables; enabled links are solid, disabled links are dotted. Click the link, then Disable Relationship or Enable Relationship. If a table loses every link to the entity this way, it is excluded from the subset database (p.115). If you still want its data, put it in a group.

When constraints change after you built the entity

Entities do not update themselves. If you add a constraint after building the entity, the entity list marks it as having a change impact. Open it, click Review Changes, accept the relationship changes you want, then use Actions > Mark Changes Review as Complete so the notice goes away (p.120 to 121) From docs. The guide's figure on p.121 shows a dialog with Added, Changed and Deleted groups and an Accepted action.

13.7 Choosing rows: criteria, operators, parameters and limits

Entity filter criteria and operators

You met entity criteria while creating an entity (13.4). A criterion is: a column, an attribute (Value or Parameter), an operator, and the value or parameter. The guide's examples use "greater than", "equals" and "IN" (p.118, p.119, p.127). The excerpt I had does not print the full list of operators in the drop-down, so do not assume more than those three; look at your own dialog.

ShopSphere examples (illustrative)
  • customer_id <= 1002: keeps the first two customers. Easy to predict, good for a lab.
  • zip_code = '560001': keeps all customers in one postal area, a "region" subset like the guide's financial-data-for-one-region example.
  • customer_id > $$CRITERIAVALUE: the same, but the number comes from a parameter (next section).

Subset with parameters

Typing the value into the entity means editing the entity every time the requirement changes. A criteria parameter lets you change the value when you run the workflow. The guide (User Guide 10.5.10, p.113, p.118, p.57) From docs says:

  • Create criteria parameters in the project (Projects, open the project, Parameters tab, Add) or use global parameters an administrator created. Global ones show an asterisk (*) in lists, and you can import one into the project first (p.57 to 58).
  • Parameter types are criteria, connection and owner. Criteria parameter names begin with $$, connection ones with $DBConnection, owner ones with $Param. Data types are String, Numeric or Date. For a Date parameter you enter an expression that says how it is used, for example TO_DATE($$CRIT1,'MM-DD-YYYY') (p.57).
  • You choose a default value and whether overriding is allowed. If you do not allow override, you cannot change the value when you run the workflow (p.57).
  • Values can live in the project or in an external parameter file. The guide's example: a parameter CRITERIAVALUE, a parameter file line $$CRITERIAVALUE=100, and an entity criterion EMPID > CRITERIAVALUE. To get EMPID greater than 500, change the file to 500 and run the same workflow (p.118).
  • For a string or date parameter on a relational source, put the value in single quotes in the parameter file (p.118).

Ignore flags. If you keep values in a parameter file you create yourself, add a flag for each criteria parameter, for example $$CRITERIAVALUE_IGNORE. "N" means use the criterion, "Y" means the workflow skips it. A file created from Test Data Manager already contains the flags, set to "N" (p.118, p.309 to 310).

To make the plan accept parameter values, tick Treat the subset criteria as a variable in the plan's connection options and give the parameter file name and path (p.279) From docs. At run time, in the Execute Workflow window, you choose where values come from (p.310 to 311): the default file named in the plan settings, a parameter file you browse to, or Add Parameter Values from the project. Criteria parameters do not appear in that list by default: click Select Parameter and add them, because "a workflow does not include parameters that do not appear in the list" (p.311).

Two silent ways to get the wrong subset

(1) You forget to select the criteria parameter in the Execute Workflow window, so the criterion is not included. (2) You edit a parameter that was created without "allow override": the change does not take effect and the workflow uses the default value and logs an error (p.311). Check the workflow log if the row counts look wrong.

Database functions in entity criteria

You may want a date rule such as "hired in the last three months". The guide (p.118 to 119) From docs warns that writing a database function directly in the criterion makes workflow generation fail, because TDM does not recognise it as a function and cannot pass it on. The documented workaround: choose the operator IN and write a SELECT query in the Value field, for example select HIREDATE from <table> where HIREDATE > add_months(current_date, -3). TDM then passes the query to the database. The ShopSphere version of this idea would be a query on ORDERS.order_date.

Filtering again inside the plan

You can also set criteria in the plan itself without editing the entity (User Guide 10.5.10, p.294, p.304) From docs. In the plan's component list you pick a subset component, then a column in the Criteria panel. TDM shows existing criteria, which you can change or add to. You then choose a method:

MethodOptionWhat it does
CustomBasicA simple expression with an operator and an operand. You can use parameters.
CustomAdvancedAn expression typed in the Expression Editor. It can use several columns, functions and parameters, including global ones (a global parameter inside an expression is written without the asterisk).
Limit(a limit type)Limit the subset result by percentage, by absolute value or by an interval of rows to write to the target.

The plan creation steps put it like this: "To limit the subset results, click Limit and choose to limit by percentage, by absolute value, or by defining an interval of rows to create" (p.304). You cannot override the subset criteria of an XSD component in the plan (p.304).

What the guide does not tell you about Limit

The excerpt I had names the three limit types and nothing more. It does not say which table the percentage applies to, how rows are chosen (first N, random?), what the "interval" arithmetic is (every Nth row? a range?), or how a Limit interacts with parent-child pulling. So I describe the three types by their names only: percentage means a share of rows, absolute value means a fixed row count, interval means "a set of rows defined by an interval". Test on a small table and count the result before relying on it. The guide also says Two-way and One-way integrity are not available when a plan uses custom Advanced or Limit criteria (p.123).

  • Percentage: for example 10 percent. Natural fit for the ShopSphere goal, but check how TDM applies it to related tables.
  • Absolute value: for example 500 rows. Handy when the test environment has a hard size cap.
  • Interval: a defined interval of rows. The guide gives no example.

Syllabus link: Day 44 "types of subset". In practice, the guide supports these ways of choosing rows: by condition (entity criteria and plan Basic/Advanced criteria), by parameterised condition, and by quantity (Limit). I label this grouping as my own summary, General concept, not a list taken from the guide.

Subset and masking in one plan

A plan can hold both subset components and masking components. The guide says the subset component gets priority: TDM does the subset first, then applies masking rules to the columns of the subset data. Masking is not applied to source data that is outside the subset, "even if the data is part of a cascade" (User Guide 10.5.10, p.275) From docs. You can also keep them in separate plans (p.304). the Informatica masking chapter covers the masking half.
