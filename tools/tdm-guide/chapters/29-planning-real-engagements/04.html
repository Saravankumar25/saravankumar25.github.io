29.11 The deployment plan

A deployment plan turns a successful POC into a repeatable service. It names phases, the condition for entering and leaving each one, and who owns it.

PhaseMain activitiesExit condition
P0 MobiliseApprove scope and success criteria; accounts and approvals; baseline KPIs measuredSigned charter and baseline
P1 PrepareSize and install the tool; network routes; masking database users with only needed rights; backup and restore testedSmoke test: connect, profile one table
P2 ConfigureConnectors, rule sets, profiling, inventory review, algorithms, keys or seeds, roles; for Informatica, policies, projects and plansInventory approved by the data steward
P3 Pilot the LOBRun the full LOB in one environment; verify with the POC criteriaEvidence pack accepted
P4 Roll outRemaining environments and files; schedule jobs; connect to the refresh process; train usersSign-off checklist complete
P5 OperateMonitor jobs, re-profile on releases, report KPIs, review risksQuarterly review

Some tool features support promotion. Delphix lets you export an environment, with its connectors, rule sets and jobs, and import it into another masking engine; the docs say moving environments between engines is the main reason (Managing environments). It also offers an inventory approval workflow that makes an approver sign off a database inventory before any masking job can run. Informatica generates a workflow from a plan and runs it (User Guide 10.5.10, p.32). Use these to move work from the pilot to production setups without re-typing it.

The refresh runbook

The safest ordering is: copy into a closed area, mask, verify, and only then open the copy to testers. Nobody sees unmasked data at any point. Delphix's masked provisioning enforces a version of this for supported databases by masking during VDB provisioning (see Provision masked VDBs).

The generation (TDG) deployment plan

For generation the same phases apply with different content. GenRocket describes a hybrid design: modelling and design happen in the cloud component, and the data itself is generated locally in the on-premises component (GenRocket architecture). Its five components are domain, attribute, generator, receiver and scenario (five key components).

StepFor ShopSphere
ModelDomains for CUSTOMERS, ORDERS, ORDER_ITEMS, PRODUCTS; attributes per column; parent-child links
DesignA generator per attribute, scenarios for UC3 to UC5, volumes (5 million orders), boundary and null cases (see the data patterns chapter)
DeployRuntime on the generation machine, a receiver that loads the QA database or writes files, access to the target
ManageVersion the scenarios, rerun on schema change, track generation time and test coverage gained
