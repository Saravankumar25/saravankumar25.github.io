1.1 Words to know first

Only a handful of terms are needed on this page. Each one is explained properly in the chapter named next to it.

Test data
The data you put into an application so you can check that it works. Think of the customers, orders and products you type in while testing an online shop. (the why-TDM chapter)
Production
The live system real customers use, holding real data. Also called "prod". (the why-TDM chapter)
Non-production environment
Any copy of the application that is not live: development, QA, UAT, staging. Testing happens here. (the why-TDM chapter)
TDM
Test Data Management: the planning, tools and habits used to give testers safe, realistic, right-sized data when they need it. (the why-TDM chapter)
Masking
Replacing real sensitive values (a real name, a real ID number) with realistic but fake ones. (the masking concepts chapter)
Subsetting
Taking a small, consistent slice of a big database instead of all of it. (the discovery and subsetting concepts chapter)
Synthetic data
Data created by a program from rules, not copied from real people. (the classification and generation concepts chapter)
Lab
A guided hands-on exercise inside a chapter, with a worked answer you can reveal.
Syllabus
The day-by-day list of topics in the programme. This guide does not change it; it only maps it to chapters.

1.3 What TDM is, in one paragraph

Test Data Management is the discipline of getting the right data to the people who test software, at the right time, without exposing anyone's private information. Testers need data that looks and behaves like real data. The easy way to get it is to copy the live database, but that copy contains real people's names, phone numbers and ID numbers, it is huge, and it goes stale. So TDM teams find the sensitive values (discovery), cut the data down to a usable size (subsetting), replace sensitive values with fake ones (masking), create brand-new data from rules where no real data fits (generation), and deliver fresh copies on request (provisioning). the why-TDM chapter explains each of these properly, starting from why testing needs data at all.

General concept

The Informatica documentation frames the same idea from the tool side: an organisation creates a smaller copy of production data, masks the sensitive data, finds the sensitive columns, and can create test data that never contained sensitive values (Informatica TDM 10.5.10 User Guide, p.21).

Why three tools and not one?

The syllabus does not explain this, so here is an honest answer in two parts.

  1. The programme's choice. Which tools are taught is decided by the programme and the organisation behind it. If you want the business reason, ask your trainer.
  2. What you gain from seeing three. From reading the three documentation sets, each product puts its weight in a different place. Informatica presents discovery, subset, masking and generation together in one client. GenRocket is built around generating data from scratch. Delphix is built around masking plus fast delivery of copies. Seeing the same ideas in three products teaches you the idea, not a menu. A TDM engineer who knows what masking is can pick up a fourth tool quickly.
General concept The second part is my reading of the documentation, not a statement from any vendor.
Why this matters

Beginners often learn "click here, then here" for one tool and are lost when the project uses another. This guide teaches the concept first (Part I), then shows each tool as one way to carry out that concept. When two tools do the same job you will see the same concept page referenced from both.
