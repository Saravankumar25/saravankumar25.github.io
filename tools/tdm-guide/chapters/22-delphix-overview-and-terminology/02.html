22.4.1 The grid: the control you use everywhere

Domains, classifiers, profile sets, roles, inventories and rule sets all use one table component, which the GUI page calls the Grid UI. Learn its few controls once. From docs

  • Sorting. Hover a column name. If a star icon appears, the column can be sorted. Click to sort, click again to reverse. An arrow shows the direction. In a grouped grid, sorting happens inside each group.
  • Filtering. Hover a header and click the three-lines icon, then the filter tab. Five filter kinds exist: text ("contains"), number (equals, greater than and so on), single-select list, multi-select list and date range. Applied filters appear as chips above the grid; the Reset button clears them. Filters persist in the browser cache until you reset them or clear the cache. A few screens (the page names Monitoring a Single Job) do not show chips or persist filters.
  • Pinning and sizing columns, and showing more columns. The same header menu offers Pin Column, auto-size options, and a last tab to reveal columns that are hidden by default.
  • Actions. The "..." button at the end of a row lists what you can do to that row. An action you may not perform is shown disabled, not hidden.
  • Select all. The header checkbox selects or deselects every record.
  • Copy a cell. Select the cell and press Ctrl+C (or Command+C). The cell highlights when copied.

There is also a List Editor for algorithm settings: an edit icon opens a section where a plus icon adds items and a delete icon removes them, and Save or Cancel finishes. You will use it in the algorithms chapter.

22.4.3 A rule you will trip over: object names

The naming requirements page lists the objects you may name yourself: algorithm, application, connector, domain, environment, file format, job, profiling group, record type, role and rule set. For all of them, leading and trailing spaces are not allowed, and a long list of special characters is rejected, including brackets, braces, parentheses, ~ ! @ # $ % ^ * " ? : ; , / \ ` + = < > ' |. An attempt to create or rename an object with one of them fails with an error. The maximum name length varies by object; the page says to look it up in the engine's API client.

Name things safely from day one

Use letters, digits, underscores and hyphens. SHOPSPHERE_DEV and shopsphere-rules-v1 are fine. ShopSphere (Dev) #1 is not.

22.4.4 Monitor: Async Tasks and Job Executions

Many actions in the engine do not finish instantly. Saving a database rule set, exporting an environment, importing settings and adding logical keys all return an Async Task ID in a message at the bottom of the screen. You follow that task under Monitor. From docs

  1. Do the long action.

    For example, click Save on a database rule set.

    A status message appears in the bottom sheet with an Async Task ID.

  2. Open Monitor, then Async Tasks.

    The grid lists every asynchronous operation, newest first. Type the task ID into the search box under the "Task ID" header to find yours.

    A row for your task with its status.

  3. Act on the result.

    For a finished export, the row's Actions menu offers Download File. For a failed import or export, a Download File link gives you the log. A task that can be cancelled has a Cancel Task action.

The second Monitor page, Job Executions, is the history of job runs. The screenshot above shows its columns, and the three counters at the top (jobs queued, jobs running and memory usage). The job-running page adds that stopping a RUNNING job leaves semi-masked data, and that indexes, constraints or triggers the job dropped are not re-created. So cancelling a masking job is a recovery situation, not a harmless undo. A QUEUED job can be cancelled with no effect on the data source.

Do not cancel a running in-place job casually

Imagine ShopSphere's masking job has masked CUSTOMERS but not yet ORDERS when someone presses Cancel. The copy now holds half-masked data, and if the job had dropped any index, it is still gone. You would restore the VDB (see the VDB chapter) rather than try to repair it by hand.

22.4.5 Admin: application settings and the About page

Beyond Roles and Users (covered later in this chapter), the Admin menu has Application Settings. It is an administrator-only screen with two parts: a Login Screen Customization section (an image of at least 150 by 150 pixels, up to 1 MB, and a message of up to 255 characters shown on the login page) and a grid of engine settings, grouped by name. The page lists these groups: LDAP, General, Mask, ASDD, JOB, SMTP, engineSync, Async, Algorithm, FileUpload, Database and Profile settings. Two of them matter to you early. The default number of update threads and streams used by jobs come from the "mask" group, and the default for non-conformant data handling is also an application setting (Admin > Application Settings > Default Non-Conformant Data Handling, as the terminology page says).

To change a value you click the pencil icon in its row, type the new value (booleans offer a true and false list), click outside the field and then save or discard in the confirmation box. The page warns that these settings are not meant to be changed often and can strongly affect the application. As a TDM engineer you usually only read them.

The Admin menu also has Utilization, which generates PDF reports: a Jobs report (job executions for a chosen environment and date range) and a Database Size report that helps customers with usage-based pricing contracts. The database-size report supports only some databases (the page lists Oracle 12c and later, several SQL Server versions, PostgreSQL versions, and Sybase 16.0 and 15.7, with other data sources unavailable). The Logs and Users pages round out the menu.

22.4.6 Audit: who did what

The Audit tab shows a record of user actions taken in the UI or through the REST APIs: what happened, who did it and when. Only an admin can open it. Every column is filterable and sortable, and an Export PDF option at the top right downloads the log with the same filters and sort order. The page lists the kinds of action that are recorded (Create, Edit, Delete, Run, Test, Export, Import, Login, Logout and a few more) and the kinds of object they target (algorithm, application, connectors, environment, rule sets, domain and many others). For a compliance officer this is the evidence that a masking job really ran, and who ran it. From docs

22.5 The object model in plain words

This is the most important picture in the chapter. The engine stores a handful of kinds of objects, and almost every confusion is "where does X live?". The short answer is that work objects live inside an environment, and shared objects live in Settings.

22.5.1 The objects, one at a time

Here is each object, with the documentation's own definition in my words, and what it is in ShopSphere terms.

From docs One consequence the domains page spells out: because a domain has a single default algorithm, you need a distinct domain (with recognition logic) for each distinct algorithm if you want the profiler to assign that algorithm.

"Connector" means two different things in Delphix

The terminology page defines Connector as the data-source connection mechanism and, separately, a Delphix Connector as a service that runs on Windows staging and target hosts to let them talk to the Continuous Data engine. It warns that the two should not be confused. In this guide, "connector" always means the first one, the data-source connection you create inside a masking environment. A related word with a licence flavour is also defined: Standard, Select and Premium connectors differ by who builds them and whether you need a separate licence (see the connectors chapter).
