22.8 Where the engine runs: deployment options at overview level

As a TDM engineer you will rarely install the engine yourself, but you should know what shape it takes, because that decides who you ask when something is down. The documentation offers two families. From docs

Virtual machine image

The engine is a virtual appliance: a ready-made machine image you import into a hypervisor or cloud. The Installation page lists VMware, AWS EC2, Azure, Google Cloud Platform, IBM Cloud, Hyper-V and OCI (Oracle Cloud). A KVM installation page also exists in the documentation set.

The first-time-setup page describes the flow for VMware, AWS EC2, Azure or GCP: power on, open the console, set the network (hostname, DNS, a static address in CIDR form such as 192.168.1.2/24 or DHCP, and a gateway) using a system administrator login, then use the browser-based Setup Wizard.

Containerized

The same engine packaged as containers on Kubernetes. The containerized installation page says it behaves like the VM version with a few small exceptions, runs on any certified Kubernetes platform that supports an OCI-compliant runtime, and names OpenShift, MicroK8s, AWS EKS and AWS ECS with Fargate as explicitly tested.

It runs as a pod of three containers (delphix-masking-app, delphix-masking-database and delphix-masking-proxy) and can be deployed directly or with Helm. One documented limitation you will meet in the connector chapter: FTP and FTPS file connectors are disabled in containerized deployments.

22.8.1 What the Setup Wizard asks

I read the whole wizard description. In order, it covers: a Welcome page where you pick the engine type (choose Continuous Compliance for a masking engine), passwords and the three administrator roles (System, Compliance and Engine administrators), time, network, network security (certificates), storage, outbound connectivity (web proxy, phone home, usage analytics and the SMTP server used for job email), authentication (LDAP, SAML/SSO and OAuth2 are all described) and network authorization (Kerberos and enterprise password vaults), registration (online or offline) and a summary. Details worth remembering:

  • The documented first logins use default accounts (a sysadmin account for engine setup and an admin account for the masking application). The page tells you to change the default password for security. I do not repeat the defaults here.
  • Engine type cannot be changed once set in the wizard, because other features such as SSO depend on it.
  • After three failed attempts the account is locked from the Compliance service.
  • The Compliance engine operates only in UTC; time zone choices during setup do not apply. Remember this when you read job times in Monitor.
  • LDAP for non-containerized engines is configured in the setup application, not in the masking UI; containerized engines keep LDAP settings local. This is a change from earlier releases that the page calls out, which is a good example of why you check your version.
  • Email for job completion needs the SMTP settings from the Outbound Connectivity page.

22.8.2 Sizing and rules that affect your work

The best-practices page gives a standard configuration for a dedicated Compliance Engine: 8 vCPUs, 64 GB of RAM as a minimum (128 GB or more recommended), a 127 GB system disk and at least 50 GB for the data storage pool, more if mapping algorithms are heavily used. The same page offers rules of thumb that affect how you plan jobs: about one vCPU per concurrent masking job, at least 1 GB of memory per masking job, and at least 1 GB per stream when a job uses several parallel streams. It notes that the engine can become I/O-bound waiting for the database, that slow networks with many hops hurt, and that cloning an engine through hypervisor features or copying its storage is not supported as a backup method.

Two engines, never one machine

Both the masked-provisioning pages and the configuration page say that Delphix Masking and Delphix Virtualization must never run inside the same virtual machine. Use separate, dedicated engines. The best-practices page also says that Continuous Data and Continuous Compliance are delivered in one OVA, and you pick which one at first setup. So an engine image can become either product, but one running engine is only one of them.

What I could not ground

I did not read the per-cloud installation pages in full, so I give no instance sizes, ports or prices. Usage-based pricing is mentioned on the supported-connectors page (per terabyte of data managed), but I have no price list. Ask your Delphix administrator for the concrete deployment you are using.

22.9 Users and roles overview

The masking engine uses role-based access control: a role is a set of allowed actions on certain kinds of objects, and a user is a person who has one role and access to certain environments. This is how ShopSphere keeps the data steward from editing connection passwords and keeps testers away from masking jobs. From docs

22.9.1 Roles, actions, objects

  • Actions you can grant: View, Add, Update, Delete, Copy, Export and Import (not every action exists for every object).
  • Objects you can grant them on include Environment, Connection, Ruleset, Inventory, Profile Job, Masking Job, Tokenize Job, Re-identify Job, Domains, Algorithms, Classifier, Profiler Set, File Format, JDBC Drivers, Plugins, Password Vault, User, Report, Approve Inventories and Diagnostic.
  • Role type: DEFAULT roles come with the product and can be viewed and duplicated but not edited or deleted. CUSTOM roles can be added, edited, deleted and duplicated.
  • Five default roles exist: IT Security Analyst, DBA, SME, Operator and Environment Owner, plus a default All Privileges role if one exists.
  • Each user has one role and a list of environments. Access to an environment does not grant unlimited access: the role still limits what the user can do there.
  • The Administrator setting on a user gives unrestricted access to everything, plus some admin-only powers (sync, audit page, user API-access settings, deleting any object, and others). With it enabled, the role and environment fields disappear.

A role that is also a security risk

The Users and roles page warns that a user allowed to add or update JDBC drivers can upload code that runs inside the engine's JVM, which is effectively running code on the engine host. The built-in DBA role includes that permission by default; the page suggests a custom role or fewer DBA assignments if you separate database work from driver installation. Treat JDBC-driver permission as administrative.

Creating a user needs: user name, email (the engine mails job completion to it), optionally first and last name and a principal for OAuth2, a password (at least eight and at most 65 characters, with an uppercase letter, a special character from a short list and a number), the Administrator checkbox, a role and the environments. An account locks after three invalid login attempts. Roles and users can also be managed through the engine's API.

22.11 Frequent releases: expect your screen to differ

The documentation set has a release-notes page for each of 2025.1 through 2026.5, and the 2026.5 notes are dated September 2026. That is eleven releases in under two years. Several facts in this chapter already show how fast the product moves:

  • The screenshots on the documentation pages carry different version numbers in the corner (for example 21.0.0.0, 22.0.0.0, 24.0.0.0, 26.0.0.0 and 2025.6.0.0), so the same documentation mixes pictures from different generations.
  • The environments screenshot has an Approval column that the text for that screen does not list.
  • The connector wizard in the text says "Connection Mode: Basic or Advanced"; the screenshot of the same wizard says "Select Connection Method: Hostname/IP (Basic) or JDBC URL (advanced)".
  • Release 2026.5 upgrades the host's Java from JDK 8 to JDK 17 and warns that custom algorithm plugins and custom JDBC drivers must be Java 17 compatible. Older pages on extended connectors still talk about Java 8, so some pages lag behind.
  • A rule set screenshot shows an action called Checklist, while the same page's text calls the action "Verify" in one place and "Checklist" in another.
A habit that saves hours

Before following any procedure in this guide on a real engine, find the version of your engine (the screenshots show it in the corner of the top bar; the Admin menu also has an About page, which I did not read) and compare it with the page you are reading. When screen and text disagree, trust the screen and tell your trainer.

22.12 Common mistakes and gotchas

Things that trip beginners
  • Looking for algorithms inside the environment. They live under Settings, shared by all environments. A deleted environment never takes them with it.
  • Assuming profiling masks anything. A profiling job only proposes domains and algorithms in the inventory. Nothing changes in the database until a masking job runs.
  • Running an in-place job on the real production database. In-place overwrites the source values. Mask a copy.
  • Forgetting the Purpose of an environment is fixed. Mask versus Tokenize/Re-Identify cannot be edited later. Create a new environment instead.
  • Special characters in names. A colon or bracket in a rule set or job name fails the save.
  • Ignoring warnings. Non-conformant data is left unmasked by default and only produces a yellow warning.
  • Believing a screenshot is exact. Versions differ; read the labels on your screen.

22.13 Recap

Recap
  • Delphix Continuous Compliance is the masking engine: it profiles to find sensitive data, masks irreversibly, or tokenizes reversibly.
  • Masking is in-place (overwrite the source, so use a copy) or on-the-fly (read one place, write another).
  • The interface has five menus: Environments, Monitor, Settings, Admin, Audit. The same grid control (sort, filter, pin, actions) appears everywhere.
  • Work objects (connector, rule set, inventory, jobs) live inside an environment inside an application. Shared objects (domains, algorithms, profile sets, classifiers, file formats, JDBC drivers) live in Settings.
  • A project flows: engine, prepare the database, environment, connector, rule set, profile, review the inventory, mask.
  • The engine is a VM image or a Kubernetes deployment, never in the same machine as the Virtualization Engine. It works in UTC.
  • Roles are sets of actions on objects; each user has one role plus environments.
  • The product changes often. Check your version and trust your screen over this text.
