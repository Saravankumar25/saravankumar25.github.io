22.8 Where the engine runs: deployment options at overview level

As a TDM engineer you will rarely install the engine yourself, but you should know what shape it takes, because that decides who you ask when something is down. The documentation offers two families. From docs

Virtual machine image

A virtual appliance: a ready-made machine image imported into a hypervisor or cloud. The Installation page lists VMware, AWS EC2, Azure, Google Cloud Platform, IBM Cloud, Hyper-V and OCI. You set the network from a console, then finish in the browser-based Setup Wizard.

Containerized

The same engine as a pod of three containers on Kubernetes (tested on OpenShift, MicroK8s, AWS EKS and AWS ECS with Fargate), deployed directly or with Helm. FTP and FTPS file connectors are disabled in this form.

22.8.1 What the Setup Wizard asks

The wizard walks through Welcome (pick Continuous Compliance as the engine type), passwords and the three administrator accounts, time, network, certificates, storage, outbound connectivity (support proxy, usage analytics and the SMTP server used for job email), authentication (LDAP, SAML/SSO, OAuth2), Kerberos and password vaults, registration and a summary. Facts worth keeping: the documented first logins use default accounts that you must change; the engine type cannot be changed once chosen; three failed logins lock the account; the engine works only in UTC, so read job times in Monitor accordingly; and in non-containerized engines LDAP is configured in the setup application, not in the masking UI, a change from earlier releases.

22.8.2 Sizing, in one line

The best-practices page gives a dedicated Compliance Engine 8 vCPUs, at least 64 GB of RAM (128 GB or more recommended), a 127 GB system disk and at least 50 GB of data storage, plus rules of thumb of about one vCPU and 1 GB of memory per concurrent masking job. It also says cloning an engine through hypervisor features is not supported as a backup.

22.8.3 What the engine must reach

The network requirements page lists the traffic. Outbound, the engine needs SMTP (25), DNS (53), NTP (123, VM engine), HTTPS to Delphix Support and to an S3 endpoint if you use one (443), LDAPS (636) and, most important for you, "various" ports to your own databases (JDBC) and file servers (FTP, SFTP, NFS, CIFS). Inbound, users reach the web interface on 443 (use HTTPS, not 80) and administrators use SSH on 22. The engine cannot be deployed behind a reverse proxy. Supported browsers are the latest and previous versions of Edge, Firefox and Chrome. When a connector test hangs, suspect a firewall on the database port before you suspect the password.

The containerized product is meant for ephemeral engines (spun up for a need, then discarded) and differs from the VM engine: no FTP file masking, no Kerberos, no SSO/OAuth, no upgrade validation and no Db2 z/OS or iSeries connector. From docs

Two engines, never one machine

Both the masked-provisioning pages and the configuration page say that Delphix Masking and Delphix Virtualization must never run inside the same virtual machine. Use separate, dedicated engines. The best-practices page also says that Continuous Data and Continuous Compliance are delivered in one OVA, and you pick which one at first setup. So an engine image can become either product, but one running engine is only one of them.

22.9 Users and roles overview

The masking engine uses role-based access control: a role is a set of allowed actions on certain kinds of objects, and a user is a person who has one role and access to certain environments. This is how ShopSphere keeps the data steward from editing connection passwords and keeps testers away from masking jobs. From docs

22.9.1 Roles, actions, objects

  • Actions you can grant: View, Add, Update, Delete, Copy, Export and Import (not every action exists for every object).
  • Objects you can grant them on include Environment, Connection, Ruleset, Inventory, Profile Job, Masking Job, Tokenize Job, Re-identify Job, Domains, Algorithms, Classifier, Profiler Set, File Format, JDBC Drivers, Plugins, Password Vault, User, Report, Approve Inventories and Diagnostic.
  • Role type: DEFAULT roles come with the product and can be viewed and duplicated but not edited or deleted. CUSTOM roles can be added, edited, deleted and duplicated.
  • Five default roles exist: IT Security Analyst, DBA, SME, Operator and Environment Owner, plus a default All Privileges role if one exists.
  • Each user has one role and a list of environments. Access to an environment does not grant unlimited access: the role still limits what the user can do there.
  • The Administrator setting on a user gives unrestricted access to everything, plus some admin-only powers (sync, audit page, user API-access settings, deleting any object, and others). With it enabled, the role and environment fields disappear.

A role that is also a security risk

The Users and roles page warns that a user allowed to add or update JDBC drivers can upload code that runs inside the engine's JVM, which is effectively running code on the engine host. The built-in DBA role includes that permission by default; the page suggests a custom role or fewer DBA assignments if you separate database work from driver installation. Treat JDBC-driver permission as administrative.

Creating a user needs a user name, an email (job completion mail goes there), a password, a role and the environments the user may open, or the Administrator checkbox. An account locks after three invalid login attempts.

22.10 Moving work between engines: export, import and sync

Real organisations often run several engines: one per stage of the software life cycle (development, QA, production), or several production engines to share a large workload. Objects must then be copied between them. Export Settings / Import Settings (on the Environments page) moves shared settings such as domains, algorithms and file formats. Export / Import Environment moves everything inside one environment (connectors, rule sets, inventory, jobs). An API-based sync does the same at scale; the docs advise moving objects in one direction only. Sync does not currently support the Application object or certain algorithms, and bundles from a newer engine may not import into an older one. From docs

22.11 ShopSphere in object terms

For ShopSphere the objects will be: application SHOPSPHERE_APP; environment SHOPSPHERE_DEV (purpose Mask); a connector to the VDB that holds an unmasked copy of SHOPSPHERE_PROD; a rule set with CUSTOMERS, ORDERS, ORDER_ITEMS and PRODUCTS; a profile job and an in-place masking job; and roles for the TDM engineer (All Privileges), data steward (SME) and DBA. These names are my illustration. Notice that CUSTOMERS.customer_id and ORDERS.customer_id must get the same algorithm so every order still points to the right customer; the keys chapter is about exactly that.

Lab: find your way around an engine

Goal: confirm you can locate every object type in this chapter on a real engine (or on the screenshots, if you have no engine yet). This lab uses documented screens only, with ShopSphere names as illustration. Do not click Delete anywhere.

  1. Sign in and note the version.

    Open the engine's address in a browser and sign in with the account your administrator gave you.

    The Environments page appears, with menus Environments, Monitor, Settings, Admin and Audit. A version number sits next to the logo in the top bar.

  2. Add an application.

    Click + Application, enter SHOPSPHERE_APP and Save. This needs a role that allows it.

    You return to the Environments list. If the button is missing or disabled, your role lacks permission, which tells you how roles work.

  3. Add an environment.

    Click + Environment. Choose the application, name it SHOPSPHERE_DEV, leave Purpose as Masking and leave the approval checkbox clear. Click Save And View.

    The environment opens with tabs Jobs, Rule Sets and Connectors, all empty. The line under the name shows Application, Purpose and Approval.

  4. Visit each tab.

    Open Connectors, then Rule Sets, then Jobs.

    Each shows an empty grid. Connectors offers a connection button, Rule Sets an add button, Jobs the profiling and masking job buttons.

  5. Visit the shared Settings.

    Open Settings and click Algorithms, then Domains.

    A long list of built-in algorithms (Owner: System) and domains. Note the framework name column, for example Secure Lookup.

  6. Try the grid.

    In the algorithms grid, hover the Algorithm Name header, open the menu, filter by "contains" with the text NAME, and read the chips above the grid. Then press Reset.

    Only matching rows remain while the filter chip is shown, and all rows return after Reset.

  7. Look at Monitor and Admin.

    Open Monitor (Async Tasks, Job Executions), then Admin > Roles.

    Monitor is probably empty on a new engine. Roles lists the default roles (All Privileges, DBA, Environment Owner, IT Security Analyst, Operator, SME) with type DEFAULT. If Admin is missing you are not an administrator.

Show a worked answer

You should be able to say, without looking: (1) the application is a label, (2) the environment holds the connector, rule set and jobs, (3) algorithms, domains and profile sets live in Settings, (4) job and task progress lives under Monitor, and (5) roles and users live under Admin. If the Application button or the Admin menu was missing, that was the role system working, not a bug.

Docs versus illustration: the steps and field names come from the Managing environments page. The names SHOPSPHERE_APP and SHOPSPHERE_DEV and the filter text are mine.

22.14 Common mistakes and gotchas

Things that trip beginners
  • Looking for algorithms inside the environment. They live in Settings and survive an environment delete.
  • Assuming profiling masks anything. It only proposes; data changes when a masking job runs.
  • Running an in-place job on production. It overwrites the source values. Mask a copy.
  • Expecting to change an environment's Purpose. It is fixed; create a new environment.
  • Ignoring warnings. Non-conformant data is left unmasked by default and only shows a yellow warning.

22.15 Recap

Recap
  • Delphix Continuous Compliance is the masking engine: it profiles to find sensitive data, masks irreversibly, or tokenizes reversibly.
  • Masking is in-place (overwrite the source, so use a copy) or on-the-fly (read one place, write another).
  • The interface has five menus: Environments, Monitor, Settings, Admin, Audit. The same grid control (sort, filter, pin, actions) appears everywhere.
  • Work objects (connector, rule set, inventory, jobs) live inside an environment inside an application. Shared objects (domains, algorithms, profile sets, classifiers, file formats, JDBC drivers) live in Settings.
  • A project flows: engine, prepare the database, environment, connector, rule set, profile, review the inventory, mask.
  • The engine is a VM image or a Kubernetes deployment, never in the same machine as the Virtualization Engine. It works in UTC.
  • Roles are sets of actions on objects; each user has one role plus environments.
  • The product changes often. Check your version and trust your screen over this text.
