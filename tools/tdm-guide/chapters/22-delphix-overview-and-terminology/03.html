22.6 How a masking project flows

With the objects named, the order of work follows from the nesting: you cannot create a rule set before a connector, and you cannot create a connector before an environment. The documentation's own table of contents for "Connecting data" (environments, connectors, extended connectors, file formats, rule sets, inventories) follows exactly this order, and the Continuous Compliance home page groups the rest as "Identify sensitive data", "Preparing data" and "Connecting data".

Where each step is taught: step 1 and the roles are in this chapter; steps 2 to 4 in the connectors and VDB chapter; step 5 in the rule sets and keys chapter; steps 6 and 7 in the profiling chapter; step 8 in the algorithms and jobs chapter and, for files, the file masking chapter. Profiling only proposes domains and algorithms; a human, usually the data steward, confirms them.

How a TDM team splits this

The "best practices for defining masking roles" page gives a sample RACI (who is Responsible, Accountable, Consulted, Informed). It makes IT Security accountable for deciding which data types are sensitive, the application owner accountable for inventory management, data masking and masked-data validation, and the data masking admin team responsible for masking administration (domains, classifiers, roles, users). In ShopSphere terms: the compliance officer decides that SSN, email and phone are sensitive, the data steward reviews the inventory, and the TDM engineer builds and runs the jobs. 22.7 The terminology page, term by term

The terminology page is a one-page glossary and worth reading yourself. Here is the part you need for masking, with a ShopSphere picture for each idea. The objects (application, environment, rule set, domain, connector) were covered above, so I move to the algorithm and job vocabulary. From docs

22.7.1 Algorithm words

Algorithm framework
A type of masking algorithm. You can create one or more usable instances from it. "FIRST NAME SL" is an instance of the Secure Lookup framework.
Algorithm instance
A named combination of a framework and its settings. This is what you actually assign to a column in the inventory.
Built-in algorithm
An algorithm instance or framework shipped with the engine. Some built-ins have behaviour that matches no built-in framework.
Non-conformant data
A value that does not fit the format an algorithm expects (for example a 10-digit rule fed a 7-digit number). By default such values are not masked and a warning is recorded, shown as a yellow triangle beside the job execution. You can choose per job, or globally under Admin > Application Settings > Default Non-Conformant Data Handling, whether the job fails, leaves the value unmasked, or sets it to null.
Collision
Two different real values masked to the same fake value. "Amy" and "Jane" both becoming "Beth" is the docs' example.
Non-conformant data means "silently left real" by default

This default surprises beginners. If ShopSphere's phone column contains n/a in some rows, an algorithm expecting ten digits does not fail the job. It leaves n/a unmasked and logs a warning. That is harmless for n/a, but a real SSN typed with spaces might slip through the same way. Always read the warning count after a job.

22.7.2 The algorithm families in one table

The terminology page describes eight families. The algorithms chapter shows how to build them. Here is only the idea, so the names are not strange later.

FamilyHow it works (docs, in short)Typical ShopSphere use
Secure LookupReplaces each value by one picked from an input file using a cryptographic hash of the original, so the same input always gets the same output. Most common. Collisions are possible.first_name, last_name: a name list.
Segment MappingPermutes short numeric or alphanumeric values to others of the same format; guaranteed collision-free if the allowed output range is at least as large as the input set. Maximum 36 digits or characters in the masked value (as the terminology page states).ssn, tax_id, and key columns that need unique values.
MappingYou supply the replacement values. The engine records all input-to-output pairs in encrypted form so no two inputs share an output. You must know how many values you will mask. You cannot mask more than one table at a time with it.A small fixed list of codes, such as product_code, if you want to hand-pick substitutes.
TokenizationThe only reversible family. Creates a unique token per input and stores both token and original.Only if an outside vendor must analyse accounts and ShopSphere must later reverse the result.
Binary Lookup, Min Max, Data Cleaning, Free Text RedactionReplace images with a supplied image; move extreme values toward the middle; standardise spellings without masking; remove sensitive material from free-text columns.Not needed for the core ShopSphere columns.

Two documented warnings you should hold onto now, because the keys chapter relies on them. First, Secure Lookup is deterministic on its input (same hash, same output), and Segment Mapping and Mapping are the collision-free choices, so these are the ones used on unique and key columns. Second, the terminology page's wording for Segment Mapping explicitly lists "Social Security Numbers, primary key columns, or foreign key columns" as its use.

22.7.3 Job options, in one look

The terminology page lists the options of both job types, and you will meet them on real screens in the profiling chapter and the algorithms and jobs chapter. A profiling job has a unique Job Name, a Rule Set, No. of Streams (tables processed in parallel), optional memory limits, Feedback Size, Profile Sets and Email. A masking job adds the Masking Method (In-Place or On-The-Fly), Update Threads (too many can deadlock T-SQL databases), Commit Size, Disable Trigger and Drop Index (both clear by default, so the job leaves indexes and triggers alone unless you turn them on), and Prescript and Postscript SQL files. Both have a Multi-Tenant option that lets one rule set serve identical schemas through different connectors chosen at run time.
