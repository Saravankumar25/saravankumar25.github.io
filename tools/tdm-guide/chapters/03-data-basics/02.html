3.4 Keys and relationships

A single table is easy. Real applications split data across many tables and connect them. Keys are the connectors. This section is the most important in the whole chapter.

Why data is split into several tables

Imagine ShopSphere stored everything in one big sheet: one row per ordered item, with the customer's name, phone and address repeated on every row. Customer Asha has two orders with three items in total, so her phone number would be typed three times. If she changes her phone number you must update every copy, and if you miss one the data disagrees with itself.

The fix is to store each fact once, in the table where it belongs, and refer to it from elsewhere. Customer facts live in CUSTOMERS. An order stores only the customer's ID, not the name and phone. To get the name, you look the ID up. The ID is a key.

General concept

Primary key

A primary key is a column (or a small group of columns) whose value is unique in every row and is never empty (null). It is the row's identity, like a library card number or a passport number.

  • CUSTOMERS.customer_id: 1001, 1002, 1003. No two customers share an ID.
  • ORDERS.order_id, ORDER_ITEMS.item_id and PRODUCTS.product_code are the primary keys of their tables.

A database enforces this: it refuses to insert a second customer with ID 1001.

Why not use the name as the key? Two customers can share a name; names change; spellings vary. A key must be stable and unique. That is why tables carry an artificial ID such as customer_id. (Keys made up of real-world data, like an email address, are called natural keys; made-up IDs are surrogate keys. Both appear in the real world.)

A key can have more than one column. Suppose a table ORDER_ITEM_NOTES allowed one note per item per language; then (item_id, language) together would be unique, though neither alone is. That is a composite key.

Foreign key

A foreign key is a column in one table whose values must match the primary key of another table. It is the link.

  • ORDERS.customer_id is a foreign key to CUSTOMERS.customer_id: it says which customer placed the order.
  • ORDER_ITEMS.order_id is a foreign key to ORDERS.order_id: it says which order this line belongs to.
  • ORDER_ITEMS.product_code is a foreign key to PRODUCTS.product_code: it says which product was bought.

The foreign key column is allowed to repeat. Customer 1001 can appear in many order rows, because Asha can place many orders. The primary key side cannot repeat.

Parent and child tables, one-to-many

The table that holds the primary key is the parent; the table with the foreign key pointing at it is the child. One customer (parent) can have many orders (children), and one order can have many items. That shape is called one-to-many.

Referential integrity

Referential integrity is the rule that every foreign key value must match a primary key value that exists. Every order must belong to a customer who exists; every item to an order that exists.

A child row whose parent is missing is called an orphan. Suppose someone deletes customer 1001 but leaves orders 5001 and 5002. Those orders now point to nobody. The "my orders" page crashes. When the database has the foreign key declared, it refuses such a delete, and it refuses to insert an order for a customer ID that does not exist. (In SQLite with foreign key enforcement switched on, both attempts are rejected with a foreign key constraint error.)

Why keys matter so much to TDM

Every TDM operation reshapes data. Each one can break referential integrity if done carelessly.

OperationHow it can break keysWhat it must do instead
SubsettingPick 100 customers but leave out their orders (missing children), or pick orders but leave out their customers (orphans).Follow the keys: choose a starting table, then bring along every related row in the other tables.
MaskingMask customer_id in CUSTOMERS to a new value but leave ORDERS.customer_id unchanged, or mask them differently. Orders no longer match customers.Apply the same masking to the parent key and every child foreign key so the values still match, or leave keys alone.
GenerationGenerate 1,000 orders with customer IDs that no generated customer has.Generate parents first and give each child a valid parent ID.
ProvisioningLoad child tables before parent tables so foreign key checks fail.Load parents first; delete children first.

Each tool has its own way to say this. The Informatica documentation says a data subset retains primary and foreign key relations so that the data stays referentially intact (User Guide 10.5.10, p.23). The Delphix introduction says it scans metadata and data to identify and preserve primary/foreign key relationships so that data is masked the same way across tables and databases (Introduction to Delphix Masking). Logical keys: keys the database does not know about

Everything above assumed the keys are declared in the database. In real life they often are not. Older systems, performance-minded designs and imported data frequently have tables with no declared primary or foreign keys at all, even though the application treats certain columns as keys. The relationships exist in the developers' heads and in the code, not in the schema.

TDM tools cannot follow a relationship they do not know about. So they let you (or their profilers) describe the relationships separately. Keys defined this way are called logical keys: the tool is told "treat this column as the key" without any change to the real database.

ToolWhat its documentation says
InformaticaPrimary-key and foreign-key profiles can discover potential relationships (p.21). The foreign key profile adds the discovered logical constraints to the TDM repository but does not apply them in the source tables; the subset workflow uses them to produce referentially intact data (p.86). You can also add a logical primary key to a table (p.109) and a logical foreign key choosing a column from a parent table (p.110). In its worked example the database contains no primary or foreign keys, so the developer creates logical ones (p.34). For data sets it advises creating logical keys in transactional tables that have no primary keys (p.239).
DelphixIn a rule set, a logical key is a unique, non-null value identifying a row. If a table has no primary key defined and you use in-place masking, you must name an existing column or columns as the logical key. It does not change the target database; it only informs Delphix. Without one, an identity column may be created, which requires permission to modify the schema or the job may fail. The rule set "Checklist" validates that every table has a primary key, an indexed identity column or a logical key (Managing rule sets).

The idea is the same in both: a key you declare to the tool, which the database may know nothing about. Chapters on Informatica subsetting and Delphix rule sets and keys show the screens.

Logical keys are only as good as your understanding

If you declare a column as a key but it is not actually unique, masking or subsetting will misbehave. A logical key must be unique and never null for every row, exactly like a real primary key. You prove it by checking the data (for example by counting rows and counting distinct values), not by assuming.
