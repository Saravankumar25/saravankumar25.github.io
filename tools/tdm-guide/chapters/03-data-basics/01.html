Everything a TDM tool does is done to data: it finds data, cuts it down, hides parts of it, makes more of it, and moves it. To follow any of that you need a small, firm vocabulary about how data is organised. This chapter gives it to you from zero. You will not become a database administrator, but you will be able to read a table, spot a key, tell a CSV from a fixed-width file and run a basic SQL query.

These ideas return constantly. Subsetting, masking and generation all have one rule in common: keep the relationships between records intact. You cannot follow that rule if you do not know what a relationship is. This chapter is also the preparation for the primary-key work in the Delphix part of the syllabus (Day 51) and the file-masking work (Day 53).

3.1 Words to know first

Data
Raw facts, such as "1001", "Asha" and "560001", before anyone says what they mean.
Information
Data with meaning: "customer 1001 is Asha, living in postal area 560001".
Database
An organised store of data that a program can search and change reliably.
Table
A grid of data about one kind of thing, like one sheet in a spreadsheet.
Row / record
One item in a table: one customer, one order.
Column / field
One attribute of every row: first name, phone, order date.
Primary key (PK)
A column (or columns) whose value is unique for every row and identifies it.
Foreign key (FK)
A column whose values point to the primary key of another table.
Referential integrity
The rule that every foreign key value must match an existing primary key value.
Schema / metadata
The description of the data (table names, columns, types, keys) as opposed to the data itself.
Flat file
A plain file holding records as lines of text, with no built-in database engine behind it.
SQL
The language used to ask a relational database questions and to change it.

3.2 Data and information

Look at this: 1001 | Asha | Menon | 560001. On its own it is just data: four values. You can guess it is a person, but you are guessing. Add labels (customer_id, first_name, last_name, zip_code) and a table name (CUSTOMERS) and it becomes information: customer 1001 is Asha Menon in postal area 560001.

That distinction matters for TDM because tools often see only data and have to work out the meaning. Discovery (see the discovery and subsetting concepts chapter) is largely the job of recovering meaning: "this column, called col_17, contains phone numbers". Column names, data types and descriptions are the clues.

3.3 Databases and tables

The spreadsheet analogy

If you have used a spreadsheet you already know the idea. A table is one sheet: columns across the top with names, rows below, one item per row. A database is the whole workbook, with several sheets (tables) that belong together.

Here is the ShopSphere CUSTOMERS table:

CUSTOMERS (fake sample rows, first five columns)
customer_idfirst_namelast_nameemailphone
1001AshaMenonasha.menon@example.com9876543210
1002RaviKumarravi.k@example.com9123456780
1003MeeraNairmeera.n@example.com9988776655
  • Each row (also called a record) is one customer.
  • Each column (also called a field or attribute) is one fact about every customer.
  • Each cell is one value: the phone number of customer 1002.

Unlike a spreadsheet sheet, a database table enforces each column's declared type, can be linked to other tables by keys, can hold millions of rows, and is queried with SQL (later in this chapter). ShopSphere uses a relational database (Oracle, SQL Server, MySQL, PostgreSQL and DB2 are examples): tables relate through keys.

General concept

Data types

Each column has a data type that says what kind of value it holds. The type controls what is allowed, how much space it takes and how it can be used (you can add numbers but not names).

Type familyTypical namesShopSphere exampleWhy a TDM person cares
Whole numbersINTEGER, INT, NUMBERcustomer_id, quantityGenerated or masked values must still be whole numbers.
Decimal numbersDECIMAL(10,2), NUMERICunit_price, total_amountPrecision matters: 10,2 means up to 10 digits, 2 after the point.
TextVARCHAR(50), CHAR(10)first_name, emailA masked name must fit the length limit.
Dates and timesDATE, TIMESTAMPdate_of_birth, order_dateA masked date of birth must still be a real date.
True/falseBOOLEAN, BIT(none in ShopSphere)Only two values exist.
Binary / large objectsBLOB, CLOB, images(none in ShopSphere)Special handling; many masking techniques do not apply.

Notice something about the ShopSphere sample data: phone, ssn and zip_code look like numbers, but they are stored as text. You never add two phone numbers, and a leading zero would be lost if they were numbers. That choice affects how you mask them: a text column can hold dashes (123-45-6789); a numeric column cannot.

Why this matters

A TDM operation must produce values the column accepts. A masked or generated name longer than the column's limit makes the load fail. A fake date such as 31 February is rejected. Many job failures in the tool chapters come down to "the new value did not fit the column's type or length".

Schema and metadata

Metadata means "data about data". For a database it is the list of tables, their columns, each column's name and type, which columns are keys, and which tables relate to which. The collection of all that is the schema.

Here is part of the ShopSphere schema written as a simple description (not the data):

CUSTOMERS
  customer_id    INTEGER       PRIMARY KEY
  first_name     VARCHAR(50)
  last_name      VARCHAR(50)
  email          VARCHAR(100)
  phone          VARCHAR(15)
  ssn            VARCHAR(11)
  date_of_birth  DATE
  zip_code       VARCHAR(10)
  tax_id         VARCHAR(20)

The metadata tells a tool a lot without reading a single row. A column called ssn of type VARCHAR(11) is a strong hint (11 characters fits 123-45-6789). TDM tools therefore read metadata first, then sample the actual data. The Informatica guide describes a TDM repository that stores the metadata you import into Test Data Manager from a source database (User Guide 10.5.10, p.26).
