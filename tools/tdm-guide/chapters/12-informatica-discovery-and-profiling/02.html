12.3 The Discover view

Inside a project, the Discover tab is where profiling happens. The guide describes it as the place to view tables, manage primary key and foreign key relationships, configure profiles, and update columns for masking (User Guide 10.5.10, p.88).

Visual referenceInformatica TDM 10.5.10 User Guide, p.88, Figure "Discover view in a Project". What to look for: the project tab bar, then Tables, Profile, Columns and Files sub-tabs; a list of tables in the upper pane; and, below, a General Properties pane and a Relationship Overview pane that draws the selected table with its related tables.
Sub-viewWhat you do there (pp.88-89)
TablesView tables in the data source and the relationships of a selected table; see its columns; define primary and foreign keys; delete a table from the metadata. You can disable a physical primary key column when you do not need composite keys or entity relationships (select the row on Tables > Columns and enable or disable from the Actions menu). You can also edit the precision of a source column to match the value you need in the target.
ProfileDefine a profile that finds columns for data domains and possible primary-key and foreign-key relationships.
ColumnsMaintain data domain assignments; mark columns Restricted or Sensitive; assign domains in bulk; define similar columns for value cascades.
FilesList XSD files in the project and open one for subset, masking and generation work.

Column properties

The Discover > Columns view shows these properties for each column (p.89):

PropertyMeaning
Table Name, Column, Owner, Data TypeWhere the column lives (Owner is the database schema) and its type.
DomainThe data domain the column belongs to.
RestrictedThe Integration Service does not write this column's value to a target.
ComputedThe column's data is computed from other columns. You cannot assign rules to it.
SensitiveThe column contains sensitive data. This is for reference only; it does not affect processing.
Similar Value ColumnsNumber of columns related to this one in a value cascade.

Sensitive columns. Marking a column sensitive is a label for people. It does not mask anything by itself. When you assign a data domain to a column, Test Data Manager marks it sensitive automatically (p.89). So a column with a domain is both labelled and ready for domain rules.

Computed columns (p.90). Example: Net_Pay = Basic_Salary + Allowances - Tax_Deduction. The database fills it in. TDM can include such a table but does not copy data into computed columns in the target, because the target database recomputes them. You cannot apply masking or generation rules, nor a value cascade or auto cascade, and you cannot run a generation operation on an entity whose primary key column is computed. ShopSphere has no computed column in our sample, but an ORDERS.total_amount computed from ORDER_ITEMS would behave this way. That is a thought experiment of ours, not the real schema.

Value cascades and auto cascades

Both make sure the same original value becomes the same masked value in several places. That is the difference between a customer whose id looks right everywhere and one whose id no longer matches across tables.

Auto cascade (keys exist)

Masks a parent table's primary key and the related foreign keys in child tables with the same value. Applied by default to tables with key constraints; you can enable or disable it. It needs key constraints between parent and child. Not available for XSD, MongoDB and Cassandra sources (p.91).

ShopSphere: mask CUSTOMERS.customer_id and ORDERS.customer_id receives the same masked value.

Value cascade (no keys)

Masks similar columns in different tables the same way when they are not linked by key constraints. You group similar columns and mark one as the driving column; a rule assigned to it goes to all the others. The columns must have the same type (p.90).

ShopSphere: an email column in CUSTOMERS and a contact_email column in some marketing table.

The guide's example: employee_num in one table and EmpID in another are similar value columns, with employee_num driving. Assign a rule to it and EmpID receives the same rule (p.90). The driving column shows a number in Similar Value Columns; the others show none.

  1. Create: in Discover > Columns select the columns, click Actions > Set as similar value columns, and click the driving-column checkbox to change No to Yes for one column (p.90).
  2. Change: select the driving column (it has a number), open the Similar Value Columns view in the Details panel, click Edit Similar Value Columns. Set Driving Column to Yes on another column (the previous one switches to No), use Add to add columns or Delete to remove them (p.91).
  3. Delete the group: select the driving column, open Similar Value Columns, select any column in the group, click Delete, confirm (p.91).

12.4 The discovery task flow

Before profiles can run, the administrator must configure a source database connection for data discovery, plus connections to the Data Integration Service and the Model Repository Service (User Guide 10.5.10, p.92). The Informatica architecture chapter explained why those services are involved. If you are a developer and the Execute button fails with a connection message, that setup is the first place to look.

  1. Create a profile.

    Name and describe it.

  2. Choose the type: primary key, entity, or data domain discovery.

    You may combine primary key with entity or with data domain.

  3. For a data domain profile, choose which data domains (or policies) to search for.

    Selecting a policy includes all its domains.

  4. Choose the sampling size.

    More rows is more reliable and slower.

  5. Run the profile and monitor the job.

    Use the project's Monitor view.

  6. When it completes, open the profile again.

    The guide says to close and reopen the profile in Test Data Manager to see results (p.103).

  7. Review the results.

    Primary key, entity and data domain results are on separate tabs.

  8. Select and approve the results to use for masking and subset.

    Approval is what applies them.
