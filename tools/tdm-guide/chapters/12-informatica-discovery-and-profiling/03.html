12.5 Primary keys: the basics, then discovery

The syllabus calls out primary key basics and "data integrity maintained in primary and foreign key columns" (Days 43 and 51). Nearly every later task, subset above all, depends on keys, so spend time here.

Primary and foreign keys in plain words

A library gives each member a card number. No two members share one, and no member is without one. That number is a primary key: a column (or combination of columns) that uniquely identifies each row. The guide's rule for keys you add by hand: a primary key column cannot contain null (empty) or duplicate values, and a table has only one primary key constraint (User Guide 10.5.10, p.109).

When a library loan record stores the member's card number, that stored number is a foreign key: it points at a row in another table. In ShopSphere:

CUSTOMERS (customer_id PK) 1 ----< ORDERS (order_id PK, customer_id FK)
ORDERS    (order_id PK)    1 ----< ORDER_ITEMS (item_id PK, order_id FK)
PRODUCTS  (product_code PK)  (ORDER_ITEMS.product_code refers to it)

Data integrity means these links stay true: every ORDERS.customer_id exists in CUSTOMERS, every ORDER_ITEMS.order_id exists in ORDERS. Test data that breaks this is useless. A subset that copies an order but not its customer produces an orphan. Masking that changes CUSTOMERS.customer_id but not ORDERS.customer_id breaks the link. TDM relies on keys to avoid both: subset follows constraints "to create subset data with referential integrity" (p.86), and auto cascades mask parent and child keys together (p.91).

Why discovery of keys matters

Real source systems often have no declared keys, for performance or legacy reasons. In the guide's own example (pp.33-34), the database "does not contain primary and foreign keys", so the project developer runs profiles to find them and then creates logical keys. If ShopSphere's imported tables came with no declared keys, you would have to do the same.

Primary key discovery

To discover possible keys, create a primary key profile (p.92). It also helps find data quality problems: a profile that finds non-unique rows where you expected unique ones shows duplicates. It is useful when the key is a combination of columns that together identify a row. After discovery you can add keys to the source table in the project.

The guide's example: an Employee table has an EmpID column that is 100% unique, so the profile identifies it as a possible primary key to add to the project table (p.92). ShopSphere equivalent: CUSTOMERS.customer_id.

Creating and running a primary key profile

  1. Open the project, click Discover, then click Profile.

    You are in the profile list of this project.

  2. Click Actions > New Profile.

    The New Profile dialog box opens.

  3. Enter a name and description and choose to create a primary key profile.

    For ShopSphere: pk_shopsphere. A clear name makes it findable later.

  4. Click Next, select the tables to profile, click OK, then Next.

    Include every table you want keys for.

  5. On the Sampling Options page, enter the maximum number of columns in the key, the maximum rows to profile, and the minimum conformance (or the maximum number of rows that may violate).

    Fewer columns in the key means a faster, simpler search.

  6. Click Finish, then Actions > Execute.

    The run is a job you can follow in Monitor (p.92).

After it completes, close and reopen the profile to see results.

Unique is not the same as a key

A profile only tests uniqueness within the sample. email and ssn may score 100 on a small sample and still be unsuitable keys. Pick the column that is the business identifier and is what child tables refer to. That judgement comes from you, not the tool. (My reasoning, not a guide quote; the guide's decision aid is the uniqueness percentage plus your own knowledge of the data.)

Applying the primary key results

Select a row and choose Verify, Approve or Reject from the Actions menu (p.104).

  • Approve: TDM adds the primary key to the table in the TDM repository.
  • Reject: does not affect the subset operation.
  • Verified column: only for tracking your review; it does not affect subset operations.

Expected result: approved keys appear on the table in Discover > Tables, under Constraints as primary key constraints. The source database is unchanged. (The location under Constraints follows from the constraint steps on pp.109-110 and the statement that TDM does not add keys to the source tables, p.87.)

You can skip discovery and add keys by hand. The guide says when you manually add keys, you do not need a primary key discovery profile, and you define constraints for subset, masking and generation without updating the source database (p.109). The step list is in the manual keys section below.
