Before you can protect data you have to know where it is. ShopSphere's CUSTOMERS table has nine columns, and it is easy to see that ssn is sensitive. But the real production database has hundreds of tables, and a Social Security number can hide in a column called NOTES. Data discovery is Informatica's name for the automatic search that finds sensitive columns and table relationships so you do not have to read every column by eye.

This chapter covers everything the guide says about discovery and profiling in Test Data Manager: the four kinds of profile, how to create and run them, how to review and approve their results, how primary keys and logical relationships fit in, and the three syllabus hands-on exercises (TDM and data profiling, profiling and masking, profiling and subset) built as labs on ShopSphere. It builds on the discovery and subsetting concepts chapter, the data basics chapter (for keys), and the project and policy tour in the guided tour of Test Data Manager.

12.1 Words to know first

Profile
A saved search definition: which tables, which kind of analysis, which sampling limits. You can run it again later.
Profiling
Reading the data (or the column names) to describe it: which columns are unique, which look like SSNs, how many are empty.
Primary key (PK)
A column, or combination of columns, whose values uniquely identify each row. No empty values, no duplicates. Like a library card number.
Foreign key (FK)
A column in a child table that holds the primary key value of a parent row, such as ORDERS.customer_id pointing to CUSTOMERS.customer_id.
Referential integrity
The rule that every foreign key value has a matching parent row. Without it you get orphan orders.
Logical key or constraint
A key relationship defined only inside TDM, not in the real database. The guide stresses that TDM does not update the source tables.
Entity
A set of related parent and child tables, used to define a subset.
Uniqueness percentage
The share of values in a column that are unique. 100 means no duplicates.
Conformance
The percentage of rows that fit a rule or pattern. A threshold lets a few rows disagree.
Curation (review)
Looking at suggested profile results and approving or rejecting each one.

12.2 What data discovery is for

The guide's overview (User Guide 10.5.10, p.86): you run profiles to discover source data for masking and subset. Before masking, you discover which columns to mask with the same rule. Before building a subset, you discover relationships between tables and the entities that shape the subset database. You can then apply the results instead of configuring entities by hand or applying a masking rule one column at a time.

Why it matters

Discovery turns "someone remembers which columns are sensitive" into a repeatable, reviewable record. A compliance officer can see which columns were found, with what confidence, and who approved them. It also supplies the keys that subsetting needs when the database does not declare them.

The profile types

The guide names four types on p.86-87. In the screens you will see three of them listed as the options when you create a profile (primary key, entity, data domain) plus column. Note a naming wrinkle: the overview calls the relationship profile "Foreign key", while the creation steps and result screens call it an entity profile. They describe the same relationship discovery.

Which sources can be profiled

Profiles run on relational sources: Oracle, Microsoft SQL Server, IBM DB2 for Linux, UNIX and Windows, MySQL, Sybase and Teradata. Use ODBC to connect to MySQL, Sybase and Teradata. Data domain profiles also run on Hive and HDFS sources (p.87). Rules from the guide (pp.87-88):

  • Not nonrelational sources. You cannot run a discovery profile on them. You can run profiles in PowerCenter or Informatica Data Quality, export the results, and import them into the TDM repository.
  • You can view imported results of profiles that use the Enterprise Discovery Profile and Profile options. For Hadoop, import results from the Developer client with the Enterprise Discovery Profile option.
  • You can import results of discovery done with mapplets that use simple regular expressions, but not mapplets that use labeler, tokenizer, content set or reference tables.
  • Importing data domains from the Model repository does not bring data patterns, metadata patterns or preferred rules.
  • A table must have the same connection in the profile as when you imported it, or results may be unexpected.
  • Two tables with the same name cannot be in one profile. If a project has two EMPLOYEE tables with different owners, make a separate profile for each.
  • If you import a MySQL source from PowerCenter, unique key constraints appear as primary keys on the Discover > Tables > Columns tab.
  • You cannot run primary key and entity profiles on Hive data sources, and you cannot run profiles on Avro or Parquet formats (pp.61, 94).

ShopSphere's relational source qualifies. Note the "same table name" rule: if ShopSphere had a CUSTOMERS table in two schemas in one project, you would need two profiles.
