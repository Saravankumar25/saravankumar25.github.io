12.8 Column profile (for data generation)

A column profile reports the range of values, list of values and data patterns of the columns you choose, so you can generate test data that looks like the real data without copying it (User Guide 10.5.10, pp.87, 97). It runs on Oracle and Microsoft SQL Server. TDM infers three kinds of rule: Range (min and max, first and last values, percent null; numeric and date), Patterns (patterns with percentage distribution, summing to 100%; string and numeric) and List of Values (unique and non-unique values with distribution; string, numeric and date). Inferred rules become auto rules you can assign in Define > Data Generation (the Informatica data generation chapter uses them).

Sampling options (p.98): minimum conformance for patterns (default 5), maximum rows (default All), minimum data coverage to show List of Values (default 80) and maximum values in the list (default 20). With a cap of 20 values, those 20 must cover at least 80% of the data.

Creating, running and reading a column profile

  1. Discover > Profile > Actions > New Profile, select Column, click Add to choose tables, set the sampling options, Finish.
  2. Actions > Execute and choose a connection.

    The run fails with a native Oracle ODBC connection (use an Oracle ODBC connection with the DataDirect driver) and fails if a Microsoft SQL Server connection has no schema name (p.101).

  3. Follow it in Monitor, then open Profile > Column Discovery.

    Each column shows % null, an Inferred Rule (select Yes to apply) and a Selected Inferred Type (pattern, list of values or range, depending on data type). Accept, reject or edit the patterns, then save (pp.106-107).

Visual reference Informatica TDM 10.5.10 User Guide, p.106, Figure "column profile results". What to look for: an Inferred Rule drop-down per column and a Properties pane showing range, patterns and list of values with percentages.

12.9 Managing profiles

  • Run many times. Edit a profile between runs; each run overwrites the earlier results (p.101).
  • Edit: open the profile and click Edit. You can rename it (not change its type), add or remove tables, override key inference options, or change domains, policies and what to search. Delete: select the row without opening it, Actions > Delete, Yes (pp.101-102).
  • Import a profile from the Model repository (p.102), for example one run in Informatica Developer on a flat file. Import the source metadata and data domains first, from a connection of the same name as the profiling connection. Use Discover > Profile > Actions > Import Profile, optionally import the curation information (saved approvals, which TDM then applies), choose the profile types and Finish. Table names may contain only alphanumerics and underscore. If you delete the project metadata afterwards, the profile shows no results.

12.10 Constraints and relationships

Discovery suggests; constraints are what TDM actually uses. Foreign key constraints define parent-child relationships between source tables, and TDM uses them to decide which tables go into a subset and to limit the values in subset columns (User Guide 10.5.10, p.107). When you create an entity you pick one table as the driving table, and TDM adds other tables based on the constraints of that table (p.107). The Informatica data subset chapter builds on this.

Table classification

In Discover > Tables you can classify tables as Temporary, Master, Configuration, Transactional, Log or Seed. It does not affect profiles, but you can filter tables by it when creating entities or plans. The guide's reason: knowing which tables are master helps you decide driving tables, and transaction and log tables are candidates for extra filter criteria (p.107). ShopSphere reading: CUSTOMERS and PRODUCTS look like master tables; ORDERS and ORDER_ITEMS look transactional (our classification).

Major and minor constraint severity

When you define a foreign key constraint you choose a severity, which decides how much data a subset pulls in (pp.108-109). The severity does not change the structure of the entity; you can change it after creating an entity and at run time in a subset plan (the run-time change does not change the entity).

Major

Moves in both directions, child to parent and parent to child. If a filtered child row selects a parent, all other children of that parent come along too. This honours referential and transactional integrity. You can apply a major constraint only from within an entity.

Minor

One direction only, child to parent. The parent row is included, but not all its other children.

The guide's example: Customer is the parent of Leads. You filter Leads to high-quality leads. With a major constraint the subset includes the customer for each high-quality lead and all that customer's leads. With a minor constraint it includes the high-quality leads and their customers only (pp.108-109).

ShopSphere version (illustrative): you filter ORDERS to total_amount > 500. Major: you get those orders, their customers, and all other orders of those customers. Minor: you get those orders and their customers only.

  • Selecting more records in the child can pull in more parents, which pull in more children, and so on until no related records remain (p.108).
  • For a smaller subset, choose the Referential Integrity Only option in a plan at run time. The data stays referentially intact, but it may not include every child of a parent, so transactional integrity might not be kept.
  • If constraints form cycles, or an object has more than one major parent constraint, TDM does recursive evaluation and needs a staging connection. Using the source connection as the staging connection is recommended (p.109).

Adding keys by hand

You can add keys yourself and skip discovery (p.109). In every case the source database is not updated. Steps are the same up to the type.

Task: add a logical primary key and a logical foreign key in ShopSphere

Goal: tell TDM that ORDERS.customer_id refers to CUSTOMERS.customer_id. Steps from the guide (pp.109-110); table and column choices are ours.

  1. Primary key on CUSTOMERS.

    In the project click Discover > Tables, click CUSTOMERS, click Constraints, then Create New Constraint. Select Primary Key, Next, click Add, choose customer_id, Finish.

    The constraint appears in the table's Constraints list.

  2. Foreign key on ORDERS.

    Click ORDERS, Constraints, Create New Constraint. Enter a Name, set Constraint Type to Foreign Key, choose Severity Level (Major or Minor), choose Parent Table CUSTOMERS, and keep Enable Constraint ticked. Click Next.

  3. Map the columns.

    In the left pane click the child column customer_id, in the right pane click the parent column customer_id, click the Link icon, then Finish.

    The relationship shows in the table's Relationship Overview.

Show a worked answer

Illustrative result: CUSTOMERS has primary key constraint on customer_id; ORDERS has a foreign key constraint to CUSTOMERS with severity Major if you want a customer's other orders to come with a filtered order. Repeat for ORDER_ITEMS.order_id to ORDERS.order_id. For the ORDER_ITEMS.product_code to PRODUCTS link, Minor is a reasonable choice because you do not want every item that uses a product. That severity choice is a design judgement of ours.

For a unique key, choose Unique Key instead of Primary Key and add columns (pp.110-111). For a conditional constraint, enter a name, choose Conditional, click Next, build an expression in the Expression Builder (see the Expression Builder section), and click Finish (p.111).

12.11 Performance and accuracy tips from the guide

The guide has no dedicated discovery performance section; these tips are scattered through it.

  • Cap the sample. Primary key and data domain profiles default to 1,000 rows; column profiles default to All, the heaviest setting (pp.93, 95, 98). A small sample is fast but can call a column "unique" or "an SSN" wrongly (my reasoning).
  • Limit key columns (default 3, p.93) and avoid case-sensitive entity comparisons, which can slow the profile (p.99).
  • Search names first, then data. You can run a domain profile on column metadata and then on the data (p.100).
  • Pick only the domains you need: disabled domains are skipped (p.75), and choosing a policy includes all its domains at once.
  • Import metadata directly from the database when there are many tables (p.60), and use the same connection for import and profile (p.88).
