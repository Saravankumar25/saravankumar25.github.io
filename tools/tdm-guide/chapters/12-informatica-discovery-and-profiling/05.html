12.8 Column profile (for data generation)

A column profile analyses data quality in the columns you choose. It reports the characteristics of columns such as range of values, list of values and data patterns, and you can use those results to generate test data that looks like the real data without copying it (User Guide 10.5.10, pp.87, 97). It runs on Oracle and Microsoft SQL Server databases. The Informatica data generation chapter uses it; here is how the profile itself works.

12.9 Managing profiles

  • Run many times. You can edit a profile between runs. Each run overwrites the earlier results (p.101).
  • Edit: Discover > Profile, click the profile name, click Edit. The dialog has General, Tables and a Relationship Sampling or Sampling tab depending on type. You can change name and description (not the type), add or remove tables, override default inference options for keys, and change domains, policies or what to search (data, column name, or both). Then Actions > Execute (p.101).
  • Delete: select the profile row without opening it, Actions > Delete, Yes (pp.101-102).
  • Import a profile from the Model repository (p.102): useful when someone ran a profile in Informatica Developer, for example on a flat file. One profile can contain several types (data domain, primary key, foreign key, column). Before importing, import the source metadata and objects, including data domains, into the TDM repository, and import metadata from a connection of the same name as the one used for the profile. Table names may contain only alphanumeric characters and the underscore.
  1. In Discover > Profile click Actions > Import Profile and choose the profile, then Next.

    It keeps the name and description unless you edit them.

  2. Optionally choose to import curation information.

    TDM then imports saved review decisions and acts on them, for example assigning a data domain to a column if the inferred domain was approved.

  3. Select the profile types, enter column profile properties if you chose Column, and click Finish.

    The imported profile appears in the Discover view.

Two gotchas the guide gives: if you delete the project metadata after importing a profile, the profile shows no results; and if you re-import the metadata and import the profile again under a different name, the results appear in the first profile as well (pp.102-103).

12.10 Constraints and relationships

Discovery suggests; constraints are what TDM actually uses. Foreign key constraints define parent-child relationships between source tables, and TDM uses them to decide which tables go into a subset and to limit the values in subset columns (User Guide 10.5.10, p.107). When you create an entity you pick one table as the driving table, and TDM adds other tables based on the constraints of that table (p.107). The Informatica data subset chapter builds on this.

Table classification

In Discover > Tables you can classify tables as Temporary, Master, Configuration, Transactional, Log or Seed. It does not affect profiles, but you can filter tables by it when creating entities or plans. The guide's reason: knowing which tables are master helps you decide driving tables, and transaction and log tables are candidates for extra filter criteria (p.107). ShopSphere reading: CUSTOMERS and PRODUCTS look like master tables; ORDERS and ORDER_ITEMS look transactional (our classification).

Constraint types

Major and minor constraint severity

When you define a foreign key constraint you choose a severity, which decides how much data a subset pulls in (pp.108-109). The severity does not change the structure of the entity; you can change it after creating an entity and at run time in a subset plan (the run-time change does not change the entity).

Major

Moves in both directions, child to parent and parent to child. If a filtered child row selects a parent, all other children of that parent come along too. This honours referential and transactional integrity. You can apply a major constraint only from within an entity.

Minor

One direction only, child to parent. The parent row is included, but not all its other children.

The guide's example: Customer is the parent of Leads. You filter Leads to high-quality leads. With a major constraint the subset includes the customer for each high-quality lead and all that customer's leads. With a minor constraint it includes the high-quality leads and their customers only (pp.108-109).

ShopSphere version (illustrative): you filter ORDERS to total_amount > 500. Major: you get those orders, their customers, and all other orders of those customers. Minor: you get those orders and their customers only.

  • Selecting more records in the child can pull in more parents, which pull in more children, and so on until no related records remain (p.108).
  • For a smaller subset, choose the Referential Integrity Only option in a plan at run time. The data stays referentially intact, but it may not include every child of a parent, so transactional integrity might not be kept.
  • If constraints form cycles, or an object has more than one major parent constraint, TDM does recursive evaluation and needs a staging connection. Using the source connection as the staging connection is recommended (p.109).

12.11 Performance and accuracy tips collected from the guide

The guide has no dedicated performance section for discovery. These tips are scattered through the chapter; I collected them and cite where each came from.

  • Cap the sample. Primary key profiles default to 1,000 rows and data domain profiles to 1,000 rows (pp.93, 95). Column profiles default to All rows (p.98), the heaviest setting. A small sample is fast but may call a column "unique" or "an SSN" wrongly (my reasoning).
  • Limit key columns. The Primary Key Rows option (default 3) caps how many columns are combined (p.93). Fewer is cheaper.
  • Be careful with case-sensitive entity comparisons. The guide warns they can affect profile performance (p.99).
  • Search names first, then data. You can run a data domain profile on column metadata and then again on the data (p.100). Name checks are cheaper than reading values.
  • Pick only domains you need. A disabled domain is excluded from profiles (p.75), and choosing a policy includes all its domains at once (p.100).
  • Combine profile types. Data domain and primary key profiles can run together (p.87).
  • Import metadata directly from the database when the source has many tables, instead of through PowerCenter or the Model repository (p.60).
  • Use the same connection for import and profile to avoid unexpected results (p.88).
