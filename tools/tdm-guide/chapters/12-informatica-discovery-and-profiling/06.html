12.12 Hands-on labs: profiling, masking and subset on ShopSphere

The syllabus lists three hands-on items that start from profiling: TDM_Handson1 (TDM and data profiling), TDM_Handson2 (data profiling and masking) and TDM_Handson3 (data profiling and subset). The syllabus gives only these titles. I do not know the exact tasks your trainer sets, so the three labs below are my reconstruction, built so they chain together on the shared ShopSphere example.

What is from the guide and what is illustrative

Every click path below (menu names, dialog names, option names) comes from the User Guide 10.5.10 and carries a page number. The ShopSphere choices (project name, profile names, which results you approve, and the expected result tables) are illustrative: they show what a sensible outcome looks like on our fictional data. Your own installation will show different numbers and may use different labels. If you have no TDM installation, do each lab on paper using the sample tables, then compare.

Starting point for all three labs: a TDM environment where an administrator has already created the database connection to ShopSphere, the Data Integration Service and the Model Repository Service connections (p.92), and you have Write permission on the project (see the permissions section of the tour). The sample rows are the shared ShopSphere rows: customers 1001 Asha Menon, 1002 Ravi Kumar, 1003 Meera Nair.

Lab 1 (TDM_Handson1): TDM and data profiling

Goal: bring ShopSphere into a project, discover sensitive columns, and approve the results. This lab uses the policy and domain you built in the guided tour; if you skipped it, use the PII policy pack that ships with TDM (p.77).

  1. Create the project.

    Projects > Actions > New; Name CustomerOrders, then OK (pp.53-54). Illustrative name. A project is where profiles and results live.

    The project opens in a new page.

  2. Import the four tables.

    In the project click Actions > Import Metadata, choose Datasource Connection, pick the ShopSphere schema, select CUSTOMERS, ORDERS, ORDER_ITEMS, PRODUCTS, choose Import Now (pp.66-67).

    Import Progress finishes and the tables appear in the Data Sources view.

  3. Add the policy to the project.

    Use the Policies tab on the project Overview (p.50) to add ShopSphere_Customer_PII or a PII pack policy. A data domain profile can only use domains from policies in the project (p.100).

    The policy and its domains are listed in the project.

  4. Create a data domain profile.

    Discover > Profile > Actions > New Profile; name dd_customers; type data domain; select CUSTOMERS; choose the policy; sampling Data and Column Name; Maximum Rows 1,000; a Minimum Conformance Percent such as 80 (illustrative value); Save (p.100).

    Why both data and name: a mismatch between them (an SSN-shaped value in an oddly named column) is exactly what profiling exists to catch.

  5. Execute and monitor.

    Actions > Execute. Open the project's Monitor view and wait for the job to finish (pp.92, 101).

    The job shows a completed status.

  6. Close and reopen the profile, then open Profile > Data Domain.

    The guide says results appear only after reopening (p.103, 105).

    Rows for CUSTOMERS columns with a Profiled data domain column and conformance percentages.

  7. Preview, then approve.

    Select ssn, open Data Preview, and confirm the first values look like 123-45-6789. Approve the rows you agree with, and Reject or fix any wrong match (p.105). Then mark the classification completed.

Show a worked answer

Illustrative result: first_name to First Name, last_name to Last Name, email to Email Address, phone to Phone, ssn to Social Security Number, date_of_birth to Birth Date, zip_code to ZIP, all approved. tax_id has no match, so open Discover > Columns and set its Domain by hand (p.95), or add a domain for it. After this lab, Discover > Columns lists those columns as sensitive, because assigning a domain marks a column sensitive (p.89).

What if it fails? No results after reopening usually means the job failed or did not finish: check Monitor and the TDM job log (p.33). A connection error at Execute points to the discovery connection setup (p.92). A column that you know is an SSN but does not match: check the pattern and conformance threshold on the domain, and remember patterns are case sensitive (p.74).

Lab 2 (TDM_Handson2): data profiling and masking

Goal: use the approved domains from Lab 1 to mask CUSTOMERS in a test schema. The profiling steps are from the guide. The masking steps are only outlined here, because the Informatica masking chapter covers rule types and plan settings in detail.

  1. Check that the domains are approved.

    Open Discover > Columns and confirm each personal column has a Domain and is marked sensitive (p.89). If not, finish Lab 1 step 7 first.

    Columns such as ssn and email show a domain name.

  2. Assign the domain rules in Define > Data Masking.

    The guide says that once you approve a domain for a column, you assign the domain's rules in the Define > Data Masking view (p.105). The default rule of each domain is applied to its columns; you may switch a column to another preferred rule (p.73).

    Each approved column shows a masking rule in that view.

  3. Handle keys so masking does not break links.

    Check that customer_id has primary key and foreign key constraints (add them by hand if profiling did not). Auto cascade then masks the parent and child keys with the same value (p.91). If you will mask customer_id itself, this is essential.

  4. Create a masking plan.

    Project > Execute: create a data masking plan and assign the policy, with a target connection to a test schema, never production (pp.31-32). Remember that TDM overwrites existing data in the target schema (p.31).

  5. Generate and run the workflow, then monitor.

    Generate the workflow from the plan and run it, then watch Monitor (pp.32-33).

    The workflow job completes; a Row Count Report on the successful run shows rows affected (p.33).

  6. Verify.

    Query the test target. The guide's example has the compliance officer validate the results (p.34).

Lab 3 (TDM_Handson3): data profiling and subset

Goal: discover keys and relationships, approve them, and set up a subset of ShopSphere customers. Profiling steps are from the guide. The subset plan itself is outlined; the Informatica data subset chapter gives the details.

  1. Pretend the metadata has no declared keys.

    This matches the guide's example database (pp.33-34) and gives profiling something to find. If your imported tables already show keys under Discover > Tables > Constraints, you can disable the physical keys on the Columns tab to practise (p.88-89), or just read along.

  2. Create a primary key and entity profile.

    Discover > Profile > Actions > New Profile; name pk_entity_shopsphere; choose primary key and entity; select all four tables; Sampling Options: key columns maximum 3, Max Rows 1,000, conformance 99 (the guide's defaults, pp.93, 99); Save.

    Why combined: an entity profile alone returns nothing when there are no physical keys (p.93).

  3. Execute, monitor, close and reopen.

    Actions > Execute; wait in Monitor; reopen the profile (p.103).

    Primary Key and Entity views show candidates.

  4. Approve primary keys.

    On Profile > Primary Key, approve the true identifiers (customer_id, order_id, item_id, product_code) and reject unique-but-wrong candidates like email or ssn (p.104).

    Approved rows show status Approved; the keys are on the tables in the TDM repository.

  5. Approve entity constraints.

    On Profile > Entity, select an entity, check the Constraints view for parent and child columns, and approve the constraints and the entity you want (p.104).

    The logical relationships CUSTOMERS to ORDERS to ORDER_ITEMS exist.

  6. Set the severity.

    On the constraints, choose Major for ORDERS to CUSTOMERS if you want a customer's other orders to follow a filtered order, Minor if not (pp.108-109). Our design choice.

  7. Define the subset structure.

    In Define, create an entity with CUSTOMERS as the driving table (p.107) so TDM adds ORDERS and ORDER_ITEMS by constraint, and a group for PRODUCTS, so the whole product list is copied as reference data (a group holds tables without tying them to the entity; p.32, p.51; that choice is ours). Create a subset plan with a filter on a parent-table column and run it as described in the subset chapter.

Show a worked answer

Illustrative result. Filtering CUSTOMERS to customer_id < 1003 keeps customers 1001 and 1002, all their orders and all items of those orders, with no orphan rows, plus the PRODUCTS in the group. Customer 1003 and her orders are absent. Verify by counting rows per table in the target and joining child to parent: the join should drop no rows.

If the subset has orphans, look first for a missing or disabled constraint. If the subset is far larger than expected, a Major constraint is probably pulling in whole families of related rows (p.108). If cycles are involved, a staging connection is required (p.109).
