12.6 Entity (foreign key) discovery

An entity is a parent table plus its related child tables. An entity profile finds possible entities by comparing column names in the source tables, and returns a list you choose from. The entities you define for a subset determine the structure and content of the subset database (User Guide 10.5.10, p.93).

The guide's example: Employee, Employee_Detail and Employee_Address all contain an EmpID column, so the profile suggests Employee as an entity with two direct relationships and two child tables. You select Employee as the entity. Later, a subset filter on EmpID (for example EmpID less than 2000) filters each table in the entity relationship (p.93).

ShopSphere reading (illustrative): customer_id appears in CUSTOMERS and ORDERS; order_id appears in ORDERS and ORDER_ITEMS; product_code appears in ORDER_ITEMS and PRODUCTS. The profile can therefore suggest CUSTOMERS to ORDERS to ORDER_ITEMS as a chain, and ORDER_ITEMS to PRODUCTS as another link.

Needs keys, or run both together

If you choose the Entity type and the physical database has no primary keys, the profile returns no results. If you run it as a primary key and entity profile, it discovers possible primary and foreign keys and returns results even without physical keys (p.93). The creation steps repeat the advice: select primary key and entity profile if the database has no primary keys (p.99).

Creating an entity profile

  1. Open the project, Discover, then Profile.

    The Profile view lists the project's profiles.

  2. Click Actions > New Profile.

    Enter a name and description.

  3. Choose to create an entity profile.

    Select primary key and entity if the physical database has no primary keys, as above.

  4. Click Next, select tables, click OK, then Next.

    Choose all tables that may relate.

  5. On Sampling Options, set the key-column maximum, the maximum rows, the minimum conformance, and the entity options from the table above.

    Defaults are fine for a first run.

  6. Click Save, then Actions > Execute.

    Follow the job in Monitor.

12.7 Data domain discovery

A data domain profile finds the source columns that hold similar data and assigns each the same data domain name, so you can apply the same masking rules to all of them at once (User Guide 10.5.10, p.94). Domains are defined with regular expressions on data and on column names (see the data domains section of the Test Data Manager tour). A project must contain policies before you create a data domain profile, because policies hold the domains the profile can search for (p.100).

Sampling options for a domain profile

OptionMeaning (p.95)
DataSearch for patterns in the data only.
Column NameSearch for patterns in the column name only.
Data and Column NameSearch both.
Maximum Rows to ProfileLimit rows profiled. Default 1,000.
Minimum Conformance PercentMinimum percentage of rows in which the data or metadata matches the domain.

Why a conformance percent? Real data is messy. If 97 of 100 rows look like SSNs and three are blank or mistyped, a threshold lets the column still match. The guide says all rows might not conform, so you enter the minimum percentage of profiled rows that must (p.100).

Creating and running a data domain profile

  1. Open the project, click Discover, then Profile, then Actions > New Profile.

    You need a policy in the project first.

  2. Enter a name and description; choose a data domain profile.

    For ShopSphere: dd_customers.

  3. Select the tables to profile and click OK, then Next.

    Start with CUSTOMERS.

  4. In Select Sampling Options, choose to add policies or data domains, then select them.

    Selecting a policy includes all its domains, which is faster to set up than ticking each one.

  5. In the Sampling panel, choose Data, Column Name, or Data and Column Name.

    You can run the profile for column metadata and then again for source data.

  6. Enter the maximum rows to profile and the minimum conformance percent.

    Defaults are a sensible start.

  7. Click Save, then Actions > Execute.

    Watch Monitor; when done close and reopen the profile.

Assigning domains by hand, and by CSV

Discovery is a suggestion, so you need ways to correct it (pp.95-96).

  1. One column: in Discover > Columns click the Domain cell of the column and choose a domain.

    The column is marked sensitive automatically.

  2. Many columns: select the columns, click Actions > Edit Assignments, choose the domain in the Edit Data Domain Assignment dialog, Save.

    Choosing a blank domain removes the previous assignment.

  3. Export or import as CSV: Actions > Export Data Domain Assignments, or Actions > Import Data Domain Assignments and pick the CSV, Finish.

    You need read and write permission on the project and the Discover Project privilege.

The import file must have these columns in order: Data Source Name, Owner Name, Table Name, Column Name, Is Sensitive, Domain Name. The first row is treated as a header and skipped, so a file without a header loses its first data row. Records import one at a time; a failure is logged and the import continues with the next record. Errors appear in Administrator > Application Logs. If an assignment already exists it is overwritten. Assignments exported from Secure@Source can be imported this way (p.96).
