28.4 Lab 4: create a connector to a VDB (TDM_Handson4)

Goal

Create an application, an environment and a database connector in the masking engine so that the engine can reach the ShopSphere VDB, and prove the connection works. This is the foundation for every later lab: no connector, no rule set, no profiling, no masking.

Prerequisites

  • The setup data from the previous section is loaded in the VDB, and you saved the "before" snapshot.
  • From your trainer or DBA: the database type, host name or IP, port, database name, schema name, and a masking user name and password. If you do not know a value, ask. A wrong guess here is the most common reason Test Connection fails.
  • The VDB is running and its host and port are reachable from the masking engine.

What "a connector to a VDB" means

The documentation pages I read do not describe a special "VDB connector". They describe database connectors, and they describe a VDB as a database that Delphix Continuous Data provisions (Delphix masking terminology). My reading, which you can confirm with your trainer, is that the masking engine treats a VDB like any other database: you create an ordinary database connector and point it at the VDB's host, port and database name. The word "VDB" tells you where the data lives, not which button to press.

Why a VDB and not production?

Masking an in-place job rewrites data. Doing that on a disposable VDB leaves production untouched and the VDB can be refreshed or rewound afterwards. The Delphix docs state this recommendation directly on the preparing-data page and add that Selective Data Distribution is advised for extra protection when masked copies are sent onward. When masking is part of VDB provisioning, the docs restrict the setup further (for example, only in-place jobs, and basic connectors) and list the details on the Provision masked VDBs page. This lab does not provision a masked VDB; it connects to an existing one.

Steps

  1. Log in to the masking engine and open the Environments page.

    Environments is the first screen after login and lists every environment your user may see. You start here because everything else (connectors, rule sets, jobs) hangs under an environment.

    A grid with the columns ID, Application, Environment, Purpose and Approval, plus buttons + Application, + Environment and an Actions menu.

  1. Add the application.

    Click + Application, type ShopSphere and click Save. The docs say an application must exist before an environment can be created, and that it is a tag that groups environments for the same real application.

    You return to the Environments list. The new application appears in the Application drop-down of the next dialog.

  2. Add the environment.

    Click + Environment. Choose the application ShopSphere, name the environment ShopSphere_DB_Mask, set Purpose to Mask, and leave the approval-workflow checkbox off. The docs say the purpose is either Mask or Tokenize/Re-Identify, and that the approval workflow (database rule sets only) makes an approver sign off the inventory before any masking job may run. It is useful in real projects, and an extra hurdle in a first lab. Click Save And View to land on the new environment's Jobs screen.

    The environment page shows three tabs: Jobs, Rule Sets and Connectors, all empty.

  3. Open the Connectors tab and click + Connection.

    The Connectors screen lists every connector in the environment, grouped by Meta Data Source (Database, File or Mainframe). The Create Connection wizard opens with the steps Details, Credentials, Custom Properties and Summary.

  1. Details step: name the connector and choose the source type.

    Enter SS_VDB_Conn as the Connection Name. In the Source Type drop-down each entry is prefixed with its Meta Data Source, for example "Database - Sybase" in the screenshot. Choose the type that matches your VDB. For Oracle, MS SQL Server and Sybase you also choose a connection mode: Basic (host and port) or Advanced (a full JDBC URL). Pick Basic unless your trainer says otherwise.

    The Next button becomes active. Test Connection and Save are also visible, but Test Connection needs the credentials from the next step.

  1. Credentials step: fill in the database facts.

    The fields depend on the database type. The docs list, among others: Schema Name (the schema that holds the tables this connector will access), Database Name (case-sensitive: it must match the name the database instance knows), Host Name/IP, Port (for MS SQL Server optional with a default of 1433), SID (Oracle only) and Instance Name (SQL Server only; if given, the port is ignored and port 1434 of the SQL Server Browser Service is used, so the firewall must allow it). Then give the user name and password of the masking user.

    All required fields are filled. The password shows as dots.

  1. Custom Properties step: skip it.

    This step lets you upload a Java properties file for extra JDBC settings. Skip it for the lab. The docs warn that property values in such a file are not hidden: anyone who can view connectors can read a password written there, so sensitive values belong in the form fields.

  2. Click Test Connection.

    The docs say the engine uses the wizard's information to attempt a database connection and then shows a success or failure message. You test now, before saving, so you can fix mistakes while the form is still open.

    A message that the connection succeeded. If it failed, read the message, correct the field it points at and test again.

  3. Review the Summary step and click Save.

    The Summary lists everything you entered. Saving creates the connector.

    You return to the Connectors tab. SS_VDB_Conn appears under the DATABASE group with a Connector ID.

  4. Test the saved connector from the grid.

    Click the actions menu (the three dots) on the connector's row and choose Test Connection. This second test proves the saved connector works, not just the form.

Verification checks

  1. Test Connection succeeds twice: once in the wizard and once from the grid. Screenshot the success message.
  2. SS_VDB_Conn is listed under DATABASE with a numeric Connector ID and no warning triangle next to its name. Note the ID: the docs say the numeric ID is what the masking API uses to refer to the connector.
  3. In your SQL client, confirm the masking user can see the data the engine will see: SELECT COUNT(*) FROM customers; returns 3 (or your row count) when run with that user.
  4. Write down the exact database name, schema name and host you used. Lab 5 and the evidence pack both need them.

What can go wrong

SymptomLikely causeWhat to do
Test Connection fails with a "database not found" style errorDatabase Name typed with the wrong capital letters (docs: the field is case-sensitive)Copy the name exactly from the DBA; retest
Test Connection hangs or times outHost, port or firewall between engine and VDBCheck from the engine network; for SQL Server with an instance name also allow port 1434
Login failsWrong user or password, or the user cannot log in from the engine's addressAsk the DBA; use the dedicated masking user
Connector saves but a warning triangle showsAuthentication is incomplete (docs: hover the icon to see which item is missing)Edit the connector, tick the Change Password box if needed, re-enter the secret
Test passes but Lab 5 cannot list tablesMasking user lacks rights on the schema, or the Schema Name is wrongCheck schema name and grants; profiling needs schema view and read rights
You cannot find where to add a "VDB" connectorThere is none; it is a normal database connectorChoose the VDB's database type as Source Type

Where masked provisioning fits (read only, no lab step)

Some teams do not run a separate masking job at all. They attach a multi-tenant masking job to a dSource and tick "Mask this VDB" when they provision a new VDB, so that masking runs as part of provisioning. The docs describe this on the page linked above, with several restrictions: for example, only Oracle, MS SQL Server and Sybase are supported, only in-place jobs can be selected, and a single masking job cannot be assigned to several VDBs at once. The screenshot shows the Masking step of the Provision VDB wizard.

What to say in the walkthrough

"I created an application and a masking environment, then a database connector that points at the ShopSphere VDB, not production. I entered host, port, database name and schema from the DBA, tested the connection in the wizard and again from the grid, and both passed. The connector has an ID and no warning icon. I used a dedicated masking user, and I kept the password out of the custom-properties file because that file is readable by anyone who can view connectors."

If asked "is a VDB connector different?": "In the documentation I read, there is no separate type; the engine just needs a database it can reach. The VDB matters because it is safe to change."
