28.1 Words to know first

Masking engine
The Delphix Continuous Compliance engine: the web application where you define connectors, rule sets, profiling jobs and masking jobs. The docs also call it the Compliance Engine.
VDB (virtual database)
A full read-and-write copy of source data that Delphix Continuous Data provisions from a dSource or another VDB. To the masking engine it is just another database to connect to. See the Delphix overview and terminology chapter.
Application
A tag assigned to one or more environments, ideally named after the real application. Here: ShopSphere.
Environment
A container that groups connectors, rule sets and jobs for one set of data sources. Its purpose is Mask or Tokenize/Re-Identify.
Connector
The saved connection details the engine uses to reach one database or one file location. Lab 4 builds one. The connectors and VDB chapter explains the types.
Rule set
The list of tables (or files) in one data source that you want to profile or mask. Its inventory records, per column or field, the domain and algorithm. See the rule sets and keys chapter.
Profiling job
A job that inspects the rule set and assigns a domain, and with it a default algorithm, to columns that look sensitive. See the Delphix profiling chapter.
Domain
A named kind of sensitive data (FIRST_NAME, SSN, ZIP) that carries one default masking algorithm.
Inventory
The table of "which column gets which algorithm" for one rule set.
In-place and on-the-fly
In-place masking updates the data where it sits. On-the-fly masking reads from a source and writes masked values to a different target. Both are job settings, explained in the algorithms and masking jobs chapter.
Non-conformant data
A value that does not fit the format an algorithm expects. By default it is left unmasked and the job records a warning, so a "successful" job can still leave data unmasked.

28.3 Setup data for every lab

All five labs use the ShopSphere tables from the guide's running example. The data is entirely fake. Everything below is my design for the lab, not something Delphix provides.

The database side

Ask your trainer which database holds the lab copy. The masking engine needs a database it is allowed to change, so the lab copy should be a VDB or another disposable copy, never SHOPSPHERE_PROD. The docs recommend a VDB as the masking target and call it the best security practice because the database runs in a sandboxed environment (Preparing data).

The VDB holds the four ShopSphere tables. Three customer rows are enough to see every effect, and the lab adds the tax and zip columns used by later labs:

Prerequisites for the whole series

  • A login to the masking engine with a role that can add environments, connectors, rule sets, inventories and jobs, and run jobs. The docs describe roles such as Administrator, DBA, SME and Operator; ask your trainer which one you hold (Users and roles).
  • Network access from the engine to the database host and port, and a database user created for masking. The docs recommend a separate masking user with read, write, update and, if you use those job options, index, trigger and constraint rights (Database user permissions). Profiling alone needs only schema view and read rights.
  • A SQL client that can query the VDB, so you can compare data before and after masking.
  • A way to read the two files (a text editor or cat) and to compare them (diff or a spreadsheet).

The "before" snapshot belongs in the evidence pack, so take it now. Run these once and save the output:

SELECT customer_id, first_name, last_name, phone, ssn, zip_code, tax_id
FROM   customers
ORDER  BY customer_id;

SELECT COUNT(*) AS customers FROM customers;
SELECT COUNT(*) AS orders    FROM orders;
SELECT COUNT(*) AS items     FROM order_items;
SELECT COUNT(*) AS orphans
FROM   orders o LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE  c.customer_id IS NULL;

The last query counts orders whose customer does not exist. It must return 0 before and after masking. If it is not 0 before you start, the lab data is already broken and the later "keys survived" check means nothing.

Why take a "before" snapshot at all?

A masking job reports success even when a column was never masked (non-conformant data is skipped with a warning by default). Only a comparison of the data itself proves the job did its work. The snapshot is the proof's left-hand side.
