28.1 Words to know first

Masking engine
The Delphix Continuous Compliance engine, where you define connectors, rule sets, profiling jobs and masking jobs.
VDB (virtual database)
A full read-and-write copy of source data that Delphix Continuous Data provisions from a dSource or another VDB. To the masking engine it is another database. See the Delphix overview and terminology chapter.
Application and environment
An application is a tag for the real system (here ShopSphere). An environment groups connectors, rule sets and jobs; its purpose is Mask or Tokenize/Re-Identify.
Connector
Saved details the engine uses to reach one database or file location (connectors and VDB).
Rule set and inventory
A rule set lists the tables or files to profile or mask. Its inventory records, per column or field, the domain and algorithm (rule sets and keys).
Profiling job, domain
A profiling job assigns a domain (a kind of sensitive data such as FIRST_NAME, with one default algorithm) to columns that look sensitive (Delphix profiling).
In-place and on-the-fly
In-place masking updates data where it sits; on-the-fly reads a source and writes masked values to a target (algorithms and masking jobs).
Non-conformant data
A value that does not fit what an algorithm expects. By default it is left unmasked and the job records a warning, so a "successful" job can still leave data exposed.

28.3 Setup data for every lab

All labs use the ShopSphere tables. The data is entirely fake and the setup is my design.

The database

Ask your trainer which database holds the lab copy. It must be one the engine may change: a VDB or other disposable copy, never SHOPSPHERE_PROD. The docs recommend a VDB as the masking target and call it the best security practice because it runs in a sandbox (Preparing data). Load the four ShopSphere tables with three customers (plus two or three orders each and a few items and products):

The table omits email and date_of_birth for width; the other columns are as in the running example. Take the "before" snapshot now and save the output:

SELECT customer_id, first_name, last_name, phone, ssn, zip_code, tax_id
FROM   customers ORDER BY customer_id;

SELECT COUNT(*) AS orphans
FROM   orders o LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE  c.customer_id IS NULL;

The orphan query counts orders whose customer is missing. It must return 0 before and after masking; if it is not 0 now, the "keys survived" check later means nothing. A masking job can report success while a column was never masked, so only a comparison of the data proves the work: the snapshot is the left-hand side of that proof.

Prerequisites

  • A login with a role that can add environments, connectors, rule sets and jobs and run jobs; ask which one you hold (Users and roles).
  • Network access from the engine to the database, and a masking user. The docs recommend a separate masking user with read, write and update rights plus index, trigger and constraint rights if you use those job options; profiling alone needs schema view and read (Database user permissions).
  • A SQL client, and a text editor and diff for the files.
  • Job and object names must be unique on the engine (the docs say job names are unique across the application), so add your initials if learners share one.
