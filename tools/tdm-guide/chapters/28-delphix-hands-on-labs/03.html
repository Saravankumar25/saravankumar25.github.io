28.5 Lab 5: create a rule set and profile the VDB (TDM_Handson5)

Goal

Turn the connector from Lab 4 into a rule set that lists the four ShopSphere tables, run a profiling job over it, read what the profiler found, and correct anything it got wrong. At the end you have an inventory: a table that says which column gets which domain and algorithm.

Prerequisites and setup data

  • Lab 4 is finished: connector SS_VDB_Conn tests successfully.
  • The CUSTOMERS, ORDERS, ORDER_ITEMS and PRODUCTS tables exist in the VDB. The concepts behind this lab are in the rule sets and keys chapter and the Delphix profiling chapter.

Steps

  1. Open the environment's Rule Sets tab and click + Rule Set.

    A rule set is the engine's "shopping list" of tables. Profiling and masking jobs both work on a rule set, never on a connector directly.

    A dialog asks "What type of data does this Rule Set contain?" with four choices: Database, Semi-Structured Files (JSON or XML), Flat Files (delimited or fixed-width) and Copybook (mainframe).

  1. Choose Database, click Continue, and fill in the Details step.

    Name the rule set SS_DB_RS and pick SS_VDB_Conn from the connector drop-down. The docs say the drop-down lists only connectors that match the chosen type; if it is empty, you have no suitable connector yet.

  2. Data Tables step: click Add Tables and select the four tables.

    The Add Database Table dialog lists the tables the connector can see. Tick CUSTOMERS, ORDERS, ORDER_ITEMS and PRODUCTS and click Save. The docs note that this dialog shows tables only, not views, indexes or stored procedures.

    The grid shows four rows with the columns Table Name, Logical Key, Filter and Custom SQL. Logical Key, Filter and Custom SQL are empty.

  1. Check keys before you save.

    Each table should have a primary key. The docs explain what happens otherwise: with in-place masking and no primary key, you must name an existing column as a logical key (it does not change the database; it only tells Delphix how to identify a row). If you give neither, the engine creates an identity column, which needs permission to change the schema, and the job may fail without it. All four ShopSphere tables have primary keys, so leave Logical Key empty.

  2. Click Next, review the Summary, and click Save.

    For a database rule set the save is an asynchronous task: a task ID appears in a bottom message, and you can watch it under Monitor, Async Tasks. The engine is reading the table definitions from the database in the background.

    The rule set SS_DB_RS appears in the Rule Sets grid. The docs say the Refresh/Save icon shows an hourglass while the engine rescans tables; in the official grid screenshot finished database rule sets show a green tick.

  3. Run the rule set Checklist.

    In the rule set's actions menu choose the verify (Checklist) action. The docs describe an Identity Column check: every table must have a primary key, an indexed identity column or a logical key. Catching a missing key now is cheaper than a masking job that fails later.

  4. Create the profiling job.

    Go to the Jobs tab, click + Profiling Job, and fill in the wizard. Job Name: SS_Profile_DB (must be unique). Rule Set: SS_DB_RS. Profile Set: ASDD Standard, the set recommended for databases (Out of the box profiling settings). Leave Multi Tenant, Multiple Profiler Expression Check and "Clear previous auto domain assignments" unticked for the first run.

  1. Configuration step: keep the defaults.

    Number of Streams defaults from an application setting (the screenshot shows 1). Feedback Size, Min and Max Memory, Comments and Email are optional. The docs add one rule worth remembering: with an ASDD profile set, Max Memory must be at least 1024 MB for each stream, so 4 streams need 4096 or more. Click Next, check the Summary and Save.

  1. Run the job.

    On the Jobs tab open the row's actions menu (the three dots) and click Run. The engine first checks free memory and the number of simultaneous jobs (the docs give a default limit of 7) and may queue the job instead of starting it.

    The job's Status changes from CREATED to QUEUED or RUNNING and then to SUCCEEDED. WARNING or FAILED means you must read the logs before moving on.

  1. Read the Profile Results.

    Click the job name (or use Monitor, Job Executions). The docs say a finished profiling job shows the findings table by table and column by column under Profile Results. For a database you can also open the rule set: the assigned algorithm column in the inventory is the result.

  2. Open the inventory and correct the findings.

    Click the rule set name to open its inventory. For any column the profiler got wrong, click the Edit icon in the Actions column. Untick Enable Automatic Updates first: while it is ticked, a later profiling run may overwrite your choice. Then pick the Domain and Algorithm you want and click Save. To record the proof, use Actions, Export Rule Set: it downloads the inventory as a CSV.

Verification checks

  1. The profiling job ends SUCCEEDED, and the Execution Summary lists all four tables as profiled with none remaining.
  2. The inventory shows a Domain and an Algorithm for each of the eight sensitive ShopSphere columns above, or you have recorded which ones are missing and fixed them by hand.
  3. No key column (customer_id, order_id, item_id) has an algorithm. Masking a primary or foreign key without a plan breaks joins.
  4. Export Rule Set and keep the CSV. This is your record of "what did the profiler find and what did we decide".

What to say in the walkthrough

"I built a database rule set with the four ShopSphere tables on the VDB connector and ran the identity-column checklist. I ran an ASDD Standard profiling job. It flagged first name, last name, email, phone, SSN, date of birth, zip and tax id by their column names and types. I did not mask any key column. Where the default algorithm was not what the data needs, I switched off automatic updates and set my own, and I exported the inventory as a CSV for the sign-off."

If asked "does profiling look at the data?": "ASDD has both name-based and data-based classifiers. For a column like a six-digit postal code, the name rule does the finding, because the data rule I read targets US formats."
