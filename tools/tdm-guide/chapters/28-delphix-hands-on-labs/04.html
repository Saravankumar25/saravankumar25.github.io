28.6 Lab 6: mask a delimited and a fixed-width file (TDM_Handson6)

Goal

Mask the customer files customers.dat (pipe-delimited) and customers_fixed.txt (fixed-width) with the file side of the engine. Files carry no built-in description of their columns, so this lab adds one step the database labs did not need: telling the engine what the fields are, with a file format.

Prerequisites and setup data

  • The two files from the setup section exist in a working folder, and the originals are copied to a separate original folder.
  • You know how the engine reaches that folder. The docs list the connection modes Filesystem Mount Point, SFTP, FTP, FTPS (mainframe datasets only), AWS S3, Other S3 Compatible Storage and Azure Blob Storage. Ask your trainer which one the lab uses. A mount point also needs a mount created through the Mount Filesystem API before you can pick it in the connector (Managing remote mounts). The file concepts are in the file masking chapter.
  • A new environment named ShopSphere_File_Mask (same steps as in Lab 4, Purpose: Mask).

Steps

  1. Create two file connectors.

    In the new environment open Connectors, click + Connection, and choose a File source type: Delimited for SS_Delim_Conn and Fixed Width for SS_Fixed_Conn. The type matters because it decides what the rule set will ask for later. For SFTP the credential step asks for Path (the directory that holds the files), Server Name, Port and User Name, plus Password or a public key. The docs add that, from version 6.0.9.0, an "User Directory as root" option exists when the path is relative to the SFTP user's home directory. Test the connection if the wizard offers it.

    Both connectors appear under the FILE group in the Connectors grid, with types Delimited and Fixed Width.

  2. Write the two format files.

    The docs say the engine needs a description of the fields and that a format file contains only the structure, never production data or personal information. For a delimited file the format file lists the field names, one per line, with no header. For a fixed-width file each line is a field name, a comma and the field length. The two official sketches below show the shape.

    My versions for ShopSphere, saved as ss_delim.fmt and ss_fixed.fmt:

    customer_id
first_name
last_name
ssn
phone
    customer_id,4
first_name,10
last_name,10
ssn,11
phone,10

    Give the fields meaningful names. The profiler uses names (and, with ASDD, values) to decide what is sensitive, so first_name is findable and FIELD_03 is not. On Windows, save with LF line endings, because the docs warn that CRLF files can fail the engine's validation.

  1. Import the formats.

    Go to Settings, Data Formats, tab Files, click + File Format. The wizard asks for the Format Type, then the file to import (a custom name is optional), then, for delimited and fixed-width formats only, the number of header and footer records (leave them empty: the lab files have none), and ends with a Summary. Save. Do this twice, once per file type.

    Both formats appear in the Data Formats grid with their Type (Delimited or Fixed Width).

  1. Create a flat-file rule set for each file.

    In the environment's Rule Sets tab click + Rule Set, choose Flat Files, and pick the matching connector. In the Data Files step click Add File Name, tick customers.dat (or customers_fixed.txt), and set its properties: Format File (ss_delim.fmt or ss_fixed.fmt), End of Record (Linux LF unless the file came from Windows), and, for the delimited file, the Delimiter |. Text Enclosure stays empty because the sample has no quotes. Save as SS_Delim_RS and SS_Fixed_RS.

    Each rule set lists one file with its format and delimiter.

  1. Profile both rule sets.

    Create one profiling job per rule set exactly as in Lab 5 (+ Profiling Job, rule set, ASDD Standard) and run them. ASDD supports delimited and fixed-width files. The results grid lists File Name, Field Name, Algorithm and Domain.

    Fields first_name, last_name, ssn and phone get domains. If the field names in your format were meaningless, only a data-level match could find them.

  1. Set the algorithms in the inventory.

    Open each rule set's inventory, choose the file format in the drop-down if asked, and edit the fields: first_name gets dlpx-core:FirstName, last_name gets dlpx-core:LastName, ssn gets dlpx-core:CM Digits (the reason is in Lab 8). Leave customer_id and phone alone in this lab. Untick Enable Automatic Updates first if you override a profiler assignment.

  2. Create a masking job per rule set.

    Jobs tab, + Masking Job. Choose Masking Method In-Place so the working copy is overwritten, pick the rule set, and keep the other settings at their defaults. The docs say in-place jobs update the source with masked values, and on-the-fly jobs read from one place and write to another. A file job does not show the database-options step. Names: SS_Mask_Delim and SS_Mask_Fixed.

  3. Run both jobs and check the status.

    Run, then open Monitor, Job Executions. Click the job name and read the Execution Summary: files masked, rows masked, files with non-conforming data.

    Status SUCCEEDED, rows masked 3 per file, no non-conforming data. A yellow WARNING means some values were left unmasked.

Docs differ slightly on on-the-fly target files

The jobs page says target files are created automatically when the name pattern matches the source (but a database-to-delimited-file job needs the target files to exist beforehand). The connector page says the target rule set must point at an existing entry in the target directory. If an on-the-fly file job masks nothing, create an empty placeholder with the same file name in the target folder and run again.

Verification checks

Run these in a shell on the folder that holds both the masked and the original files:

diff original/customers.dat customers.dat
awk -F'|' '{print NF}' customers.dat | sort | uniq -c
awk '{print length($0)}' customers_fixed.txt | sort | uniq -c
diff <(cut -c1-4,36-45 original/customers_fixed.txt) <(cut -c1-4,36-45 customers_fixed.txt)

The last command compares only the customer_id (characters 1 to 4) and phone (characters 36 to 45) columns of the fixed-width file. It should print nothing. It needs a shell that supports process substitution, such as bash.

  1. Names and SSN differ between original and masked, and the SSN still looks like ddd-dd-dddd.
  2. customer_id and phone are identical to the original (they were out of scope).
  3. Every line of the delimited file has 5 fields, and every line of the fixed-width file is still 45 characters. A different count means the masked value did not fit the field or the format did not match the data.
  4. Row count is unchanged: 3 lines in each file.
  5. Consistency: save the masked files as run1, copy the originals back into the working folder, run both jobs again, and run diff against the run1 copies. It should print nothing, because the docs describe the Name and Character Mapping frameworks as deterministic for the same configuration and key.

What can go wrong

SymptomLikely causeWhat to do
Job succeeds but nothing changedOn-the-fly target file missing, or the file name or pattern does not matchCheck the placeholder file and the File Name or Pattern column of the rule set
A delimited file lost its last fieldsMore fields in the data than in the format file; the docs say extra fields are dropped after maskingAdd the missing field names to the format and reimport; restore from the original
A delimited file gained an extra delimiterFewer fields in the data than in the format (docs: delimiters are appended)Make the format match the data
Fixed-width: the wrong part of the line is maskedA wrong field length shifts every later offsetRecount lengths; the docs warn about exactly this
Fixed-width line got longerA masked name was longer than the field. The docs I read do not say how this case is handledCheck line length; on a copy of the algorithm set a Maximum Masked Name Length (an option of the Name framework)
Format import fails on WindowsThe format file has CRLF line endingsConvert to LF and import again
Warning for a Phone or SSN valueNon-conforming data, such as text in a phone fieldSee the log of the file in Execution Components
What to say in the walkthrough

"Files have no schema, so I gave the engine one: a file format per file type with field names only, no real data. I made a file connector, a flat-file rule set and an inventory per file, profiled them, and assigned FirstName, LastName and a digit-mapping algorithm to the SSN field. I masked in-place on a working copy and compared against the original: the structure is unchanged, 5 fields per line and 45 characters per fixed-width line, and the names and SSNs are different. The same input gave the same output on a second run."
