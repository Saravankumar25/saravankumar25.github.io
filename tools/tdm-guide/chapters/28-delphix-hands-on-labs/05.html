28.7 Lab 7: mask FirstName in the database (TDM_Handson7)

Goal

Run one real in-place masking job on the ShopSphere VDB that changes customers.first_name and nothing else, then prove by query that the job did exactly that. The algorithm rationale is in the algorithms and masking jobs chapter; here you see it work.

Prerequisites and setup data

  • Labs 4 and 5 are done: rule set SS_DB_RS exists and has an inventory.
  • The VDB can be restored if a job goes wrong. Ask how: for example, a snapshot or bookmark taken before the run. The docs I read describe rewind and refresh for masked VDBs only, so I cannot promise the exact route for your VDB.
  • Two extra lab-only things in the VDB (fake data, delete them after the course): a copy table for before/after comparison, and an edge-case customer. The copy table holds unmasked fake data. In real work you would never copy sensitive data next to the masked data.
CREATE TABLE customers_before AS SELECT * FROM customers;

INSERT INTO customers
  (customer_id, first_name, last_name, email, phone, ssn, date_of_birth, zip_code, tax_id)
VALUES
  (1004, 'Asha', 'Iyer', 'asha.i@example.com', 'CALL-ME-NOW', 'N/A',
   '1992-01-15', '560002', NULL);

INSERT INTO customers_before SELECT * FROM customers WHERE customer_id = 1004;

Customer 1004 has the same first name as 1001. Two customers named Asha should receive the same masked first name; that is the consistency check. Its phone and SSN values are deliberately bad: Lab 8 uses them to show non-conformant data.

Steps

  1. Make a rule set that contains only today's masking.

    A masking job masks every column that has an algorithm in the inventory. After Lab 5 your inventory has eight columns assigned. To mask only first_name, duplicate the rule set (the row's actions menu, Duplicate), name the copy SS_DB_RS_FN, and open its inventory. The docs say a copy includes the inventory and any filters. Use the "Clear Masking Assignment" icon on each assigned row (it works per column, as in the profiling chapter): the docs say it removes that assignment and disables automatic updates, after a short confirmation bar. Then edit first_name only.

    The inventory shows an algorithm for first_name and blank algorithm cells for every other column.

  2. Assign the algorithm.

    Edit CUSTOMERS.first_name: untick Enable Automatic Updates, Domain FIRST_NAME, Algorithm dlpx-core:FirstName, Save. This is the algorithm the profiler proposed in the official profiling screenshot, so you are confirming, not inventing.

What the FirstName algorithm does (from its docs page)

From docs It is an instance of the Name framework and needs string input. Null, empty and whitespace-only values are returned unmasked, and it raises no non-conformant-data errors. A single character is treated as an abbreviation and masked to a single character. By default at most two names are masked and returned, and leading and trailing white space is not preserved. It is deterministic for the same configuration and key and it is not unique: collisions are possible, and a masked value can even equal the input (FirstName, Name framework). The Name framework page adds that its default comparison is case-insensitive, so "Peter" and "peter" mask to the same value.

  1. Create the masking job.

    Jobs tab, + Masking Job. Job Name SS_Mask_FirstName. Masking Method: In-Place. Rule Set: SS_DB_RS_FN. Leave "Stop job on first occurrence" off and Multi Tenant off. Next, the database options: Commit Size and Update Threads can stay default; the docs warn that several update threads can cause deadlocks, especially on tables without an index. Do not tick Disable Constraints, Drop Indexes or Disable Triggers: first_name is not a key. Number of Streams: 1. Save.

  1. Run the Checklist, then run the job.

    The job's Checklist action repeats the identity-column check. Then choose Run in the actions menu. Take the VDB snapshot first.

  2. Watch the execution.

    Open the job name from Monitor, Job Executions. The Execution Summary counts tables and rows masked and, importantly, tables and columns with non-conforming data. The Events list shows the stages in order, from initialising and collecting configuration to job completed. Execution Components lists each table with progress and rows per minute.

    Masking Completed, one table masked (CUSTOMERS), rows masked equal to the row count (4), nonconforming data 0.

Verification checks

-- 1. first names changed
SELECT c.customer_id, b.first_name AS before_name, c.first_name AS after_name
FROM   customers c JOIN customers_before b ON b.customer_id = c.customer_id
ORDER  BY c.customer_id;

-- 2. how many unchanged?
SELECT COUNT(*) AS unchanged
FROM   customers c JOIN customers_before b ON b.customer_id = c.customer_id
WHERE  c.first_name = b.first_name;

-- 3. same input, same output (1001 and 1004 are both Asha)
SELECT COUNT(DISTINCT first_name) AS distinct_masked
FROM   customers WHERE customer_id IN (1001, 1004);

-- 4. nothing else changed
SELECT COUNT(*) AS other_changes
FROM   customers c JOIN customers_before b ON b.customer_id = c.customer_id
WHERE  c.last_name <> b.last_name OR c.phone <> b.phone OR c.ssn <> b.ssn;
  1. Query 1 shows a different name on every row. Query 2 should return 0, but it is not guaranteed to: the docs say the masked value can equal the input. If one row matches, record it and move on; it is a property of the algorithm, not a failure.
  2. Query 3 returns 1: both Asha rows got the same masked name.
  3. Query 4 returns 0 and the "orphans" query from the setup still returns 0.
  4. Screenshot the Execution Summary and save the job report (Report and Logs).

28.8 Lab 8: mask alphanumeric text, SSN and telephone number (TDM_Handson8)

Goal

Mask three different kinds of value with three algorithms, verify format and consistency with queries, and deliberately feed in two bad values to see what non-conformant data looks like in a log. The ShopSphere table has no free alphanumeric column, so this lab adds one, membership_code, such as SS-A7K29X.

Prerequisites and setup data

ALTER TABLE customers ADD membership_code VARCHAR(12);
UPDATE customers SET membership_code = 'SS-A7K29X' WHERE customer_id = 1001;
UPDATE customers SET membership_code = 'SS-B3M81Q' WHERE customer_id = 1002;
UPDATE customers SET membership_code = 'SS-C9D55R' WHERE customer_id = 1003;
-- customer 1004 keeps membership_code NULL on purpose
ALTER TABLE customers_before ADD membership_code VARCHAR(12);
UPDATE customers_before b SET membership_code =
  (SELECT c.membership_code FROM customers c WHERE c.customer_id = b.customer_id);

Then refresh the rule set SS_DB_RS (actions menu, Refresh) so it sees the new column, duplicate it as SS_DB_RS_Sens, clear its assignments, and assign the three below. Lab 7's first-name masking is not repeated here.

Choosing the algorithms

The choice column below separates what the docs state from what I decided. The default algorithm for the SSN domain is not stated in the pages I read, so confirm it in Settings, Domains instead of relying on my memory of any product.

ColumnAlgorithmBasis in the docsDesign choice or caution
membership_code (alphanumeric text)dlpx-core:CM Alpha-NumericMasks ASCII digits, lower and upper case letters, keeps other characters; for non-numeric data types. Example: "ABCxyz123" becomes "HANwhp391"The "SS-" prefix will be masked too. To keep it, a custom Character Mapping instance with a preserve range is the documented route
ssn (text, ddd-dd-dddd)dlpx-core:CM DigitsMasks every digit and keeps letters and punctuation; Character Mapping gives one-to-one output for text inputs and is deterministic until the key changesMy choice. Segment Mapping with dashes ignored is the other documented option for SSNs. The docs I read do not say outputs follow US SSN validity rules
phone (10 digits)dlpx-core:Phone USKeeps the first digits, replaces the three digits before the last four with 555, and masks the last four with a hash of the digits; other characters are preserved; input up to 30 symbols and at least one digitMy choice for a clearly fake number. Phone Unique (last 7 digits hashed) was the profiler's own pick in the official screenshot; the page does not promise uniqueness

Pages: CM Alpha-Numeric, CM Digits, Phone US, Character Mapping and Segment Mapping.

Steps

  1. Assign the algorithms in SS_DB_RS_Sens.

    For each of the three columns, Edit, untick Enable Automatic Updates, set Domain (membership_code has no built-in domain: pick one that fits or leave the domain empty as your engine allows) and Algorithm, Save.

    Three assigned rows, every other column blank.

  2. Create and run the job SS_Mask_Sensitive.

    In-place, rule set SS_DB_RS_Sens, defaults elsewhere. Take the snapshot first. Run it.

    The status is WARNING (non-conformant) rather than SUCCEEDED, because customer 1004's SSN and phone do not fit. This is the expected outcome in this lab.

  3. Read the warning.

    Open the job, then View Logs on the CUSTOMERS row in Execution Components. The docs say each event shows Event type UNMASKED_DATA (or JOB_ABORTED), Cause PATTERN_MATCH_FAILURE, a row count and the column name, and that only a pattern of the bad value is shown (L for letters, N for digits, P for punctuation), never the value itself. For "CALL-ME-NOW" expect a pattern like letters, punctuation, letters, punctuation, letters.

Verification checks

-- SSN keeps its shape and stays unique (rows with a real SSN)
SELECT COUNT(*) AS bad_shape FROM customers
WHERE customer_id <= 1003 AND ssn NOT LIKE '___-__-____';
SELECT COUNT(DISTINCT ssn) AS distinct_ssn FROM customers WHERE customer_id <= 1003;

-- nothing left equal to the original
SELECT COUNT(*) AS unmasked FROM customers c
JOIN customers_before b ON b.customer_id = c.customer_id
WHERE c.customer_id <= 1003
  AND (c.ssn = b.ssn OR c.phone = b.phone OR c.membership_code = b.membership_code);

-- phone pattern, PostgreSQL syntax (use REGEXP_LIKE on Oracle)
SELECT customer_id, phone FROM customers
WHERE customer_id <= 1003 AND phone !~ '^[0-9]{3}555[0-9]{4}$';

-- the edge row stayed as it was, which is the problem to report
SELECT customer_id, ssn, phone, membership_code FROM customers WHERE customer_id = 1004;
  1. bad_shape is 0 and distinct_ssn is 3. unmasked is 0, with the same caution as Lab 7: an equal value is possible but unlikely.
  2. The phone query returns no rows.
  3. membership_code values differ from the originals, keep the "-" and keep the 9-character shape; the NULL stays NULL (the docs say null, empty and whitespace-only values never trigger non-conformant handling in Character Mapping).
  4. Row 1004 still shows "N/A" and "CALL-ME-NOW". These bad values stayed unmasked and produced the warning. In real life this is how bad source data leaks through, so a WARNING status must never be ignored.
  5. Orphan query from the setup: 0. Other columns unchanged.

What to say in the walkthrough

"I matched each algorithm to the kind of value: CM Alpha-Numeric for the membership code, CM Digits for the SSN so the dashes stay and every digit changes, and Phone US for phone so numbers look obviously fake. My checks were shape, uniqueness, no values left equal and no orphans. I planted a bad row on purpose: the job finished with a WARNING, and the log showed the pattern of the bad value, not the value. I would never sign off a run that has an unexplained warning."

Be ready to say which parts are documented (what each algorithm does) and which parts are your own design (choosing CM Digits for SSN).
