Delphix masking: what it is and how it is organised

You have now seen two other families of tools. Informatica TDM is a large suite that discovers, subsets, masks and generates data. GenRocket builds synthetic data from scratch. This part of the guide is about the third tool, Delphix, and more precisely its masking product, called Delphix Continuous Compliance. Its engine finds sensitive values in a database or a file and replaces them with realistic but fictitious ones, so that a copy of production can safely go to testers.

This section maps what the product is for, what its screens look like, which objects the engine keeps (an environment, a connector, a rule set, an inventory and so on), and in what order a masking project touches them. Tool-specific facts are from the Delphix Continuous Compliance documentation, version 2026.5 (documentation home). Delphix releases often, so screens may differ from the pictures here; treat them as a guide to layout.

8.1 Words to know first

These are the words you meet in the first five minutes. Each one gets a fuller treatment later in the chapter.

Continuous Compliance engine
The Delphix product that discovers sensitive data and replaces it with realistic fictitious data. It runs as a virtual appliance (a pre-built machine image), and people also call it the masking engine or the Compliance Engine.
Profiling
Scanning column names and, optionally, the data itself to decide which columns hold sensitive values such as names or Social Security numbers. Delphix documentation also calls this sensitive data discovery.
Masking
Replacing sensitive values with fictitious ones so the original cannot be recovered. It is one-way.
Tokenization
A reversible alternative: values are swapped for meaningless tokens, and the engine can later turn the tokens back into the originals (re-identification).
Application and environment
An application is a label for the system whose data you protect. An environment is the folder-like container, inside one application, that holds your connectors, rule sets and jobs.
Connector
The saved connection details (host, port, user and so on) that tell the engine how to reach one database or one set of files.
Rule set
The list of tables (or files) of one connector that you want to profile and mask.
Inventory
The detailed list of every column or field in a rule set, with its data classification and the masking algorithm chosen for it.
Domain
A named kind of sensitive data (for example "first name") paired with the default algorithm that should protect it.
Algorithm
The recipe that turns one real value into a masked one. A single recipe can be reused on many columns.
Job
A saved, runnable task: a profiling job, a masking job, a tokenization job or a re-identification job.
VDB
A virtual database: a lightweight, writable copy of a database that Delphix's virtualization product creates in minutes. The next chapter explains it from zero.

8.2 What Delphix masking is

8.2.1 The problem it answers

The story is covered in the chapter on sensitive data and regulations and the chapter on masking concepts. Production holds real customers. Testers and developers need data that behaves like production but must not leak real people. The Delphix introduction frames the same problem: breaches, pressure from regulators and the fact that teams also want to move faster. It says that encryption suits data in motion or at rest on disks, but is a poor fit for protecting non-production copies used for development, testing and reporting.

Its answer is masking: replace confidential values (the page names Social Security numbers, patient records and credit card numbers) with fictitious yet realistic data. It adds that masking, unlike encryption, protects data irreversibly in downstream environments, and that masking should stay consistent across different data sources while keeping referential integrity. Referential integrity means that a value which points to another table's row (a foreign key) still points to the right row after masking. That idea drives the rule set and keys chapter.

Why this matters for ShopSphere

ShopSphere's testers need CUSTOMERS, ORDERS and ORDER_ITEMS that join correctly (every order belongs to a customer). If the tool blanked the names but broke the joins, test cases such as "show a customer's last five orders" would return nothing. Realistic and consistent is the whole point.

8.2.2 The platform around it

The masking capability is one part of the Delphix DevOps Data Platform. The introduction page describes four services: virtualize (compressed, lightweight, writable virtual copies), identify and secure (find sensitive values and mask them), manage (provision and audit copies from one point of control) and self-service (let developers and testers refresh, rewind, bookmark, branch and share their copies).

Delphix sells more than one product, and the terminology page separates them. Delphix Continuous Data (the Data Engine) delivers data on demand and creates VDBs (next chapter). Delphix Continuous Compliance (the Compliance or masking engine) discovers sensitive data and replaces it, and is the subject of this whole part. Data Control Tower unifies governance across applications and clouds. The words "engine" and "Delphix" alone are ambiguous, so say which one you mean.

Two numbers that disagree inside the docs

The introduction page says "eighteen algorithm frameworks" in one place and "seven out-of-the-box algorithm frameworks" in another. Both appear in the same page, so no count is quoted here. The algorithms chapter lists the frameworks that the algorithm pages actually describe.

Think of the engine as a three-step assembly line that you configure once and re-run on every refresh: find the sensitive columns, decide what replaces them, apply the replacement.

8.3.1 Finding sensitive data: profiling

The introduction names two methods. Column-level profiling uses regular expressions to scan the names of columns (metadata) against dozens of pre-configured classifiers, for example a pattern that recognises a column called ssn or last_name. Data-level profiling also uses regular expressions but scans the values. You can write or import your own classifiers. When something is judged sensitive, the engine recommends and assigns a masking algorithm.

A regular expression (regex) is a compact pattern language for text. The pattern [0-9]{3}-[0-9]{2}-[0-9]{4} describes the shape of a US Social Security number, so a data-level classifier can ask "do the values in this column match that shape?".

The profiling chapter covers profile sets, domains and classifiers in practice. The object model section shows where they fit. For background on why discovery comes first, see discovery and subsetting concepts.

8.3.2 Replacing the values: masking and tokenization

The docs list two ways to secure data. Masking (also called anonymization on that page) replaces values with realistic, fictitious ones. Tokenization (also called pseudonymization) uses reversible algorithms so the data can be returned to its original state later. The page describes a token as something that conveys no meaning in appearance or format.

ShopSphere example

Row 1001 of CUSTOMERS holds Asha | Menon | asha.menon@example.com | 123-45-6789. After masking, the test copy might hold Divya | Pillai | email9482@example.com | 481-92-3057 (example values): same shape, different person, and nobody can work back to Asha. Tokenization would instead be chosen only if an outside vendor must analyse accounts and ShopSphere must later reverse the result.

Masking is not tokenization

Tokenization is the only reversible method: the engine stores both token and original. Do not use it on a test copy just to "be safe", because the originals stay recoverable by design.

8.3.3 In-place versus on-the-fly

A masking job has a Masking Method: In-Place or On-The-Fly. The job-creation page defines them in one sentence each.

In-Place

The job updates the data in the source environment with masked values. It reads rows, masks them, and writes the masked values back over the originals in the same database.

Consequence: run it on a copy of production, never on production itself. The unmasked originals are gone after the run.

This is why the Delphix pages keep recommending a VDB or other copy as the thing you mask (see the VDB chapter).

On-The-Fly

The job reads unmasked data from a source and writes the masked result to a different target. You choose a source environment and source connector when you define the job.

Consequence: the source stays untouched. The supported pairings are limited: same-type to same-type (Oracle to Oracle, delimited file to delimited file), and database to delimited file.

It needs a second environment and connector for the source side.

One more difference shows up in the keys discussion of the rule set chapter: because an in-place job has to find each row again in order to update it, it needs a key per table. The database preparation pages for SQL Server, Db2 and Sybase offer on-the-fly masking as the alternative when a table has no usable key.

The discovery page names four classifier frameworks. Pairing them with ShopSphere's CUSTOMERS table shows why the engine can use both column names and values. The matches below show what each framework would look at, not output from a real profiling run.

Domains, classifiers, profile sets, roles, inventories and rule sets all use one table component, which the GUI page calls the Grid UI. Learn its few controls once.

8.4.2 Icons worth recognising

The icon reference page explains about thirty-eight icons. The ones you will meet here: Edit, Delete, Duplicate, View, Download, Test Connection, Database and File; five ruleset-refresh icons (success, in progress, failed, waiting, cancelled, and N/A for file rule sets); the job-status icons (success, created, failed, queued, running, skipped, warning); and, beside each table name in an inventory, three icons that update the Custom SQL, the Filter Condition and the Logical Key (shown as a key).

8.4.3 A rule you will trip over: object names

The naming requirements page lists the objects you may name yourself: algorithm, application, connector, domain, environment, file format, job, profiling group, record type, role and rule set. For all of them, leading and trailing spaces are not allowed, and a long list of special characters is rejected, including brackets, braces, parentheses, ~ ! @ # $ % ^ * " ? : ; , / \ ` + = < > ' |. An attempt to create or rename an object with one of them fails with an error. The maximum name length varies by object; the page says to look it up in the engine's API client.

Name things safely

Use letters, digits, underscores and hyphens. SHOPSPHERE_DEV and shopsphere-rules-v1 are fine. ShopSphere (Dev) #1 is not.

8.4.4 Monitor, Admin and Audit in brief

Long actions (saving a database rule set, exporting an environment) return an Async Task ID in a message at the bottom of the screen. Open Monitor > Async Tasks, search that ID, and download an export file or the log of a failed import from the row's Actions menu. Monitor > Job Executions is the history of job runs. Cancelling a RUNNING job leaves semi-masked data, and any indexes, constraints or triggers it dropped are not re-created, so cancel only in an emergency and expect to restore your copy.

Under Admin you find Roles, Users (later in this section), Application Settings (administrators only; engine-wide defaults such as the default update threads, streams and non-conformant data handling, grouped by area), Logs, Utilization (PDF reports of job executions and of database sizes) and About. The Audit tab, open to administrators only, records who did what (create, edit, delete, run, test, import, export, login and more) and can be exported to PDF. For a compliance officer it is the evidence that a masking job ran, and who ran it.

8.6 How a masking project flows

With the objects named, the order of work follows from the nesting: you cannot create a rule set before a connector, and you cannot create a connector before an environment. The documentation's own table of contents for "Connecting data" (environments, connectors, extended connectors, file formats, rule sets, inventories) follows exactly this order, and the Continuous Compliance home page groups the rest as "Identify sensitive data", "Preparing data" and "Connecting data".

Where each step is taught: step 1 and the roles are in this section; steps 2 to 4 in the connectors and VDB chapter; step 5 in the rule sets and keys chapter; steps 6 and 7 in the profiling chapter; step 8 in the algorithms and jobs chapter and, for files, the file masking chapter. Profiling only proposes domains and algorithms; a human, usually the data steward, confirms them.

How a TDM team splits this

The "best practices for defining masking roles" page gives a sample RACI (who is Responsible, Accountable, Consulted, Informed). It makes IT Security accountable for deciding which data types are sensitive, the application owner accountable for inventory management, data masking and masked-data validation, and the data masking admin team responsible for masking administration (domains, classifiers, roles, users). In ShopSphere terms: the compliance officer decides that SSN, email and phone are sensitive, the data steward reviews the inventory, and the TDM engineer builds and runs the jobs. This is a sample from the vendor, not a rule.

8.7 The terminology page, term by term

The terminology page is a one-page glossary. The objects (application, environment, rule set, domain, connector) are covered above; this section covers the algorithm and job vocabulary.

8.7.1 Algorithm words

Algorithm framework
A type of masking algorithm. You can create one or more usable instances from it. "FIRST NAME SL" is an instance of the Secure Lookup framework.
Algorithm instance
A named combination of a framework and its settings. This is what you actually assign to a column in the inventory.
Built-in algorithm
An algorithm instance or framework shipped with the engine. Some built-ins have behaviour that matches no built-in framework.
Non-conformant data
A value that does not fit the format an algorithm expects (for example a 10-digit rule fed a 7-digit number). By default such values are not masked and a warning is recorded, shown as a yellow triangle beside the job execution. You can choose per job, or globally under Admin > Application Settings > Default Non-Conformant Data Handling, whether the job fails, leaves the value unmasked, or sets it to null.
Collision
Two different real values masked to the same fake value. "Amy" and "Jane" both becoming "Beth" is the docs' example.
Non-conformant data means "silently left real" by default

If ShopSphere's phone column contains n/a in some rows, an algorithm expecting ten digits does not fail the job. It leaves n/a unmasked and logs a warning. That is harmless for n/a, but a real SSN typed with spaces might slip through the same way. Always read the warning count after a job.

8.7.2 The algorithm families in one table

The terminology page describes eight families. The algorithms chapter shows how to build them.

Two documented points matter for keys. First, Secure Lookup is deterministic on its input (same hash, same output), and Segment Mapping and Mapping are the collision-free choices, so these are the ones used on unique and key columns. Second, the terminology page's wording for Segment Mapping explicitly lists "Social Security Numbers, primary key columns, or foreign key columns" as its use.

8.7.3 Job options, in one look

The terminology page lists the options of both job types, and you will meet them on real screens in the profiling chapter and the algorithms and jobs chapter. A profiling job has a unique Job Name, a Rule Set, No. of Streams (tables processed in parallel), optional memory limits, Feedback Size, Profile Sets and Email. A masking job adds the Masking Method (In-Place or On-The-Fly), Update Threads (too many can deadlock T-SQL databases), Commit Size, Disable Trigger and Drop Index (both clear by default, so the job leaves indexes and triggers alone unless you turn them on), and Prescript and Postscript SQL files. Both have a Multi-Tenant option that lets one rule set serve identical schemas through different connectors chosen at run time.

8.8 Where the engine runs: deployment options at overview level

The documentation offers two deployment families.

Virtual machine image

A virtual appliance: a ready-made machine image imported into a hypervisor or cloud. The Installation page lists VMware, AWS EC2, Azure, Google Cloud Platform, IBM Cloud, Hyper-V and OCI. You set the network from a console, then finish in the browser-based Setup Wizard.

Containerized

The same engine as a pod of three containers on Kubernetes (tested on OpenShift, MicroK8s, AWS EKS and AWS ECS with Fargate), deployed directly or with Helm. FTP and FTPS file connectors are disabled in this form.

8.8.1 What the Setup Wizard asks

The wizard walks through Welcome (pick Continuous Compliance as the engine type), passwords and the three administrator accounts, time, network, certificates, storage, outbound connectivity (support proxy, usage analytics and the SMTP server used for job email), authentication (LDAP, SAML/SSO, OAuth2), Kerberos and password vaults, registration and a summary. Facts worth keeping: the documented first logins use default accounts that you must change; the engine type cannot be changed once chosen; three failed logins lock the account; the engine works only in UTC, so read job times in Monitor accordingly; and in non-containerized engines LDAP is configured in the setup application, not in the masking UI, a change from earlier releases.

8.8.2 Sizing, in one line

The best-practices page gives a dedicated Compliance Engine 8 vCPUs, at least 64 GB of RAM (128 GB or more recommended), a 127 GB system disk and at least 50 GB of data storage, plus rules of thumb of about one vCPU and 1 GB of memory per concurrent masking job. It also says cloning an engine through hypervisor features is not supported as a backup.

8.8.3 What the engine must reach

The network requirements page lists the traffic. Outbound, the engine needs SMTP (25), DNS (53), NTP (123, VM engine), HTTPS to Delphix Support and to an S3 endpoint if you use one (443), LDAPS (636) and, most important for you, "various" ports to your own databases (JDBC) and file servers (FTP, SFTP, NFS, CIFS). Inbound, users reach the web interface on 443 (use HTTPS, not 80) and administrators use SSH on 22. The engine cannot be deployed behind a reverse proxy. Supported browsers are the latest and previous versions of Edge, Firefox and Chrome. When a connector test hangs, suspect a firewall on the database port before you suspect the password.

The containerized product is meant for ephemeral engines (spun up for a need, then discarded) and differs from the VM engine: no FTP file masking, no Kerberos, no SSO/OAuth, no upgrade validation and no Db2 z/OS or iSeries connector.

Two engines, never one machine

Both the masked-provisioning pages and the configuration page say that Delphix Masking and Delphix Virtualization must never run inside the same virtual machine. Use separate, dedicated engines. The best-practices page also says that Continuous Data and Continuous Compliance are delivered in one OVA, and you pick which one at first setup. So an engine image can become either product, but one running engine is only one of them.

8.9 Users and roles overview

The masking engine uses role-based access control: a role is a set of allowed actions on certain kinds of objects, and a user is a person who has one role and access to certain environments. This is how ShopSphere keeps the data steward from editing connection passwords and keeps testers away from masking jobs.

8.9.1 Roles, actions, objects

  • Actions you can grant: View, Add, Update, Delete, Copy, Export and Import (not every action exists for every object).

  • Each user has one role and a list of environments. Access to an environment does not grant unlimited access: the role still limits what the user can do there.
  • The Administrator setting on a user gives unrestricted access to everything, plus some admin-only powers (sync, audit page, user API-access settings, deleting any object, and others). With it enabled, the role and environment fields disappear.

8.10 Moving work between engines: export, import and sync

Real organisations often run several engines: one per stage of the software life cycle (development, QA, production), or several production engines to share a large workload. Objects must then be copied between them. Export Settings / Import Settings (on the Environments page) moves shared settings such as domains, algorithms and file formats. Export / Import Environment moves everything inside one environment (connectors, rule sets, inventory, jobs). An API-based sync does the same at scale; the docs advise moving objects in one direction only. Sync does not currently support the Application object or certain algorithms, and bundles from a newer engine may not import into an older one.

8.13 Common mistakes and gotchas

Common mistakes
  • Looking for algorithms inside the environment. They live in Settings and survive an environment delete.
  • Assuming profiling masks anything. It only proposes; data changes when a masking job runs.

8.22 Database permissions and preparing the database

8.22.1 A dedicated masking user

The permissions page recommends creating a separate database user for the engine, in non-production, rather than reusing a person's account. Reasons given: it is easy to replicate with its privileges, it can be a central directory user used in many places, and access audits on the database host become simpler. For masking jobs that user needs to read, write and update table data; create, drop, disable and enable indexes, triggers and constraints; and add or delete columns (the engine may add a temporary column, as you will see in the keys chapter). For profiling jobs it needs only to see object definitions (the schema) and read table data.

8.22.2 Preparing each database

The "Preparing data" pages say, first of all, that using a VDB is recommended: it is also the best security practice because the database runs in a sandbox, and the page adds that Selective Data Distribution is advised for further security. The per-database pages share one logic. In-place masking changes every row of every masked table, which creates huge amounts of log and undo data, so the database should be tuned for a heavy write load, and log files can hold unmasked copies of the data and must be cleared afterwards.

DatabaseWhat the page asks for (overview)
OracleSwitch off archive logging for the copy (NOARCHIVELOG), enough memory (automatic SGA management), larger undo space and retention for big in-place updates (about 2 to 3 times the largest table) to avoid "snapshot too old" (ORA-01555), well-sized redo logs, PCTFREE 40 to 50, and use ROWID as the logical key. Switching off archive logging, dropping constraints or giving a user schema-altering rights are fine on a disposable copy and unacceptable on production. That is one more reason the docs steer you to a VDB or another non-production copy.

8.23 What a VDB is, from zero

Suppose ShopSphere's production database is 500 GB. Testers need a copy, and so do developers, and the compliance team will not allow the unmasked copy anywhere near them. Making four physical 500 GB copies takes hours and terabytes, and refreshing them is a chore. Delphix's virtualization product solves the copying half of the problem. Its pages describe it this way.

  • The Continuous Data engine compresses the data it gathers, often to a third of the original size or better, and from that creates lightweight virtual copies that are fully readable and writable, independent of one another and created or removed in minutes. The introduction claims ten virtual copies fit in the space of one physical copy.
  • A dSource is the engine's copy of a source database's persistent data layer, from which VDBs are made and refreshed. A snapshot is the state of a dataset at one moment, and a TimeFlow is the timeline of those states.
  • A VDB (virtual database) is a full read-and-write copy of the source data, provisioned from a dSource or from another VDB, and managed by the Continuous Data engine. You can refresh it (pull newer data), rewind it (go back in time), disable it and enable it.

Analogy, with its limit: think of a VDB as your own editable version of a shared master file. Everyone edits their own version, and the big file is stored once. The documentation does not explain the storage mechanism, so do not push the analogy further than "cheap, fast, independent copies". To the application a VDB looks like an ordinary database with a host, a port and a name, which is what makes the connector idea below work.

Why masking a VDB beats masking a copy by hand

An in-place job overwrites its source (see the overview chapter). On a VDB that is safe: production is untouched, the VDB can be thrown away, and a refresh brings fresh data and re-runs the masking job. Child VDBs of a masked VDB contain only masked data, so you can hand out many independent masked copies cheaply.

8.23.2 Rules and restrictions you must know

  • Provisioning or refreshing masked VDBs is supported only for Oracle, MS SQL Server and Sybase; Db2, for example, is not supported.
  • One job per VDB. A masking job cannot be assigned to several VDBs at once; if you reuse a rule set on many VDBs, create a unique job for each. Only in-place jobs can be selected.
  • Masking happens during provisioning. A VDB that was provisioned without a masking job can never be masked later, and a masked VDB cannot be unmasked, changed to another job, or given extra masking jobs. You cannot make an unmasked snapshot of it.
  • The connector used for masked provisioning must be a "basic" connector (host and port), unless you mask an Oracle pluggable database, which needs an "advanced" connector.
  • Masking and Virtualization must never run in one virtual machine, and engine versions must be compatible (a compatibility matrix is on the page: for example 5.3.0.0 and later pairs with 5.3.0.0 and later, and minor versions need not match).
  • Refreshing a masked VDB (Refresh VDB, choose a snapshot or point in time) re-runs the masking job.

To let the Virtualization Engine reach the masking engine, an administrator can change the host, port and credentials it uses through the engine's CLI (maskingjob, then serviceconfig, then update, set values and commit). It lists jobs automatically at each login, and maskingjob fetch refreshes the list on demand. The page notes that Delphix does not check network availability between the two engines.

8.25 Common mistakes and gotchas

Connector and VDB pitfalls
  • Wrong case in Database Name. It must match the database exactly.
  • Testing the wrong thing. A passing Test Connection proves login, not that the user may drop indexes or alter tables; a job can still fail later for missing privileges.
  • Passwords in a properties file or JDBC URL. Both can be seen by other users; use the form field.
  • Deleting a connector to "tidy up". Its rule sets and inventory go with it.
  • Masking the real database. Always mask a VDB or other copy, with an in-place job.

  • Imported connectors without passwords. Import and sync do not carry passwords; re-enter them.

Delphix: rule sets, primary keys and data integrity

You now have an environment and a connector (the connectors and VDB chapter). The next object in the chain is the rule set: the list of tables, or files, that the engine will profile and mask. Building one is mostly point and click. The part that needs real understanding is keys. Delphix, like most masking engines, wants to know for every table which column or columns identify one row, and it expects masked values in related tables to stay matched. This section covers both.

Keys are covered in general in the data basics chapter; here they are explained briefly, with the masking twist. Tool-specific facts are from the Delphix Continuous Compliance documentation, version 2026.5.

Documentation gaps

The introduction says the engine scans metadata and data "to identify and preserve" primary/foreign key relationships, but the rule set pages describe no automatic foreign key handling, only the rule that the same deterministic algorithm must be used on both sides. The order in which the engine picks a key also differs between the database pages.

8.27 Words to know first

Rule set
A group of tables or flat files, within one data source, on which you may run profile, masking or tokenization jobs.
Inventory
The detailed list of every column or field in a rule set with its domain and algorithm. You open it by clicking the rule set's name.
Primary key (PK)
A column (or columns) that uniquely identifies each row of a table and is never empty.
Foreign key (FK)
A column in one table that holds the primary key value of a row in another table, linking them.
Referential integrity
The promise that every foreign key value matches a real row in the table it points to.
Logical key
A unique, non-null column (or comma-separated columns) you tell Delphix to treat as the key. It changes nothing in the database; it is only information for Delphix.
Identity column
A database column that numbers rows automatically. Delphix can use an existing one as the key, or create a temporary one when a table has no key.
ROWID
In Oracle, a built-in pseudocolumn holding each row's address. The Oracle preparation page recommends it as the logical key for speed.
Deterministic (consistent) algorithm
One that always turns the same input into the same output (for a given algorithm key). This is what keeps matching values matching.
Checklist
An action on a rule set (and on a job) that checks every table has a primary key, an indexed identity column or a logical key.

8.29 Why a masking engine needs a key on every table

In-place masking works in three moves: read a row, compute the masked values, write them back to that same row. To write to the right row, the engine must be able to name it. The preparation pages for SQL Server, Db2 and Sybase say so plainly: a key is a unique, non-null value that identifies a row, and for in-place masking "this key looks up the row to update the masked record". For speed the key should be indexed (a clustered index is best, the pages say).

Analogy: a librarian who must correct the address on 100,000 library cards. If each card has a printed number, she can pull card 48213 directly. If cards have no numbers she must compare every card to find the right one, and with duplicate names she might correct the wrong person. The key is the card number. The analogy stops at speed: the engine updates in batches, not card by card.

The pages then list what the engine does with a table, in this order of preference.

SituationWhat the engine uses
You defined a logical keyThat key. It "can override the key used". One or several columns, but always unique and never null.
The table has a primary keyThe primary key.
No primary key, but an identity columnThe identity column. If it is not indexed, the engine adds an index (named with i_MASKING_GENERATED_IDENTITY_TMP on SQL Server).
No key at allThe engine adds a temporary identity column called MASKING_GENERATED_IDENTITY_TMP and removes it when the job ends. This needs a database user allowed to alter the table, and slows the job. If identity support is unavailable the job may fail.

A detail the pages disagree on: the SQL Server page lists the order as logical key, primary key, identity column, none. The Db2 and Sybase pages list primary key, identity, logical key, none, but still describe the logical key as the override. The practical rule is the same: define a logical key when you want to control the choice. The documentation recommends on-the-fly masking as the alternative when a table has no key, since that method writes new rows rather than updating old ones.

Why the temporary column is not a free pass

The 2025.5 and 2025.6 release notes list known issues: failed jobs on heap tables (tables without a clustered index) may leave the generated temporary identity column and index behind. So "the engine will add one for me" is a fallback with a cost. Give the table a real key.

8.29.1 Oracle and ROWID

Oracle tables have the built-in ROWID. 8.33 Logical keys, filters and custom SQL

8.33.1 What a logical key is, and when you must add one

A logical key tells Delphix "treat these columns as the row identifier for this table". The page defines it as a unique, non-null value that identifies a row. It does not change the target database; it is information for Delphix only. The rule from the page: if a table has no primary key defined in the database and you use in-place masking, you must name an existing column or columns as a logical key. For several columns, separate them with commas. If you do not, and there is no primary key, the engine creates an identity column, which needs a database user allowed to modify the schema, otherwise the job may fail.

Limits worth knowing, all from the pages: a logical key cannot exceed 1,024 characters; the column must exist (the dialog warns that masking jobs fail if the key column does not exist); a fixed-issues entry says null values in logical key columns are now rejected at create or update; and if some tables get an invalid key, the other changes are still saved, the old key stays, and the failures are listed in the Async Tasks page under "Exception Detail".

Which ShopSphere tables need one?

All four core ShopSphere tables have a declared primary key (customer_id, order_id, item_id, product_code), so none needs a logical key. A staging table with no declared key is the typical case. The lab adds one on an example table. A composite key is also possible: ORDER_ITEMS could use the logical key order_id,product_code if that pair is unique, though its own primary key is the better choice.

8.33.3 Filter and custom SQL (briefly)

Two other table properties live beside the key. A filter is a WHERE condition that restricts which rows the job loads (the dialog's hint: prefix the column with the table name, as in customer.cust_id < 1000). Custom SQL replaces the engine's own SELECT. A table can have a filter or custom SQL, never both; adding one removes the other. The page's rules for custom SQL: it must include the primary key column(s) and every column you will mask; it must include the ROWID column (the engine uses it to identify and update each row, and omitting it may fail the job or leave masking incomplete); and you can edit only one table at a time. The "Generate Custom SQL" link suggests a statement for you. Filters are covered with subsetting ideas in the discovery and subsetting chapter.

Two statements to reconcile

The custom SQL text says it must contain the primary key column(s) and the masked columns, and also that it must include ROWID. A fixed-issues entry for Oracle also says a table with a primary key failed when the key was missing from custom SQL. Include both the key and the ROWID if your database supports it, and test with a small run. The documents do not say whether ROWID applies to non-Oracle databases.

8.34 The Checklist: does every table have a usable key?

The engine can check your keys for you. Choosing Checklist in the Actions menu of a database rule set (or of a job) runs an Identity Column Check. It confirms that every table in the rule set has a primary key, an indexed identity column or a logical key. The new-features page describes it as helping you understand the side effects of a missing key before the job runs.

The result is a dialog. If tables lack a key, it lists their names and explains that, for connectors that support identity columns, the engine will add a temporary column before the job starts, which may lengthen the run, and that where identity support is not available the job may fail. You can either update the rule set or go ahead with the job. If everything has a key, the dialog says the check passed.

A passing checklist is narrower than it sounds

The job page says the check "relies solely on ruleset configuration". Even if a job disables a primary key constraint, the check still passes. It proves tables have a key, not that the key will be usable when the job runs, and not that your masking will keep foreign keys consistent. That second question is the next section.

8.35.1 What breaks if you mask the two sides differently

Suppose ShopSphere's profiling flagged only the sensitive columns, and a well-meaning engineer also masked customer_id, but gave CUSTOMERS and ORDERS different algorithms, or a random one on each side. Each value is replaced independently.

Often the best choice is not to mask the key

A profiler marks customer_id as non-sensitive, because it is a meaningless number. If nobody can identify Asha from 1001, leaving key columns unmasked is the simplest and safest way to keep integrity. Mask a key only when the key itself is sensitive (an SSN used as a key, for example). This is general practice, not a statement from the documentation.

8.35.2 How Delphix keeps matching values matching

The documentation's promise appears in the introduction: Delphix masks consistently, so data is masked the same way across tables and databases. The pages that explain how give four ingredients.

  1. Use the same deterministic algorithm on columns that reference each other. The Oracle, PostgreSQL and Db2 driver pages all say this almost word for word: use the same deterministic algorithms on primary key fields that reference each other so referential integrity is kept when constraints are re-enabled. The PostgreSQL and Db2 pages add that if a foreign key column and the key it references do not share one deterministic algorithm, the job fails with an integrity constraint violation. The SQL Server page says it too, with a stronger warning: the failure is near certain.
  2. Use an algorithm whose output is unique. Secure Lookup picks a value from a list by hashing the input, so it is consistent, but different inputs can collide on the same output, which is fine for names and wrong for keys. The Segment Mapping page says to use it for columns with unique values such as SSNs, primary keys and foreign keys, and that for keys you must use the same Segment Mapping algorithm on each side. The Character Mapping page says the same input always gives the same output (until you rekey it) and no two different text inputs share an output, "useful for masking primary and foreign key columns". The SQL Server page's examples of unique algorithms are Dlpx-Core CM Alpha-Numeric, and the CM Numeric page describes a numeric one that keeps the number of significant digits. The algorithms chapter covers them.
  3. Do not use algorithms that are random or unsuitable. The Secure Lookup page says its RANDOMIZE hash method picks a random value every time and "should never be used where referential integrity is required". The Gender SL page says the same of itself. The Date Shift Discrete page says it is not suitable for columns with unique constraints, unique indexes, primary keys or foreign keys. The terminology page notes the Mapping algorithm can mask only one table at a time (the Mapping page says this limit ended with engine 6.0.10.0), so on older engines tables must be masked one after another.
  4. Let the database allow the update. A primary key referenced by foreign keys cannot normally be changed. So a job that masks a key must enable Disable Constraints and also Drop Indexes. The known-issues page records a job failure when primary keys are masked without Drop Indexes together with Disable Constraints, and the Oracle plugin page says the same. The constraints are re-enabled after masking, which is when mismatched values would be caught.
Where the domain helps

The discovery page says the domain mechanism "helps to ensure that the same masking algorithm is applied consistently across rule sets whenever a particular type of sensitive data is discovered". If ShopSphere defines one domain for customer identifiers and gives it one algorithm, every profiling run that finds such a column assigns the same algorithm. That is a good way to keep both sides of a key aligned, though the documentation does not claim it handles key relationships by itself.

8.35.3 Algorithm syncability: the same output on two engines

Many teams run a masking engine for each stage (see the overview chapter's note on multiple engines). If the dev engine and the QA engine mask 1001 differently, test data from the two will not join. The Algorithm syncability page is about this. It says algorithms can be synced between engines through an API, and that syncing out-of-the-box instances updates their individual keys. An algorithm key is the secret value that decides the output; two engines produce the same masked value only if they have the same algorithm and the same key.

The page also separates two kinds. Non-deterministic algorithms cannot guarantee the same output for the same input across jobs, so they "cannot be used for syncable masking": it lists DATE SHIFT(VARIABLE), the Gender SL and SexualOrientation SL instances and SECURE SHUFFLE, and says all Secure Lookup (Random) algorithms are non-deterministic by design. Fixed algorithms, such as DATE SHIFT(FIXED) and ZIP+4, always give the same result and need no syncing. Everything else is deterministic and depends on its key. The page does not mention primary or foreign keys at all: its subject is consistency between engines. Within one engine, consistency comes from using the same algorithm on both columns.

8.37 Common mistakes and gotchas

Key and rule set pitfalls
  • Believing a passing Checklist means integrity is safe. It only proves each table has a key.
  • Masking the primary key with a non-unique algorithm. Duplicates break the key. Use a unique, deterministic algorithm, and the same one on the foreign key side.
  • Masking a key without Disable Constraints and Drop Indexes. The job fails on the key constraint.
  • Using a random algorithm on a key. RANDOMIZE and the Gender SL type never preserve integrity.
  • Forgetting the wizard's Save. The logical key, filter or table list is lost.
  • Typing a logical key column that does not exist. The job fails, or the table is listed under Exception Detail in Async Tasks.
  • Leaving out a child table. A foreign key table linked to a masked key must be in the rule set.
  • Assuming refresh wipes your masking choices. It keeps existing algorithm assignments and updates the table list and columns.

8.38 Recap

Recap
  • A rule set is the list of tables or files of one connector that jobs run on. There are four types: Database, Semi-Structured Files, Flat Files and Copybook.
  • Creating one takes three steps (Details, Data Tables, Summary); the wizard's Save stores everything and starts an Async Task. Edit, Refresh, Duplicate, Delete and Checklist are in the Actions menu.
  • In-place masking finds each row by a key: a logical key if you set one, otherwise the primary key, otherwise an identity column, otherwise a temporary one the engine creates.
  • A logical key is a unique, non-null column (or comma-separated columns) given to Delphix only; it changes nothing in the database. On Oracle, ROWID is the recommended one.
  • The Checklist's Identity Column Check reports tables that have no usable key; it does not test integrity.
  • If you mask a primary key, mask the foreign key with the same deterministic, unique algorithm, and enable Disable Constraints and Drop Indexes on the job.
  • Algorithm syncability concerns producing the same output on several engines; non-deterministic algorithms cannot be synced.

8.39 Words to know first

Sensitive data discovery / profiling
The process of scanning a data source to find columns or file fields that hold sensitive information. The docs use both names for the same thing.
Profiling job
A saved set of instructions that says "scan this rule set using this profile set". You create it once and can run it many times.
Rule set
The list of tables (or files) that a job is allowed to look at. A profiling job covers only what is in the rule set; new tables are not discovered until you add them.
Profile set
A bundle of recognition rules (classifiers). Choosing a profile set decides which kinds of sensitive data the job can detect.
Classifier
One recognition rule, tied to one domain. Example: "a column whose name looks like ssn" or "a value that looks like an email address".
Domain
A named kind of sensitive data, such as FIRST_NAME, SSN or EMAIL, together with the default masking algorithm for it.
Algorithm
The recipe that actually replaces a real value with a safe one. Profiling only chooses an algorithm; the masking job runs it.
Inventory
The table of every column or field in a rule set with its domain and algorithm. It is the profiler's output and the masking job's input.
Confidence
The number (shown 0 to 100 in the UI) that says how sure the profiler is about a match.
Assignment threshold
The minimum confidence needed before the profiler writes a domain and algorithm into the inventory.

Automated Sensitive Data Discovery, the current profiler. It uses classifiers. The older "legacy" profiler uses search and type expressions.

8.40 Why profile at all?

Picture the ShopSphere developers asking for a copy of SHOPSPHERE_PROD to test the Customer Orders app. A TDM engineer must hide every real name, phone number and tax id before handing it over. With four tables and nine customer columns you could do that by reading the table definitions. With a real database of 3,000 columns you cannot, and one forgotten column is a privacy incident.

A profiling job automates the first pass. The documentation describes it as examining metadata (column names and types) and potentially the data itself, then assigning the matching domain and its algorithm to each column it judges sensitive . A person then reviews the result. That last step matters: the profiler is a fast assistant, not an auditor.

Why it matters

Profiling is where masking projects are won or lost. Masking jobs only protect what is in the inventory. A column the profiler missed, and nobody caught, goes to the test environment untouched.

8.42 How the profiler decides: classifiers, strengths and thresholds

The profiler looks at each column and asks a panel of four judges. Each judge looks at a different kind of evidence and answers with a score. The scores are combined into one confidence per domain. If the best confidence reaches the assignment threshold, that domain (and its algorithm) is written into the inventory.

8.42.1 The four classifier frameworks

A classifier framework is a kind of judge; a classifier instance is one configured judge for one domain. The docs list four frameworks and say you cannot install more .

FrameworkLooks atLevelPlain-English job
PATHThe name (for databases: table name and column name)Column"The column is called first_name, so it is probably a first name."
TYPEData type and lengthColumnRejects impossible matches, e.g. a yes/no flag cannot be an SSN.
REGEXThe actual values, using patternsData"The values look like 123-45-6789."
LISTThe actual values, checked against a listData"The values are all on the list of known first names."

PATH and TYPE are cheap, because they only need the table definition. REGEX and LIST must read sample rows, so they are what lets the profiler find a sensitive column even when its name is meaningless, such as COL_17. The built-in value lists carry English values, so data-level detection is limited to English .

8.42.2 Match strength, reject strength and how scores combine

Inside the engine every classifier reports a number from -1.0 to 1.0. The UI shows the same idea as -100 to 100, and in practice you only see 0 to 100 because non-matches are not displayed .

  • Match strength: how sure the classifier is that this data belongs only to its domain. 0.01 means "maybe, but it could be many things". 1.0 means "certainly this and nothing else".
  • Reject strength: how strongly a non-match counts against the domain. -1.0 eliminates the domain at once.
  • Combining: if results disagree in sign, the larger absolute value wins; if they agree, the match gets stronger. Only the strongest column-level result and the strongest data-level result are combined, and the docs warn that the exact formula may change.
Two worked examples from the docs

Rejection. A column named ssn_present matches the SSN PATH classifier (0.67). But it is boolean, the SSN TYPE classifier returns -1.0, and the verdict is -1.0, so SSN is not assigned.

Competition. A column named passport_no holds 9-digit numbers. Both the SSN and the PASSPORT_NO REGEX classifiers give 0.5. Only the PASSPORT_NO PATH classifier also matches (0.67). Final confidence: PASSPORT_NO 0.84, SSN 0.5, so PASSPORT_NO wins.

The built-in PATH classifiers usually carry 0.67. A REGEX or LIST classifier has to beat that to override a name match, which is why the docs advise a low match strength (0.1 to 0.5) for patterns that are not unique. A nine-digit pattern could be an SSN, an account number or a row id, so it gets a small score. A dashed pattern like 001-23-4567 is distinctive, so it gets a high one.

8.42.5 Assignment threshold

The default minimum confidence for ASDD is 1, so "any positive match, no matter how weak, triggers an assignment" . That is very permissive, and the docs contrast it with the legacy profiler, which by default wanted an 80% match for data-level expressions. You can raise the threshold per profile set (integer 1 to 100) or globally with the application setting ASDD/DefaultAssignmentThreshold. A higher threshold means fewer false alarms and more missed columns. Because a missed column is worse than a false alarm, many teams keep the threshold low and review the inventory.

8.42.7 The legacy profiler, briefly

Before ASDD, profiling used search expressions (patterns on column names or data) and type expressions (data type and minimum length). The legacy profile sets are kept so that old jobs keep giving the same results, and they contain no type classifiers to restrict matches by column type . The legacy classifier tables list patterns such as ssn(?!\w*ID) for SSN and (?>((tele?)?phone)|...) for telephone. The legacy version of the Add Profile Set dialog (not the ASDD one pictured below) carries a banner saying legacy profile sets are deprecated and will be removed in a future release. Use ASDD for new work; the profileTypeExpressions page only shows API scripts for legacy type expressions.

ASDD currently supports databases, delimited files, fixed-width files, JSON files, XML files and mainframe data . Its stated limits: XML or JSON documents stored inside database columns are not profiled, and the Informix database is a known problem for discovery because of the column-truncation SQL.

8.47 From findings to a reviewed inventory

The profiler writes its decisions into the rule set's inventory. Reaching it takes one click: Environment > Rule Sets tab > click the rule set's name. The "Inventory" tab that older versions had was removed, and the banner in the screenshots says so .

A database inventory lists every column of every table. The number beside a table name is its column count. Primary key, foreign key and index flags appear under the column name, and data type and length are shown read-only. By default the visible columns are Table Name, Column Name, Data Type, Domain, Algorithm and File Format. For fixed-width and delimited files, fields are grouped under record types; see the file masking chapter.

8.47.1 Correcting one column: the Edit dialog

  1. Click the pencil (Edit) icon in the Actions column of the column's row.

    The Edit Column (or Edit Field) dialog opens. From the inventory screen only the Masking section is editable.

  2. Decide about Enable Automatic Updates.

    When ticked (the default), a profiling job may change this column's masking decision. When unticked, your choice wins over the profiler. If you are about to override the profiler, untick it first, otherwise the next profiling run may undo your work.

  3. Pick the Domain and the Algorithm.

    The Domain drop-down fills in that domain's default algorithm; you may replace it with any other algorithm.

  4. If you chose a DATESHIFT algorithm on a column that is not a native date or datetime, fill in the Date Format.

    The default is yyyy-MM-dd. The letters are case sensitive: D means day of the year, d day of the month, MM month, yyyy four-digit year.

  5. Add a note if useful, then click Save.

    Nothing takes effect until you save.

Three more inventory tools worth knowing :

  • Clear Masking Assignment (the circular-arrow icon in a row's Actions column, enabled only when that column or field has an assignment) removes the applied masking assignment and, in the same click, switches automatic updates off for it. A confirmation bar appears for a few seconds; if you do nothing, the clearing goes ahead, and Cancel keeps your assignment.
  • Nulling algorithms. If you pick an algorithm that can return null (such as Null SL) for a column that has a NOT NULL constraint, the UI shows an error.
  • Inventory Approval Workflow (database rule sets only, enabled per environment). Every edit sets the status to NEW; the editor clicks Submit; an Admin or a user with the Inventory Approval privilege clicks Approve or Reject. A masking job for that rule set will not run unless the status is Approved. This gives a data steward a formal sign-off point.

Review every row in this order: is the domain right, is the algorithm right for the application (see the algorithms chapter), is confidence low (worth a second look, not necessarily wrong), and what is missing. Rows with no domain, such as UNMASKED_00 in the database screenshot, matter as much as flagged ones. Put the reason for each manual change in the Notes field for the audit trail.

Everything above is also available through the Masking API. The documentation's createInventory example assigns an algorithm and a domain to a column with PUT /column-metadata/{id} and a body such as {"algorithmName": "AddrLine2Lookup", "domainName": "ADDRESS_LINE2"} . The script needs helper files that are not shown, so it cannot be run as printed.

Why the checkbox matters in teams

A TDM engineer who fixes ten columns by hand, and a colleague who re-runs profiling the next day, are a common cause of "my changes disappeared". Untick automatic updates on every column you corrected deliberately, and let the profiler keep updating the rest.

8.50 Common mistakes and gotchas

Watch out for these
  • Treating profiling as the finish line. The output is a draft. Review every flagged and every unflagged column, especially free-text and oddly named ones.
  • Forgetting that only the rule set is scanned. A table added to the database after the rule set was built is invisible to profiling.
  • Editing assignments and leaving automatic updates ticked. The next profiling run can replace your edits. Untick it on columns you decided by hand.
  • Changing a domain's default algorithm and expecting old inventories to change. They do not; only future profiling runs are affected.
  • Max Memory below 1024 MB per stream with an ASDD profile set. The docs say the job needs at least that. Four streams need 4096 MB or more.
  • Trusting name matching alone. A column called ssn_present is a flag, not an SSN; TYPE classifiers exist to reject these, but they only help when the data type is right.
  • Using legacy profile sets for new work. They are deprecated and give less coverage.
  • Expecting value-level detection in languages other than English. The built-in lists are English only.
  • Sharing the PDF report or CSV without thinking. They list table and column names with their domains, which tells a reader exactly where your sensitive data lives, so store them with care.

8.51 Recap

Key points
  • Profiling scans a rule set with a profile set and writes domain and algorithm assignments into the inventory.
  • Classifiers come in four frameworks: PATH and TYPE look at columns; REGEX and LIST look at values. Scores combine into a confidence compared with the assignment threshold (default 1).
  • A domain is a kind of sensitive data with one default algorithm. Changing it affects only future runs.
  • Create the job in an environment: rule set, profile set (ASDD Standard by default), streams, memory (at least 1024 MB per stream for ASDD).
  • Read results on the job page, in the PDF, in the rule set inventory or in an exported CSV.
  • Correct findings in the Edit dialog and untick Enable Automatic Updates so that the profiler does not overwrite you.
  • For ShopSphere, expect the customer columns to be flagged and price or amount columns to be false alarms.
