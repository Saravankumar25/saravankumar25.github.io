2.1 Discovery, profiling and subsetting: the concepts

Day 43-44

Imagine you have to move a flat. Before you pack, you walk through every room and list what is there: which boxes are fragile, which items belong together, which papers are private. Only then do you decide what to take and how to wrap it. Test data work follows the same order. First you look inside the production database (discovery and profiling). Then you take only what you need (subsetting). After that, you protect what you took (masking, covered in the masking concepts chapter).

This section teaches the two first steps as ideas, without any tool buttons. It builds on the data basics chapter (tables, primary keys, foreign keys) and on the sensitive data chapter (what sensitive data is, and how patterns and names reveal it). The hands-on tool chapters that follow are Informatica discovery and profiling, Informatica data subset and Delphix profiling.

What you will learn
  • What data discovery and profiling are, why they come first, and what a profile reports: types, patterns, sensitive-looking columns, keys and relationships.
  • The difference between looking at metadata (names and types) and looking at the data itself, and why a human must review the results.
  • What data subsetting is, why teams do it (size, speed, cost, privacy), and the main ways to choose a subset: by filter, by percentage or row count, by time window, by driver table.
  • What a driver table is, how related "child" rows come along, and how to keep referential integrity so the subset still works.
  • How subsetting and masking combine, and how a subset compares with a full copy.
  • A worked ShopSphere subset with before and after rows.

2.1.1 Words to know first

Data discovery
The step of finding out what is in a data source: which tables and columns exist, which hold sensitive data, how tables relate. Informatica uses "data discovery" for the whole activity and "profile" for each job inside it.
Profile (verb: to profile)
A job that scans a data source and reports facts about it. Delphix and GenRocket also say "profiling".
Metadata
Data about data: table names, column names, data types, lengths, key definitions. The column ssn and its type "string of 11 characters" are metadata. The value 123-45-6789 is data.
Primary key (PK)
A column (or set of columns) whose values are unique for every row and identify it, such as customer_id.
Foreign key (FK)
A column whose values point to a primary key in another table, such as ORDERS.customer_id pointing to CUSTOMERS.customer_id.
Parent table and child table
The table holding the primary key is the parent; the table holding the foreign key is the child. CUSTOMERS is the parent of ORDERS, and ORDERS is the parent of ORDER_ITEMS.
Referential integrity
The promise that every foreign key value points to a row that really exists. A child row with no parent is an orphan, and it means the data is broken.
Data subset
A smaller copy of a database that still hangs together: fewer rows, same structure, referential integrity intact.
Driving table (driver table)
The table you start from when you pick a subset. The tool finds related rows in other tables starting from it. Informatica uses exactly this term for the starting table of an entity.
Entity (Informatica)
A driving table plus all the tables related to it. It is the unit that Informatica copies to a subset database.

2.1.2 Data discovery and profiling

What it is

Data profiling means scanning a data source with software and producing a report of facts about it. Data discovery is the wider goal: using those facts to decide what to mask, what to subset, and how tables connect. Informatica puts it plainly: run profiles to discover source data for data masking and data subset operations (User Guide 10.5.10, p.86). From docs

A profile changes nothing: it measures, lists and flags. Unlike a building survey, its flags are guesses that people must confirm.

Why it comes first

Masking and subsetting are only as good as your knowledge of the data.

  • You cannot mask a sensitive column you did not know about. Missing one column of SSNs means a leak.
  • You cannot subset safely without knowing the relationships. If you cut ORDERS without knowing it points at CUSTOMERS, you will leave orphans.
  • You cannot choose a masking technique without knowing the column's type, length and shape.
  • Real databases are rarely documented. Old tables, renamed columns and half-forgotten fields are normal.
Why it matters

Both Informatica and Delphix describe profiling as the step that feeds the next one. Informatica says that before masking you can discover which columns to mask with the same rules, and before subsetting you can discover relationships between tables and the entities for the subset (User Guide 10.5.10, p.86). Delphix says that after connecting data, the next step is discovering which of it should be secured (Delphix "Discovering your sensitive data"). From docs

What a profile reports

Typically: each column's data type and length; value patterns and their share (99 percent of phone values are ten digits); ranges, minimum, maximum and the share of nulls; the most common values; sensitive-looking columns (email matches an Email Address domain); primary key candidates (customer_id is 100 percent unique); and foreign key candidates (ORDERS.customer_id matches CUSTOMERS.customer_id).

The four profile types in Informatica

2.1.3 Metadata profiling and data profiling

A profile can look at two different things, and the difference decides how fast it is and what it can find.

Metadata profiling

Reads only descriptions: table names, column names, types, lengths, declared keys.

  • Fast, and does not need to read any real customer values.
  • Finds a column called ssn, or user_email.
  • Misses cryptic names such as FLD_X2, and cannot tell whether notes contains an SSN.

Data profiling

Reads actual values (often a sample) and measures patterns, counts and uniqueness.

  • Slower, because it reads rows.
  • Finds a column of SSN-shaped values even when its name is meaningless.
  • Needs access to real production data, which is itself a privacy decision.

The tools expose the same split under different names. From docs

Sampling: a look, not a census

Scanning every row of a table with 80 million rows would be slow, so profiles often sample. Sampling means reading only some rows. That is efficient, but it has a catch: a value that appears in only 1 row in 10,000 may not be in the sample. If a few rows of a mostly-clean column hold real phone numbers, a small sample may miss them. Informatica reflects this with options such as "Maximum Rows to Profile" and "Minimum Conformance Percent" (p.95): the second one is the share of profiled rows that must match the pattern before the column is claimed for the domain.

2.1.4 Finding keys and relationships

Subsetting needs to know which tables are parents and which are children. Ideally the database declares its primary and foreign keys and the tool simply reads them. In practice many databases declare few or none (for performance, or because the application enforces the links). GenRocket's documentation says this directly: custom referential integrity is added "when referential integrity does not exist between tables in the source database" but the user still needs to subset (GenRocket "How to Add Custom Referential Integrity to Imported Table Schemas"). From docs Discovery fills that gap by inferring the links.

Primary key discovery

A primary key candidate is a column, or a small set of columns, whose values are unique. Informatica's primary key profile reports the percentage of unique values and lets you limit how hard it searches (User Guide 10.5.10, pp.92 to 93). From docs

Its options and defaults: the maximum number of columns combined into a key (3), the maximum rows to profile (1,000) and a conformance criterion, the minimum percentage of unique values allowed (99 percent) (p.93).

Why would you allow less than 100 percent? Because real data is messy. If 99.8 percent of values are unique and a few rows are duplicates, the column is probably meant to be a key and the duplicates are data-quality bugs. Informatica notes that a primary key profile is useful to find such non-unique rows (p.92). The result table shows, per candidate, the table, the column or combination of columns, the uniqueness percentage, whether it is verified, any existing constraint and a status of verified, approved or rejected (pp.103 to 104). When you approve a candidate, TDM adds it as a key to the table in its repository, not in the source database. Rejecting a candidate does not affect the subset (p.104). From docs

Unique does not mean a good key

ssn is 100 percent unique in the table above, yet it would be a poor primary key: it is sensitive, so masking will change it, and every table that used it as a link would need identical treatment. A human picks customer_id, the "meaningless but stable" identifier. Uniqueness tells you what can be a key. A person decides what should be.

Foreign key and entity discovery

To find parent-child links, Informatica's entity profile "returns a list of possible entities by comparing column names in the source tables" (p.93). In the guide's example, Employee, Employee_Detail and Employee_Address all contain an EmpID column, so the profile suggests Employee as an entity with two child tables. When you later subset, a filter on EmpID applies to every table in that relationship. From docs

The profile options show what matters when matching columns (p.94): whether to compare using the datatypes the tool inferred or the documented ones, whether comparison is case sensitive, whether to trim spaces first, the maximum number of foreign key results to return and the minimum confidence percent (the share of foreign key values that match). A coincidental match is the risk: two unrelated integer columns can overlap by chance, so discovery proposes and a person approves.

One practical detail: if you choose the entity profile type and the physical database has no primary keys, the profile returns nothing. Run the profile as primary key and entity together, and it can discover both the primary and foreign keys even when the database declares none (p.93). From docs

Delphix says its masking keeps referential integrity by scanning metadata and data to identify and preserve the primary and foreign key relationships between elements, so that data is masked the same way across tables and databases (Delphix "Introduction to Delphix Masking"). From docs How keys are defined in a Delphix rule set is covered in the Delphix rule sets and keys chapter.

Between the two, false negatives are the more dangerous in a privacy project, because nobody notices them. That is why discovery tools build review into the workflow, and why you should plan for it. In Informatica, each result row has a status, and you can verify, approve or reject it. The guide says the Verified column is for your own tracking and does not affect data subset operations, and that marking the data domain classification as completed does not affect any process either; it simply records that you reviewed everything (pp.104 to 105). From docs The data viewer for a selected column shows the first 200 records, so reviewers can look at real values before approving (p.105).

A review routine that works

  1. Sort the results by confidence.

    Informatica shows % data conformance and whether the column name matched (p.105). High on both is easy to accept.

    A short list of obvious accepts and a longer list that needs thought.

  2. Look at the actual values for doubtful rows.

    Names alone mislead. Five sample values usually settle it.

  3. Ask the data steward about anything ambiguous.

    "Is tax_id a personal or a company number?" is not something a tool can answer.

  4. Scan the unflagged columns too, and record your decisions.

    Check free-text and generically named columns. A profile only covers the tables it was given, and re-profiling will not remember your reasons.

    A short list of columns added by hand, and a written list of accepted and rejected findings.

2.1.6 What is data subsetting?

Start with the problem. ShopSphere's production database holds eight years of history: tens of millions of customers, hundreds of millions of orders, terabytes in total. A tester working on the checkout screen does not need all of it. Copying everything to every test environment is slow, expensive and risky. Data subsetting means copying only a slice of the database, small enough to be cheap, and consistent enough to be useful.

From docs Informatica describes the goal as a "small, targeted, and referentially intact copy" of production data for use in a nonproduction environment such as development, test or training, and gives the example of financial data for a specific region or time period (User Guide 10.5.10, p.112). GenRocket frames it the same way: production data may contain sensitive data, "you also do not need all that data for application testing, only a subset" (GenRocket "Synthetic Data Masking (SDM) and Data Subsetting Overview").

Why teams subset

  • Size and storage cost: smaller copies need less disk and money (GenRocket lists saved storage as a benefit).
  • Speed: a small copy refreshes overnight instead of over days, and tests and reports run faster.
  • Privacy: fewer real records copied means less exposure and less to mask (the minimum necessary idea from the sensitive data chapter).
  • Focus: you can pick exactly what a test needs, such as one region or one scenario.

A subset is not just "the first 1,000 rows"

Beginners sometimes subset by taking the first N rows of each table. That breaks the data: the first 1,000 orders belong to customers that may not be in the first 1,000 customers. The result is orphans: orders with no customer, items with no order. A real subset starts from a choice (a set of customers, a time window) and then follows the relationships so that every kept row has all the parents it points to. Everything in the next sections is about doing that correctly.

2.1.8 Driver tables and child rows

Now the core mechanic. Every subset has a starting point: a table and a condition. The tool picks the matching rows there, then follows the relationships to select related rows in other tables.

Informatica: the entity and its driving table

From docs In Informatica, an entity "consists of a driving table and related tables". The driving table is the starting point; TDM finds the tables related to it from physical (declared) and logical (discovered or added) constraints, and adds them to the entity by default. You then define filter criteria on columns of tables in the entity (User Guide 10.5.10, p.114). The guide's example: Employee as the driving table, with primary key EmpID, three child tables holding an EmpID foreign key, and a fourth table, BankAccounts, linked through an account number from one of the children (p.115). The Entity Map shows the star on the driving table.

The Entity Map can show all tables, the parents or children of a selected table, or cyclic relationships, and you can disable a relationship; a table left unrelated is excluded (p.115). The guide advises running data discovery before creating an entity so the constraints exist (p.116).

The guide's own small example

An employee has ID 10 and you want everything about that employee. Employee is the driving table; Employee_History and Employee_Order are related to it by EmpID. Define the criteria "EmpID equals 10". After the plan runs, the target database holds one Employee row for EmpID 10, all of that employee's history rows and all of their orders (p.121). From docs

GenRocket: the subset table and the hierarchy

From docs In GenRocket's G-Subset, only one table in a configuration can have subsetting conditions (Where clause and/or row limit). Rows that meet the condition are included, "all records in related tables associated with those meeting the Where Clause condition will be inserted as well" (Subsetting how-to). The Traverse Full Hierarchy page shows what "related" means. Its example database has Organization (1 row), Department (4), Employee (120), Address, Attendance, Payroll and Qualification (120 each) and Project (8). The condition is on Payroll: hours > 10, limited to 10 rows.

  • Default behaviour: G-Subset goes up from the subset table to the top-most parent to build its queries, then migrates from the top down: Organization, Department, Employee, Payroll. Only the ancestor rows related to the chosen Payroll rows move: 10 employees, the departments they belong to, and so on.
  • Traverse Full Hierarchy enabled: it also brings the other children of those ancestors: Project (2 rows), and Address, Attendance and Qualification rows for the same 10 employees.

The same page notes that the option is only available when a subsetting condition has been added to a table, and that masking rules you set for those extra tables are applied to them too.

Choose the driving table by the test question

If the test is "does the customer page show the right orders?", drive from CUSTOMERS. If the test is "does the monthly report add up?", drive from ORDERS with a date filter and let the parents (customers) and children (items) follow. The table you drive from decides which rows are complete and which are partial.

2.1.9 Keeping referential integrity

Referential integrity is the rule that every foreign key value points to a row that exists. It is the one property a subset must never lose. If it breaks, the application crashes or shows empty pages, and testers blame the data. GenRocket's page defines it in the same plain terms: it "refers to the accuracy and consistency of the defined relationships" between parent and child tables (GenRocket "How to Add Custom Referential Integrity to Imported Table Schemas"). From docs

How a naive subset breaks it

Suppose someone takes the first 6 rows of ORDERS and the first 4 rows of CUSTOMERS "to keep it small". Order 5006 belongs to customer 1005, who is the fifth customer and was left out. Order 5006 is now an orphan.

SELECT o.order_id, o.customer_id
FROM   ORDERS o
LEFT JOIN CUSTOMERS c ON c.customer_id = o.customer_id
WHERE  c.customer_id IS NULL;      -- any row returned is an orphan order

On the naive subset this query returns one row (order 5006, customer 1005). On a correct subset it returns nothing. The same check works one level down (ORDER_ITEMS to ORDERS, and ORDER_ITEMS to PRODUCTS). Run these checks after every subset: they are cheap and catch the commonest failure.

Integrity options in Informatica plans

From docs Informatica goes beyond "no orphans". It also offers several ways to decide how much extra data to pull to keep the subset coherent. You choose the option in the plan's advanced settings, so the same entity can yield different subsets (User Guide 10.5.10, pp.121 to 123). By default all constraint relationships in an entity are "major", which can pull in excess data; you can optimise relations so that the entity has the minimum number of major relations while still covering all tables (p.119).

2.1.11 Reduced copies and full copies

A subset is one way to make a test copy small. There are other ways to get a test copy, and each has a place. The comparison below is a general guide, with the Delphix statements marked.

A full physical copy is the most realistic but the slowest and most exposed. A subset is small and quick to refresh but may miss rare cases. A virtual copy looks full but shares storage with its source, so it is cheap to create, but it still holds all the data and needs masking. General concept

From docs Delphix describes virtualization as producing "a functioning database or filesystem copy that is lightweight and ephemeral" (terminology page), and its introduction claims that ten virtual copies can fit into the space of one physical copy. The pages I read do not describe a subsetting feature for Delphix, so treat "virtual copy" and "subset" as two different answers to the same cost problem: Delphix makes full copies cheap; Informatica and GenRocket make copies small.

Common mistakes and gotchas

Mistakes beginners make
  • Taking "the first N rows" of every table. It creates orphans. Always start from a driving table and follow relationships.
  • Trusting discovery output without review. Reject coincidental key matches, add missed sensitive columns.
  • Choosing a sensitive column as a key. A unique SSN is a poor primary key because masking will change it.
  • Assuming a percentage limit is random. The documentation excerpts do not say so; verify.
  • Forgetting reference tables. A subset with an empty PRODUCTS table breaks every order screen. Copy lookup tables in full.
  • Filtering on a column you also mask. Decide whether the filter sees real or masked values.

Recap

Remember
  • Discovery and profiling come first: they report types, patterns, sensitive-looking columns, key candidates and relationships, from metadata (names and types) and from data (values, usually sampled).
  • Profiles guess. False positives waste effort or change keys; false negatives leak data. A human reviews and approves.
  • A subset is a small, targeted, referentially intact copy: cheaper to store, faster to refresh and test, and less real data exposed.
  • You choose rows by filter condition, percentage, row count or interval, time window, or by a driving table; tools also copy some tables in full.
  • A driving table is the starting point: related rows are followed down to children and up to parents so there are no orphans. Informatica calls the group an entity; GenRocket follows the hierarchy from the subset table.
  • Informatica offers transactional, referential-only, two-way and one-way integrity options that trade subset size against completeness.
  • Subsetting and masking are partners. Keep keys consistent when you combine them, and check for orphans afterwards.

2.2.1 Words to know first

Masking
Replacing sensitive values with realistic but fictitious values so test data cannot identify real people. Delphix defines it as iterating through a dataset to identify all sensitive fields and replace them with desensitised values to eliminate risk in lower environments.
Technique (Informatica) / algorithm (Delphix)
The method that changes a value, such as substitution or date shift. Informatica turns a technique plus settings into a rule. Delphix turns an algorithm framework plus settings into an algorithm instance.
Deterministic
Always gives the same output for the same input (and same settings). The opposite is non-deterministic or random: a different output each time.
Repeatable
Informatica's word for deterministic output across runs and tables, switched on with a seed.
Seed / key
A starting value that controls the output of a deterministic technique. Same seed (Informatica) or same algorithm key (Delphix) gives the same masked values; changing it changes them.
Dictionary / lookup file
A list of replacement values, such as thousands of first names, that substitution picks from.
Collision
Two different inputs masked to the same output. Fine for names, harmful for a column that must be unique.
Irreversible
You cannot get the original value back from the masked one.
Format-preserving
The masked value keeps the original's shape: a 10-digit phone stays 10 digits, a card number keeps its checksum.
In-place and on-the-fly
In-place masking changes the data where it sits. On-the-fly masking reads unmasked data and writes masked data to a different place.

How the sources use the words: From docs

  • Delphix says tokenization is "the only type of algorithm that allows you to reverse its masking". Reversible is a risk in test data

If a test copy can be turned back into the real data, then stealing the copy plus the key or mapping table is a breach. For ordinary test environments, prefer irreversible masking. Use encryption or tokenization when you truly need to come back, such as a vendor round trip, and guard the key like production data.

Anonymisation is a destination, masking is a vehicle

Masking is a set of techniques. Whether the masked result counts as anonymous under a law depends on the whole data set (the combinations you saw in the sensitive data chapter) and is the compliance officer's call.

Algorithm chaining

Combine several steps into one result. Why chain at all?

Real columns are related: the email contains the name, the full name contains the first name. If each is masked independently, the masked email will name someone different from the masked name. Chaining makes the dependent value follow the one it depends on.

How the tools achieve it

  • Informatica seed and repeatable output. With repeatable output, "John Smith" is masked as "Frank Martinez" in every table, account number 1234 always becomes 6549 and 5678 always becomes 3214, across runs. A seed, a number from 1 through 999 with default 1, is the starting point; use the same seed on the same kind of column in different tables. An administrator can set a central seed that overrides all others, and a seed can come from a parameter file (pp.154 to 155). From docs
  • Informatica cascades. An auto cascade masks a parent key and the related foreign keys in child tables with the same value, applied by default where key constraints exist (p.91). A value cascade does the same for similar columns that are not linked by a key, such as employee_num in one table and EmpID in another, by choosing a driving column (p.90). From docs
  • Delphix key and domain. Most algorithms carry a key; the same algorithm with the same key gives the same output, and changing the key changes every output (the Algorithms page gives an example where "Michelle" becomes "Rachael" and after rekeying "Ben"). Because each domain has one default algorithm, every column found in that domain is masked the same way (Discovering your sensitive data). From docs
  • Delphix across engines. Algorithms can be synchronised between masking engines so that two engines mask the same input the same way. Algorithms that cannot guarantee the same output, such as the variable Date Shift, SecureShuffle and the random Secure Lookup, are called non-deterministic and cannot be used for syncable masking, while a fixed Date Shift is deterministic (Algorithm syncability page). From docs
Things that quietly break consistency
  • Different spellings of the same value. Informatica's key masking is case sensitive by default, so "john brown" and "JOHN BROWN" can mask differently unless you convert the source to one format first with a preprocessing expression (p.166). Delphix Secure Lookup has a case-sensitive option and whitespace options with similar effects.
  • The value hiding inside another column. A name in FIRST_NAME may also appear inside FULL_NAME or DESCRIPTION. Informatica's delimited string masking masks such substrings consistently, for example "Donne, John" and "John Donne, General Manager" (pp.166 to 167).
  • Random options. A "random" mode is fine for a column that nothing links to. The Delphix Secure Lookup RANDOMIZE method "does not maintain referential integrity and should never be used" where it is required.
  • Different algorithm or seed for the same data in two jobs. Keep one policy and one seed or key per kind of data (this is what a policy from the sensitive data chapter is for).
Repeatable output has a price

The same property that keeps joins working also means the mapping can be recomputed by anyone who has the seed or key and the algorithm. For a small value space (an SSN has about a billion possibilities) that is guessable. Treat seeds and keys as secrets, store them outside the test environment, and rotate them when policy says so (Delphix lets you randomise an algorithm key through its API; the Algorithms page gives the endpoint).

Irreversible by design. A good masking technique throws the original away. Substitution picks an unrelated value; shuffle and key masking cannot be undone without the seed and source. 2.2.7 Static or dynamic, in-place or on-the-fly

Two different choices are often mixed up. General concept Static versus dynamic asks when data is masked. In-place versus on-the-fly asks where the masked data ends up.

Static masking

Create a masked copy once. The copy is stored, and from then on anyone using it sees masked data. This is what test data management normally does.

Dynamic masking

Mask at the moment of reading, depending on who asks. The stored data stays real, and an application or proxy hides values from some users. It protects production views, not test copies. The TDM sources I read do not cover it.

A word of caution on vocabulary: GenRocket also uses "dynamically" for masking that happens as rows are inserted into the destination, which is closer to on-the-fly than to the dynamic masking above (GenRocket "SDM and Data Subsetting Overview").

Common mistakes and gotchas

Mistakes beginners make
  • Calling encryption "masking". It can be reversed. Use it only when reversal is intended.
  • Masking keys independently. Joins break. Use the same seed or key, or cascades.
  • Ignoring the job warnings. In Delphix, non-conformant values are left unmasked by default and only flagged.
  • Trusting one technique for everything. Shuffle leaves real values in place; substitution can collide; date shifting can reorder dates.
  • Forgetting free text and indirect identifiers. They defeat column-level masking.
  • Sharing the seed or key with the test team. It makes the mapping reproducible by anyone who has it.
  • Declaring success without validating. Run discovery again on the masked data and check joins.

Recap

Remember
  • Masking replaces real values with realistic fake ones, usually irreversibly. Encryption and tokenization are reversible; anonymisation is a legal goal that masking helps reach.
  • Good masked data is safe, realistic, valid, consistent, repeatable and still fit for the tests.
  • Common techniques: substitution, shuffle, key masking, encryption, nulling and redaction, date shifting, numeric variance, format-preserving masking, character replacement, and chaining several of them.
  • Deterministic masking (same input, same output, from a seed or key) is what keeps keys and joins working across tables and systems. Random masking is for columns nothing links to.
  • Choose by column type, uniqueness, format and test needs. Not every column needs masking, and free text needs special handling.
  • Masking can be in place or on the fly; static copies are the norm for test data.
  • Always validate: rediscover, check joins, formats, uniqueness, repeatability and job warnings.

2.3.1 Words to know first

Test data
Any data the application is fed or finds waiting in its database during a test. It includes both the rows in the database and the values typed into screens or sent in files.
Test condition
One specific situation a test wants to check, such as "customer with no phone number" or "order with the maximum number of items". Each condition needs data that creates it.
Positive (valid) data
Data the application should accept and process normally.
Negative (invalid) data
Data the application should reject or handle gracefully, such as letters in a phone number.
Boundary value
A value sitting exactly on the edge of what is allowed. If customers must be 18 or older, the boundary values are 17, 18 and 19 years.
Edge case
A rare or unusual situation outside normal use, such as a surname containing an apostrophe. GenRocket describes it as a rare or unexpected scenario outside the typical usage pattern.
Synthetic data
Data made by a program following rules, instead of being taken from real events. GenRocket's help centre puts it as data manufactured by an algorithm rather than real-world events.
Generator
The small piece of logic that produces the values for one column, for example "count up from 1" or "pick a name from a list".
Seed
A starting number given to a random generator. The same seed gives the same "random" values every time, so a test data set can be rebuilt exactly.
Distribution
How values are spread: for example, 20% of customers have no orders, 40% have one. Real data is lumpy, and good test data copies the lumps that matter.
Referential integrity
The promise that every foreign key points at a row that exists. An order whose customer_id has no matching customer breaks it. See the data basics chapter.
Parent table / child table
The table being pointed at (CUSTOMERS) is the parent; the table holding the foreign key (ORDERS) is the child.
Coverage matrix
A grid that lists test conditions against the data that covers them, so you can see gaps at a glance.

2.3.2 Why classify test data at all?

General concept Imagine a kitchen preparing for a cooking class. The chef does not just buy "food". She buys the exact ingredients each recipe needs, in the amounts each recipe needs, and she keeps the allergy-sensitive items (nuts) in a separate, labelled place. Test data works the same way. You prepare the exact rows each test needs, and you keep the dangerous ones (real personal data) away from places they must not be.

The analogy stops being accurate in one place: a chef can taste the soup, but nobody can "see" whether a table of 5 million rows has the right mix. That is why we write the classification down, as a plan, before building anything.

Why it matters

Without classification, teams fall into two traps. Either they copy everything from production (huge, risky, and still missing the odd cases that have never happened yet), or they hand-type five "happy path" rows and discover the bugs in production. Classification gives you a short list of questions to ask for any data request: where does it come from, how sensitive is it, and what must it prove?

2.3.5 What synthetic data is

Concept. Synthetic data is data created by a program following rules you set. No row in it was ever a real person's record.

Simple explanation. A film set looks like a street, but nobody lives in the houses. Synthetic data looks like customers, but no customer exists. It is built to be good enough to exercise the application, which is a different goal from being a copy of reality.

The analogy stops being accurate in one place. A film set is built once and looks right from one angle. Synthetic data must stay correct from every angle the application looks at it: the foreign keys must join, the dates must be in order, and the totals must add up.

What the tools say.

  • GenRocket: "Synthetic Test Data" is data manufactured or generated by an algorithm rather than real-world events. Its stated benefit is that companies can maximise test coverage by testing all permutations and combinations. From docs Why Synthetic Test Data? ↗
  • Informatica: data generation creates realistic test data for test environments, using generation rules that hold the logic. You import the metadata (table and column definitions) so the tool knows which columns to fill, assign rules to columns, then create a plan and run it (User Guide 10.5.10, p.190). From docs

Note what both descriptions have in common. The tool needs to know the shape of the target (the metadata) and a rule for each column. It does not need to see any real customer.

2.3.6.1 Which one should you choose?

  1. Is a realistic mix of messy data essential, such as for a new analytics report or a migration rehearsal?

    Lean towards masked production, because the real mess is the thing being tested.

    Result: use the subsetting and masking techniques from the subsetting and masking concept chapters.

  2. Is the system new, so there is no production data yet, or are you testing a feature with no history?

    Generate. There is nothing to copy.

    Result: use rules from this section.

  3. Do you need exact boundary, negative or very large data sets?

    Generate. Production rarely holds the 51st item in an order or a customer aged exactly 18 today.

  4. Do you need both realism and designed edge cases?

    Use a hybrid: masked subset as the base, generated rows added on top, with generated keys chosen so they never clash with the real ones.

Generated is not the same as safe by default

If a generator copies a real value (for example, picks names from an unmasked production table as its dictionary) the result is no longer purely synthetic. Always check where a generator's source list came from. Dictionaries should be made-up or public lists, never an export of real customers.

2.3.7.2 Seeds: making "random" repeatable

Concept. Computers do not produce truly random numbers. They run a formula that produces a long, random-looking list, starting from a number called the seed. Same seed, same list.

Why it matters. Suppose a test fails on Tuesday because customer 2003 had a zip code with a leading zero. If the data is regenerated on Wednesday with different random values, you may never see that customer again. With a fixed seed you can rebuild exactly Tuesday's data and debug it. The opposite is also useful: change the seed on purpose to get a fresh data set when you want fresh coverage.

GenRocket describes this directly: seeding generates the same set of random data for the same seed value every time, a seed can be set on the domain (a global seed variable) or in an attribute's generator configuration, and two attributes using the same generator and same seed produce the same random series. It also notes that GenRocket can generate the same data as previous runs through a seed on a domain or generator (FAQ). From docs What is Seeding? ↗

The snippet below is my own illustration of the principle in plain Python, not a vendor tool. It builds the 50 customers and orders designed in section 2.3.10. Run it twice with seed 42 and you get identical data; run it with seed 7 and you get different data.

import random

def generate(seed):
    rnd = random.Random(seed)              # the seed lives here
    first = ["Asha","Ravi","Meera","Kiran","Divya","Arjun","Sana","Vikram"]
    last  = ["Menon","Kumar","Nair","Iyer","Rao","Shah","Das","Pillai"]
    customers = []
    for i in range(50):
        cid = 2001 + i                     # sequential: 2001, 2002, ...
        customers.append((cid, rnd.choice(first), rnd.choice(last),
                          "%06d" % rnd.randint(560001, 560099)))   # random
    # exact distribution: 10 customers get 0 orders, 20 get 1, 15 get 2, 5 get 5
    counts = [0]*10 + [1]*20 + [2]*15 + [5]*5
    rnd.shuffle(counts)                    # random WHO, exact HOW MANY
    orders, oid = [], 9001
    for cust, n in zip(customers, counts):
        for _ in range(n):
            orders.append((oid, cust[0], rnd.randint(1, 4)))  # parent id, items
            oid += 1
    return customers, orders

c1, o1 = generate(42)
c2, o2 = generate(42)
c3, o3 = generate(7)
print(len(c1), len(o1), sum(x[2] for x in o1))   # 50 75 179
print(c1 == c2 and o1 == o2, c1 == c3)           # True False

Expected result when I ran it (Python 3.13): the first print shows 50 75 179 and the second shows True False. The first three customers with seed 42 were (2001, 'Ravi', 'Menon', '560095'), (2002, 'Divya', 'Iyer', '560029') and (2003, 'Meera', 'Kumar', '560087'). The item total 179 and these exact names depend on the random generator inside your Python version, so yours may differ. What must hold on your machine is True False.

2.3.7.3 Distributions: how values are spread

If every customer got exactly two orders, the data would be repeatable but unrealistic. Real shops have many customers with none, most with one or two, and a few with many. The snippet above states this on purpose: 10, 20, 15 and 5 customers get 0, 1, 2 and 5 orders. That is a distribution.

Both tools let you state percentages rather than writing a loop:

  • Informatica's random technique lets a regular expression create a fixed percentage of the generated values, and pattern percentages must total 100 (User Guide 10.5.10, p.220). Null and invalid-value rows are also set as percentages (pp.210 to 211). From docs
  • GenRocket's MultiWeightGen assigns weights (a percentage and a value) so that, for example, 50% of parents have 2 children, 20% have 3 and 30% have 1. With exactPercentage set to true, ten parents give exactly five, two and three parents of each type. From docs Generate Children based on Weights ↗
Exact or approximate?

With "10% of rows null", you can ask for roughly 10% (each row has a 10% chance) or exactly 10% (5 of 50). For small data sets such as 50 customers, always choose exact, otherwise a run can produce zero nulls and your null test silently tests nothing.

2.3.7.4 Rules that link columns

Some values only make sense in combination. A shipped date must come after the order date. A flight cannot leave and arrive at the same airport. Informatica's guide has both examples. It describes a conditional constraint: an expression such as To_City != From_City that restricts values in one column based on another (User Guide 10.5.10, pp.201 to 202). When the rule's own limits make the constraint impossible (for example a modified date that must be later than a created date of 31 July 2014, the last date the rule allows), the rule wins and the tool generates data with warning messages. From docs The lesson for your own designs: when two rules fight, decide which one is the boss, and expect warnings from the other.

2.3.8 Generating parent and child tables so every key is valid

Concept. A child row needs a parent that exists. If you generate ORDERS first and pick customer_id values at random, some will point at customers that do not exist, and the database (or the application's joins) will fail.

Simple explanation. You cannot write a library card for a member who has not been registered. So you register members first, then issue cards that carry a registered member's number.

2.3.8.1 Two common ways to keep keys valid

A. Child picks from existing parents

Generate the whole parent table first. Then, for each child row, choose a parent id from the finished list.

Informatica calls this a reference lookup rule: you name the parent table and assign parent columns to child columns (User Guide 10.5.10, p.229). From docs

Good when the parent table already exists, for example loading new orders against real or masked customers.

B. Children are made inside each parent

Loop over parents. For each parent, decide how many children it has, then create exactly that many, stamping the parent's id on each.

GenRocket works this way: a parent domain's loop count and the child's count per parent drive the output, and it generates data sequentially along the relationships (see its "Parent, Child, and Sibling Relationships" page). From docs

Good when both tables are being created together, and when you want a controlled number of children per parent.

GenRocket's page also says every domain has an id or primary attribute that is used to guarantee referential integrity between domains, and its FAQ says it can generate synthetic data with full referential integrity. It introduces a "sibling" idea: a table that merely describes another (the page's example is a role table describing a user table) is marked as a sibling instead of a parent, to avoid generating unnecessary data. From docs Parent, Child, and Sibling Relationships ↗

2.3.8.2 How many children per parent?

Informatica's plan settings for data generation include a minimum and maximum number of child records for each parent record, each with a default of 1, and percentages for "parent records without children" and "child records without parent" for self-cyclic tables and reference lookup rules (User Guide 10.5.10, p.285). From docs Those last two settings exist because sometimes you want a customer with no orders (a null-style condition) or, rarely, a deliberately orphaned child (for a data-quality test). Do this only on purpose and label it, so nobody mistakes it for a bug.

Self-referencing tables

A table whose foreign key points at itself (an employee table with a manager id) has no "parents first" order. The tool needs a special rule: the first rows have no parent, later rows point back at earlier ones. Informatica's setting names self-cyclic tables specifically (p.285). ShopSphere has none, so we do not build one here.

2.3.10.4 Deploy and verify

After the run, check three things before you hand the data over. These SQL checks are what I ran against my generated rows in SQLite; the syntax works on most databases.

-- 1. No orphan orders (expected: 0)
SELECT COUNT(*) FROM orders o
LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL;

-- 2. The orders-per-customer distribution matches the design
SELECT n AS orders_per_customer, COUNT(*) AS customers
FROM (SELECT c.customer_id, COUNT(o.order_id) AS n
      FROM customers c
      LEFT JOIN orders o ON o.customer_id = c.customer_id
      GROUP BY c.customer_id) t
GROUP BY n ORDER BY n;

-- 3. The null and empty rows really exist (expected: 2, 1, 1, 1)
SELECT SUM(CASE WHEN phone IS NULL THEN 1 ELSE 0 END)    AS null_phone,
       SUM(CASE WHEN email IS NULL THEN 1 ELSE 0 END)    AS null_email,
       SUM(CASE WHEN zip_code = '' THEN 1 ELSE 0 END)    AS empty_zip,
       SUM(CASE WHEN tax_id IS NULL THEN 1 ELSE 0 END)   AS null_tax_id
FROM customers;

2.3.13 Common mistakes and gotchas

Mistakes beginners make
  • Generating children before parents. The foreign keys then point at nothing. Always parents first, or have the child rule read from the finished parent table.
  • All-random data and no designed edges. Random values almost never hit an exact boundary, a null, or a name with an apostrophe. Put those rows in on purpose.
  • Not recording the seed. A failed test cannot be reproduced if the data cannot be rebuilt.
  • Requesting "about 10% null". In a 50-row data set that can come out as zero. Ask for an exact count.
  • Totals that do not add up. Derive total_amount from the items instead of generating it separately.
  • Loading invalid values into constrained columns. The load fails or the constraint is silently dropped. Keep negative data in the input channel.
  • Treating synthetic as automatically realistic. It only mirrors what you modelled. Compare a few generated distributions against real, masked, aggregated figures.
  • Reusing real values as the "dictionary". A name list exported from production defeats the purpose.

2.3.14 Recap

Recap
  • Classify test data along three lines: source (production-derived or synthetic), sensitivity (what harm a leak causes) and purpose (what the row must prove).
  • The seven purposes are valid, invalid, boundary, edge case, null or empty, volume and security. The syllabus data patterns (boundary, sequential, random, edge cases, null) are ways of shaping values to serve them.
  • Synthetic data is created from rules. It gives privacy and designed coverage; masked production gives real-world mess. Hybrids use both.
  • Generation needs a target shape, a rule or generator per column, and run settings. A seed makes it repeatable and a distribution makes it realistic.
  • Generate parents first and make every foreign key copy an existing parent id; control how many children each parent gets.
  • GenRocket's cycle is Model, Design, Deploy, Manage. Test data as a service means requestable, catalogued, repeatable data owned by a small expert group.
  • A coverage matrix shows gaps before the testers find them.
