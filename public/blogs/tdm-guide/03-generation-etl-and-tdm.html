3.1 Test data classification and synthetic data generation

Day 45, Day 46, Day 47

So far you have met two ways to get test data. You can copy and cut down real data (the discovery and subsetting concepts chapter) and then hide the sensitive parts (the masking concepts chapter). This section introduces the third way: make the data up, on purpose, from rules. Before we do that we need a better question than "where do I get data?". The better question is: what is this data for?

A tester checking the login screen does not need "a lot of customers". She needs one normal customer, one customer whose account is locked, one with a very long surname, one with no phone number, and one whose date of birth makes them exactly 18 today. Each of those rows has a different job. Naming the jobs is called classifying test data, and it is the starting point for designing any data set, whether you copy it, mask it or generate it.

This section is also where the course syllabus phrase "Model, Design, Deploy, Manage" first appears, and where the five "data patterns" of the syllabus (boundary conditions, sequential, random, edge cases, null) are placed on a map. The tool chapters later (the Informatica data generation chapter and the GenRocket chapters) assume you have read this one.

What you will learn

  • The seven purposes of test data (valid, invalid, boundary, edge case, null or empty, volume, security) and how the syllabus "data patterns" map onto them.

3.1.1 Words to know first

Test data
Any data the application is fed or finds waiting in its database during a test. It includes both the rows in the database and the values typed into screens or sent in files.
Test condition
One specific situation a test wants to check, such as "customer with no phone number" or "order with the maximum number of items". Each condition needs data that creates it.
Positive (valid) data
Data the application should accept and process normally.
Negative (invalid) data
Data the application should reject or handle gracefully, such as letters in a phone number.
Boundary value
A value sitting exactly on the edge of what is allowed. If customers must be 18 or older, the boundary values are 17, 18 and 19 years.
Edge case
A rare or unusual situation outside normal use, such as a surname containing an apostrophe. GenRocket describes it as a rare or unexpected scenario outside the typical usage pattern.
Synthetic data
Data made by a program following rules, instead of being taken from real events. GenRocket's help centre puts it as data manufactured by an algorithm rather than real-world events.
Generator
The small piece of logic that produces the values for one column, for example "count up from 1" or "pick a name from a list".
Seed
A starting number given to a random generator. The same seed gives the same "random" values every time, so a test data set can be rebuilt exactly.
Distribution
How values are spread: for example, 20% of customers have no orders, 40% have one. Real data is lumpy, and good test data copies the lumps that matter.
Referential integrity
The promise that every foreign key points at a row that exists. An order whose customer_id has no matching customer breaks it. See the data basics chapter.
Parent table / child table
The table being pointed at (CUSTOMERS) is the parent; the table holding the foreign key (ORDERS) is the child.
Coverage matrix
A grid that lists test conditions against the data that covers them, so you can see gaps at a glance.

3.1.2 Why classify test data at all?

General concept Imagine a kitchen preparing for a cooking class. The chef does not just buy "food". She buys the exact ingredients each recipe needs, in the amounts each recipe needs, and she keeps the allergy-sensitive items (nuts) in a separate, labelled place. Test data works the same way. You prepare the exact rows each test needs, and you keep the dangerous ones (real personal data) away from places they must not be.

The analogy stops being accurate in one place: a chef can taste the soup, but nobody can "see" whether a table of 5 million rows has the right mix. That is why we write the classification down, as a plan, before building anything.

Why it matters

Without classification, teams fall into two traps. Either they copy everything from production (huge, risky, and still missing the odd cases that have never happened yet), or they hand-type five "happy path" rows and discover the bugs in production. Classification gives you a short list of questions to ask for any data request: where does it come from, how sensitive is it, and what must it prove?

3.1.5 What synthetic data is

Concept. Synthetic data is data created by a program following rules you set. No row in it was ever a real person's record.

Simple explanation. A film set looks like a street, but nobody lives in the houses. Synthetic data looks like customers, but no customer exists. It is built to be good enough to exercise the application, which is a different goal from being a copy of reality.

The analogy stops being accurate in one place. A film set is built once and looks right from one angle. Synthetic data must stay correct from every angle the application looks at it: the foreign keys must join, the dates must be in order, and the totals must add up.

What the tools say.

  • GenRocket: "Synthetic Test Data" is data manufactured or generated by an algorithm rather than real-world events. Its stated benefit is that companies can maximise test coverage by testing all permutations and combinations. From docs Why Synthetic Test Data? ↗
  • Informatica: data generation creates realistic test data for test environments, using generation rules that hold the logic. You import the metadata (table and column definitions) so the tool knows which columns to fill, assign rules to columns, then create a plan and run it (User Guide 10.5.10, p.190). From docs

Note what both descriptions have in common. The tool needs to know the shape of the target (the metadata) and a rule for each column. It does not need to see any real customer.

A real-world example from the Informatica guide

The guide's own example is an airline that sells plane tickets. Rules load dictionary values such as names into the customer tables, create random number strings for ticket numbers, create a numeric sequence for identification numbers, and use a reference lookup for values such as airport codes (User Guide 10.5.10, p.191). From docs Map that to ShopSphere and you get: a name dictionary for first_name, a sequence for customer_id, random strings for order references, and a lookup of valid product_code values.

3.1.6.1 Which one should you choose?

  1. Is a realistic mix of messy data essential, such as for a new analytics report or a migration rehearsal?

    Lean towards masked production, because the real mess is the thing being tested.

    Result: use the subsetting and masking techniques from the subsetting and masking concept chapters.

  2. Is the system new, so there is no production data yet, or are you testing a feature with no history?

    Generate. There is nothing to copy.

    Result: use rules from this section.

  3. Do you need exact boundary, negative or very large data sets?

    Generate. Production rarely holds the 51st item in an order or a customer aged exactly 18 today.

  4. Do you need both realism and designed edge cases?

    Use a hybrid: masked subset as the base, generated rows added on top, with generated keys chosen so they never clash with the real ones.

Generated is not the same as safe by default

If a generator copies a real value (for example, picks names from an unmasked production table as its dictionary) the result is no longer purely synthetic. Always check where a generator's source list came from. Dictionaries should be made-up or public lists, never an export of real customers.

3.1.7.2 Seeds: making "random" repeatable

Concept. Computers do not produce truly random numbers. They run a formula that produces a long, random-looking list, starting from a number called the seed. Same seed, same list.

Why it matters. Suppose a test fails on Tuesday because customer 2003 had a zip code with a leading zero. If the data is regenerated on Wednesday with different random values, you may never see that customer again. With a fixed seed you can rebuild exactly Tuesday's data and debug it. The opposite is also useful: change the seed on purpose to get a fresh data set when you want fresh coverage.

GenRocket describes this directly: seeding generates the same set of random data for the same seed value every time, a seed can be set on the domain (a global seed variable) or in an attribute's generator configuration, and two attributes using the same generator and same seed produce the same random series. It also notes that GenRocket can generate the same data as previous runs through a seed on a domain or generator (FAQ). From docs What is Seeding? ↗

The snippet below is my own illustration of the principle in plain Python, not a vendor tool. It builds the 50 customers and orders designed in section 3.1.10. Run it twice with seed 42 and you get identical data; run it with seed 7 and you get different data.

import random

def generate(seed):
    rnd = random.Random(seed)              # the seed lives here
    first = ["Asha","Ravi","Meera","Kiran","Divya","Arjun","Sana","Vikram"]
    last  = ["Menon","Kumar","Nair","Iyer","Rao","Shah","Das","Pillai"]
    customers = []
    for i in range(50):
        cid = 2001 + i                     # sequential: 2001, 2002, ...
        customers.append((cid, rnd.choice(first), rnd.choice(last),
                          "%06d" % rnd.randint(560001, 560099)))   # random
    # exact distribution: 10 customers get 0 orders, 20 get 1, 15 get 2, 5 get 5
    counts = [0]*10 + [1]*20 + [2]*15 + [5]*5
    rnd.shuffle(counts)                    # random WHO, exact HOW MANY
    orders, oid = [], 9001
    for cust, n in zip(customers, counts):
        for _ in range(n):
            orders.append((oid, cust[0], rnd.randint(1, 4)))  # parent id, items
            oid += 1
    return customers, orders

c1, o1 = generate(42)
c2, o2 = generate(42)
c3, o3 = generate(7)
print(len(c1), len(o1), sum(x[2] for x in o1))   # 50 75 179
print(c1 == c2 and o1 == o2, c1 == c3)           # True False

Expected result when I ran it (Python 3.13): the first print shows 50 75 179 and the second shows True False. The first three customers with seed 42 were (2001, 'Ravi', 'Menon', '560095'), (2002, 'Divya', 'Iyer', '560029') and (2003, 'Meera', 'Kumar', '560087'). The item total 179 and these exact names depend on the random generator inside your Python version, so yours may differ. What must hold on your machine is True False.

3.1.7.3 Distributions: how values are spread

If every customer got exactly two orders, the data would be repeatable but unrealistic. Real shops have many customers with none, most with one or two, and a few with many. The snippet above states this on purpose: 10, 20, 15 and 5 customers get 0, 1, 2 and 5 orders. That is a distribution.

Both tools let you state percentages rather than writing a loop:

  • Informatica's random technique lets a regular expression create a fixed percentage of the generated values, and pattern percentages must total 100 (User Guide 10.5.10, p.220). Null and invalid-value rows are also set as percentages (pp.210 to 211). From docs
  • GenRocket's MultiWeightGen assigns weights (a percentage and a value) so that, for example, 50% of parents have 2 children, 20% have 3 and 30% have 1. With exactPercentage set to true, ten parents give exactly five, two and three parents of each type. From docs Generate Children based on Weights ↗
Exact or approximate?

With "10% of rows null", you can ask for roughly 10% (each row has a 10% chance) or exactly 10% (5 of 50). For small data sets such as 50 customers, always choose exact, otherwise a run can produce zero nulls and your null test silently tests nothing.

3.1.7.4 Rules that link columns

Some values only make sense in combination. A shipped date must come after the order date. A flight cannot leave and arrive at the same airport. Informatica's guide has both examples. It describes a conditional constraint: an expression such as To_City != From_City that restricts values in one column based on another (User Guide 10.5.10, pp.201 to 202). When the rule's own limits make the constraint impossible (for example a modified date that must be later than a created date of 31 July 2014, the last date the rule allows), the rule wins and the tool generates data with warning messages. From docs The lesson for your own designs: when two rules fight, decide which one is the boss, and expect warnings from the other.

3.1.8 Generating parent and child tables so every key is valid

Concept. A child row needs a parent that exists. If you generate ORDERS first and pick customer_id values at random, some will point at customers that do not exist, and the database (or the application's joins) will fail.

Simple explanation. You cannot write a library card for a member who has not been registered. So you register members first, then issue cards that carry a registered member's number.

3.1.8.1 Two common ways to keep keys valid

A. Child picks from existing parents

Generate the whole parent table first. Then, for each child row, choose a parent id from the finished list.

Informatica calls this a reference lookup rule: you name the parent table and assign parent columns to child columns (User Guide 10.5.10, p.229). From docs

Good when the parent table already exists, for example loading new orders against real or masked customers.

B. Children are made inside each parent

Loop over parents. For each parent, decide how many children it has, then create exactly that many, stamping the parent's id on each.

GenRocket works this way: a parent domain's loop count and the child's count per parent drive the output, and it generates data sequentially along the relationships (see its "Parent, Child, and Sibling Relationships" page). From docs

Good when both tables are being created together, and when you want a controlled number of children per parent.

GenRocket's page also says every domain has an id or primary attribute that is used to guarantee referential integrity between domains, and its FAQ says it can generate synthetic data with full referential integrity. It introduces a "sibling" idea: a table that merely describes another (the page's example is a role table describing a user table) is marked as a sibling instead of a parent, to avoid generating unnecessary data. From docs Parent, Child, and Sibling Relationships ↗

3.1.8.2 How many children per parent?

Informatica's plan settings for data generation include a minimum and maximum number of child records for each parent record, each with a default of 1, and percentages for "parent records without children" and "child records without parent" for self-cyclic tables and reference lookup rules (User Guide 10.5.10, p.285). From docs Those last two settings exist because sometimes you want a customer with no orders (a null-style condition) or, rarely, a deliberately orphaned child (for a data-quality test). Do this only on purpose and label it, so nobody mistakes it for a bug.

Self-referencing tables

A table whose foreign key points at itself (an employee table with a manager id) has no "parents first" order. The tool needs a special rule: the first rows have no parent, later rows point back at earlier ones. Informatica's setting names self-cyclic tables specifically (p.285). 3.1.13 Common mistakes and gotchas

Mistakes beginners make
  • Generating children before parents. The foreign keys then point at nothing. Always parents first, or have the child rule read from the finished parent table.
  • All-random data and no designed edges. Random values almost never hit an exact boundary, a null, or a name with an apostrophe. Put those rows in on purpose.
  • Not recording the seed. A failed test cannot be reproduced if the data cannot be rebuilt.
  • Requesting "about 10% null". In a 50-row data set that can come out as zero. Ask for an exact count.
  • Totals that do not add up. Derive total_amount from the items instead of generating it separately.
  • Loading invalid values into constrained columns. The load fails or the constraint is silently dropped. Keep negative data in the input channel.
  • Treating synthetic as automatically realistic. It only mirrors what you modelled. Compare a few generated distributions against real, masked, aggregated figures.
  • Reusing real values as the "dictionary". A name list exported from production defeats the purpose.

3.1.14 Recap

Recap
  • Classify test data along three lines: source (production-derived or synthetic), sensitivity (what harm a leak causes) and purpose (what the row must prove).
  • The seven purposes are valid, invalid, boundary, edge case, null or empty, volume and security. The syllabus data patterns (boundary, sequential, random, edge cases, null) are ways of shaping values to serve them.
  • Synthetic data is created from rules. It gives privacy and designed coverage; masked production gives real-world mess. Hybrids use both.
  • Generation needs a target shape, a rule or generator per column, and run settings. A seed makes it repeatable and a distribution makes it realistic.
  • Generate parents first and make every foreign key copy an existing parent id; control how many children each parent gets.
  • GenRocket's cycle is Model, Design, Deploy, Manage. Test data as a service means requestable, catalogued, repeatable data owned by a small expert group.
  • A coverage matrix shows gaps before the testers find them.

3.2.2 What ETL is and why it exists

Concept. ETL is a repeatable process that moves data from where it is created to where it is needed, fixing it on the way.

Simple explanation. Think of a school canteen. Vegetables arrive muddy from several farms (extract brings them to the back door), staff wash, cut and combine them in the prep room (transform), and trays go to the serving counter (load). Each stage has its own place and rules.

The analogy stops being accurate here: an ETL job runs many times and must give the same kind of result each time, even if interrupted and restarted. Cooks can improvise; ETL jobs must not.

Why it matters

Data in real companies lives in many places and many shapes. ShopSphere's orders sit in one database, product prices in a spreadsheet maintained by buyers, and a partner sends a daily file where dates are written day first. A manager who asks "how much did we sell last week, per product?" needs one clean answer. Someone has to collect, clean and combine. ETL is the name for doing that on purpose, automatically, and with a record of what happened.

ETL appears in data warehouses and reports (the classic case), system migrations, keeping two systems in step, feeding analytics, and test data provisioning, the topic of the next chapter.

3.2.5.2 Full versus incremental extraction

Full extract

Read every row, every run.

Good: simple; no state to remember; picks up deletions automatically because the target is rebuilt.

Bad: slow and heavy as data grows; reads unchanged data again and again.

Use for: small reference tables such as PRODUCTS, and first-time loads.

Incremental extract

Read only rows that are new or changed since the last successful run.

Good: fast; kind to the source.

Bad: needs a reliable way to know "what changed"; misses deleted rows unless you plan for them.

Use for: large, growing tables such as ORDERS.

3.2.5.3 The watermark technique

The simplest incremental method is a watermark: store the highest value you have processed, and next time ask only for rows beyond it. It needs a column whose value only ever grows, such as an increasing order number or a "last modified" timestamp.

ShopSphere's order feed has an increasing order_id, so we keep a small control table with one row per job:

CREATE TABLE etl_control (
  job_name      TEXT PRIMARY KEY,
  last_order_id INTEGER
);
INSERT INTO etl_control VALUES ('orders_daily', 0);

-- Extract only new orders (the feed holds text, so convert for the comparison)
INSERT INTO stg_orders
SELECT 1, o.*
FROM   feed_orders o
WHERE  CAST(o.order_id AS INTEGER) >
       (SELECT last_order_id FROM etl_control WHERE job_name = 'orders_daily');

-- After the whole run succeeds, move the watermark forward
UPDATE etl_control
SET    last_order_id = (SELECT MAX(CAST(order_id AS INTEGER)) FROM stg_orders)
WHERE  job_name = 'orders_daily';

Expected result in my SQLite run: on the first run (watermark 0) five orders (5001 to 5005) were staged and the watermark moved to 5005. On the second run, with orders 5006 and 5007 newly added to the feed, only those two were staged and the watermark moved to 5007.

Three ways a watermark goes wrong
  • Moving the watermark too early. If you advance it before the load finishes and the job fails, those rows are never retried. Advance it as the very last step, in the same transaction as the load when possible.
  • A column that is not strictly increasing. If IDs can be assigned out of order by two servers, a late row with a smaller number is skipped forever. A "last modified" timestamp has the same trap when clocks differ.
  • Changes and deletes are invisible. A watermark on order_id sees new orders, not edits to old ones, and never sees a deleted row. For edits use a last-modified column; for deletes use CDC or a periodic full comparison.

3.2.5.5 Good extraction habits

  1. Record the run.

    Give every run a batch id and a timestamp, and write both next to the extracted rows. When something looks wrong later, you can say exactly which run brought it in.

  2. Read a consistent snapshot.

    If you extract CUSTOMERS and then ORDERS five minutes later, new orders may point at customers you did not capture. Extract related tables in one transaction or point in time, or cut the orders to a time you know customers cover.

    What you should see: every order in staging has its customer in staging, or the job knows why not.

3.2.6 The staging area

Concept. The staging area is a temporary landing zone between the source and the final target. Extracted data is stored there in nearly the same form as it was found.

Simple explanation. In the canteen, it is the delivery bay where crates are put down before anyone peels anything.

Why it matters. Staging gives you four things:

  • A frozen copy. You can transform, check and re-run without hitting the source again.
  • Separation of duties. Extraction only reads; transformation only reshapes; neither depends on the other being fast.
  • Safe restarts. A failure in the transform step does not need a new extract.

Informatica's plans give you the same idea in their connection options.   • Mirror the source, with all columns as text. A staged row should never fail because a date has a strange format. Conversion is the transform step's job.

  • No keys, no foreign keys, no constraints. Staging must accept bad data so that the transform step can decide what to do with it.
  • Empty it each run (or partition by batch). Old staged data is usually not worth keeping beyond debugging.

3.2.7 Transform: cleaning and reshaping

Concept. Transformation turns staged raw data into the clean, consistent, correctly typed shape the target needs.

Why it matters. This is where business rules live. If the transform is wrong, the data is wrong everywhere downstream, and nobody can tell from the target alone. Transformations are therefore the part of ETL most worth documenting and testing.

There are nine everyday kinds of transformation: cleaning, type conversion, mapping, deduplication, lookups, filtering, joining, derived columns and aggregation. We cover each in turn using the ShopSphere staging rows from the previous section. Each subsection shows the idea, the SQL, and the before and after.

3.2.7.1 Cleaning

Idea. Make values consistent so that equal things look equal. "MENON", "Menon" and "menon " are the same surname to a person, but three different strings to a database.

  UPPER(SUBSTR(TRIM(last_name),1,1))  || LOWER(SUBSTR(TRIM(last_name),2))  AS last_name,
  COALESCE(LOWER(TRIM(email)), 'not provided')                              AS email

3.2.7.2 Type conversion

Idea. Staging holds everything as text. The target needs real dates and numbers so that sorting, comparing and adding work properly. As text, "9" sorts after "10", and "20/10/2026" sorts before "21/09/2026" only by accident.

  CAST(order_id AS INTEGER) AS order_id,
  SUBSTR(order_date,7,4) || '-' || SUBSTR(order_date,4,2) || '-' || SUBSTR(order_date,1,2) AS order_date,
  CAST(total_amount AS REAL) AS total_amount
FROM stg_orders
WHERE total_amount NOT GLOB '*[^0-9.]*';   -- only rows whose amount is numeric

3.2.7.4 Deduplication

Idea. Keep one row for each real-world thing. Customer 1002 arrived twice in the staging data.

SELECT customer_id, first_name, last_name, email, zip_code
FROM (
  SELECT s.*,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY customer_id) AS rn
  FROM stg_customers s
) t
WHERE rn = 1;

ROW_NUMBER() numbers the rows inside each customer id (1, 2, ...); keeping only number 1 removes the extras. The ORDER BY inside the window decides which duplicate survives. Here the two copies were identical so it did not matter. In real data the copies often differ, and you must choose a rule such as "keep the latest by modified date" or "keep the one with the most filled-in columns".

3.2.7.6 Filtering, validating and rejecting

Idea. Some rows should not reach the target. Filtering removes rows that are valid but unwanted (for example, test orders). Validating checks rows against rules and rejects those that fail, keeping them aside with a reason so someone can fix them.

3.2.7.7 Joining and derived columns

Joining combines rows from different inputs. To build the sales fact table we join order items to their orders for date, customer and status. Ask of every join: "what happens to a row with no match?" An inner join drops it; a left join keeps it with empty columns. That is a business decision, not a technical one. Derived columns calculate values that do not exist in the source, such as line_amount as quantity times unit price (item 2: 2 × 100.00 = 200.0).

3.2.8 Load: writing into the target

Concept. Loading writes the transformed rows into the target tables, in a way that is correct, repeatable and fast enough.

Why it matters. A load that half-finishes leaves the target in a state nobody understands: some rows from tonight, some from yesterday. Loads must either complete or leave things as they were, and they must be safe to run again.

3.2.9 Batch, streaming, and ETL versus ELT


3.2.9.1 Batch versus streaming at a glance


Batch collects data for a period (an hour, a night) and processes it as one group. It is easy to reason about and to re-run, and results are always "as of the last run". Most ETL, and nearly all test data provisioning, is batch. Streaming processes each event within seconds of arrival. Results are fresh, but you must handle duplicates and out-of-order events, so it is used where the answer must be current, such as fraud alerts. A middle path, micro-batching, runs a small batch every minute or so.


3.2.9.2 ETL versus ELT


In ETL, transformations run in the ETL engine, on its own servers, before data reaches the target. In ELT, raw data is loaded into the target first (often a powerful cloud warehouse) and transformed there using its SQL engine.

3.2.13 Error handling


Concept. Error handling is the plan for what the job does when something goes wrong, decided before it goes wrong.


Why it matters. Something will go wrong. A file will arrive empty, a database will be down for maintenance, a date will say 31 February. The question is whether you find out from an alert at 2 a.m. with a clear row count, or from an angry tester at 10 a.m. with a half-loaded database.

3.2.13.3 Reprocessing rejected rows


Run 1 rejected orders 5004 and 5005, and the watermark moved past them, so nothing picks them up again. Rejected rows need their own path: group the reject table by reason, have the owner fix the cause (the "abc" amount; whether customer 9999 arrives tomorrow), then re-stage the corrected rows as a new batch and run transform and load again.


Idempotence and restarts

A safe job can be run twice with no harm. Achieve this with upserts, with "delete the target rows of this batch, then insert them" loads, and with watermarks moved last. Without it, every failed run needs a careful human cleanup, and humans make mistakes at 2 a.m. In my SQL, the fact load used INSERT OR REPLACE keyed on item_id for this reason (other databases: MERGE or delete-then-insert).

FROM   fact_order_line f

3.2.15 Performance ideas


Performance tuning is its own craft, and the right fix depends on measurement. These are the ideas that help most often, in the order I would try them. General concept


    

  1. Think in sets, not rows.
    One SQL statement that updates a million rows is much faster than a program that updates them one by one. Many ETL tools give you a row-by-row feeling in their diagrams, but good ones process rows in streams and batches.
    2. 

  2. Use bulk loading for big loads.
    See 8.8.1 for the documented examples from GenRocket's FAQ.
    3. 

  3. Tune commit size.
    A commit after every row is slow; a commit after 50 million rows risks a huge rollback. Informatica's default of 10,000 rows is a hint at the ballpark, not a rule.
    4. 

  4. Handle indexes and constraints during the load.
    Maintaining an index for every inserted row costs time. Some loads drop indexes first and rebuild afterwards. Delphix exposes this as the "Drop Indexes" job option and warns that multiple update threads can cause deadlocks, advising fewer threads if that happens (jobs page). From docs
    5. 

  5. Run in parallel.
    Independent tables can load at the same time. Delphix jobs have "Number of Streams", described as the number of parallel streams, so several tables are processed at once; some streams finish before others, so the number of active streams falls during the job (jobs page). From docs Informatica allows up to eight concurrent workflows (p.276).

3.2.19 Common mistakes and gotchas


Mistakes beginners make

    

  • Transforming while extracting. Business logic buried in the source query is invisible and slows the source.
    • 

  • Inner joins on lookups. A failed match silently deletes rows. Use left joins with a default, or an explicit reject.
    • 

  • Moving the watermark before the load finishes. A failure then loses data forever.
    • 

  • Overwriting when history matters. Upsert is right for corrections; a history-keeping load is right when reports must show "as it was".
    • 

  • Letting one bad row stop everything, or letting bad rows disappear. Reject with a reason, and set a threshold for when to stop.
    • 

  • No reconciliation. A job that "succeeds" with the wrong totals is worse than one that fails loudly.
    • 

  • Forgetting that deletes are invisible to a watermark. Plan for them, or accept and document the gap.
    • 




3.2.20 Recap


Recap

    

  • ETL moves data from sources to targets in three steps: extract (read), transform (clean, convert, enrich, combine, summarise) and load (write), usually through a staging area that keeps a raw copy.
    • 

  • Extraction can be full or incremental; a watermark or change data capture tells an incremental run what is new.
    • 

  • Transformation covers cleaning, type conversion, value mapping, deduplication, lookups, filtering and rejecting, joining, derived columns and aggregation. Lookups and joins must decide what happens when nothing matches.
    • 

  • Loads can be truncate and load, append, incremental, upsert, bulk, or history-keeping (slowly changing dimension). A safe load can be run twice without harm.
    • 

  • An ETL architecture has sources, an integration engine, a metadata repository, a scheduler, monitoring and logs, and targets. Tools add layers: mappings, sessions, workflows, schedules.
    • 

  • A mapplet is Informatica's reusable group of transformations. TDM can import mapplets as masking and generation rules.
    • 

  • Good ETL rejects bad rows with reasons, tolerates a set number of errors, reconciles counts, and records every run.
    • 

  • ELT loads raw data first and transforms inside the target; test data work usually transforms (masks) before loading.

3.3.1 Words to know first




TDM pipeline
The chain of stages that turns production (or a generator) into a usable test data set: find sensitive data, cut it down, mask it, load it, check it.


Provisioning
Delivering a prepared data set to a test environment so testers can use it.


In-place masking
Masking that changes the values inside the database you point it at. Delphix describes in-place jobs as updating the source environment with the masked values.


On-the-fly masking
Masking while copying: unmasked data is read from the source and only masked data is written to the target. This is the ETL order.


Deterministic (consistent) masking
Masking that turns the same input into the same output every time, so the same customer is masked identically in every table and every run.


Driving table
The table whose rows decide which rows are copied. Informatica uses the term for the starting point of a subset.


Audit trail
A record of who ran what, when, and with which settings, kept so that compliance questions can be answered later.


Refresh
Re-running the pipeline to replace old test data with a new copy.


Receiver
GenRocket's component that receives generated data and writes it into a usable format at a destination. It plays the role of the load stage.


Workflow (Informatica)
The runnable job that Test Data Manager generates from a plan.





3.3.2 The same underlying idea


Concept. Both ETL and TDM move data and change it on the way. Both read from a source, apply rules, and write to a target. Both are driven by definitions that tell the engine what to do, both run as repeatable jobs, and both need logs, error handling and connections to databases.

3.3.3.1 The differences in more detail


Shape. ETL changes shape because the target has a different purpose (a star schema, as in the previous chapter). TDM keeps shape because the application under test expects its own tables. The documents show this: GenRocket's G-Subset can only migrate between databases of the same type, for example MySQL to MySQL (G-Subset overview); Delphix on-the-fly masking supports Oracle to Oracle or delimited file to delimited file, and database to delimited file (jobs page). From docs


Consistency. A warehouse can lose the original keys and use surrogate ones. A test database cannot, because the application joins on the real keys. Masking must keep joins working: if customer_id in CUSTOMERS is masked differently from customer_id in ORDERS, the join returns no rows. Delphix's terminology page shows how its algorithms deal with this: a secure lookup algorithm picks replacements by a cryptographic hash of the original value, "so masking output is consistent for each input"; mapping algorithms guarantee no collisions; segment mapping permutes short values with no collisions and is suggested for unique columns such as Social Security Numbers and keys. From docs Delphix masking terminology ↗


Size. Informatica describes a data subset as a "small, targeted, and referentially intact copy" of production for nonproduction use (User Guide 10.5.10, p.112). From docs Small matters because test environments are cheap and many; but small must still be whole, meaning parents and children come together. Section 3.3.6 shows the integrity options.


Repeatability. Informatica lets you use criteria parameters so the same workflow produces different subsets by changing values at run time (p.113). Delphix jobs can be multi-tenant, so the same rule set masks identical schemas through different connectors chosen when the job runs. GenRocket can regenerate the same data with a seed (General FAQ). From docs


Success measure. A broken ETL job is noticed when a report is wrong. A broken TDM job may produce a data set that looks fine and leaks a real phone number. Its success has to be proven by checks for leakage as well as for counts, which is why section 3.3.7 ends with a test step.

Here is the picture to keep in your head for the tool chapters. Every stage is something you met in the ETL chapter; the two extra boxes at the ends (profile and test) are TDM additions. General concept



3.3.5.1 Stage by stage


    

  1. Profile.
    Reason: you cannot mask what you have not found. Profiling scans columns for patterns (SSN-like, phone-like) and learns which tables relate.
    Output: a list of sensitive columns and a relationship map, approved by a data steward. Covered in the Informatica profiling chapter and the Delphix profiling chapter.
    2. 

  2. Extract the subset.
    Reason: copying everything is slow and expands the exposure. Choose driver rows, then pull in all related rows so the subset is whole.
    Output: a consistent slice in staging or in a stream, still containing real values.
    3. 

  3. Mask (transform).
    Reason: this is the stage that removes risk, so it must happen before data lands anywhere testers can read.
    Output: the same rows with sensitive values replaced consistently.
    4. 

  4. Load.
    Reason: put the result where tests run, in the right order and within the target's constraints.
    Output: a populated test database or set of files.
    5. 

  5. Verify, then test.
    Reason: nobody should trust a TDM job on its exit code. Check keys, counts and, crucially, that no original sensitive value survived.
    Output: pass or fail evidence, stored with the run.
    6. 



The supporting services mirror ETL architecture: a rules repository (metadata), an orchestrator (scheduler), logs (monitoring), plus a place to keep versions of data sets. Why the order extract, mask, load matters

If you load first and mask afterwards (an ELT-style order), there is a time window in which real personal data sits in the test database, copies may be taken, and a failed masking job leaves the original data behind. Delphix says it plainly for in-place jobs: when a masking job fails, the target "may be in a partially masked or unmasked state" (Job monitoring), and stopping a running job results in semi-masked data (Running and Stopping Jobs). From docs On-the-fly masking avoids the window by never writing unmasked data to the target.

3.3.8 Pitfalls: where ETL habits hurt TDM


3.3.8.1 Masking after load instead of before


The ETL reflex "land the raw data, then clean it" is wrong for sensitive data. Between the load and the end of masking, real values sit in an environment with wide access, and a failure leaves them there. Prefer on-the-fly or pre-load masking, or in-place masking inside a protected staging environment that testers cannot reach, and copy onward only after verification. Informatica's plan masks data inside the same workflow that loads the target, with subset first (p.275); Delphix on-the-fly jobs never write unmasked rows to the target; GenRocket G-Subset replaces sensitive values in the dump file before insertion. From docs


3.3.8.2 Consistency across ETL and masking


When keys are masked, they must be masked identically wherever they appear. I tested this with the three ShopSphere customers and four orders by adding 70000 to the key.


-- Customer keys masked, order keys left alone: the join breaks
SELECT COUNT(*) FROM ord o JOIN (SELECT customer_id + 70000 AS customer_id FROM cust) c
  ON c.customer_id = o.customer_id;                        -- returns 0

-- The same rule applied to both tables: the join works
SELECT COUNT(*) FROM (SELECT order_id, customer_id + 70000 AS customer_id FROM ord) o
  JOIN (SELECT customer_id + 70000 AS customer_id FROM cust) c
  ON c.customer_id = o.customer_id;                        -- returns 4


Two further consistency risks come from ETL-style staging. First, if the same person appears in two systems (CRM and billing) and each is masked by a separate job with a random rule, the person gets two different fake identities and cross-system tests fail. Use deterministic rules and share the algorithm and its key across jobs. Delphix algorithms differ in this respect: some are non-deterministic and "cannot guarantee the same output for the same input across masking jobs", while others are fixed (Algorithm syncability ↗); the terminology page also notes that a secure lookup can collide, which matters when a column must stay unique. From docs Second, a reversible method such as tokenization (the only algorithm type that allows reversing, per the terminology page) is a deliberate exception, not a default.


3.3.8.3 Performance


Masking adds work to every row, and subsetting adds joins. Plan for it as you would for ETL: choose commit sizes, parallelism and index handling, and expect trade-offs. Delphix's guidance includes number of streams, update threads (reduce them if you see database deadlocks), and the option to drop indexes during a job; Informatica allows up to eight workflows at once. A subset reduces volume, which is usually the biggest performance win, so extract less before you optimise anything else. From docs
