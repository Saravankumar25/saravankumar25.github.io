5.1 Informatica: masking data, rules and mapplets

Day 44, Day 54, Day 55, Day 56, TDM_Handson2

The previous chapters showed how to find sensitive columns (the Informatica discovery and profiling chapter) and how to cut production down to a small consistent slice (the Informatica data subset chapter). This section covers the step that makes the slice safe to hand to testers: data masking, replacing real sensitive values with realistic fake ones, so a tester sees "Divya Iyer" where production has "Asha Menon". The general idea is in the masking concepts chapter; here is exactly how Informatica TDM does it.

In the syllabus this is Day 44 (substitution, shuffle, key masking, encryption), Day 54 (masking rules, algorithms, mapplet creation, transformations), Days 55 and 56 (mask first name; alphanumeric text, SSN, telephone number) and the masking half of TDM_Handson2.

5.1.1 Words to know first

Masking technique
The logic that replaces a value, such as "pick a name from a list" (substitution) or "swap values between rows" (shuffle).
Masking parameters
The options of a technique, such as the dictionary to use, the seed, or the range of dates allowed.
Masking rule
A technique plus its parameters, saved under a name. "FirstName_Substitution" is a rule. The same technique with different parameters is a different rule.
Data domain
A named group of columns that mean the same thing (for example "Social Security Number"), found by patterns in the data or in column names. You can attach preferred masking rules to it.
Policy
A bundle of data domains (and so their rules) that you reuse across projects. It holds no data source itself.
Deterministic / repeatable
The same input always gives the same masked output, so "Asha" becomes the same fake name in every table and in every run.
Seed
A starting number that makes repeatable output reproducible. Same seed, same rule, same input, same result.
Dictionary
A flat file or database table of replacement values used by substitution, for example a list of first names.
Mapplet
A reusable group of PowerCenter transformations with input and output ports. TDM can import one as a custom masking rule.
Value cascade / auto cascade
Ways to make related columns receive the same masked value: a value cascade for similar columns you group by hand, an auto cascade for primary and foreign keys.

5.1.2 The big picture: rules, domains, policies and assignments

Four objects and how they connect

Start with the ShopSphere problem. Your CUSTOMERS table has first name, last name, email, phone, SSN, date of birth, zip code and tax ID, all sensitive. You do not want to configure "how to mask an SSN" nine times in nine projects. TDM lets you define it once and reuse it. The guide's building blocks (User Guide 10.5.10, p.71 to 73, p.135 to 138, p.149 to 150) From docs:

RuleA masking technique, an optional rule qualifier and masking parameters. Can have an override option."SSN_Rule" using SSN masking
Data domainThe functional meaning of a column, identified from data patterns and column-name patterns; holds one or more preferred rules, one of them the default."Social Security Number Domain": data pattern for 999-99-9999 and column names matching SSN or SOCIAL
PolicyA collection of data domains. Contains no data source; can be applied to many projects."ShopSphere_PII_Policy"

You can create rules, domains and policies in any order. The guide's high-level policy task flow (p.72): create masking rules, define data domains, assign the rules to the domains, create a policy, assign the domains to the policy. You can apply the rules to source columns, data domains, policies and plans (p.136).

Data domains and preferred rules

A data domain (User Guide 10.5.10, p.73 to 76) From docs "represents the functional meaning of a column based on the column data or the column name". The guide's SSN example: social security numbers may sit in a column called SSN, in another table's SOCIAL_SECURITY and even in a COMMENTS column. You define a data expression for the format (regular expression [0-9]{3}-[0-9]{2}-[0-9]{4}) and metadata expressions for column names such as .*SSN* and .*SOCIAL*. Data discovery profiles (see the Informatica discovery and profiling chapter) use these patterns to assign domains to columns; without Data Discovery you assign columns by hand (p.73). Link back to discovery: profiling finds the sensitive columns, domains carry the rule to them.

When you attach masking rules to a domain they are called preferred rules. If you attach several, one is the default rule, applied to all columns of the domain, and you can change an individual column to another preferred rule (p.73). The guide's example: a Last_Name domain with shuffle as the default and substitution as another preferred rule for a different table.

TDM ships three policy packs, PII, PHI and PCI, each listing domains with a default rule (p.77 to 80). The PII pack, for example, pairs First Name Domain with First Name Rule, Phone Domain with Phone Number Rule and Social Security Number Domain with Social Security Number Rule. The guide does not say which technique each default rule uses, so open a rule in your install to see.

The task flow

A masking plan must contain at least one rule or one policy (User Guide 10.5.10, p.135). The PowerCenter Integration Service does the masking when the workflow runs. If a plan has both subset and masking components, subsetting happens first (p.275), as in the Informatica data subset chapter. Plans are explained in the Informatica plans, workflows and warehouse chapter, and the screens in the Informatica TDM tour.

5.1.3 Creating masking rules

A rule is created in the Policies view, then added to a project, then assigned to columns. The guide recognises three kinds (User Guide 10.5.10, p.136 to 138) From docs:

KindWhat it isColumnsUse it when
StandardA built-in technique with parameters. One masking technique per rule.One input column, one output columnMost cases: mask a name, an SSN, a date
AdvancedA combination of techniques; masks multiple source columns, or one column based on more than one input.Input, variable and output columnsA full name built from masked first and last name; conditional masking; dependent columns
MappletLogic imported from a mapplet exported from PowerCenter or the Model repository.Multiple input and output columnsYou need a PowerCenter masking technique TDM does not offer natively

Creating a standard rule

  1. Click Policies, then Actions > New > Masking Rule.

    The Rule Wizard opens (User Guide 10.5.10, p.139).

  2. Enter a name and optional description. Pick the datatype of the column the rule will be applied to.

    Techniques depend on datatype: you cannot blur a string by a percentage. A rule can be created for string, numeric and date types (p.72).

  3. Select the Standard masking rule type. Tick Override Allowed if users may change parameters when they assign the rule. Click Next.

    Override is described below. The next screen changes depending on the masking technique you select (p.139).

  4. Enter the masking parameters.

    These decide exactly how values are masked: dictionary, seed, range, mask format and so on. Section 5.1.6 lists them per technique.

  5. Enter the exception handling options.

    Decide what to do with nulls, empty spaces and errors (14.5). Click Finish (p.139 to 140).

    The rule appears in the Policies view and can be edited, copied (Actions > Duplicate) or deleted there (p.139, p.146).

Previewing a rule: the Rule Simulator

The guide describes a built-in preview so you do not have to run a full workflow to see what a rule does (User Guide 10.5.10, p.137, p.140) From docs. It works for standard rules only (the text says "simulate the output of a standard rule").

  1. Policies view, click a masking rule name to open its Rule Properties, then click Rule Simulator.

    This opens the simulator tab.

  2. Choose a source in Source Details: Default, My Test Data or Connection, then click Edit.

    Default uses sample data supplied by TDM. My Test Data lets you type rows (up to 100). Connection reads real rows (the Configure Source Details page opens).

  3. If Connection: open the Connection tab, pick connection and owner, Browse to the table, choose the column.

    By default up to 10 random columns are listed; type the column name if yours is missing. Enter the number of rows: default 20, maximum 100. Click OK.

  4. Click Go.

    The Rule Simulator tab lists original values beside masked values.

  5. Adjust the rule and run the simulation again on the same data.

    The latest simulation configuration is stored in the browser cache, and clearing the cache deletes it (p.137).

Override

With Override Allowed ticked, whoever assigns the rule may change its parameters for one column (p.136, p.146): select the column, Actions > Override, edit, Save. The Override column then reads Yes-Overridden. Different overridden seeds on columns that must match will break the match.

Creating a mapplet rule

The wizard path (p.140 to 141): Policies, Actions > New > Masking Rule, name, datatype, Mapplet masking type, browse to the exported XML (for Hadoop, select Hadoop and browse to a Developer tool mapplet), Next, mark at least one input and one output column as mandatory, Finish. Details and limits are in 14.9.

Creating an advanced rule

  1. Policies, Actions > New > Masking Rule. Enter a name and description, choose Advanced, click Next.

    Advanced rules combine techniques (User Guide 10.5.10, p.141).

  2. In Input Columns click Add New. Give the name, datatype, precision and scale. Choose whether assigning it is mandatory in every project.

    You cannot enter masking properties on input columns, because input columns just receive the source value.

  3. In Variable Columns click Add New. For each, enter an expression, a masking rule or a dependent column.

    Variable columns are scratch fields for intermediate results. If you apply a masking rule, say which input column feeds it.

  4. In Output Columns click Add New. Enter an expression, a masking rule or a dependent column.

    The output column receives the final value written to the target.

  5. Click OK and finish.

    The column names in the rule do not have to match source column names; you map them at assignment time (p.156 to 157).

The full parameter tables for advanced rules are in 14.8.

5.1.4 Assigning rules to columns

Add rules to the project first

Rules live in the Policies area; a project only sees them after you add them. Projects, open the project, Overview > Policies, Actions > Add Additional Rules, tick your rules, OK; they appear under Additional Rules (User Guide 10.5.10, p.141 to 142) From docs.

Assigning a standard rule, step by step

  1. Open the project, click Define | Data Masking, select a column.

    Choose the column that needs masking, for example CUSTOMERS.first_name.

  2. If Domain is blank, click the Policy column and pick a policy that contains the rule you want.

    The list of rules comes from the data domain's preferred rules, then the policy's rules (p.142, p.145).

  3. Click inside the Masking Rule column and pick a rule.

    Domain preferred rules are at the top; the rest of the policy's rules are below. For a substitution rule you can set the rule assignment parameters (lookup condition, unique substitution column, see 14.6). For a mapplet or advanced rule you map columns (below).

  4. Click Save for each column.

    If you move to another row without saving, TDM discards the assignment (p.145). This is the most common beginner loss.

  5. If you changed an assignment that other objects use, the Impacted Objects dialog lists plans, columns and domains.

    Click Export for a CSV, Continue to save. Regenerate and rerun the affected plans (p.142).

No rules appear in the list?

No rules listed? Check that a rule exists for the column datatype, that the project has a policy with masking rules, and that the domain's preferred rule is in a policy assigned to the project (p.145). The Integration Service does not mask integers longer than 28 characters (p.145, p.152).

Assigning a mapplet or advanced rule (port mapping)

These rules have named input and output ports, so you map source columns to them (User Guide 10.5.10, p.142 to 143) From docs. Pick the rule in the Masking Rule column; a Custom Rule Assignment or Advanced Rule Assignment dialog opens. Select a source column and a same-datatype rule input port, click Link (or Show Simple), then Next, link rule output ports to source columns, Save. For an expression cascade in an advanced rule, Add Associated Table lets you combine two tables with a join condition. Sybase to Hadoop limits a custom rule to 20 columns (p.143).

Many columns, many rules

  • One rule on many columns: search for similar columns, for example all ID columns, tick them and click Single Rule Assignment. Pick a policy and a masking rule, click OK (p.147 to 148). The guide's figure on p.148 shows this dialog.
  • Clearing: select the column and click Clear Assignment, confirm, and Continue if the Impacted Objects dialog appears (p.148).

Cascades: keeping values consistent between tables

The ShopSphere customer_id is a primary key in CUSTOMERS and a foreign key in ORDERS. If you mask the key but the foreign key keeps its old value, the join breaks. TDM handles this with cascades (User Guide 10.5.10, p.90 to 91) From docs:

  • Auto cascade: masks a primary key in a parent table and the related foreign keys in child tables with the same value. Applied by default to tables with key constraints; can be switched off or on. Needs key constraints between parent and child. Not available for XSD, MongoDB and Cassandra sources.
  • Value cascade: for similar columns not linked by key constraints (the guide's example: employee_num in one table and EmpID in another). Select the columns in Discover | Columns, Actions > Set as similar value columns, and choose a driving column. A rule assigned to the driving column is assigned to all the group. The columns must have the same type. In the masking view the driving column shows the number of other columns in the cascade.
  • Not for computed columns: you cannot apply masking or generation rules to computed columns or build cascades on them (p.90).

Changing or deleting rules after assignment

Editing or deleting a rule shows an Impacted Objects dialog, but changes do not flow into plans: regenerate and rerun them. Deleting a rule does not remove it from the columns, domains and plans using it. If you change a custom rule's field names or types, import the mapplet again (p.144 to 146) From docs. For XSD sources you apply rules to XML elements and attributes in Discover > Files (p.144); shuffle is not allowed for XSD (p.135).

5.1.5 Parameters that most techniques share

Before the techniques, three ideas appear again and again (User Guide 10.5.10, p.153 to 155) From docs.

Repeatable output and the seed

Repeatable output returns deterministic values: the same input gives the same masked value, every time you generate and run the workflow. Use it when the same value occurs in several tables and the target tables must show the same masked value. The guide's example: customer John Smith has account numbers 1234 and 5678 in many tables; masking turns John Smith into Frank Martinez everywhere, 1234 into 6549, 5678 into 3214, on every run.

The seed is the generator's starting point: 1 to 999, default 1 (p.154; the key masking string table says 1,000, p.168, so I use 999). Give the same seed to columns that must match, such as Cust_ID in four tables. You can put the seed in a parameter file variable. A TDM administrator can set a central seed that overrides every other seed (p.155).

Substitution and expression masking keep a storage table of source and masked value pairs; you name the storage connection in the plan (p.286: IDM_SUBSTITUTION_STORAGE, IDM_EXPRESSION_STORAGE), and expression masking fails without it (p.163). Key masking is deterministic from source, rule and seed (p.164). Repeatable means "same in, same out", not "reversible".

Exception handling

Every rule has an Exception Handling section that decides what happens with nulls, blanks and errors (p.155):

Substitution masking

What it does. Replaces a value with a "similar but unrelated" value looked up in a dictionary, a flat file or database table of replacement values (User Guide 10.5.10, p.176 to 177) From docs. Gotchas.

  • Choose Unique Substitution Data only if the dictionary is bigger than the number of distinct values in the column. A dictionary of 4 names cannot uniquely replace 20 customers; the operation fails.
  • Two customers with the same first name get the same replacement only if Repeatable Output is on (the storage table remembers pairs). Without repeatability, each row can get a different value.

Shuffle masking

What it does. Swaps values of one column between rows of the same table. The guide's example (p.173) uses four rows: Tom Bender, Sue Slade, Bob Bold, Eli Jones. After a shuffle of the first-name column they read Bob Bender, Eli Slade, Tom Bold, Sue Jones. You can restrict which values may be swapped by a lookup condition or a constraint. Works on date, numeric and string columns From docs.

Other forms the guide describes.

  • Delimited strings: the guide's example masks "John Donne" consistently when it appears as the strings John and Donne in two columns and as "Donne, John" or "John Donne, General Manager" in two more. Assign delimited string masking with comma and space as delimiters to the last two (p.166 to 167).
  • Dates: output dates fall between 1753 and 2400 and are always valid. A leap year maps to a leap year; a 31-day month to a 31-day month; February stays February (p.167). Give the same seed as another column to get matching dates.
  • Numbers: to keep a primary-key to foreign-key relationship intact between two tables, give the key column in each table the same seed. Deterministic output means 1001 in CUSTOMERS and 1001 in ORDERS both become the same new number (p.167).

Gotchas. Output is not guaranteed unique when there are fewer source characters than result characters (p.165). By default a masked character may differ from the original only in case ("x" to "X"); Case Insensitive treats both cases as one character so it cannot. To get identical output for "John Brown" and "JOHN BROWN", convert to one case first with a preprocessing expression (p.166).

Choosing a technique: questions to ask

  • Does the test environment need this column at all? If not, nullification is the simplest and safest.
  • Does the application check a format (SSN pattern, card checksum, phone layout, URL)? Use the matching built-in technique (SSN, SIN, credit card, phone, email, IP, URL) so the checks pass.
  • Does it need real-looking text such as names and places? Substitution (new values from a dictionary) or shuffle (existing values moved between rows).
  • Is the value an identifier that appears in several tables and must stay joinable? Use key masking with the same seed, or rely on auto cascade for keys with constraints, or repeatable substitution with the same seed (14.4, 14.5).
  • Is it a number or date where only "near the original" matters? Random masking with blurring.
  • Do you need to undo the masking later? Format preserving encryption, knowing the privacy trade-off.
  • Does a masked value depend on more than one column? An advanced rule, or a mapplet if PowerCenter logic already exists.

5.1.9 Custom rules: mapplets and the Data Masking transformation

This is the Day 54 topic "masking rules, algorithms, mapplet creation, using transformations". I will separate three things: what the guide says, what it does not say, and the general idea.

What the guide says From docs

  • Purpose. Mapplet rules let you use PowerCenter masking techniques that are "not available in Test Data Manager" (User Guide 10.5.10, p.150). The mapplet holds the logic to mask the input columns and return data to the target columns (p.137, p.152).
  • How it gets in. You export the mapplet to an XML file from the PowerCenter repository or the Model repository, then import it in Test Data Manager as a rule (p.137, p.140). To mask Hadoop data you import mapplets built in the Developer tool (p.137). The TDM repository then stores the mapplet logic, and you cannot change the mapplet inside Test Data Manager (p.137).
  • What it must contain. One or more Data Masking transformations, and all transformations must be passive (they must not add or remove rows) (p.137, p.150). It can have multiple input and multiple output columns (p.137).
  • Required ports. Mark at least one input and one output column as mandatory; mandatory columns need source and target assignments when you assign the rule (p.137, p.141, p.155).
  • Custom masking parameters (p.156): Column Name, Column Type (input or output), Data Type, Precision, Mandatory, Group Name (input, output or another name you gave in the mapplet).
  • Exporting the other way. You can also export rules as PowerCenter mapplets (p.150).
  • Assignment. Select the rule in the Masking Rule column, then link source input columns to rule input ports and rule output ports to source columns (p.142 to 143). Sybase to Hadoop limit: 20 columns.
  • Hadoop engine limits. A Blaze engine allows Expression, Data Masking, Case Converter, Comparison, Decision, Labeler, Merge, Parser, Weighted Average, Standardizer and Java Passive transformations in a mapplet rule; Spark allows Expression, Data Masking and Java Passive; Hadoop mapplets cannot use sequence generator, lookup or classifier (p.62, p.137).
  • Changes. If you change the name or type of a field of a custom rule, existing assignments do not see it; import the mapplet again (p.144).
  • Data Masking transformation session properties (User Guide chapter 3, p.52 to 53): SSN High Group File path, DMO Cache Directory, Cache Size (default 8 MB), Shared Storage Table (default disabled) and Storage Commit Interval (default 100,000).

What the guide does not say

The guide tells you to export a mapplet containing Data Masking transformations; it does not teach building one in PowerCenter Designer or the Developer tool, and gives no list of the transformation's port properties and no finished example. "Mapplet creation" as a click-by-click task is outside this guide; ask your trainer which PowerCenter material your course uses.

The general idea General concept

General concept (not from the guide). A transformation in PowerCenter is one processing step on rows of data (calculate, look up, mask). A mapplet is a reusable bundle of such steps with input and output ports, like a function you write once and call from many mappings. A Data Masking transformation applies masking techniques to a port. A mapplet rule therefore means "run my own bundle of steps instead of one built-in technique", for example mask phone numbers differently per country.

5.1.12 Common mistakes and gotchas

Watch out for these
  • Forgetting to click Save after each assignment; TDM discards unsaved assignments (User Guide 10.5.10, p.145).
  • Not rerunning plans. Edits to rules, assignments or domains do not change existing plans until you regenerate and run them (p.144 to 148).
  • Different seeds on columns that must match. The same seed gives the same output across columns (p.154, p.167). Different seeds give different values, and joins break.
  • Repeatable substitution or expression masking with no storage table. Expression masking fails; substitution cannot remember pairs (p.163, p.176, p.286).
  • Unique substitution with a short dictionary. The operation fails (p.176).
  • Short mask formats. Trailing characters stay unmasked (p.164).
  • Masking the primary key but not the foreign key. Use auto cascade, value cascade or the same seed (p.90 to 91, p.167).
  • Shuffle on XSD or Spark, expression repeatable on Hadoop, flat-file dictionaries on Hadoop. Documented as unsupported (p.62, p.135, p.163, p.176).
  • Expecting reversibility from the wrong technique. Only format preserving encryption is described as decryptable (p.161).

5.1.13 Recap

Key points
  • A rule is a technique plus parameters. Rules attach to columns directly or through data domains, which a policy groups for reuse. Always preview a standard rule in the Rule Simulator.
  • Three rule kinds: standard (one input, one output), advanced (input, variable, output columns with expressions, conditions and dependent masking) and mapplet (imported PowerCenter logic made of passive transformations including Data Masking transformations).
  • Repeatable output and a seed make masking deterministic. Substitution and expression masking also need a storage table.
  • Substitution gives realistic values from a dictionary; shuffle moves real values between rows; key masking keeps character types deterministically; random masking uses ranges and blurring; encryption can be reversible; nullification empties the column; SSN, SIN, phone, credit card, email, IP and URL are built-in formats.
  • Choose by what the application needs: realism, format validity, joinability across tables, reversibility, or nothing at all.
  • The guide covers importing and assigning mapplet rules but does not teach building the mapplet in PowerCenter.
  • Masking happens after subsetting when both are in one plan.

5.2.1 Words to know first

Data generation
Creating new, realistic but fictional rows by following rules, instead of copying real rows. Also called synthetic data creation.
Generation rule
A saved recipe for one kind of value, for example "ten random digits starting with 6 to 9". It names a technique and sets its parameters.
Assignment
The link between a rule and a target column: "column phone uses rule Phone_10_digits".
Global rule
A named rule created once in the Policies area and reusable in every project. Standard, custom and advanced rules are global.
Ad hoc rule
An unnamed rule created inside one project directly on a column. It cannot be moved to another project.

5.2.2 What data generation is for

  1. Open Policies and choose Actions > New > Generation Rule.

    Creating it in Policies, not inside a project, makes the rule global and reusable.

  2. Enter a name, pick the column's data type, select the standard type and optionally tick Override Allowed.

    The data type decides which techniques the wizard offers, so choose it first.

  3. Click Next, fill in the parameters, set the exception test data options and click Finish.

5.2.4.3 Override: one rule, small variations

If a rule has Override Allowed set, whoever assigns it can change its parameters for that one column without touching the global rule. The guide's example: a rule that makes random dates from 2011 to 2012 with override on; a user assigns it and adds Saturday and Sunday as excluded days, so that column gets weekday dates only (p.193). To do it, select the column in Define | Data Generation, choose Actions > Override, edit the values and Save. The Override column then reads Yes-Overridden (p.196).

5.2.4.4 Custom and advanced rules, in brief

A custom rule imports a PowerCenter mapplet. You must mark at least one input and one output column as required. The guide's use: combine first and last name into a full name, or use PowerCenter transformations such as an SQL or Stored Procedure transformation (User Guide 10.5.10, p.196). An advanced rule has input, variable and output ports and can mix techniques. Both get their own sections in the technique tour.

5.2.5 Default rules: what happens to columns you ignore

Columns without an assigned rule receive the default rule for their data type (User Guide 10.5.10, p.193). The defaults (Numeric, String, Date and Binary, plus separate primary key and unique key defaults for each type) are visible on a project's Overview | Properties tab (pp.193-194).

Keys get their own defaults because a primary key must never repeat or be empty. The administrator configures the initial defaults (p.193), and in the plan's Data Generation Properties you can adjust them again and tick Apply Default Rule to columns without rules (p.285).

Two more shortcuts the guide mentions (pp.194, 205):

  • Default data domain rule. You set this when you create and run a data domain profile (the Informatica discovery and profiling chapter), so discovery can feed generation.
  • Auto rule. After a column profile you review and finalise results. Columns whose Inferred Rule shows Yes can take the Auto Rule, which fills the column from the approved profile results. Do not apply an auto rule to a primary key column, because a primary key cannot contain nulls.
Default rules are not a plan

The guide notes that default rules are not filled in if the rules are not part of the project. If the default boxes in the plan are blank, you must choose the default rules yourself (p.284). Random defaults are fine for a column nobody tests, not for one with business meaning such as email.

5.2.7 Tables, entities, relationships and keys

Real data is not a pile of independent tables. Every ShopSphere order must point to a customer that exists, and every order item to an order that exists. If you generate each table separately with random numbers, the foreign keys will point nowhere and the app will fail for reasons unrelated to what you wanted to test. TDM gives you two tools for this.

5.2.7.1 Entities: generate a parent with its children

An entity defines tables related by physical or logical constraints, and keeps the hierarchy (User Guide 10.5.10, p.277). You can add entities (and plain tables) to a generation plan. You create the entity in the project's Define area, pick a driving table, and TDM finds related tables from the constraints. If your database has no declared foreign keys, add a logical foreign key on the Discover | Tables | Constraints tab, mapping the child column to the parent column (the Informatica subsetting chapter; User Guide 10.5.10, pp.110, 116).

For each relationship in an entity map there are Minimum and Maximum properties: the fewest and most child records to generate for each parent record (p.117). The plan-level Data Generation Properties repeat this as Minimum and Maximum (guide default 1 for each), plus Parent Records Without Children and Child Records Without Parent percentages for self-cyclic tables or reference lookups (p.285). A link between XML elements works the same way. A range set on an individual relationship takes priority over the plan-level ratio (p.207).

5.2.7.2 Reference lookup: borrow values from a table that already exists

The second tool is the reference lookup technique (see Reference Lookup). Instead of making values, it reads them from an existing parent table, so a child column can only receive keys that exist there. The plan then needs a Reference Lookup Connection, a connection to the database that holds the parent tables (User Guide 10.5.10, p.280). Use it for static reference data: ShopSphere's PRODUCTS table is the natural example for ORDER_ITEMS.product_code.

What I could and could not confirm

The guide says entities keep parent-child hierarchy and lets you set child counts per parent. It does not spell out, in the pages I read, exactly how TDM copies the parent key into the child's foreign key column, or whether a reference lookup may read a parent table generated in the same plan rather than one already loaded in the database. After a first run, always check keys with a quick join query (the lab does). Verify in your version

5.2.7.3 Primary keys and unique values

  • A computed column as primary key blocks generation for an entity: you cannot run generation that includes an entity whose primary key column is a computed column (p.191).
  • For multirecord IMS sources imported from PowerCenter, the table sequence is not imported, so you must supply it with the Manage Sequence button on the entity's Entity Map tab (pp.191-192). This is a mainframe case you can skip for ShopSphere.
  • Many techniques have a Generate Unique Values checkbox. It cannot be combined with regular-expression patterns, and cannot be used for binary or flat-file dictionary rules (pp.216, 222-223).
  • For ids, the cleanest choice is the Sequence technique. A sequence never repeats within a run, and "Start Sequence from Last Value" lets a second run continue where the first stopped (p.231).

5.2.8 How many records? And exception data

The number of rows is not part of a rule. It is set in the plan: the field Number of Records to Generate is marked Required for generation plans (User Guide 10.5.10, p.280). In the plan wizard it is step 14: "enter the number of records that you want to generate" (p.305). You can also give criteria per entity on the generation criteria step (p.305).

For a parent-child set, the Minimum and Maximum child settings decide how many children each parent gets, so total rows in the child tables are not a round number. My reading, flagged because the guide gives no worked example of totals: with 50 customers and 1 to 3 orders each, expect between 50 and 150 orders. Confirm with the Row Count report (the plans, workflows and warehouse chapter).

5.2.8.1 Exception test data: nulls and invalid values

Almost every technique ends with the same two settings, Null Values and Invalid Values (User Guide 10.5.10, pp.210-211). Each takes a rule (an existing global rule, or "Default") and a percentage, which may have up to two decimal places.

  • Null Values: the percentage of rows that will contain a null in this column. Cannot be generated for MongoDB sources (p.210).
  • Invalid Values: the percentage of rows that deliberately break the rule, where "invalid" means whatever does not conform to the rule: outside the numeric range, wrong length, not in the dictionary and so on.

The guide's trick: make a rule "Recent_Dates" for 2012 to 2013 and, in its Invalid Values setting, choose a second saved rule "Dates_2005" (2005 to 2010) at 15 percent. Now 85 percent of dates are recent and 15 percent are old (p.210). So "invalid values" is really a way to mix in a second population.

Why would I want bad data?

Good testing needs negative cases. If ShopSphere's checkout rejects a customer with no phone number, you need rows with no phone number. Ten percent nulls in phone and two percent invalid zip_code values give your tests something to reject, without hand-crafting rows.

5.2.9.1 Sequence

From docs A global or ad hoc rule that makes numeric or date values in a sequence. You pick a beginning value and an increment (User Guide 10.5.10, p.230).

When: ids and anything that must be ascending: customer ids, ticket numbers, consecutive dates. The guide's example is a TICKET_NUMBER column with start 1000 and increment 1 (p.231).

Parameters (pp.231-232): numeric rules take Start Value, Increment Value and Start Sequence from Last Value, which makes the next run continue from the previous output (on a string column it restarts from the beginning). Date rules take Start Date and Increment by (a number plus year, month, day, hour, minutes or seconds). Null Values and Invalid Values apply, where invalid means below the start for a positive increment.

ShopSphere: customer_id with start 1001, increment 1 gives 1001, 1002, 1003 and so on. A date sequence for order_date with start 2026-01-01 and increment 1 day gives one order per consecutive day.

Limits: you cannot add a conditional constraint to a sequence column (p.201) or put conditions on a sequence rule (p.234).

5.2.9.2 Random

From docs A global or ad hoc rule that creates random strings, numbers and dates, for things like salary and birth dates (p.220). For strings you give a minimum and maximum length; for numbers a minimum and maximum value; for dates a range. You can instead supply a regular expression (a compact pattern language for text shapes) and say what percentage of rows follow it. If you use several patterns the percentages must total 100.

For strings the usable operators are ., \d, \w, alternation (a|b|c), {n} repeat counts and [ ] sets. To make numbers that contain special characters, use the string technique. To make plain numbers use the numeric technique, which allows \d, alternates like (1|2|3) and [0-9], and alternates cannot be nested (p.223).

Patterns cannot make valid checksummed numbers

For credit card, Social Security and Social Insurance numbers the guide warns that pattern-made values might not be valid, because real numbers follow algorithms that a pattern cannot reproduce (p.224). That is fine for "SSN-like" test data, and it is why the Credit Card technique exists.

Date example: a random date rule from 1950-01-01 to 2005-12-31 for date_of_birth gives values such as 1990-04-12 and 1999-07-23. Set Exclude to Saturday and Sunday and no value falls on a weekend; "invalid" for dates means outside the range or on an excluded day (p.221).

5.2.9.3 Set of Values

From docs You type the values you want and the percentage of rows for each; the percentages must total 100 (decimals allowed). Works for string, numeric and date, and can be global or ad hoc (pp.232-233). Best for columns with a handful of values, such as membership status.

Parameters: Value (one row per value, add rows as needed), Distribution%, and the usual Null Values and Invalid Values. For this technique "invalid" means anything not in the list (p.233).

The guide's example is a PAYMENT_TYPE column with Visa 60, MasterCard 30, Paypal 10. ShopSphere: zip_code with 560001 at 40, 600017 at 35 and 682001 at 25. Of 50 customers, about 20, 17 or 18, and 12 or 13 will get each zip code. Percentages are targets, so expect small rounding differences.

5.2.9.4 Dictionary

From docs Loads values from a dictionary (a flat file or relational table of values) into a column. Good for columns with realistic but finite values: names, states, countries. Before you create the rule, someone with permission must add the dictionary under Administrator | Dictionaries. Works for string, numeric, date and binary data; flat file or relational source; binary only from relational (p.215).

Parameters (p.216): Dictionary Name; Dictionary Column (longer values are truncated to the target size); an optional Dictionary Lookup Column plus Table Column to match rows; Serial Number Columns (relational dictionaries, needed for binary); Generate Unique Values (not for flat-file dictionaries or binary); Null and Invalid Values (invalid means not in the dictionary).

If both lookup and table columns are of double data type the process generates nulls (p.216). The guide's example makes two string rules from one names dictionary: one picks the first-name column, one the last-name column (p.215).

ShopSphere: first_name uses dictionary NAMES column FIRST, last_name uses column LAST. Sample output: Meera, Nair; Ravi, Kumar; Asha, Menon. The dictionary's name and column names here are placeholders I made up. Because the two rules pick independently, "Ravi Menon" is as likely as "Ravi Kumar", which is fine for testing and wrong for anything that needs a believable family name.

5.2.9.5 Credit Card

From docs Creates card numbers by issuing network. Output is a string (not numeric, date or binary), and numbers must pass verification using Luhn's algorithm, the check-digit formula real cards follow (pp.226-227). Formatted output looks like XXXX-XXXX-XXXX-XXXX.

Parameters (pp.227-228): Issuing Network (required: American Express, Discover, JCB, Mastercard or Visa); an optional Issuer Identification Number of up to six starting digits (a value invalid for the network makes the workflow fail; blank lets TDM use valid ones); Distribution % (must total 100); Generate Formatted Values; Generate Unique Values; Null and Invalid Values. Valid starting digits include Visa 4, Mastercard 51 to 55 and American Express 34 and 37.

ShopSphere: the four tables hold no card numbers, so imagine a later PAYMENTS.card_no column. A rule with Visa at 60 percent and Mastercard at 40 percent, formatted, gives values shaped like 4666-1760-3137-2159 and 5122-3307-9244-0268. I computed those two to pass the Luhn check, but TDM would produce its own digits.

5.2.9.6 Reference Lookup

From docs An ad hoc rule that takes column values from an existing table, for string, numeric and date columns. You name the parent table and map parent columns to child columns. The same rule can fill several child columns from the same parent table (p.229). The guide's example: use the same customer ids that exist in another table.

Parameters (p.230): Minimum (default 1) and Maximum (default 3) child records per parent; Data Source (connection to the parent table); Parent Table; pairs of Child Column and Parent Column; a Parent Table Filter; the percent of parent records without children and of child records without a parent (if that is 0 you must give a Default Value to write instead of nulls).

ShopSphere: ORDERS.customer_id reads CUSTOMERS.customer_id with minimum 1 and maximum 3, so each existing customer gets one to three orders. Set "Parent records without children" to 10 and about one customer in ten has no orders, a useful edge case. Remember the plan needs a Reference Lookup Connection (p.280), and see the note on reference lookup about where the parent rows must already live.

Reference lookup is not for XML targets

You cannot use reference lookup or effective dates rules for an XSD (XML) source (p.206).

5.2.9.7 Expression

From docs An ad hoc rule that computes a value from an expression you build in the Expression Builder, choosing columns and functions from lists. Works for string, numeric and date (p.219). Parameters: Expression, Null Values, Invalid Values (invalid = does not follow the expression) (p.220). If you tick "Override Data Type to Numeric" on a string column, you cannot enter a numeric expression (p.219).

The guide's example builds a Name column from FirstName and LastName with CONCAT (FirstName+'/'+LastName). ShopSphere: imagine a display_name column built as CONCAT(CONCAT(first_name,' '),last_name), giving "Asha Menon". I mirrored the nested CONCAT style the guide uses in its advanced example; check the exact function list in your Expression Builder.

When: any column that is a function of other columns in the same row. The dependent column must still be assignable after its inputs, so assign rules to the inputs too.

5.2.9.8 Conditional

From docs An ad hoc rule with one or more rows of "if this condition, then use this generation rule". Conditions are applied in the order listed (reorder with the up and down arrows). Works for string, numeric and date, but you cannot apply conditions to effective dates or sequence rules (p.234).

The guide's example: DEPT_ID 11 gets a 5 percent hike, 22 gets 10, 33 gets 15. The column that the condition reads (DEPT_ID) must itself have a rule, and TDM generates it first, then the dependent column (p.234).

ShopSphere (hypothetical city column): if zip_code = '560001' then city is "Bengaluru", if '600017' then "Chennai", if '682001' then "Kochi". Each "then" is a one-value Set of Values rule. The guide does not describe a catch-all "else" row, so make sure every possible input value has a condition. Check how unmatched rows behave

5.2.9.9 Effective Dates

From docs An ad hoc date rule that fills two related columns, an effective start date and an effective end date, so that periods follow one another without overlap. It makes a random start in a range, an end after it, and the next start right after that end. A grouping column decides how many dates are in each sequence: the number of rows sharing the same grouping value (pp.217-218).

You create the rule on either the start or the end column and name the other. Parameters: Start Date/Time, End Date/Time, Exclude (up to two different weekdays), Effective Start Date column, Effective End Date column, Grouping Column, Invalid Values (percent of rows breaking the sequence; the rule is fixed to Default) (pp.218-219).

ShopSphere: a hypothetical CUSTOMER_ADDRESS_HISTORY table with grouping column customer_id gives each customer a chain of addresses with no gaps. Good for testing "address on the order date" logic.

5.2.9.10 Advanced

From docs A combination of techniques that fills one or several target columns from one or more input, variable and output ports (pp.199, 212). Use it when one column needs two techniques, or the value depends on other columns. You can generate string, numeric and date data.

An input port (optional) takes a target column or a parameter. A variable port holds intermediate values and uses either Conditional or Generation Rule Set (rules with distribution percentages, optionally grouping records by foreign key). An output port receives the data and needs an Expression built from the inputs and variables. Port names need not match column names; you map them when you assign the rule (pp.199, 214-215).

5.2.9.11 Custom

From docs A global rule built from a PowerCenter mapplet. You import it, and mark at least one input and one output column as required. Works for string, numeric and date (pp.196, 211). Use it when you need PowerCenter transformations (SQL, Stored Procedure) or logic that the built-in techniques cannot express.

You map your table columns to the mapplet's input ports and its output ports to target columns (p.204).

ShopSphere: a mapplet that takes first and last name and returns "Asha Menon" for a display_name column. Building mapplets is covered in the Informatica masking chapter.

5.2.10 Conditional constraints: rules between columns

Techniques fill one column at a time. A conditional constraint is a table-level rule that restricts what may appear in a column based on another column. It becomes part of the target table's metadata (User Guide 10.5.10, p.201).

The guide's example: a flight table with From_City and To_City both filled by the same dictionary rule, plus the constraint To_City != From_City so no ticket flies from a city to itself (p.202). A ShopSphere analogue with hypothetical columns: delivery_date > order_date.

To create one, open Discover > Tables, click the table, open the Constraints tab, choose Create New Constraint, set the type to Conditional and build the expression in the Expression Builder (pp.110-111).

Where the constraint cannot be used: numeric sequence, date sequence and random data patterns (p.201). On XSD sources you cannot constrain an element that allows more than one child per parent (p.201).

When the rule and the constraint disagree, the rule wins

The guide's example: both Created_Date and Modified_Date use a random date rule ending 31 July 2014, with the constraint Modified_Date > Created_Date. When Created_Date is 31 July 2014 no later date is allowed, so TDM writes a date within the rule's range anyway and generates warning messages (p.202). The constraint was broken, quietly. Read the warnings in the Monitor logs (the plans, workflows and warehouse chapter) and loosen the rule's range, not just the constraint.

5.2.13 Why a generation plan stands alone

The guide is firm: when you add data generation components to a plan, you cannot add data masking or data subset components, and the reverse holds too (User Guide 10.5.10, pp.274-276, 305). It repeats the rule in the plan overview, the task list, the component table and the creation steps. A Hadoop plan likewise cannot do subset or generation (p.306).

The guide states the restriction but does not explain it. My explanation, as a concept and not a quote: masking and subsetting both read existing rows from a source, then change or filter them. Generation has no source rows; it builds new rows from rules. A plan that tried to do both would have to decide what the masking rule should act on. Keeping them apart avoids that.

One plan: subset and masking

Source connection to target connection. The guide says you can combine them in one plan, or keep separate plans (p.304). If both are present, subset runs first and masking applies only to the subset rows (p.275).

Another plan: generation

Only entities, tables or XSD files with generation rule assignments. Number of records to generate. No source data is masked or subsetted in this plan.

What to do when you need both. Use two plans:

  • Masked copy of old customers plus brand-new ones: run a masking plan into the test database, then a generation plan into the same schema. Make the generation sequences start above the existing ids, or continue with "Start Sequence from Last Value", so keys do not collide.
  • Generate once, then make small slices: send the generation plan to the test data warehouse, then create a related data set, a subset of that data set built from an entity or group (pp.248-251). That is subsetting generated data without breaking the rule.
Why it matters

This restriction is a favourite interview and review question, and it shapes how you design a data pipeline: generation is its own track, not a masking option.

5.2.14 Common mistakes and gotchas

Things that go wrong
  • Forgetting to Save each assignment. The earlier assignment is discarded (p.203).
  • Editing a rule and expecting a finished plan to change. Regenerate and rerun the plan (pp.195-196).
  • Combining masking or subset components with generation components in one plan. Not allowed (pp.274-275). Use two plans.
  • Using a pattern and "Generate Unique Values" together. The guide says uniqueness is unavailable with a regular expression (pp.222-223). Use sequences for keys.
  • Re-running into a table that already has ids from 1001. Key collisions. Truncate the target, or continue the sequence from its last value (p.231).
  • Believing pattern-made SSNs or card numbers are valid. They might not be (p.224). Use the Credit Card technique when validity matters.
  • Ignoring warnings. A rule that conflicts with a conditional constraint wins quietly and only logs a warning (p.202).

5.2.15 Recap

Recap
  • Generation builds new rows from rules and never reads production data. It is set up in a project, run from a plan, and executed as a generated workflow.
  • Rules come as standard, custom, advanced (global) and ad hoc (per project). Unassigned columns get the default rule for their data type.
  • The eleven techniques are Sequence, Random, Set of Values, Dictionary, Credit Card, Reference Lookup, Expression, Conditional, Effective Dates, Advanced and Custom. Reference Lookup, Expression, Effective Dates and Conditional are ad hoc.
  • Null and invalid values are mixed in by percentage through the Exception Test Data settings.
  • Entities with minimum and maximum child counts, and reference lookups, keep parent-child keys consistent. Always verify keys with a join.
  • The number of records is a plan setting. A generation plan cannot contain masking or subset components.
  • Conditional constraints restrict one column using another, but a conflicting rule wins and only produces a warning.

5.3.5 Plan components in practice

5.3.5.1 Masking and subset components

Masking components are policies and rules. You may restrict a run to some of them, and turn masking on or off per column in the plan criteria. 5.3.15 The Test Data Warehouse

Test data goes stale and gets damaged. A tester deletes orders to check a refund flow; a batch job rewrites prices; another team starts testing on the same tables. Re-running the whole subset and masking plan each time is slow. The Test Data Warehouse solves this: it is a central location that stores multiple versions of test data, and multiple Test Data Manager services can use the same warehouse, so teams share one store (User Guide 10.5.10, p.236).

The guide's scenario: before any tests, store the original data as a data set. After each team finishes, store the modified data as another version. To return the environment to its original state, restore the version holding the original data. You can restore any version (p.237).

5.3.15.1 What is behind it

You create a Test Data Warehouse Service in the Informatica Administrator tool. That application service manages two relational databases (pp.26-28, 236):

  • the test data warehouse repository, which holds project metadata (plan information, version, tags) and source table metadata of each data set;
  • the test data warehouse itself, which holds the actual source data you put in data sets.

The service copies the metadata created when you make a data set and creates the data set tables in the warehouse (p.27). Workflows that store data in the warehouse need connections to the external source databases, the repository and the warehouse (p.28). Data coverage tasks run on the Data Integration Service (p.26).

A plain database backup

Restores a whole database, usually needs a DBA, and carries no test metadata. Hard for a tester to find "the data from the refund tests".

A warehouse data set (concept view)

Holds chosen tables, with application name, version and tags you can search. Testers with Execute permission can reset it, or pick it up from the portal. The analogy to a backup stops here: a data set can also be edited and sliced into related data sets.

5.3.17 Restoring: the reset

Reset moves data from a data set version in the warehouse to a target, so a test environment goes back to a known state (User Guide 10.5.10, p.240). You can make the reset delete everything in the target and replace it, which suits tables you do not share. Or you can keep other testers' data in the target and replace only the part that overlaps the data set. In selective resets TDM runs an SQL script that backs up the deleted data in the target (p.241).

5.3.17.3 Speed versus downtime

Disabling constraints lets TDM load several tables in parallel, so resets finish sooner. But constraints are disabled for the entire table, and while they are off, other testers' tests that use those tables might fail. If tables are shared, a slower reset may be better than downtime; if no one else is using them, disable constraints (pp.242-243). As good practice, create an index on foreign keys in the target so child-record deletes are quick (p.243).

5.3.17.4 Failure and special cases

  • Failed reset: if recovery was enabled, backups are kept. Restore with a separate plan: put the backed-up tables in a group, add it as a subset component, use the backup schema as source and the real database as target, disable constraints and indexes, set Treat Source Row As Update and Update As "Update else Insert", and put the backup prefix in the Reset Recovery Prefix advanced field (p.247). On success TDM deletes the backup tables (p.246).
  • Empty strings in non-null columns: a reset fails if it must copy empty strings into a non-null column, for example from an Oracle warehouse to SQL Server. The project can supply default values, but a reset fails if the non-null target columns are unique (p.243).
  • PWX NRDB Batch target: you must delete the target files yourself first; the reset only copies (p.243).

Owner and domain administrator can grant Read (view, monitor, create coverage tasks, run related data set plans), Write (create, edit metadata and data, classify, delete, create related plans) and Execute (reset). Users also need matching privileges such as View Data Set or Reset Data Set (pp.252-253).
  • Lock and unlock. Owner and administrator can lock a data set so nobody edits or resets it, for example while you check it first. The owner and administrator can still reset it (p.254).
  • View and edit data. From the Tables tab you can browse, or run SQL in the SQL Query field and edit the grid, add or delete rows and add row-level tags. DML only, no DDL. Restrictions: no aggregates, GROUP BY or joins in SELECT; no table aliases or owner names; dates in WHERE need TO_DATE; Oracle BLOB and RAW data cannot be viewed or edited (pp.255-258).
  • Related data sets. A related data set is a subset of a data set, cut by an entity or group built inside the data set and run in a plan. A lineage window shows parent and child data sets (pp.248-252). ShopSphere use: a hotfix needs only the Kochi customers.
  • Self-service portal. Publish a data set as a data pack. Testers without Test Data Manager can then view and restore the data. You cannot delete a published data set until you delete the data pack (pp.239, 247-248).
  • Delete. From the Data Sets view, delete whole data sets or single versions, Actions > Delete. Data and metadata are removed (p.248).

5.3.20 Common mistakes and gotchas

Things that go wrong
  • Changing a plan and expecting the old workflow to follow. Generate and run again (p.275).
  • Mixing generation with masking or subset in one plan. Not allowed (p.274).
  • Forgetting the eight-workflow limit. Extra workflows queue (p.276).
  • Criteria parameters silently missing. They are not in the run list by default; add them with Select Parameter or the workflow ignores them (p.311).
  • Leaving tables unclassified before a reset. They are treated as transactional (p.241).
  • Truncating a shared schema on reset. You delete other testers' data (p.244).
  • Disabling constraints on shared tables. Other tests may fail during the window (p.243).

5.3.21 Recap

Recap
  • A plan defines a masking, subset or generation operation; TDM generates a workflow (an ETL job) from it and the PowerCenter Integration Service runs it.
  • Subset plus masking can share a plan (subset first); generation cannot share a plan with either.
  • Connections, target options, update strategy, error and recovery and parameter files control where and how the run happens, with overrides per source or table.
  • Monitor shows each job's status (In Queue, Running, Success, Error, Terminated), its logs by severity, and sessions with row counts. Start at the first Error.
  • Reports: Audit Trail, Data Masking, Plan Audit, Plan Detail and Row Count.
  • The Test Data Warehouse stores versioned data sets. Reset restores a version, with master and transactional classification deciding what is deleted or upserted.
  • Data coverage analysis finds gaps in a data set; ilmcmd, tdwcmd and tdwquery script and inspect the same objects.
