Informatica TDM: what it is and how it is built

Part I (the start-here chapter through the ETL and TDM chapter) explained why test teams need safe, small, realistic data and which techniques produce it. From here on we look at tools. This section opens Part II with Informatica Test Data Management, usually shortened to TDM. Before you click anything in it, you need a mental map: what the product is for, which pieces run behind the web page, where each kind of information is stored, and what order of work the product expects.

That map matters because almost every error message and permission problem you meet later is really a "this piece cannot reach that piece" problem. If you know the pieces, you can guess where to look. The next chapter, A guided tour of Test Data Manager, walks through the screens. The Informatica discovery and profiling chapter goes deep on discovery and profiling.

4.1 Words to know first

Test Data Manager (TDM)
The web page you work in. The same name is also used for the whole product, which is confusing. In this guide, "Test Data Manager" with spaces means the web client, and "TDM" means the whole product.
Policy
A named bundle that says "these kinds of data must be protected, and this is how". It holds data domains and holds no actual data.
Data domain
A group of columns that mean the same thing, for example "all columns that hold a Social Security number", found by looking at column names or at the values.
Project
The workspace for one job: it holds your imported source tables, profiles, masking assignments, subset definitions and plans.
Plan
The final recipe: which tables, which rules, from which connection to which connection. You turn a plan into a workflow and run it.
Workflow
The runnable job that actually copies and changes data. TDM generates it from a plan, and a PowerCenter service runs it.
Application service
A background program in the Informatica installation that does one job, such as running profiles or running workflows. You never see it on the Test Data Manager screens, but TDM calls it.
Repository
A relational database where Informatica keeps its own working information (definitions, metadata, results). It is not your business data.
Metadata
Data about data: table names, column names, data types, keys. Importing "metadata" copies this description, not the rows.
Informatica domain
The family of Informatica services installed together and managed as one unit, with a shared set of users.

4.2 What Informatica TDM is for

Start with ShopSphere's problem. The online retailer has a production database, SHOPSPHERE_PROD, with real customers. Testers need data that behaves like it, but real names, phone numbers and SSNs must never reach the test lab. Copying the whole database is slow and risky. Writing test rows by hand is slow and unrealistic.

The guide describes TDM as a product that works with PowerCenter, PowerExchange and other Informatica applications to manage nonproduction data (anything that is not the live system: test, development, training) (User Guide 10.5.10, p.21). With it an organisation can make a smaller copy of production data, mask the sensitive parts, find the sensitive columns in the first place, or build test data that never touched production. It can also store test data in a central place and reset it later.

And users have roles and privileges (rules about who may do what) that an administrator manages in the Informatica Administrator, so two people can log in to the same Test Data Manager and see different things.

Other items in the guide's overview, which we only name here: exporting flat-file results to an HP ALM test-management server, and masking or moving data on Hadoop clusters (User Guide 10.5.10, pp.22-23). They are real features of the 10.5.10 guide but not part of the ShopSphere path in this book.

Why it matters

The guide's own motivation (p.21) is blunt: organisations guard production tightly but protect test copies far less. TDM exists to close that gap without making developers rewrite code to create test data. When someone asks you "what does TDM do?", the short honest answer is: find the sensitive data, shrink the data, mask it, or generate it instead, and keep versions of the result.

4.3 Use cases: performance, security, and verified data

The guide groups what TDM is used for into three families (User Guide 10.5.10, pp.23-24). Seeing them as three goals helps you choose the right feature later.

4.3.1 Performance in testing environments

Here "performance" means the testing team's speed and agility, not database speed. The guide lists these ways TDM helps (p.23):

  • Subsets keep primary and foreign key relations, so the smaller data is still referentially intact (every child row still finds its parent row).
  • Flat file results can be copied straight to an integrated test tool.
  • Generated data serves teams who are not allowed to see production at all.
  • The test data warehouse keeps several versions of test data in one shared place, and teams on different machines that host a Test Data Manager Service in one domain can share it.
  • Data sets can be edited, with row-level tags to track changes, and restored to return a test system to an earlier state.
ShopSphere example

The Customer Orders team runs a "refund" test that deletes orders. After the run, the test environment is in a strange state. Without TDM, someone re-copies the database (hours). With a stored data set, a tester resets the environment to "masked set v1" from the Data Sets view. This restore idea is the guide's "restore a data set version" use case. The refund story is ours, not the guide's.

4.3.2 Security and compliance

The guide frames the challenge as finding sensitive information in huge volumes of production data and making sure it does not appear in test data (p.24). Its three suggestions:

  1. Run profiles to find sensitive columns, comparing against PII, PCI or PHI regulation standards. (Those three names are explained in the sensitive data and regulations chapter.)
  2. Run a data masking operation to remove sensitive values, with standard formats (such as credit card or Social Security numbers) or custom formats.
  3. Store results in the test data warehouse so fewer uncontrolled copies exist.

4.3.3 Verified test data with Data Validation Option

Data Validation Option (DVO) is a separate Informatica solution used with PowerCenter to check that target data is accurate and that the transformation did not introduce errors (p.24). Used with TDM, it can compare production and development data. The guide's example is a team that must send compliance reports for test data made from production, and needs "verifiable proof" that the test data holds no sensitive values.

The documentation excerpt I used mentions DVO only at this level. It does not describe how DVO is configured, so this book does not either. If your project uses it, ask your trainer or read the DVO guide.

Goal: performance

"Give testers the right data quickly, and let them get it back."

Features: subset, flat-file copy to test tool, data generation, test data warehouse, restore.

Goal: security and compliance

"Prove sensitive data is not in the test lab."

Features: profiles with PII, PCI, PHI domains, masking, a single controlled warehouse, DVO for proof.

4.4 The architecture: what runs behind the web page

The guide says TDM consists of tools, the Test Data Manager Service and other application services, and databases (User Guide 10.5.10, p.25). A useful picture is a restaurant. Tools are the dining room and the order pad (where people ask). Services are the kitchen stations (grill, pastry, dishwashing), each doing one job. Databases are the pantry and the recipe books. The analogy breaks down in one place: here the "waiter" (the TDM Server) also keeps the plans and definitions in its own book (the TDM repository).

One sentence in the guide: the TDM Server is the interface between Test Data Manager and the application services (p.27). I treat them as the same hub, and you should read "TDM Server" as "the part that takes your click and calls the right service". That is my reading, so check it with your administrator.

4.4.5 TDM connections

TDM needs connections to databases, repositories and services, and what it needs depends on what you run (User Guide 10.5.10, p.28):

  • Discovery needs a database source connection and a Data Integration Service.
  • Subset and masking workflows need connections to services, the TDM repository, external database sources, and Informatica sources and targets.
  • Workflows that store data in the test data warehouse need external database sources, the test data warehouse repository and the test data warehouse itself.
  • To copy flat file results to a test tool, you first integrate the test tool server with TDM.

The guide splits them into service, repository and database connections. The table below keeps its meaning and shortens the words.

Connection kindExamples and purpose (pp.29-30)

Repository connectionsTDM repository (a masking, generation or subset workflow needs it); Model repository; profiling warehouse (the Data Integration Service loads profile results there); PowerCenter repository; test data warehouse repository and test data warehouse.

You pick them when creating a plan; TDM tests them when it generates the workflow, and the Integration Service uses them when it runs it.

4.5 The TDM process, end to end

4.5.1 Create a data masking policy

A policy contains data domains that describe what you want to mask. It has no data source, so one policy can serve many projects (p.31). A data domain groups sensitive fields by column name or by the data inside, using patterns written as regular expressions (a compact way to describe text shapes; the guided tour of Test Data Manager has a short primer). A domain also holds masking rules. A rule is a built-in masking technique plus specific settings; rules can also be built from imported mapplets.

ShopSphere: a policy named for customer personal data, with domains for SSN, email, phone, first name and last name. (the policy name and domain list are ours).

4.5.2 Create a project and import metadata

A project organises everything for discovery, masking, subset and generation. You import metadata for the sources you want to subset or mask, and target metadata if you want to generate data. You can import from a PowerCenter folder, from the Model repository, or from an external database. You also create a target schema, and the guide warns that TDM overwrites any data that already exists in the target schema (p.31).

Target schema warning

Point your plan at a schema made for test data. "TDM overwrites data that already exists in the target schema" is the guide's own wording (p.31). Never aim a target connection at SHOPSPHERE_PROD.

4.5.3 Discover source information

Profiles can discover three things (pp.31-32):

  • Primary keys, when a source has none. A primary key profile suggests candidates.
  • Entities (related tables), when the project has several sources. An entity profile suggests possible relationships between tables. You select entities from the results to shape the subset.
  • Data domains. A data domain profile searches columns that fit each domain, so you can mask all of them with the same rules.

Running a profile makes the TDM Server ask the Data Integration Service to extract source data, and the results go to the profiling warehouse. Constraints you add are stored in the TDM repository. The TDM server does not update the data sources (p.32). All of this is the subject of the Informatica discovery and profiling chapter.

4.5.4 Define data masking and data subset operations

For subset, you define which tables to include and how they relate (p.32). Three building blocks appear:

BlockMeaning in the guideShopSphere reading
EntityA set of tables related by physical or logical constraints.CUSTOMERS with its ORDERS and ORDER_ITEMS.
GroupA set of unrelated tables.PRODUCTS, copied whole as reference data (our design choice).
TemplateOptional container holding entities and groups."Customer Orders subset kit".

You also assign masking rules to source columns, create a subset plan from entities, groups and templates (with optional filters on parent-table columns), and create a masking plan that carries the policies and rules. Rules outside policies are allowed too. TDM stores projects, entities, groups, templates and plans in the TDM repository (p.32). The Informatica data subset chapter and 14 teach these in detail.

4.5.5 Define a data generation operation

Three tasks (p.32): create the entities for the plan, create generation rules and assign them to target-table columns, then create a generation plan with entities and tables, assigning default generation rules to columns that have none. The Informatica data generation chapter covers it.

4.5.6 Create plans

A plan holds what a workflow needs. Two rules matter for planning (pp.32-33):

  • A masking operation and a subset operation can share one plan or have separate plans.
  • A data generation operation cannot be combined with masking or subset in the same plan. It needs its own plan.

In either plan you can choose the test data warehouse as a target connection to save the result as a data set, and you can enter test tool integration properties to copy flat file results to an integrated HP ALM server. A generation plan also asks for the number of records. Then you generate the workflow and run it. The Informatica plans, workflows and warehouse chapter covers plans and the warehouse.

4.5.7 Monitor the workflow

Each workflow appears as a job in the Monitor view, together with jobs such as metadata imports and profiling (p.33). You can run the Row Count Report on a successfully run workflow to see how many rows the plan affected, and open the TDM job log to troubleshoot. In ShopSphere terms: after the masking run, the compliance officer checks that the row counts in the test target match the intended subset, and the QA lead opens the job log if the workflow failed.

4.7 Advanced parameterization at a glance

Here is a problem you will meet within a week of working on a real project. ShopSphere's QA team needs test data for sprint 14 regression (orders from this month, in schema QA1), then for performance tests (orders from last year, in schema PERF, on a different server). Making a new plan for each request is slow. Editing one plan every time is error-prone.

The guide's answer is parameters: placeholders in the plan that point to a value, and the value is read when the workflow runs (User Guide 10.5.10, pp.35, 51). You change the value and run the same plan again to get different test data.

You must import source metadata from every source connection you might need into the project. A workflow whose parameter value points at metadata the project does not contain cannot run (p.35).

4.7.2 The sequence in the guide

The guide lists 16 tasks. Grouped into five phases they read like this (pp.35-36):

  1. Prepare the project.

    Create a project and import the required source metadata. Create connection, owner and criteria parameters in it with default values, and choose whether the default may be overridden. Optionally import global parameters.

  2. Use parameters in the entity.

    Create an entity with the required tables and add filter criteria that use parameters. You can add several criteria; they can be project or global parameters.

  3. Use parameters in the plan.

    Create a plan using parameters. On the Plan Settings page, add the source and target connection types as variables and choose the connection parameters. You must enter a parameter file name and the path to that file on the machine that hosts the PowerCenter Integration Service. In Advanced Settings, add schema owners as variables and select the owner parameters. Save the plan.

  4. Optional: use a parameter file.

    From the plan's Properties tab, Actions > Create Parameter File downloads a file listing every parameter in the plan. You may edit values, and set the "ignore" flags of criteria parameters to "Y" to leave them out of a run.

  5. Run.

    From the plan Properties page, Actions > Generate and Execute, then pick how values are supplied. Choose Default (the file entered in Plan Settings), Use Parameter File (a different file), or Add Parameter Values (edit values in Test Data Manager, and use the Select Parameter button to include criteria parameters). Click Generate and Execute and monitor the workflow.

What you should see: the same plan, different data each time you change values. The guide's two examples: change owner and criteria values to get data in the same connection but a different schema, or change connection parameters and include different criteria to get data between different connections (p.36).

4.8 Common mistakes and gotchas

Watch out
  • Looking for business data in the TDM repository. The repositories hold definitions, metadata, results and stored data sets. Your source and target databases are separate and need their own connections.
  • Treating "the TDM Server", "Test Data Manager" and "TDM" as three products. They are the web client, the go-between, and the product name respectively. When a document is ambiguous, ask which piece is meant.
  • Planning generation and masking in one plan. The guide says a generation operation needs its own plan (p.33).
  • Forgetting the overwrite. TDM overwrites existing data in the target schema (p.31). Use a dedicated test schema.
  • Skipping discovery on a database with no declared keys. The guide's example had none, so profiles created the logical keys the subset needed (p.34).
  • Importing only one connection's metadata, then parameterizing the connection. The workflow cannot run (p.35).
  • Assuming every feature in the guide exists in your installation. Licences, privileges and version differ. Confirm in your version.

4.9 Recap

Key points
  • Informatica TDM finds sensitive data, makes smaller copies, masks, generates data, and stores versions of test data (User Guide 10.5.10, pp.21-22).
  • Use cases fall into performance, security and compliance, and verified data with DVO.
  • Four tools (Test Data Manager, Developer, Administrator, PowerCenter Client), a TDM Server, about ten application services, and seven databases make up the architecture.
  • Your business databases need connections; they are not TDM's repositories.
  • The process is: policy, project and import, optional discovery, define, plan, generate and run, monitor.
  • Generation needs its own plan; masking and subset can share one.
  • Parameters (connection, owner, criteria) let one plan produce different test data.

4.18.4 Project logs

PowerCenter writes workflow and session logs when you run a plan from a project. Unless you set locations, it uses defaults from the PowerCenter Integration Service: $PMWorkflowLogDir\, $PMSessionLogDir\ and $PMBadFileDir\ (reject files hold rows that could not be written) (p.52). You can set them in the Edit Project dialog but not when creating the project: open the project, Actions > Edit, Default Log File tab, fill in the three directories with a trailing slash, Save (p.59). 4.18.5 Data masking transformation session properties

You can tune run-time properties of the masking session (pp.52-53). The guide ties better performance to a bigger Cache Size (the dictionary cache in memory; default 8 MB, at least 32 MB recommended for 100,000 records) and a bigger Storage Commit Interval (rows committed per batch to the storage table; default 100,000). 4.20 Data sources

A project cannot do anything until it knows what tables it is working on. To do subset, masking or discovery, you import source metadata into the TDM repository. To generate data, you import target metadata instead (User Guide 10.5.10, p.60). A project can hold more than one type of source, for example a flat file and a relational database, and you can create constraints that relate them and add filter criteria for subset and masking.

A numeric precision limit

If a numeric column has a precision above 28, you cannot apply a masking or subset condition to it. The Integration Service passes that row and column to the target without applying the condition (p.60). Check unusual numeric columns before you trust a run.

4.20.1 TDM source definitions

You can import source metadata from PowerCenter, from the Model repository, or directly from the source database (p.60). The guide's points:

  • The TDM project and the repository folders share the same name, so workflow information goes to the correct folder.
  • If the source is relational and has many tables, importing straight from the database is faster than going through PowerCenter or the Model repository.
  • Importing from the PowerCenter or Model repository brings in the definitions Informatica services support, by importing the repository folder that holds them; TDM makes a copy of that folder in the TDM repository.
  • MongoDB sources imported into PowerCenter need unique column names of at most 80 characters.
  • Flat files must come from the PowerCenter or Model repository; you cannot create flat file connections in Test Data Manager.
  • rowid is a reserved keyword. You cannot import Oracle sources that use it as a column or table name.

  • On Sybase, you cannot move data from a source DBO schema to a target non-DBO schema if the data has an identity column and indexes.
  • If auto identity is enabled in Sybase and a table has no primary or unique keys, Sybase adds a SYB_IDENTITY_COL column. Mark it Restricted (restricted means the Integration Service does not write the value to the target), or the workflow fails.
  • To disable an identity column on Microsoft SQL Server, the database user needs execute permission on sp_help.

If the table is part of profile results, a warning appears and it is removed from them too. If it is part of an entity, group, masking plan or generation plan, the Impacted Objects dialog lists what will be affected; a table in a template that is part of a plan does not list the template and plan. You delete one table at a time.

4.22 Policies

A policy is a data masking component that describes how to protect specific types of source data (User Guide 10.5.10, p.71). It is built from three smaller things that you can create separately, in any order:

Ruleone masking (or generation) technique with specific settings
→

→
Policya set of data domains
→
Projectyou assign the policy to a data source

The ShopSphere reading: a rule is "replace first names from a dictionary of fake names". A domain is "First Name", the group of every column that holds first names. The policy is the compliance officer's list of domains that must be masked in any customer-data project. Once the policy exists, the Customer Orders project simply receives it and every first-name column gets the first-name rule. You can apply one policy to many projects (p.71).

Policies task flow (p.72): create masking rules, define data domains that describe which columns can receive the same rules, assign the rules to the domains, create a policy, assign the domains to the policy. The order is flexible; you can create a policy first and fill it later.

4.22.1 Rules

A rule defines logic to mask sensitive data or to generate test data (p.72). You can create rules for string, numeric and date data types. You can add rules to data domains and then use the domains in policies and plans. After you add rules to a project, you still assign them to columns, matching the column's data type. The built-in masking techniques (substitution, shuffle, key masking and so on) are the subject of the Informatica masking chapter; generation rules are in the Informatica data generation chapter.

4.22.2 Data domains

A data domain represents the functional meaning of a column, based on its data or its name. Assign a masking rule to the domain and all columns in that domain are masked with the same rule. You can also give it generation rules so generated data follows the same logic (p.73). The guide says to assign at least one masking rule to each domain.

The guide's Social Security example: the number might be in a column called SSN, in a column called SOCIAL_SECURITY in another table, or buried in a COMMENTS column. One domain describes all three: a data expression for the format 999-99-9999 and metadata expressions for the likely column names such as SSN or Social (p.73).

If you do not have Data Discovery, you can still use domains to group data, but you must associate columns with domains manually (p.73). With discovery, a profile does the assignment for you (the discovery and profiling chapter).

Preferred rules and the default rule

Rules you attach to a domain are called preferred rules. If there are several, you mark one as the default, which applies to every column in the domain. You may change an individual column to another preferred rule, and you can even apply more than one rule to a column (p.73).

Guide example, with a ShopSphere twist

The guide's Last_Name domain has a shuffle rule as default and a substitution rule as another preferred rule: shuffle for customer last names in one table, substitution in another (p.73). In ShopSphere: last_name in CUSTOMERS uses the default, while a hypothetical shipping_contact_last_name in another table uses the second preferred rule. Generation rules work the same way: in the guide, Date_of_Birth defaults to date random generation and also offers date sequence generation (p.74). The ShopSphere column is ours.

4.22.3 Data patterns and metadata patterns

A regular expression (regex) is a text string that describes a search pattern; it matches strings of characters in the source data (p.74). TDM uses regexes in two ways, and a domain may hold several of each. A column belongs to the domain if any expression matches (pp.74-75).

Data pattern (look at values)

Describes what the data looks like. SSN example from the guide: [0-9]{3}-[0-9]{2}-[0-9]{4}.

Use when you do not trust column names (an SSN hidden in a COMMENTS column).

Metadata pattern (look at column names)

Describes the column name. Guide example: .*Name* matches Name, Employee_Name and Organization_Name; .*SSN*, .*SOCIAL*, .*SECURITY* find SSN columns.

Use when names are reliable and values vary.

A regex primer, using only what the guide lists

Regexes are case sensitive. The guide lists these building blocks (pp.74-75), and gives a tutorial site for more. I added the ShopSphere reading.

Watch out

4.25 Words to know first

Profile
A saved search definition: which tables, which kind of analysis, which sampling limits. You can run it again later.
Profiling
Reading the data (or the column names) to describe it: which columns are unique, which look like SSNs, how many are empty.
Primary key (PK)
A column, or combination of columns, whose values uniquely identify each row. No empty values, no duplicates. Like a library card number.
Foreign key (FK)
A column in a child table that holds the primary key value of a parent row, such as ORDERS.customer_id pointing to CUSTOMERS.customer_id.

A set of related parent and child tables, used to define a subset.

The share of values in a column that are unique. 100 means no duplicates.

4.26 What data discovery is for

The guide's overview (User Guide 10.5.10, p.86): you run profiles to discover source data for masking and subset. Before masking, you discover which columns to mask with the same rule. Before building a subset, you discover relationships between tables and the entities that shape the subset database. You can then apply the results instead of configuring entities by hand or applying a masking rule one column at a time.

Why it matters

Discovery turns "someone remembers which columns are sensitive" into a repeatable, reviewable record. A compliance officer can see which columns were found, with what confidence, and who approved them. It also supplies the keys that subsetting needs when the database does not declare them.

4.27.2 Value cascades and auto cascades

Both make sure the same original value becomes the same masked value in several places. That is the difference between a customer whose id looks right everywhere and one whose id no longer matches across tables.

Auto cascade (keys exist)

Masks a parent table's primary key and the related foreign keys in child tables with the same value. Applied by default to tables with key constraints; you can enable or disable it. It needs key constraints between parent and child. Not available for XSD, MongoDB and Cassandra sources (p.91).

ShopSphere: mask CUSTOMERS.customer_id and ORDERS.customer_id receives the same masked value.

Value cascade (no keys)

Masks similar columns in different tables the same way when they are not linked by key constraints. You group similar columns and mark one as the driving column; a rule assigned to it goes to all the others. The columns must have the same type (p.90).

ShopSphere: an email column in CUSTOMERS and a contact_email column in some marketing table.

The guide's example: employee_num in one table and EmpID in another are similar value columns, with employee_num driving. Assign a rule to it and EmpID receives the same rule (p.90). The driving column shows a number in Similar Value Columns; the others show none.

  1. Create: in Discover > Columns select the columns, click Actions > Set as similar value columns, and click the driving-column checkbox to change No to Yes for one column (p.90).
  2. Change: select the driving column (it has a number), open the Similar Value Columns view in the Details panel, click Edit Similar Value Columns. Set Driving Column to Yes on another column (the previous one switches to No), use Add to add columns or Delete to remove them (p.91).
  3. Delete the group: select the driving column, open Similar Value Columns, select any column in the group, click Delete, confirm (p.91).

4.29 Primary keys: the basics, then discovery

The syllabus calls out primary key basics and "data integrity maintained in primary and foreign key columns" (Days 43 and 51). Nearly every later task, subset above all, depends on keys, so spend time here.

4.29.1 Primary and foreign keys in plain words

A library gives each member a card number. No two members share one, and no member is without one. That number is a primary key: a column (or combination of columns) that uniquely identifies each row. The guide's rule for keys you add by hand: a primary key column cannot contain null (empty) or duplicate values, and a table has only one primary key constraint (User Guide 10.5.10, p.109).

When a library loan record stores the member's card number, that stored number is a foreign key: it points at a row in another table. In ShopSphere:

CUSTOMERS (customer_id PK) 1 ----< ORDERS (order_id PK, customer_id FK)
ORDERS    (order_id PK)    1 ----< ORDER_ITEMS (item_id PK, order_id FK)
PRODUCTS  (product_code PK)  (ORDER_ITEMS.product_code refers to it)

Data integrity means these links stay true: every ORDERS.customer_id exists in CUSTOMERS, every ORDER_ITEMS.order_id exists in ORDERS. Test data that breaks this is useless. A subset that copies an order but not its customer produces an orphan. Masking that changes CUSTOMERS.customer_id but not ORDERS.customer_id breaks the link. TDM relies on keys to avoid both: subset follows constraints "to create subset data with referential integrity" (p.86), and auto cascades mask parent and child keys together (p.91).

Why discovery of keys matters

Real source systems often have no declared keys, for performance or legacy reasons. If ShopSphere's imported tables came with no declared keys, you would have to do the same.

4.30 Entity (foreign key) discovery

An entity is a parent table plus its related child tables. An entity profile finds possible entities by comparing column names in the source tables, and returns a list you choose from. The entities you define for a subset determine the structure and content of the subset database (User Guide 10.5.10, p.93).

The guide's example: Employee, Employee_Detail and Employee_Address all contain an EmpID column, so the profile suggests Employee as an entity with two direct relationships and two child tables. You select Employee as the entity. Later, a subset filter on EmpID (for example EmpID less than 2000) filters each table in the entity relationship (p.93).

ShopSphere reading (illustrative): customer_id appears in CUSTOMERS and ORDERS; order_id appears in ORDERS and ORDER_ITEMS; product_code appears in ORDER_ITEMS and PRODUCTS. The profile can therefore suggest CUSTOMERS to ORDERS to ORDER_ITEMS as a chain, and ORDER_ITEMS to PRODUCTS as another link.

Needs keys, or run both together

If you choose the Entity type and the physical database has no primary keys, the profile returns no results. If you run it as a primary key and entity profile, it discovers possible primary and foreign keys and returns results even without physical keys (p.93). The creation steps repeat the advice: select primary key and entity profile if the database has no primary keys (p.99).

4.34 Constraints and relationships

Discovery suggests; constraints are what TDM actually uses. Foreign key constraints define parent-child relationships between source tables, and TDM uses them to decide which tables go into a subset and to limit the values in subset columns (User Guide 10.5.10, p.107). When you create an entity you pick one table as the driving table, and TDM adds other tables based on the constraints of that table (p.107). The Informatica data subset chapter builds on this.

4.34.1 Table classification

In Discover > Tables you can classify tables as Temporary, Master, Configuration, Transactional, Log or Seed. It does not affect profiles, but you can filter tables by it when creating entities or plans. The guide's reason: knowing which tables are master helps you decide driving tables, and transaction and log tables are candidates for extra filter criteria (p.107). ShopSphere reading: CUSTOMERS and PRODUCTS look like master tables; ORDERS and ORDER_ITEMS look transactional (our classification).

4.34.3 Major and minor constraint severity

When you define a foreign key constraint you choose a severity, which decides how much data a subset pulls in (pp.108-109). The severity does not change the structure of the entity; you can change it after creating an entity and at run time in a subset plan (the run-time change does not change the entity).

Major

Moves in both directions, child to parent and parent to child. If a filtered child row selects a parent, all other children of that parent come along too. This honours referential and transactional integrity. You can apply a major constraint only from within an entity.

Minor

One direction only, child to parent. The parent row is included, but not all its other children.

The guide's example: Customer is the parent of Leads. You filter Leads to high-quality leads. With a major constraint the subset includes the customer for each high-quality lead and all that customer's leads. With a minor constraint it includes the high-quality leads and their customers only (pp.108-109).

ShopSphere version (illustrative): you filter ORDERS to total_amount > 500. Major: you get those orders, their customers, and all other orders of those customers. Minor: you get those orders and their customers only.

  • Selecting more records in the child can pull in more parents, which pull in more children, and so on until no related records remain (p.108).
  • For a smaller subset, choose the Referential Integrity Only option in a plan at run time. The data stays referentially intact, but it may not include every child of a parent, so transactional integrity might not be kept.
  • If constraints form cycles, or an object has more than one major parent constraint, TDM does recursive evaluation and needs a staging connection. Using the source connection as the staging connection is recommended (p.109).

4.35 Performance and accuracy tips from the guide

The guide has no dedicated discovery performance section; these tips are scattered through it.

  • Cap the sample. Primary key and data domain profiles default to 1,000 rows; column profiles default to All, the heaviest setting (pp.93, 95, 98). A small sample is fast but can call a column "unique" or "an SSN" wrongly (my reasoning).
  • Limit key columns (default 3, p.93) and avoid case-sensitive entity comparisons, which can slow the profile (p.99).
  • Search names first, then data. You can run a domain profile on column metadata and then on the data (p.100).
  • Pick only the domains you need: disabled domains are skipped (p.75), and choosing a policy includes all its domains at once.
  • Import metadata directly from the database when there are many tables (p.60), and use the same connection for import and profile (p.88).

Watch out
  • Not reopening the profile. Results only show after you close and reopen it (User Guide 10.5.10, p.103).
  • Running an entity-only profile on tables without keys. It returns nothing. Combine it with a primary key profile (p.93).
  • Approving every unique column as a key. Uniqueness is evidence, not proof. Choose the real identifier that child tables use.
  • Trusting a domain match without a preview. Use the Data Preview tab (first 200 records) and the conformance percentage before approving (p.105).
  • Expecting profiling to change the source database. Keys and constraints live in the TDM repository only (pp.86-87, 109).
  • Profiling with a different connection from the one used for import, or putting two same-named tables in one profile (p.88).
  • Importing a CSV of domain assignments without a header row. The first row is skipped (p.96).
  • Forgetting that each run overwrites results. Export or note decisions you want to keep before editing and re-running (p.101).
  • Column profile failing on Oracle or SQL Server. Native Oracle ODBC connections and a missing SQL Server schema name both cause failures (p.101).
  • Expecting profiles on every source. Not nonrelational sources, Avro or Parquet, and Hive only for data domains (pp.87-88, 94).
  • Assuming a pattern is case-insensitive. The guide says regular expressions are case sensitive (p.74).

4.38 Recap

Key points
  • Discovery profiles find what to mask and how tables relate before you configure masking or subset (User Guide 10.5.10, p.86).
  • Four profile types: primary key, entity (called foreign key in the overview), data domain and column. Primary key and entity, or primary key and data domain, can run together.
  • Primary keys uniquely identify rows; foreign keys point at them. Discovery proposes keys with a uniqueness percentage, and you approve or reject.
  • Data domain profiles match column values or names to domains defined by regular expressions; sampling options set the rows and the conformance threshold.
  • Results are suggestions: preview, approve or reject, correct by hand or by CSV, and close and reopen the profile to see them.
  • Constraints you approve or add (primary, foreign, logical, unique, conditional) live in the TDM repository. Major severity brings all siblings; minor does not.
  • Auto cascade keeps parent and child keys masked the same way; value cascades do it for similar columns without keys.
  • Labs 1 to 3 chain profiling into masking and subset on ShopSphere. Their menu paths are from the guide; the data and results are illustrative.

4.39 Words to know first

Data subset
A small, targeted copy of production data that keeps related rows together, so it can be used in development, test or training.
Referential integrity
The rule that every foreign key points at a row that exists. An order whose customer is missing breaks it.
Entity
In TDM, a set of tables that are related by physical or logical constraints, built around one starting table. You filter the entity to say "which customers".
Driving table
The one table you pick as the starting point of an entity. The guide says "driving table"; the syllabus says "driver table". They mean the same thing. People also say "root table", but the guide does not use that word.
Group
A set of tables that are not related to each other (or that you want copied without filtering), added to a plan as they are.
Template
An optional container that holds entities and groups. The guide mentions it but gives almost no detail (see 13.5).
Constraint
A rule linking two tables, usually a foreign key from a child table to a parent table. It can be physical (declared in the database) or logical (added in TDM because the database does not declare it).
Major / minor constraint
A severity setting on a foreign key. Major moves in both directions (child to parent and parent to child). Minor moves only child to parent.
Criteria parameter
A named placeholder (for example $$CRITERIAVALUE) used in an entity filter so the value can change at run time without editing the entity.
Plan / workflow
A plan lists what to do (which entities, groups, rules, connections). A workflow is the runnable job TDM generates from the plan.

4.40.1 The idea in one example

Imagine ShopSphere's production database holds 2 million customers. 4.42 Entities and the driving table

4.42.1 What an entity is

An entity is a shape: "start at this table, and include everything connected to it". The guide says an entity "consists of a driving table and related tables" (User Guide 10.5.10, p.114) . You then put a filter on columns of the tables in the entity to say which rows you want.

Here is the same idea on ShopSphere. We choose CUSTOMERS as the driving table because the business question is "give me some customers and everything they did". ORDERS points at CUSTOMERS through customer_id, ORDER_ITEMS points at ORDERS through order_id, and ORDER_ITEMS points at PRODUCTS through product_code. If the database does not declare a foreign key (common in older systems), you can accept one that data discovery inferred (see the Informatica discovery and profiling chapter), or add one by hand as a logical constraint. The guide's advice before you build an entity is: run data discovery to identify constraints, and add constraints to the source to define the child tables (p.116).

This is the guide's procedure (User Guide 10.5.10, p.116 to 117) , with the reason for each step.

    The Define area is where all the "design" objects live: subset components here, masking assignments in Define | Data Masking (see the Informatica masking chapter).

  2. Click Actions > New > Entities.

    This starts the New Entity dialog.

    Names matter later: plans list components by name. Something like ShopSphere_Customer_Entity beats Entity1.

4.43.1 Groups

A group is "one or more unrelated tables" you want copied to the subset database. 4.44 How related rows are pulled

This is the part that makes subsetting more than a filter. When your filter selects customer 1001, which other rows must come with it? The answer depends on the constraint severity and on the data integrity option you pick in the plan. Both are covered in the guide (User Guide 10.5.10, p.108 to 109, 119 to 123).

4.44.1 Major and minor constraints

When a foreign key is defined, you give it a severity. The guide's rules :

  • Major constraints move in both directions, child to parent and parent to child. A selected child pulls in its parent, and the parent then pulls in all of its children. This keeps referential and transactional integrity (p.108).
  • Minor constraints move one way only, child to parent. The parent row comes along, but the parent's other children do not (p.108 to 109).
  • You define the constraint on the child table. Severity does not change the entity's structure. You can change it after the entity exists, and also at run time in a subset plan, which leaves the entity unchanged (p.108).
  • By default every constraint in an entity is major (p.119).

The guide's own example (p.108 to 109) uses Customer as parent and Leads as child, with a filter on Leads that keeps only high-quality leads. With a major constraint, the subset receives each qualifying lead, its customer, and all leads of that customer. With a minor constraint it receives only the qualifying leads and their customers.

4.44.2 The loop that surprises beginners

With major relations the pulling can chain. The guide describes it (p.108, p.122): a selected child record pulls in its parents; each parent then selects all its related children; those children might point to other parents not yet in the subset, which pull in more children, "in a loop until there are no more related records to select". This is how a small filter can grow into a big subset. You will see exactly this in the ShopSphere example when PRODUCTS is related by a major constraint (13.11).

For schemas with cycles, or objects that have more than one major parent, TDM uses recursive evaluation to compute the subset, and that needs a staging connection. The guide recommends using the source connection as the staging connection (p.109).

4.44.3 The four data integrity options

The entity says how tables are connected. The data integrity option in the plan says how aggressively TDM follows those connections at run time. This lets you reuse one entity to produce different subsets. You choose it in the Advanced Settings area of the Plan Settings page when you create the plan; the field is called Data Integrity for Subset and its default is Transactional Integrity for Major Relation Type (User Guide 10.5.10, p.121, p.287) .

Two terms first. (A staging connection, mentioned below, is a database connection TDM uses for temporary working tables.) Referential integrity means no child row points at a missing parent. Transactional integrity goes further: if a parent is in the subset, all of its children are too, so a business transaction (a customer with all their orders) is complete.

4.44.4 Which option for ShopSphere?

  • One criterion on CUSTOMERS, want complete customer histories: keep the default Transactional option. Every order and line of a selected customer comes along.
  • Same criterion, want the smallest consistent database for a quick smoke test: Referential Integrity Only. You may get a customer with only some of their orders. For a test that checks "order total equals sum of lines" that is fine; for one that counts "all orders for this customer" it is not.
  • Criteria on both CUSTOMERS and ORDERS (for example zip code and order value): consider Two-way so that both tables end up with data, or edit the criteria to OR (see the table).

4.44.5 Optimizing relations

Because every relationship starts as major (p.119), a subset can pick up more rows than you need. Optimize Relations asks TDM to analyse the entity and propose which relationships can be minor while still reaching every table. The guide's procedure (User Guide 10.5.10, p.119 to 120) :

  1. Make sure the entity already has a criterion.

    TDM raises an error if you optimize an entity with no criteria at entity level (p.119).

  2. Open the entity and click Actions > Optimize Relations.

    TDM analyses the constraints. The Optimize Relationships page lists each parent and child with the current and the proposed type.

  3. Optional: Download Optimizations.

    Saves the proposal as a CSV so you can review it with a colleague.

  4. Click Optimize to accept all proposals.

    You cannot accept some and reject others (the guide says results cannot be applied selectively). A list of plans that include the entity appears; regenerate and rerun them.

  5. Click Continue.

    The entity is updated. You can still edit single constraints by hand afterwards.

You can also optimize at run time in the plan (the "Optimize Relationship Type for Entities" setting, p.283). That changes the run, not the saved entity, and it also requires criteria at the plan level (p.283). When you choose Two-way or One-way integrity, optimization is ignored (p.122 to 123).

4.44.6 Disabling and enabling relationships

Sometimes you do not want TDM to follow a link at all, for example a link to a huge audit table. In the Entity Map or the Relationships view you can disable a relationship (p.120) . In the map, choose to view all relationships and show excluded tables; enabled links are solid, disabled links are dotted. Click the link, then Disable Relationship or Enable Relationship. If a table loses every link to the entity this way, it is excluded from the subset database (p.115). If you still want its data, put it in a group.

4.44.7 When constraints change after you built the entity

Entities do not update themselves. If you add a constraint after building the entity, the entity list marks it as having a change impact. Open it, click Review Changes, accept the relationship changes you want, then use Actions > Mark Changes Review as Complete so the notice goes away (p.120 to 121) . The guide's figure on p.121 shows a dialog with Added, Changed and Deleted groups and an Accepted action.

4.45 Choosing rows: criteria, operators, parameters and limits

4.45.1 Entity filter criteria and operators

You met entity criteria while creating an entity (13.4). A criterion is: a column, an attribute (Value or Parameter), an operator, and the value or parameter. The guide's examples use "greater than", "equals" and "IN" (p.118, p.119, p.127). The excerpt I had does not print the full list of operators in the drop-down, so do not assume more than those three; look at your own dialog.

ShopSphere examples (illustrative)
  • customer_id <= 1002: keeps the first two customers. Easy to predict, good for a lab.
  • zip_code = '560001': keeps all customers in one postal area, a "region" subset like the guide's financial-data-for-one-region example.
  • customer_id > $$CRITERIAVALUE: the same, but the number comes from a parameter (next section).

4.45.2 Subset with parameters

Typing the value into the entity means editing the entity every time the requirement changes. A criteria parameter lets you change the value when you run the workflow. The guide (User Guide 10.5.10, p.113, p.118, p.57) says:

  • Create criteria parameters in the project (Projects, open the project, Parameters tab, Add) or use global parameters an administrator created. Global ones show an asterisk (*) in lists, and you can import one into the project first (p.57 to 58).
  • Parameter types are criteria, connection and owner. Criteria parameter names begin with $$, connection ones with $DBConnection, owner ones with $Param. Data types are String, Numeric or Date. For a Date parameter you enter an expression that says how it is used, for example TO_DATE($$CRIT1,'MM-DD-YYYY') (p.57).
  • You choose a default value and whether overriding is allowed. If you do not allow override, you cannot change the value when you run the workflow (p.57).
  • Values can live in the project or in an external parameter file. The guide's example: a parameter CRITERIAVALUE, a parameter file line $$CRITERIAVALUE=100, and an entity criterion EMPID > CRITERIAVALUE. To get EMPID greater than 500, change the file to 500 and run the same workflow (p.118).
  • For a string or date parameter on a relational source, put the value in single quotes in the parameter file (p.118).

Ignore flags. If you keep values in a parameter file you create yourself, add a flag for each criteria parameter, for example $$CRITERIAVALUE_IGNORE. "N" means use the criterion, "Y" means the workflow skips it. A file created from Test Data Manager already contains the flags, set to "N" (p.118, p.309 to 310).

To make the plan accept parameter values, tick Treat the subset criteria as a variable in the plan's connection options and give the parameter file name and path (p.279) . At run time, in the Execute Workflow window, you choose where values come from (p.310 to 311): the default file named in the plan settings, a parameter file you browse to, or Add Parameter Values from the project. Criteria parameters do not appear in that list by default: click Select Parameter and add them, because "a workflow does not include parameters that do not appear in the list" (p.311).

Two silent ways to get the wrong subset

(1) You forget to select the criteria parameter in the Execute Workflow window, so the criterion is not included. (2) You edit a parameter that was created without "allow override": the change does not take effect and the workflow uses the default value and logs an error (p.311). Check the workflow log if the row counts look wrong.

4.45.3 Database functions in entity criteria

You may want a date rule such as "hired in the last three months". The guide (p.118 to 119) warns that writing a database function directly in the criterion makes workflow generation fail, because TDM does not recognise it as a function and cannot pass it on. The documented workaround: choose the operator IN and write a SELECT query in the Value field, for example select HIREDATE from <table> where HIREDATE > add_months(current_date, -3). TDM then passes the query to the database. The ShopSphere version of this idea would be a query on ORDERS.order_date.

4.45.4 Filtering again inside the plan

You can also set criteria in the plan itself without editing the entity (User Guide 10.5.10, p.294, p.304) . In the plan's component list you pick a subset component, then a column in the Criteria panel. TDM shows existing criteria, which you can change or add to. You then choose a method:

What the guide does not tell you about Limit

The excerpt I had names the three limit types and nothing more. It does not say which table the percentage applies to, how rows are chosen (first N, random?), what the "interval" arithmetic is (every Nth row? a range?), or how a Limit interacts with parent-child pulling. So I describe the three types by their names only: percentage means a share of rows, absolute value means a fixed row count, interval means "a set of rows defined by an interval". Test on a small table and count the result before relying on it. The guide also says Two-way and One-way integrity are not available when a plan uses custom Advanced or Limit criteria (p.123).

  • Percentage: for example 10 percent. Natural fit for the ShopSphere goal, but check how TDM applies it to related tables.
  • Absolute value: for example 500 rows. Handy when the test environment has a hard size cap.
  • Interval: a defined interval of rows. The guide gives no example.

Syllabus link: Day 44 "types of subset". In practice, the guide supports these ways of choosing rows: by condition (entity criteria and plan Basic/Advanced criteria), by parameterised condition, and by quantity (Limit). I label this grouping as my own summary, , not a list taken from the guide.

4.45.5 Subset and masking in one plan

A plan can hold both subset components and masking components. The guide says the subset component gets priority: TDM does the subset first, then applies masking rules to the columns of the subset data. Masking is not applied to source data that is outside the subset, "even if the data is part of a cascade" (User Guide 10.5.10, p.275) . You can also keep them in separate plans (p.304). the Informatica masking chapter covers the masking half.

4.46 Subsetting XML: XSD sources in brief

XML data is a tree, not a set of tables, so entities and driving tables do not apply. Instead you put a filter on an element or attribute and set a scope: the level of the tree at which the filter is applied. You can apply one filter per hierarchy, and the scope changes the outcome (User Guide 10.5.10, p.114, p.124) .

The procedure (p.124): import the XML source definition from the PowerCenter repository into the project; click Discover > Files; open the XSD file; select an element or attribute; on the Criteria tab of the Details tab click Edit; choose an operator; enter a value (you cannot use a parameter here); choose the scope; click OK. Then add the XSD file to a plan and run it.

The guide's worked example (p.127 to 134): a master XML file lists departments, each with an address, employees and contractors, each with a name, address and skill. Test group A wants employees skilled in Java; group B wants departments located in BLR.

  • Group A: criteria on the element Skill on the Employee branch, operator Equals, value JAVA, scope Employee. The output has all Java employees. Because Department is an ancestor of Employee, the departments that have such employees come along with all their child elements.
  • Group B: delete the Skill criterion, then put a criterion on City: Equals, BLR, scope Department. The output has every department whose address city is BLR, with all child elements.
Visual referenceInformatica TDM 10.5.10 User Guide, p.127, Figure (Criteria tab of the file page). What I saw: a dialog titled "Edit - Skill" with tabs General, Data Masking, Data Generation and Criteria. Criteria is selected and shows three fields: Operator set to Equals, Value set to JAVA, Scope set to Departments/Department/Employee, with OK and Cancel buttons.

The lesson carries over to relational data: the level where you filter decides which ancestors and descendants appear. For the ShopSphere tables the equivalent of "scope" is your choice of driving table and relationship types.

The guide's own summary of "Creating a Data Subset" is seven steps (User Guide 10.5.10, p.126) . Here they are with the reason and what you should see.

  1. Create a project and add the data sources.

    A project is the workspace that holds sources, parameters, components and plans. The guide advises separate projects for XSD sources and relational sources. If you ran discovery in the Informatica discovery and profiling chapter, it is the same project.

    The tables of the source appear in the project, with constraints from physical keys.

  2. Optional: create connection, owner or criteria parameters.

    Do this now if you want the same plan to serve different values later (13.7).

  3. Create the subset components for your source type.

    Relational and flat file: entities and groups. XSD: criteria with scope on elements and attributes.

    Generate a workflow from the plan (the PowerCenter Repository Service generates the mappings) and execute it (the PowerCenter Integration Service does the extraction and load). You can do both in one step with Actions > Generate and Execute (p.308, p.310).

    Watch status in the Workflow Executions view: In Queue, Running, Success or Error. Click the Job ID to open the workflow log (p.311 to 312).

4.49.5 Option A versus a major relationship

Why did I insist on changing PRODUCTS to minor? With the default (all major), the loop from 13.6 applies: line 9001 pulls in its parent product P-100. As a major parent, P-100 then selects all order lines for P-100, from every customer. Those lines pull their orders, the orders pull their customers, and so on, until nothing new is added. A popular product like P-100 can connect nearly everyone, so "10 percent of customers" turns into most of the database (the right-hand column above, illustrative counts). Minor means: bring the product along, but do not let the product pull its other lines.

4.49.6 Option B: reference table as a group

PRODUCTS is small and looks like reference data. Another valid design: disable the ORDER_ITEMS to PRODUCTS relationship in the entity (p.120) so the entity is just customers, orders and lines, then create a group containing PRODUCTS (tick it from the residual tables, p.116) and add both the entity and the group to the plan. The target gets all 12 products (unfiltered) and still has no orphan lines. The trade-off: 8 unused products travel along, which is harmless here but would matter for a 2-million-row table. Pick Option A for big parent tables and Option B for small reference tables.

4.51 Common mistakes and gotchas

Watch out for these
  • No criterion, huge subset. An entity without a filter copies everything it reaches.
  • Everything is major by default, so a popular parent table can balloon the result (p.119, 13.11). Optimize relations or set minor.
  • Missing constraints. If the database does not declare a foreign key, TDM will not follow it until you add a logical constraint (p.109, p.116).
  • Editing without rerunning. After you edit or delete an entity, group or rule, the plans that use it do not pick up the change until you generate and run them again (p.124, p.275).
  • Using a database function directly in a criterion. Workflow generation fails; use IN with a SELECT clause (p.118 to 119).
  • Parameter not selected or not overridable. Criteria parameters must be added in the Execute Workflow window, and non-overridable ones ignore your edit (p.311).
  • Forgetting quotes on string or date parameter values in the parameter file (p.118).
  • Cycles and a missing staging connection. Cyclic or multi-major-parent structures need one (p.109, p.122).
  • Mutually exclusive criteria give an empty subset. Several criteria are ANDed; use OR in the plan's Advanced criteria if you want either (p.122).
  • Treating the Limit like a magic 10 percent. The guide does not describe how it interacts with related rows. Test it.

4.52 Recap

Key points
  • A data subset is a small, referentially intact copy of production data; TDM can build one from relational, flat file or XSD sources.
  • An entity is a driving table plus the tables related to it by constraints; a group is a set of unrelated tables copied as they are; a template is an optional container the guide barely describes.
  • Filter criteria, with an operator and either a value or a parameter, choose rows. A plan can add Custom (Basic, Advanced) criteria or a Limit by percentage, absolute value or interval.
  • Major constraints move both ways and can pull in far more than you expected; minor constraints go child to parent only. Optimize Relations suggests which can be minor.
  • Integrity options (Transactional, Referential only, Two-way, One-way) trade completeness against size.
  • The workflow: project, parameters, components, optional optimization, plan, run, monitor.
