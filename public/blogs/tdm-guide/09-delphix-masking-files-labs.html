Delphix: masking algorithms and masking jobs

Profiling tells you which columns are sensitive. Masking is the step that actually changes them. In Delphix the work is split in two: an algorithm decides how one value becomes another, and a masking job applies the assigned algorithms to every row of a rule set. This section covers both halves. First the idea of algorithms (frameworks, instances, keys, lookup files, uniqueness), then a catalogue of every algorithm framework the documentation lists, then a close look at the algorithms for first name, SSN, alphanumeric text and telephone number. The second half explains how to build, run, monitor and tune a masking job.

It ends with two labs on the ShopSphere tables: masking FirstName, and masking alphanumeric text, SSN and telephone number. Rule sets and inventories are covered in the rule sets and keys chapter and the profiling chapter. For the generic ideas behind masking see the masking concepts chapter, and for the Informatica equivalent see the Informatica data masking chapter. Masking files is the topic of the file masking chapter, and the full lab set is in the Delphix hands-on labs chapter.

Tool-specific facts are from the Delphix Continuous Compliance documentation, version 2026.5. Screenshots come from engine versions 22.0.0.0 to 26.0.0.0 as shown in their banners. Before and after values in the ShopSphere tables below are examples of the documented behaviour; a real engine produces different values because the output depends on the algorithm key and lookup file.

9.1 Words to know first

Algorithm (instance)
A named, ready-to-use masking recipe with its configuration, such as dlpx-core:FirstName. You assign instances to columns.
Algorithm framework
A kind of algorithm that you can configure to create new instances, such as Secure Lookup or Segment Mapping. "FIRST NAME SL" is an instance of the Secure Lookup framework.
Out-of-the-box instance
An instance that ships with the engine. These cannot be edited or deleted; you create your own from a framework instead.
Algorithm key
A secret value inside most algorithms. Changing it changes the output, so the same input masks to something different.
Deterministic
Same input, same algorithm, same key, same configuration gives the same output every time. This keeps joins working across tables and across runs.
Lookup file
A plain text file with one replacement value per line (no header). The algorithm picks a line based on the input, so the output is always something from your file.
Collision
Two different inputs masked to the same output. Fine for names, harmful in a unique column.
Non-conformant data
A value that does not fit the format an algorithm expects, such as letters in a numeric-only algorithm. By default it is left unmasked and a warning is recorded.
Masking job
A saved set of options saying "apply the inventory of this rule set", with a method (in-place or on-the-fly), threads, memory and scripts.
In-place / on-the-fly
In-place changes the data where it sits. On-the-fly reads from a source and writes masked data to a different target.
Stream
One parallel lane of work. More streams let the engine mask several tables at once.

9.3 What an algorithm is, in five ideas

9.3.1 Idea 1: framework versus instance

Think of a framework as a recipe template ("replace each value with one chosen from a list") and an instance as a filled-in recipe ("...using this list of first names, ignoring case"). The documentation's own example: "FIRST NAME SL" is an instance of the Secure Lookup framework . The analogy stops being accurate in one place: a framework is not something you assign to a column. Only instances are assigned.

9.3.2 Idea 2: the key makes output repeatable but secret

Most algorithms include a key. If FirstNameLookup masks "Michelle" to "Rachael", changing the key might make it "Ben" instead . The key can be randomised through an API call (PUT /algorithms/{algorithmName}/randomize-key). Two consequences:

  • Within one key, repeatable output means the same customer name masks the same way in every table and every run, so test data stays internally consistent.
  • Whoever knows the key and the algorithm might be able to rebuild mappings, so treat the key like a password and do not casually re-key production algorithms, because every later run would produce different test data.

9.3.3 Idea 3: unique versus non-unique

Some algorithms may give two inputs the same output (collisions). Others guarantee that different inputs give different outputs. The docs are consistent about which is which:

PropertyFrameworksUse it for
Collisions possible (non-unique)Secure Lookup, Name, Full Name, Date Shift Discrete or Variable, Free Text Redaction, Min MaxNames, cities, comments: values that repeat naturally in real data
No collisions (unique)Character Mapping, Segment Mapping, Mapping, TokenizationKeys and identifiers: primary keys, foreign keys, SSN, account numbers

Caveat from the docs: even Character Mapping can collide for numeric data types, because "001" and "1" are the same number once stored in a numeric column .

9.3.4 Idea 4: a lookup file is just a list

Lookup-based algorithms (Secure Lookup, Name and their out-of-the-box instances such as FirstNameLookup, LastNameLookup and FullNMLookup) hold a list of fake values. The engine hashes the input, uses the hash to choose a line, and returns that line. The file has one value per line, no header, in ASCII or UTF-8 . For example, a tiny file for cities could be:

Smallville
Clarkville
Farmville
Townville

With a hash method of SHA256 (the default) the same input always chooses the same line. The framework also offers LEGACY (to mimic old behaviour) and RANDOMIZE, which picks a random line each time and therefore does not keep referential integrity. RANDOMIZE suits things like gender, where you want a statistical spread rather than consistency .

9.3.5 Idea 5: masking versus tokenization

Almost all masking is one-way. Tokenization is the one family that can be reversed, which is why it exists: mask data, send it to an outside vendor, and later re-identify the vendor's findings . It is covered in the framework catalogue below.

Generic technique names and their Delphix counterparts

The generic technique names map onto Delphix frameworks as follows:

  • Substitution: Secure Lookup, Name, Mapping (replace a value with another real-looking value).
  • Shuffle: SecureShuffle (moves existing values between rows).
  • Key masking: Character Mapping and Segment Mapping (keyed permutation that keeps uniqueness).
  • Encryption: Tokenization (AES-128 in the framework description, reversible).

9.5 Deep dive: masking a first name

The default tool is dlpx-core:FirstName, an instance of the Name framework. It needs String input. If the value is null, empty or only spaces, it comes back unchanged. Words joined by a hyphen count as one word, a single letter is treated as an initial and masks to a single letter, and by default at most two names are masked and extra ones dropped. It raises no non-conformant data errors, and it can occasionally mask a name to itself .

9.6 Deep dive: alphanumeric text with Character Mapping

Character Mapping swaps each maskable character for another one from the same group, using a key. You define groups such as [0-9] and [a-zA-Z]; a digit becomes a digit and a letter a letter; anything not in a group (dashes, spaces) is left alone. Every maskable position affects every other, no two text inputs share an output, and a masked value never equals the original if at least one character is masked. That makes it suitable for keys and identifiers .

Three ready instances cover most needs:

9.7 Deep dive: SSN with Segment Mapping (or Character Mapping)

An SSN has structure (3 digits, dash, 2 digits, dash, 4 digits) and often serves as a lookup key, so you want unique, format-preserving output. The Segment Mapping page names Social Security Numbers as a typical use and describes exactly the controls you need :

  • Up to 10 segments, each up to 6 characters, each treated as Mask alpha-numeric, Mask numeric, Preserve or Mask with a constant value.
  • Ignore characters (such as the dash) are removed before masking and put back afterwards, so "123-45-6789" and "123456789" mask alike.
  • Numeric segments are masked as whole numbers, alpha-numeric ones character by character.
  • Values must match the segment pattern; data longer than the pattern passes through unmasked, and short numeric segments are reported as non-conformant unless you choose "Mask partial segments".

9.9 More algorithms you will meet: dates, email, mapping, tokenization

The labs use four algorithms, but the rest of ShopSphere (and any real project) needs a few more. Each paragraph below is a short orientation from the framework pages .

9.9.1 Dates (date_of_birth, order_date)

Three out-of-the-box instances differ in how much they preserve. Date Shift Fixed moves every date five days forward and rolls within the month, so the same input always gives the same output and no two dates collide ("2001-02-27" becomes "2001-02-04"). Date Shift Variable picks a random day within the same month and year and can collide. Date Shift Discrete sends every date of one year-month to one fixed day (about one in thirty dates may collide), so it is unsuitable for columns with unique, primary or foreign key constraints. When you build your own Date Shift instance you choose a minimum and maximum shift and a unit; equal values give a fixed shift, 0 inside the range is never used (a date never masks to itself), and Roll keeps all larger and smaller units unchanged. For a column that is not a native date type, set the Date Format in the inventory (default yyyy-MM-dd, case sensitive). Pairs such as admission and discharge need Dependent Date Shift so the order and the interval survive.

9.9.2 Email

The Email framework splits at the "@". The default dlpx-core:Email Unique hashes the whole input into a 52-character Base32 name and replaces the domain with example.com, so every input gets its own output (64 characters in total, which matters for short columns). dlpx-core:Email SL instead picks a readable name such as "E.Duboise" from a 20,000-value lookup, so collisions are possible but the data looks more human. The Email Unique output is what the profiling screenshots showed for the EMAIL domain, so ShopSphere's email column is covered by default; check that the column is wide enough for 64 characters.

9.9.3 Mapping: you decide the replacements

A Mapping algorithm replaces each distinct input with a value you supplied, and it never reuses an output, so there are no collisions. You must provide at least as many replacement values as there are distinct inputs, or the job reports "No free mappings are available". Mappings can be imported as a plain list of outputs or as a CSV with input,output columns, and exported (encrypted with a passphrase), reset or deleted. All mappings load into memory during a job, so give the job enough memory. Mappings can live on the engine or in your own PostgreSQL database shared by several engines. Before engine 6.0.10.0, only one table could be masked at a time with a mapping algorithm; later versions allow concurrent jobs.

9.9.4 Tokenization: masking you can reverse

The Tokenization framework encrypts values with AES-128 and Base64 so a vendor can analyse data they cannot read, and you can later re-identify their findings. The output is longer than the input; if it would not fit the column, the framework either fails the job or falls back to a reversible Character Mapping. Segment Mapping, Character Mapping and Mapping can also be used for tokenization under conditions the framework pages list. You create a domain with both a masking and a tokenization algorithm, then a Tokenization environment, and use + Tokenization Job and + Re-Identification Job; the form has the same fields as a masking job.

9.10 Creating, choosing and managing algorithms

9.10.1 Create your own instance

  1. Settings > Algorithms > + Algorithm.

    Your instances are called user-defined algorithms; once saved they are available to all users.

  2. Enter a unique Algorithm Name, a Description and choose the Framework, then Next.

    Name and framework are locked after creation, so choose carefully. The wizard shows the framework's Mask Type (for Date Shift it showed LOCAL_DATE_TIME).

  3. Fill in the framework's configuration, then Next.

    The panel on the right explains each field. The frameworks in the catalogue each have their own options.

  4. Check the Summary and Save.

    The algorithm appears in the grid. Creating and editing are asynchronous tasks; a "Run in background" option may appear if it takes time.

To use a new algorithm in a profiling job you must first attach it to a domain as that domain's default (see the profiling chapter). If you build the inventory by hand, no domain is needed .

9.10.2 Choosing between Character Mapping and Segment Mapping

The docs say Character Mapping is intended to replace Segment Mapping in many cases, but not all .

Prefer Character Mapping when

  • Data is dirty or inconsistently formatted: it keeps non-masked characters automatically
  • You need Unicode (first plane) rather than just a-z and 0-9
  • Inputs differ in length and you want to preserve the last characters (reverse preserve ranges)
  • You want every position to influence every other

Prefer Segment Mapping when

  • Parts of the value must be masked differently by position
  • You need to map input ranges to different output ranges (A-D to W-Z)
  • You need numeric segments limited to a value range (up to 6 digits)

9.10.3 Multi-column algorithms

A multi-column algorithm (for example Dependent Date Shift or Multi Column Address) is assigned once but spans several columns, each filling a logical field. It is meant for coordinated masking, such as two dates that must keep their interval. Each non-optional logical field must be assigned for every Algorithm Group number, and incomplete assignments may only be noticed when the job runs. They only work where whole rows are processed together, and cannot be called by other algorithms through chaining .

9.10.4 Usage and syncability (engine administration)

  • Usage. GET algorithm/{algorithmName}/usage lists every column, file field, domain and other algorithm that uses it. PUT on the same path with replacementAlgorithmName swaps it everywhere, with optional environment and rule set filters. The docs warn that this can change many inventories and is hard to undo, so first GET usage for both algorithms and export global settings and affected environments .
  • Syncability. Algorithms are fully syncable between engines (GET /syncable-objects?object_type=USER_ALGORITHM). Non-deterministic ones (all Secure Lookup Random algorithms, DateShiftVariable, Gender SL, SexualOrientation SL, SecureShuffle) cannot give the same output twice, so they cannot be used for syncable masking. DateShiftFixed and RepeatFirstDigit are listed as fixed. Syncing an out-of-the-box instance updates its key but does not replace its files .

If two engines mask the same source, identical output on both needs the same keys, which is what syncing delivers.

9.11 Masking jobs: in-place or on-the-fly

A masking job lives in an environment next to the profiling jobs of the profiling chapter. A masking environment supports Profiling and Masking jobs; a tokenize environment supports Profiling, Tokenization and Re-Identification jobs, created with the same flow . Start with the one choice that shapes everything else, the masking method.

In-Place

Updates the source environment with masked values. Typical use: you already copied production into a test database (for example a virtual database) and mask that copy where it sits. Risk: if the job fails midway, that database may be partly masked.

On-The-Fly

Reads unmasked data from a source environment and connector, and writes masked data to the target. Typical use: production stays untouched and the masked copy goes elsewhere. Supported pairs: same connector type (Oracle to Oracle, delimited file to delimited file) and database source to delimited-file target.

For a database-to-file job, tick Database to File Job so that the source connector list shows database connectors. Target files need not exist in advance if the file name pattern matches the source, but in a database-to-delimited-file job the target files must be created first, with names matching the source tables. You need the View Connector role to create or run on-the-fly jobs .

9.11.1 Create a masking job, step by step

  1. In the environment's Jobs tab click + Masking Job.

    The Create Masking Job wizard opens: Details, then Database Options (database rule sets only), Configuration, Summary.

  2. Details: unique Job Name, Masking Method, Rule Set.

    The name must be unique across the entire application. For On-The-Fly you also choose Source Environment and Source Connector.

  3. Details: decide the optional boxes.

    Multi-Tenant reuses a rule set for identical schemas through different connectors, chosen at run time. Selective Data Distribution must be on if the job will be used in masked VDB provisioning. Stop job on first occurrence aborts on the first non-conformant value, but only where the algorithm or global setting says non-conformant data is a failure.

9.11.3 Non-conformant data: when a value does not fit the algorithm

If a value does not match what an algorithm expects (letters going into a numeric-only algorithm, an 11-digit string into a 10-digit segment pattern), the job, depending on settings, fails, skips the value, or nulls it. The global default is the application setting DefaultNonConformantDataHandling; an algorithm's own setting overrides it, and a job can override both with Job-level Non-Conforming Data Handling: Use global setting, Fail on encounter (FAIL), Don't mask value (DONT_MASK) or Set value to null (NULLIFY). The job-level override applies only to Hop-based jobs. By default non-conformant data is not masked and the job ends with a warning .

Unmasked data in a test database is a leak, so never ignore a yellow warning. Open the execution component's logs. The Error Report lists the event type (UNMASKED_DATA, or JOB_ABORTED if the job stopped), the cause (PATTERN_MATCH_FAILURE), the row count and the column, plus a sample of the pattern of the bad value, never the value itself. Each character is shown as a class: N digit, L letter, M mark, P punctuation, S symbol, Z separator, O other, U unknown.

To find the offending rows, translate the pattern into a database query. For the pattern LLLLL on an Oracle column, the docs use SELECT EXCEPTION_00 FROM testdata_EXCEPTION WHERE regexp_like(EXCEPTION_00, '[[:alpha:]]{5}');. For a multi-column algorithm the pattern is shown for every masked column of that algorithm, so you must read the message to find the real culprit.

9.11.4 Speed: PerfLogger and best practices

From version 2026.3 the throughput log is called PerfLogger. It logs at job start (every 10,000 rows), then every 30 seconds after 100,000 rows, and once at the end with totals. The main number is RPM, rows per minute; MB/sec is only informational, and BPR is the average bytes per row. Rows of about 1 KB or more lower RPM. A sharp RPM drop to zero with an unchanged BPR points at the target side (transaction log pressure, auto-growth, many indexes). If RPM falls below earlier runs, check for concurrent jobs, new indexes, constraints or triggers, and bigger rows .

The best practices page recommends, for a dedicated compliance engine, 8 vCPUs and 64 GB RAM minimum (128 GB or more preferred), about one vCPU per concurrent job, at least 1 GB of memory per job and per stream (more for particularly wide rows or big lookup files such as 500,000 values), the engine near the database server on a slow network, and tuning the masked VDB first (for Oracle, no-archivelog mode; for SQL Server, SIMPLE recovery) . Mapping algorithms are the other big memory user: all mappings load into memory, so a 2 GB mapping needs much more job memory than a 2 MB one.

SELECT COUNT(*) FROM orders o JOIN customers c ON c.customer_id = o.customer_id;

Why each expectation is justified.

  • tax_id: Character Mapping keeps letters as letters and digits as digits, and gives no two inputs the same output, so the shape and uniqueness checks should pass. The docs promise a masked value never equals the input if at least one character is masked.
  • ssn: Segment Mapping produces "no overlaps or repetitions", so duplicates should be 0. The page does not say a value can never map to itself, which is why that check is "0 or very close".   • phone: Phone Unique masks only the last seven digits and keeps all other characters, so the first three digits must be unchanged. 9.13 Common mistakes and gotchas

Watch out for these
  • Using a non-unique algorithm on a key or unique column. Secure Lookup, Name and Date Shift Discrete can collide. Use Character Mapping, Segment Mapping or Mapping for keys, and the same algorithm on every column that must still match, including foreign keys.
  • Ignoring the yellow Warning status. Non-conformant values are left unmasked by default, so real data can reach the test database. Read the Error Report after every run.
  • Testing for "zero unchanged values" with name algorithms. The documentation says a masked name can equal the input; test for "a small number", and use Character Mapping when a changed value is mandatory.
  • Running an in-place job on the only copy of the data. Cancelling or failing midway can leave data semi-masked, and dropped indexes or triggers are not recreated.
  • Several update threads on tables without indexes. The docs warn of deadlocks, especially on T-SQL databases.
  • Re-keying an algorithm casually. It changes every masked value, so test data from before and after no longer matches.
  • Letting the profiler overwrite your algorithm choice. Untick Enable Automatic Updates when you assign by hand (see the profiling chapter).
  • Assuming a masked SSN or phone number is a valid real-world number. The frameworks keep shape and uniqueness, not issuing rules.
  • Giving a job too little memory. Below the recommended 1024 MB, and with large lookup files or mappings, performance suffers or jobs fail.

9.14 Recap

Key points
  • A framework is a configurable kind of algorithm; an instance is a ready recipe you assign to a column. Output is repeatable for the same input, key and configuration.
  • Lookup frameworks (Secure Lookup, Name) pick a line from a list file and may collide. Character Mapping and Segment Mapping are keyed and collision free, which suits keys and identifiers.
  • Algorithms used in the labs: dlpx-core:FirstName for first names, Segment Mapping or CM Digits for SSN, dlpx-core:CM Alpha-Numeric for alphanumeric text, dlpx-core:Phone Unique for telephone numbers.
  • A masking job is in-place (changes the data where it sits) or on-the-fly (reads a source, writes a target). Key settings: commit size, update threads, batch update, streams, row limit, memory, pre and post SQL.
  • Run the job, then monitor status, components, logs and the Error Report; non-conformant data is left unmasked by default.
  • Always verify with SQL: row counts, side by side, distinct counts, uniqueness, format and join checks.

9.15 Words to know first

Flat file
A plain text file where each line is a record and each record holds fields in a fixed order, such as a .txt, .csv or .dat file. The extension is only a habit; the engine cares about the layout.
Record / field
A record is one line (one customer). A field is one value in it (the phone number).
Delimited file
Fields are separated by a character such as , or |.
Fixed-width file
Every field has a set length, so field two starts at a known position, with no separator.
File format (definition)
A small description file you upload that lists a file's field names (and, for fixed width, lengths). It is metadata only. Many data files can share one format.
End-of-record
The character or characters that end a line: LF on Linux, CR+LF on Windows.
Text enclosure
A character, often a double quote, that wraps a value so the value may contain the delimiter. "Menon, Asha" is one field.
Escape
How a literal enclosure character inside an enclosed value is written, by default by doubling it.
Record type and qualifier
When one file mixes record layouts, a record type names each layout and up to three qualifiers say how to recognise it.
Header and footer
Lines at the start or end that should be copied through unmasked.
File connector / rule set
The connector says where the files are. The file rule set lists which files (or name patterns) to process and which format each uses.
Encoding
How characters become bytes. ASCII and UTF-8 are supported for the main file types; mainframe data must be EBCDIC.

9.16.1 Look at the file before you describe it

The extension (.txt, .dat, .csv) tells the engine nothing; only the layout matters. Before you write a format, answer four questions about the actual file. These commands are ordinary Linux tools, not Delphix features:

head -3 customers.dat                      # what separates the fields?
cat -A customers.dat | head -2             # $ marks LF; ^M$ means CR+LF (Windows)
awk -F'|' '{print NF}' customers.dat | sort | uniq -c   # same field count on every line?
file customers.dat                         # ASCII or UTF-8 text?

If cat -A shows ^M$ at line ends, the end-of-record is CR+LF. If the field counts vary, the file has several record layouts or stray delimiters, which points to record types or enclosures.

The same ShopSphere record as fixed width, with lengths 6, 12, 12 and 30, looks like this (dots stand for padding spaces):

1001..Asha........Menon.......asha.menon@example.com......
^1-6  ^7-18       ^19-30      ^31-60

Field 2 starts at position 7 because field 1 is six characters long. The engine computes every start from the lengths you list, which is why one wrong length shifts everything after it.

9.18.1 End-of-record

Choose LF for Linux-style files and CR+LF for Windows-style ones in the rule set's file properties. The docs do not describe the failure mode; a wrong choice likely glues lines together or leaves a stray carriage return in the last field. The rule set page also lets you use a control character as delimiter or end-of-record: click the CTRL button for a virtual keyboard, or type it as $[hex value], for example $[01] for ^A. The docs say to avoid typing ^t or \t .

9.18.2 Enclosures and escaping

Take the line 1004|"Rao, Kiran"|... with a pipe delimiter and a double quote enclosure. The comma inside the quotes belongs to the value. If a value itself contains a quote, it must be escaped. The rule set offers an Enclosure Escaping Strategy :

  • Double Enclosure (the default): the escape character is the enclosure character, so "" means one literal quote.
  • Custom: any single character except escape sequences and control characters.
  • Escape "Enclosure Escape Character" (checkbox): the escape character can also escape itself, so with * as escape, ** is one literal *.

For a large number of rule sets the docs provide an API script that updates these settings through PUT /file-metadata, for all delimited rule sets with an enclosure or for one rule set ID. A custom escape character or the "escape the escape" flag is not supported for delimited fields holding structured (JSON or XML) data; only double enclosure is.

9.20 Record types, qualifiers, header and footer

Real feeds often mix layouts in one file. The docs' example has lines like address, account1234, 9A Lexington Street, ... and email, account1234, bar@example.com: the first field says what kind of record follows. A record type describes one layout; up to three qualifiers (a field plus a regular expression) tell the engine which lines belong to it. A line gets exactly one record type, and if several qualifiers match, the engine cannot guarantee which wins. Record types and header/footer apply only to delimited and fixed-width formats, and can be managed only on the Formats page, not on the inventory page .

  1. Add a record type: + Record Type, enter a Record Name, Choose File (a definition file for that layout), Save.

    Each layout needs its own field list.

  2. Add qualifiers: + Qualifiers, pick the record type, choose 1 to 3 qualifiers, and for each give a Field Name and a Regular Expression.

    The record type applies when its expressions match the chosen fields. For the example, field type with expression address.

  3. Header and footer: + Header & Footer, enter how many records at the start and the end to leave unmasked, Save.

    Those lines reappear unchanged in the masked output. Without this, a header such as customer_id|first_name|... would be treated as data.

Editing a record type's name and deleting a record type are in its row's Actions column. To reach the format from a rule set inventory, use the Edit File Format button.

Mounts in plain words. A mount makes a folder on a file server (shared over NFS or CIFS) appear as a folder on the engine, so the engine can read and write files there as if they were local. You register the mount first (a name, the server address and the shared path) and then pick it in the connector. Use SFTP when the files sit on a normal server you can log in to, and a mount when the share already exists.

Cloud storage. "Prefix" and "delimiter" work as in the cloud vendor's list-objects calls: the prefix (for example json/) limits which objects the engine sees. On-the-fly note. For on-the-fly file masking you need a second connector (and environment) for the target. One page says the target rule set's file path must already point to a file with the same name in the target directory, which the masked file then replaces. The masking job page says target files need not exist in advance if the file name pattern matches the source. The docs do not reconcile these two statements; test on your engine version.

9.22.1 Mainframe data sets (overview)

The engine can also mask IBM z/OS data sets, described by a COBOL copybook, but the data must be EBCDIC (not ASCII or UTF-8). Where a record area can be read in several ways (COBOL REDEFINES), you give redefine conditions such as [CUST-TYPE]='P' so that exactly one reading applies per record. Operators are =, <, <=, >, >= with AND, OR and NOT. Mainframe formats list a variable-length checkbox in the rule set and can be reached over FTPS or other file modes. Masking a node that has Level 88 children is not supported .

9.25 File masking jobs

A file job uses the same + Masking Job wizard as in the algorithms and masking jobs chapter, with differences you will notice at once: there is no Database Options step (no commit size, update threads, triggers or constraints), and for files the Row Limit counts delimited or fixed-width lines, mainframe records or XML elements in process per stream . The choice that matters is the method.

In-Place

The engine reads the original file, masks each field, writes the result to a hidden temporary file ending .msk in the connector's location, and only after success writes it over the original. If anything fails, the original stays intact, and the user and group permissions stay the same.

On-The-Fly

Reads the source file and writes masked data straight to the target file, with no temporary file. The docs say it is significantly faster than in-place. Source and target use different connectors, so you create a separate environment and connector for the source.

For file-to-file jobs the target does not need to be a database. If your source is a database and the target a delimited file, tick Database to File Job as described earlier, make the target files in advance with the source table names, and expect binary data to be written as hex strings (the default hex prefix is \x) . If a file pattern matches nothing on the source, the job still reports success although no file was masked, so check the Execution Components for the file names. Monitoring and logs work as for databases; file jobs report Bytes Masked as well as Rows Masked, and the execution summary calls them Files rather than Tables.

9.28 Common mistakes and gotchas

Watch out for these
  • Uploading real data as a "format". Format files are schema only. A copy of last week's feed in the format dialog puts real values in the engine.
  • Forgetting that a format is shared. Editing fields or algorithm assignments for one file changes every file and rule set that uses the same format.
  • Wrong delimiter or end-of-record. The job may succeed while masking the wrong text. Open the output and look.
  • Header not declared. The header row is masked as if it were a customer.
  • Field count mismatch. Extra fields are silently dropped and missing ones are padded with delimiters.
  • Wrong fixed-width lengths. Every later field shifts. Count characters, not bytes.
  • File name pattern that matches nothing. The job can still end in success, so read the Execution Components.
  • Windows line endings in the format file. Use LF to avoid parsing failures.
  • Assuming UTF-16 or other encodings work. The docs list ASCII and UTF-8 (UTF-8 for Parquet, EBCDIC for mainframe).
  • Treating a masked file as safe without checking it. Run the verification commands and grep for known real values.

9.29 Recap

Key points
  • Files have no built-in column names, so a file format definition (schema only) maps positions or names to fields. Formats are global and shared.
  • Delimited files need a delimiter and end-of-record (and optionally an enclosure and escape strategy); fixed-width files need exact lengths.
  • Record types with up to three qualifiers handle mixed layouts; header and footer counts protect unmasked lines.
  • Connectors reach files by filesystem mount, SFTP, FTP or FTPS, S3, S3-compatible storage and Azure Blob; mainframe data needs EBCDIC and a copybook.
  • A file rule set lists files or patterns and gives each its format, end-of-record and delimiter; the inventory assigns algorithms to fields.
  • In-place file masking writes a hidden .msk file and replaces the original on success; on-the-fly writes to a separate target and is faster.
  • Always verify the output file: line counts, field counts, original values gone, unique fields still unique.

9.30 Words to know first

Masking engine
The Delphix Continuous Compliance engine, where you define connectors, rule sets, profiling jobs and masking jobs.
VDB (virtual database)
A full read-and-write copy of source data that Delphix Continuous Data provisions from a dSource or another VDB. To the masking engine it is another database. See the Delphix overview and terminology chapter.
Application and environment
An application is a tag for the real system (here ShopSphere). An environment groups connectors, rule sets and jobs; its purpose is Mask or Tokenize/Re-Identify.
Connector
Saved details the engine uses to reach one database or file location (connectors and VDB).
Rule set and inventory
A rule set lists the tables or files to profile or mask. Its inventory records, per column or field, the domain and algorithm (rule sets and keys).
Profiling job, domain
A profiling job assigns a domain (a kind of sensitive data such as FIRST_NAME, with one default algorithm) to columns that look sensitive (Delphix profiling).
In-place and on-the-fly
In-place masking updates data where it sits; on-the-fly reads a source and writes masked values to a target (algorithms and masking jobs).
Non-conformant data
A value that does not fit what an algorithm expects. By default it is left unmasked and the job records a warning, so a "successful" job can still leave data exposed.

9.35.1 Goal

Mask the customer files customers.dat (pipe-delimited) and customers_fixed.txt (fixed-width) with the file side of the engine. Files carry no built-in description of their columns, so this lab adds one step the database labs did not need: telling the engine what the fields are, with a file format.

9.35.2 Prerequisites and setup data

  • The two files from the setup section exist in a working folder, and the originals are copied to a separate original folder.
  • You know how the engine reaches that folder. The docs list the connection modes Filesystem Mount Point, SFTP, FTP, FTPS (mainframe datasets only), AWS S3, Other S3 Compatible Storage and Azure Blob Storage. A mount point also needs a mount created through the Mount Filesystem API before you can pick it in the connector (Managing remote mounts). The file concepts are in the file masking chapter.

  1. Set the algorithms in the inventory.

  2. customer_id and phone are identical to the original (they were out of scope).

9.36.1 Goal

What the FirstName algorithm does (from its docs page)

It is an instance of the Name framework and needs string input. Null, empty and whitespace-only values are returned unmasked, and it raises no non-conformant-data errors. A single character is treated as an abbreviation and masked to a single character. By default at most two names are masked and returned, and leading and trailing white space is not preserved. It is deterministic for the same configuration and key and it is not unique: collisions are possible, and a masked value can even equal the input (FirstName, Name framework). The Name framework page adds that its default comparison is case-insensitive, so "Peter" and "peter" mask to the same value.

Do not tick Disable Constraints, Drop Indexes or Disable Triggers: first_name is not a key. Number of Streams: 1. Save.

    The job's Checklist action repeats the identity-column check. Then choose Run in the actions menu. Take the VDB snapshot first.

  2. Watch the execution.

9.39 Common mistakes and gotchas

Mistakes that cost the most time
  • Masking a database you cannot restore. Cancelling a running in-place job leaves semi-masked data, the docs warn. Snapshot first.
  • Believing SUCCEEDED means "all masked". Non-conformant values are skipped by default; read the non-conforming-data line of the summary every time.
  • Running a rule set with leftover assignments. A job masks every assigned column in its rule set.
  • Letting the profiler overwrite your choice. Untick Enable Automatic Updates before assigning by hand.
  • Trusting a file format without checking the data. A wrong field count or length silently drops or shifts data, and editing a shared format changes every file that uses it.
  • Using a non-unique algorithm where uniqueness matters. Name and lookup-style algorithms can collide; Character Mapping is the documented unique-output family.
  • Keeping screenshots of unmasked rows. A screenshot of unmasked rows is itself a copy of sensitive data: capture counts and patterns, or mask first. The engine's non-conformant log shows only patterns (docs).

9.40 Recap

Recap
  • The labs form a chain: connector, rule set and profile, files, FirstName, then text, SSN and phone.
  • A "connector to a VDB" is an ordinary database connector pointed at a VDB, a safe place to mask.
  • Profiling proposes; the inventory is where you decide. Turn off automatic updates before overriding.
  • Files need a format file: field names for delimited, names and lengths for fixed-width.
  • Verify with before/after queries, not job status alone. Explain every warning before sign-off.
  • CM Digits and CM Alpha-Numeric keep format with unique text output; Phone US gives fake but plausible numbers; FirstName is realistic but not unique.
