1.1 Start here: what this guide covers and how to use it

Welcome. This guide takes you from "I have never heard of Test Data Management" to "I can sit in front of three real tools and use them". It is written for the 60-day programme whose syllabus you will find mapped chapter by chapter further down this page.

This first chapter is a map. It tells you who the guide is for, what the subject is, how every chapter is laid out, and how to pace yourself. Nothing here is hard. Read it once, bookmark the study plan, and move on to the why-TDM chapter.

1.1.1 Words to know first

Only a handful of terms are needed on this page. Each one is explained properly in the chapter named next to it.

Test data
The data you put into an application so you can check that it works. Think of the customers, orders and products you type in while testing an online shop. (the why-TDM chapter)
Production
The live system real customers use, holding real data. Also called "prod". (the why-TDM chapter)
Non-production environment
Any copy of the application that is not live: development, QA, UAT, staging. Testing happens here. (the why-TDM chapter)
TDM
Test Data Management: the planning, tools and habits used to give testers safe, realistic, right-sized data when they need it. (the why-TDM chapter)
Masking
Replacing real sensitive values (a real name, a real ID number) with realistic but fake ones. (the masking concepts chapter)
Subsetting
Taking a small, consistent slice of a big database instead of all of it. (the discovery and subsetting concepts chapter)
Synthetic data
Data created by a program from rules, not copied from real people. (the classification and generation concepts chapter)
Lab
A guided hands-on exercise inside a chapter, with a worked answer you can reveal.
Syllabus
The day-by-day list of topics in the programme. This guide does not change it; it only maps it to chapters.

1.1.3 What TDM is, in one paragraph

Test Data Management is the discipline of getting the right data to the people who test software, at the right time, without exposing anyone's private information. Testers need data that looks and behaves like real data. The easy way to get it is to copy the live database, but that copy contains real people's names, phone numbers and ID numbers, it is huge, and it goes stale. So TDM teams find the sensitive values (discovery), cut the data down to a usable size (subsetting), replace sensitive values with fake ones (masking), create brand-new data from rules where no real data fits (generation), and deliver fresh copies on request (provisioning). the why-TDM chapter explains each of these properly, starting from why testing needs data at all.

General concept

The Informatica documentation frames the same idea from the tool side: an organisation creates a smaller copy of production data, masks the sensitive data, finds the sensitive columns, and can create test data that never contained sensitive values (Informatica TDM 10.5.10 User Guide, p.21).

Why three tools and not one?

The tools are licensed products

Informatica TDM, GenRocket and Delphix are commercial software. You cannot download and run them on a laptop for free the way you can with a text editor. Whether you can click the buttons yourself depends on what your organisation provides: a training environment, a shared server, or nothing yet. That is why labs come in two flavours:

Thinking labs (no tool needed)

Work on paper or in a text file: reason about keys, design a masking plan, write a GenRocket-style model in a table. Every learner can do these, and they build the exact skill the tool labs need.

Tool labs (access needed)

Step-by-step instructions for the product screens, based on the documentation. Use them when you have access. Without access, read them as a rehearsal and compare with the screenshots linked from the vendor pages.

GenRocket material is from its help site as crawled for this guide. If your environment is a different version, expect small differences and trust the screen in front of you.

1.1.11 Common mistakes and gotchas

Skipping Part I and going straight to the tool

The tools use ordinary data ideas (keys, formats) and TDM ideas (masking, subsetting) as if you know them. Learners who skip Part I can click through a lab but cannot say why a job failed.

Memorising buttons

Button positions change between versions. Learn what each step is for, then find the button.

Treating this guide as the vendor manual

It is a study guide built from the vendors' public documentation. For a production project always read your product version's own documentation and follow your organisation's process.

Practising with real data

Even in a lab, do not use real customer files. Use the ShopSphere sample rows.

Reading without doing the labs

Reading feels like learning. Doing the work and comparing with the worked answer is learning. Take the labs seriously, even the thinking labs.

1.2.2 What software testing is, and why it needs data

Testing in brief

Imagine ShopSphere's developers have just changed how discounts are calculated. Before the change reaches real shoppers, someone has to check it. They log into a copy of the app, place an order, and look at the total. If the discount is wrong, they report a bug. That checking is software testing.

Testing is not a single activity. Teams run many kinds: a developer checks one function, a QA engineer clicks through a whole purchase, a performance tester sends thousands of orders at once, a business user confirms the app does what the business asked. They all share one need.

An application without data does nothing

An online shop with an empty database has no customers to log in, no products to buy, no orders to total. A test that says "check the discount for a returning customer" needs a returning customer to exist. So before the test starts, the environment must already contain:

  • customers with the right attributes (a returning customer, a new one, one with an expired card);
  • products with prices;
  • earlier orders for those customers, linked correctly to them.

That pre-loaded information is test data. It is as essential to a test as the code under test.

General concept
Why this matters

Bad test data produces two kinds of waste. Tests that should pass fail because the data is wrong (a false alarm that costs a developer an afternoon). Or tests pass when they should fail because the data never contained the tricky case (a bug reaches customers). Good data is not a luxury; it decides whether the test result can be trusted.

1.2.4 The naive approach: copy production

The quickest way to get realistic, consistent data is to take a backup of the production database and restore it into the test environment. It is what many teams do first, because it works on day one and needs no special tool. This is the production copy approach.

It feels right: the data is as real as data can be, and every relationship between tables is already correct. The problems appear later, and they are serious. Here are eight, each shown with ShopSphere.

Problem 1: privacy and security leaks

Production holds real names, phone numbers, ID numbers and dates of birth. A full copy puts all of that into environments where far more people have access: every developer, every tester, contractors, sometimes outside vendors. Non-production systems usually have weaker access controls, weaker monitoring and more people logged in.

ShopSphere example. The row for customer 1001 (Asha Menon, her email, her phone, her SSN) is now in the dev database, in the QA database, in the UAT database, in a test engineer's laptop dump, and in a screenshot attached to a bug report. Any one of those is a breach waiting to happen.

It is also often a legal problem. Laws and standards such as GDPR, HIPAA and PCI restrict how personal data can be used. The Delphix introduction names exactly these three (HIPAA, PCI and GDPR) as mandates organisations must stay compliant with, and notes that growing pressure from regulators and consumers makes protecting sensitive data across the enterprise essential (Introduction to Delphix Masking). From docs the sensitive data and regulations chapter explains the regulations.

Problem 2: huge size

Production databases grow for years. A full copy needs the same disk space as production, multiplied by the number of environments. Storage costs add up, and so does the time to move and back up the copies.

ShopSphere example. If production is 4 TB (invented for illustration), five test environments need 20 TB, and most of the content is orders from five years ago that no current test will ever read.

Problem 3: slow refreshes

Copying terabytes takes hours or days. Teams therefore refresh rarely, queue for the operations team, and sometimes freeze the data for weeks to avoid doing it again.

ShopSphere example. QA breaks the data while testing refunds. Restoring it takes two days. Everyone waits, or carries on with broken data and gets false test results.

Problem 4: stale data

A copy is a snapshot of one moment. The day after, production has moved on. New products, new account types and new features may be missing from the copy, so tests of the newest code run against data that does not contain it.

ShopSphere example. A "gift card" payment type launched last week. The copy taken last month has no orders that use it, so the gift-card tests find nothing to test.

Problem 5: missing edge cases

Real data contains the cases that happened. It does not contain the cases that have not happened yet, or have happened too rarely to be in your copy. Tests need values at the boundary: the largest allowed order, an empty field, a name with an apostrophe, a negative quantity that the app must reject.

ShopSphere example. Nobody in production has a 300-character last name, so no test checks that the screen handles one. The first customer who does crashes the checkout page.

This is where synthetic data comes in. GenRocket's help site defines synthetic test data as data manufactured by an algorithm rather than collected from real-world events, and says companies can maximise test coverage by using it to test all permutations and combinations (Why Synthetic Test Data?). From docs

Problem 6: broken relationships when people shrink or edit it

Realising the copy is too big, someone tries to cut it down by hand: "delete orders older than 2023". But orders are linked to customers and order items are linked to orders. Delete in the wrong order or the wrong rows and you leave order items pointing to orders that no longer exist, or orders for customers who have been removed. The application then crashes or gives nonsense, for reasons unrelated to the code being tested.

ShopSphere example. A script deletes customers who have not logged in since 2022. It forgets their rows in ORDERS. Now there are orders with a customer_id that matches nobody. The "my orders" page fails for the wrong reason.

The same breakage happens if someone replaces names with random text by hand and uses different replacements in different tables: the customer is "Asha" in one table and "Priya" in another. The data basics chapter explains the keys that tie tables together and why every TDM operation must respect them. The Informatica documentation describes the goal directly: a data subset keeps primary and foreign key relationships so that the data stays referentially intact (User Guide 10.5.10, p.23). From docs

Problem 7: cost

The costs are not only disk space. Add the time of people who run restores, the delay while testers wait, the licence and infrastructure cost of big environments, and the risk cost of a breach or regulator fine. None of it appears as a line "test data" on a budget, which is partly why the problem lingers.

Problem 8: no repeatability and no control

If every team makes its own copy at its own time, nobody knows which data version a bug was found on. Tests that passed Monday fail Tuesday because the data under them changed. Nobody can say who has a copy of what.

Worked example: one bug report, three failures

A ShopSphere tester finds that the "order history" screen shows an empty page for customer 1002 in the QA environment. She files a bug. The developer cannot reproduce it on his machine because his data is different. After a day of investigation they discover that the QA database was a partial manual copy in which customer 1002's orders were not copied. The bug is not in the code at all.

That one incident shows three problems from the list: broken relationships (problem 6), no control (8) and slow refresh (3: fixing it means a new copy). It also cost a day of two people's time. Multiply by a team and a year and the cost of unmanaged test data becomes visible.

1.2.5 So what is Test Data Management?

Test Data Management (TDM) is the set of processes, roles and tools that plan, create, protect, deliver and retire the data used in non-production environments. In simpler words: it is how you make sure the right testers get the right safe data at the right time, without copying production carelessly.

General concept

Some people use "TDM" for the software and some for the practice. In this guide "TDM" is the practice, and "a TDM tool" is software that supports it.

Goals of TDM

  1. Protect people. No real sensitive data in non-production.
  2. Fit the test. Data that is realistic, consistent and covers the cases the tests need.
  3. Right size. Smaller than production where possible, large only where tests need it.
  4. Be fast. Data on request, refreshed in minutes or hours, not weeks.
  5. Be repeatable and traceable. Known data versions, known owners, known copies.
  6. Lower cost. Less storage, less waiting, less rework, lower breach risk.

1.2.6 The six capabilities of TDM

TDM splits into six capabilities. A project may use all six or only a few. The first four change the data; the last two deliver and control it.

1. Discover

You cannot protect what you cannot find. Discovery means scanning a database or a set of files to locate sensitive data: which columns hold names, ID numbers, phone numbers. Large databases can have thousands of columns, and sensitive values hide in odd places such as a "notes" column. Discovery also finds the relationships between tables, which later steps need.

Why it matters: if discovery misses a column, that column goes into test unmasked.

ShopSphere: discovery flags ssn, phone, email, date_of_birth and tax_id in CUSTOMERS. The discovery and subsetting concepts chapter teaches this in depth.

2. Subset

Subsetting builds a smaller database from a big one: for example "only customers from the last two years, and everything linked to them". Done properly, every order in the subset still has its customer and its items. Smaller means cheaper, faster to load and easier to refresh.

ShopSphere: pick 5,000 customers and bring their orders and items along, leaving the other millions of rows behind. The discovery and subsetting concepts chapter covers it; the Informatica data subset chapter shows it in Informatica.

3. Mask

Masking replaces sensitive values with realistic but fake ones. The application still works because the fake values look right (a fake phone has ten digits), but nobody can learn about a real person from them. Good masking is consistent: the same real value always becomes the same fake value, so relationships between tables survive.

The Delphix documentation describes masking as replacing confidential information such as social security numbers, patient records and card numbers with fictitious yet realistic data, and contrasts it with encryption: masking is irreversible, while encryption can be undone by someone who obtains the credentials (Introduction to Delphix Masking). From docs

ShopSphere: Asha Menon, 9876543210, 123-45-6789 becomes, say, a made-up name, a made-up ten-digit number and a made-up SSN pattern. The masking concepts chapter teaches the techniques.

4. Generate

Generation creates data from rules instead of copying real data. You describe what you need ("fifty customers, each with a first name, a last name, a phone number") and a tool produces it. Informatica's documentation gives the second reason almost word for word: use data generation when you need test data but do not want to use production data, for example when test teams handle sensitive data and have no access to production (User Guide 10.5.10, p.23). From docs

ShopSphere: generate a customer whose name is 300 characters long. The classification and generation concepts chapter covers the idea; Part III is GenRocket, a tool built around it.

5. Provision and refresh

Provisioning means delivering a ready dataset into an environment: loading it into the QA database, or placing a file where a test tool expects it. Refreshing means doing it again later to get new or reset data. Speed and repeatability matter most here.

Both Informatica and Delphix address this in their own way. Informatica describes a test data warehouse that stores multiple versions of test data and can restore a version to put an environment back into a particular state (User Guide 10.5.10, p.23). Delphix describes virtual copies that are readable and writable, can be created or removed in minutes, and take a fraction of the storage of physical copies; in its example ten virtual copies fit in the space of one physical copy (Introduction to Delphix Masking). From docs

6. Govern

Governance is the rules and records around the other five: who may request what, which data is approved for which environment, which masking rules are in force, an audit trail of who received which dataset. It is the least glamorous capability and the first one auditors ask about.

Delphix says the platform lets operators audit, monitor and report against access and usage, and generates reports and email notifications confirming sensitive data has been masked. Informatica's administrator manages roles and privileges that decide what each TDM user can do (User Guide 10.5.10, p.23). From docs

Why the six are separate ideas

Beginners often use "masking" to mean everything. It is only one of six. A team that masks but never subsets still has a huge, slow copy. A team that subsets but never discovers may mask the wrong columns. Learn the six as separate tools in a toolbox, then pick the ones a project needs.

1.2.10 Real-world scenarios at ShopSphere

Three short stories, each choosing a different mix of the six capabilities.

Scenario 1: weekly QA refresh

Situation. QA tests every Monday and needs realistic data, but production holds real customers.

Approach. Each Friday night a job reads production, picks the last 12 months of customers and their orders (subset), replaces names, emails, phones, SSNs and dates of birth with fake but consistent values (mask), and loads the result into QA (provision). Discovery was done once, and its results are re-checked when the schema changes.

Outcome. QA gets fresh, safe, small data every Monday without anyone touching production data by hand.

Scenario 2: a new loyalty-points feature

Situation. ShopSphere adds loyalty points. No production data has points yet.

Approach. Nothing to copy, so the team generates 10,000 customers with random point balances, including zero, the maximum and a negative balance that the app must reject.

Outcome. The feature is tested before launch, including the edge cases, with no personal data involved.

Scenario 3: performance test before the holiday sale

Situation. The company expects ten times normal traffic and needs 50 million orders in the performance environment.

Approach. Real production does not have that many. The TDM engineer generates the volume, and masks a real sample so that distributions (how many items per order, typical prices) match the real shape.

Outcome. The load test runs at realistic scale, safely.

1.2.11 Benefits and trade-offs

Benefits

  • Lower privacy and compliance risk.
  • Faster test cycles because data is ready.
  • Smaller storage and infrastructure cost.
  • Better test coverage through generated edge cases.
  • Repeatable tests on known data.
  • Fewer false bug reports from bad data.

Trade-offs and costs

  • Set-up effort: discovery, rules and approvals take time up front.
  • Licence and infrastructure cost for commercial tools.
  • Masked data is never exactly real data; some production-only bugs may not reproduce.
  • Generated data is only as good as its rules; it can miss real-world quirks you did not think of.
  • New skills and a new process for the team to learn.
  • Ongoing upkeep as the schema and the regulations change.
General concept
Masked and generated data compared

Masking starts from real data and hides the identifying parts, so it keeps real-world shape and messiness. Generation starts from rules, so it is safe by construction and covers cases you design, but only the cases you thought of. Many teams use both: masked data for realism, generated data for edge cases and volume. the classification and generation concepts chapter compares them in detail.

1.2.14 Common mistakes and gotchas

"We mask it, so it is safe"

Masking only protects the columns you masked. If discovery missed a column, or a free-text "notes" field contains names, sensitive data survives. Discovery and verification matter as much as the masking itself.

Treating TDM as a one-off project

Production changes every day: new columns, new data, new rules. A TDM set-up that is never maintained goes stale just like a copied database.

Using one technique for everything

Masking is not always right. If no real data exists for the case, or real data cannot be used at all, generate. If the problem is only size or speed, subset or virtualise.

Ignoring relationships

Any change to the data (subset, mask, generate) must keep related tables consistent. The data basics chapter explains how; skipping it leads to the "orders with no customer" bug.

Believing tool names are the concepts

"Plan", "rule set", "scenario" and "domain" mean different things in different products. Learn the concept, then learn each tool's word for it.

1.3.4 Keys and relationships

A single table is easy. Real applications split data across many tables and connect them. Keys are the connectors. This section is the most important in the whole chapter.

Why data is split into several tables

Imagine ShopSphere stored everything in one big sheet: one row per ordered item, with the customer's name, phone and address repeated on every row. Customer Asha has two orders with three items in total, so her phone number would be typed three times. If she changes her phone number you must update every copy, and if you miss one the data disagrees with itself.

The fix is to store each fact once, in the table where it belongs, and refer to it from elsewhere. Customer facts live in CUSTOMERS. An order stores only the customer's ID, not the name and phone. To get the name, you look the ID up. The ID is a key.

General concept

Primary key

A primary key is a column (or a small group of columns) whose value is unique in every row and is never empty (null). It is the row's identity, like a library card number or a passport number.

  • CUSTOMERS.customer_id: 1001, 1002, 1003. No two customers share an ID.
  • ORDERS.order_id, ORDER_ITEMS.item_id and PRODUCTS.product_code are the primary keys of their tables.

A database enforces this: it refuses to insert a second customer with ID 1001.

Why not use the name as the key? Two customers can share a name; names change; spellings vary. A key must be stable and unique. That is why tables carry an artificial ID such as customer_id. (Keys made up of real-world data, like an email address, are called natural keys; made-up IDs are surrogate keys. Both appear in the real world.)

A key can have more than one column. Suppose a table ORDER_ITEM_NOTES allowed one note per item per language; then (item_id, language) together would be unique, though neither alone is. That is a composite key.

Foreign key

A foreign key is a column in one table whose values must match the primary key of another table. It is the link.

  • ORDERS.customer_id is a foreign key to CUSTOMERS.customer_id: it says which customer placed the order.
  • ORDER_ITEMS.order_id is a foreign key to ORDERS.order_id: it says which order this line belongs to.
  • ORDER_ITEMS.product_code is a foreign key to PRODUCTS.product_code: it says which product was bought.

The foreign key column is allowed to repeat. Customer 1001 can appear in many order rows, because Asha can place many orders. The primary key side cannot repeat.

Parent and child tables, one-to-many

The table that holds the primary key is the parent; the table with the foreign key pointing at it is the child. One customer (parent) can have many orders (children), and one order can have many items. That shape is called one-to-many.

Referential integrity

Referential integrity is the rule that every foreign key value must match a primary key value that exists. Every order must belong to a customer who exists; every item to an order that exists.

A child row whose parent is missing is called an orphan. Suppose someone deletes customer 1001 but leaves orders 5001 and 5002. Those orders now point to nobody. The "my orders" page crashes. When the database has the foreign key declared, it refuses such a delete, and it refuses to insert an order for a customer ID that does not exist. (When I tried this in SQLite with foreign key enforcement switched on, both attempts were rejected with a foreign key constraint error.)

Why keys matter so much to TDM

Every TDM operation reshapes data. Each one can break referential integrity if done carelessly.

Logical keys: keys the database does not know about

Everything above assumed the keys are declared in the database. In real life they often are not. Older systems, performance-minded designs and imported data frequently have tables with no declared primary or foreign keys at all, even though the application treats certain columns as keys. The relationships exist in the developers' heads and in the code, not in the schema.

TDM tools cannot follow a relationship they do not know about. So they let you (or their profilers) describe the relationships separately. Keys defined this way are called logical keys in this guide: the tool is told "treat this column as the key" without any change to the real database.

If you declare a column as a key but it is not actually unique, masking or subsetting will misbehave. A logical key must be unique and never null for every row, exactly like a real primary key. 1.3.5 Flat files

Not all test data lives in databases. Banks, insurers and retailers exchange huge amounts of data as files: one system writes a file overnight, another reads it in the morning. The syllabus includes masking "files (txt, dat)" (Day 53), so you need to read them comfortably.

A flat file is a file holding records as lines of text. "Flat" means there is no table engine, no keys, no data types: it is just text in a layout that both sides agree on. All the structure lives in the agreement, not in the file.

General concept

.txt, .dat, .csv: what the extension tells you (little)

A file extension is only a label. .txt says "text", .csv says "comma-separated values", .dat says "data". None of them tells you how the records are laid out. A .dat file can be comma-separated, pipe-separated, fixed-width or something else; a .txt file can hold any of those too. You find the layout from the file specification (a document from the team that produces the file), or by opening the file and looking.

Why this matters

A tool that masks files has to be told the layout, because the file itself does not say. The Delphix documentation puts it directly: unlike databases, files typically have no built-in metadata describing the format of their fields, so you must provide that information (Managing file formats). From docs

Records, fields, headers and footers

  • A record is one line (one customer, one order), ending with an end-of-record marker, usually a line break.
  • A field is one value within the record.
  • A header is a record at the top that is not data: often the column names, or a label with a date.
  • A footer (or trailer) is a record at the end, often a count or a total so the reader can check nothing was lost.

Delimited files

In a delimited file a special character, the delimiter, separates the fields. The most famous is the comma, giving the CSV (comma-separated values) format. Pipes (|), tabs and semicolons are also common, especially when data itself contains commas.

Here is a ShopSphere customer file in CSV with a header row. All values are fake:

Fixed-width and masking

If you mask a name in a fixed-width file and the new name is longer than the field, it either overflows into the next field (corrupting the record) or is cut off. Masked values must fit the field. More detail for Delphix is in the Delphix file masking chapter.

Line endings

The end of a record is marked by invisible characters that differ by platform. Windows traditionally uses two characters (carriage return then line feed, often written CR+LF); Linux uses one (line feed, LF). If a tool assumes the wrong one, records are read wrongly or every line gets an odd extra character. Delphix asks you to choose the end-of-record, Windows/DOS (CR+LF) or Linux (LF), when you assign a file format, and to enter the delimiter for a delimited file (Managing file formats). Encodings: how text becomes bytes

Computers store characters as numbers; an encoding is the agreed table. Two matter to you:

  • ASCII: an old, small table with 128 characters: English letters, digits, punctuation. One byte per character.
  • UTF-8: a modern encoding that can represent essentially every writing system, including Tamil, Hindi, Chinese and emoji. It is ASCII-compatible: plain English text looks identical, but other characters take two, three or four bytes.

This causes two classic problems.

  1. Garbled text. A file written in one encoding and read as another turns "Müller" into something like "MÃ¼ller". The data is not lost; it was read with the wrong table.
  2. Fixed-width surprises. If a layout counts bytes but a name has an accented letter, "Müller" is 7 bytes in UTF-8 though it is 6 characters. The field after it shifts by one. Always ask whether widths are in bytes or characters.

From docs Note that a WHERE on one table does not by itself bring along the related rows of other tables; keys do that, which is why subsetting is more than a filter.

JOIN: combine tables through keys

A join follows a foreign key. Here, each order is matched to its customer by customer_id:

FROM customers c
JOIN orders o ON o.customer_id = c.customer_id;

FROM customers c

SELECT c.last_name, p.product_name, i.quantity
FROM order_items i
JOIN orders o    ON o.order_id = i.order_id
JOIN customers c ON c.customer_id = o.customer_id
JOIN products p  ON p.product_code = i.product_code
ORDER BY i.item_id;

The result has four rows: Menon with Wireless Mouse (1), Menon with USB-C Cable (1), Menon with Laptop Stand (1) and Kumar with USB-C Cable (2). A subsetting tool does something like this walk in reverse: start from the customers you chose and follow the keys out to every related row.

COUNT: how many?

SELECT COUNT(*) AS customer_count FROM customers;

Returns 3. With GROUP BY you can count per group:

SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id;

Returns 1001 with 2 orders and 1002 with 1 order. TDM people use COUNT constantly: how many rows before and after a subset? Does the masked table have as many rows as the source? Does the number of distinct values in a candidate key equal the number of rows? (COUNT(DISTINCT customer_id) counts the unique values.)

INSERT and UPDATE: change data

INSERT INTO customers (...) VALUES (...) adds a row (the lab below has full examples); the column list and value list must line up. If you inserted an order with customer_id 9999 when no such customer exists, a database that enforces the foreign key rejects it.

UPDATE customers
SET zip_code = '560002'
WHERE customer_id = 1001;

After the UPDATE, a SELECT for customer 1001 returns zip_code 560002. Never write UPDATE without a WHERE unless you really mean to change every row: the statement above, without its last line, would give all three customers the same postal code.

Masking is, at its core, a very large controlled UPDATE: replace the value in a sensitive column in every row (with a consistent rule). Delphix's in-place masking updates the source table; a copy-style approach writes to a different target. The tool generates the SQL for you, but understanding that it is an UPDATE explains why a table with no key is a problem: the tool needs a way to say "this exact row". Delphix's documentation says the custom SQL for a table must include the primary key column(s) and the columns to be masked (Managing rule sets). From docs

1.3.7 Data volumes and why size matters

ShopSphere's sample tables hold ten rows between them. The real database holds millions of customers and tens of millions of orders. Size changes everything about TDM.

Sizes run from KB (a short text file) through MB (a CSV of tens of thousands of customers) and GB (a small production database) to TB (a large enterprise database).

Why size matters to a TDM engineer:

  • Time. Masking updates every row of every sensitive column. Ten times the rows is roughly ten times the work unless you add parallelism. Delphix profile jobs have a setting for the number of parallel streams, for example two streams to run two tables of a rule set at once (Delphix masking terminology). From docs
  • Storage. Every environment that holds a full copy multiplies the cost. See the why-TDM chapter.
  • Memory and file limits. A file of many gigabytes cannot be opened in a spreadsheet; you work on it with tools or by sampling.
  • Test fitness. Performance tests need volume; functional tests do not. Matching size to purpose is part of the job.
  • Row count versus width. A table with a hundred million narrow rows and a table with a million rows of large documents behave very differently. Ask for both numbers.
General concept
Always ask for counts first

Before any TDM job, ask for the row count of each table. It tells you whether a subset is needed, how long a job should take, and gives you a number to verify afterwards (row counts before and after should reconcile with what you expect).

1.3.9 Common mistakes and gotchas

Treating a column as unique because the sample looks unique

Three rows with distinct emails do not prove emails are unique across three million rows. Test with counts of all rows against counts of distinct values.

Assuming the database enforces the keys

Many databases, especially older ones and data warehouses, have no declared foreign keys. Relationships exist only by convention. That is why profiling for keys and logical keys exist.

Masking keys inconsistently

If a key is masked in one table and not in its child tables (or masked differently), relationships break. Mask keys the same way everywhere, or leave them alone.

Uploading real data to define a format

A layout needs only structure. Delphix says not to upload production data, sample records or PII when defining file formats (Managing file formats). From docs

1.3.10 Recap

Recap
  • A database holds tables; a table has rows (records) and columns (fields) with data types. Metadata and schema describe the data without containing it.
  • A primary key uniquely identifies a row; a foreign key in a child table points at a parent's primary key; together they give one-to-many relationships.
  • Referential integrity means every foreign key matches an existing parent. Subsetting, masking and generation must all preserve it.
  • Logical keys are keys declared to the tool when the database does not declare them. Informatica and Delphix both support them.
  • Flat files have no built-in schema: know the layout (delimited or fixed-width), header and footer records, record types, line endings and encoding.
  • XML and JSON nest children inside parents instead of using foreign keys.
  • SELECT, WHERE, JOIN, COUNT, INSERT and UPDATE cover most of the SQL you will read. The orphan check (LEFT JOIN where the parent is null) is a TDM staple.
  • Size drives time, cost and test fitness: ask for row counts first.

1.4.1 Words to know first

Sensitive data
Any data that could hurt a person or a company if it leaked or was misused: identity details, health records, payment details, passwords, trade secrets. "Sensitive" is a business and legal judgement, not just a technical one.
PII (Personally Identifiable Information)
Data that identifies a person, alone or combined with other data. Examples: name, email, phone number, a government ID number, a home address.
PHI (Protected Health Information)
Health-related data that can be tied to a person: diagnoses, treatments, medical record numbers, insurance member IDs. Informatica describes its PHI pack as aimed at the healthcare and pharmaceutical industries (User Guide 10.5.10, p.79).
PCI (Payment Card Industry) data
Payment card details such as the card number and expiry date. Informatica describes its PCI pack as aimed at banking and finance (User Guide 10.5.10, p.80).
Identifier
A piece of data that points to one person. A direct identifier does it on its own (an SSN). An indirect identifier (also called a quasi-identifier) only does it when combined with others (zip code plus birth date).
Re-identification
Working out who a "nameless" record belongs to by combining it with other information.
Data classification
Sorting data into sensitivity levels (for example public, internal, confidential, restricted) so each level gets the right protection.
Data domain
A named kind of data, such as "Social Security number" or "First name", described by how the data looks and what its column is usually called. Both Informatica and Delphix use this word, with slightly different meanings.
Rule
In Informatica, the logic that changes a value: a masking rule uses a masking technique (such as substitution) with chosen settings. Rules are covered in the masking concepts chapter.
Policy
In TDM, a named bundle that says which kinds of data are sensitive and how to protect each kind. Section 1.4.8 shows the exact Informatica structure.
Data steward
The person who knows a data set's meaning and quality and answers questions such as "what is in this column and who may see it?".
Compliance officer
The person responsible for making sure the organisation follows laws and internal rules about data.

1.4.3 The three families: PII, PHI and PCI

People in TDM talk in three abbreviations. They overlap, and a single column can belong to more than one family, but each one points at a different law or standard and a different industry.

PII: personally identifiable information

General concept PII is data that identifies a person. The definition differs a little between countries and laws, but the everyday list is stable:

  • Names, email addresses, phone numbers, postal addresses.
  • Government-issued numbers: SSN (US), passport number, driver's licence number, national ID. India's Aadhaar and PAN are comparable examples.
  • Date of birth, age, gender, place of birth.
  • Online identifiers such as IP addresses.

ShopSphere's CUSTOMERS table is almost pure PII: first_name, last_name, email, phone, ssn, date_of_birth, zip_code and tax_id.

General concept PCI refers to the Payment Card Industry. The PCI DSS (Data Security Standard) is a rulebook created by the card brands for anyone who stores, processes or sends card data. In TDM talk, "PCI data" means card number, card expiry date, security code, cardholder name.

When you need card numbers for testing, use numbers designed for testing (payment providers publish "test card numbers") or let a generator or masking tool make numbers that pass the format check but belong to no account.

1.4.4 Direct and indirect identifiers: why "just remove the names" fails

A common beginner idea is: "We will delete the name column and then the data is anonymous." It is not, and understanding why is the most important privacy idea in this section.

Two kinds of identifier

Direct identifiers

Point to one person by themselves.

  • Full name (mostly)
  • SSN, passport number
  • Email address, phone number
  • Card number

Removing or replacing these is the obvious first step.

Indirect identifiers (quasi-identifiers)

Harmless alone, identifying in combination.

  • Zip or postal code
  • Date of birth
  • Gender
  • Job title, employer
  • Rare product or rare diagnosis

Easy to forget, which is why they cause leaks.

General concept Research on public records, most famously by the computer scientist Latanya Sweeney, has found that a large share of people in the United States can be singled out from just three facts: zip code, full date of birth and gender. The exact percentage depends on the data set and the year, so do not quote a number from this guide. Remember the shape of the result: three boring columns, one unique person.

Protecting a data set means looking at combinations. It is why the PII and PHI packs both include Birth Date, ZIP and State, not only names and ID numbers. It is also why masking techniques that move a date a little or blur a number (see the masking concepts chapter) exist: they weaken the combination while keeping the data useful for testing.

Free text is the other hiding place

Informatica's data domain page notes that a Social Security number might sit in an SSN column, in a column called SOCIAL_SECURITY in another table, and also inside a COMMENTS column (User Guide 10.5.10, p.73). From docs A support agent typing "customer 123-45-6789 called about refund" into a notes field has just put an SSN where no column name will ever warn you. Delphix's Free Text Redaction algorithm exists for exactly this problem (the masking concepts chapter explains it).

1.4.5 Privacy laws and standards in plain words

This is not legal advice

Everything in this section is a plain-language orientation General concept, written so you can follow a meeting and ask good questions. Laws change, have exceptions, and apply differently depending on where your company and your customers are. Treat every statement here as "roughly true, check with legal". The tool documentation does not teach law, so none of this comes from the tool sources, except where marked.

Why should a tester care about laws? Because when a court or regulator looks at a data leak, they do not ask "was it production or test?". They ask "was personal data properly protected?". A copy in a test database is still personal data.

GDPR in plain words

General concept The GDPR (General Data Protection Regulation) is a European Union law that has applied since May 2018.

  • What it protects: "personal data", meaning any information about an identifiable person. That is broader than a name and number: online identifiers and location data can count.
  • Who it applies to: organisations that handle the personal data of people in the EU, even if the organisation sits outside Europe. A ShopSphere with customers in Germany would be in scope no matter where its servers are.
  • Ideas behind it: there must be a lawful reason to use the data (consent is one such reason); use it only for the purpose it was collected for; collect and keep no more than needed ("data minimisation"); keep it secure; let people see and delete their data.
  • Fines at a high level: the most serious breaches can lead to fines of up to 20 million euros or 4 percent of worldwide yearly turnover, whichever is higher. Lesser breaches have a lower ceiling.

The consequence for test data. Two GDPR ideas hit TDM directly. First, purpose: a customer who gave details so ShopSphere could deliver an order did not necessarily agree to have them copied into a test lab. Second, minimisation and security: copying a whole production database to a loosely guarded test server is hard to justify when a small, masked copy would do. The law also treats truly anonymous data (nobody can be identified any more) as outside its scope, which is one reason masking and subsetting are popular. Whether a particular masked data set counts as anonymous is a question for your compliance officer.

HIPAA in plain words

General concept HIPAA is a United States law from 1996 that, through its Privacy and Security Rules, protects health information.

  • What it protects: PHI, health information that identifies a person (section 1.4.3).
  • Who it applies to: "covered entities" (health plans, healthcare providers, healthcare clearinghouses) and their "business associates", meaning vendors who handle PHI for them. A software company testing a hospital's billing system is typically a business associate.
  • Minimum necessary: people and systems should receive only the least PHI they need for their job. Testers rarely need the real thing.
  • De-identification: HIPAA describes two accepted ways to de-identify health data so it is no longer treated as PHI. One removes a defined list of 18 kinds of identifiers (names, detailed locations, most date elements except the year, phone numbers, record numbers and so on). The other has a qualified expert certify that the risk of identifying anyone is very small. This is why Delphix has a domain called HIPAA_DATE and why dates and ZIP codes feature so heavily in PHI discussions.
  • Penalties at a high level: civil penalties in tiers depending on how careless the organisation was, and criminal penalties for knowing misuse.

From docs Both tools mention these regimes only briefly. Delphix's introduction lists HIPAA, PCI and GDPR as examples of mandates organisations must stay compliant with, and Informatica packages its PHI and PCI policy packs for healthcare and banking respectively (User Guide 10.5.10, pp.79 to 80). GenRocket's column-profiling page says that identifying PII early helps organisations meet requirements "such as HIPAA".

What Informatica does: data patterns and metadata patterns

From docs Informatica describes a data domain using regular expressions. A regular expression (regex) is a compact text recipe for a pattern, for example "three digits, a hyphen, two digits, a hyphen, four digits". The guide separates two kinds (User Guide 10.5.10, pp.74 to 75):

  • A data pattern matches the values. Its example for Social Security numbers is [0-9]{3}-[0-9]{2}-[0-9]{4}.
  • A metadata pattern matches column names. Its examples for Social Security numbers are .*SSN*, .*SOCIAL* and .*SECURITY*.

A column joins the data domain if it matches any expression in the domain. When you run a data domain profile you choose to search the data only, the column name only, or both, how many rows to read (default 1,000) and a minimum conformance percent, since not every row has to match the pattern (pp.95 and 100). One real example: how Delphix recognises an SSN

The ASDD Standard listing (Delphix "ASDD standard profile set", source page ↗) shows the SSN domain is defined by three classifiers. In our words:

  1. A PATH classifier.

    A regex on the column path catches names like ssn or social security number with variants such as social_security_no. Its match strength is listed as 0.67.

  2. A REGEX classifier on the data.

    Patterns for the nine-digit format. The dashed or spaced form (123-45-6789) is listed with match strength 0.7, while nine bare digits are listed with only 0.1.

    The lower number for bare digits fits the idea in the weaknesses table above: nine digits in a row are far more likely to be something other than an SSN.

  3. A TYPE classifier.

    The column must be a Number or String of at least 9 characters. This rejects tiny columns.

The excerpt I had does not explain how the strengths are combined into a final decision, so read the product page for your version before relying on the numbers. What matters for a beginner is the design: several weak clues, each with a weight, are combined to decide.

What GenRocket does: column names only

From docs GenRocket's "Data Column Profiling" scans column headers, not the data. 1.4.8 Policies, rules and data domains

Now the vocabulary promised at the start. A TDM tool needs one place that records the answer to "what is sensitive here, and how do we protect each kind?". Informatica calls that place a policy. The structure is worth learning exactly, because it explains many menus you will see later. From docs (User Guide 10.5.10, p.71)

What each piece is

Policy (Informatica)
"A data masking component that describes the methods to maintain the privacy of specific types of source data". It contains data domains. You assign a policy to a data source in a project, and one policy can serve several projects (p.71).
Data domain (Informatica)
Describes the functional meaning of a column based on its data or its name. It carries data patterns, metadata patterns, a sensitivity level, a status (enabled or disabled) and, optionally, preferred masking and generation rules (pp.73 to 75).
Rule (Informatica)
"A logic to mask sensitive data or to generate test data": a technique plus its parameters. Rules exist for string, numeric and date data (p.72).
Preferred rule and default rule
When you attach several rules to a domain they are "preferred rules", and one is the default, applied to all columns in the domain unless you pick another. The guide's example: a Last_Name domain with a shuffle rule as default and a substitution rule as another preferred rule (p.73).
Policy pack
A ready-made policy shipped with TDM. There are three: PII, PHI and PCI, visible after installation (p.77).

The order of work does not matter. The guide says you can create policies, rules and domains in any order, then connect them: create masking rules, define domains, assign rules to domains, create a policy, assign domains to it (p.72). From docs

Common mistakes and gotchas

Mistakes beginners make
  • "We removed the names, so it is anonymous." Birth date plus zip plus gender can identify people (section 1.4.4).
  • Trusting automatic discovery. It gives candidates. Review them, and add what it misses.
  • Forgetting free-text columns. Notes, comments and descriptions can hold names and ID numbers that no column name reveals.
  • Ticking "sensitive" and stopping. In Informatica the flag is only a label. A masking rule must still be assigned (p.89).
  • Assuming a law's definition fits every country. Ask your compliance officer which regimes apply to your data subjects.
  • Mixing up Delphix "rule set" with Informatica "rule".
  • Treating PCI as a law. It is an industry standard, enforced through payment contracts.
  • Copying documentation sample values into tests. Samples like card numbers can be real by accident.

Recap

Remember
  • Sensitive data is whatever could harm a person or the company if leaked. PII identifies people, PHI ties health facts to a person, PCI covers payment card data.
  • Direct identifiers point to one person. Indirect identifiers (zip, birth date, gender) identify when combined, so deleting names is not enough.
  • GDPR and HIPAA, in plain words, say: have a lawful purpose, use the minimum necessary, secure it, and de-identify where you can. This is the legal case for subsetting and masking. This guide is not legal advice.
  • Classification gives each column a sensitivity level, and each level maps to an action.
  • Tools find sensitive columns by column names, data patterns and value lists, plus type checks. The output is candidates for human review.
  • An Informatica policy contains data domains. A domain holds patterns, a sensitivity level and preferred rules. A rule is a technique plus parameters. Delphix uses domains, classifiers, profile sets and algorithm instances for the same ideas.
  • People decide: the compliance officer sets what is sensitive, the data steward explains the data, the TDM engineer builds and runs the policy.
