1.2 What TDM is, in one paragraph

Test Data Management is the discipline of getting the right data to the people who test software, at the right time, without exposing anyone's private information. Testers need data that looks and behaves like real data. The easy way to get it is to copy the live database, but that copy contains real people's names, phone numbers and ID numbers, it is huge, and it goes stale. So TDM teams find the sensitive values (discovery), cut the data down to a usable size (subsetting), replace sensitive values with fake ones (masking), create brand-new data from rules where no real data fits (generation), and deliver fresh copies on request (provisioning). the why-TDM chapter explains each of these properly, starting from why testing needs data at all.

The Informatica documentation frames the same idea from the tool side: an organisation creates a smaller copy of production data, masks the sensitive data, finds the sensitive columns, and can create test data that never contained sensitive values (Informatica TDM 10.5.10 User Guide, p.21).

1.6 What software testing is, and why it needs data

1.6.1 Testing in brief

Imagine ShopSphere's developers have just changed how discounts are calculated. Before the change reaches real shoppers, someone has to check it. They log into a copy of the app, place an order, and look at the total. If the discount is wrong, they report a bug. That checking is software testing.

Testing is not a single activity. Teams run many kinds: a developer checks one function, a QA engineer clicks through a whole purchase, a performance tester sends thousands of orders at once, a business user confirms the app does what the business asked. They all share one need.

1.6.2 An application without data does nothing

An online shop with an empty database has no customers to log in, no products to buy, no orders to total. A test that says "check the discount for a returning customer" needs a returning customer to exist. So before the test starts, the environment must already contain:

  • customers with the right attributes (a returning customer, a new one, one with an expired card);
  • products with prices;
  • earlier orders for those customers, linked correctly to them.

That pre-loaded information is test data. It is as essential to a test as the code under test.

Why this matters

Bad test data produces two kinds of waste. Tests that should pass fail because the data is wrong (a false alarm that costs a developer an afternoon). Or tests pass when they should fail because the data never contained the tricky case (a bug reaches customers). Good data is not a luxury; it decides whether the test result can be trusted.

Testers usually want data that is:

1.7.1 Who needs data, and when?

In ShopSphere, a single sprint can ask for data in several ways at once:

  • A developer fixing a rounding bug needs one customer with a specific order total.
  • A QA engineer testing refunds needs hundreds of orders in different states (paid, shipped, returned).
  • A performance tester needs millions of orders to see whether the site slows down.
  • A business analyst in UAT needs data that "looks like our real customers" so they can judge whether a screen makes sense.
  • An automation engineer needs the same data every night so the automated tests are repeatable.

Five people, five different requirements. If nobody manages this, each one solves it alone, usually in the least safe way. That is the next section.

1.8 The naive approach: copy production

The quickest way to get realistic, consistent data is to take a backup of the production database and restore it into the test environment. It is what many teams do first, because it works on day one and needs no special tool. This is the production copy approach.

It feels right: the data is as real as data can be, and every relationship between tables is already correct. The problems appear later, and they are serious. Here are eight, each shown with ShopSphere.

1.8.1 Problem 1: privacy and security leaks

Production holds real names, phone numbers, ID numbers and dates of birth. A full copy puts all of that into environments where far more people have access: every developer, every tester, contractors, sometimes outside vendors. Non-production systems usually have weaker access controls, weaker monitoring and more people logged in.

ShopSphere example. The row for customer 1001 (Asha Menon, her email, her phone, her SSN) is now in the dev database, in the QA database, in the UAT database, in a test engineer's laptop dump, and in a screenshot attached to a bug report. Any one of those is a breach waiting to happen.

It is also often a legal problem. Laws and standards such as GDPR, HIPAA and PCI restrict how personal data can be used. The Delphix introduction names exactly these three (HIPAA, PCI and GDPR) as mandates organisations must stay compliant with, and notes that growing pressure from regulators and consumers makes protecting sensitive data across the enterprise essential (Introduction to Delphix Masking). the sensitive data and regulations chapter explains the regulations.

1.8.2 Problem 2: huge size

Production databases grow for years. A full copy needs the same disk space as production, multiplied by the number of environments. Storage costs add up, and so does the time to move and back up the copies.

ShopSphere example. If production is 4 TB (invented for illustration), five test environments need 20 TB, and most of the content is orders from five years ago that no current test will ever read.

1.8.3 Problem 3: slow refreshes

Copying terabytes takes hours or days. Teams therefore refresh rarely, queue for the operations team, and sometimes freeze the data for weeks to avoid doing it again.

ShopSphere example. QA breaks the data while testing refunds. Restoring it takes two days. Everyone waits, or carries on with broken data and gets false test results.

1.8.4 Problem 4: stale data

A copy is a snapshot of one moment. The day after, production has moved on. New products, new account types and new features may be missing from the copy, so tests of the newest code run against data that does not contain it.

ShopSphere example. A "gift card" payment type launched last week. The copy taken last month has no orders that use it, so the gift-card tests find nothing to test.

1.8.5 Problem 5: missing edge cases

Real data contains the cases that happened. It does not contain the cases that have not happened yet, or have happened too rarely to be in your copy. Tests need values at the boundary: the largest allowed order, an empty field, a name with an apostrophe, a negative quantity that the app must reject.

ShopSphere example. Nobody in production has a 300-character last name, so no test checks that the screen handles one. The first customer who does crashes the checkout page.

This is where synthetic data comes in. GenRocket's help site defines synthetic test data as data manufactured by an algorithm rather than collected from real-world events, and says companies can maximise test coverage by using it to test all permutations and combinations (Why Synthetic Test Data?).

1.8.6 Problem 6: broken relationships when people shrink or edit it

Realising the copy is too big, someone tries to cut it down by hand: "delete orders older than 2023". But orders are linked to customers and order items are linked to orders. Delete in the wrong order or the wrong rows and you leave order items pointing to orders that no longer exist, or orders for customers who have been removed. The application then crashes or gives nonsense, for reasons unrelated to the code being tested.

ShopSphere example. A script deletes customers who have not logged in since 2022. It forgets their rows in ORDERS. Now there are orders with a customer_id that matches nobody. The "my orders" page fails for the wrong reason.

The same breakage happens if someone replaces names with random text by hand and uses different replacements in different tables: the customer is "Asha" in one table and "Priya" in another. The data basics chapter explains the keys that tie tables together and why every TDM operation must respect them. The Informatica documentation describes the goal directly: a data subset keeps primary and foreign key relationships so that the data stays referentially intact (User Guide 10.5.10, p.23).

1.8.7 Problem 7: cost

The costs are not only disk space. Add the time of people who run restores, the delay while testers wait, the licence and infrastructure cost of big environments, and the risk cost of a breach or regulator fine. None of it appears as a line "test data" on a budget, which is partly why the problem lingers.

1.8.8 Problem 8: no repeatability and no control

If every team makes its own copy at its own time, nobody knows which data version a bug was found on. Tests that passed Monday fail Tuesday because the data under them changed. Nobody can say who has a copy of what.

Worked example: one bug report, three failures

A ShopSphere tester finds that the "order history" screen shows an empty page for customer 1002 in the QA environment. She files a bug. The developer cannot reproduce it on his machine because his data is different. After a day of investigation they discover that the QA database was a partial manual copy in which customer 1002's orders were not copied. The bug is not in the code at all.

That one incident shows three problems from the list: broken relationships (problem 6), no control (8) and slow refresh (3: fixing it means a new copy). It also cost a day of two people's time. Multiply by a team and a year and the cost of unmanaged test data becomes visible.

1.9 So what is Test Data Management?

Test Data Management (TDM) is the set of processes, roles and tools that plan, create, protect, deliver and retire the data used in non-production environments. In simpler words: it is how you make sure the right testers get the right safe data at the right time, without copying production carelessly.

Some people use "TDM" for the software and some for the practice. In this guide "TDM" is the practice, and "a TDM tool" is software that supports it.

1.9.1 Goals of TDM

  1. Protect people. No real sensitive data in non-production.
  2. Fit the test. Data that is realistic, consistent and covers the cases the tests need.
  3. Right size. Smaller than production where possible, large only where tests need it.
  4. Be fast. Data on request, refreshed in minutes or hours, not weeks.
  5. Be repeatable and traceable. Known data versions, known owners, known copies.
  6. Lower cost. Less storage, less waiting, less rework, lower breach risk.

1.10 The six capabilities of TDM

TDM splits into six capabilities. A project may use all six or only a few. The first four change the data; the last two deliver and control it.

1.10.1 1. Discover

You cannot protect what you cannot find. Discovery means scanning a database or a set of files to locate sensitive data: which columns hold names, ID numbers, phone numbers. Large databases can have thousands of columns, and sensitive values hide in odd places such as a "notes" column. Discovery also finds the relationships between tables, which later steps need.

Why it matters: if discovery misses a column, that column goes into test unmasked.

ShopSphere: discovery flags ssn, phone, email, date_of_birth and tax_id in CUSTOMERS. The discovery and subsetting concepts chapter teaches this in depth.

1.10.2 2. Subset

Subsetting builds a smaller database from a big one: for example "only customers from the last two years, and everything linked to them". Done properly, every order in the subset still has its customer and its items. Smaller means cheaper, faster to load and easier to refresh.

ShopSphere: pick 5,000 customers and bring their orders and items along, leaving the other millions of rows behind. The discovery and subsetting concepts chapter covers it; the Informatica data subset chapter shows it in Informatica.

1.10.3 3. Mask

Masking replaces sensitive values with realistic but fake ones. The application still works because the fake values look right (a fake phone has ten digits), but nobody can learn about a real person from them. Good masking is consistent: the same real value always becomes the same fake value, so relationships between tables survive.

The Delphix documentation describes masking as replacing confidential information such as social security numbers, patient records and card numbers with fictitious yet realistic data, and contrasts it with encryption: masking is irreversible, while encryption can be bypassed through schemes to obtain user credentials (Introduction to Delphix Masking).

ShopSphere: Asha Menon, 9876543210, 123-45-6789 becomes, say, a made-up name, a made-up ten-digit number and a made-up SSN pattern. The masking concepts chapter teaches the techniques.

1.10.4 4. Generate

Generation creates data from rules instead of copying real data. You describe what you need ("fifty customers, each with a first name, a last name, a phone number") and a tool produces it. Use it when real data does not exist yet (a new feature), when you need edge cases, when you need very large volumes, or when real data cannot be used at all.

Informatica's documentation gives the second reason almost word for word: use data generation when you need test data but do not want to use production data, for example when test teams handle sensitive data and have no access to production (User Guide 10.5.10, p.23).

ShopSphere: generate a customer whose name is 300 characters long. The classification and generation concepts chapter covers the idea; Part III is GenRocket, a tool built around it.

1.10.5 5. Provision and refresh

Provisioning means delivering a ready dataset into an environment: loading it into the QA database, or placing a file where a test tool expects it. Refreshing means doing it again later to get new or reset data. Speed and repeatability matter most here.

Both Informatica and Delphix address this in their own way. Informatica describes a test data warehouse that stores multiple versions of test data and can restore a version to put an environment back into a particular state (User Guide 10.5.10, p.23). Delphix describes virtual copies that are readable and writable, can be created or removed in minutes, and take a fraction of the storage of physical copies; in its example ten virtual copies fit in the space of one physical copy (Introduction to Delphix Masking).

1.10.6 6. Govern

Governance is the rules and records around the other five: who may request what, which data is approved for which environment, which masking rules are in force, an audit trail of who received which dataset. It is the least glamorous capability and the first one auditors ask about.

Delphix says the platform lets operators audit, monitor and report against access and usage, and generates reports and email notifications confirming sensitive data has been masked. Informatica's administrator manages roles and privileges that decide what each TDM user can do (User Guide 10.5.10, p.23).

Why the six are separate ideas

Beginners often use "masking" to mean everything. It is only one of six. A team that masks but never subsets still has a huge, slow copy. A team that subsets but never discovers may mask the wrong columns. Learn the six as separate tools in a toolbox, then pick the ones a project needs.

1.14 Real-world scenarios at ShopSphere

Three short stories, each choosing a different mix of the six capabilities.

Scenario 1: weekly QA refresh

Situation. QA tests every Monday and needs realistic data, but production holds real customers.

Approach. Each Friday night a job reads production, picks the last 12 months of customers and their orders (subset), replaces names, emails, phones, SSNs and dates of birth with fake but consistent values (mask), and loads the result into QA (provision). Discovery was done once, and its results are re-checked when the schema changes.

Outcome. QA gets fresh, safe, small data every Monday without anyone touching production data by hand.

Scenario 2: a new loyalty-points feature

Situation. ShopSphere adds loyalty points. No production data has points yet.

Approach. Nothing to copy, so the team generates 10,000 customers with random point balances, including zero, the maximum and a negative balance that the app must reject.

Outcome. The feature is tested before launch, including the edge cases, with no personal data involved.

Scenario 3: performance test before the holiday sale

Situation. The company expects ten times normal traffic and needs 50 million orders in the performance environment.

Approach. Real production does not have that many. The TDM engineer generates the volume, and masks a real sample so that distributions (how many items per order, typical prices) match the real shape.

Outcome. The load test runs at realistic scale, safely.

1.15 Benefits and trade-offs

Benefits

  • Lower privacy and compliance risk.
  • Faster test cycles because data is ready.
  • Smaller storage and infrastructure cost.
  • Better test coverage through generated edge cases.
  • Repeatable tests on known data.
  • Fewer false bug reports from bad data.

Trade-offs and costs

  • Set-up effort: discovery, rules and approvals take time up front.
  • Licence and infrastructure cost for commercial tools.
  • Masked data is never exactly real data; some production-only bugs may not reproduce.
  • Generated data is only as good as its rules; it can miss real-world quirks you did not think of.
  • New skills and a new process for the team to learn.
  • Ongoing upkeep as the schema and the regulations change.
Masked and generated data compared

Masking starts from real data and hides the identifying parts, so it keeps real-world shape and messiness. Generation starts from rules, so it is safe by construction and covers cases you design, but only the cases you thought of. Many teams use both: masked data for realism, generated data for edge cases and volume. the classification and generation concepts chapter compares them in detail.

1.18 Common mistakes and gotchas

"We mask it, so it is safe"

Masking only protects the columns you masked. If discovery missed a column, or a free-text "notes" field contains names, sensitive data survives. Discovery and verification matter as much as the masking itself.

Treating TDM as a one-off project

Production changes every day: new columns, new data, new rules. A TDM set-up that is never maintained goes stale just like a copied database.

Using one technique for everything

Masking is not always right. If no real data exists for the case, or real data cannot be used at all, generate. If the problem is only size or speed, subset or virtualise.

Ignoring relationships

Any change to the data (subset, mask, generate) must keep related tables consistent. The data basics chapter explains how; skipping it leads to the "orders with no customer" bug.

Believing tool names are the concepts

"Plan", "rule set", "scenario" and "domain" mean different things in different products. Learn the concept, then learn each tool's word for it.

1.23 Keys and relationships

A single table is easy. Real applications split data across many tables and connect them. Keys are the connectors. This section is the most important in the whole chapter.

1.23.1 Why data is split into several tables

Imagine ShopSphere stored everything in one big sheet: one row per ordered item, with the customer's name, phone and address repeated on every row. Customer Asha has two orders with three items in total, so her phone number would be typed three times. If she changes her phone number you must update every copy, and if you miss one the data disagrees with itself.

The fix is to store each fact once, in the table where it belongs, and refer to it from elsewhere. Customer facts live in CUSTOMERS. An order stores only the customer's ID, not the name and phone. To get the name, you look the ID up. The ID is a key.

1.23.2 Primary key

A primary key is a column (or a small group of columns) whose value is unique in every row and is never empty (null). It is the row's identity, like a library card number or a passport number.

  • CUSTOMERS.customer_id: 1001, 1002, 1003. No two customers share an ID.
  • ORDERS.order_id, ORDER_ITEMS.item_id and PRODUCTS.product_code are the primary keys of their tables.

A database enforces this: it refuses to insert a second customer with ID 1001.

Why not use the name as the key? Two customers can share a name; names change; spellings vary. A key must be stable and unique. That is why tables carry an artificial ID such as customer_id. (Keys made up of real-world data, like an email address, are called natural keys; made-up IDs are surrogate keys. Both appear in the real world.)

A key can have more than one column. Suppose a table ORDER_ITEM_NOTES allowed one note per item per language; then (item_id, language) together would be unique, though neither alone is. That is a composite key.

1.23.3 Foreign key

A foreign key is a column in one table whose values must match the primary key of another table. It is the link.

  • ORDERS.customer_id is a foreign key to CUSTOMERS.customer_id: it says which customer placed the order.
  • ORDER_ITEMS.order_id is a foreign key to ORDERS.order_id: it says which order this line belongs to.
  • ORDER_ITEMS.product_code is a foreign key to PRODUCTS.product_code: it says which product was bought.

The foreign key column is allowed to repeat. Customer 1001 can appear in many order rows, because Asha can place many orders. The primary key side cannot repeat.

1.23.4 Parent and child tables, one-to-many

The table that holds the primary key is the parent; the table with the foreign key pointing at it is the child. One customer (parent) can have many orders (children), and one order can have many items. That shape is called one-to-many.

1.23.6 Referential integrity

Referential integrity is the rule that every foreign key value must match a primary key value that exists. Every order must belong to a customer who exists; every item to an order that exists.

A child row whose parent is missing is called an orphan. Suppose someone deletes customer 1001 but leaves orders 5001 and 5002. Those orders now point to nobody. The "my orders" page crashes. When the database has the foreign key declared, it refuses such a delete, and it refuses to insert an order for a customer ID that does not exist. (When I tried this in SQLite with foreign key enforcement switched on, both attempts were rejected with a foreign key constraint error.)

Why keys matter so much to TDM

Every TDM operation reshapes data. Each one can break referential integrity if done carelessly.

1.23.7 Logical keys: keys the database does not know about

Everything above assumed the keys are declared in the database. In real life they often are not. Older systems, performance-minded designs and imported data frequently have tables with no declared primary or foreign keys at all, even though the application treats certain columns as keys. The relationships exist in the developers' heads and in the code, not in the schema.

TDM tools cannot follow a relationship they do not know about. So they let you (or their profilers) describe the relationships separately. Keys defined this way are called logical keys in this guide: the tool is told "treat this column as the key" without any change to the real database.

Without one, an identity column may be created, which requires permission to modify the schema or the job may fail. The rule set "Checklist" validates that every table has a primary key, an indexed identity column or a logical key (Managing rule sets).

The idea is the same in both: a key you declare to the tool, which the database may know nothing about. Chapters on Informatica subsetting and Delphix rule sets and keys show the screens.

Logical keys are only as good as your understanding

If you declare a column as a key but it is not actually unique, masking or subsetting will misbehave. A logical key must be unique and never null for every row, exactly like a real primary key. You prove it by checking the data (for example by counting rows and counting distinct values), not by assuming.

1.24 Flat files

Not all test data lives in databases. Banks, insurers and retailers exchange huge amounts of data as files: one system writes a file overnight, another reads it in the morning. The syllabus includes masking "files (txt, dat)" (Day 53), so you need to read them comfortably.

A flat file is a file holding records as lines of text. "Flat" means there is no table engine, no keys, no data types: it is just text in a layout that both sides agree on. All the structure lives in the agreement, not in the file.

1.24.1 .txt, .dat, .csv: what the extension tells you (little)

A file extension is only a label. .txt says "text", .csv says "comma-separated values", .dat says "data". None of them tells you how the records are laid out. A .dat file can be comma-separated, pipe-separated, fixed-width or something else; a .txt file can hold any of those too. You find the layout from the file specification (a document from the team that produces the file), or by opening the file and looking.

Why this matters

A tool that masks files has to be told the layout, because the file itself does not say. The Delphix documentation puts it directly: unlike databases, files typically have no built-in metadata describing the format of their fields, so you must provide that information (Managing file formats).

1.24.2 Records, fields, headers and footers

  • A record is one line (one customer, one order), ending with an end-of-record marker, usually a line break.
  • A field is one value within the record.
  • A header is a record at the top that is not data: often the column names, or a label with a date.
  • A footer (or trailer) is a record at the end, often a count or a total so the reader can check nothing was lost.

1.24.3 Delimited files

In a delimited file a special character, the delimiter, separates the fields. The most famous is the comma, giving the CSV (comma-separated values) format. Pipes (|), tabs and semicolons are also common, especially when data itself contains commas.

Here is a ShopSphere customer file in CSV with a header row. All values are fake:

customer_id,first_name,last_name,email,phone
1001,Asha,Menon,asha.menon@example.com,9876543210
1002,Ravi,Kumar,ravi.k@example.com,9123456780
1003,Meera,Nair,meera.n@example.com,9988776655

And an orders file, .dat extension, pipe-delimited, with a header record (H), data records (D) and a footer record (T) that carries the record count:

H|ORDERS|20260215
D|5001|1001|2026-01-15|1098.00
D|5002|1001|2026-02-03|1499.00
D|5003|1002|2026-02-10|598.00
T|3

Reading it: the first field of each line says what kind of record it is. This is a file with several record types in one file, a layout common in business exchanges. The footer says "3 data records", so a reader can detect a truncated file.

What if the data contains the delimiter? If a last name were "O'Neil, Jr." in a comma file the comma would split it into two fields. The usual answer is an enclosure (also called a qualifier or quote character), commonly the double quote: 1004,Liam,"O'Neil, Jr.",liam@example.com,9000000001. Then a literal quote inside the field needs an escape, often by doubling it. The Delphix rule-set page documents settings for exactly this: an enclosure escaping strategy for delimited files, with a default of "Double enclosure" (the escape character is the same as the enclosure), and an option to use a custom single character (Managing rule sets).

1.24.4 Fixed-width files

In a fixed-width file there is no delimiter. Each field occupies an exact range of character positions, padded with spaces. The layout is defined by position:

The data, with a ruler line on top so you can count columns (the ruler is not part of the file):

Delimited

  • Fields found by a separator character.
  • Field length can vary.
  • Needs rules for delimiters inside values.
  • Easy to open in a spreadsheet.

Fixed-width

  • Fields found by position.
  • Every field has a set length; short values are padded.
  • No delimiter issues, but a masked value must not exceed the field width.
  • Needs the layout specification to read at all.
Fixed-width and masking

If you mask a name in a fixed-width file and the new name is longer than the field, it either overflows into the next field (corrupting the record) or is cut off. Masked values must fit the field. More detail for Delphix is in the Delphix file masking chapter.

1.24.5 Line endings

The end of a record is marked by invisible characters that differ by platform. Windows traditionally uses two characters (carriage return then line feed, often written CR+LF); Linux uses one (line feed, LF). If a tool assumes the wrong one, records are read wrongly or every line gets an odd extra character. Delphix asks you to choose the end-of-record, Windows/DOS (CR+LF) or Linux (LF), when you assign a file format, and to enter the delimiter for a delimited file (Managing file formats). It also supports using a control character as the delimiter or end of record, entered in a particular format (Managing rule sets).

1.24.6 Records of different shapes in one file

The orders file above mixed header, data and footer lines. Other files mix different kinds of data record. The Delphix documentation gives an example where some records carry an account number and a postal address while others carry an account number and an email address, told apart by the first field ("address" or "email"). It calls the differentiating field a record type qualifier, supports up to three qualifiers, and says a record gets exactly one record type. It also says that header and footer records can be configured so unmodified copies go into the masked output, and that these features apply only to delimited and fixed-width formats (Managing record types and header/footer records).

The point for you: a file is rarely "just rows". Before touching it, list the record types it contains. Masking a header line as if it were a customer would corrupt it.

1.24.7 Encodings: how text becomes bytes

Computers store characters as numbers; an encoding is the agreed table. Two matter to you:

  • ASCII: an old, small table with 128 characters: English letters, digits, punctuation. One byte per character.
  • UTF-8: a modern encoding that can represent essentially every writing system, including Tamil, Hindi, Chinese and emoji. It is ASCII-compatible: plain English text looks identical, but other characters take two, three or four bytes.

This causes two classic problems.

  1. Garbled text. A file written in one encoding and read as another turns "Müller" into something like "MÃ¼ller". The data is not lost; it was read with the wrong table.
  2. Fixed-width surprises. If a layout counts bytes but a name has an accented letter, "Müller" is 7 bytes in UTF-8 though it is 6 characters. The field after it shifts by one. Always ask whether widths are in bytes or characters.

The Delphix page on control characters says the control-character value supports the UTF-8 character set (Managing rule sets); I did not find an encoding-selection setting described in the pages I read for this section, so check your version for how it handles encodings.

1.24.8 XML and JSON at a glance

Some files are not line-and-column shaped at all; they are nested. Two formats dominate.

XML wraps values in named tags (for example <firstName>Asha</firstName>); JSON uses braces, names and values:

{
  "customerId": 1001,
  "firstName": "Asha",
  "orders": [
    { "orderId": 5001, "total": 1098.00 },
    { "orderId": 5002, "total": 1499.00 }
  ]
}

In both formats the orders are inside the customer. The parent-child relationship is shown by nesting instead of by a foreign key. For TDM, the thing to remember is that sensitive values (here the name) hide inside the structure, and a tool must know the path to them. The Delphix rule-set page lists source types of Database, Fixed Width, Delimited, JSON, XML and DataSet, and the rule-set creation dialog offers Database, Semi-Structured, Flat Files and Copybook (Managing rule sets). A copybook describes mainframe record layouts; this guide only mentions it so that you recognise the word.

1.24.9 How the Delphix documentation treats file formats and keys

A short orientation, so that later Delphix chapters feel familiar. All statements below are from the pages linked; details come later in the Delphix rule sets and keys chapter and the Delphix file masking chapter.

  • Formats are defined separately from files. You add them under Settings, in a Data Formats area with a tab for File formats and one for Mainframe (Managing file formats).
  • A format is shared. Changing a file format's inventory affects every data file that uses that format. This applies to Fixed-Width, Delimited, Mainframe, JSON and XML formats.
  • Rule sets group the tables or files a job will work on, and a rule set can be of type database, flat file, semi-structured or copybook (Managing rule sets).
  • Keys appear in the rule set. A database table's rule-set row shows a logical key column, and a table without a primary key needs one for in-place masking (see the logical keys section above).
  • A filter is a WHERE clause that limits the rows from a table, which is how a rule set does a simple subset. You will see WHERE in the SQL section next.

1.25 Basic SQL you will see

SQL (Structured Query Language, often said "sequel") is the language for asking a relational database questions and changing its data. You will meet it in TDM tools in small doses: a WHERE filter for a subset, a custom query for a table, a check of results. You need to read it, not master it.

All statements below were run against the ShopSphere tables and sample rows from this section, and the results shown are what they returned. To try them yourself, use any relational database you can access; for a free practice option, SQLite works on a laptop. The create-table statements are in the lab at the end of this section. Details such as date handling differ slightly between databases.

1.25.1 SELECT: read data

SELECT chooses columns; FROM names the table.

SELECT first_name, last_name, zip_code
FROM customers;

1.25.2 WHERE: choose rows

WHERE keeps only the rows that satisfy a condition.

SELECT * FROM orders
WHERE customer_id = 1001;
Result: Asha's two orders
order_idcustomer_idorder_datetotal_amount
500110012026-01-151098.00
500210012026-02-031499.00

Text values go in quotes; numbers do not. Because zip_code is text in our table, WHERE zip_code = '600017' returns Ravi Kumar. You can combine conditions with AND and OR, and compare with <, >, LIKE and others.

Why this matters

A WHERE clause is the simplest subset there is: "only customers in postal area 600017". Both the Informatica and Delphix documentation use filters like this to limit rows. Delphix describes a rule-set filter as a WHERE clause, and says to prefix the column with the table name, for example customer.cust_id < 1000 (Managing rule sets). Note that a WHERE on one table does not by itself bring along the related rows of other tables; keys do that, which is why subsetting is more than a filter.

1.25.3 JOIN: combine tables through keys

A join follows a foreign key. Here, each order is matched to its customer by customer_id:

SELECT c.first_name, o.order_id, o.total_amount
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id;
Result
first_nameorder_idtotal_amount
Asha50011098.00
Asha50021499.00
Ravi5003598.00

c and o are short nicknames (aliases) for the tables. The ON line states the key match. Meera does not appear: she has no orders, and a plain JOIN keeps only matches. A LEFT JOIN keeps every customer and shows empty (null) where there is no order:

SELECT c.first_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;

This returns Asha 5001, Asha 5002, Ravi 5003 and Meera with no order id. You can chain joins to walk the whole chain customer, order, item, product:

SELECT c.last_name, p.product_name, i.quantity
FROM order_items i
JOIN orders o    ON o.order_id = i.order_id
JOIN customers c ON c.customer_id = o.customer_id
JOIN products p  ON p.product_code = i.product_code
ORDER BY i.item_id;

The result has four rows: Menon with Wireless Mouse (1), Menon with USB-C Cable (1), Menon with Laptop Stand (1) and Kumar with USB-C Cable (2). A subsetting tool does something like this walk in reverse: start from the customers you chose and follow the keys out to every related row.

1.25.4 COUNT: how many?

SELECT COUNT(*) AS customer_count FROM customers;

Returns 3. With GROUP BY you can count per group:

SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id;

Returns 1001 with 2 orders and 1002 with 1 order. TDM people use COUNT constantly: how many rows before and after a subset? Does the masked table have as many rows as the source? Does the number of distinct values in a candidate key equal the number of rows? (COUNT(DISTINCT customer_id) counts the unique values.)

1.25.5 INSERT and UPDATE: change data

INSERT INTO customers (...) VALUES (...) adds a row (the lab below has full examples); the column list and value list must line up. If you inserted an order with customer_id 9999 when no such customer exists, a database that enforces the foreign key rejects it.

UPDATE customers
SET zip_code = '560002'
WHERE customer_id = 1001;

After the UPDATE, a SELECT for customer 1001 returns zip_code 560002. Never write UPDATE without a WHERE unless you really mean to change every row: the statement above, without its last line, would give all three customers the same postal code.

Masking is, at its core, a very large controlled UPDATE: replace the value in a sensitive column in every row (with a consistent rule). Delphix's in-place masking updates the source table; a copy-style approach writes to a different target. The tool generates the SQL for you, but understanding that it is an UPDATE explains why a table with no key is a problem: the tool needs a way to say "this exact row". Delphix's documentation says the custom SQL for a table must include the primary key column(s) and the columns to be masked (Managing rule sets).

1.26 Data volumes and why size matters

ShopSphere's sample tables hold ten rows between them. The real database holds millions of customers and tens of millions of orders. Size changes everything about TDM.

Sizes run from KB (a short text file) through MB (a CSV of tens of thousands of customers) and GB (a small production database) to TB (a large enterprise database).

Why size matters to a TDM engineer:

  • Time. Masking updates every row of every sensitive column. Ten times the rows is roughly ten times the work unless you add parallelism. Delphix profile jobs have a setting for the number of parallel streams, for example two streams to run two tables of a rule set at once (Delphix masking terminology).
  • Storage. Every environment that holds a full copy multiplies the cost. See the why-TDM chapter.
  • Memory and file limits. A file of many gigabytes cannot be opened in a spreadsheet; you work on it with tools or by sampling.
  • Test fitness. Performance tests need volume; functional tests do not. Matching size to purpose is part of the job.
  • Row count versus width. A table with a hundred million narrow rows and a table with a million rows of large documents behave very differently. Ask for both numbers.
Always ask for counts first

Before any TDM job, ask for the row count of each table. It tells you whether a subset is needed, how long a job should take, and gives you a number to verify afterwards (row counts before and after should reconcile with what you expect).

Goal: decide the primary key of each file, the foreign keys between them, and any problems.

  1. For each file, name a candidate primary key.

    A candidate must be unique and never empty in every row. Test it by looking for repeats.

  2. Find the foreign keys.

    Which column in one file should match the primary key of another? Write each as child.column to parent.column.

  3. Check integrity.

    For each foreign key, list the values and check each one exists in the parent. Note any orphans.

  4. Spot a trap.

    Customers 1001 and 1004 look similar. Is that a key problem?

  5. Decide how you would tell a tool.

    The files have no declared keys. What would you tell a TDM tool to treat as logical keys?

Show a worked answer

1. Primary keys. customers.csv: customer_id (1001 to 1004, all distinct). Not the name: Asha Menon appears twice. Not the email as a choice either; it is unique in this sample but emails can change, so it is a weaker key. orders.dat: the first field, the order id (5001 to 5004, all distinct). order_items.txt: item_id (9001 to 9005, all distinct).

1.28 Common mistakes and gotchas

Treating a column as unique because the sample looks unique

Three rows with distinct emails do not prove emails are unique across three million rows. Test with counts of all rows against counts of distinct values.

Assuming the database enforces the keys

Many databases, especially older ones and data warehouses, have no declared foreign keys. Relationships exist only by convention. That is why profiling for keys and logical keys exist.

Masking keys inconsistently

If a key is masked in one table and not in its child tables (or masked differently), relationships break. Mask keys the same way everywhere, or leave them alone.

Uploading real data to define a format

A layout needs only structure. Delphix says not to upload production data, sample records or PII when defining file formats (Managing file formats).

1.29 Recap

Recap
  • A database holds tables; a table has rows (records) and columns (fields) with data types. Metadata and schema describe the data without containing it.
  • A primary key uniquely identifies a row; a foreign key in a child table points at a parent's primary key; together they give one-to-many relationships.
  • Referential integrity means every foreign key matches an existing parent. Subsetting, masking and generation must all preserve it.
  • Logical keys are keys declared to the tool when the database does not declare them. Informatica and Delphix both support them.
  • Flat files have no built-in schema: know the layout (delimited or fixed-width), header and footer records, record types, line endings and encoding.
  • XML and JSON nest children inside parents instead of using foreign keys.
  • SELECT, WHERE, JOIN, COUNT, INSERT and UPDATE cover most of the SQL you will read. The orphan check (LEFT JOIN where the parent is null) is a TDM staple.
  • Size drives time, cost and test fitness: ask for row counts first.
