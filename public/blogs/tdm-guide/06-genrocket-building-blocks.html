6.1 GenRocket: what it is and how it works

Day 46

The earlier part of this guide explained why teams need test data and how to make it safely: copy a slice of production (subsetting), hide the sensitive parts (masking), or build data from nothing (generation). The Informatica part showed one commercial tool for all three. This part turns to a tool that is built around the third way: GenRocket. It does not copy your production data at all. You describe the shape of the data you want, and it manufactures as many rows as you ask for, already consistent with each other.

This first GenRocket chapter is the map. You will learn the five building blocks the whole product is made of, where each piece runs (some in a cloud web site, some on your own machine), what a "project" is, and how the syllabus phrase Model, Design, Deploy, Manage (Day 46) lines up with real screens. The two chapters after this one go deep on the building blocks: domains, attributes and generators, then receivers and scenarios. Nothing here needs a licence to understand; you only need to know what a table and a column are.

What you will learn
  • What "synthetic test data" means and why GenRocket's own pages argue it improves test coverage.
  • The five key components (domain, attribute, generator, receiver, scenario) with an everyday analogy, and how they map to the ShopSphere tables.
  • What "Test Data Automation" and the Model, Design, Deploy, Manage cycle mean in GenRocket's documentation.
  • The hybrid architecture: design in the cloud web platform, generate on your own machine with the GenRocket Runtime.
  • What the runtime is made of, the requirements the docs list, and the shape of the setup, including Docker and Jenkins at overview level.
  • Projects, project versions, project types, project categorization and the Project Dashboard.
  • Who can do what: users, roles and the licensing idea in the documentation.

6.1.1 Words to know first

Synthetic test data
Data manufactured by an algorithm instead of captured from real events. GenRocket's page defines it in nearly those words. Nobody's real name or card number is in it.
Domain
One "thing" you want data for, such as a customer. For a database it is a table. For output it can also be a file, message, JSON or XML document.
Attribute
One characteristic of a domain, such as firstName or email. For a database it is a column.
Generator
The small engine attached to an attribute that decides what value to produce, for example "a first name from a list" or "count up from 1".
Receiver
The component that takes the raw generated values and puts them into a usable form: a CSV file, a JSON file, SQL insert statements, a database table and many more.
Scenario
A saved instruction sheet: which domains to generate, how many rows of each, in what order. Running it is what actually produces data.
Test Data Automation (TDA)
The phrase GenRocket's pages use for its approach: test data defined once as components and then generated automatically, in real time, whenever a test needs it.
Web platform
GenRocket's web application in the cloud, where you model and design. Also called GenRocket Cloud.
GenRocket Runtime
A set of Java programs installed on your own computer or server. It reads a downloaded scenario and generates the data there, inside your firewall.
Project and project version
A project holds the data model for one application or database. A version is one release's copy of that model, with its own domains, receivers and scenarios.
Referential integrity
The promise that every foreign key points to a row that exists. See the data basics chapter.

6.1.2 What GenRocket is and why synthetic data

From docs GenRocket's welcome pages are short and to the point. They define synthetic test data as data "manufactured or generated by an algorithm rather than real-world events", and argue that companies can maximise test coverage by using it to test all permutations and combinations. The product's pitch is a platform in which you design that data once, deliver it in any format, and repeat it whenever a test runs.

Think of a bakery that has to supply cupcakes for a hundred different tasting events. One approach is to buy finished cakes from a rival shop, scrape off the logos and send them out (that is masked production data). The GenRocket approach is to own the recipe and the oven. You write down "chocolate, 12 per tray, nut-free, one tray with a deliberately burnt top" and the oven makes exactly that on demand. The analogy stops being accurate in one respect: a recipe produces cakes that taste alike, while a GenRocket recipe can be told to vary values, include edge cases and keep related trays consistent with each other.

Why it matters

A tester for ShopSphere's "Customer Orders" app needs a customer with 0 orders, one with 1, one with 200, one whose email is missing and one whose surname is 60 letters long. Production rarely contains all of these, and copying production brings real names along (see why TDM exists). Because GenRocket's data is manufactured to a rule, you can ask for the odd cases directly and rebuild the same set tomorrow.

From docs The documentation is also frank about the work involved. The FAQ says the harder data-design tasks are assigned to a small group of trained "Test Data Engineers", while testers and developers mainly search for the data they need, deploy it into their test environment and tweak it. That is the "TDM engineer" role this guide is aimed at. The Test Data Workflow page starts from the same person: it says the workflow begins with a Power User, a Test Data Engineer.

From docs One more design choice matters for privacy. The Test Data Projects page says a project contains no customer data. It holds your data model and the five components that describe how to generate data. The architecture diagram (below) labels the cloud part "No Customer Data Stored".

Worked example: one customer row

Take the ShopSphere row 1001 | Asha | Menon | asha.menon@example.com | 9876543210 | 123-45-6789 | 1990-04-12 | 560001 from the earlier chapters. In GenRocket terms: the domain is CUSTOMERS. The attributes are customer_id, first_name, last_name, email and so on. A generator on first_name produces "Asha" (then a different name for the next row), a generator on customer_id counts 1001, 1002, 1003. A receiver writes the lines into a file. A scenario says "make 3 of these". Every value is fake, so the row can go to any test environment.

From docs GenRocket calls its platform a Test Data Automation platform. The CI/CD page explains the idea with a short list of things any generator of data must know, and then shows how GenRocket captures each one:

Notice that the runtime has now joined the list as a sixth piece. The five components are the design; the runtime is the engine that executes it. The docs describe the runtime as a secure Java program that executes encrypted scenarios inside the customer's firewalled environment.

6.1.5 Architecture: a cloud for design, your machine for generation

From docs The Architecture page says GenRocket is built on a hybrid architecture. The cloud component is where synthetic data is modelled and designed. The on-premise component is where synthetic data is generated locally. The cloud itself is offered as a Virtual Private Cloud (VPC) or a Dedicated Private Cloud (DPC).

Read the diagram from top to bottom. A designer logs in to the web platform and builds the design. The design is then sent to the customer side as an encrypted scenario file. On the customer side, the runtime runs it and writes data into databases and files that never leave your network.

Why it matters

For a bank or hospital, the question "does our data leave the building?" decides whether a tool may be used at all. In this design, the cloud holds only the design (a data model and rules, not data). The only place rows are created is on a machine you control. Compare this with a masking tool (Informatica masking chapter), where real data is read and transformed.

The Architecture page links onward to security, team permissions, the runtime overview and "G-Repository", the component that keeps scenarios and configuration files synchronised across a company's machines. There is also a downloadable PDF, "Components and Ports Configuration Guide", which the docs call a vital resource for core components, diagrams, port configurations and deployment advice. I did not open that PDF; if your organisation deploys GenRocket, that is the document to ask for.

6.1.6 The GenRocket Runtime

6.1.6.1 What it is

From docs The runtime is a set of Java jar files, downloaded from GenRocket Cloud and installed wherever data generation is needed: a laptop, a shared machine, a server, a virtual machine or a container. The pages list these jars.

6.1.6.3 Profiles: how the runtime knows who you are

A scenario file is encrypted and tied to your organisation. To run it, the runtime must find a profile file (extension .grp) in a hidden folder named .genrocket in your home directory. The profile ties the machine to a GenRocket licence.

ProfileUsed for
User ProfileEvery person who runs the runtime. It matches the scenario to your organisation and checks that you have an enabled account
Server ProfileA server with no particular person, typically a CI/CD machine. An organisation administrator must first add the server in the web platform

Both are downloaded from the web platform. Whenever a resource value changes, the docs say you must download your profile again and replace the old one.

6.1.6.4 Port 443, online mode and the offline certificate

From docs The runtime runs in online mode by default: when you run a scenario, it contacts GenRocket Cloud over port 443 to confirm the licence. The "Verify Port 443" page gives a quick test: open https://app.genrocket.com/license/check in a browser, or run curl on the same address. If the port is open you see a short JSON message saying a valid user or server was not found. That odd-looking "failure" is the proof that the connection works.

If your company blocks that port, the docs offer an offline certificate: download a file from the web platform, put it in the .genrocket folder, and run scenarios without internet. The certificate is specific to one organisation and lasts 24 hours, so you download a fresh one each day.

Offline certificate pitfall from the docs

If the home directory stored in your resource.home.directory resource does not match the machine's real home directory, you get "Unable to validate license". The fix on the page is: correct the resource value, download the certificate again and retry.

6.1.6.5 Setting it up: the shape of the steps

You will not install the runtime in this guide's labs (the hands-on chapter assumes a trainer or lab machine has done it), but you should know what the steps look like. The three operating-system articles are long and similar. Here is the Windows article's skeleton, in my words. Details such as folder paths and the exact variable names belong to the vendor page for your system.

  1. Check the prerequisites.

    An active GenRocket user account and access to the cloud address from your network, port 443 open, admin rights on the machine, and Java installed.

    What you should see: java -version prints one of the supported versions.

  2. Download the runtime zip from the web platform.

    Log in, open the Options menu, and choose the download for the current runtime version. The docs also show a curl or wget way to fetch it.

    What you should see: a zip file named with the runtime version number.

  3. Extract it into your home directory and name the folder genrocket.

    The page warns that you must not end up with a nested folder such as genrocket\genrocket-3.5.x, and that the user name in the path must not itself be "genrocket".

    What you should see: a genrocket folder with bin and lib inside.

  4. Set the environment variables.

    Point the home variable at the folder, add its bin directory to PATH, check JAVA_HOME, and for Java 11 or later add the documented JAVA_OPTS value.

    What you should see: after opening a new terminal window, the word genrocket is recognised.

  5. Run genrocket once.

    This downloads the other jars into lib and creates the hidden .genrocket folder.

    What you should see: no error. If you see "genrocket is not a recognized command", the troubleshooting page says to check the folder name, the home variable and PATH.

  6. Download the helper libraries and your user profile.

    The page uses genrocket -lib for libraries. The profile comes from the Download menu in the Resources pane and goes into .genrocket.

    What you should see: a .grp profile file inside .genrocket.

  7. Fill in your organisation resources.

    Three default resources hold folder paths for you (home directory, JDBC config directory and output directory; the screenshots in the next section show them). Set them to real folders, and enter N/A for the JDBC one if you do not connect to a database.

    What you should see: your own paths in the Resources pane of the web platform.

From docs Typing genrocket alone, or genrocket -h, prints the list of runtime command-line options. That is the quickest way to see what your installed version supports.

6.1.6.6 Updates, Docker and Jenkins at overview level

Updates. The docs distinguish a full runtime update (replace the whole genrocket folder) from a jar-only update (done from the command line, and sometimes without re-downloading the runtime). Release notes say which is needed, and users see a pop-up after login when a new release arrives.

Docker. For teams that run containers, GenRocket provides a Docker image you download from the web platform (or with curl) and load with docker load. The page's basic idea is that a container forgets everything when it stops, so you mount folders from the host for the runtime, the scenarios, the configuration files, the .genrocket profile folder and the output. The page also notes that the runtime must be set up when using a container, and describes a custom-image option.

Jenkins (continuous integration). Jenkins is a popular tool that runs build and test jobs automatically. The Windows and Mac/Linux Jenkins pages walk through running a scenario as a Jenkins build step. The outline is the same as a normal setup, applied to the Jenkins server:

  1. Install the runtime on the Jenkins server and set the variables in Jenkins's own configuration screen.

    Jenkins builds do not see your personal environment, so the home variable and PATH must be set where Jenkins reads them.

  2. Register the Jenkins server in the web platform and download its Server Profile into the server's .genrocket folder.

    No person is logged in on a build server, so it uses a server profile, not a user profile.

  3. Create a Freestyle job and add a build step that runs the scenario.

    First the page has you run the bare genrocket command to prove Jenkins can find it, then replace it with genrocket -d -r SCENARIO_NAME.grs.

    What you should see: a SUCCESS message in the console output, and your generated files in the output folder.

The CI/CD page adds two ways to trigger generation from a pipeline: a shell or batch command running the runtime, or a REST request to a GenRocket server component. It also describes Java and REST APIs that let a pipeline create or modify a scenario in real time, for example to change a loop count (how many rows) per test.

Not covered here

Linux and Mac setup, the multi-user server, G-Repository administration and API method details are separate topics in the help centre. I read only the overview-level material for them, so I do not describe them further.

6.1.8 Projects, project versions and categories

6.1.8.1 What a project is, and how many you need

From docs A Test Data Project contains the data model for one application or database you want data for. It contains aspects of your model (domains, attributes, generators, receivers, scenarios) but no customer data. This is also the unit of licensing: the Test Data Projects page says GenRocket is licensed based on the number of projects a customer needs.

The page gives a way to count. Start with what you are testing, find the applications and their databases, and count them. It then lists factors that may split one thing into several projects: database size, complexity of related tables, whether functions are related, and special message formats.

For ShopSphere's "Customer Orders" app with its single SHOPSPHERE_PROD schema, the docs' rule suggests one project, because the four tables are related.

6.1.8.3 Creating a project

  1. Open the Projects pane in the Project Dashboard and click New Project.

    If you cannot see this button, the docs say you lack permission; ask your organisation's administrator to assign the right role.

  2. Enter a name, a type if offered, and a description.

    The docs recommend a description. Choose the industry type if you can: they say it helps GenRocket assign the right generator to attributes.

  3. Optionally pick a team or tick Master Project, then click Save.

    A master project is a way to share master domains with other projects; teams are explained in the user section below.

6.1.8.4 Project versions

From docs A project is born with a version numbered 1.0. A new version is normally created when the release your domains and scenarios test goes to production, and the next release needs testing. Each version has its own domains, receivers, scenarios and configuration.

There are two ways to make one, both from the Manage menu in the Project Versions pane.

New Version

A blank slate. No domains or scenarios from before. Use it when the data model changes so much that starting fresh is easier.

The dialog asks for a version number and description, an optional default date format (for the whole version; a more specific format at attribute or generator level wins), and an optional Enforce Type/Limit checkbox.

Copy Version

Replicates the whole version, or a subset of domains, so the new version matches the next release of your software.

The docs state a limit: permitted users can copy a version five times in 24 hours, counted from the first copy.

The Project Dashboard page lists some of those icons: generator search, the Domain Referencing Wizard, a project-version status report (which flags attributes with no generator, id attributes without a range generator, and foreign keys without the proxy reference generator), a global seed assigner and a generator tuning wizard. Terms like proxy reference generator are explained in the generators chapter.

6.1.8.5 Project categorization

A company with hundreds of projects needs a way to find them. From docs Project categorization lets an organisation administrator build a three-level list, then lets users filter projects by it:

  • Business Unit: the top level, such as a department or team (the docs' example is "Bank").
  • Category: a group of similar projects within a unit (Credit Card, Checking, Savings). No limit on how many.
  • Tag: the lowest level, a keyword for a category (New Accounts, Payments Received). A category can have up to five tags.

Only an Org Admin creates the units, categories and tags; an Org Admin or the project's creator assigns them to projects; any user can then filter projects by them. The docs recommend using this only when you have many projects, and say a small organisation can find projects by name. 6.1.11 Common mistakes and gotchas

Things that trip up beginners
  • Expecting data to appear in the web platform. The cloud holds designs, not data. Rows are created only when a downloaded scenario runs under the runtime on your machine. The "Preview" you see in the web platform is a sample for checking configuration.
  • Forgetting the profile. Without a valid .grp profile (or offline certificate) in .genrocket, the runtime refuses to run. Download a fresh profile whenever a resource value changes.
  • Environment variables set but not picked up. A terminal opened before you changed variables keeps the old values. Close it and open a new one.
  • Port 443 blocked. The runtime cannot validate the licence. Use the browser or curl test, then ask the network team or use the offline certificate.
  • Treating the number of generators or receivers as fixed. The docs give changing counts ("765+", "120+", "more than 100"). Look the name up in your version rather than relying on a number.
  • Creating a new project for every release. A new version is the documented tool for that, and project count is a licensing unit.
  • Confusing the five components with the four phases. See the warning in the four-steps section.

6.2.2 Domains: the tables of your design

6.2.2.1 What a domain is

From docs A domain "defines real-world objects", a noun such as a person, place or thing. When you model a database, a domain is a table and its attributes are the columns. The docs' own example has four tables, Company, Department, User and Address, each becoming a domain with its columns as attributes. At least one domain must exist in a project to generate any data.

A domain inside a project version is a template: it holds the attributes, generators and relationships. When you create a scenario, GenRocket copies the template into a scenario domain. Changes you make to the template cascade down to every scenario unless the scenario (or the scenario domain) is locked. This is similar to a document template and the letters printed from it, with one difference: you can pin a printed letter so that later edits to the template leave it alone.

The docs also state a rule that surprises beginners: a template domain works independently and cannot really reference another domain's attributes. Relationships at the domain level are "just probable". The real references are made at the scenario level, where related domains are put together. You will see this again with ProxyReferenceGen below.

Each time a domain is created or imported, it gets three default variables, all initially 1 (details below): id, loopCount and seed.

Names have a small rule. The "New Domain" page notes that a domain name should contain only letters and numbers (spaces are now also allowed), so for the ShopSphere table ORDER_ITEMS I would name the domain OrderItems and put the real table name ORDER_ITEMS in the Table Name field you can see on the dashboard. The page does not say what happens with an underscore, so I avoid it.

6.2.3 Relationships: parent, child and sibling

Real tables point at each other: ORDERS.customer_id is a foreign key to CUSTOMERS (data basics chapter). If you generate 50 customers and 80 orders with random customer numbers, some orders will point at customers that do not exist, which breaks referential integrity. GenRocket's answer is to generate data in order, from parent to child, so a child can only pick a key a parent has already made.

From docs The documentation says GenRocket "generates synthetic data with full referential integrity" because every domain has an id or primary attribute, and children refer to the parent's primary attribute. It also says GenRocket looks at relationships differently from a database. A database table can have several foreign keys. A GenRocket domain may have only one parent but many siblings, because generating sequentially along several parents would produce "a large amount of unnecessary data".

TermMeaningRule of thumb from the docsShopSphere

SiblingA domain that only "describes" another, used for lookupsIf the table is an adjective of another (role is an adjective of user), mark it a siblingPRODUCTS describes an item: a sibling of ORDER_ITEMS

The scenario page adds a vocabulary pair: the primary domain is the one a scenario is created for, and the root domain is the first parent up the chain. For an ORDER_ITEMS scenario, ORDER_ITEMS is primary and CUSTOMERS is root, so the scenario creates customers, then orders, then items, and every key matches.

Why it matters

Valid foreign keys are the reason a test can load generated data into a real database and not see constraint errors. The same guarantee is what the generation concepts chapter asked for in principle (parents before children); GenRocket builds it into the domain model.

From docs A generator creates synthetic data (or queries existing data) for one attribute. Every attribute needs one. 6.2.6.1 How a generator gets assigned automatically

You rarely pick generators from scratch. For each new or imported attribute GenRocket tries these steps in order, according to the "How are Generators Assigned" page:

  1. Is there a matching Project generator tag? If yes, use it.
  2. Otherwise, a matching Organization generator tag?
  3. Otherwise, an intelligent guess from the domain name, attribute name, the project's industry type and usage patterns of other users. If Enforce Type/Limit is on, the column's type is considered too (a date column gets FlexibleDateRangeGen, a uniqueidentifier gets UUIDGen).
  4. If nothing fits, SimplePatternGen, which builds a value like name1, name2, name3 from the attribute name and the row's id.
Treat SimplePatternGen as a to-do marker

It generates values like street1, which are unique but not realistic. When you see it on an attribute, the tool could not guess; pick a better generator. The Project Version status report flags attributes without a generator.

Conditional generators can express rules such as "if age is under 18, return Child; between 18 and 60, Adult" or "50% Regular, 30% Premium, 20% VIP". The docs contrast them with test data rules (G-Rules), which attach conditions to cases instead of single attributes. The patterns they enable are taken further in the data patterns chapter.

6.2.6.6 Seeding: repeatable randomness

If two runs of a "random" generator give different numbers, test failures cannot be reproduced. A seed fixes this: the docs show a RandomGen for numbers 1 to 25 giving a new set every run when the seed is empty, but the same set whenever the seed is 1; a different seed (2) gives a different, but also repeatable, set. A seed can be set on an attribute's generator or through the domain's seed variable (button Global Seed applies it to the whole domain).

6.2.6.7 Linked generators

One attribute can hold several generators in a row (gen1, gen2...). They run left to right, a generator may use any generator to its left, and the last one gives the value. The docs' example builds a full name in a single fullName attribute: NameGen, AlphabetGen (middle initial), NameGen (last name), then ConcatGen joining the three. Without linking you would need four attributes and would have to hide three of them with Visible turned off.

6.2.6.8 ReferenceGen and ProxyReferenceGen: how a child finds its parent key

This pair is the mechanism behind foreign keys, and it confuses everyone once. The docs explain it as follows.

ProxyReferenceGen (domain level)

A placeholder. Because a template domain cannot see another domain, the foreign-key attribute holds this generator, whose only parameter is startRange (default 1000). It marks "a parent's key goes here".

Assigned automatically when you import with DDL or XTS and the column has a foreign key.

ReferenceGen (scenario level)

The real thing. When a scenario is created and the parent relationship exists, GenRocket swaps the proxy for ReferenceGen. Its one parameter reference points at the parent's primary attribute, such as #{AddressScenario.User.id}.

It can also be set up manually, as in the docs' "User and Address" example.

It explains why the project version status report asks for "foreign key attributes that do not have the ProxyReferenceGen". If the proxy is missing, the child will not find its parent when a scenario is made, and the reference value will not be filled in. The referenced attribute is the parent's primary attribute; if another column should be the target, tick its Primary checkbox.

6.2.6.9 Enforcing data type and size

A generator does not know that first_name is varchar(5) unless you tell it. From docs The Enforce Type/Limit option makes the generator keep values within the attribute's Type and Size. It is on automatically for generators assigned by a DDL or XTS import, can be enabled for a whole project version when you create it, and can be set manually per generator. The docs list integer limits it applies, for example 127 for tinyint, 32767 for smallint and 2147483647 for int.

  1. Open the attribute, set Type (for example varchar) and Size (for example 5) and save.

    These tell GenRocket the limits.

  2. Tick Enforce Type/Limit in the generator section and save the generator.

    What you should see: the preview now shows names of at most five characters.

6.2.6.10 Primary keys after the current maximum

When you insert into a table that already holds rows, new keys must not collide with old ones. The docs' recipe links two generators in the id attribute. gen1 is QueryOnceGen with resourceName pointing at the JDBC resource, query = select max(id) + 1 from <tableName> and a sampleValue (5001 in the example) used for previews. gen2 is RangeGen whose startRange references gen1.

The General FAQ adds a second pattern for the parent side: write the parent's ids to a delimited file as you insert, then read them back with a list generator when generating children, so the keys match.

6.2.8 Common mistakes and gotchas

Watch for these
  • Expecting a DDL import to set relationships. It does not. Run the Domain Referencing Wizard.
  • Giving a table several parents. Use one parent and mark describing tables as siblings.
  • Referencing an attribute below the current one. The value is empty. Reorder first.
  • Leaving SimplePatternGen in place. It means no better guess was found.
  • Forgetting Enforce Type/Limit. Values may not fit the target column.
  • Forgetting that a new domain's loopCount is 1. A first run gives one row.
  • Using ListGen for large lists. It supports up to 15 values. The docs recommend ListCSVV2Gen or another file-based list generator for more. ListCSVGen loads the whole file into memory.
  • Exhausted unique values. RandomGen with a small range and uniqueLimit 1 stops with "Exhausted attempts to find the next valid random value" when the loop count is too high (the page's own example is a range of 1 to 20, a limit of 1 and 20 rows). Widen the range, raise the limit or lower the row count.

6.2.9 Recap

Key points
  • A domain is a table (template), an attribute is a column, and each attribute needs a generator.
  • Create domains by hand, with Scratch Pad, from DDL, or from a database with XTS. Imports do not set relationships or receivers.
  • Each domain has three variables: id, loopCount and seed.
  • One parent, many siblings. Parents generate first, so child foreign keys always find a parent.
  • ProxyReferenceGen is the domain-level placeholder; ReferenceGen is the scenario-level real reference.
  • GenRocket assigns generators by tags, then by guess, then SimplePatternGen. Replace them one at a time or in groups.
  • Seeds make random data repeatable; linked generators build complex values; Enforce Type/Limit keeps values inside column limits.

6.3.2.4 Output folders: organisation resources

Receivers do not hold a user's folder name. They use resource references. A new account has three: resource.home.directory, resource.jdbc.directory and resource.output.directory (the dashboard screenshot in the overview chapter shows them). The resource page recommends the home directory be the real home folder, and the other two be different folders, preferably sub-folders of home, because using the same path for all three can cause errors "or, in some cases, a process that never finishes". After changing any resource value you must download your profile again and replace the old file in .genrocket; otherwise you get the error "Unable to Download Users Profile" if a resource has no value, or stale paths if you forget.

6.3.2.5 Configuration files, V2 receivers and bulk load

  • Configuration file. A file that tells a merge receiver how to combine data from different domains into one nested output. It defines file name segments, the segment files and the element layout. It is created in the Configuration Management tab and its name goes in the merge receiver's configName. Some imports (JSON, XML) create one for you.
  • V2 receivers. Names contain "V2" just before "Receiver", for example GenericSQLInsertV2Receiver. They add two parameters, resourcePath and resourceSubDir, so a receiver can point to different configuration folders without creating more global resources. The vendor says V1 receivers will eventually be hidden from the picker; scenarios that already use them keep working.
  • Bulk load receivers. Inserting through JDBC averages about 4,000 records per second, according to the page, which is slow for millions of rows. Bulk-load (partition) receivers write the database's native bulk-load file format instead. The page lists receivers for MySQL, Oracle, PostgreSQL, MS SQL, DB2, Sybase, Snowflake, Databricks, Parquet and delimited files.

6.3.3.7 Writing straight into a database: the JDBC receivers

From docs GenericSQLInsertReceiver inserts generated rows directly into a table through JDBC. Its parameters include resourceName* (the resource that points to the connection information), databaseName*, tableName*, truncate*, statementSeparator*, nullValue* and quoteTextData*. Property keys are columnName, columnType and include. The newer GenericSQLInsertV2Receiver adds resourcePath, resourceSubDir, continueOnError and logErrorDetails. The V2 page says it suits "up to 10,000 rows into a table with 25 columns or fewer", and recommends the GenericSQLInsertThreadReceiver for larger loads.

truncate empties the table

The V2 page warns that its truncate parameter can truncate or delete all existing rows before inserting, and that this cannot be undone. The default is "notApplicable" (nothing deleted). Never point a truncating receiver at a database you have not backed up.

Direct database receivers need a JDBC configuration file (config.properties) on the machine running the scenario. It holds driver, user, password, url and, for receivers, batchCount. Its folder comes from resource.jdbc.directory. You can check a connection with the runtime's --test-jdbc option before running a scenario.

Update receivers. SQLUpdateReceiver runs batched UPDATE statements whose values come from attributes (up to 20 attributes mapped to variables var1 to var20), which is the basis of replacing real values with synthetic ones in a table. SQLBatchUpdateReceiver reads one or more update statements from an XML configuration file that can address several databases, using placeholders such as #{firstName}. The FAQ also names StoredProcedureCallReceiver for calling procedures, while the FAQ says SQLUpdateReceiver can run DDL and DML scripts before or after a load, and another page uses SQLUpdateV2Receiver to create a database table.

6.3.3.8 Nested data: segment-and-merge receivers (overview)

JSONFileReceiver and XMLFileReceiver are flat. For nested output (customers containing orders containing items) GenRocket uses two receiver types together:

  1. Add SegmentDataCreatorReceiver to each domain except the merge domain.

    Each domain writes its rows as a small XML "segment" file, tagged with its parent's id so relationships survive.

  2. Create a merge domain and add a merge receiver, such as JSONSegmentMergeReceiver or XMLSegmentMergeReceiver.

    The merge receiver reads the segments and the configuration file, and writes nested files. Others exist for Avro, Parquet, delimited, fixed, EDI, HL7, SWIFT and SOAP.

  3. Put the merge scenario last in a scenario chain, create the configuration file, and download both.

    Merging only works once every segment exists. Imports of JSON, XSD and some other models set most of this up for you.

The JSON merge page lists parameters such as outputPath, configName, segmentPath and recordsPerFile. If the root domain's loop count is 50 and recordsPerFile is 8, seven files are made (six with 8 records, one with 2). I do not walk through a full nested build here; the vendor pages do it with many screenshots.

6.3.3.9 Masking receivers (overview)

GenRocket also masks: it replaces sensitive values with synthetic ones, a method it calls Synthetic Data Replacement. The file-masking receivers take an existing file and write a new one with the targeted values replaced: DelimitedFileMaskReceiver, ExcelFileMaskReceiver, JSONFileMaskReceiver, XMLFileMaskReceiver, ParquetFileMaskReceiver, ORCFileMaskReceiver, EDIFileMaskReceiver and FileMaskMultiBlockReceiver (fixed files such as VSAM). The same documents describe database masking in place (IPM). The vendor states that production data is never sent to GenRocket, since only metadata is used. How this compares with masking in other tools is in the Informatica masking chapter and the masking concepts chapter.

6.3.4 Scenarios

6.3.4.1 What a scenario is

From docs A scenario contains instructions that tell the GenRocket engine what synthetic data to generate and how much. You select the domains, say how many rows each produces, decide their order, download the scenario to a computer, and run it with the runtime. Domains, attributes, generators and receivers are its building blocks, so all four must exist first.

A scenario is for one primary domain. If the primary domain has parents, the scenario pulls them in as helper domains so that foreign keys are valid: a scenario for Address with parents User and Department also creates departments and users. To output data for several related domains, create a scenario per domain and link them in a chain (below). The docs recommend a scenario for every domain, except pure helper domains.

6.3.4.4 Scenario domains, relationships and locks

A scenario holds copies of template domains (scenario domains). Template changes flow into scenarios unless the scenario, a scenario domain or an attribute is locked. A lock stops changes made higher up from cascading down; while a scenario is locked the Sync button is hidden, and a locked item cannot be deleted. Use Sync to pull in template changes deliberately.

You can also change a relationship for one scenario only, leaving the template alone. The vendor's story: for the Student scenario, make Teacher the parent of Student instead of Subject. The steps are to add the Teacher domain to the scenario, remove the Student domain's current parent, and add Teacher as its parent. Changes at scenario level do not flow back up. Relationships cannot be changed at the test data case level, so this is the place to do it.

6.3.4.5 Scenario variables and scenario state

Variables. Scenario variables are name-and-value pairs usable only inside the scenario that created them. In the Scenario Variables pane click New Variable, give a name and value and save, then reference it from a parameter (double-click the parameter field and pick it).

State. Normally every run of a scenario produces the same data, for example a RangeGen starting at 10000 starts there every time. Sometimes you want the next run to continue (ids 10000 to 10099 first, then 10100 and on). Clicking Make Stateful saves each generator's position at the end of every successful run; Make Stateless turns it off. By default scenarios are stateless. The state is kept in a small H2 database in the .genrocket folder of the machine, and two runtime options list or clear it: --state-list and --state-clear (with an id or all).

6.3.4.6 Scenario chains and chain sets

A scenario chain links two or more scenarios so that one downloaded file runs them in order. The vendor example has Department, User and Address scenarios that produce three files from one command. A chain set links chains. A chain holds up to 25 scenarios and a chain set up to 25 chains. Optionally set a delay in seconds after a scenario.

  1. In the Scenario Chains pane click New Scenario Chain, enter a name and description and click Save.

    Naming makes the chain findable among many.

  1. Click the plus beside each scenario to add it, in the order they should run.

    Parents must come first so that their output exists before children use it.

  2. Set delays with the pencil icon if you want one, then Save and Download.

    What you should see: a chain file you run just like a scenario.

6.3.4.7 Running a scenario with the runtime

The scenario file is run from a command window on a machine that has the runtime and your profile.

  1. Download the scenario (or chain).

    The Download button on the dashboard, or the cloud icon in the Scenarios pane. Several scenarios can be downloaded together as a ZIP with Batch Download (up to 15).

  2. Open a command window or terminal in the folder where the file was saved.

    The command needs to find the file.

  1. Run genrocket -r <ScenarioName>.grs.

    The -r option means "run". Chains use the same command.

    What you should see: lines saying the licence was validated, the runtime versions, "Running Scenario ..." for each scenario, and finally "All done!" with the elapsed time.

When data is inserted into a database and loading fails, the runtime throws an exception to the command line (or to the testing framework when it runs in an automated pipeline), so no error means success. The vendor's note on stopping a run: press Ctrl+C, and on Windows answer the "Terminate batch job (Y/N)?" prompt with Y to abort.

In automated environments the same command is placed in a build step (see the Jenkins section in the overview chapter). Scenarios can also be run through a repository server or an API, which this guide does not cover.

6.3.4.8 The Scenario Thread Engine (overview)

The thread engine speeds up chains and chain sets by running several of their scenarios at the same time: genrocket -r Chain.grs -threaded 10. The docs caution that threads may run in any order, so use it only where order does not matter, for example many segment files that a merge receiver combines later (the engine waits for every segment before merging). Do not use it where SQL inserts depend on parent rows already being present, because the order matters for referential integrity. Their example generated 10,000 EDI documents in 23 minutes 50 seconds with 20 threads against 53 minutes 20 seconds with one (on the vendor's test machine).

6.3.5 ShopSphere end to end: CUSTOMERS to CSV and ORDERS to SQL inserts

Everything below uses the design from the domains, attributes and generators chapter. It is a practice build, not copied from a vendor page, so each step says which documented feature it uses. I chose SQLFileInsertReceiver for orders because it needs no database connection.

Lab: one chain, two outputs

Goal: produce Customers.csv with 50 customers and Orders.sql with 100 insert statements whose customer_id values all exist in the CSV.

  1. Check your resources.

    In the Resources pane the home and output directories must point to real folders on the machine that will run the scenario, and your profile must be in .genrocket. If you change one, download the profile again.

    Expected: three resource rows with paths (JDBC may be N/A).

  2. Add a DelimitedFileReceiver to the Customers domain.

    Set fileName to Customers.csv, delimiter to a comma, includeHeader True, quoteTextData None, appendToFile false. Leave path as the output resource.

    Expected: the receiver appears in Domain Receivers.

  3. In its Attributes Property Keys tab, set columnName to the table's column names.

    Set the id, names and other columns to customer_id, first_name and so on, so the CSV header matches the source database. Set include false for anything the consumer does not want.

  4. Add a SQLFileInsertReceiver to the Orders domain.

    Set tableName to ORDERS, fileName to Orders.sql, batchCount 100, statementSeparator a semicolon, quoteTextData Single, nullValue NULL, appendToFile false. Set the column names to order_id, customer_id, order_date and total_amount.

    Setting useQuotes false on the numeric columns is a reasonable choice, but the vendor page only says "sometimes a numeric value should be quoted".

    Expected: the property-key tab shows the real column names.

  5. Create the scenarios.

    Use Quick Scenario on Customers and on Orders. The Orders scenario brings Customers in as its parent. Both will normally have their receivers, so in the Orders scenario open the Scenario Domain Receivers pane and disable the Customers receiver (or use Disable Non-Primary Receivers), so the CSV is written once, by the Customers scenario.

    Expected: the Orders Scenario Dashboard lists Customers and Orders, with Orders as primary and Customers as root.

  6. Set the row counts in the Scenario Domains table.

    Customers: 50. Orders: 2, meaning two orders for each customer, so 100 in total.

    Expected: the summary for Orders reads like "2 Orders For Each Customers" (wording is the product's).

  7. Create a chain called ShopSphereChain with CustomersScenario first and OrdersScenario second, then download it.

    Order matters: parents first.

  8. Run genrocket -r ShopSphereChain.grs from the download folder.

    Expected: "Running Scenario CustomersScenario", then "Running Scenario OrdersScenario", then "All done". Output folder holds Customers.csv and Orders.sql.

Show how to check the result

Open the CSV: it should have a header and 50 rows with customer ids from 1001 to 1050 (if the id variable was set to 1001). Open the SQL file: it should contain 100 insert into ORDERS(order_id,customer_id,order_date,total_amount) values (...) lines whose customer_id values lie between 1001 and 1050, and every customer should appear twice. If you load both into a test database, load customers first so the foreign key is satisfied. (Load order is general database practice, not a documented GenRocket feature.) A header row in the CSV needs includeHeader true; if the Excel viewer shows a single column, the delimiter is wrong.

Variation: insert straight into a database

Replace the SQLFileInsertReceiver with GenericSQLInsertV2Receiver. Create a config.properties file with driver, user, password, url and batchCount, place it in the JDBC resource folder, set resourceName, databaseName and tableName, leave truncate on "notApplicable", and put the JDBC driver jar in the runtime's lib folder. Test the connection with --test-jdbc, then run the chain. This needs a database and credentials from the trainer or DBA, so it is optional here.

6.3.7 Common mistakes and gotchas

Watch for these
  • Changing a receiver or loop count and re-running the old file. The scenario file is a snapshot. Download it again after every change.
  • Wrong chain order. Children before parents means keys do not exist when you load the data.
  • Column names that do not match the database. In SQL receivers, columnName must be the real column.
  • Parent data written twice. A child scenario brings its parents in; disable the non-primary receivers if you only want the child's file.
  • Using the thread engine with SQL inserts. Order matters there.
  • Truncating a table by accident. Leave truncate on "notApplicable".
  • Expecting the profile to refresh itself. After resource changes, download it again.

6.3.8 Recap

Key points
  • A receiver turns generator output into a format. Sixteen categories, 120+ receivers; more than one can sit on a domain.
  • Receivers use organisation resources for folders. Download your profile again whenever a resource changes.
  • Delimited, fixed, JSON, XML, Excel and SQL-file receivers cover most beginner needs; segment-and-merge receivers make nested output; masking receivers replace values in existing files.
  • JDBC receivers insert directly and need a JDBC config file; V2 adds resource path settings; bulk-load receivers are for very large volumes.
  • A scenario is built for a primary domain and pulls in its parents. A child's loop count is per parent row.
  • Download, then run with genrocket -r. Chains run several scenarios in order. Locks, state and variables control behaviour between runs.
  • When something fails, the commonest causes are a missing profile, wrong paths or variables, relationship or ordering mistakes, and Java memory settings.
