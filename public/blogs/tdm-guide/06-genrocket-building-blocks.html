GenRocket: what it is and how it works

GenRocket is built around the third way of making test data: generation. It does not copy production data at all. You describe the shape of the data you want, and it manufactures as many rows as you ask for, already consistent with each other.

The product is made of five building blocks. Some pieces run in a cloud web site and some on your own machine, and GenRocket's own method is Model, Design, Deploy, Manage. The building blocks are covered in detail in domains, attributes and generators, then receivers and scenarios.

6.1 Words to know first

Synthetic test data
Data manufactured by an algorithm instead of captured from real events. GenRocket's page defines it in nearly those words. Nobody's real name or card number is in it.
Domain
One "thing" you want data for, such as a customer. For a database it is a table. For output it can also be a file, message, JSON or XML document.
Attribute
One characteristic of a domain, such as firstName or email. For a database it is a column.
Generator
The small engine attached to an attribute that decides what value to produce, for example "a first name from a list" or "count up from 1".
Receiver
The component that takes the raw generated values and puts them into a usable form: a CSV file, a JSON file, SQL insert statements, a database table and many more.
Scenario
A saved instruction sheet: which domains to generate, how many rows of each, in what order. Running it is what actually produces data.
Test Data Automation (TDA)
The phrase GenRocket's pages use for its approach: test data defined once as components and then generated automatically, in real time, whenever a test needs it.
Web platform
GenRocket's web application in the cloud, where you model and design. Also called GenRocket Cloud.
GenRocket Runtime
A set of Java programs installed on your own computer or server. It reads a downloaded scenario and generates the data there, inside your firewall.
Project and project version
A project holds the data model for one application or database. A version is one release's copy of that model, with its own domains, receivers and scenarios.
Referential integrity
The promise that every foreign key points to a row that exists. See the data basics chapter.

6.2 What GenRocket is and why synthetic data

GenRocket's welcome pages are short and to the point. They define synthetic test data as data "manufactured or generated by an algorithm rather than real-world events", and argue that companies can maximise test coverage by using it to test all permutations and combinations. The CI/CD page describes the product as a component-based platform for defining and provisioning test data for high-volume, automated testing.

Think of a bakery supplying cupcakes for a hundred tasting events. One approach is to buy finished cakes from a rival shop and scrape off the logos (masked production data). The GenRocket approach is to own the recipe and the oven: "chocolate, 12 per tray, one tray with a deliberately burnt top", made on demand. The analogy breaks in one place: a recipe makes cakes that taste alike, while a GenRocket recipe can vary values, include edge cases and keep related trays consistent.

Why it matters

A tester for ShopSphere's "Customer Orders" app needs a customer with 0 orders, one with 1, one with 200, one whose email is missing and one whose surname is 60 letters long. Production rarely contains all of these, and copying production brings real names along (see why TDM exists). Because GenRocket's data is manufactured to a rule, you can ask for the odd cases directly and rebuild the same set tomorrow.

The documentation is also frank about the work involved. The FAQ says the harder data-design tasks are assigned to a small group of trained "Test Data Engineers", while testers and developers mainly search for the data they need, deploy it into their test environment and tweak it. The Test Data Workflow page starts from the same person: it says the workflow begins with a Power User, a Test Data Engineer.

One more design choice matters for privacy. The Test Data Projects page says a project contains no customer data. It holds your data model and the five components that describe how to generate data. The architecture diagram (below) labels the cloud part "No Customer Data Stored".

6.2.1 The problem the vendor says it solves

GenRocket's 2020 webinar (the CEO and CTO, with a partner company) opens with the market problem: test automation is spreading fast, but test data is not keeping up. Citing an industry quality report that he names as the World Quality Report, the CEO gives two figures: 69% of organisations use spreadsheets to generate test data, and 59% still create it manually. He adds stories from unnamed customers: a large financial firm with a TDM tool finds the data it needs in production only about a third of the time, and a healthcare insurer's fastest delivery of test data is 34 days. The complaints he hears each week are that data is too slow, does not match the test cases, and is too manual.

These are the vendor's claims: the report, the two percentages (which the talk does not reconcile) and the customer stories are unverified. The 2022 overview video promises the matching fix, cutting days to minutes by replacing spreadsheets and manual methods. Its examples (25 hours of data preparation down to five to ten minutes per cycle, 16 days down to two hours, over 1,200 hours saved in nine months) are also vendor claims, with no method shown.

6.2.2 Traditional TDM versus synthetic test data automation

Both videos describe the contrast; the 2022 video draws it most clearly. The CEO does not call traditional test data management (TDM) wrong. He says it helps with privacy law and faster provisioning, and that GenRocket adds to it. The differences are in the starting point and in what each can produce.

Traditional TDM: copy, mask, subset, refresh

Start from a production database or application. Copy the data, run a masking algorithm to make a secure copy in a lower (non-production) environment, and refresh it from time to time. Testers then search the copy for data that fits their test case. The data is realistic and keeps referential integrity.

The gaps the vendor says its enterprise customers report: no unique data, no negative data (deliberately invalid values), not every permutation and combination, not enough volume, nothing in a required condition, and no dynamic data spanning many applications.

Synthetic test data automation

Start from the metadata (table and column definitions), not the data. The metadata becomes a test data project that acts as the template. It is versioned (version 1, version 2) and lifecycle-managed so it follows the application. Against the project you build test data cases for unit, integration, load and performance tests, and negative cases. Each gives realistic data with referential integrity plus the variety that copies lack.

The 2020 webinar adds that "query generators" can still blend a few real production values, such as an account number, into generated rows.

"Stateful" data, one of the gaps, is data in a particular condition that a workflow needs; for ShopSphere, an order already shipped whose payment has settled. On masking, the CTO said in the 2020 Q&A that when GenRocket moves production data to staging it replaces sensitive columns with synthetic values instead of obfuscating them. The help centre also lists masking receivers and an in-place masking project type (sections 6.8.2 and 19.3.9), so check the current product. The concepts are in the chapters on subsetting, masking and generation.

The five-component page adds a small note: the components can also be managed through the Runtime Application Interface (API). The CI/CD page, quoted later, uses that to change a scenario while a pipeline runs.

Worked example: one customer row

Take the ShopSphere row 1001 | Asha | Menon | asha.menon@example.com | 9876543210 | 123-45-6789 | 1990-04-12 | 560001 from the earlier chapters. In GenRocket terms: the domain is CUSTOMERS. The attributes are customer_id, first_name, last_name, email and so on. A generator on first_name produces "Asha" (then a different name for the next row), a generator on customer_id counts 1001, 1002, 1003. A receiver writes the lines into a file. A scenario says "make 3 of these". Every value is fake, so the row can go to any test environment.

6.3.1 The five components in plain words

The 2020 webinar explains the same five pieces before any demo, and its wording is a good way to remember them. A domain is a noun: a person, place or thing, such as organisation, department, user or address, with no limit on how many or how they are arranged. Its attributes are its characteristics (name, password, phone number, date of birth, card number). Each attribute gets a generator, and a generator has parameters that control exactly what comes out; a name generator, for example, can be told to give first, last, male or female names, and the CTO says its lists allow around 40 million combinations. A generator's output is raw, unformatted data, and the receiver formats it. The scenario is the instruction set that runs and produces the data. His rule of thumb is one scenario per domain, linked into a chain with a loop count each; section 6.25.7 works through his example with the arithmetic.

6.5 Architecture: a cloud for design, your machine for generation

The Architecture page says GenRocket is built on a hybrid architecture. The cloud component is where synthetic data is modelled and designed. The on-premise component is where synthetic data is generated locally. The cloud itself is offered as a Virtual Private Cloud (VPC) or a Dedicated Private Cloud (DPC).

Read the diagram from top to bottom. A designer logs in to the web platform and builds the design. The design is then sent to the customer side as an encrypted scenario file. On the customer side, the runtime runs it and writes data into databases and files that never leave your network.

Why it matters

For a bank or hospital, the question "does our data leave the building?" decides whether a tool may be used at all. In this design, the cloud holds only the design (a data model and rules, not data). The only place rows are created is on a machine you control. Compare this with a masking tool (Informatica masking chapter), where real data is read and transformed.

The Architecture page links onward to security, team permissions, the runtime overview and "G-Repository", the component that keeps scenarios and configuration files synchronised across a company's machines. It also offers a downloadable PDF, "Components and Ports Configuration Guide", for deployments.

6.5.1 What the 2020 webinar adds to the architecture

In the webinar the CTO and CEO describe the same hybrid design in plain terms. The CEO lists the hosting choices as on-premises, a dedicated private cloud, and a virtual private cloud (VPC), and says about 90% of customers use the VPC; the current docs name the VPC and the dedicated private cloud. In the live demo the CTO builds a project, a domain and a receiver in the cloud, then downloads the result as an encrypted scenario. The file stays the same size (22 KB in his demo) whether it generates one row or a billion, because it holds instructions, not data. He runs it with the runtime, a set of Java programs, so it works on any machine with Java: Windows, Linux, Mac and even some mainframes. The CEO's conclusion is that all generation can happen on a test automation server inside the corporate network, which is what the "No Customer Data Stored" label in the diagram above means.

Speed, scale and patent: the vendor's claims

The 2020 webinar claims that a typical automated test case gets its data in about 100 milliseconds, that a run reaches thousands of rows per second, and that parallel runs produce millions or billions of rows in minutes. The CTO adds that importing metadata for 10,000 tables of 100 attributes takes around eight minutes. For contrast, the help centre says JDBC inserts average about 4,000 records per second (section 6.23.5). Real speed depends on the receiver, the database and the machine.

Both videos say GenRocket holds the only patent for synthetic test data generation (the 2020 webinar dates it to 2017). That is the vendor's statement.

6.6.3 Profiles: how the runtime knows who you are

A scenario file is encrypted and tied to your organisation. To run it, the runtime must find a profile file (extension .grp) in a hidden folder named .genrocket in your home directory. The profile ties the machine to a GenRocket licence.

ProfileUsed for
User ProfileEvery person who runs the runtime. It matches the scenario to your organisation and checks that you have an enabled account
Server ProfileA server with no particular person, typically a CI/CD machine. An organisation administrator must first add the server in the web platform

Both are downloaded from the web platform. Whenever a resource value changes, the docs say you must download your profile again and replace the old one.

6.6.4 Port 443, online mode and the offline certificate

The runtime runs in online mode by default: when you run a scenario, it contacts GenRocket Cloud over port 443 to confirm the licence. The "Verify Port 443" page gives a quick test: open https://app.genrocket.com/license/check in a browser, or run curl on the same address. If the port is open you see a short JSON message saying a valid user or server was not found. That odd-looking "failure" is the proof that the connection works.

If your company blocks that port, the docs offer an offline certificate: download a file from the web platform, put it in the .genrocket folder, and run scenarios without internet. The certificate is specific to one organisation and lasts 24 hours, so you download a fresh one each day.

Offline certificate pitfall from the docs

If the home directory stored in your resource.home.directory resource does not match the machine's real home directory, you get "Unable to validate license". The fix on the page is: correct the resource value, download the certificate again and retry.

6.6.5 Setting it up: the shape of the steps

The outline of the Windows setup follows; folder paths and exact variable names belong to the vendor page for your system.

  1. Check the prerequisites.

    An active user account, the cloud address reachable on port 443, admin rights, and Java installed.

    What you should see: java -version prints a supported version.

  2. Download the runtime zip from the web platform (Options menu) and extract it into your home directory as a folder named genrocket.

    The page warns against a nested folder such as genrocket\genrocket-3.5.x.

    What you should see: a genrocket folder with bin and lib inside.

  3. Set the environment variables, open a new terminal and run genrocket once.

    The first run downloads the other jars into lib and creates the hidden .genrocket folder.

    What you should see: no error. "genrocket is not a recognized command" means the folder name, home variable or PATH is wrong.

  4. Download your user profile into .genrocket and fill in your organisation resources.

    Resources hold folder paths for home, JDBC configuration and output (enter N/A for JDBC if you connect to no database).

    What you should see: a .grp profile file in .genrocket and your own paths in the Resources pane.

Typing genrocket alone, or genrocket -h, prints the runtime's command-line options for your version.

6.6.6 Updates, Docker and Jenkins at overview level

Updates. A full runtime update replaces the whole genrocket folder; a jar-only update is done from the command line. Release notes say which is needed.

Docker. GenRocket provides a Docker image you download from the web platform and load with docker load. A container forgets everything when it stops, so you mount host folders for the runtime, scenarios, configuration files, the .genrocket profile folder and the output.

Jenkins (continuous integration). Jenkins is a popular tool that runs build and test jobs automatically. The Windows and Mac/Linux Jenkins pages run a scenario as a build step. The outline: install the runtime on the Jenkins server and set the variables where Jenkins reads them (builds do not see your personal environment); register the server in the web platform and download its Server Profile into the server's .genrocket folder (no person is logged in on a build server); then create a Freestyle job whose build step first runs bare genrocket to prove Jenkins can find it, and then genrocket -d -r SCENARIO_NAME.grs. You should see a SUCCESS message in the console and your files in the output folder. Section 6.25.10 shows how the 2020 webinar combines this with Selenium tests.

The CI/CD page adds two ways to trigger generation from a pipeline: a shell or batch command running the runtime, or a REST request to a GenRocket server component. It also describes Java and REST APIs that let a pipeline create or modify a scenario in real time, for example to change a loop count (how many rows) per test.

Not covered here

Linux and Mac setup, the multi-user server, G-Repository administration and API method details are separate topics in the help centre and are not described here.

6.8 Projects, project versions and categories

6.8.1 What a project is, and how many you need

A Test Data Project contains the data model for one application or database you want data for. It contains aspects of your model (domains, attributes, generators, receivers, scenarios) but no customer data. This is also the unit of licensing: the Test Data Projects page says GenRocket is licensed based on the number of projects a customer needs.

The page's way to count: list the applications and databases you are testing. Database size, complexity of related tables, unrelated functions and special message formats may split one into several projects.

  1. Open the Projects pane in the Project Dashboard and click New Project.

    If you cannot see this button, the docs say you lack permission; ask your organisation's administrator to assign the right role.

  2. Enter a name, a type if offered, and a description.

6.8.4 Project versions

A project is born with a version numbered 1.0. A new version is normally created when the release your domains and scenarios test goes to production, and the next release needs testing. Each version has its own domains, receivers, scenarios and configuration.

There are two ways to make one, both from the Manage menu in the Project Versions pane.

New Version

6.11 Common mistakes and gotchas

Common gotchas
  • Expecting data to appear in the web platform. The cloud holds designs, not data. Rows are created only when a downloaded scenario runs under the runtime on your machine. The "Preview" you see in the web platform is a sample for checking configuration.
  • Forgetting the profile. Without a valid .grp profile (or offline certificate) in .genrocket, the runtime refuses to run. Download a fresh profile whenever a resource value changes.
  • Environment variables set but not picked up. A terminal opened before the change keeps the old values; open a new one.
  • Port 443 blocked. The runtime cannot validate the licence. Use the browser or curl test, then ask the network team or use the offline certificate.
  • Treating the number of generators or receivers as fixed. Docs and videos give different, dated counts. Look the name up in your version.
  • Creating a new project for every release. Use a new version; project count is a licensing unit.
  • Confusing the five components with the four phases. See the warning in the four-steps section.

6.12 Recap

Key points
  • GenRocket makes synthetic data from a model: no production rows are copied, and projects contain no customer data.
  • Five components do the work: domain (table or file), attribute (column), generator (value recipe), receiver (output format), scenario (instruction sheet).
  • "Model, Design, Deploy, Manage" is GenRocket's own methodology and the Test Data Automation four-step process; the vendor's videos present it as a demo and their statistics and speeds as claims.
  • Traditional TDM copies, masks, subsets and refreshes production data; synthetic test data automation starts from metadata and adds unique, negative, high-volume and stateful data.
  • Design happens in the cloud web platform; generation happens on your machine with the GenRocket Runtime, which needs Java, a profile, and usually port 443.
  • Docker and Jenkins are two ways to run the same runtime in automated environments.
  • A project is one data model and a licensing unit; a version is one release of it; categories help find projects.
  • Roles and teams control who may change what; named users run scenarios on one machine at a time.

6.14 Domains: the tables of your design

6.14.1 What a domain is

A domain "defines real-world objects", a noun such as a person, place or thing. When you model a database, a domain is a table and its attributes are the columns. The docs' own example has four tables, Company, Department, User and Address, each becoming a domain with its columns as attributes. At least one domain must exist in a project to generate any data.

A domain inside a project version is a template: it holds the attributes, generators and relationships. When you create a scenario, GenRocket copies the template into a scenario domain. Changes you make to the template cascade down to every scenario unless the scenario (or the scenario domain) is locked. It is like a letter template, except that you can pin a printed letter so later edits leave it alone.

The docs also state a rule: a template domain works independently and cannot really reference another domain's attributes. Relationships at the domain level are "just probable". The real references are made at the scenario level, where related domains are put together. You will see this again with ProxyReferenceGen below.

Each time a domain is created or imported, it gets three default variables, all initially 1 (details below): id, loopCount and seed.

The "New Domain" page says a domain name should contain only letters and numbers (spaces are now also allowed), so ORDER_ITEMS becomes a domain named OrderItems with ORDER_ITEMS in the Table Name field. The page does not say what happens with an underscore.

6.14.6 Importing a live database schema (XTS)

"XTS" stands for Extract Table Schema. This is the documented way to pull a database's structure straight from the database. Two steps:

  1. Extract the schema with the runtime.

    Run the runtime's -xts option with the path to a JDBC properties file and, optionally, the table names (genrocket -xts /path/config.properties company,department,user). With no names, every table is extracted. Options exist to exclude tables (-xt, -xf), and tables in a specific schema are written schema1:tablename. The properties file holds four required entries: driver, user, password and url.

    What you should see: an encrypted schema file, tied to your organisation. The page calls it a schema extract; it does not say more about what is read.

  2. Import the file with the XTS Import Wizard.

    Open Self Serve Options then XTS Wizard (or choose Import from XTS in the New Domain menu), choose the file, optionally enable Enforce Type/Limit, click Save and wait. The project is frozen until the import finishes.

    What you should see: domains, attributes and generators created for every extracted table, and the wizard's step 1 ready to be marked completed.

Each step has its own wizard that works on many domains at once, because the setup after importing hundreds of tables is also repetitive; you tick each step as complete so that the next unlocks.

ShopSphere: which method?

ShopSphere has three tables. If the team gives you CREATE TABLE scripts, a DDL import takes minutes and keeps the primary key and sizes. If you can reach a dev copy of the database with a read-only account, an XTS extract avoids typing anything. Either imports a schema, not rows.

6.15 Relationships: parent, child and sibling

Real tables point at each other: ORDERS.customer_id is a foreign key to CUSTOMERS (data basics chapter). If you generate 50 customers and 80 orders with random customer numbers, some orders will point at customers that do not exist, which breaks referential integrity. GenRocket's answer is to generate data in order, from parent to child, so a child can only pick a key a parent has already made.

The documentation says GenRocket "generates synthetic data with full referential integrity" because every domain has an id or primary attribute, and children refer to the parent's primary attribute. It also says GenRocket looks at relationships differently from a database. A database table can have several foreign keys. A GenRocket domain may have only one parent but many siblings, because generating sequentially along several parents would produce "a large amount of unnecessary data".

The scenario page adds a vocabulary pair: the primary domain is the one a scenario is created for, and the root domain is the first parent up the chain. For an ORDER_ITEMS scenario, ORDER_ITEMS is primary and CUSTOMERS is root, so the scenario creates customers, then orders, then items, and every key matches.

Why it matters

Valid foreign keys are the reason a test can load generated data into a real database and not see constraint errors. The principle (parents before children) is in the generation concepts chapter; GenRocket builds it into the domain model.

6.18 Generators: the recipe for each value

A generator creates synthetic data (or queries existing data) for one attribute. Every attribute needs one. GenRocket advertises over 765 generators (a growing number), grouped by purpose and, for many countries, by country. Generators produce raw values only; receivers format them (receivers and scenarios chapter).

6.18.1 How a generator gets assigned automatically

You rarely pick generators from scratch. For each new or imported attribute GenRocket tries these steps in order, according to the "How are Generators Assigned" page:

  1. Is there a matching Project generator tag? If yes, use it.
  2. Otherwise, a matching Organization generator tag?
  3. Otherwise, an intelligent guess from the domain name, attribute name, the project's industry type and usage patterns of other users. If Enforce Type/Limit is on, the column's type is considered too (a date column gets FlexibleDateRangeGen, a uniqueidentifier gets UUIDGen).
  4. If nothing fits, SimplePatternGen, which builds a value like name1, name2, name3 from the attribute name and the row's id.
Treat SimplePatternGen as a to-do marker

It generates values like street1, which are unique but not realistic. When you see it on an attribute, the tool could not guess; pick a better generator. The Project Version status report flags attributes without a generator.

6.18.6 Seeding: repeatable randomness

If two runs of a "random" generator give different numbers, test failures cannot be reproduced. A seed fixes this: with the same seed, a generator gives the same set every run. A seed can be set on an attribute's generator or through the domain's seed variable (button Global Seed applies it to the whole domain). The data patterns chapter shows the docs' example.

6.18.7 Linked generators

One attribute can hold several generators in a row (gen1, gen2...). They run left to right, a generator may use any generator to its left, and the last one gives the value. The docs' example builds a full name in a single fullName attribute: NameGen, AlphabetGen (middle initial), NameGen (last name), then ConcatGen joining the three. Without linking you would need four attributes and would have to hide three of them with Visible turned off.

6.18.8 ReferenceGen and ProxyReferenceGen: how a child finds its parent key

This pair is the mechanism behind foreign keys, and it confuses everyone once. The docs explain it as follows.

ProxyReferenceGen (domain level)

A placeholder. Because a template domain cannot see another domain, the foreign-key attribute holds this generator, whose only parameter is startRange (default 1000). It marks "a parent's key goes here".

Assigned automatically when you import with DDL or XTS and the column has a foreign key.

ReferenceGen (scenario level)

The real thing. When a scenario is created and the parent relationship exists, GenRocket swaps the proxy for ReferenceGen. Its one parameter reference points at the parent's primary attribute, such as #{AddressScenario.User.id}.

It can also be set up manually, as in the docs' "User and Address" example.

This is why the project version status report flags "foreign key attributes that do not have the ProxyReferenceGen": without the proxy, the child will not find its parent when a scenario is made. The referenced attribute is the parent's primary attribute; to target another column, tick its Primary checkbox.

6.18.9 Enforcing data type and size

A generator does not know that first_name is varchar(5) unless you tell it. The Enforce Type/Limit option makes the generator keep values within the attribute's Type and Size. It is on automatically for generators assigned by a DDL or XTS import, can be enabled for a whole project version when you create it, and can be set manually per generator. The docs list integer limits it applies, for example 127 for tinyint, 32767 for smallint and 2147483647 for int.

  1. Open the attribute, set Type (for example varchar) and Size (for example 5) and save.

    These tell GenRocket the limits.

  2. Tick Enforce Type/Limit in the generator section and save the generator.

    What you should see: the preview now shows names of at most five characters.

6.18.10 Primary keys after the current maximum

When you insert into a table that already holds rows, new keys must not collide with old ones. The docs' recipe links two generators in the id attribute. gen1 is QueryOnceGen with resourceName pointing at the JDBC resource, query = select max(id) + 1 from <tableName> and a sampleValue (5001 in the example) used for previews. gen2 is RangeGen whose startRange references gen1.

The General FAQ adds a second pattern: write the parent's ids to a delimited file as you insert, then read them back with ListCSVGen at scenario level so the keys match.

6.18.11 Inside a few generators, as shown in the 2020 demo

The CTO opens individual attributes to show that every generator works the same way: parameters decide its behaviour. Each example below is followed by what the docs say.

  • A counter (RangeGen). The id uses a range generator with a start, an end and a "jump". Starting at 1,000 it counts 1000, 1001, ...; setting the jump to 3 makes the preview step by 3. The RangeGen page confirms startRange, endRange and jumpAmount, and that with no end it runs to the largest long number.
  • Names (NameGen). He says the name generator draws on lists of first, last, male and female names for about 40 million combinations. The NameGen page confirms this and gives the list sizes (1,000 male, 3,000 female, 10,000 last names).
  • A constant plus the id (ConcatGen). He replaces the username generator with a concatenation generator, types the constant "user" and picks the id attribute as the second part. The ConcatGen page builds BR01-1000 the same way, from a constant and a RangeGen value.
  • A hashed value. He passes the id through an MD5 setting and the hash appears at the end of each output row. A hash is a one-way scramble: the same input always gives the same output, but the output cannot be turned back into the input. The EncryptGen page lists MD5, SHA-1, SHA-256, SHA-384 and SHA-512.
  • SSN and card numbers. He says the SSN generator avoids numbers that are never issued, such as area number 666 The SSNGen page does not mention such a rule, so check the preview. For cards he picks Discover, MasterCard and Visa and says the numbers pass the Luhn check, the checksum formula payment forms use to catch mistyped numbers. The CreditCardGen page confirms Luhn-valid output and one on/off parameter per card brand. Luhn-valid does not mean real: no person owns these numbers.

6.18.12 Linked generators and "patterns, not randomness" in the 2020 Q&A

Asked how to generate values defined by a regular expression, the CTO answers in three parts. A regular-expression generator exists for that. More broadly, he says most generators do not produce random data, because random data is not good for testing; they produce patterns, and because linked generators can talk to each other, simple patterns combine into complex data. His examples are if/then/else, case, switch and a multi-way generator that works in percentages. For very complex rules there is a separate feature, test data rules, which takes if/then/else conditions. The docs name matching generators (IfThenElseGen, EvalCaseGen, SwitchGen, MultiWeightGen, StringRegexGen; see section 6.18.5) and describe test data rules (G-Rules) as the condition-based alternative. 6.20 Common mistakes and gotchas

Watch for these
  • Expecting a DDL import to set relationships. It does not. Run the Domain Referencing Wizard.
  • Giving a table several parents. Use one parent and mark describing tables as siblings.
  • Referencing an attribute below the current one. The value is empty. Reorder first.
  • Leaving SimplePatternGen in place. It means no better guess was found.
  • Forgetting Enforce Type/Limit. Values may not fit the target column.
  • Forgetting that a new domain's loopCount is 1. A first run gives one row.
  • Using ListGen for large lists. It supports up to 15 values. The docs recommend ListCSVV2Gen or another file-based list generator for more. ListCSVGen loads the whole file into memory.
  • Exhausted unique values. RandomGen with a small range and uniqueLimit 1 stops with "Exhausted attempts to find the next valid random value" when the loop count is too high (the page's own example is a range of 1 to 20, a limit of 1 and 20 rows). Widen the range, raise the limit or lower the row count.

6.21 Recap

Key points
  • A domain is a table (template), an attribute is a column, and each attribute needs a generator.
  • Create domains by hand, with Scratch Pad, from DDL, or from a database with XTS. Imports do not set relationships or receivers.
  • Each domain has three variables: id, loopCount and seed.
  • One parent, many siblings. Parents generate first, so child foreign keys always find a parent.
  • ProxyReferenceGen is the domain-level placeholder; ReferenceGen is the scenario-level real reference.
  • GenRocket assigns generators by tags, then by guess, then SimplePatternGen. Replace them one at a time or in groups.
  • Seeds make random data repeatable; linked generators build complex values; Enforce Type/Limit keeps values inside column limits.
GenRocket: receivers and scenarios

Besides describing the data (domains, attributes and generators), two jobs remain: say what format the rows must arrive in, and say how many of what, in which order. The first job belongs to receivers, the second to scenarios. Once both exist, you download the scenario, run it with the GenRocket Runtime, and files or database rows appear.

Receivers come first (the common ones in detail, the rest by family), then scenarios, scenario chains and related controls, an end-to-end ShopSphere build and a troubleshooting table. Patterns and the 50-record exercise are in the data patterns chapter and the GenRocket hands-on chapter.

6.23.4 Output folders: organisation resources

Receivers do not hold a user's folder name. They use resource references. A new account has three: resource.home.directory, resource.jdbc.directory and resource.output.directory (the dashboard screenshot in the overview chapter shows them). The resource page recommends the home directory be the real home folder, and the other two be different folders, preferably sub-folders of home, because using the same path for all three can cause errors "or, in some cases, a process that never finishes". 6.23.5 Configuration files, V2 receivers and bulk load

  • Configuration file. A file that tells a merge receiver how to combine data from different domains into one nested output. It defines file name segments, the segment files and the element layout. It is created in the Configuration Management tab and its name goes in the merge receiver's configName. Some imports (JSON, XML) create one for you.
  • V2 receivers. Names contain "V2" just before "Receiver", for example GenericSQLInsertV2Receiver. They add two parameters, resourcePath and resourceSubDir, so a receiver can point to different configuration folders without creating more global resources. The vendor says V1 receivers will eventually be hidden from the picker; scenarios that already use them keep working.
  • Bulk load receivers. Inserting through JDBC averages about 4,000 records per second, according to the page, which is slow for millions of rows. Bulk-load (partition) receivers write the database's native bulk-load file format instead. The page lists receivers for MySQL, Oracle, PostgreSQL, MS SQL, DB2, Sybase, Snowflake, Databricks, Parquet and delimited files.

6.24.7 Writing straight into a database: the JDBC receivers

GenericSQLInsertReceiver inserts generated rows directly into a table through JDBC. Its parameters include resourceName* (the resource that points to the connection information), databaseName*, tableName*, truncate*, statementSeparator*, nullValue* and quoteTextData*. Property keys are columnName, columnType and include. The newer GenericSQLInsertV2Receiver adds resourcePath, resourceSubDir, continueOnError and logErrorDetails. The V2 page says it suits "up to 10,000 rows into a table with 25 columns or fewer", and recommends the GenericSQLInsertThreadReceiver for larger loads.

truncate empties the table

The V2 page warns that its truncate parameter can truncate or delete all existing rows before inserting, and that this cannot be undone. The default is "notApplicable" (nothing deleted). Never point a truncating receiver at a database you have not backed up.

Direct database receivers need a JDBC configuration file (config.properties) on the machine running the scenario. It holds driver, user, password, url and, for receivers, batchCount. Its folder comes from resource.jdbc.directory. You can check a connection with the runtime's --test-jdbc option before running a scenario.

Update receivers. SQLUpdateReceiver runs batched UPDATE statements whose values come from attributes (up to 20 attributes mapped to variables var1 to var20), which is the basis of replacing real values with synthetic ones in a table. SQLBatchUpdateReceiver reads one or more update statements from an XML configuration file that can address several databases, using placeholders such as #{firstName}. The FAQ also names StoredProcedureCallReceiver for calling procedures, while the FAQ says SQLUpdateReceiver can run DDL and DML scripts before or after a load, and another page uses SQLUpdateV2Receiver to create a database table.

6.24.8 Nested data: segment-and-merge receivers (overview)

JSONFileReceiver and XMLFileReceiver are flat. For nested output (customers containing orders containing items) GenRocket uses two receiver types together:

  1. Add SegmentDataCreatorReceiver to each domain except the merge domain.

    Each domain writes its rows as a small XML "segment" file, tagged with its parent's id so relationships survive.

  2. Create a merge domain and add a merge receiver, such as JSONSegmentMergeReceiver or XMLSegmentMergeReceiver.

    The merge receiver reads the segments and the configuration file, and writes nested files. Others exist for Avro, Parquet, delimited, fixed, EDI, HL7, SWIFT and SOAP.

  3. Put the merge scenario last in a scenario chain, create the configuration file, and download both.

    Merging only works once every segment exists. Imports of JSON, XSD and some other models set most of this up for you.

The JSON merge page lists parameters such as outputPath, configName, segmentPath and recordsPerFile. If the root domain's loop count is 50 and recordsPerFile is 8, seven files are made (six with 8 records, one with 2). The vendor pages walk through a full nested build.

6.24.9 Masking receivers (overview)

GenRocket also masks: it replaces sensitive values with synthetic ones, a method the file-masking overview calls Synthetic Data Masking (SDM). The file-masking receivers take an existing file and write a new one with the targeted values replaced: DelimitedFileMaskReceiver, ExcelFileMaskReceiver, JSONFileMaskReceiver, XMLFileMaskReceiver, ParquetFileMaskReceiver, ORCFileMaskReceiver, EDIFileMaskReceiver and FileMaskMultiBlockReceiver (fixed files such as VSAM). The same documents describe database masking in place (IPM). The vendor states that production data is never sent to GenRocket, since only metadata is used. How this compares with masking in other tools is in the Informatica masking chapter and the masking concepts chapter.

6.25 Scenarios

6.25.1 What a scenario is

A scenario contains instructions that tell the GenRocket engine what synthetic data to generate and how much. You select the domains, say how many rows each produces, decide their order, download the scenario to a computer, and run it with the runtime. Domains, attributes, generators and receivers are its building blocks, so all four must exist first.

A scenario is for one primary domain. If the primary domain has parents, the scenario pulls them in as helper domains so that foreign keys are valid: a scenario for Address with parents User and Department also creates departments and users. To output data for several related domains, create a scenario per domain and link them in a chain (below). The docs recommend a scenario for every domain, except pure helper domains.

6.25.4 Scenario domains, relationships and locks

A scenario holds copies of template domains (scenario domains). Template changes flow into scenarios unless the scenario, a scenario domain or an attribute is locked. A lock stops changes made higher up from cascading down; while a scenario is locked the Sync button is hidden, and a locked item cannot be deleted. Use Sync to pull in template changes deliberately.

You can also change a relationship for one scenario only, leaving the template alone. The vendor's story: for the Student scenario, make Teacher the parent of Student instead of Subject. The steps are to add the Teacher domain to the scenario, remove the Student domain's current parent, and add Teacher as its parent. Changes at scenario level do not flow back up. Relationships cannot be changed at the test data case level, so this is the place to do it.

6.25.5 Scenario variables and scenario state

Variables. Scenario variables are name-and-value pairs usable only inside the scenario that created them. In the Scenario Variables pane click New Variable, give a name and value and save, then reference it from a parameter (double-click the parameter field and pick it).

State. Normally every run of a scenario produces the same data, for example a RangeGen starting at 10000 starts there every time. Sometimes you want the next run to continue (ids 10000 to 10099 first, then 10100 and on). Clicking Make Stateful saves each generator's position at the end of every successful run; Make Stateless turns it off. By default scenarios are stateless. The state is kept in a small H2 database in the .genrocket folder of the machine, and two runtime options list or clear it: --state-list and --state-clear (with an id or all).

6.25.7 Worked example: how loop counts multiply along a chain

In its 2020 webinar, GenRocket's CEO explains chains with a three-level example: Organization, Department and User, with one scenario per domain, linked so that every user belongs to a real department and every department to a real organization (referential integrity). Each scenario has a loop count, and a child's count applies to every parent row, so the numbers multiply down the chain.

6.25.8 Running a scenario with the runtime

The scenario file is run from a command window on a machine that has the runtime and your profile.

  1. Download the scenario (or chain).

    The Download button on the dashboard, or the cloud icon in the Scenarios pane. Several scenarios can be downloaded together as a ZIP with Batch Download (up to 15).

  2. Open a command window or terminal in the folder where the file was saved.

    The command needs to find the file.

  1. Run genrocket -r <ScenarioName>.grs.

    The -r option means "run". Chains use the same command.

    What you should see: lines saying the licence was validated, the runtime versions, "Running Scenario ..." for each scenario, and finally "All done!" with the elapsed time.

When data is inserted into a database and loading fails, the runtime throws an exception to the command line (or to the testing framework when it runs in an automated pipeline), so no error means success. The vendor's note on stopping a run: press Ctrl+C, and on Windows answer the "Terminate batch job (Y/N)?" prompt with Y to abort.

The 2020 webinar's live demo shows a simple way to check a run. The CTO builds a user domain with an XML receiver, downloads the scenario (about 22 KB, and he points out it would stay that size whether it generates one row or a billion, because it holds instructions, not data), and runs it from a command line with the Java-based runtime. He then opens the XML output and checks that the ids start at 1,000 and rise by one, as the id generator was set to do, that the other values follow their generators' patterns, and that scrolling to the end shows 10,000 rows, the loop count he had set.

Scenarios can also be run through a repository server or an API, which are not covered here. Section 6.25.10 shows the command inside a pipeline.

6.25.9 The Scenario Thread Engine (overview)

The thread engine speeds up chains and chain sets by running several of their scenarios at the same time: genrocket -r Chain.grs -threaded 10. The docs caution that threads may run in any order, so use it only where order does not matter, for example many segment files that a merge receiver combines later (the engine waits for every segment before merging). Do not use it where SQL inserts depend on parent rows already being present, because the order matters for referential integrity.

6.25.10 Scenarios inside an automated test pipeline

Later in the 2020 webinar, the CEO plays a short vendor video about combining GenRocket with Jenkins (a tool that runs jobs automatically) and Selenium (a tool that drives a web browser to run functional tests). The point is that data is created at the moment a test needs it, not prepared days earlier. In plain steps:

  1. A Jenkins job starts.

    A trigger such as a build normally starts it; the video starts it by hand.

  2. The job opens a shell and runs GenRocket against a test plan.

    A test plan here is a set of scenarios to work through, so one command covers the whole run.

    What you should see: the Jenkins console showing the test plan loading and executing.

  3. When a test needs data, GenRocket generates it.

    Each test gets fresh data shaped for it, not a shared set that earlier tests may have changed.

  4. GenRocket then calls a Selenium step that performs the functional test.

    The test consumes the data it was just given.

  5. The data can be cleared, and the next test gets fresh data.

    The CEO says it need not sit around; in the 2022 overview video he adds that the transaction can be rolled back before the next test case runs.

The Jenkins page in the help centre (see the overview chapter) runs one named scenario per build step; the test-plan runner in the video is not documented on those pages, so check the current documentation before copying this layout.

Where should the runtime run when the test servers are in the cloud?

A viewer asked about cloud-hosted applications in the 2020 webinar's Q&A. The CTO's answer: for a quick data set on your own computer, download the scenario and run it with the local runtime (two or three minutes, he said, against an hour of hand-written Python or Groovy). For a full regression suite on a cloud test server, such as one on Amazon or Azure, install Java and the GenRocket jars on that server and generate the data there. Do not generate it elsewhere and carry it up, because that is slow and moves a lot of data into the cloud. The rule of thumb is: run the runtime where the tests run.

The build below uses the design from the domains, attributes and generators chapter. SQLFileInsertReceiver is used for orders because it needs no database connection.

Lab: one chain, two outputs

Goal: produce Customers.csv with 50 customers and Orders.sql with 100 insert statements whose customer_id values all exist in the CSV.

  1. Check your resources.

    In the Resources pane the home and output directories must point to real folders on the machine that will run the scenario, and your profile must be in .genrocket. If you change one, download the profile again.

    Expected: three resource rows with paths (JDBC may be N/A).

  2. Add a DelimitedFileReceiver to the Customers domain.

    Set fileName to Customers.csv, delimiter to a comma, includeHeader True, quoteTextData None, appendToFile false. Leave path as the output resource.

    Expected: the receiver appears in Domain Receivers.

  3. In its Attributes Property Keys tab, set columnName to the table's column names.

    Set the id, names and other columns to customer_id, first_name and so on, so the CSV header matches the source database. Set include false for anything the consumer does not want.

  4. Add a SQLFileInsertReceiver to the Orders domain.

    Set tableName to ORDERS, fileName to Orders.sql, batchCount 100, statementSeparator a semicolon, quoteTextData Single, nullValue NULL, appendToFile false. Set the column names to order_id, customer_id, order_date and total_amount.

    Setting useQuotes false on the numeric columns is a reasonable choice, but the vendor page only says "sometimes a numeric value should be quoted".

    Expected: the property-key tab shows the real column names.

  5. Create the scenarios.

    Use Quick Scenario on Customers and on Orders. The Orders scenario brings Customers in as its parent. Both will normally have their receivers, so in the Orders scenario open the Scenario Domain Receivers pane and disable the Customers receiver (or use Disable Non-Primary Receivers), so the CSV is written once, by the Customers scenario.

    Expected: the Orders Scenario Dashboard lists Customers and Orders, with Orders as primary and Customers as root.

  6. Set the row counts in the Scenario Domains table.

    Customers: 50. Orders: 2, meaning two orders for each customer, so 100 in total.

    Expected: the summary for Orders reads like "2 Orders For Each Customer" (the product's wording).

  7. Create a chain called ShopSphereChain with CustomersScenario first and OrdersScenario second, then download it.

    Order matters: parents first.

  8. Run genrocket -r ShopSphereChain.grs from the download folder.

    Expected: "Running Scenario CustomersScenario", then "Running Scenario OrdersScenario", then "All done". Output folder holds Customers.csv and Orders.sql.

Show how to check the result

Open the CSV: it should have a header and 50 rows with customer ids from 1001 to 1050 (if the id variable was set to 1001). Open the SQL file: it should contain 100 insert into ORDERS(order_id,customer_id,order_date,total_amount) values (...) lines whose customer_id values lie between 1001 and 1050, and every customer should appear twice. If you load both into a test database, load customers first so the foreign key is satisfied. (Load order is general database practice, not a documented GenRocket feature.) A header row in the CSV needs includeHeader true; if the Excel viewer shows a single column, the delimiter is wrong.

Variation: insert straight into a database

Replace the SQLFileInsertReceiver with GenericSQLInsertV2Receiver. Create a config.properties file with the connection settings (driver, user, password, url, batchCount) in the JDBC resource folder, set the receiver's table settings, leave truncate on "notApplicable", and put the JDBC driver jar in the runtime's lib folder. Test with --test-jdbc, then run the chain. This needs a database and credentials from the DBA.

6.28 Common mistakes and gotchas

Watch for these
  • Changing a receiver or loop count and re-running the old file. The scenario file is a snapshot. Download it again after every change.
  • Wrong chain order. Children before parents means keys do not exist when you load the data.
  • Column names that do not match the database. In SQL receivers, columnName must be the real column.
  • Parent data written twice. A child scenario brings its parents in; disable the non-primary receivers if you only want the child's file.
  • Truncating a table by accident. Leave truncate on "notApplicable".

6.29 Recap

Key points
  • A receiver turns generator output into a format. Sixteen categories, 120+ receivers; more than one can sit on a domain.
  • Receivers use organisation resources for folders. Download your profile again whenever a resource changes.
  • Delimited, fixed, JSON, XML, Excel and SQL-file receivers cover most needs; segment-and-merge receivers make nested output; masking receivers replace values in existing files.
  • JDBC receivers insert directly and need a JDBC config file; V2 adds resource path settings; bulk-load receivers are for very large volumes.
  • A scenario is built for a primary domain and pulls in its parents. A child's loop count is per parent row.
  • Download, then run with genrocket -r. Chains run several scenarios in order. Locks, state and variables control behaviour between runs.
  • Loop counts multiply down a chain (3 organizations x 3 departments x 3,000 users = 27,000 in the 2020 webinar), so work out the expected row count before you run, then compare it with the output.
  • In a pipeline, run the runtime where the tests run, generate data when a test needs it, and clear it afterwards.
  • When something fails, the commonest causes are a missing profile, wrong paths or variables, relationship or ordering mistakes, and Java memory settings.
